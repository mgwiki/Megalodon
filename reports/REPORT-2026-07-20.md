## Executive Summary

The original project goal remains:

```text
For Megalodon theorems exported as THF/TPTP:
  run Vampire with a per-problem timeout of at most 10 seconds;
  emit detailed Vampire proof certificates;
  reconstruct those certificates as native Megalodon proof terms;
  check the reconstructed proof in the original Megalodon source context;
  use no aby, no admit, no incomplete QED, no bridge assumptions,
  no certificate-derived hidden Known theorem, and no Python proof engine.
```

That goal is not yet complete.

The best current positive result is narrower. A focused detached certificate
for the `UnionI` theorem now passes strict native certificate checking and
native preprocessing proof-term checking. This is a meaningful exported-problem
result because the example exercises original source facts, set-generated
definitions, classical reasoning, Skolemization/choice, AVATAR splitting, and
the final refutation-to-goal path. However, the same proof does not yet close
as an original Megalodon source theorem.

The active frontier is therefore not Vampire proof search. It is also not
basic certificate parsing. The current frontier is:

```text
Can the checked exported Vampire refutation be composed into the live
Megalodon theorem at the original proof site, with all source names,
local binders, local hypotheses, generated set equalities, Skolem witnesses,
choice principles, and library logical constants resolved to real Megalodon
objects?
```

For the focused `UnionI` case the answer is still no. The detached certificate
checks; the original source command still does not close. Earlier July 20
diagnostics timed out in returned-proof expansion; after the latest returned-
proof expansion refactor, the same probe now gets through returned-proof
expansion, live-basis expansion, proposition-extensionality expansion,
double-negation candidate construction, and refutation replay, and it builds a
local Vampire proof payload. It still times out before the original source
command fully closes.

The latest diagnostic run used only `/project/tmp` and a 10-second Vampire
timeout. The most relevant timings are:


This means returned-proof expansion is no longer the only visible slow path.
It remains expensive, but about 48 seconds of the latest focused run is still

`vampire_certificate_reconstruct_aby_goal`, returned proof application,

The same focused source probe still reports an internal final-refutation bad

## Evidence Classification

The project now uses evidence classes to avoid confusing integration progress
with proof reconstruction.

E1 is the real goal:

```text
Original-context proof reconstruction. A Megalodon theorem is proved at its
original source site by a native proof term reconstructed from a Vampire
certificate. No aby, admit, incomplete QED, bridge assumption, certificate-
derived hidden Known theorem, or Python proof-producing step is used.
```

E2 is exported-problem proof checking:

```text
Megalodon checks a native proof term for the Vampire certificate against the
exported problem or saved certificate, but the result is not yet composed back
into the original theorem command.
```

E3 is focused proof-term evidence:

```text
Synthetic or focused examples exercise one native proof-term elaboration path,
small-kernel rule, or preprocessing transformation fragment.
```

E4 is structural and integration evidence:

```text
Vampire emits data, Megalodon parses it, source maps and roles validate,
metadata is well-formed, or diagnostic harnesses run. This is useful but is
not proof reconstruction.
```

Under this classification:

- The focused detached `UnionI` preprocessing proof-term check is E2-like.
- The live proposition-choice diagnostic is E3/E4 support for a logical-basis
  dependency.
- The broad source-map and certificate validation harnesses are E4 unless they
  construct and check native proof terms and discharge original source facts.
- Older runs that generated scripts with bridge premises, `aby`, admits, or
  hidden known assumptions are not qualifying.
- The project does not currently have a 100-theorem E1 suite.

This evidence discipline is one of the most important audit-driven changes in
the project. Future reports should continue to state which evidence class a
number belongs to.

## User Requirements

The active user requirements are:

- Use Megalodon THF/TPTP export.
- Use Vampire on the exported TPTP input, with THF where needed.
- Do not run Vampire for more than 10 seconds per problem.
- Avoid repeated broad or sequential Vampire runs; use batch export and
  parallel proof generation/checking when broad tests are appropriate.
- Use `/project/tmp` for temporary artifacts and generated diagnostic output.
- Do not use `aby` in any counted result. In Megalodon `aby` is implemented as
  admission.
- Do not use `admit` or incomplete QED in counted results.
- Assume classical logic. The Megalodon library theorem `xm` is available and
  may be used.
- Use Megalodon's own equality, `False`, disjunction, implication, and other
  library logical constants, not private replacement encodings in final proofs.
- Recover original names and facts through the source map and the live
  Megalodon context, not by hardwiring current-library examples such as
  `famunion`, `In`, or `Union`.
- Treat TPTP facts generated from Megalodon `set` commands as generated
  definitional/reflexivity obligations when appropriate, even when they do not
  correspond to explicit source claims.
- Prefer adding exact detail to Vampire certificates over reconstructing
  missing details by uncertain Megalodon-side or Python-side heuristics.

These requirements rule out a pass-count-oriented approach that only lowers
aggregate bridge assumptions. They also rule out a final proof pipeline driven
by Python translation scripts.

## Summary of Work Done

The work has gone through several phases.

The first phase built a Python-oriented translator and proof-skeleton
generator. That was useful for discovering the shape of Vampire output and for
making human-readable Megalodon skeletons with claims. It also helped expose
source-name mangling, proof-step classes, Skolemization issues, and the need
for batch/parallel test infrastructure. But it was not an acceptable final
architecture because it became a second proof reconstruction engine outside
both Vampire and Megalodon's kernel.

The second phase added richer Vampire output. The Vampire fork gained a
Megalodon-oriented certificate path that prints S-expression certificates with
source origins, step roles, parent links, formulas, clauses, equality metadata,
rewrite metadata, Skolem metadata, branch-choice data, and an expanding
`kernel_v1` vocabulary. The current Vampire head is:

```text
6f3977d81 Avoid unsafe backward demodulation replay substitutions
```

The most recent Vampire-side fix disables an unsafe optional
backward-demodulation substitution recording path that could crash after
Vampire had already found a refutation. The certificate path is expected to
use explicit rewrite metadata and real parent information instead of that
unsafe optional replay-substitution state.

The third phase moved the import path into Megalodon. The main implementation
file is:

```text
/project/Megalodon/src/vampire_cert_v1.ml
```

with integration in:

```text
/project/Megalodon/src/megalodon.ml
```

Megalodon now parses the native certificate, validates source maps and source
kinds, checks many structural invariants, reconstructs native `Syntax.pf`
proof terms for supported fragments, and can run focused native
preprocessing-proof checks.

The fourth phase responded to the audits. It introduced evidence
classification, stopped counting hidden bridge assumptions as proof
reconstruction, moved away from generated scripts as the trusted artifact,
and tightened the distinction between structural validation and native kernel
proof checking.

The fifth and current phase focuses on source-context composition. The
frontier is no longer just replaying a detached proof object. The issue is
gluing a checked refutation to the original Megalodon theorem and original
lemmas/definitions.

Recent Megalodon commits in this phase include:

```text
fb562d5 Expand source aliases for local proof context
1fc9c17 Normalize source aliases in native final checks
91c0b99 Speed returned proof expansion diagnostics
```

The first of these expands source-map aliases to live global symbols, local
term variables, and local definitions during source-context handoff. This
moved the top-level source-composition proposition for the focused `UnionI`
case from certificate-local names toward live `In`/`Union` names.

The second adds a source-name alias normalizer inside native final validation
paths. It derives aliases from source-map entries rather than from hardwired
set-library names. It also adds detailed timing markers around the
unchecked-finish path used by the focused source replay, so slow stages can be
localized without broad tests.

The third refactors returned-proof expansion so recursive expansion is raw and
normalization is performed once at proof-term term boundaries instead of at
every recursive node. It also caches expanded live-basis bodies and adds
elapsed timing around returned-proof expansion, unchecked finish, and supplied
refutation construction. This changed the focused source probe from timing out
inside returned-proof expansion to reaching local proof-payload construction,
which exposes a later slow path in source-command closure.

## Current Linking Status

The source-linking story has four layers.

The first layer is source-origin identity. Vampire certificates carry source
names, roles, generated-source kinds, aliases, and source-map entries.
Megalodon validates these entries and rejects many malformed or unresolved
cases. This layer is mostly in place.

The second layer is name recovery. This is now substantially better than in
the audited July 14 state. Source-map aliases are used to recover live names
from exported and certificate-local aliases. The recent implementation uses
source-map entries and alias generation, not benchmark-specific names. For the
focused `UnionI` source command, the top-level composed proposition now prints
with live `In` and `Union`.

The third layer is proposition linkage. This remains partial. The checker can
validate source propositions in detached paths and can compare proof
propositions after local-source localization. The newest commit also
normalizes source aliases inside native final validation. However, the
original source command still shows that some nested proof-context assumptions
are not normalized to live source propositions before final composition.

The fourth layer is proof linkage. This is incomplete. Original Megalodon
lemmas, local hypotheses, and generated definitional facts must be supplied as
actual live proofs, not as source labels or certificate-derived known facts.
The detached `UnionI` check reports two remaining source assumptions: one
known/library assumption and one conjecture assumption. The original theorem
composition must discharge these using the live context and the
refutation-to-goal transformation.

The fifth layer is final theorem composition. This is the missing E1 result.
The importer must take the checked refutation of the negated conjecture and
turn it into a proof of the original theorem under the original local binders
and hypotheses. It must use Megalodon's equality and logical constants, live
excluded middle (`xm`), live source lemmas, and generated set equalities. It
must not use `aby`, `admit`, incomplete QED, bridge assumptions, or hidden
certificate-derived knowns.

## Set-Command Facts and Equality

Some TPTP axioms originate from Megalodon's `set` command rather than from
explicit named `Theorem` or `Claim` declarations. These can be equalities or
definitional facts with no corresponding source proof name.

The correct treatment is:

```text
If a source fact is generated by Megalodon's set machinery and is a
definitional equality, prove it in Megalodon by reflexivity/conversion or the
appropriate generated definition mechanism.
```

It should not be counted as an arbitrary assumed lemma.

The implementation has partial support for this idea. Earlier work around
`Empty_eq` recognized source facts and equality shapes and avoided requiring
every generated set fact to correspond to a user-written claim. This direction
should continue, but it is not complete.

Equality should ultimately be Megalodon's equality. Internal certificate
normalization may use a canonical equality head for parsing or matching, but
the final reconstructed proof should compose against the live Megalodon
equality and its library principles. A private equality layer would be another
bridge and would not satisfy the user's requirement.

## Skolemization and Choice Status

Skolemization is still one of the hardest open pieces.

Vampire introduces Skolem functions and epsilon-like witnesses while proving
the exported problem. Reconstruction is sound only if Megalodon proves the
corresponding transformation from the original formula to the Skolemized
form, or otherwise checks an explicit certificate contract for that
transformation.

The project has made real progress here:

- Vampire emits Skolem parent information and introduced-symbol metadata.
- Vampire emits branch-choice witness terms and Skolem branch contracts.
- Megalodon parses and validates much of this metadata.
- Focused native proof-term paths now handle some Skolem/CPS fragments.
- The focused detached `UnionI` preprocessing check passes.

But the final original-source path still exposes certificate-local choice:

```text
#Eps_i
vampire_exists_prop_choice
```

These are not acceptable in the final counted path unless replaced by checked
Megalodon proofs using the live library context. The live proposition-choice
checker is a step in this direction. It proves that one certificate-side
choice basis can be derived from the currently loaded Megalodon context,
rather than blindly trusted. The analogous set-valued choice/equidimensional
Skolem witness path is still the next exposed blocker.

The current focused source timeout also points to Skolem/choice indirectly.
The returned-proof expansion is likely expanding a large proof containing
Skolem-shadow CPS fragments and certificate-local aliases. The next fix should
not be a special case for `UnionI`; it should define a general live-basis and
source-alias expansion contract for these fragments.

## Smolka-Style Transformation Status

The Smolka-style layer is the source/preprocessing proof layer between the
original higher-order Megalodon proposition and the clausal Vampire refutation.
It includes transformations such as:

- logical encoding;
- definitional expansion;
- rectification;
- ENNF;
- FOOL normalization;
- CNF projection;
- Skolemization;
- set-generated equality handling;
- generated predicate/function definitions;
- transport between source-level and certificate-level formulas.

The implementation has many pieces of this layer, but it is still too
monolithic. The certificate format can represent many transformation steps,
and several focused native proof-term paths check. The detached `UnionI`
result demonstrates that a nontrivial exported proof can pass a native
preprocessing proof-term gate.

The original source command shows the remaining weakness: Smolka-style
transformations are not yet cleanly connected to live source proofs and live
source symbols all the way through final theorem composition.

The correct architectural split should be:

```text
source theorem/context
  -> source/preprocessing proof-producing transformations
  -> clausal/small-kernel proof replay
  -> contradiction/refutation
  -> final classical source theorem proof
```

Each arrow should have an explicit checked proof object or a small reviewed
logical-basis proof. Large OCaml-side reconstruction heuristics should not be
the long-term plan.

## Prover9/Ivy Lessons

The Prover9/Ivy analysis remains the best architectural guide.

Prover9 does not print Ivy proof objects directly from raw high-level proof
justifications. It first expands the proof in the prover, then lowers the
expanded proof into a small Ivy kernel. The relevant pipeline is:

```text
Prover9 proof
  -> expand_proof
  -> expand_proof_ivy
  -> Ivy S-expression proof object
```

The Ivy kernel carries a small amount of exact data:

- parent clause ids;
- positions;
- substitutions;
- rule tags such as `input`, `instantiate`, `flip`, `resolve`, `paramod`,
  `propositional`, and limited `new_symbol`.

The lesson for this project is direct:

```text
Vampire should lower complex inferences into small explicit certificate
steps while it still has exact substitutions, selected literals, equality
directions, positions, sorts, parent/result formulas, and generated-symbol
dependencies.
```

Megalodon should then check a comparatively simple primitive certificate and
elaborate it to native proof terms.

The current project has moved in this direction but has not completed the
pivot. There is still too much proof logic in:

```text
/project/Megalodon/src/vampire_cert_v1.ml
```

and too much certificate/detailing logic in the Vampire Megalodon output
implementation. The code has grown because it is handling many inference
classes directly instead of first lowering them to a small primitive IR.

The intended primitive clausal kernel should remain small. A practical target
is:

- `input`, already linked to a checked source or preprocessing proof;
- `instantiate`;
- `resolve`;
- `factor`;
- `equality_resolution`;
- `equality_factoring`;
- `paramodulate` or equality transport at explicit positions;
- final empty-clause/contradiction.

Other constructs should be handled by expansion layers:

- demodulation and rewrite chains lower to equality transport/paramodulation;
- unit-resulting resolution lowers to binary resolution plus instantiation;
- superposition lowers to instantiated equality transport;
- AVATAR is either an explicit SAT/RUP layer or is excluded from a small E1
  milestone;
- Skolemization and clausification belong to the Smolka-style preprocessing
  layer, not the clausal kernel.

## Python Status

Python was useful early in the project for:

- inspecting certificates;
- translating proof output into readable skeletons;
- analyzing frequent inference classes;
- generating quick diagnostics over corpora.

Python should not be part of the counted proof path. It should not generate a
proof term that qualifies as reconstruction. It should not accumulate new
logical reconstruction logic that duplicates the OCaml/Vampire work.

The current strategic direction is:

```text
Python may summarize and inspect.
Vampire emits exact certificate data.
Megalodon checks and elaborates native proof terms.
```

This should remain a hard rule.

## Testing Strategy

The testing strategy changed after repeated user feedback about slow
iteration.

Broad runs should use:

- batch export of all selected problems;
- parallel Vampire runs, typically 10 to 20 workers depending on the machine;
- per-problem Vampire timeout at or below 10 seconds;
- cached Vampire outputs;
- parallel certificate checking;
- `/project/tmp` for generated output.

But broad runs should not be repeated when a focused blocker is known. The
current blocker is in original-context source composition for `UnionI`, so the
current validation has deliberately used focused commands only.

The correct near-term testing ladder is:

1. Keep the focused detached `UnionI` native preprocessing check passing.
2. Make the focused original-source `UnionI` theorem close without `aby`,
   `admit`, incomplete QED, bridges, or certificate-derived knowns.
3. Add a committed focused regression for that exact source case.
4. Move to a small E1 suite of 5 to 10 source theorems already known to be
   solved by Vampire under 10 seconds.
5. Only then return to 87/100-style corpus runs.

The current reportable validation is focused. It does not claim a broad pass.

## Audit Response Status

The audits made several central points.

First, "strict" structural validation is not proof reconstruction. The current
reports now explicitly separate E1/E2/E3/E4 evidence. Detached certificate
checks are not described as original theorem proofs.

Second, bridge premises and certificate-derived knowns are not acceptable.
The current architecture treats these as forbidden in counted modes. The live
proposition-choice diagnostic was added specifically because a hidden
certificate-local choice theorem is not a legitimate proof dependency.

Third, source linkage must be semantic, not just label-based. The current
source map work is better than before, but not finished. The focused `UnionI`
failure demonstrates that top-level source names can be correct while nested
proof-context fragments remain certificate-local. This is exactly the kind of
semantic source-linking issue the audits warned about.

Fourth, scope had escaped the MVP. This remains a risk. The certificate and
importer support many inference and preprocessing classes. That was
pragmatically necessary to reach serious examples, but it should not be the
long-term trusted shape. The Prover9/Ivy reset remains the right strategic
direction.

Fifth, Python should be quarantined. The current counted path is not Python,
but the project must avoid growing Python proof logic further.

Sixth, the first proper milestone should be a small number of genuinely
closed source proofs, not another broad structural pass. This report agrees.

   `vampire_exists_prop_choice` still appear in diagnostic paths. They must be
   replaced by checked live proofs or explicit transformation certificates.

5. The Smolka-style transformation layer is not cleanly separated.

   Transformations from source formulas to clausal formulas are represented
   and partially checked, but the proof-producing contracts are not yet a
   small clear layer.

6. The importer is too large.

   `src/vampire_cert_v1.ml` contains too much inference-specific proof logic.
   The long-term path should move exact inference decomposition toward
   Vampire-side primitive certificates.

7. The Vampire output path is not yet a clean primitive IR builder.

   It emits increasingly rich data, but it does not yet mirror Prover9's
   clean `expand_proof` / `expand_proof_ivy` architecture.

8. Source facts generated by `set` commands need systematic handling.

   Some generated equalities should be proved by reflexivity or conversion,
   not looked up as original source claims or treated as assumptions.

## Current Outlook

The project is not finished, but the current blocker is usefully specific.
The next several engineering steps should be:

1. Fix returned-proof expansion for the focused source `UnionI` path.

   The new timing markers show this is the current slow stage. The fix should
   use source-map aliases and live-basis proofs generally, not hardwired
   set-library names.

2. Eliminate certificate-local aliases from nested proof-context fragments.

   The source alias normalizer should be applied or integrated at the point
   where returned proof fragments are expanded into the live context.

3. Replace set-valued choice/Skolem witnesses with checked live proofs.

   The proposition-choice checker is a model. The next target is the
   `#Eps_i` path exposed in `UnionI`.

4. Close one original source theorem.

   `UnionI` is the right current target because it exercises the hard boundary
   without requiring a broad corpus run.

5. Build a small E1 suite.

   After `UnionI`, select 5 to 10 theorems already known to be solved by
   Vampire under 10 seconds and add a committed regression gate.

6. Resume Vampire-side primitive IR work.

   The importer should not keep growing as a proof-search/reconstruction
   engine. Complex Vampire inferences should be lowered in Vampire to
   primitive records, following the Prover9/Ivy model.

7. Only then run 87/100-style broad tests.

Broad parallel tests are useful once the source path can close examples,
but broad repeated failures are currently a waste of iteration time.

## Detailed Chronology

This section gives a longer history because the project has changed direction
several times, and an external reviewer needs to know which parts of the
current branch are exploratory leftovers and which parts represent the
intended path.

The initial user request was to download Vampire and Megalodon, find the
existing Vampire proof reconstruction code for Lean, and adapt that idea to
Megalodon. The natural first observation was that Lean and Megalodon are
similar at the level relevant to this project: both ultimately check proof
terms, not just tactic traces. Therefore the right endpoint is not a textual
proof script accepted by automation, but a proof term whose proposition is
checked by Megalodon.

The early implementation nevertheless used a Python translator heavily. That
was a pragmatic discovery tool. It made it possible to inspect TPTP proof
output, map Vampire source labels to proof skeleton claims, and quickly see
which inference classes were common. It also showed why a skeleton with
`claim ... admit` is useful to humans but not a qualifying result. Those
skeletons can be informative artifacts, especially for manual continuation,
but they are not reconstruction.

The first serious testing lesson was performance. Running Megalodon export,
Vampire, and reconstruction one problem at a time was wasteful. The user
correctly pushed for a batch strategy:

```text
export all selected problems once;
run Vampire on the exported THF/TPTP files in parallel;
cache the proof outputs;
run reconstruction/checking over cached outputs in parallel.
```

That remains the right broad testing plan. The current focused iterations
avoid broad testing not because broad testing is unimportant, but because the
active failure is already known and broad runs would only repeat the same
expensive source-composition problem many times.

The next strategic correction was about source names. The first translators
and proof skeletons were too willing to hardwire names observed in the current
library. The user objected to names such as `famunion` or set-library-specific
aliases appearing in reconstruction logic. That criticism was correct. The
reconstruction must work for arbitrary Megalodon developments, so the only
acceptable source of name recovery is the export/source map, plus Megalodon's
live context. The current alias work is a direct response: it derives aliases
from source-map entries and symbol-name normalization functions, not from a
table of benchmark names.

The next correction was about `aby`. Megalodon's `aby` is implemented as
admission, so it cannot occur in counted scripts or proof paths. Similarly,
`-allowincompleteqed` is allowed for generating problems but not for checking
the reconstructed result. This led to the current policy that all qualifying
results must be native checked proof terms or source commands without `aby`,
`admit`, incomplete QED, bridges, or hidden knowns.

The following phase focused on Vampire proof modes. The user repeatedly asked
why the project was not modifying the Lean/Vampire proof-output path more
directly. That was another valid criticism. The project initially spent too
much time trying to infer proof details on the Megalodon side. The current
direction is to make Vampire emit richer, exact information while it still has
the proof search data structures: substitutions, sorts, selected literals,
positions, equality directions, generated symbols, and parent/result formulas.

The Prover9/Ivy analysis sharpened this into a concrete architectural model.
Prover9 expands normal proof justifications into simpler internal proof steps,
then lowers those expanded steps into Ivy objects. The target checker receives
small explicit inferences, not opaque large prover steps. The same pattern
should drive Vampire/Megalodon:

```text
Vampire high-level proof
  -> Vampire-owned expansion/detailing pass
  -> small primitive Megalodon certificate
  -> Megalodon proof-term checking
```

The July audits then exposed a trust-boundary problem. A strict certificate
parser that accepts a proof object is not enough if the generated Megalodon
theorem contains extra bridge premises. A proof term that checks after the
importer inserted the desired proposition into `Known` is not reconstruction.
A source label that names a real theorem is not enough unless the proposition
attached to the certificate input is semantically the same as the source
theorem proposition. These observations led to the current evidence classes
and to the rejection of certificate-derived knowns in counted paths.

The recent work has moved from the clausal core into final source
composition. The focused `UnionI` example is now the main case study because
it is large enough to expose the real boundary but small enough to iterate on
without broad corpus runs. The detached certificate checks, which means the
certificate-side proof object is not the immediate problem. The original
source command does not close, which means the remaining problem is gluing the
refutation into the live Megalodon theorem.

## Implementation Details: Vampire

The Vampire fork's Megalodon path has accumulated several classes of metadata.
The most important are source metadata, equality metadata, Skolem metadata,
branch/AVATAR metadata, and kernel-step metadata.

Source metadata records where an input or generated formula came from. It
distinguishes roles such as axiom, conjecture, generated definition, generated
set fact, local hypothesis, and known/library fact. This is necessary because
the final Megalodon proof must discharge each certificate input in a different
way. A theorem source should resolve to a checked theorem proof. A local
hypothesis should resolve to a local proof binder. A generated set equality
may need reflexivity/conversion. A conjecture source is handled by the final
refutation-to-goal composition.

Equality metadata exists because many Vampire inferences are equality-driven.
Vampire knows the rewritten side, the direction, the parent equality, and
often the target position. If Megalodon must rediscover these from a printed
formula, the reconstruction becomes fragile and expensive. Prover9's
demodulation expansion is the model: each rewrite is converted into a
paramodulation/equality transport step with exact positions.

Skolem metadata records introduced symbols and their dependencies. This is
critical for avoiding unsound global definitions. A Skolem function whose
definition depends on local variables cannot be installed as an arity-zero
global object. The recent branches moved in the direction of preserving parent
formula quantifier metadata, introduced witness records, and branch contracts
so Megalodon can reconstruct the right dependent proof shape.

Branch and AVATAR metadata records component variables, split symbols,
component formulas, and SAT/refutation structure. AVATAR is dangerous for a
small trusted path because it can easily turn into "assume a component and
trust the SAT layer." The current focused detached `UnionI` check handles a
multi-variable AVATAR split, but long-term the AVATAR layer should either be
lowered to explicit proof objects or excluded from the first small E1
milestone.

Kernel-step metadata is the intended future center. It should describe
primitive proof steps rather than high-level Vampire inferences. The current
branch has a growing `kernel_v1` vocabulary, but it is not yet a clean
standalone proof expansion module. The expert should treat this as partial
progress rather than a completed Prover9/Ivy equivalent.

## Implementation Details: Megalodon

Megalodon's importer has several conceptual stages.

The first stage parses the S-expression certificate into typed OCaml
structures. This is already much better than parsing ad hoc proof text, but
the parser itself is only the beginning.

The second stage validates certificate structure. It checks step ids, parent
references, source-map entries, source roles, selected metadata consistency,
and strict-mode invariants. This is useful E4 evidence. It is not by itself a
proof.

The third stage elaborates supported certificate fragments to native
Megalodon proof syntax. The important trust boundary is `Syntax.pf`: a proof
counts only if Megalodon checks the proof term against the proposition it is
supposed to prove. The importer should therefore construct proof terms, not
just print scripts.

The fourth stage validates source/preprocessing fragments. This includes
localizing source-local aliases, checking generated facts, composing source
assumptions, and validating transformation proof terms. This is the layer
where many of the current problems live.

The fifth stage composes a checked refutation with the original theorem
context. This stage must respect Megalodon's live binders and hypotheses. If
the theorem is:

```text
forall X x Y:set, x :e Y -> Y :e X -> x :e Union X
```

then the final proof term must be a proof of that exact proposition in the
source context, not just a proof of an exported alpha-equivalent clause under
certificate-local constants.

The newest changes affect stage four and stage five. Source aliases such as
`#In` and `#Union` are now normalized to source names in additional final
validation checks. Timing markers show which substage of final composition is
slow. The result is not a finished proof, but it makes the next failure much
more precise.

## Focused Case Study: UnionI

The current focused theorem is:

```text
Theorem UnionI :
  forall X x Y:set, x :e Y -> Y :e X -> x :e Union X.
vampire UnionEq.
Qed.
```

This theorem is a good test case for several reasons.

First, it is not merely propositional. It has set variables, membership,
union, and a source lemma/definition boundary around `UnionEq`.

Second, it involves original local binders and hypotheses. The proof must
connect Vampire's refutation of the negated exported conjecture back to the
live theorem's local assumptions.

Third, it exercises generated or definitional source facts. Some relevant
facts come from Megalodon's set machinery and may need reflexivity or
conversion rather than lookup as named claims.

Fourth, it exercises Skolemization and choice. The negated conjecture and
clausal transformations introduce witnesses. The proof object contains
certificate-local epsilon-style terms such as `#Eps_i`.

Fifth, it exercises AVATAR splitting. Earlier work fixed multi-variable AVATAR
split replay for the saved certificate.

The current saved detached certificate has 131 checked steps and 126 native
preprocessing proof-term steps. That is a real accomplishment: Megalodon is
not merely parsing the certificate; it is checking a substantial native proof
object for the exported problem.

The original source command still fails. The diagnostic story is now:

1. Vampire finds and emits the proof under the 10-second limit.
2. Megalodon parses and validates the certificate.
3. The native preprocessing proof-term path can check the saved detached
   certificate.
4. The source command constructs a candidate refutation-to-goal proof.
5. The top-level proposition after source composition uses live `In` and
   `Union`.
6. A nested final-refutation bad application still contains `#In` and
   `#Union` in proof-context hypotheses.
7. The source command times out during returned-proof expansion.

This is why the next step should not be another broad run. The focused case
has already isolated the failure class.

## Source-Map Alias Normalization

The current alias approach is based on source-map data. For each source-map
entry, the code computes normalized aliases for both the TPTP name and the
source name. It then maps those aliases back to the source name, subject to
basic checks that avoid empty aliases and trivial self-mappings.

The important property is that this mechanism is not a list of special
library constants. If a future development exports a different symbol, its
aliases should be recovered from that development's source map.

The new normalizer operates on both terms and proofs:

```text
TmH alias          -> TmH source_name
PTmAp proof term   normalizes the term argument
PLam prop body     normalizes the proposition binder
```

It is currently used in final native proof checks and proposition checks. The
focused source timeout suggests that a related normalization is needed earlier
or deeper in the returned-proof expansion path. The expert should review
whether alias normalization should be applied:

- immediately after parsing certificate terms;
- after source-map validation;
- before native proof-term construction;
- before final source-context composition;
- or in all of these places with idempotence guarantees.

The risk is accidental over-normalization. The code must not decide that two
unrelated symbols are equal merely because their printed names have similar
normalized forms. The source-map entry must remain the authority.

## Live Basis Proofs

The project must distinguish approved library facts from certificate-local
facts. Classical logic is available, especially `xm`, and the Megalodon
library already contains logical constants and eliminators. The reconstruction
should use those facts explicitly.

The proposition-choice gate is an example. The certificate path had a
certificate-side proposition-choice theorem. The current live check verifies
that the corresponding proof can be built from the current Megalodon context.
This prevents a certificate from silently smuggling in the proposition it
needs as a known theorem.

The same pattern should be applied to other logical-basis elements:

- double-negation elimination should be derived from `xm` or an approved
  classical theorem;
- proposition extensionality should come from Megalodon's library facts;
- `False` elimination should use the live library theorem;
- set-valued choice/epsilon should use live `Eps_i`/choice facts where
  available, with exact type alignment;
- equality transport should use Megalodon's equality.

The danger is that a basis proof can be accidentally specialized to the
current example. The implementation should build reusable proof combinators
over live library symbols, with failure diagnostics when a needed symbol is
not present.

## Proposed Primitive Certificate IR

The current certificate supports many constructors. A smaller primitive layer
would make the trust boundary easier to review. The following IR is a proposed
direction, not a statement of current completion.

Each primitive step should have:

```text
id: stable step name
rule: one primitive rule
parents: ordered parent step ids
conclusion: canonical formula/clause
substitution: explicit variable instantiation, when relevant
positions: explicit literal/term positions, when relevant
direction: equality/rewrite direction, when relevant
sorts: variable and symbol sorts needed for checking
origin: source/preprocessing/kernel classification
```

The clausal kernel should be small:

```text
input
instantiate
resolve
factor
equality_resolution
equality_factoring
paramodulate
contradiction
```

Macro rules should lower to those primitives:

```text
superposition            -> instantiate + paramodulate + simplification
demodulation             -> paramodulate/equality transport at positions
definition rewrite chain -> one equality transport per occurrence
unit resulting resolution-> repeated binary resolution
subsumption resolution   -> instantiate + resolve/factor as needed
condensation             -> instantiate + factor/propositional cleanup
```

Preprocessing rules should not be mixed into the clausal kernel:

```text
rectification
ENNF
FOOL transformation
CNF projection
Skolemization
predicate/function definitions
set-generated equalities
```

These need their own source/preprocessing certificate layer. That layer may
itself use proof terms, but it should be conceptually separate from resolution
and paramodulation.

## Proposed Smolka-Style Contracts

The Smolka-style transformation layer should be made explicit through
contracts. A contract should state:

```text
given source formula F and generated formula G,
Megalodon has a checked proof that F implies/equates/transforms to G
in the direction required by the refutation pipeline.
```

Practical initial contracts could include:

- Definitional unfolding/refolding:

  ```text
  F is convertible to G by a named source definition or generated definition.
  Proof method: Megalodon conversion/equality transport.
  ```

- Set-generated reflexivity equality:

  ```text
  G is an equality generated by the set command.
  Proof method: reflexivity/conversion, not source assumption.
  ```

- Rectification:

  ```text
  F and G differ only by alpha-renaming and binder hygiene.
  Proof method: kernel conversion or explicit alpha-equivalence proof.
  ```

- Negation normal form:

  ```text
  F -> G under classical/logical equivalences.
  Proof method: live logic basis, including xm where necessary.
  ```

- CNF projection:

  ```text
  F implies each generated clause, or unsatisfiability of clauses implies
  contradiction from F.
  Proof method: explicit proof terms for implication chains and disjunctions.
  ```

- Skolemization:

  ```text
  Existential witnesses introduced by Vampire are justified by live choice
  principles with exact dependency variables and types.
  Proof method: checked choice/epsilon proof, not global Skolem axioms.
  ```

The first E1 milestone does not need every transformation class. It needs the
classes that occur in the first small suite. For `UnionI`, that likely means
definitional/set facts, classical refutation-to-goal, Skolem/choice, and
possibly AVATAR.

## Non-Qualifying Work

The following artifacts have been useful but should not be counted as final
reconstruction:

- generated Megalodon scripts containing `claim ... admit`;
- any script containing `aby`;
- any result checked with `-allowincompleteqed`;
- broad structural certificate passes that do not construct native proof
  terms;
- native proof-term checks that rely on certificate-derived `Known` entries;
- Python-generated proof terms or scripts;
- detached certificate checks not composed into the original theorem context;
- source-label checks that do not validate source propositions;
- hidden bridge assumptions, even when Megalodon kernel-checks the stronger
  theorem.

These artifacts can remain diagnostic, but reports should not describe them
as solving the original goal.

## Medium-Term Plan

The medium-term plan should be deliberately staged.

Stage 1: close `UnionI` in the original source context.

This is the current focused milestone. It requires fixing returned-proof
expansion, nested source alias cleanup, and live choice/Skolem composition.

Stage 2: make the result reproducible.

Commit a small regression that runs the original source theorem without
forbidden assumptions. Include a cached certificate or deterministic refresh
path. The regression should fail if a bridge or hidden known is introduced.

Stage 3: select 5 to 10 source theorems.

Choose theorems already known to be solved by Vampire within the 10-second
limit. Avoid examples before `xm` if they lack the agreed classical context.
The point is not breadth yet; the point is proof closure discipline.

Stage 4: create a small primitive IR design and implementation checkpoint.

Move one frequent macro inference class from Megalodon-side reconstruction
toward Vampire-side primitive expansion. Definition rewrite chains or
demodulation are likely good candidates because Prover9 gives a clear model.

Stage 5: broaden carefully.

After 5 to 10 source theorems close, run a parallel cached check over a larger
set. Report E1/E2/E3/E4 separately. Do not collapse them into one pass count.

Stage 6: target the 100-theorem requirement.

Only once the small E1 suite is stable should the project return to the
original 100-theorem objective.

## Bottom Line

The project has moved substantially away from the initial Python skeleton path
and toward native Megalodon proof terms over detailed Vampire certificates.
The current branch has real exported-problem proof-term evidence for a serious
focused example. It also has better source linking, live proof-basis checking,
and diagnostics than the audited earlier states.

But the original goal is still open. The project does not yet reconstruct 100
Megalodon theorems from Vampire proofs in the original source context. The
current strongest result is a detached `UnionI` certificate check, not a
closed original-source theorem proof.

The immediate next target should be one fully closed source theorem, probably
the focused `UnionI` case, with no forbidden assumptions. The broader
architectural target should remain a Prover9/Ivy-style primitive certificate
generated by Vampire and checked by Megalodon, with Smolka-style
source/preprocessing transformations separated from the clausal kernel.
