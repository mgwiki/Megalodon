## Executive Summary

The original target remains:

```text
For a theorem in an original Megalodon development:
  export the theorem and relevant context as THF/TPTP;
  run Vampire with a per-problem timeout of at most 10 seconds;
  emit a detailed proof certificate from Vampire;
  import the certificate into Megalodon;
  elaborate it to native Megalodon proof terms;
  check the proof in the original Megalodon context;
  use no aby, no admit, no incomplete QED, and no bridge assumptions.
```

That target is not yet complete.

The project has made real progress, but the strongest current result is still
below the final bar. The focused `UnionI` Vampire certificate now passes a
strict detached native certificate and preprocessing proof-term check. That is
substantial because `UnionI` exercises source facts, generated set definitions,
Skolemization, choice, AVATAR splitting, and final classical
refutation-to-goal composition. The same proof does not yet close as a
Megalodon source command in the original theorem context. The failure has
moved from Vampire search and certificate emission into the final proof-term
composition and live-symbol cleanup boundary.

The most important architectural correction since the early reports remains
the July 16 audit point: pass counts that depend on dynamically installed
certificate-derived `Known` propositions are not proof reconstruction. They
are structural diagnostics. Counted progress must now mean proof terms checked
against original source facts, generated definitional obligations, approved
library facts, or fixed reviewed logical basis proofs. A certificate step must
not justify itself by inserting the proposition it needs into the known-theorem
table.

The current branch is closer to the intended Prover9/Ivy-style architecture
than the first prototypes were. Vampire emits more certificate detail, including
source origins, equality/rewrite metadata, Skolem metadata, branch choice data,
AVATAR split information, and `kernel_v1` primitive-expansion contracts.
Megalodon consumes a native S-expression certificate, validates source maps and
metadata, and constructs native `Syntax.pf` proof terms for a growing but still
incomplete subset. However, too much proof logic is still inside the large
`src/vampire_cert_v1.ml` importer, and too much Vampire-side proof detailing is
still embedded in the large Megalodon checker/export implementation rather
than a clean standalone primitive-certificate builder.

The current practical frontier is no longer "can Vampire find the proof?" or
"can a Python translator produce a readable skeleton?" It is also no longer
"can the saved focused `UnionI` certificate be checked as a detached native
proof-term object?" That now passes. The frontier is:

```text
Can a checked Vampire certificate refutation be composed back into a proof
of the live Megalodon theorem using the original local binders, hypotheses,
definitions, generated set equalities, library equality, live choice/epsilon,
and classical principles such as xm?
```

For `UnionI`, the answer is still no. The focused detached certificate passes;
the original source command still fails during final source composition. The
latest focused source-command run no longer falls into the accidental default
grouped-Skolem timeout, but it still produces a local proof fragment that does
not close the live theorem. The remaining leaked generated symbol is tied to a
proposition-level Skolem/choice artifact (`Eps_prop` in the certificate
basis), not to a missing Vampire refutation.

## Evidence Classes

The project now uses four evidence classes. This classification is essential
because previous reports and runs could otherwise look more successful than
they really are.

E1 is the actual goal:

```text
Original-context proof reconstruction. A Megalodon theorem is proved at its
original proof site by a native proof term reconstructed from a Vampire
certificate. The result uses no aby, no admit, no incomplete QED, no bridge
assumption, no certificate-derived Known theorem, and no Python proof-producing
step.
```

E2 is useful but not final:

```text
Exported-problem-bound closed proof reconstruction. Megalodon checks a native
proof term for a Vampire certificate against the exported THF/TPTP problem,
but the proof is not yet composed back into the original source theorem.
```

E3 is focused proof-term evidence:

```text
Synthetic or focused examples exercise a particular native proof-term
elaboration path, small-kernel rule, or preprocessing transformation fragment.
```

E4 is structural and integration evidence:

```text
Vampire emits certificates; Megalodon parses them; source maps, metadata,
roles, and certificate structure are validated; or diagnostic modes run.
This is valuable plumbing evidence, but it is not proof reconstruction.
```

Under this classification:

- The broad strict live certificate/source/metadata runs are E4 unless they
  also build and check native proof terms and compose them into original
  source theorems.
- Old preprocessing proof-term frontier numbers that relied on transitional
  dynamic `Known` implications are E4 diagnostics.
- The native clausal core and focused `Syntax.pf` fixtures are E3.
- The focused detached `UnionI` native preprocessing proof-term check is
  E2-like evidence: it is a real native proof-term check over the exported
  certificate, but not an original-context theorem proof.
- The small source-command prefix through `Empty_eq` is the best E1-style
  smoke evidence so far, but it is narrow and does not satisfy the 100-theorem
  goal.

## User Requirements and Constraints

The active requirements are:

- Use THF/TPTP exports from Megalodon.
- Run Vampire with `--input_syntax tptp`.
- Do not run Vampire for more than 10 seconds per problem.
- Prefer batch export, parallel Vampire runs, and parallel certificate checks.
- Use `/project/tmp` for temporary artifacts and generated diagnostic output.
- Do not use `aby` in final proofs. In Megalodon, `aby` is implemented as an
  admission and cannot count.
- Do not use `admit` or incomplete QED in final proofs.
- Assume classical logic. The theorem `xm` is available and should be used
  where needed.
- Use Megalodon's library equality, `False`, disjunction, implication, and
  related logical constants. Do not introduce private replacement logic in the
  final proof.
- Recover original source names and facts from the source map and live
  Megalodon context, not from hardwired benchmark names.
- Treat source entries generated by Megalodon `set` commands as generated
  definitional or reflexivity obligations when appropriate, not as assumed
  claims that must already exist in the source file.
- Get exact proof data from Vampire whenever possible: sorts, selected
  literals, substitutions, rewrite positions, directions, parent/result
  formulas, introduced symbols, and dependency information.
- Use Python for corpus inspection and diagnostics only, not as a qualifying
  proof reconstruction engine.

These constraints rule out broad Megalodon-side guessing, library-specific
name hacks, and pass-count-oriented work that does not close checked proof
terms.

## High-Level Approach

The intended architecture is now:

```text
Original Megalodon theorem and local context
  -> THF/TPTP export with source-origin metadata
  -> Vampire proof search
  -> Vampire-side certificate detailing while Vampire still knows exact data
  -> canonical S-expression certificate
  -> Megalodon certificate parser and small checkers
  -> native Syntax.pf elaboration
  -> composition with the original Megalodon theorem context
```

This is the Prover9/Ivy-style path recommended by the audits. The important
lesson from Prover9's Ivy export is that an external proof checker should not
be asked to rediscover complex prover-side information. Prover9 first expands
ordinary proof objects into simpler proof objects, then prints those objects
for Ivy. The analogous Vampire work should lower complex Vampire inferences
into an explicit small-kernel certificate vocabulary before Megalodon checks
them.

The intended small clausal kernel remains roughly:

- `input` as a boundary from a proved source/preprocessing clause;
- `instantiate`;
- `resolve`;
- `factor`;
- `equality_resolution`;
- `equality_factoring`;
- `paramodulate`;
- final empty-clause or contradiction marker.

Some names should remain outside that logical core:

- `rename` should usually be alpha-conversion or an instantiation detail.
- `truth_conflict` probably belongs to the FOOL/source-preprocessing layer
  unless a real clausal proof forces it into the kernel.
- AVATAR should not be smuggled in as trusted component assumptions. It needs
  either an explicit SAT/RUP-style object or a small reviewed AVATAR layer.
- Skolemization is a source/preprocessing transformation, not a clausal kernel
  inference.

The work currently spans both repositories:

- Vampire is responsible for printing enough exact proof detail.
- Megalodon is responsible for parsing, checking, elaborating proof terms, and
  connecting checked certificate assumptions back to the live source theorem.
- Python is not part of the trusted architecture.

## Audit-Driven Course Corrections

The July 12 and July 13 states were useful prototypes. They produced skeletons
and exposed many Vampire proof shapes, but they leaned too much on generated
proof scripts, broad reconstruction in Python, and bridge assumptions. The
audits correctly rejected that direction as a final architecture.

The July 13 audit specifically recommended moving to native OCaml
infrastructure, S-expression proof objects, Megalodon's existing syntax and
checking code, and a Prover9/Ivy-style certificate. That course correction has
mostly happened at the format and implementation-language level. The native
certificate is S-expression based, parsed in OCaml, and elaborated to
Megalodon `Syntax.pf` terms in the supported fragments.

The July 16 audit made the sharper trust-boundary correction. It observed that
the reported preprocessing proof-term frontier was overclassified because many
steps were justified by dynamically inserting the required proposition into
the `Known` theorem table. The implementation now treats such transitional
knowns as diagnostic-only. Counted modes are supposed to reject them unless an
explicit environment variable opts into the old structural behavior.

This correction is still the most important standard for evaluating the
current work. If a new path introduces a certificate-derived `Known`
proposition, it should be reported as E4 or rejected, not counted as proof
reconstruction.

The July 16 and July 17 design documents also asked for:

- a clearer source-context API;
- a separate source/preprocessing transformation layer;
- a small-kernel proof object rather than a large inference-specific importer;
- evidence classes instead of ambiguous pass counts;
- parallel batch testing rather than repeated sequential Vampire runs;
- one then ten then one hundred original-context E1 proofs, in that order.

The implementation has partially followed this plan. It has not fully
completed the pivot. The report should therefore be read as a progress report,
not as a success claim.

## Vampire-Side Work

The Vampire fork has gained a Megalodon-oriented certificate output path. The
certificate is S-expression based and carries more than ordinary TPTP proof
text. It includes source and role information, parent links, step names,
formula terms, clause data, and an expanding set of rule-specific metadata.

Important Vampire-side improvements from the recent branches include:

- source-origin preservation for TPTP inputs exported from Megalodon;
- standard Skolem metadata, including parent formula information and
  introduced symbol data;
- branch choice witness terms;
- Skolem parent instantiation contracts and quantifier metadata;
- equality-resolution and equality-substitution helper metadata;
- subsumption pivot metadata;
- equality/rewrite/demodulation metadata aligned with primitive replay;
- multi-step and macro metadata for harder inference classes;
- a `MegalodonKernelSyntax` vocabulary boundary for `kernel_v1` metadata.

The current committed Vampire head is:

```text
6f3977d81 Avoid unsafe backward demodulation replay substitutions
```

The latest Vampire commit disables unsafe optional substitution recording in
`InferenceRecorder::backwardDemodulation`. This is not intended as a trusted
proof shortcut. It avoids a proof-output crash after Vampire has already found
a refutation, in a situation where the Megalodon certificate path uses
explicit rewrite metadata and real parents rather than the optional
substitution bank entry.

This change was motivated by the focused `UnionI` source-command frontier.
Before it, Vampire could report a refutation and then crash while printing the
proof. With the change, proof output for the focused certificate completes.
The trust boundary is unchanged: the Megalodon certificate checker should use
the explicit rewrite data and actual parent formulas in the certificate, not
unsafe replay-substitution state from Vampire's internal indexing machinery.

The biggest remaining Vampire-side gap is not metadata quantity. It is the
absence of a clean, isolated primitive proof IR builder. The current
certificate path still lives inside a large exporter/checker implementation.
The final architecture should not grow by adding one-off output cases forever.
It should construct typed primitive records first, then serialize them through
one canonical printer.

The desired internal shape remains:

```text
MegalodonPrimitiveStep {
  id;
  rule;
  parent ids;
  conclusion;
  selected literal and equality indices;
  rewrite position and direction;
  substitution;
  variable and symbol sorts;
  source or preprocessing payload when outside the clausal kernel;
}
```

Macro inferences such as unit-resulting resolution, demodulation,
superposition, AVATAR, and complex preprocessing should either lower to this
vocabulary or declare an explicit, fail-closed expansion contract.

## Megalodon-Side Work

Megalodon now has a native certificate importer and checker for the Vampire
certificate format. The important files are:

- `src/vampire_cert_v1.ml`;
- `src/vampire_cert_v1.mli`;
- `src/megalodon.ml`;
- kernel syntax and certificate test infrastructure under
  `tests/vampire_certificate`.

The importer performs several jobs:

- parse the S-expression certificate;
- parse or compare source THF formulas;
- validate source roles and metadata;
- check source-map consistency;
- classify source obligations;
- reconstruct native proof terms for supported clausal and preprocessing
  steps;
- check those proof terms with Megalodon's `check_propofpf`;
- compose certificate refutations into source-command proof attempts.

That functionality is useful, but its concentration in
`src/vampire_cert_v1.ml` is still a design smell. The audits warned against
turning the importer into another prover. That risk is real. The next
implementation phase should extract new qualifying work into smaller modules:

- certificate syntax;
- clausal kernel structural checker;
- clausal kernel proof-term elaborator;
- source-context resolver;
- Smolka/source-preprocessing transformation checker;
- final original-context composition.

The latest committed Megalodon changes are focused on the final source-command
frontier, not on broad new inference search. They include:

- A source-command `vampire` path that tries native certificate refutation
  replay before falling back to older source-goal reconstruction.
- Guarded timing and debugging instrumentation around final proof composition.
- A live-basis expander that replaces some fixed certificate-side principles
  by proofs built from the currently loaded Megalodon context.
- Handling of `not` either through a live `notE` theorem if present or as
  definitional implication to `False` when `notE` is absent.
- A live proof sketch for the set-choice certificate principle using live
  `Eps_i` and `Eps_i_ax`.
- Export of `native_core_exists_choice_hash` through
  `src/vampire_cert_v1.mli` so `src/megalodon.ml` can recognize the fixed
  certificate-side choice principle.
- Debugging helpers that scan a final candidate proof for missing live
  references such as certificate-local `split_4` or generated Skolem names.
- Experimental cleanup paths for certificate-local AVATAR split atoms and
  Skolem witness symbols.
- Corrected cleanup gating: the heavy grouped Skolem CPS cleanup is opt-in
  only, while the lightweight final split/witness cleanup is controlled
  separately.
- Final-proof diagnostics that report missing live references and local proof
  fragments that fail to close the theorem.

This is the right place to debug original-context composition, but it should
not become a broad Megalodon-side reconstruction engine. If a proof fails
because exact inference data is missing, the right fix is normally to make
Vampire print the data, not to make Megalodon guess it.

## Linking Back to Original Megalodon Source

Linking to the original Megalodon development has improved, but it remains
incomplete.

The current system no longer treats every certificate input as a free
assumption. Source-map entries are checked and classified. The checker can
distinguish:

- global known facts;
- axioms or theorem hashes;
- local hypotheses;
- definitions;
- generated facts;
- conjecture entries;
- unresolved entries;
- set-generated reflexivity obligations.

Earlier source-context work added audits that load a Megalodon file, resolve
hash-backed knowns against the live context, and reject source-map entries that
claim unavailable hashes. Generated `set_reflexivity` and
`local_set_reflexivity` entries can produce reflexivity or conversion proof
terms rather than being accepted as unnamed axioms. Local hypothesis matching
also accounts for proof-local definitions that shift de Bruijn indices.

This source linkage was strong enough to close the earlier real-source prefix
through `Empty_eq`. That prefix included original source facts and set
definitions, not only artificial standalone THF problems. The gate is still
small, but it is the best E1-style evidence so far.

The current frontier is `UnionI`:

```text
Theorem UnionI :
  forall X x Y:set, x :e Y -> Y :e X -> x :e Union X.
vampire UnionEq.
Qed.
```

For the focused detached `UnionI` certificate, the native checker reports
three source bindings and two remaining source assumptions by kind: one known
source and one conjecture source. This means the detached certificate is not
an anonymous refutation detached from the exported problem. It is source-aware
at the exported-problem level.

The missing part is live theorem composition. The proof is generated under an
exported negated conjecture and certificate-local symbols. Megalodon must turn
that into a proof under the theorem's live binders and hypotheses:

```text
X:set, x:set, Y:set,
Hxy : x :e Y,
HYX : Y :e X
  |- x :e Union X
```

The proof term must use the live `In`, `Union`, equality, `False`, `not`,
epsilon, choice, and source theorem constants. It must not retain
certificate-local symbols such as `#In`, `#Union`, `split_4`, `sK4`, or fixed
certificate-basis names that have not been expanded to live proofs.

The latest debugging shows exactly this class of problem. The direct
certificate check passes, but source-command composition still leaks
certificate-local or generated symbols into the final candidate proof. The
current focused failure is not the earlier accidental grouped-Skolem timeout:
that heavy cleanup path is now gated as opt-in. The remaining live-symbol
diagnostic reports that a generated witness path still depends on
certificate-side proposition choice (`Eps_prop`) and a generated Skolem symbol
rather than being replaced by a proof built from the live Megalodon context.

The source-context abstraction therefore still needs to become a real API,
not only a collection of helper checks. Conceptually it should look like:

```ocaml
type source_proof =
  | GlobalKnown of source_id * Syntax.tm * Syntax.pf
  | LocalHyp of source_id * int * Syntax.tm
  | Definitional of source_id * Syntax.tm * Syntax.pf
  | GeneratedSetEq of source_id * Syntax.tm * Syntax.pf
  | ConjectureNegation of source_id * Syntax.tm
  | Unresolved of source_id * Syntax.tm
```

The final composition code should consume this API explicitly, build a proof
from only approved source proofs and generated definitional proofs, and reject
any unexpanded certificate-local symbol.

## Set-Command Equalities and Equality

The user correctly pointed out that some TPTP axioms come from Megalodon's
`set` command and may not correspond to explicit named `claim` entries. These
facts should not be hardwired by name or admitted. If they are definitional
equalities, they should be proved by Megalodon reflexivity or conversion.

The implementation partially supports this:

- source obligations can be classified as generated set/reflexivity facts;
- source-context auditing separates generated obligations from ordinary
  source claims;
- some equality-shaped source facts have been handled in previous source
  prefix work;
- `Empty_eq` now closes in the real-source prefix gate.

This is still not complete. The source resolver needs a general rule:

```text
source-map entry originated from a Megalodon set or definition command
  -> reconstruct a definitional equality proof by reflexivity or conversion
  -> use it as an ordinary checked source proof in the certificate replay
```

This should be driven by source metadata and formula checking, not by names
such as `Empty_eq`, `UnionEq`, or current-library set constructors.

On equality, the intended final invariant is:

```text
The certificate may recognize equality by normalized internal heads, but
checked final proof terms must close using Megalodon's ordinary equality and
ordinary equality eliminators.
```

There should not be a private equality in the final proof environment. Some
certificate-layer hashes are useful for parsing and fixed-basis recognition,
but those hashes must elaborate back into live Megalodon constants and checked
proofs before an E1 result can count.

## Smolka-Style Transformations

The Smolka-style layer is the source-to-clause proof-producing layer. It is
separate from the clausal kernel.

The intended pipeline is:

```text
original Megalodon proposition
  -> exported THF formula
  -> definition expansion or folding
  -> rectification
  -> FOOL/boolean normalization
  -> ENNF
  -> Skolemization
  -> CNF projection
  -> clausal proof inputs
```

Each arrow must be justified by a checked Megalodon proof term or by a small
reviewed transformation primitive that expands to a proof term. Merely
recording that Vampire performed the transformation is not enough.

Current status by transformation layer:

- Source input and source-map checking have usable foundations.
- Definition input/fold/unfold has partial support and is tied to live source
  contexts in simple cases.
- Rectification has diagnostic and partial native proof-term support, but
  still risks falling into broad transitional mechanisms if not kept under a
  strict trust policy.
- FOOL and Boolean normalization have several focused repairs and metadata
  checks, but not a complete source-level proof-producing layer.
- ENNF and CNF projection are partially handled in focused cases.
- Skolemization has much richer metadata and some real proof-term seeds, but
  the general source-level proof is not done.
- AVATAR splitting has improved for a focused multi-variable case, but general
  AVATAR/SAT proof replay is not solved.
- Final refutation-to-live-goal composition is still open for `UnionI`.

The main design question for the expert is where the Smolka layer should live.
One possible approach is to have Vampire emit a detailed source-preprocessing
certificate while it still has exact parent formulas, introduced symbols,
substitutions, and dependencies. Megalodon would then check a small
transformation vocabulary. Another possible approach is to reconstruct more of
the transformation proofs directly in Megalodon from the source and result
formulas. The audit-favored direction is the first: Vampire should explain,
Megalodon should check.

A reasonable first Smolka object vocabulary would include:

- `source_input`;
- `definition_unfold`;
- `definition_fold`;
- `rectify`;
- `fool_lift`;
- `fool_distinctness`;
- `ennf`;
- `cnf_project`;
- `skolemize`;
- `avatar_split_input` or a separate AVATAR layer boundary.

The most important correctness rule is that none of these may become a hidden
bridge theorem. A transformation object must either elaborate to a proof term
or fail.

## Skolemization

Skolemization remains one of the central unsolved pieces.

There has been meaningful progress:

- Vampire now emits more explicit Skolem metadata.
- Parent formula quantifier information is preserved.
- Introduced symbol names and aliases are recorded.
- Branch choice information is available in more cases.
- Megalodon preserves parent and child formula relationships in typed data.
- Several earlier Skolem failures have moved forward.
- The focused `UnionI` detached certificate no longer stops at the earlier
  Skolem metadata failure.

The focused `UnionI` check that currently passes directly reports:

```text
Vampire certificate v1 source map checked 3 sources.
Vampire certificate v1 closed checked 131 steps.
Vampire certificate v1 native preprocess proof term checked 126 steps.
Vampire certificate v1 native preprocess source bindings checked 3 assumptions.
Vampire certificate v1 native preprocess source assumptions remaining 2.
Vampire certificate v1 native preprocess source assumptions remaining by kind
  known=1 local=0 definition=0 generated=0 conjecture=1 unresolved=0.
Everything looks good.
```

That is real evidence that the exported certificate contains enough
Skolem-related information for the detached preprocessing proof-term checker
on this case.

The unsolved part is the general proof-producing transformation:

```text
source formula with existential structure
  -> Skolemized formula with introduced symbols
```

A qualifying proof needs to account for:

- nullary Skolem constants;
- dependent Skolem functions;
- multiple introduced symbols;
- nested quantifier dependencies;
- branch-sensitive witness definitions;
- aliases for generated symbols;
- interaction with CNF projection and AVATAR;
- live choice/epsilon principles from the Megalodon context;
- final removal or conservative definition of generated symbols before
  original-context proof closure.

The latest July 20 diagnostic runs exposed this boundary again. The proof
contains generated symbols such as `sK4`, and cleanup paths try to replace or
discharge them. A split-only cleanup experiment removed leaked AVATAR split
symbols, but a generated Skolem witness remained. The cleanup gating has now
been corrected so the heavy grouped Skolem CPS path is no longer entered by
default. After that fix, the focused source-command run reached final local
proof checking and failed with a live-reference diagnostic: the proof fragment
still referred to a generated `sK4` path whose body depends on
certificate-side `Eps_prop`.

This should not be solved by hardwiring `sK4`. The general solution is to make
Skolem symbols conservative proof objects:

```text
introduced Skolem symbol
  -> explicit dependency list and sort
  -> choice/epsilon witness definition or proof-producing transformation
  -> source-map/live-symbol expansion
  -> no generated witness symbol remains in final E1 proof
```

The current implementation is approaching that but does not yet complete it.

The most important unresolved Skolem subcase is proposition-valued choice.
Set-valued choice can be related to the live Megalodon constants `Eps_i` and
`Eps_i_ax` in the focused file. The certificate basis also contains
`Eps_prop` and a proposition-choice principle used to justify
proposition-valued Skolem witnesses. In the focused `UnionI` source file there
is no live `Eps_prop` declaration. Therefore an E1 proof may not simply keep
that certificate-side symbol. The next implementation choice is either to
derive the needed proposition-choice witness from the live classical context
(`xm`, `FalseE`, proposition extensionality, and equality transport), or to
introduce a carefully reviewed source/preprocessing object that eliminates the
prop-valued Skolem witness before final theorem closure. Treating `Eps_prop`
as a hidden bridge assumption would violate the audit-driven trust boundary.

## AVATAR and SAT Reasoning

AVATAR remains a major open problem. It cannot be treated as a free bridge
from split components to the final refutation.

Recent progress:

- Vampire emits more AVATAR split metadata.
- Megalodon can replay a focused multi-variable AVATAR split shape.
- The saved `UnionI` certificate gets past the previous multi-variable split
  blocker.
- A focused regression fixture covers a component with several quantified set
  variables and a later SAT refutation.
- The July 20 diagnostics identified an actual final-composition leak of a
  certificate-local split symbol such as `split_4`.
- A split-only replacement pass can discharge leaked AVATAR split symbols in
  the focused `UnionI` proof fragment.

The limitation is that AVATAR proof replay is not solved generally. The final
proof still interacts with Skolem witness cleanup and certificate-local choice
symbols. The current cleanup path is too entangled with the large native
preprocessing replay code.

The final design should choose one of two explicit strategies:

1. Lower AVATAR to explicit SAT/RUP-style proof objects plus checked links
   from split atoms to clauses.
2. Define a small Megalodon-checked AVATAR layer with exact component,
   split-atom, branch, and SAT-conflict data.

Avoiding AVATAR-heavy proofs is acceptable only for a deliberately scoped
early milestone. It cannot be the final solution because serious Vampire
proofs frequently use AVATAR.

## Current `UnionI` Frontier

The focused `UnionI` case is the most useful current representative because
it combines many of the hard boundaries:

- original source theorem;
- live local binders and hypotheses;
- source theorem argument `UnionEq`;
- generated set/definition facts;
- negated conjecture refutation;
- Skolemization;
- choice;
- AVATAR splitting;
- final classical refutation-to-goal composition.

The direct detached check passes. The command used for the passing detached
check was essentially:


## What Has Been Done

The project has done the following substantial work:

1. Replaced the initial Python-heavy proof skeleton path as the qualifying
   direction.

   Python remains useful for inspecting corpora, summarizing proof shapes, and
   classifying failures. It is no longer the trusted path for proof
   reconstruction.

2. Added a native Vampire certificate format.

   Vampire emits Megalodon-oriented S-expression certificates. Megalodon
   parses them natively and works with Megalodon syntax and proof-term
   structures instead of translating through ad hoc Python scripts.

3. Added strict certificate and source-map validation.

   The checker validates source formulas, roles, origins, and source
   obligations. It distinguishes original facts from generated and unresolved
   facts.

4. Added native proof-term elaboration for selected clausal and preprocessing
   fragments.

   The checked fragments use Megalodon's proof-term checker. The old
   transitional known behavior is classified as diagnostic only.

5. Added source-context resolving foundations.

   Global knowns, theorem hashes, local hypotheses, definitions, generated
   reflexivity obligations, and conjecture entries are handled separately.

6. Improved equality, demodulation, and paramodulation metadata.

   Vampire now exposes more exact data, reducing the need for Megalodon-side
   guessing.

7. Improved Skolem metadata and proof-term handling.

   Parent quantifiers, introduced symbols, aliases, and branch/witness
   contracts are better represented. Several earlier Skolem blockers moved
   forward.

8. Improved AVATAR split handling.

   A focused multi-variable AVATAR split case now replays in the detached
   certificate path.

9. Added live-basis expansion experiments.

   The source-command path can replace some fixed certificate basis principles
   with live Megalodon proofs, especially for double negation, `not`/`False`,
   proposition extensionality, and set choice.

10. Identified the current final-composition bug class.

    Diagnostics now report missing live references and final proof-shape
    mismatches. The current known leaks are AVATAR split symbols and generated
    Skolem witness symbols in the final source-command proof candidate.

  expansion.
- A standalone Megalodon small-kernel checker/elaborator module.
- A complete Smolka-style source/preprocessing proof-producing layer.
- General Skolemization proof reconstruction.
- General AVATAR proof reconstruction.
- General original-context composition for negated conjecture refutations.

  terms.
- A final guarantee that no certificate-derived `Known` proposition enters

The project should therefore not be described as finished. It should be

clear current frontier.

## Main Problems and Risks

### Risk 1: Recreating a Reconstruction Prover in Megalodon

The largest implementation risk is continuing to grow `src/vampire_cert_v1.ml`
with special cases. Megalodon should check explicit proof data. It should not
reconstruct missing substitutions, pivots, literal choices, rewrite positions,
or Skolem dependencies by search.

Mitigation:

- Move proof detail to Vampire.
- Keep Megalodon rules small and fail-closed.
- Extract small modules from the importer.
- Reject unsupported rule names in counted modes.

### Risk 2: Hidden Bridge Assumptions

The July 16 audit showed how easy it is to smuggle a bridge through a dynamic
`Known` table. A future run could accidentally do the same through a live
basis expander, cleanup replacement, or source binding.

Mitigation:

- Audit every `Known` in the final proof.
- Distinguish original source knowns from certificate-derived knowns.
- Check final proofs under a proof delta containing only approved library
  basis, original source facts, and generated definitional facts with proof
  terms.

### Risk 3: Treating Skolem Symbols as Axioms

Generated Skolem symbols cannot remain unconstrained in final E1 proofs. They
must be tied to choice/epsilon witnesses or explicit transformation proofs.

Mitigation:

- Require dependency/sort/witness metadata from Vampire.
- Represent Skolemization as a proof-producing Smolka object.
- Ensure generated symbols are eliminated, definitionally expanded, or
  conservatively introduced with checked proofs.

### Risk 4: Source Names Rather Than Source Proofs

Recovering original names is useful, but name recovery alone is not proof
reconstruction. A source ID must resolve to a live proof or generated
definitional proof whose proposition matches the exported formula under the
right binder context.

Mitigation:

- Use source maps, hashes, and semantic formula comparison.
- Keep local hypotheses and local definitions separate.
- Treat conjecture negation only at final composition.

### Risk 5: AVATAR Is Deferred Too Long

Many serious Vampire proofs use AVATAR. If all near-term progress avoids
AVATAR, the system may look better than it is.

Mitigation:

- Use `UnionI` and selected longer saved proofs as AVATAR frontier cases.
- Decide between SAT/RUP lowering and a small AVATAR checker layer.
- Do not count AVATAR component assumptions as proof inputs.

### Risk 6: Testing Can Waste Time

Repeated sequential Vampire runs are expensive and often repeat known search
failures.

Mitigation:

- Cache exported THF problems.
- Run Vampire once per problem with <=10 seconds.
- Parallelize 10 to 20 jobs for broad gates.
- Iterate on saved proofs for focused failures.
- Use broad tests only after a focused fix is validated.

## Recommended Next Work

The next useful work should be narrow and proof-producing.

Step 1: Fix the current `UnionI` cleanup gating.

The heavy grouped Skolem CPS cleanup should remain opt-in. Lightweight final
symbol cleanup should handle AVATAR split atoms and generated witness symbols
without entering the expensive grouped CPS path. This is a focused code fix
and should be followed by exactly one focused source-command run under
`/project/tmp`, not a broad suite.

Step 2: Make the final proof reject all unexpanded certificate-local symbols.

Before trying to prove more theorems, add or enforce a final scan:

```text
No #In/#Union certificate heads.
No split_N symbols.
No sK_N symbols unless conservatively defined and expanded.
No certificate-local Eps_i/Eps_prop or choice theorem unless replaced by live
Megalodon basis proofs.
No certificate-derived Known propositions.
```

Step 3: Finish `UnionI` as an E1 theorem.

The next credible milestone is one nontrivial original-context theorem after
`Empty_eq`, preferably `UnionI`, closed by a Vampire certificate and checked
Megalodon proof term.

Step 4: Extract the source-context API.

Make source proof resolution explicit. The final composition path should
receive resolved source proofs, generated set equality proofs, local
hypotheses, and conjecture negation data as structured values.

Step 5: Specify and implement the first Smolka transformation objects.

Start with the transformations that block `UnionI`: source input, generated
set equality/definition, a single Skolemization/choice pattern, CNF
projection, and AVATAR split boundary.

Step 6: Move more macro expansion to Vampire.

For frequent inferences, Vampire should emit primitive chains with exact
substitutions, positions, sorts, and selected literals. Unit-resulting
resolution, demodulation, and superposition/paramodulation remain high-value
targets.

Step 7: Grow E1 results gradually.

After `UnionI`:

```text

E1_PASS 100
```

Do not jump to broad pass counts until the first and tenth original-context
proofs are real.

## Current Outlook

The project is not complete, but the current obstacle is much more sharply
defined than it was in the early reports.

The promising facts are:

- The native certificate path exists.
- The source-map and source-obligation machinery exists.
- Vampire emits much richer proof details than before.
- The dynamic-`Known` trust problem has been recognized and reclassified.
- The detached `UnionI` certificate checks in native preprocessing proof-term
  mode.
- The current source-command failure points to live proof composition and
  generated-symbol cleanup, not to proof search.

The concerning facts are:

- The final E1 goal is still not achieved.
- There is no 100-theorem original-context suite.
- `src/vampire_cert_v1.ml` remains too large and too central.
- The Vampire certificate emitter still lacks a clean internal primitive IR
  builder.
- Skolemization and AVATAR are still not fully proof-producing layers.
- The latest source-command proof fragment still contains a
  proposition-choice/Skolem dependency that has not been eliminated into live
  Megalodon proof terms.

The best next milestone is not another broad reportable pass count. It is a
single, audited, original-context `UnionI` proof:

```text
Vampire proves exported UnionI THF in <= 10 seconds.
Vampire emits a native certificate.
Megalodon checks the certificate and source bindings.
Megalodon composes the refutation into the live theorem.
The final proof term contains no aby, admit, bridge, generated Skolem leak,
AVATAR split leak, certificate-local equality, or certificate-derived Known.
```

Once that exists, the project will have a concrete end-to-end template for
source linkage, set definitions, Skolemization, AVATAR, choice, and final
classical composition. Then a ten-theorem E1 milestone is realistic. Only
after that should the 100-theorem goal be treated as an engineering scaling
problem rather than an unresolved architecture problem.

## Bottom Line

The project has moved from an exploratory skeleton generator toward a real
certificate-and-proof-term architecture. It has useful native infrastructure,
good source metadata foundations, improved Vampire-side proof detail, and a
focused detached `UnionI` certificate that checks.

The final goal is still open. The next decisive proof of progress is not a
larger structural pass count. It is one source-linked original Megalodon
theorem, preferably `UnionI`, reconstructed from a Vampire certificate and
checked without admissions or hidden assumptions. The current work should stay
focused on that boundary: source-context glue, Smolka-style transformation
proofs, Skolem/choice conservativity, AVATAR split elimination, and live-symbol
cleanup in the final proof term.
