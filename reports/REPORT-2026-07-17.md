## Executive Summary

The project is not finished. The central goal remains:

```text
Take a Vampire proof over THF exported from a Megalodon development,
reconstruct it as a native Megalodon proof term,
and compose it back into the original Megalodon theorem context,
with no admit, no aby, no incomplete QED, no bridge assumptions,
and no certificate-derived Known facts.
```

That goal is still not achieved in general. The most important missing
deliverable is E1 original-context reconstruction: the proof must be glued to
the original Megalodon theorem, local hypotheses, local definitions, library
lemmas, generated `set` equalities, and final conjecture discharge. Current
work has built significant infrastructure for that, but it has not completed
the end-to-end path.

The direction of the project is now substantially better than in the early
iterations. The early Python translator and large Megalodon-side textual
replay were useful exploration tools, but they are not the qualifying path.
The current intended path is:

```text
Vampire primitive certificate IR
  -> canonical S-expression certificate
  -> Megalodon small-kernel parser/checker
  -> native Syntax.pf proof terms
  -> original Megalodon source/context composition
```

The major architectural correction came from the Prover9/Ivy analysis and the
July 16 audit. The project should not ask Python or a large OCaml importer to
rediscover Vampire's proof choices. Vampire should expand complex proof steps
while it still has the exact selected literals, substitutions, positions,
sorts, and parent clauses. Megalodon should then check a small explicit proof
object.

  July 16 audit's main trust-boundary criticism.

- No general E1 original-context proof reconstruction exists yet.
- The Vampire primitive object is still a migration layer. Much of it is
  structured rendered data, not fully typed Vampire terms, literals,
  substitutions, positions, and clauses.
- The Megalodon checker is still too monolithic. `src/vampire_cert_v1.ml`
  remains a large parser/checker/emitter/oracle that should be split into
  smaller kernel, elaboration, and source-context modules.
- Smolka-style source-to-clause transformations are only partially
  proof-producing. Skolemization, FOOL, ENNF, CNF projection, definition
  folding, and source formula comparison all have useful pieces, but the
  complete proof-producing transformation layer is not done.
- The original-source hash story is only partially solved. The new resolver
  addresses the common case where the THF source map carries a proposition
  hash but the live Megalodon environment knows the theorem by proof hash.
  Remaining blockers include real-development local-context composition,
  generated-definition transport, set-command obligations in live E1 examples,
  and final conjecture discharge for nontrivial non-equality goals. Equality
  orientation and expanded equality forms now have a first checked path, but
  only in focused cases and source-context recovery, not as a general E1
  solution.
- The concrete cached real cases `hammer.11453.77` and `hammer.11703.242`
  expose the current
  source-context/live-context problem in a cleaner way than before. Its native
  clausal cores check 65 and 44 proof-term steps respectively. The standalone
  origin-loaded probes and the live focused runs show two source-glue patterns:
  `11453` mainly exercises loaded known facts plus expanded equality transport,
  while `11703` exercises a loaded known theorem, four live local facts, and
  conjecture-boundary handling. The remaining issue is to generalize this
  beyond two focused equality-shaped targets to real-development E1 examples
  with varied final goals, generated `set` obligations, larger source
  contexts, and nontrivial Smolka/preprocessing transformations.
- The latest parallel batch changes this picture from two isolated
  representative targets to eleven focused real targets. The additional
  targets mostly increase confidence in source-context recovery, equality
  transport, local fact matching, and local-type aliasing. They do not yet
  settle Skolemization, CNF projection, AVATAR, or general macro lowering.
- AVATAR is not yet fully certified as a small proof object. Some restricted
  native proof-term fixtures exist, but the general SAT/RUP-style object is
  unfinished.
- The project still lacks a held-out E1 suite of original Megalodon theorems
  reconstructed with no trust-boundary exceptions.

My current assessment is:

- The direction is now correct.
- The earlier pass-count-oriented work was too optimistic and sometimes
  counted structural checks as proof reconstruction.
- The current URR primitive-chain work is the right kind of progress: small,
  Vampire-side, explicit, auditable, and increasingly consumed by Megalodon's
  native proof-term checker.
- The next milestone should be a small number of full E1 examples, not another
  broad structural `PASS 100`.

## Original Task and Operating Constraints

The original task was to use Vampire's existing proof reconstruction/export
work, especially the Lean-oriented code, and modify the approach so Vampire
proofs are reconstructed in Megalodon. The important observation was that
Lean and Megalodon are similar in the relevant sense: both check proof terms.
The final artifact should not be a script full of declarations and admits; it
should be a proof term or proof-term-producing path accepted by Megalodon.

The constraints clarified during the project are:

- Use THF/TPTP problems exported from Megalodon.
- Run Vampire with `--input_syntax tptp`, generally in CASC mode.
- Do not run Vampire for more than 10 seconds per problem.
- Avoid repeatedly rerunning unsuccessful Vampire searches. Identify the
  solvable problems once, then iterate on those proofs.
- Use `/project/tmp` for all temporary operations that require temporary
  storage.
- Run broad export/Vampire/check jobs in parallel, usually with 10 to 20
  workers.
- Do not use `aby` in final scripts, because it is implemented as an admission
  in Megalodon.
- Assume classical logic. Excluded middle `xm` and usual logical constants
  such as `or`, `False`, and equality are available from the Megalodon library
  and context.
- Avoid theorem-specific or library-specific hardwiring. The system must
  reconstruct Vampire proofs over arbitrary Megalodon libraries, not just the
  current benchmark corpus.
- TPTP axioms generated from Megalodon `set` commands may have no
  corresponding source claims. Those should be proved explicitly, usually by
  reflexivity or conversion.
- Recover original Megalodon names, lemmas, definitions, and local context
  entries from the source-map/name-mangling information rather than inventing
  private names.
- Prefer exporting richer proof detail from Vampire over guessing in Python or
  Megalodon. Vampire knows the selected literals, substitutions, positions,
  and sorts at the time it performs an inference.

The Prover9/Ivy lesson is now the controlling architectural principle:

```text
Expand complex prover inferences inside the prover into a small certificate
kernel, then have the external checker verify only that small explicit object.
```

The trajectory is as follows.

The first phase used Python to parse Vampire proof output and emit Megalodon
proof skeletons. That produced useful inspection data and made the proof shape
concrete for humans. It also demonstrated that declarative `claim` skeletons
could be connected to many original names. However, it was not a sound final
architecture. It duplicated proof reconstruction outside both Vampire and
Megalodon, depended on heuristic parsing, and could produce admission-heavy
scripts.

The second phase introduced native S-expression certificates emitted by
Vampire and parsed by Megalodon. This moved the active path into the two
relevant systems. It enabled source-map validation, closed-mode checks,
negative fixtures, and parallel cached test harnesses.

The third phase added stricter source linking and closed-mode validation. This
removed several obvious loopholes from the early pipeline. It became possible
to reject missing source names, incompatible roles, and certificate inputs that
did not match exported THF declarations.

The fourth phase overgrew on the Megalodon side. The large OCaml importer in
`src/vampire_cert_v1.ml` accumulated parsing, source-map logic, THF parsing,
certificate validation, textual script emission, proof-term experiments,
preprocessing transformations, and many inference-specific replay paths. This
made progress visible but moved too much responsibility away from Vampire.

The fifth phase pivoted toward native `Syntax.pf` checking and a small kernel.
This produced genuine seeds, especially for focused core proof-term checks.
However, the July 16 audit found that some native preprocessing checks were
installing certificate-derived `Known` propositions and then applying them.
That is a hidden bridge assumption. The current branch accepts that critique.

The current phase is the Prover9/Ivy-style phase. The goal is no longer to
grow a Megalodon-side reconstruction oracle. The goal is to make Vampire emit
explicit primitive proof objects and make Megalodon check them with a small,
auditable kernel and a separate source/transformation layer.

## Evidence Classes

The project now uses evidence classes rather than ambiguous pass counts.

E1 means original Megalodon theorem reconstruction. This is the target:
native Megalodon proof terms in the original theorem context, with no
admissions, no bridge assumptions, no certificate-derived `Known` facts, and
the final contradiction composed back into the original goal.

E2 means a closed native `Syntax.pf` proof of a live Vampire certificate, but
still bound to exported THF rather than fully composed into the original
Megalodon source theorem.

E3 means focused or synthetic primitive-kernel native proof-term checks. These
can be valuable and genuine, but they are not yet full reconstruction of a
real exported development.

E4 means structural certificate/source/metadata validation and transitional
diagnostics. Strict live `PASS 100` runs are E4 unless they also build and
check proof terms. Transitional preprocessing runs with
`MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1` are also E4.

This classification matters. Earlier reports sometimes treated large pass
counts as stronger evidence than they really were. The current report does not
count a certificate as reconstructed merely because Vampire emitted it and
Megalodon parsed it.

## Current Architecture

The current architecture has five layers.

The first layer is the Megalodon source exporter. It exports Megalodon
developments as THF/TPTP problems. It also emits source-map information that
records how TPTP declarations correspond to original Megalodon symbols,
lemmas, local assumptions, definitions, generated facts, and conjecture
boundaries.

The second layer is Vampire proof search and proof export. The Vampire fork
contains `Shell/MegalodonChecker/MegalodonChecker.cpp` and
`Shell/MegalodonChecker/MegalodonKernelSyntax.{hpp,cpp}`. It emits native
S-expression certificates containing proof units, clauses, formula payloads,
source references, and `kernel_v1` metadata. This is the layer that should
eventually own macro expansion into primitive proof objects.

The third layer is Megalodon's certificate parser and structural checker. Most
of it still lives in `src/vampire_cert_v1.ml`, with shared kernel vocabulary
now extracted into `src/vampire_kernel_syntax.ml`. This layer parses
certificates, validates source metadata, checks rule contracts, rejects
unsupported rules, validates primitive expansion metadata, and runs smoke and
audit harnesses.

The fourth layer is Megalodon's native proof-term elaboration. This layer
constructs `Syntax.pf` terms for the small supported kernel and focused
preprocessing fixtures. It checks them with Megalodon's proof checker. The
important trust-boundary invariant is that counted modes must not install
certificate-derived `Known` theorems.

The fifth layer is original-context composition. This is the least complete
layer. It must map source references back to original Megalodon theorem
context entries, use library-known hashes for global lemmas, use local
hypotheses at the right binder indices, prove generated `set` equalities by
reflexivity/conversion, unfold definitions conservatively, and convert the
exported refutation back into the original goal.

The intended end state is a much cleaner module split:

- `vampire_kernel_syntax.ml`: certificate syntax, rule names, and contracts.
- `vampire_kernel_check.ml`: small structural and kernel checks.
- `vampire_kernel_elab.ml`: `Syntax.pf` elaboration for primitive kernel
  steps.
- `vampire_source_context.ml`: original Megalodon source-context resolution.
- `vampire_cert_v1.ml`: legacy compatibility parser/oracle during migration,
  not the main reconstruction engine.

## What Has Been Done

### Python skeleton reconstruction

The early Python tools parsed Vampire output and emitted Megalodon-style proof
skeletons. They were useful for understanding proof shape, name mangling, and
Megalodon syntax. They helped reveal that humans need proof skeletons linked
to original symbols, not anonymous proof-step dumps.

This phase also established that:

- Vampire could solve a nontrivial subset of the exported THF problems.
- Megalodon could export enough source-map information to recover many
  original names.
- A skeleton with declarative `claim` blocks is useful for human debugging.
- Some hard proof families recur frequently: URR, superposition,
  demodulation, FOOL transformations, skolemization, CNF/ENNF, AVATAR, and
  definition folding.

However, the Python path is no longer considered qualifying. It can remain a
diagnostic tool, but it should not reconstruct missing proof data by search or
guessing. In particular, Python should not infer pivots, substitutions,
positions, hidden clauses, or AVATAR state that Vampire already knows.

### Native S-expression certificates

Vampire now emits native S-expression certificates for Megalodon. These are
substantially better than the early textual proof output. The certificates can
record:

- proof unit ids;
- rule names;
- formula and clause payloads;
- parent links;
- source names and source roles;
- variable sorts;
- substitutions;
- selected literals;
- rewrite positions and directions;
- substituted parent literals and clauses;
- formula transformation metadata;
- Skolemization metadata;
- AVATAR split/component/refutation metadata;
- `kernel_v1` metadata and primitive-expansion contracts.

Megalodon parses these certificates natively. It has positive and negative
fixtures for many rule families. The smoke suite exercises both accepted and
rejected certificates, which is important because many previous defects were
trust-boundary mistakes rather than ordinary syntax errors.

### Closed and source-linked checking

The project added strict and closed checking modes. These modes prevent some
classes of unsound success by rejecting missing source maps, unsupported
rules, unknown derived assumptions, and source mismatches.

Important improvements include:

- source-map parsing for THF declarations;
- formula comparison between source-map declarations and certificate inputs;
- rejection of source-map/hash mismatches;
- handling of copied conjecture aliases;
- source-map support for generated `set_reflexivity` facts;
- source-map support for local facts and local definitions;
- handling of THF `$false` as an empty clause at the source boundary;
- explicit source-obligation auditing.

These checks are valuable, but by themselves they are E4. They show that the
certificate is well connected to the exported THF problem. They do not prove
Vampire's inferences unless proof terms are constructed and checked.

### Trust-boundary reset after the July 16 audit

The July 16 audit identified the most serious trust issue in the native
proof-term experiments: some preprocessing paths dynamically installed a
certificate-derived proposition as a `Known` theorem and then applied it. A
proof term that uses such a theorem may pass `check_propofpf`, but the theorem
was not actually proved.

That pattern is equivalent to adding a hidden bridge assumption. The current
branch treats it as non-qualifying.

The counted native proof-term paths now traverse checked proofs and reject
forbidden certificate-derived `Known` names, except for a fixed reviewed
logical basis. The old transitional behavior is still available only when
explicitly enabled for diagnostics. Reports and tests classify those runs as
E4.

This is a methodological correction more than a numerical one. It prevents
the project from improving pass counts by hiding unsupported proof obligations
inside the known-theorem table.

### Kernel syntax extraction in Megalodon

Megalodon now has an extracted kernel syntax boundary in
`src/vampire_kernel_syntax.ml` and its interface file. This module owns the
shared schema string, accepted kernel rule vocabulary, primitive-expansion
contracts, and rule support checks.

This extraction is small but important. It reduces one class of monolith
growth in `src/vampire_cert_v1.ml` and gives both tests and implementation a
single place to ask which `kernel_v1` rules are supported. The strict checker
uses this module to reject unsupported rules. A negative fixture checks that
behavior.

The extraction is not enough by itself. The next Megalodon-side extraction
should move actual primitive-kernel checking and proof-term elaboration into
separate modules. New broad proof power should not continue accumulating in
`vampire_cert_v1.ml`.

### Kernel syntax extraction in Vampire

Vampire now has `Shell/MegalodonChecker/MegalodonKernelSyntax.{hpp,cpp}`.
This C++ boundary owns the shared kernel schema string, supported rule checks,
primitive-expansion field generation, and increasingly the standard layout of
certificate metadata.

Earlier versions of the exporter assembled many `step_extra "kernel_v1"`
fields directly inside `MegalodonChecker.cpp`. That made it hard to audit the
certificate vocabulary and hard to migrate toward a real primitive object.
The current branch has moved several field clusters into named records and
serializer helpers.

The current Vampire boundary includes migration records for:

- kernel step ids and rule names;
- parent and conclusion metadata;
- literal-selection metadata;
- rewrite metadata;
- URR trace metadata;
- AVATAR component, definition, split, dependency, and refutation metadata;
- primitive-expansion chain metadata;
- rendered-domain wrappers for terms, formulas, literals, clauses,
  substitutions, positions, and units.

These are still rendered-domain records. They are not yet fully typed Vampire
kernel objects. The value is that the structure is now explicit and localized,
so the next step of replacing rendered wrappers with typed objects is
mechanical rather than a full redesign.

### Source-context work

The source-context layer has improved, but it is not complete.

It can now distinguish and report several source categories:

- hash-backed global known facts;
- local hypotheses;
- local definitions;
- generated facts;
- conjecture facts;
- unresolved facts;
- generated `set_reflexivity` obligations.

The checker has smoke coverage for source bindings and generated
set-reflexivity. It also resolves some source-map definitions in native source
context, and it handles THF `$false` source declarations as empty clauses.
The latest URR core proof audit also makes the source-context gap visible in
a measurable way. The two checked URR-containing closed certificates produce
native core proof terms, but still report remaining source assumptions. The
audit now classifies those assumptions by source kind and emits sampled issue
records. On the earlier cached URR audit that first exposed the
source-context gap:

- `hammer.11453.77` passes the native core proof-term check, then reports
  `known=6 local=0 definition=0 generated=0 conjecture=1 unresolved=0`.
- `hammer.11703.242` passes the native core proof-term check, then reports
  `known=1 local=4 definition=0 generated=0 conjecture=1 unresolved=0`.

This was useful because it gave the next E1 work item directly. The remaining
assumptions were no longer anonymous clauses. They were original global facts
such as `SNo_1`, `SNo_eps_1`, `add_SNo_1_1_2`, `mul_SNo_distrR`,
`mul_SNo_oneL`, `add_SNo_cancel_L`, local facts such as `Hguv`, `Lfv3`,
`Lfu3`, `L2n3`, and the final conjecture boundary. Those assumptions must be
discharged through original Megalodon lemmas, local hypotheses, local
definitions, generated `set` equalities, and the conjecture boundary before
the result can count as E1.

A focused origin-loading probe on `examples/hammer/100thms_12_h.mg` exposed a
specific hash mismatch issue. The THF source-map hashes for known facts match
source/proposition identifiers, while the Megalodon runtime theorem table
uses the actual proof hash for `Known`. Some facts therefore cannot be
resolved by testing the source-map hash directly as a `Known` proof. The
right source-context operation is:

1. read the source-map original name and source proposition;
2. resolve the original name through the loaded Megalodon theorem table;
3. build `Known theorem_hash`;
4. check with Megalodon's proof checker that this proof has the source-map
   proposition.

That keeps name recovery useful while avoiding an unsound "same name means
same theorem" shortcut.

The committed source-linking patch implements the first version of that
operation. The `source_context` now carries the loaded Megalodon known-name
table. For a global known source binding, the resolver tries these candidates:

- the source-map hash;
- the original Megalodon source name resolved through the loaded known table;
- the TPTP/source-map name resolved through the loaded known table.

It accepts a candidate only if the resulting proof term checks against the
exact exported source-map proposition. It also handles a common exported-shape
case where a known theorem has an unused leading `forall` binder by wrapping
the proof in a corresponding type lambda and rechecking. It also has a narrow
equality-symmetry synthesis path for exported source facts that are expanded
or oppositely oriented forms of Megalodon's library equality. The same
source-map aliases are now visible in source-application proof filtering and
in the final native certificate proof-checking delta, while hash-keyed
definitions are preserved.

This is real E1 infrastructure progress, but it is not yet E1 completion. On
the representative origin-loaded probe for `hammer.11453.77`, the source audit
now improves to:

```text
known_checked=6 known_missing=0 known_mismatch=0 conjecture_checked=1 unresolved=1
```

The earlier alias failure of the form `expected: (SNo _0)` versus
`actual: (#SNo _0)` is gone, and the earlier equality-orientation mismatch is
also gone. The relevant equality issue matters because Megalodon equality is
the library equality

```text
eq A l r := forall Q:A -> A -> prop, Q l r -> Q r l
```

so the correct fix was not a private equality or a bridge axiom. The resolver
synthesizes the needed equality symmetry from the checked original theorem
proof and then rechecks the exported proposition.

The same representative case then exposed a separate FOOL boundary. The native
core proof needed to move between a proposition and equality to `$false`,
analogous to the existing equality-to-`$true` support. Commit `f002937` adds
that narrow FOOL false-equality proof conversion. With the source-linking and
FOOL false-equality fixes together, the origin-loaded probe for
`hammer.11453.77` checks 65 native core proof steps and reports:

```text
Vampire certificate v1 native core source assumptions remaining 1.
Vampire certificate v1 native core source assumptions remaining by kind
known=0 local=0 definition=0 generated=0 conjecture=1 unresolved=0.
```

This is close to the E1 boundary, but it is still not E1. The exported
refutation has been checked against the original loaded known facts, but it
has not yet been composed through the live `aby` replacement path into the
original Megalodon theorem statement with the final conjecture discharged.

The remaining boundary is now the final refutation-to-goal composition. The
checker has a closed proof of contradiction from the exported source facts and
one remaining conjecture assumption. The live theorem replacement path still
has to turn that into a proof of the current Megalodon goal, using the already
assumed classical context and the Megalodon library logical constants, not by
installing a certificate-derived theorem.

The target API is still roughly:

```ocaml
type source_proof =
  | GlobalKnown of string * Syntax.tm
  | LocalHyp of int * Syntax.tm
  | Definitional of Syntax.tm * Syntax.pf
  | Generated of Syntax.tm * Syntax.pf
  | Unresolved of string * Syntax.tm

type source_context = source_id -> source_proof
```

The missing part is not the datatype idea; it is the full operational
composition:

- resolving every global theorem to the correct existing Megalodon known hash
  even when the THF source map contains a proposition hash rather than the
  theorem proof hash;
- preserving local hypothesis indices across export/import;
- accounting for binder shifts introduced by local definitions and generated
  variables;
- supplying definitions to conversion rather than as arbitrary proof facts;
- proving generated `set` equalities by reflexivity/conversion;
- treating the negated conjecture only at the final refutation-to-goal
  boundary;
- returning a proof in the original theorem context rather than only in an
  exported-THF context.

This remains the main E1 gap.

The most recent committed source-context fixes narrow this gap further for
`hammer.11703.242`. The problem was not that the original theorem
`add_SNo_cancel_L` was unavailable; it was that source-map `type` symbols such
as `SNo` and `add_SNo` were being treated as ordinary generated proof
variables while reconstructing the exported source proposition. That
over-generalized the exported proposition, so the loaded theorem could not
check against it. Commit `03f9dfa` parses source-map type declarations into
the native symbol table, excludes source-map external symbols from the
generated proof-variable prefix, improves mismatch diagnostics, and allows
the resolver to instantiate leading universal binders of a loaded theorem
with closed terms from the exported proposition before rechecking.

Commit `fb7af99` extends the same source-context treatment to source-map
`local_type` declarations. These declarations describe live local variables
introduced around the `aby` call. They must be available while parsing local
facts and conjectures, but they must not be treated as external global symbols:
the local terms still belong to the live Megalodon proof context. The focused
`local_term_source_live` smoke fixture now checks this behavior by exporting a
small theorem with local variables `p` and `x` and a local hypothesis `Hpx`;
the source-context audit reports one local fact and one conjecture, with no
unresolved source binding.

After this change, the focused origin-loaded audit for `hammer.11703.242`
reports:

```text
Vampire certificate v1 source context audited total=7
known_checked=1 known_missing=0 known_mismatch=0
local_checked=0 local_missing=4 local_mismatch=0 ...
Vampire certificate v1 native core source assumptions remaining by kind
known=0 local=4 definition=0 generated=0 conjecture=1 unresolved=0.
hammer.11703.242 ORIGIN_PARTIAL_PASS
```

This is a meaningful source-linking improvement, but it is still not E1. The
four local facts are live proof-context obligations, not detached global
theorems. They must be recovered at the actual `aby` site from the current
Megalodon local proof context and then composed with the final conjecture
boundary.

### Smolka-style transformation work

The project has accumulated useful source-to-clause transformation support,
but it remains partial and too mixed into the large importer.

Handled or partially handled areas include:

- source and formula inputs;
- formula copies;
- rectification metadata;
- ENNF transformations;
- CNF literal and formula projection metadata;
- FOOL Boolean lifting and equality-to-true conversions;
- predicate definition input and fold chains;
- skolemization metadata, introduced symbols, dependencies, and substitutions;
- source formula comparison for some higher-order/lambda cases;
- generated set-reflexivity;
- selected direct Skolemization proof-term fixtures using classical choice.

The important design point is that these transformations should not become
clausal-kernel rules. They should form a separate proof-producing
source/preprocessing layer. Smolka-style transformation replay should take a
source formula proof and produce a checked proof of the clausified formula or
clause boundary. The small clausal kernel should then operate on that boundary.

Skolemization is the hardest part of this layer. Current work has handled some
direct cases with explicit generated definitions and classical choice, and it
has improved formula matching with Vampire's explicit substitution lists.
However, full dependent Skolemization across arbitrary exported Megalodon
developments is not finished. The checker must track introduced symbols,
dependency order, witness sorts, definitional unfolding, and the proof that
the Skolemized formula follows in the classical setting.

The Smolka-style work should be extracted and handled one transformation at a
time, with actual proof terms. Transitional `Known` implications are useful
only as E4 diagnostics.

### Equality and logical basis

The current direction is to use Megalodon's existing equality and logical
constants, not a private equality. Earlier scaffolding sometimes introduced
certificate-level equality encodings for convenience. That is not the target.
The final proof should use the equality and logical constants from the
Megalodon library/context.

The fixed logical basis can include reviewed classical principles such as
excluded middle, double-negation elimination, choice, and not-forall/existence
principles, assuming they are part of the intended Megalodon environment.
Those principles must be distinguished from certificate-derived facts. It is
acceptable to use a reviewed library theorem. It is not acceptable to create a
new `Known vampire_step_123` theorem whose proposition is exactly the missing
certificate inference.

## Current Status by Area

### Vampire-side primitive IR

Status: in progress, not complete.

The Vampire side now has a real boundary module and several structured
rendered records. That is meaningful progress. The exporter is no longer only
a collection of open-coded string fields.

However, the final Prover9/Ivy-style object should be stronger:

```text
struct MegalodonPrimitiveStep {
  id;
  rule;
  parent ids;
  conclusion clause/formula;
  selected literal/equality indices;
  rewrite position and direction;
  substitution;
  variable and symbol sorts;
  source/preprocess payload when rule is not clausal;
}
```

Current records are still mostly rendered strings with domain labels. The
next step is to use Vampire's internal term, literal, substitution, and
position information directly when constructing primitive steps, then use a
single canonical printer.

### Megalodon-side small kernel

Status: seeded, not extracted enough.

Megalodon has genuine native proof-term seeds for parts of the clausal kernel
and focused fixtures. It also has strict checks that reject unsupported rules
and forbidden certificate-derived `Known` constants.

The remaining issue is structure. The proof-term checker and elaborator should
be extracted from the monolithic certificate module. New reconstruction power
should land in an isolated kernel elaborator, not in the legacy importer.

The stable clausal kernel should remain small:

- input boundary from proved source/preprocessing clauses;
- instantiate;
- resolve;
- factor;
- equality resolution;
- equality factoring;
- paramodulate;
- final contradiction marker.

`rename` should be handled as alpha-conversion or a restricted substitution
case, not as an uncontrolled broad inference. `truth_conflict` should probably
remain in the FOOL/source-preprocessing layer unless real clausal proofs show
it belongs in the kernel.

### Original Megalodon source glue

Status: partial infrastructure, with the first global-known resolver now
implemented in working state.

This is the biggest missing piece. The system has source-map parsing, source
categories, smoke tests, and some definition/set-reflexivity support. It does
not yet reliably produce an original-context theorem proof for arbitrary
Megalodon developments.

The newest source audit work improves observability rather than solving the
composition problem. It reports:

- `known_checked`, `known_missing`, and `known_mismatch`;
- `local_checked`, `local_missing`, and `local_mismatch`;
- definition, generated, conjecture, and unresolved source counts;
- sampled issue records containing the step id, kind, original name, hash,
  and reason.

The newest implementation follows the intended discipline for global knowns:
it may look up the original theorem or axiom name in the current environment,
but it still runs `check_propofpf` to verify that the found `Known` proof
proves the exact source-map proposition. It also brings source-map aliases
into the proof-checking delta so that original Megalodon names can be used
when checking source applications and final native certificate proofs.

The next source-glue implementation work is narrower:

- synthesize equality symmetry and other small library-derived source proofs
  when the original theorem is propositionally the right fact but has the
  opposite equality orientation or an expanded equality form;
- finish local-hypothesis and local-definition composition under the original
  theorem binders;
- compose the final negated-conjecture refutation back into the original
  Megalodon goal, including FOOL cases where Vampire represents the boundary
  as equivalence with `False` while the proof term is implication-to-`False`;
- keep generated `set` equalities as reflexivity/conversion proofs, not
  claims or imported assumptions.

The expert reviewer should treat this as unfinished. The design direction is
clear and the first name-to-known-hash repair is now present, but the
implementation has not reached the required E1 standard.

### Skolemization

Status: partial.

The project understands that skolemization must be classical and
proof-producing. There are direct proof-term fixtures and improved matching
for explicit substitutions and generated symbols. Some focused real cases
moved past earlier Skolem mismatches.

The remaining problems are:

- dependent Skolem functions across nested binders;
- stable introduced-symbol scoping;
- witness sort checking;
- interaction with definitions and source-map names;
- conversion between exported THF formulas and Megalodon terms;
- proof-producing composition with later CNF and clausal steps.

The next implementation should isolate skolemization into the
source/preprocessing layer and use explicit generated definitions plus choice
proofs, not dynamic `Known` implications.

### AVATAR

Status: useful metadata and restricted proof-term fixtures, not complete.

Vampire emits AVATAR split/component/definition/refutation metadata, and some
restricted native proof-term fixtures pass without transitional-known opt-in.
That is useful. It is not a full certificate for AVATAR.

The likely final approach should use either:

- an explicit SAT/RUP-style object for the propositional layer; or
- a separately checked AVATAR layer with split dependencies and refutation
  traces.

AVATAR should not be hidden inside a broad bridge theorem.

### URR

Status: best current macro-lowering vertical slice.

URR now has a visible primitive chain with parent/result/final-result checks
and rule-specific payload validation. This is the area that most resembles the
desired Prover9/Ivy path.

The next work is clear:

- consume the rule-specific payloads directly in the small-kernel elaborator;
- broaden the focused URR core-proof audit beyond the two currently cached
  URR cases as more live certificates are regenerated;
- elaborate every primitive chain into Megalodon `Syntax.pf`;
- remove reliance on the URR macro as a trusted rule.

### Broad test suite

Status: useful but not final.

The broad 100-case and 300-case live/cached runs are useful for integration.
They should be kept fast, parallel, and cached. Vampire should stay capped at
10 seconds. Temporary artifacts should remain under `/project/tmp`.

However, broad structural pass counts should not drive the next milestone.
The next meaningful milestone is a focused E1 gate: a small but real set of
original Megalodon theorems reconstructed end to end with no trust exception.

## Main Problems and Risks

### Risk 1: continuing monolith growth

`src/vampire_cert_v1.ml` and `MegalodonChecker.cpp` have grown too large. Some
growth has been productive, but the project should now enforce module
boundaries. The audits repeatedly warned that adding more replay heuristics to
the large importer is the wrong direction.

Mitigation:

- Put new primitive checking in `vampire_kernel_check.ml`.
- Put proof-term elaboration in `vampire_kernel_elab.ml`.
- Put source glue in `vampire_source_context.ml`.
- Keep `vampire_cert_v1.ml` as compatibility infrastructure.
- Keep moving Vampire certificate construction into
  `MegalodonKernelSyntax` and then into typed primitive-step builders.

### Risk 2: structural checks being reported as proof reconstruction

The project has many useful structural tests. It is tempting to report a broad
`PASS 100` as reconstruction evidence. That is wrong unless the run checked
native proof terms in a counted mode without bridge facts.

Mitigation:

- Continue using E1/E2/E3/E4 labels.
- Require every reported pass count to state its evidence class.
- Keep transitional-known runs opt-in and label them E4.

### Risk 3: Megalodon-side guessing

If the Megalodon importer guesses pivots, substitutions, positions, sorts, or
hidden formula transformations, it duplicates Vampire and becomes fragile.

Mitigation:

- Export exact detail from Vampire.
- Reject missing details in counted mode.
- Use Python only as diagnostics.
- Make primitive payloads required by rule.

### Risk 4: source-context ambiguity

Even if the exported THF proof is checked, E1 requires connection to the
original Megalodon theorem. Local hypotheses, definitions, set commands, and
the conjecture boundary can easily be mishandled.

The latest concrete instance of this risk is the distinction between
source-map proposition hashes and Megalodon theorem proof hashes. Treating
those as interchangeable loses real theorem identity information. Trusting
only recovered names is also too weak. The source resolver needs both:
name-based lookup into the loaded Megalodon context and proof-checker
confirmation against the exported proposition.

Mitigation:

- Define and implement the concrete `source_context` API.
- Add small original-context fixtures with local hypotheses and local
  definitions.
- Include at least one generated `set` equality proved by reflexivity.
- Include at least one theorem that requires final refutation-to-goal
  composition.

### Risk 5: skolemization unsoundness

Skolemization is classical and subtle in dependent/higher-order settings.
Treating it as a syntactic rewrite is unsafe.

Mitigation:

- Handle skolemization in a separate transformation layer.
- Use explicit introduced-symbol metadata and dependencies from Vampire.
- Use reviewed classical choice principles.
- Check witness sorts and binder scopes.
- Require proof terms in counted mode.

## Recommended Next Plan

The next work should be narrow and proof-producing.

1. Consume URR primitive chains as proof data.

   Implement Megalodon elaboration for the primitive steps rather than
   treating URR as a macro. The result should be an E2 proof-term check for
   real live URR-containing certificates. The current two-case URR core audit
   is the seed; the next step is to make the primitive payloads the normal
   data path rather than extra metadata.

2. Extract the primitive kernel checker.

   Move the kernel checker and proof-term elaborator out of
   `vampire_cert_v1.ml`. Avoid adding new broad replay power during the move.

3. Finish the source-context API.

   Start with a small committed fixture set:

   - one global known lemma;
   - one local hypothesis;
   - one local definition;
   - one generated `set` equality;
   - one final conjecture/refutation composition.

   The first concrete implementation unit, global-known resolution through
   the loaded original Megalodon environment, is now in working form. The next
   source-context unit should synthesize library equality symmetry from a
   checked original theorem proof, then handle local binders and final
   conjecture composition. Source-map proposition hashes should still not be
   used directly as theorem proof hashes when they differ from Megalodon's
   runtime `Known` ids.

4. Produce ten E1 examples.

   Use only problems already known to be solvable by Vampire under 10 seconds.
   Do not rerun broad Vampire search unnecessarily. Generate certificates in
   parallel, then check in parallel. The goal is ten real original-context
   reconstructions, not a large structural pass count.

5. Add Smolka-style transformations one family at a time.

   Handle rectification, FOOL, ENNF, CNF, definition folds, and skolemization
   as proof-producing transformations. Each family should have positive and
   negative fixtures, and broad tests should run only after the focused proof
   path works.

6. Re-run a held-out 100-theorem gate only after E1 exists.

   A fresh 100-case gate should measure the final architecture. It should not
   be used as a substitute for building the architecture.

## Current Bottom Line

The project has made real progress, but not the final proof reconstruction.
The important change is that the project now has a clearer trust boundary and
a better architecture.

The previous Python and broad Megalodon-side replay work was useful for
learning, but not the final path. The current path is to export a small,
explicit, Vampire-side primitive certificate and check it in Megalodon with
native proof terms. The URR primitive-chain work is the best current example
of that direction.

The immediate priority should be to turn that direction into an E2 and then
E1 result:

## Late July 17 Update: Original-Context Glue

After the main body of this report was first written, the work moved further

composing a checked Vampire refutation back into the original Megalodon
theorem context.

The immediate target was not a new broad pass count. It was the representative
origin-loaded case `hammer.11453.77`, where the native core checker already

That remaining assumption is the boundary between a refutation of the exported
THF negated conjecture and a proof of the current Megalodon goal. In other
words, the checker has proof data for "source facts imply contradiction with
the exported conjecture", but the live `aby` replacement still has to turn that
into a Megalodon proof term for the theorem currently being checked.

The latest committed work therefore focuses on this boundary rather than on
more Megalodon-side proof-search heuristics. Commit `1fffcd2` adds:

- recognition of the specific situation where Vampire proves an equality in
  the opposite orientation from the current Megalodon goal;
- a small equality-symmetry transport proof for positive equality goals, using

Commit `8145477` then threads the native core environment through that same

```text

actual:   SNo (eps_ 1) -> True
```

The exact pretty-printing varies with expansion, but the semantic issue is
the same. Source proofs proved the raw Megalodon proposition, while some
native core steps expected the lifted equality/iff-to-true form produced by
Vampire's FOOL translation.

Commit `5a5ecbb` closes that focused failure in the right trust-boundary
direction. The native core had been using a fixed helper proposition for
proposition extensionality:

```text
(p -> q) -> (q -> p) -> p = q
```

but the loaded Megalodon library theorem `prop_ext` at the same proof hash has
the library shape:

```text
iff p q -> p = q
```

The previous tempting workaround would have been to replace the loaded theorem
globally with the native helper theorem. That is unsafe in the original source
context because it reintroduces hidden helper facts and can invalidate other
loaded propositions. The committed fix instead rewrites proof terms locally:
when a native helper-shaped `prop_ext` application supplies two implications,
the final checker constructs an explicit `iff` proof using the loaded `iffI`
theorem, or a checked conjunction encoding if `iffI` is unavailable, and then
applies the real loaded Megalodon `prop_ext`. No certificate-derived `Known`
theorem is installed for this conversion.

- loaded known theorem recovery;
- local hypothesis recovery;
- local type alias recovery;
- compact versus expanded equality transport;
- final target-stop reconstruction inside the original large source file;
- generated `set` equality handling in the source-context smoke layer.

The key remaining blocker exposed by the same batch-development process is
Skolemization. The current representative is `hammer.11228.26`. Its native
certificate checks far enough to identify the precise missing proof-term
operation:

```text
u233: native core proof-term skolemization cannot instantiate dropped parent
      variable X1.
```

The relevant certificate data is already explicit. Vampire says that parent
variable `X1 : set -> prop` is replaced by the witness term `(sK0 X0)`, and
that the Skolem symbol depends on `X0`. The Megalodon side currently fails
because its Skolem proof-term helper only tries to instantiate parent
variables from the result variables, then falls back to type-based guessing.
The correct next step is to pass the Vampire-emitted Skolem substitution into
that helper and instantiate dropped parent variables from the explicit
certificate substitution. This follows the audit's recommendation: use the
detail emitted by Vampire, do not reconstruct or guess it in a side program.

The current status after this addendum is therefore:

- The broad architecture remains the Prover9/Ivy-style architecture:
  Vampire emits explicit primitive or transformation detail; Megalodon checks
  it with a small native proof-term path and then composes it into the
  original context.
- The project now has eleven focused real-target original-context
  reconstructions through the live `vampireaby` path, all using real Vampire
  and native Megalodon certificate checking.
- This is still not a general solution and not the requested final 100-theorem
  suite. It is a deliberately small parallel frontier for fast iteration.
- The next technical work should be Skolemization substitution replay, then
  CNF/ENNF/FOOL transformation proofs, then a broader parallel held-out suite
  only after those transformation gaps are represented by checked proof terms.
