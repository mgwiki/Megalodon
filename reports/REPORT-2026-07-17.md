## Executive Summary

The project is not finished. It has made real progress, especially in the
last branch, but it is not yet a general Vampire-to-Megalodon proof
reconstructor.

The intended finished system is:

```text
Megalodon source theorem and local context
  -> THF/TPTP export
  -> Vampire proof search
  -> Vampire-emitted explicit proof certificate
  -> Megalodon native proof-term checking
  -> proof of the original Megalodon goal
```

The proof must not use `admit`, `aby`, incomplete QED, arbitrary bridge
assumptions, Python proof reconstruction, certificate-derived `Known`
theorems, or a private replacement for Megalodon's equality/logical
constants. Classical reasoning is allowed; in particular `xm`, double
negation elimination, `False`, disjunction, and equality are assumed to be
available from the loaded Megalodon development.

The main conclusion is:

- The early Python and generated-script path is useful only for diagnostics.
- The broad Megalodon-side OCaml replay path is also not the target if it
  guesses information Vampire already knows.
- The correct path is the Prover9/Ivy-style path: Vampire expands complex
  inferences into simple proof objects while it still has substitutions,
  selected literals, positions, sorts, and parent clauses; Megalodon checks
  those objects and composes the result into the original source context.
- The current branch is now much closer to that path, but it is still a
  partial implementation with narrow focused successes rather than a completed
  100-theorem system.

The strongest current evidence is a focused parallel real-target batch over
eleven obligations from `examples/hammer/100thms_12_h.mg`. For each selected
obligation, Megalodon exports the live target, calls real Vampire with
`--proof megalodon` and a 10-second timeout, parses the native certificate,
checks the native certificate steps, resolves the original source facts, and
reconstructs the selected `aby` proof term before stopping at the target. All
eleven selected targets pass in the committed smoke harness.

This is meaningful E1-style evidence because the proofs are linked back to
the live Megalodon target and source context. It is not the final requested
100-theorem suite, not a full-file pass, and not evidence that all
source-to-clause transformations are solved.

The newest committed technical improvement is explicit Skolem substitution
replay. In the representative failure `hammer.11228.26`, Vampire emits that a
dropped parent variable is instantiated by a Skolem term such as `(sK0 X0)`.
Megalodon now consumes that Vampire-emitted substitution instead of guessing
the witness from remaining result variables. After commit `6354f0f`, the
native certificate for the focused `11228.26` target checks 37 steps and 3
sources. The remaining failure is no longer the Skolem proof term. It is the
final transport from a native-core double-negated target to the current live
Megalodon goal.

The most important remaining gaps are:

- the focused E1 batch has only eleven real targets, not 100;
- final refutation-to-goal transport is still incomplete for native-core
  `False` versus loaded Megalodon `False`;
- Smolka-style source transformations are represented and partly checked, but
  not all are proof-producing in counted mode;
- the Vampire-side primitive IR exists only partially, with URR as the first
  serious vertical slice;
- the large historical OCaml and C++ modules still exist and should not be
  allowed to grow into another reconstruction prover;
- AVATAR, broad CNF/ENNF/FOOL transformation proof production, and general
  Skolemization remain open beyond the cases described here.

## The Objective and Constraints

The original objective was to take the Vampire proof reconstruction work,
especially the Lean-style proof output, and port it to Megalodon. Since
Megalodon and Lean are both proof-term based, the intended result is not a
textual replay script but a Megalodon proof term that checks against the
current Megalodon kernel.

The requested operational constraints are now part of the project discipline:

- use THF/TPTP;
- use `/project/tmp` for temporary files and generated run artifacts;
- cap Vampire proof search at 10 seconds per target;
- run export/search/checking in parallel, normally 10 to 20 jobs for broad
  batches;
- avoid repeatedly re-running known-unsolved Vampire searches;
- use real Vampire proof output, not fabricated test proof objects, for the
  main evidence;
- do not use `aby` or `admit` in resulting scripts/proofs;
- assume classical reasoning is available from the Megalodon library;
- use Megalodon's existing equality and logical constants;
- avoid hardwiring theorem names from a particular library, except that
  loaded library facts may be resolved by their source-map name, original
  Megalodon name, or hash and then checked semantically.

The project also adopted explicit evidence classes:

- E1: original Megalodon target reconstructed in the live source context, with
  no `admit`, no `aby`, no bridge assumptions, and no certificate-derived
  `Known`.
- E2: closed native `Syntax.pf` proof of an exported Vampire certificate,
  still at the exported THF/certificate boundary.
- E3: focused or synthetic small-kernel proof-term checks.
- E4: structural certificate, metadata, source-map, or integration checks.

The audits were right that E4 evidence should not be reported as proof
reconstruction. It remains valuable for engineering, but it is not the same
as E1 or E2.

## Current Architecture

The current intended architecture has four layers.

### 1. Vampire Primitive Certificate Layer

Vampire should emit explicit proof data. For complex internal inferences, the
proof printer should not merely say "superposition" or "URR" and ask
Megalodon to rediscover the details. It should print the relevant primitive
facts:

- parent step ids;
- selected literals;
- pivot literals;
- equality sides and orientation;
- rewrite positions;
- substitutions;
- introduced symbols;
- variable sorts;
- result formulas/clauses;
- source/preprocessing metadata.

The Vampire fork now has an extracted `MegalodonKernelSyntax` boundary and a
series of commits moving certificate fields into structured records. Recent
work includes explicit records for:

- kernel parent records;
- literal selections;
- rewrite metadata;
- source formula transforms;
- rectification renamings;
- CNF clause metadata;
- definition folds;
- URR traces;
- AVATAR metadata;
- split dependencies;
- primitive expansion chains;
- URR primitive parent/final-result/rule-payload metadata.

This is still not a complete primitive IR. It is a partial boundary around the
large `MegalodonChecker.cpp` exporter. The main missing piece is a typed
internal list of primitive proof steps constructed before printing and then
serialized by one canonical printer.

### 2. Megalodon Certificate Syntax and Checking

On the Megalodon side, the native certificate parser/checker lives mostly in
`src/vampire_cert_v1.ml`, with `src/vampire_kernel_syntax.ml` now extracted
for shared `kernel_v1` vocabulary, supported rule names, and primitive
contracts.

The checker performs:

- strict certificate parsing and structural validation;
- source-map validation;
- native term/proposition reconstruction;
- native core proof-term checking for supported fragments;
- primitive metadata audits;
- source-context audits;
- final goal composition for some live targets.

The broad historical module is still too large. The design documents call for
new work to move into separate modules:

- `vampire_kernel_syntax.ml`
- `vampire_kernel_check.ml`
- `vampire_kernel_elab.ml`
- `vampire_source_context.ml`

Only the first of these has been substantially extracted so far. Further
growth in the monolithic importer should be treated as suspect unless it is a
small compatibility or bug fix.

### 3. Source Context Layer

The source-context layer is the part that links exported THF names back to
the current Megalodon proof state. This has become the main focus because a
checked exported refutation is not enough: the final object must prove the
original Megalodon goal using the original lemmas, definitions, and local
hypotheses.

The current resolver handles several source kinds:

- global known theorems;
- local hypotheses;
- local type declarations;
- local definitions;
- generated facts;
- generated `set` equalities;
- conjecture boundary facts;
- unresolved facts.

Global known recovery now tries the source-map hash, the original Megalodon
name, and the TPTP name against the loaded known table. It does not accept a
candidate merely by name. It uses `check_propofpf` to confirm that the loaded
proof proves the exported source proposition, including instantiating leading
universal binders when the exported source proposition contains closed terms.

Local recovery now uses source-map `local_type` declarations to reconnect
original local names such as `f` and `g` to the live de Bruijn variables in
the current Megalodon context. Local facts can also be resolved through
proof-producing expanded-equality conversion when the live local hypothesis is
a compact equality but the exported formula uses an expanded polymorphic
equality shape.

Generated `set` equalities are not treated as user theorem assumptions. They
are proof obligations discharged by reflexivity or conversion in Megalodon.

### 4. Final Refutation-to-Goal Transport

The final layer turns a checked Vampire refutation into a proof of the current
Megalodon goal. This is where the negated conjecture boundary is discharged.

Several cases are already implemented:

- direct target match;
- equality target with opposite orientation, using equality symmetry;
- expanded equality target, where the exported proposition uses Megalodon's
  polymorphic equality head and source-map aliases;
- proposition-extensionality helper normalization, where native helper-style
  applications are rewritten into applications of the loaded Megalodon
  `prop_ext` theorem with an explicit `iff` proof;
- classical discharge using available `xm`/double-negation principles in
  supported cases.

The current failing frontier is a native-core double-negation over
`All(Prop, DB 0)`, the native-core encoding of `False`, where the live goal
expects the loaded Megalodon `False`. The experimental uncommitted edit tries
to bridge those with `FalseE` and native false elimination, but it has not
yet produced a checked final proof for `hammer.11228.26`.

## Prover9/Ivy Lessons

The Prover9/Ivy analysis remains the best architectural model.

Prover9 does not ask Ivy to reconstruct a high-level proof from sparse hints.
It runs proof expansion inside Prover9 first:

```text
ordinary Prover9 proof
  -> expand_proof
  -> expand_proof_ivy
  -> small Ivy object
```

The small Ivy object has a limited vocabulary:

- input;
- instantiate;
- flip;
- resolve;
- paramod;
- propositional simplification;
- limited new-symbol handling.

For resolution and paramodulation, Prover9 emits explicit instantiation
steps, positions, and parent ids. The checker is not asked to rediscover
unifiers. Demodulation and rewrite chains are expanded into individual
paramodulation-like steps using the exact occurrence information available in
the prover.

The direct lesson for this project is:

- Vampire should expand complex inferences while it still has the proof data.
- Megalodon should check small explicit steps.
- Python should only inspect or summarize, not prove.
- The OCaml importer should not guess substitutions, rewrite sites, or
  literal selections that Vampire could have printed.

The current URR primitive chain is the first serious application of that
lesson. The next macro classes should follow the same pattern.

## What Has Been Implemented

### Trust Boundary Reset

The July 16 audit found that the native preprocessing proof-term mode was
installing certificate-derived propositions into the known theorem table and
then applying them. That is bridge-assumption behavior in another form.

The current branch reclassifies such runs as structural diagnostics. Counted
native paths reject certificate-derived `Known` names, except for a fixed
reviewed logical basis. The old transitional behavior is gated by
`MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1` and should not be used
for qualifying evidence.

This was an essential correction. It lowered headline pass counts but made
the remaining evidence more honest.

### Kernel Vocabulary Boundary

`src/vampire_kernel_syntax.ml` now centralizes the Megalodon-side `kernel_v1`
schema, supported rule names, and primitive-expansion contracts. The Vampire
fork has a corresponding `Shell/MegalodonChecker/MegalodonKernelSyntax.*`
boundary. Unsupported kernel rule names fail in the checker.

This is not yet the full kernel checker/elaborator extraction, but it is the
first concrete step toward stopping uncontrolled growth in the monolithic
checker/exporter.

### URR Primitive Expansion

Unit-resulting resolution has a vertical slice of Prover9/Ivy-style
elaboration:

- Vampire emits an ordered primitive expansion chain;
- the chain records primitive parent/result relationships;
- Megalodon checks final primitive id and final result clause;
- rule payloads include substitutions, pivots, symmetry literals, and factor
  pairs;
- focused native audits reject missing or inconsistent URR primitive data.

This is still narrower than the full proof problem, but it is the right kind
of work. It moves detail from heuristic replay into explicit Vampire-emitted
proof objects.

### Source-Context Recovery

The branch can now recover several categories of original Megalodon facts:

- loaded theorem references by source hash/name/TPTP alias;
- local proof facts in the current context;
- local type aliases from source-map declarations;
- expanded equality source facts;
- generated `set` equalities by reflexivity/conversion;
- conjecture boundary facts for final transport.

The `hammer.11703.242` target was the main driver for local-context recovery.
It requires one loaded theorem, four local facts, and two conjecture boundary
entries. Earlier detached checks could not reconnect the local facts. The
current live path does.

The `hammer.11203.25` target exposed local type aliasing: exported source
propositions mentioned original local names, while the live goal used de
Bruijn variables. Source-map `local_type` declarations now restore that link.

The `hammer.11572.88` and `hammer.11578.57` targets exposed compact versus
expanded equality source facts. Local proof resolution now returns a proof of
the exported proposition, not merely the raw local hypothesis.

### Live Target Harness

Focused live iteration is now practical.

The relevant options are:

```text
-vampireabytarget <line> <char>
-vampireabytargetstop
```

These let a run on a large Megalodon file skip non-target `aby` calls, invoke
Vampire only at the selected obligation, reconstruct that obligation, print a
target-stop marker, and exit before unrelated later obligations.

This fixed a major iteration problem. Before this mode, a focused run could
spend time on earlier unrelated Vampire calls or fail later in the file after
the target proof had already been reconstructed.

### Skolem Substitution Replay

The newest committed work addresses a representative Skolemization failure.

In `hammer.11228.26`, Vampire emits a Skolem formula step where a parent
variable is intentionally dropped from the result variables and replaced by a
Skolem witness term. The certificate includes the needed substitution:

```text
X1 : set -> prop  :=  (sK0 X0)
```

Previously, Megalodon's native Skolem proof-term helper tried to instantiate
parent variables only from result variables, then fell back to type-based
guessing. That was the wrong direction: Vampire already had emitted the
witness.

Commit `6354f0f` changes the native certificate checker so:

- `native_core_skolem_formula_proof` receives the explicit Vampire
  substitution;
- dropped parent variables are instantiated from that substitution;
- Skolem witness extraction normalizes witnesses under inner binders;
- direct Skolem target rewrite uses binder-aware outer-witness rewriting;
- debug output around formula orientation failure is available under a gate.

Validated before the report:

```text
TMPDIR=/project/tmp ./makeopt
TMPDIR=/project/tmp JOBS=4 \
  tests/vampire_certificate/run_real_vampire_targets_smoke.sh
TMPDIR=/project/tmp SOURCE_CONTEXT_ONLY=1 \
  tests/vampire_certificate/run_native_cert_v1_smoke.sh
```

The focused `11228.26` run now reaches:

```text
Vampire native certificate checked 37 steps and 3 sources at line 11228 char 26;
source_context known=1 local=0 local_definition=0 conjecture=2 unresolved=0.
Vampire certified aby at line 11228 char 26 (...)
Failure: Vampire native certificate did not reconstruct current aby goal
```

This is progress because the Skolem proof-term issue is no longer the
blocking error. The remaining issue is final live-goal transport.

## Linking to Original Megalodon Lemmas and Definitions

This has improved substantially, but it is not complete.

### Global Lemmas

The source resolver can link a certificate source entry to a loaded
Megalodon theorem by:

- source-map proof hash;
- original Megalodon source name;
- TPTP-exported name;
- source-map alias.

It only accepts the link after checking that the loaded proof term proves the
source proposition expected by the certificate. For polymorphic or universally
quantified facts, it can instantiate leading binders with closed terms from
the exported proposition.

This fixed the known-theorem side of targets such as `11703.242`, where the
certificate needs `add_SNo_cancel_L`.

### Local Hypotheses

Local hypotheses are handled in the live `vampireaby` path by using the
current Megalodon proof context, source-map local declarations, and de Bruijn
index reconstruction. The important point is that local source facts are not
serialized as arbitrary axioms. They are resolved to the live local proof
context and then checked as proof terms.

The current implementation also tolerates irrelevant local variables and
hypotheses before the relevant local facts. A reduced stress fixture verified
that the resolver was not relying on convenient local-context ordering.

### Local Definitions

Local definitions are recognized as source-context entries. The current
system can use definitional conversion in focused fixtures. The design goal
is that local definitions should be represented as conservative source facts
or definitional reductions, not as arbitrary proof assumptions.

This area is less exercised than local hypotheses and global knowns. It
should remain a focus for the next E1 batch expansion.

### Set-Generated Equalities

The user pointed out that some TPTP axioms come from Megalodon's `set`
command and may not correspond to claims. The current treatment is correct in
principle: such equalities are generated proof obligations and should be
proved by reflexivity or conversion in Megalodon.

There are smoke fixtures for local `set` reflexivity source obligations. This
needs broader real-target coverage, but the trust boundary is right: these
facts are not imported as unchecked assumptions.

### Conjecture Boundary

Conjecture facts are deliberately not resolved as ordinary assumptions. They
are the boundary where a refutation of the negated conjecture must be turned
into a proof of the current goal.

The supported final transport cases are enough for the eleven focused batch
targets. The current `11228.26` failure shows that this layer still needs a
more general bridge between native-core falsehood and loaded Megalodon
falsehood.

## Smolka-Style Transformations

Smolka-style transformations are still an incomplete layer. The project now
has a clearer contract for them:

- source input and formula-term input;
- definition input/fold/unfold;
- rectification;
- FOOL Boolean lifting and exhaustiveness;
- ENNF;
- CNF literal/formula projection;
- Skolemization with explicit introduced symbols, dependencies, sorts, and
  substitutions;
- proof-producing output or rejection in counted mode.

The important audit lesson is that these transformations must not be handled
by installing a certificate-derived theorem such as "this source formula
implies this clause" and then applying it. That was the dynamic-`Known` bug.

Current status:

- Structural metadata for these transformations is much richer than before.
- Strict live 100-certificate runs are useful E4 evidence that the metadata
  can be generated and parsed.
- Some transformation proof-term fragments exist.
- Skolem substitution replay now uses explicit Vampire metadata and has
  passed the representative native certificate step in `11228.26`.
- Full proof-producing ENNF/CNF/FOOL/Skolem transformation coverage is not
  finished.

The next design step should keep source/preprocessing transformations
separate from the clausal small kernel. They are not resolution or
paramodulation rules. They are source-to-clause proof obligations.

## Equality

The project should use Megalodon's equality directly. It should not introduce
a private equality theory.

The current implementation is largely aligned with that:

- expanded equality heads are recognized as Megalodon's polymorphic equality;
- final equality-shaped goal transport uses Megalodon equality and equality
  symmetry;
- compact live equalities can be matched against expanded exported equality
  forms through source-map-aware deltas;
- source local facts can be transformed proof-producingly between compact and
  expanded equality forms.

This fixed real targets such as `11453.77`, where the final goal was an
expanded equality with source-map aliases.

There may still be old helper terminology in code and reports, but the
desired invariant is clear: equality should resolve to Megalodon's equality
constant and checked proof rules, not to an untrusted private equality
encoding.

## Current Evidence Classification

### E1-Style Focused Live Reconstruction

The eleven-target real batch is the strongest evidence. It is not the final
100-theorem suite, but each target exercises the live original-source path:

```text
live Megalodon target
  -> THF export with source map
  -> real Vampire --proof megalodon
  -> native certificate parse/check
  -> source-context recovery
  -> final proof-term reconstruction
  -> target stop
```

These runs use the original large hammer source file and real Vampire output.

### E2/E3 Native Core Evidence

There are focused native proof-term checks for clausal core fragments and URR
primitive chains. These are valuable because they construct/check `Syntax.pf`
objects rather than scripts or strings. They remain narrower than full E1.

### E4 Structural Evidence

Strict certificate validation, metadata audits, source-map parsing, and broad
live certificate generation are E4 unless they also construct and check proof
terms with source composition.

The project has sometimes over-reported these in the past. This report
intentionally separates them.

## Open Problems

### 1. Final Native-False Transport

`hammer.11228.26` now checks the native certificate after Skolem substitution
replay, but final reconstruction fails.

The checked certificate appears to produce a native-core double negation of
the current target, where falsehood is represented as:

```text
forall _:prop, _0
```

The live Megalodon context has its loaded `False` definition and `FalseE`.
The finalizer must bridge these in a proof-producing way, probably by
converting:

```text
((target -> native_false) -> native_false)
```

into:

```text
((target -> live_False) -> live_False)
```

and then applying the loaded `dneg`, or by an equivalent `xm` proof. The
uncommitted attempt is close in shape but currently fails proof-term checking.

This should be the immediate next fix because it unlocks the next
representative Skolem-containing real target.

### 2. Small Primitive IR Is Still Partial

URR has a useful primitive chain. Other frequent classes need the same
treatment:

- ordinary resolution;
- subsumption resolution;
- superposition/paramodulation;
- demodulation and definition rewrite chains;
- factoring and equality factoring;
- condensation;
- CNF projection steps;
- Skolem/source transformations.

The key rule is that Vampire must emit exact substitutions, positions, and
selected literals. Megalodon should not search for them.

### 3. Source/Preprocessing Proof Production

The Smolka-style layer is the largest conceptual gap. Structural metadata is
not enough. Each transformation should either produce a checked proof term or
be rejected in counted mode.

Skolemization is the current active subproblem. Explicit substitution replay
is a real improvement, but general dependent Skolemization and its interaction
with final conjecture discharge are not yet solved.

### 4. Monolith Control

`src/vampire_cert_v1.ml` and `Shell/MegalodonChecker/MegalodonChecker.cpp`
are still large. The audits were right that simply moving from Python to a
large OCaml/C++ pair is not enough.

The project needs enforceable rules:

- no new broad proof-search logic in Python;
- no certificate-derived `Known` in counted paths;
- new kernel work goes into isolated modules;
- Vampire-side macro handlers build primitive records rather than hand-written
  strings;
- textual script generation remains a debugging output, not the qualifying
  product.

### 5. Held-Out 100-Theorem Suite

The requested final benchmark is at least 100 Megalodon theorems and their
Vampire proofs. The current eleven-target batch is a focused frontier, not
that benchmark.

The next suite should be built only after the next transformation blockers are
handled. Otherwise the suite will mostly measure known unsupported classes or
encourage another round of broad heuristic patching.

## Bottom Line

The project has moved from exploratory translation toward real proof
reconstruction. The most important achievements are:

- explicit rejection of dynamic certificate-derived `Known` in counted paths;
- a shared kernel vocabulary boundary;
- Vampire-side URR primitive expansion metadata;
- native Megalodon proof-term checking for focused core fragments;
- source-context recovery for loaded knowns, locals, local type aliases,
  expanded equalities, set equalities, and conjecture boundaries;
- eleven focused real-target reconstructions in the live original-source
  path;
- explicit Skolem substitution replay using Vampire-emitted data.

The main unfinished work is equally clear:

- finish final transport for native-core falsehood;
- expand the Vampire primitive IR beyond URR;
- make Smolka-style source transformations proof-producing;
- reduce dependence on the monolithic importer/exporter;
- build the real 100-theorem E1 suite.

The direction is now substantially healthier than the early Python or broad
Megalodon-side replay approaches. The project should continue, but it should
be judged by native checked proof terms connected to original Megalodon
sources, not by structural certificate pass counts or broad heuristic replay.
