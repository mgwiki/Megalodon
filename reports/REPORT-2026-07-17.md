# Vampire to Megalodon Proof Reconstruction: Project Report

Date: 2026-07-17

This report summarizes the current state of the Vampire-to-Megalodon proof
reconstruction project for expert review. It incorporates the previous reports
from 2026-07-12 through 2026-07-16, the audits of those reports, the audit
responses, the Prover9/Ivy analysis, the Smolka-style transformation
discussion, and the current local `vampire/megalodon5` branches.

The report is deliberately conservative. Earlier project reports sometimes
used broad pass counts before the trust boundary was fully understood. The
later audits corrected that accounting. The present report follows the stricter
classification: a successful integration run, source-map check, or structural
certificate validation is useful evidence, but it is not the same as a
Megalodon proof of the original theorem.

## Executive Summary

The project is not finished. It has made real progress, but it has not yet
achieved the original target: 100 representative Megalodon theorems proved by
Vampire from THF/TPTP exports and reconstructed back inside the original
Megalodon development with no `admit`, no `aby`, no incomplete QED, no hidden
bridge assumptions, no certificate-derived `Known` facts, and no private
replacement for Megalodon's equality or logical constants.

The major positive change over the week is architectural. The project began
with a large Python-oriented proof skeleton generator and a growing
Megalodon-specific Vampire dump. That path produced useful evidence and test
material, but the audits correctly identified it as non-convergent: it was
becoming a heuristic prover outside Vampire and outside Megalodon's kernel.
The project has since moved toward the Prover9/Ivy-style architecture that the
audits recommended:

```text
Megalodon source theorem and local context
  -> THF/TPTP export with origin/source metadata
  -> Vampire proof search with timeout <= 10s
  -> Vampire-emitted primitive certificate data
  -> Megalodon small checker and Syntax.pf elaboration
  -> proof of the original Megalodon theorem
```

The strongest current implementation evidence is not E1 original-context proof
reconstruction. It is a fail-closed native proof-term preprocessing frontier:


## Objective and Non-Negotiable Constraints

The objective is to adapt Vampire proof reconstruction to Megalodon. The
original motivation was Vampire's Lean-oriented proof reconstruction work:
Lean and Megalodon are both proof-term-oriented systems, so Vampire should be
able to emit enough information for Megalodon to replay a refutation as a
checked proof term.

The target is not merely a standalone proof checker for first-order clauses.
The target is a proof of the original Megalodon theorem. That means a complete
solution must preserve:

- the original theorem statement;
- global lemma and definition references;
- local hypotheses;
- local definitions introduced during proof;
- facts generated by Megalodon `set` commands;
- the negated conjecture introduced for refutation;
- symbol and type/sort identity across export and reimport;
- transformations such as rectification, FOOL processing, ENNF/CNF,
  predicate definitions, Skolemization, and AVATAR if used by Vampire.

The working constraints that shaped the implementation are:

- The input problems are THF/TPTP exports from Megalodon, not hand-written toy
  FOF problems.
- Vampire should be invoked with TPTP input syntax and a hard timeout not
  exceeding 10 seconds per problem.
- Batch testing should be parallel. The preferred loop is export many
  problems, run Vampire in parallel, and check the resulting certificates in
  parallel.
- Temporary artifacts belong under `/project/tmp`.
- The final scripts or proof terms may not use `aby`; in Megalodon, `aby` is
  implemented as admission.
- The final scripts or proof terms may not use `admit` or
  `-allowincompleteqed`.
- Classical logic may be assumed. In particular, `xm` is available, and the
  standard Megalodon library constants for `False`, disjunction, equality,
  proposition extensionality, choice-like principles, and related classical
  facts should be used from the context rather than reinvented privately.
- The implementation must be general for arbitrary Megalodon libraries. It
  cannot succeed by hardwiring current benchmark names such as particular set
  library theorems.
- If a TPTP axiom comes from a Megalodon `set` command and has no
  corresponding claim, the reconstruction should prove the equality directly,
  typically by reflexivity or conversion.
- Vampire should emit exact proof data while it still has it: selected
  literals, substitutions, rewrite positions, equality directions, sorts,
  generated symbols, Skolem dependencies, parent clauses, and result clauses.
  Megalodon should check that data, not rediscover it by heuristic search.

These constraints rule out the original Python-heavy direction as a final
answer. They also rule out a broad Megalodon-side OCaml replay engine if it
has to guess Vampire's internal proof choices.

## Evidence Classes

The project now uses evidence classes to avoid ambiguous "pass" labels.

E1 is the target: an original Megalodon theorem is reconstructed in its live
source context with no `admit`, no `aby`, no incomplete QED, no bridge
assumption, and no certificate-derived `Known`.

E2 is a closed native `Syntax.pf` proof of a live Vampire certificate at the
exported THF/certificate boundary. It is real proof-term evidence but not yet
composed into the original theorem command.

E3 is a focused or synthetic native proof-term check for a small-kernel rule
or a limited transformation family.

E4 is structural evidence: certificate parsing, metadata validation,
source-map validation, live Vampire run success, transitional diagnostics, and
integration testing that does not prove every inference by native proof terms.

Under this classification:

- `PASS 100` from a strict live certificate run is E4.
- Old preprocessing runs that required transitional certificate-derived
  `Known` facts are E4.
- The native clausal core fixtures are E3 unless they are live exported
  proofs and pass a closed proof-term gate.
- Focused native proof-term passes for live hammer certificates are E2-like
  evidence for the exported certificate boundary, but still not E1.
- No current broad run establishes E1.

This evidence discipline is the main correction from earlier reporting.

## Audit-Driven History

The July 12 report documented the initial implementation line: Vampire emitted
a rich Megalodon-specific proof object, and a large Python reconstructor
generated source-linked Megalodon proof skeletons with declarative claims. That
work was useful because it produced source maps, benchmark data, skeletons,
and concrete failure examples. It was not a final reconstruction system. The
audit correctly observed that the Python layer had become a heuristic theorem
prover with library-specific patterns, bounded search, equality-chain search,
quantifier reconstruction, source-proof inlining, and set-theoretic
recognizers. The audit recommended stopping that implementation line and
moving toward a small Prover9/Ivy-style certificate.

The July 13 report accepted the pivot. It introduced a certificate-v1 direction
and began moving away from Python as the qualifying path. The audit, however,
found that derived Vampire clauses could still become assumptions through an
`input`-like mechanism. That meant a no-`admit` generated theorem could still
be a theorem from extra derived premises, not from the original source
premises. The audit also found that the nominally small certificate was already
growing too broad and too stringly typed.

The July 14 report described the switch to a native S-expression certificate
and an OCaml importer in Megalodon. This was a real operational improvement:
Python was no longer the counted path, source metadata was better, and
parallel cached tests were in place. The audit found two principal gaps:
strict mode still allowed bridge premises, and source linking was still too
label-based. A certificate could attach a nontrivial clause to a valid source
name without semantically proving that it was the exported source formula.

The July 15 report was the first one whose closed results the audit considered
meaningful. Closed mode rejected bridge and derived premises, and supported
source formulas were structurally compared against exported THF formulas. The
audit still criticized the architecture: the main Megalodon module was growing
into a broad textual replay engine, not a small proof-term checker.

The July 16 report introduced the native `Syntax.pf` direction:
`corepfcheck` and `preprocesspfcheck` built proof terms rather than only
emitting scripts. The audit accepted the small clausal core seed but found a
serious hidden trust issue in the broader preprocessing path: it could create
a proposition, dynamically add it to the proof checker's `Known` table under a
generated name, and then apply that generated theorem. This was equivalent to
a bridge assumption, even though it appeared inside a native proof term. The
audit required a trust-boundary reset.

The July 17 branch implements that reset in the counted path. Transitional
certificate-derived `Known` facts are excluded from counted proof-term modes.
The old behavior is retained only as a diagnostic mode and must be reported as
structural, not reconstruction, evidence. The same branch also begins moving
the certificate vocabulary into shared modules:

- Megalodon has `src/vampire_kernel_syntax.ml`.
- Vampire has `Shell/MegalodonChecker/MegalodonKernelSyntax.{hpp,cpp}`.
- Vampire-side emission now uses a `MegalodonKernelStep` migration object for
  more of the `kernel_v1` metadata.

This is aligned with the audit direction, but the extraction is incomplete.
Large monolithic files still dominate the implementation.

## What Has Been Implemented

### Source and Origin Metadata

The THF/TPTP export path now carries more origin metadata than at the start of
the project. Exported obligations can be connected to Megalodon source
locations and source commands. The path distinguishes certified `vampire`
commands from legacy `aby` commands, so the audit logs can tell whether a
problem was produced for the new no-`aby` route or for the old automation.

Megalodon-side strict checking no longer only compares labels. For supported
exported THF formulas, source validation parses and compares the formula shape
against the certificate input. Unsupported source syntax fails closed where
formula matching is required.

Source-context classification has also become more explicit. The checker can
classify source obligations as global known facts, local hypotheses, local
definitions, generated facts, conjecture facts, unresolved facts, and
set-reflexivity obligations. This is not yet final E1 composition, but it is
the necessary data model.

The current source-link status is:

- Global lemmas and definitions can be recognized through exported source
  identifiers and checked formulas in the supported fragment.
- Local hypotheses can be represented and source-bound in selected live
  examples.
- Local definitions are classified distinctly from ordinary assumptions.
- `set`-generated equalities are identified as a separate class; the intended
  proof is by reflexivity or conversion rather than by an arbitrary claim.
- The conjecture side is represented as the negated conjecture used for the
  Vampire refutation.
- Full conversion of the final refutation into a proof of the original theorem
  in the original source proof state remains incomplete.

The missing E1 step is not just a printer detail. The implementation still
needs a concrete source-context API that resolves each certificate source id
to an actual Megalodon proof object:

```text
GlobalKnown     existing theorem or library fact
LocalHyp        local proof-context hypothesis
Definitional    local or global definitional equality with proof
Generated       generated fact with proof, such as set reflexivity
Conjecture      negated conjecture boundary
Unresolved      hard failure in counted mode
```

The source context must preserve binder scopes, local hypothesis indices,
definition shifts, theorem hashes, and the final refutation-to-goal
composition.

### Native Certificate v1

Megalodon now has a native certificate-v1 path in OCaml. It parses Vampire
S-expression certificates, validates structural metadata, validates source
metadata, and can elaborate selected fragments into native `Syntax.pf` proof
terms.

Several modes exist, and they must not be conflated:

- Strict certificate validation checks schema, metadata, and source
  consistency. It is mostly E4.
- Closed textual/script modes reject explicit bridge and derived premises, but
  are not the final proof-term architecture.
- `corepfcheck` is the small native clausal proof-term seed.
- `preprocesspfcheck` is a larger native proof-term path for selected
  source/preprocessing transformations and clausal steps. It is now
  fail-closed against certificate-derived `Known` in counted mode.
- Transitional preprocessing modes may still be useful for diagnostics, but
  they are not counted as proof reconstruction.

The native checker constructs `Syntax.pf` terms and calls Megalodon's proof
checking machinery. That is materially better than printing scripts and
looking for forbidden tokens. The caveat is that much of the implementation
still lives in `vampire_cert_v1.ml`, and not all of it has been extracted into
a small auditable kernel.

### Fail-Closed Trust Boundary

The biggest correction since the July 16 audit is the fail-closed treatment of
certificate-derived known theorems.

The old broad preprocessing proof-term path could produce:

```text
Generated proposition P -> Q
Generated name vampire_some_transformation_uNNN
Known vampire_some_transformation_uNNN : P -> Q
Application of that Known to the parent proof
```

That looked like a native proof term, but the implication was simply inserted
into the proof environment. The current counted proof-term path rejects that
pattern except for a fixed reviewed logical basis. The fixed basis includes
the classical and logical principles that the project is allowed to assume
from the Megalodon development, such as excluded middle, double-negation
reasoning, not-forall/existence conversion, choice-like principles used for
Skolemization, and propositional extensionality where explicitly required.

This is a decisive distinction. It means the current 88-case frontier is not
just the old 94-case structural frontier with a different label. It is still
not final E1, but it is on the correct side of the main trust boundary.

### Vampire Kernel Syntax Boundary

On the Vampire side, the project has introduced
`Shell/MegalodonChecker/MegalodonKernelSyntax.{hpp,cpp}`. This module now owns
part of the emitted `kernel_v1` vocabulary, primitive-expansion contract, and
rendering helpers. It provides a place to grow a real primitive certificate IR
instead of scattering ad hoc field construction throughout
`MegalodonChecker.cpp`.

On the Megalodon side, `src/vampire_kernel_syntax.ml` holds the corresponding
rule names and structural contracts for `kernel_v1` metadata. Unsupported
kernel rule names fail closed in the checker. There are negative fixtures for
invalid rule names.

The Vampire extraction currently contains migration-stage records:

- `PrimitiveExpansion`
- `PrimitiveStep`
- `MegalodonKernelStep`
- rendered parent and conclusion records

This is good directionally, but it is not yet the typed primitive IR requested
by the audit. Many fields remain rendered strings. The target should be a
Vampire-side internal object with typed access to:

- rule name;
- step id;
- parent ids;
- conclusion clause/formula;
- selected literal indices;
- pivot data;
- substitution data;
- rewrite position and direction;
- equality side terms;
- sorts of variables and symbols;
- Skolem introduced symbol and dependency list;
- source/preprocess metadata for non-clausal transformations.

The immediate implementation rule should be: macro inference handlers build
primitive records first, and a single canonical printer serializes those
records. Direct string assembly in individual inference cases should be
migration-only.

### Primitive Expansion Work

Vampire now emits richer primitive-expansion metadata for several macro
inferences. This is an explicit response to the Prover9/Ivy recommendation:
complex inferences such as unit-resulting resolution and subsumption
resolution should be lowered to small proof steps rather than replayed by a
large Megalodon-side macro prover.

Completed or partially completed emission work includes:

- URR primitive chain metadata;
- primitive step ids and required primitive rule summaries;
- parent counts and result clauses for several primitive steps;
- equality symmetry metadata;
- substitution metadata;
- resolution pivot metadata;
- subsumption fast-path primitive result metadata;
- SAT-subsumption primitive chains with substitute, equality-symmetry,
  resolve, factor, and final identity-substitute records;
- rectification variable maps for alpha-renaming/binder identity.

The recent `hammer.10640.42/u251` failure showed why this matters. Megalodon
strict mode rejected a subsumption-resolution primitive expansion that had a
rendered expansion string but lacked the required
`primitive_expansion_final_result_clause` and per-step records. Vampire commit
`0ebdf2a67` fixes that branch by making the SAT-subsumption path build
`PrimitiveStep` records for the side substitution, equality symmetries,
resolution, factorization, and final identity substitution. A fresh focused
certificate now contains the required final result clause and six primitive
steps for `u251`.

This does not finish SAT/subsumption replay as checked Megalodon proof terms,
but it removes a real Vampire-side proof-object gap. The fresh focused
Megalodon check now passes the old `u251` strict metadata point and reaches a
different preprocessing proof-term blocker at `u223`.

### Native Clausal Core

The project has a native clausal core seed. The intended small kernel remains:

- input/source boundary;
- explicit instantiation/substitution;
- binary resolution;
- factor;
- equality resolution;
- equality factoring;
- paramodulation;
- final contradiction marker.

Renaming should be alpha-conversion or part of instantiation, not a broad new
logical rule. `truth_conflict` should usually live in FOOL/source
preprocessing unless a clausal proof object demonstrates it belongs in the
core.

The core proof-term path constructs `Syntax.pf` values and checks them. It is
real progress. Its limitation is coverage: the strongest early core fixtures
were synthetic `core.cnf.*` examples, and real hammer proofs usually pass
through preprocessing, Skolemization, predicate definition, FOOL, and AVATAR
layers before reaching a simple clausal core.

The correct path is not to grow a broad clausal macro engine in Megalodon. It
is to make Vampire lower its macros to explicit primitive records, then let
Megalodon check those records with a small proof-term elaborator.

### Smolka-Style Transformation Layer

The project now treats source/preprocessing transformations as a separate
proof-producing layer, not as clausal kernel rules. This is the right reading
of the Smolka-style work for this project.

The relevant transformation classes are:

- source input and formula-term input;
- definition input, fold, and unfold;
- rectification and alpha-renaming;
- FOOL Boolean lifting, Boolean equality, and exhaustiveness;
- ENNF and propositional normalization;
- CNF projection and clause extraction;
- Skolemization with explicit dependencies and choice;
- AVATAR split definitions and component/refutation reasoning;
- final refutation-to-goal composition.

Several representative transformations now have native proof-term support:

- Predicate-definition introduction metadata is emitted by Vampire and
  checked by Megalodon.
- Predicate-definition fold chains are replayed step by step as native proof
  terms for the representative cached family, instead of using generated
  fold-chain known theorems.
- Rectification over formula propositions can be checked using explicit
  Vampire-emitted variable maps, avoiding Megalodon-side guessing of compact
  binder names.
- Some FOOL formula transformations are handled with typed fallback witnesses
  and native proof terms.
- Compact Skolem formulas whose source is implicit in the checked parent can
  be replayed in representative cases.
- Skolemization under conjunctive formula contexts can project the changed
  conjunct, apply the recursive Skolem proof, preserve the unchanged conjunct,
  and reintroduce conjunction.
- Committed Skolem work uses Vampire's `kernel_v1` parent-formula metadata
  to match each generated definition to the witness term that actually occurs
  in the parent formula's target. This avoids a real ordering bug where source
  traversal and introduced-symbol order could swap definitions, as happened
  in `hammer.10640.42/u223`.
- Quantified AVATAR two-component split replay is implemented for a repeated
  live family using split-definition directions, excluded middle,
  double-negation reasoning, not-forall/existence conversion, explicit choice
  witnesses, and the instantiated source clause.
- Metadata-only AVATAR split definitions can now be recovered from split
  dependency metadata when no standalone `avatar_definition` step is present.
- Committed AVATAR work generalizes the one-variable component proof from
  a single component literal to a component clause with one or more literals.
  The proof builds a predicate over the whole component clause, obtains a
  choice witness for the quantified component case, and derives a separate
  not-proof for each instantiated component literal by injection into the
  component clause. This moves `hammer.10640.42` past `u260`.
- Committed mixed-AVATAR work then replays split-only result clauses that mix
  previous split literals, positive component splits, and a single-literal
  complemented negative ground component. This moves the same fresh
  `hammer.10640.42` certificate past `u279`.

This is substantial proof-term progress. It is also still incomplete and too
centralized in `vampire_cert_v1.ml`. The expert should evaluate whether the
next phase extracts this logic into a transformation checker/elaborator with a
small interface, rather than adding another several thousand lines to the
existing module.

### Equality

The project should use Megalodon's equality directly. Earlier experiments that
introduced private equality-like wrappers or shadowed equality were not the
right final direction. The current design assumes Megalodon equality and
library logical constants are in context.

In certificates, Vampire may still print equality-like wrappers because of
TPTP/FOOL encodings or proposition-valued equality. Megalodon should
interpret these as exported syntax to be mapped back to the native equality
and proposition equality principles, not as a new equality theory.

For `set`-generated equalities with no corresponding source claim, the source
context should classify the obligation as generated/definitional and prove it
by reflexivity or conversion. It should not create a fresh arbitrary claim.

### The `vampire` Command

Megalodon now has a separate fail-closed `vampire` proof command path. It uses
the live certificate route but cannot silently fall back to `aby`, `admit`,
incomplete proof states, native fallback reconstruction, or target skipping.
It is accepted only when the native Vampire certificate path reconstructs the
proof term required by the current gate.

This is important for E1, but it is not sufficient. The command still needs
full original-context composition and broader native proof-term coverage before
it can be the final user-facing reconstruction mechanism.

## Remaining Frontiers

### Formula Orientation

`hammer.1009.43/u98` fails because the native formula-orientation proof
constructor currently supports only equality symmetry, true-equality
elimination, and directly matching logical structure.

This should not be fixed by adding benchmark-specific formula rewrites in
Megalodon. The better fix is to identify what Vampire knows about the
orientation: source formula, target formula, equation or definitional
conversion being applied, and direction. If the step is a general
preprocessing transformation, Vampire should emit a small transformation
certificate. Megalodon should check that certificate.

### SAT-Subsumption Primitive Metadata

The Vampire-side failure for `hammer.10640.42/u251` has been fixed in commit
`0ebdf2a67`. The focused regenerated artifact under
`/project/tmp/live_one_10640_sat_primitive_20260717_231818` contains:

```text
primitive_expansion_step_1_rule=equality_symmetry

primitive_expansion_step_3_rule=resolve
primitive_expansion_step_4_rule=factor

```

The broad cached 100-case frontier has not yet been regenerated after this
Vampire commit, so its aggregate `88/100` number should be read as stale with
respect to this one failure. The next broad run should use the new Vampire
binary and update the frontier accounting.

### Skolem Parent-Formula Matching

The fresh `hammer.10640.42` certificate exposed a concrete Skolemization bug
at `u223`: the generated definitions for `sK1` and `sK2` could be paired with
the wrong predicate because the old Megalodon code followed source traversal
order, while Vampire's introduced-symbol metadata used a different order.

The committed fix does not guess from names. It reads Vampire's
`kernel_v1` metadata:

- `introduced_count`;
- `introduced_i_witness_term`;
- `parent_i_formula`.

For each parent formula, Megalodon extracts the antecedent existential and
then chooses the introduced witness term that actually occurs in that parent
formula's target after closing over the parent context. This is the right
shape of fix: richer Vampire data, local proof-term construction, and no
library-specific recognizer.

This fix is committed as `b18063f` and focused-tested. It is not yet part of
a refreshed broad frontier number.

The next fresh Skolem/frontier case is `hammer.1009.43/u98`. That failure is
not the same as the stale cached dependency failures. The current Vampire
certificate has rectification maps, and Megalodon gets past the old cached
`u80` blocker. The new failure is a formula-orientation proof inside a
Skolemization step whose before/after formulas differ by nested Boolean
structure and proposition-valued equality orientation. The right fix is a
proof-producing orientation rule for those exact equality/Boolean forms, not
a library-specific recognizer for the concrete set-theoretic theorem.

### Skolem Dependency Context

`hammer.10785.27/u226` and `hammer.11145.52/u240` fail because native Skolem
replay sees the Skolem body mention a context variable that is not declared as
a dependency.

There are two possible causes:

1. Vampire's certificate omits a real dependency.
2. Megalodon's proof-term elaborator is opening the formula under a context
   that includes variables not intended as Skolem dependencies.

The fix should be based on explicit Vampire data: quantified prefix, dependency
vector, introduced symbol, symbol sort, body formula, and before/after
formulas. It should not infer dependencies from pretty-printed variable names.

### AVATAR Split-Clause Composition

The focused blocker `hammer.10640.42/u279` was an
`avatar_split` whose result clause contains a mix of previous split literals,
a positive quantified component split, and a negative complemented ground
component split:

```text
not split_1, split_2, not split_3
```

The source clause has:

- the same two-literal quantified component class used for `split_2`;
- a complemented ground component corresponding to `split_3`;
- a previous split literal for `split_1`.

Commit `e5cc32d` implements the first checked version of the required
classical case split for this shape:

- assume the target split clause is false;
- for a positive result split, derive `not split`, use the component
  definition to refute the corresponding source component literals, using
  choice for quantified components;
- for a negative result split, derive the positive split atom by classical
  reasoning and use the component definition to refute the complemented source
  component;
- combine those component refutations with the previous split literals to
  contradict the source clause.

The implementation remains intentionally conservative. It handles the common
mixed split-only shape that the certificate states explicitly; it does not
pretend to solve arbitrary AVATAR. Multi-variable component classes and
multi-literal complemented negative components still fail closed until the
certificate has an explicit tuple/dependency proof object. This should grow
into a separate AVATAR certificate layer, not into a general-purpose
Megalodon-side search procedure.

### Missing Certificates

Eight old synthetic `core.cnf.*` entries in the cached 100 frontier are
classified as `NO_CERT`. They are not current proof checker failures. They
should either be regenerated with the current Vampire binary or excluded from
frontier accounting if they are stale placeholders.

### Original-Context Composition

The largest remaining architectural gap is still E1 composition. The project
has source metadata, source classification, formula comparisons, and some live
source-context smoke tests. It does not yet reliably take a checked Vampire
refutation certificate and return a proof of the original Megalodon theorem in
the original local proof state.

This gap includes:

- resolving global theorem names to existing Megalodon known facts;
- preserving local hypothesis indices across export/import;
- handling local definitions and `set` definitions without treating them as
  arbitrary claims;
- ensuring generated facts have proof terms;
- discharging the negated conjecture boundary to prove the positive original
  goal;
- maintaining binder scopes and de Bruijn indices through the whole pipeline;
- making failures explain exactly which source proof obligation is missing.

This should be the next major design/implementation focus in parallel with
the Vampire primitive IR work.

## Problems Encountered

The project encountered several recurring problems.

The first problem was success accounting. Early pass counts mixed admitted
skeleton checks, bridge-premise scripts, structural certificate checks, and
actual proof reconstruction. The audits forced a better taxonomy. This is now
mostly fixed in reporting, but future work must keep the distinction
mechanically enforced.

The second problem was importer-side proof search. The Python reconstructor
and later parts of the OCaml importer tended to grow whenever a new Vampire
proof shape appeared. That can produce short-term frontier improvements, but
it is not a scalable or auditable design. The project has pivoted away from
Python, but the OCaml module remains large and must be constrained.

The third problem was missing Vampire detail. Many difficult failures were
caused by Megalodon trying to reconstruct information Vampire already knew:
pivots, substitutions, rewrite positions, sort information, binder identity,
Skolem dependencies, and primitive macro expansions. The rectification
variable-map fix is the clearest positive example of the preferred solution:
Vampire emitted exact binder mapping data, and Megalodon stopped guessing.

The fourth problem was source/preprocessing complexity. Real Megalodon
exports are not simple first-order clause sets. They involve formula
processing, definitions, FOOL encodings, Skolemization, and AVATAR. The right
response is not to put all of this into the clausal kernel. The project now
separates a source/preprocessing proof layer from the clausal kernel, but that
separation is not yet clean in code.

The fifth problem was hidden trust. Bridge assumptions were first explicit
premises, then later reappeared as certificate-derived `Known` propositions in
native proof terms. The current branch fixes the counted-mode policy, but the
expert should inspect this carefully because it is the easiest defect to
reintroduce.

The sixth problem was testing cost. Long sequential Vampire runs wasted time.
The current process is better: use 10-second Vampire timeouts, cache proof
artifacts, run broad checks in parallel, and focus iteration on the small set
of known checker failures.

## Relation to Prover9/Ivy

The Prover9/Ivy lesson is still the main architectural guide. Prover9's
`prooftrans` can expand complex proof steps into simpler proof objects. Ivy
then checks a small calculus rather than reproducing the full prover.

For this project, the analogous design is:

- Vampire should lower unit-resulting resolution to binary resolution chains.
- Vampire should lower demodulation/superposition-like rewrites to explicit
  paramodulation or equality-substitution primitives with positions.
- Vampire should expose substitutions, pivots, equality directions, and result
  clauses directly.
- Megalodon should check a small number of primitive constructors.
- Source/preprocessing transformations should be separately certified and
  proof-producing.

The project is partially on this path. URR and subsumption-resolution metadata
are being lowered to primitive chains. The `MegalodonKernelSyntax` extraction
creates a place for a real IR. However, the full Prover9/Ivy-style primitive
certificate is not complete. The current implementation still contains many
macro-specific branches in `MegalodonChecker.cpp` and many replay functions in
`vampire_cert_v1.ml`.

The next review should ask a simple question: for each new proof family, did
the fix add precise Vampire-emitted proof data and a small Megalodon checker,
or did it add another Megalodon-side recognizer? The former is the desired
direction; the latter is regression toward the old architecture.

## Relation to Smolka-Style Transformations

The Smolka-style lesson is also important but should not be misread. The point
is not to duplicate all of Vampire preprocessing in a separate language. The
point is to preserve the proof graph and source correspondence while justifying
local transformations with proof-producing procedures in the target system.

For Megalodon this implies:

- The source/preprocessing layer should be a typed sequence of
  transformations, not a bag of formula strings.
- Each transformation should have explicit inputs and outputs.
- Each transformation should elaborate to `Syntax.pf` or fail.
- Skolemization should be explained through conservative definitions and
  choice, with explicit dependencies.
- Definition introduction/folding should use real definitional equalities.
- FOOL and Boolean transformations should use the fixed Megalodon logical
  basis.
- CNF projection should connect formulas to clauses with proof terms.
- AVATAR should eventually be represented by an explicit propositional
  certificate layer or lowered split-definition reasoning, not by hidden
  assumptions.

The current state is mixed but improving. Some transformation classes have
representative native proof-term implementations. The most recent AVATAR and
Skolem fixes are proof-producing. The fold-chain work removed a bridge-like
known theorem path. But the implementation is not yet a clean transformation
framework, and coverage is still shaped by the current hammer frontier.

## Current Outlook

The project is viable, but only if the next work remains disciplined. The
short-term temptation is to raise the 88/100 frontier to 100/100 by adding
more Megalodon-side special cases. That would repeat the failure mode the
audits identified. The better plan is:

1. Finish the current fail-closed frontier cases with proof-object fixes,
   starting with the formula-orientation failure now exposed by the fresh
   `hammer.1009.43/u98` certificate and then regenerating the stale cached
   Skolem-dependency cases before treating them as current blockers.
2. Extract the primitive checker/elaborator from `vampire_cert_v1.ml` into
   smaller modules.
3. Extend `MegalodonKernelSyntax` into a real typed Vampire primitive IR.
4. Make macro inference handlers in Vampire build primitive records first and
   print through a single canonical path.
5. Define and implement the source-context API for original Megalodon theorem
   composition.
6. Prove set-command equalities by reflexivity/conversion in that source
   context.
7. Stabilize Skolemization with explicit dependency vectors and choice-based
   proof terms.
8. Treat AVATAR as a separate explicit layer, not as a general bridge; keep
   the current mixed-split replay conservative and fail-closed.
9. Demonstrate 10 live E2 certificates through the small primitive path.
10. Demonstrate 10 live E1 original-context reconstructions.
11. Only then rerun a fresh held-out 100-theorem gate.

The order matters. A fresh 100-case run before the primitive IR and E1
composition are stable would mainly produce another broad diagnostic number.
It would not settle the project.

## Recommended Questions for Expert Review

The expert should focus on the following questions.

Is the current fail-closed `preprocesspfcheck` path really free of
certificate-derived `Known` facts in all counted modes?

Is `MegalodonKernelSyntax` growing into a real primitive proof IR, or is it
only a printer helper around rendered strings?

Can the native clausal kernel be extracted from `vampire_cert_v1.ml` without
carrying the broad textual replay machinery with it?

Is the source-context API concrete enough to reconstruct an original theorem,
including local hypotheses, local definitions, `set` equalities, and the
negated conjecture boundary?

Are the current Smolka-style transformations proof-producing in Megalodon, or
do any of them still rely on hidden assumptions or dynamic known facts?

Does Vampire emit all information needed for Skolemization: dependencies,
sorts, introduced symbols, source formula, target formula, and definitional
or choice justification?

For each remaining frontier failure, is the proposed fix adding precise
Vampire data and a small checker, or is it adding another heuristic
Megalodon-side recognizer?

Are future broad tests held out enough to prevent overfitting to the current
100-case frontier?

## Final Assessment

The project has moved from a broad, admitted, Python-assisted skeleton system
toward a real Vampire-certificate-to-Megalodon-proof-term pipeline. That is
the right direction. The branch now has real native proof-term construction,
better source validation, a stricter trust boundary, a separate `vampire`
command path, and the beginning of a shared kernel certificate vocabulary.

The project is still not at the requested finish line. The main missing pieces
are a typed Vampire primitive IR, a small extracted Megalodon kernel
checker/elaborator, robust proof-producing Smolka-style transformations,
Skolem dependency discipline, and final original-context theorem composition.

The current 88-case fail-closed preprocessing frontier is a useful and
concrete engineering waypoint. It should be used to guide the next few fixes,
but it should not become the success criterion. The real success criterion is
E1: original Megalodon theorems reconstructed from Vampire certificates with
no hidden proof assumptions.
