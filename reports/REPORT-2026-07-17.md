Date: 2026-07-17

This report summarizes the state of the Vampire-to-Megalodon proof
reconstruction project for external review. It incorporates the previous daily

## Executive Summary

The project is not finished. It is now much better aligned with the audit
recommendations than it was earlier in the week, but it is still a prototype
with focused successes, not a general 100-theorem Vampire-to-Megalodon proof
reconstructor.

The intended finished pipeline remains:

```text
original Megalodon theorem and proof context
  -> THF/TPTP export
  -> Vampire proof search, timeout <= 10s
  -> Vampire-emitted explicit certificate
  -> Megalodon native proof-term checking
  -> proof of the original Megalodon goal
```

The final path must not use `admit`, `aby`, incomplete QED, bridge
assumptions, Python proof reconstruction, certificate-derived `Known`
theorems, or private replacements for Megalodon's equality and logical
constants. The project assumes a classical Megalodon context: `xm`,
double-negation principles, `False`, disjunction, proposition extensionality
where needed, and Megalodon's equality are expected to be available from the
loaded development.

The most important architectural conclusion is unchanged from the July 15 and
July 16 audits:

- Python was useful for exploration, but it is not a qualifying path.
- A broad Megalodon-side OCaml replay engine is also not the final target if
  it guesses proof details Vampire already knows.
- The target architecture is Prover9/Ivy-style: Vampire expands complex
  internal inferences into small explicit proof objects while it still has the
  exact selected literals, substitutions, positions, sorts, introduced
  symbols, and parent clauses; Megalodon checks those objects and elaborates
  native proof terms.
- Source and preprocessing transformations must be proof-producing. They
  cannot be justified in counted modes by dynamically installing the
  proposition to be proved as a `Known` theorem.

There has been real progress:

- Vampire now has a `MegalodonKernelSyntax` boundary and a first
  `MegalodonKernelStep` builder, with rendered-domain wrappers for clauses,
  literals, substitutions, positions, Skolem metadata, source transforms,
  CNF metadata, definition folds, AVATAR records, URR traces, and subsumption
  primitive metadata.
- Megalodon has a native certificate parser/checker, a shared
  `vampire_kernel_syntax.ml` vocabulary, native proof-term checking for a
  clausal core, source-context resolution infrastructure, and fail-closed
  guards against certificate-derived `Known` propositions in counted
  proof-term modes.
- The live strict 100-case THF/Vampire/certificate run passes structurally:
  `/project/tmp/live_strict_100_megalodon5_current/summary.tsv` reports
  `PASS 100`.
- The current live Skolem proof-term frontier is no longer wholly blocked by
  stale certificates or direct transitional `Known` assumptions:
  `/project/tmp/live-skolem-frontier-script.183108/counts.txt` originally
  reported `SKOLEM_PF_PASS 24` out of 35 eligible Skolem-heavy cases, and the
  checker-only recheck after the left-last-pivot resolution fix reports
  `SKOLEM_PF_PASS 31`, with one remaining rectification blocker, one
  deliberately refused transitional predicate-definition blocker, and two
  stale no-certificate artifacts.

The critical qualifications are:

- `PASS 100` is E4 structural/integration evidence, not proof
  reconstruction. It shows that Vampire can find proofs and Megalodon can
  parse/validate the certificates and metadata for 100 THF problems. It does
  not mean those 100 proofs have been reconstructed as Megalodon proof terms.
- The 31/35 cached recheck of the live Skolem proof-term frontier is
  E2/E3-style focused evidence, not the final E1 original-context target. It
  also has 4 unresolved/non-certificate cases.
- Original-context proof composition is still only partially implemented.
- The small-kernel path is present, but extraction is incomplete. Most logic
  still lives in the large historical `src/vampire_cert_v1.ml` and
  `Shell/MegalodonChecker/MegalodonChecker.cpp` modules.

The current best description is: the project has moved from "broad replay and
bridges" toward a real proof-object architecture, but the qualifying line is
still ahead.

The audit trajectory matters because it changed what is counted as progress.

The July 14 audit found that earlier strict runs still allowed bridge
premises and that source linking was label-based rather than
proposition-based. That made some earlier "passes" integration evidence, not
reconstruction evidence.

The July 15 audit accepted that closed/source-checked evidence was improving,
but criticized the project for growing a large Megalodon-side replay engine.
It recommended a Prover9/Ivy-style path: keep the current machinery as a
regression oracle, but move proof detail into Vampire and make Megalodon a
small checker.

The July 16 audit found the most important hidden trust bug in the native
preprocessing path: many transformations were proved by dynamically adding a
certificate-derived proposition to the `Known` theorem table and then applying
it. That is a bridge assumption in disguise. The current branch now treats
such behavior as structural diagnostics only. Counted native proof-term paths
must reject certificate-derived `Known` names except for a fixed reviewed
logical basis.

The audit response and design documents from July 16-17 are accepted here as
binding project policy. The correct next milestone is not "raise a broad
frontier number by adding more Megalodon-side heuristics"; it is "produce
small explicit Vampire certificates and check them natively without hidden
assumptions, then compose them with the original source context."

## Evidence Classes Used in This Report

The project now uses evidence classes rather than ambiguous "pass" labels:

- E1: original Megalodon theorem reconstructed in its live source context,
  with no `admit`, no `aby`, no bridge assumptions, and no
  certificate-derived `Known`.
- E2: closed native `Syntax.pf` proof of a live Vampire certificate, still at
  the exported THF/certificate boundary.
- E3: focused or synthetic native proof-term checks for the small kernel or a
  limited transformation fragment.
- E4: structural certificate validation, metadata validation, source-map
  validation, integration runs, and transitional diagnostics.

The live strict 100-case run is E4. The old preprocessing frontiers that
required `MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1` are E4. The
native core proof-term tests are E3 unless they are live exported proofs with
closed proof terms. Focused live Skolem proof-term checks are closer to E2,
but they are still not E1 until they are composed into the original Megalodon
theorem context.

This distinction is the main correction from earlier reporting.

## Original Objective and Operational Constraints

The original task was to download Vampire and Megalodon, find or adapt the
Vampire proof reconstruction support originally aimed at Lean, and port proof
reconstruction to Megalodon. The expected final system should:

1. Export Megalodon goals to THF/TPTP.
2. Run Vampire on THF problems, not FOF approximations.
3. Use a short Vampire timeout, currently capped at 10 seconds per problem.
4. Run export, Vampire proof search, and certificate checking in parallel,
   normally 10 to 20 jobs for broad batches.
5. Avoid repeatedly rerunning known-unsolved Vampire searches.
6. Ask Vampire to emit proof objects rich enough for reconstruction.
7. Check those proof objects in Megalodon using native proof terms.
8. Link source facts back to original Megalodon lemmas, definitions, local
   hypotheses, set-generated equalities, and conjectures.
9. Use Megalodon's existing equality, `False`, disjunction, and classical
   library facts.
10. Avoid theorem-specific hardwiring and library-specific tricks.
11. Avoid `admit`, `aby`, or `-allowincompleteqed` in the resulting proof.
12. Validate on at least 100 representative Megalodon theorems and their
   Vampire proofs.

Additional local constraints from the conversation are also followed:

- `/project/tmp` is the temporary directory for generated proof/test artifacts.
- Vampire compilation should use parallel build commands such as
  `make -j10` where possible.
- Test harnesses should run in parallel and should not perform slow sequential
  export/search/check cycles when a batch artifact can be reused.
- Problems before the library's excluded-middle point are not a priority
  because the reconstruction assumes classical reasoning.
- The result should be general over libraries; it should not hardwire
  theorem names like `famunion` or optimize for the current benchmark list.

## Current Architecture

The intended architecture now has four layers.

### Vampire Certificate and Primitive IR Layer

Vampire is responsible for emitting proof details while they are still
available internally. For a complex inference, the certificate should not
merely say "superposition" or "unit_resulting_resolution" and leave
Megalodon to reverse-engineer the missing local facts. Vampire should emit:

- parent step identifiers;
- selected literals and pivot indices;
- equality side and rewrite direction;
- rewrite positions;
- substitutions before and after macro steps;
- variable and symbol sorts;
- introduced Skolem symbols and their dependencies;
- source formulas before and after transformations;
- result formulas and clauses;
- AVATAR split/component/refutation metadata where relevant;
- primitive expansion chains for macro inferences.

The Vampire fork now contains
`Shell/MegalodonChecker/MegalodonKernelSyntax.{hpp,cpp}`. This is not yet the
complete primitive proof IR requested by the audits, but it is a real boundary
around the old monolithic exporter. The current line counts show the state:

### Megalodon Certificate Checker Layer

Most Megalodon-side work still lives in `src/vampire_cert_v1.ml`, which is
too large:

```text
25575 src/vampire_cert_v1.ml
   54 src/vampire_kernel_syntax.ml
```

The extracted `src/vampire_kernel_syntax.ml` is currently small. It owns the
shared `kernel_v1` rule vocabulary and primitive-contract table. That is a
useful start, but not yet the modular checker/elaborator requested by the
audits.

The desired module split remains:

- `vampire_kernel_syntax.ml`: syntax, stable rule names, primitive contracts;
- `vampire_kernel_check.ml`: structural and type checks for the primitive
  certificate;
- `vampire_kernel_elab.ml`: native `Syntax.pf` elaboration for primitive
  steps;
- `vampire_source_context.ml`: source-context lookup and proof resolution;
- a compatibility module for parsing the historical certificate format.

The current monolithic file does useful work, but future broad additions to it
should be treated as technical debt unless they are small compatibility fixes
or extraction steps.

Current native checker capabilities include:

- strict S-expression certificate parsing;
- source-map validation;
- supported source formula comparison;
- source-obligation auditing;
- source-context auditing against loaded Megalodon knowns and locals;
- native core proof-term checking;
- native preprocessing proof-term checking for selected fragments;
- explicit rejection of certificate-derived `Known` propositions in counted
  proof-term paths;
- proof-producing handling of several generated set/reflexivity obligations;
- partial final composition back to live Megalodon `aby` targets.

### Source Context Layer

Source context is the bridge between exported THF identifiers and the original
Megalodon development. A checked exported refutation is not sufficient if its
premises are not connected back to real Megalodon facts.

The intended API shape remains:

```ocaml
type source_proof =
  | GlobalKnown of string * Syntax.tm
  | LocalHyp of int * Syntax.tm
  | Definitional of Syntax.tm * Syntax.pf
  | Generated of Syntax.tm * Syntax.pf
  | Unresolved of string * Syntax.tm

type source_context = source_id -> source_proof
```

The current implementation handles several source categories:

- global known facts resolved by hash/original name/TPTP name, then checked
  semantically;
- local hypotheses in the live proof context;
- local types and proof-local definitions;
- source-map aliases for mangled exported names;
- generated `set` equalities, proved by reflexivity/conversion when possible;
- conjecture facts, discharged at the final refutation-to-goal boundary;
- unresolved facts, which fail strict qualifying modes.

This is one of the most important improvements over early source-map work.
The checker is no longer allowed to accept an arbitrary source formula merely
because a label exists. It must compare the exported proposition against a
real source proposition or supply a proof-producing generated fact.

Remaining source-context gaps include:

- full local definition proof production when a local `set` equality is
  actually used by the refutation;
- robust original-name recovery for every mangled THF name shape;
- full final composition for larger local contexts with several definitions,
  hypotheses, and negated conjecture variants;
- avoiding any reliance on the old `aby` command as part of final evidence.

### Smolka-Style Transformation Layer

Source-to-clause transformations are not ordinary clausal kernel rules. They
are a separate proof-producing layer, roughly following the Smolka-style
view:

- source formula input;
- formula-term input/copying;
- definition input/fold/unfold;
- rectification;
- FOOL Boolean lifting and exhaustiveness;
- ENNF;
- CNF literal/formula projection;
- Skolemization using explicit introduced symbols, dependencies, sorts, and
  a choice principle;
- optional later AVATAR/SAT layers.

The current branch has made progress on these transformations, especially on
rectification/FOOL/ENNF/CNF and Skolemization metadata, but they are not
complete. The important trust invariant is now explicit: a transformation
either produces a checked native proof term or is rejected in counted mode.
It cannot silently insert a certificate-derived theorem such as
`vampire_skolem_formula_u123` or `vampire_predicate_definition_u123` into the
known table.

The latest Skolem work is the clearest example of this layer beginning to
work properly.

### Trust Reset for Preprocessing Proof Terms

The July 16 audit found that the native preprocessing proof-term frontier was
using certificate-derived `Known` propositions. The current branch makes that
behavior fail closed in counted proof-term modes. The old behavior is only
available through:

```sh
MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1
```

and is classified as diagnostic E4 evidence.

The checker now traverses checked proof terms and rejects generated
certificate-derived proof constants with names beginning with `vampire_`,
except for a fixed reviewed logical basis such as choice and
not-forall/existence lemmas. This makes the trust boundary mechanically harder
to bypass.

### Core Textual Emission Reclassified

Earlier textual closed emission could be useful, but it is not the target
when native proof terms are available. Commit `3a44524` explicitly
reclassified core textual closed emission as diagnostic. That prevents
generated `.mg` scripts from being counted as the primary reconstruction
evidence.

### Preprocess Macro Reconstruction

Commit `a445ee3` reconstructed several preprocessing macros natively rather
than through transitional knowns. The significant families are:

- `rectify_formula`;
- `fool_formula`;
- `ennf_formula`;
- associated `_subst` follow-up steps.

The associated audit moved a selected cached preprocessing corpus into
`PREPROCESS_STRUCTURAL_PASS 84` without the transitional-known opt-in. This
is still not the final target, but it removed one large class of hidden
bridges.

### Skolemization

The Skolemization work is currently the most active proof-term frontier.

Commit `5655c7f` made a live direct/nested Skolem preprocessing fixture check
as a real native proof term. It added explicit substitution replay through a
chain of existential binders and sequential conservative definitions for
nullary Skolem symbols.

Commit `10a6d53` expanded the dependent Skolem frontier. It delays generated
Skolem expansion until a symbol application supplies enough arguments for the
definition's leading lambda arity. It also added normalization of generated
Skolem definitions for formula-orientation matching while keeping the proof
term on Megalodon's real equality.

Commit `1a5096a` handled nested Skolem orientation. It generalized sequential
Skolem definitions from nullary/top-level occurrences to a preorder walk of
the source formula, including walks under `forall`, `vampire_or`,
`vampire_and`, and implication. It can eliminate nested
`vampire_exists_prop` in the forward direction using the existing choice
principle and then continue structural conversion.

This work is not theorem-specific hardwiring. It uses Vampire-emitted
substitution lists, introduced symbol metadata, and source formulas. The
remaining problems are in general proof-term opening/orientation and related
preprocessing fragments, not in recognizing a single benchmark theorem.

### Subsumption and URR Metadata

Megalodon now validates subsumption primitive chain payloads emitted by
Vampire. The representative check ensures that a `subsumption_resolution`
macro carrying primitive expansion metadata has coherent pivot and chain
fields. This is not yet a complete proof-term implementation for every
subsumption case, but it is aligned with the Prover9/Ivy plan: emit the chain
from Vampire and make Megalodon verify the explicit payload.

### Clause Resolution Proof Context

Commit `dd324ce` fixed a proof-context bug in native clause/clause
resolution. The bad branch occurred when the selected pivot was the only
literal in the left clause. The elaborator shifted the right parent proof by
one proof-hypothesis slot before consuming it, even though the surrounding
proof already had exactly the required context. This produced ill-formed
proof terms such as:

```text
Proof hypothesis index 12 is out of bounds for context length 12
```

The fix is small but important: it removes the extra proof shift in the
left-last-pivot case and adds a dedicated regression fixture,
`native_cert_v1_resolve_left_last_pivot_valid`. This was a general
clause-resolution proof-opening bug, not a benchmark-name special case. The
cached seven-case failure cluster now passes.

### AVATAR Status

AVATAR support has improved structurally. The branch now accepts unreferenced
AVATAR split component counts in the validator, and the Vampire side emits
more explicit AVATAR records: components, definitions, split dependencies,
split steps, and refutations.

This remains outside the first small clausal-kernel milestone. The desired
future path is either explicit SAT/RUP-style AVATAR proof objects or a
separately checked AVATAR layer. It should not be represented as a hidden
bridge theorem.

## Linking to Original Megalodon Lemmas, Definitions, and Theorems

This is one of the central requirements, and it is only partially done.

### What Works

The source-context resolver can load a Megalodon file, inspect known facts and
local proof context, and resolve some certificate source facts back to actual
Megalodon proofs.

The current system can:

- resolve global knowns by hash/original name/TPTP name;
- verify that a resolved known proves the exported source proposition;
- handle source-map aliases produced by name mangling;
- match local hypotheses in simple and shifted contexts;
- account for local type declarations;
- account for local `set` definitions as source-map facts;
- prove generated set-reflexivity equalities by reflexivity/conversion when
  possible;
- omit source facts from the proof spine when they are already discharged by
  source-context proofs;
- leave negated conjecture facts for the final refutation-to-goal boundary.

This is materially better than a label-only source map. It reduces the risk
that the certificate attaches an arbitrary formula to a valid source name.

### What Is Still Missing

The source glue is not yet a complete E1 implementation for arbitrary larger
developments.

Open areas include:

- full proof production for local definitions when used by the refutation;
- full proof production for `set` equalities beyond simple reflexivity or
  conversion cases;
- robust handling of every export name-mangling pattern;
- final composition of a closed native certificate into the exact original
  Megalodon target without depending on `aby`;
- handling larger local contexts where hypotheses, local definitions, and
  generated facts interleave;
- systematic proof of all source-to-clause transformation facts before the
  clausal kernel begins.

The project has therefore made progress on "linking" but has not completed
the original-context proof.

## Equality and Logical Constants

Earlier code paths risked introducing private equality/logical encodings.
The current policy is that the resulting proof must use Megalodon's equality
and logical constants.

The certificate still has an internal representation of equality and clauses,
because it must parse Vampire/TPTP terms. That is not the same as introducing
a new trusted equality. The counted proof-term path should translate
certificate equality into Megalodon's equality and use Megalodon's native
proof rules and library facts.

The same applies to:

- `False`;
- disjunction;
- implication;
- classical principles such as `xm` and double negation;
- proposition extensionality where explicitly used;
- choice principles for Skolemization.

The remaining risk is not policy; it is implementation coverage. Some
normalization/matching logic still lives in the broad checker. The future
small-kernel elaborator should make the equality boundary explicit and small.

## Skolemization Status

Skolemization has moved from "mostly blocked or transitional" to "partially
proof-producing on live regenerated cases."

The current Skolem path uses:

- Vampire-emitted `skolem_formula` steps;
- explicit source formulas;
- explicit substitution lists;
- introduced-symbol metadata;
- dependency names and sorts where available;
- conservative generated definitions for Skolem symbols;
- Megalodon choice principles;
- normalization of generated Skolem definitions for formula matching.

The latest work handles:

- direct existential Skolemization;
- nested existential orientation in several formula contexts;
- nullary Skolem symbols;
- dependent Skolem applications where expansion must wait for enough
  arguments;
- multiple Skolem introductions discovered by walking the source formula in
  preorder.

The main remaining Skolem-related blockers are:

- proof-term opening/shifting in later clausal steps after Skolemization;
- rectification cases that are not bijective Vampire-variable renamings;
- predicate-definition folds after Skolemization;
- broader source/preprocessing proof chains that mix Skolemization with
  AVATAR, definitions, and CNF in more complex ways.

The current cached recheck of the live frontier is 31/35. It is encouraging,
but it is not the end state.

## Prover9/Ivy Path and Small Kernel

The project is now broadly on the Prover9/Ivy path, but not far enough along.

The desired small clausal kernel is:

- `input`: boundary from a proved source/preprocessing clause;
- `instantiate`: explicit substitution;
- `resolve`: binary resolution;
- `factor`: duplicate literal contraction;
- `equality_resolution`: contradiction from a negative reflexive equality;
- `equality_factoring`: equality-specific factoring;
- `paramodulate`: equality rewrite at an explicit position;
- `contradiction`: final empty-clause marker.

Additional names need careful placement:

- `rename` should be alpha-conversion or a special case of instantiation, not
  a broad logical rule.
- `truth_conflict` probably belongs in the FOOL/preprocessing layer unless
  real clausal proofs force it into the kernel.
- AVATAR should be a separate SAT/RUP-style layer or explicit split/refutation
  proof layer, not part of the first kernel milestone.

The most important missing operation is:

```ocaml
open_step_theorem :
  global_context ->
  parent_step_variables ->
  result_step_variables ->
  substitution ->
  stored_proof ->
  opened_proof
```

This operation must define exactly how a stored step theorem is opened in the
context of a later step:

- retained variables are opened without stale shifts;
- substituted variables are closed in the result context;
- dropped variables require explicit substitutions or fail closed;
- proof-hypothesis indices are shifted correctly;
- globals and local result variables have a documented shadowing rule.

The former seven-case Skolem-frontier `resolve` cluster is strong evidence
that this operation still needs to be specified and extracted cleanly. The
cluster is fixed, but the fix was still a local correction inside the large
checker rather than the reusable operation the small-kernel design needs.

## Problems and Technical Debt

### The Monoliths Are Still Too Large

The biggest code-structure problem remains module size and responsibility
mixing.

On the Megalodon side, `src/vampire_cert_v1.ml` still contains parsing,
source maps, structural validation, proof-term checking, preprocessing logic,
textual emission, source-context logic, and multiple test-facing modes.

On the Vampire side, `MegalodonChecker.cpp` is still the main proof exporter.
`MegalodonKernelSyntax` is a good extraction, but it is still mostly a
rendered-record boundary.

The next work should reduce these modules, not add another several thousand
lines to them.

### E4 Pass Counts Are Easy to Misread

The project now has many useful runs that say `PASS`, but only some are proof
reconstruction passes. The report and harness names must be disciplined:

- `PASS 100` in strict live mode is certificate integration.
- `PREPROCESS_STRUCTURAL_PASS` is structural/preprocessing diagnostic.
- `SKOLEM_PF_PASS` is a focused native proof-term frontier.
- E1 requires original-context proof composition without `aby`/`admit`/bridges.

This distinction should be visible in every future report.

### Python Must Stay Quarantined

Python utilities are acceptable for corpus inspection, summaries, and
debugging. They should not grow new logical reconstruction power, and no
Python-generated proof should count in the qualifying path.

### Smolka Transformations Are Still Partial

The branch has meaningful pieces for formula transforms, rectification, FOOL,
ENNF, CNF, and Skolemization. It does not yet have a complete proof-producing
source-to-clause pipeline.

The safe ordering is:

1. source formula proof;
2. rectification proof;
3. FOOL proof;
4. ENNF proof;
5. CNF projection proof;
6. Skolem proof;
7. clausal kernel proof.

Every boundary must produce a proof term or fail closed.

### AVATAR Is Not Yet a Kernel Story

AVATAR metadata is improving, but final proof production is still a separate
problem. The safest direction is an explicit SAT/RUP object for the Boolean
part and a proof-producing bridge from split clauses back to the clausal
kernel. The current AVATAR support should remain outside the first small
kernel milestone.

## Recommended Next Milestones

The next milestones should be strict and narrow.

1. Fix the remaining Skolem-frontier blockers.
   The seven-case resolve cluster is fixed. The remaining proof-producing
   blockers are rectification (`hammer.10644.15`) and predicate-definition
   proof production (`hammer.11925.125`), plus the two no-certificate cases.

2. Extract `open_step_theorem`.
   Do not add more local proof-shifting special cases. Specify the operation
   once and reuse it for `resolve`, `factor`, `instantiate`,
   `equality_resolution`, `equality_factoring`, `paramodulate`, and `flip`.

3. Keep counted modes free of certificate-derived `Known`.
   The `TRANSITIONAL_vampire_predicate_definition_u269` failure in
   `hammer.11925.125` is correct behavior until a real proof term exists.

4. Turn one live proof into a complete E1 proof without `aby`.
   Choose a small but real original-context target with source facts and at
   least one generated set/reflexivity or local-definition fact.

5. Convert the Vampire rendered wrapper records into typed primitive records.
   The current `MegalodonKernelStep` builder is a useful migration boundary.
   The next step is typed terms, literals, substitutions, positions, and
   parent references, not more string metadata.

6. Move Megalodon kernel checking out of `vampire_cert_v1.ml`.
   Create `vampire_kernel_check.ml`, `vampire_kernel_elab.ml`, and
   `vampire_source_context.ml`, then migrate functionality without adding
   new replay power during the move.

7. Prove ten live exported certificates as E2.
   These should be real Vampire proofs, closed native proof terms, no
   transitional knowns, no textual-emitter fallback.

8. Compose ten live original-context theorems as E1.
   Only after this should the project rerun the 100-theorem held-out gate as
   proof reconstruction rather than structural validation.

9. Keep broad tests parallel and bounded.
   Use `/project/tmp`, `JOBS=10` or higher where suitable, and Vampire
   timeouts of at most 10 seconds. Reuse generated artifacts when debugging
   checker failures.

## Outlook

The project is now pointed in the right direction. The main risk is relapse:
adding more Megalodon-side guessing to raise short-term pass counts. That
would repeat the earlier failure mode and make the system harder to audit.

The promising path is narrower:

- make Vampire print exact primitive proof data;
- keep the small kernel small;
- make Megalodon check native proof terms only from explicit data;
- treat source/preprocessing transformations as proof-producing layers;
- compose back into the original Megalodon context;
- use clear evidence labels.

With the clustered Skolem/resolve proof-opening bug fixed, the next iteration
should turn focused live certificates into E2 or E1 evidence and extract the
proof-opening rule into the small-kernel path. If instead the next iteration
broadens the OCaml reconstructor again, the audits' main concern will remain
unresolved.

My current assessment is:

- E4 integration is strong: 100 live THF certificates can be generated and
  structurally validated.
- E3/E2 proof-term evidence is real but still narrow: native core, URR slices,
  and 31 Skolem-heavy cached rechecks of live frontier certificates.
- E1 original-context reconstruction is partially implemented and not yet
  delivered at scale.
- The project should continue, but under the stricter small-kernel and
  source-context plan described above.
