## Executive Summary

The project is not complete. The most important unfinished requirement is still
E1: a Vampire proof reconstructed as a native Megalodon proof term and glued
back to the original Megalodon theorem, its local context, its lemmas, its
definitions, its generated `set` equalities, and the final conjecture
discharge, with no `admit`, no `aby`, no incomplete QED, no bridge
assumptions, and no certificate-derived `Known` facts.

The work since the previous report is nevertheless materially better aligned
with the July 16 audit. The key correction was to accept the audit's evidence
classification and stop treating broad preprocessing proof-term passes with
dynamic `Known` insertion as reconstruction evidence. The qualifying path is
now explicitly:

```text
Vampire primitive certificate IR
  -> canonical S-expression certificate
  -> Megalodon small-kernel parser/checker
  -> native Syntax.pf proof terms
  -> original Megalodon source/context composition
```

Strict live certificate runs that only validate source maps and metadata are
useful, but they are E4 structural evidence. Transitional preprocessing runs
that opt in to certificate-derived `Known` facts are also E4 diagnostics. The
counted path must build and check `Syntax.pf` values without such facts.

The strongest progress since the audit is architectural rather than numerical:

- Megalodon now has an extracted `vampire_kernel_syntax` boundary for kernel
  rule names, schema strings, and primitive-expansion contracts.
- Vampire now has a matching `MegalodonKernelSyntax` boundary and rejects
  unsupported `kernel_v1` rule names before printing certificates.
- Counted native proof-term modes reject certificate-derived `Known` names
  except for the fixed reviewed logical basis.
- The source-context layer now distinguishes global known facts, local
  hypotheses, local definitions, generated facts, conjecture facts, and
  unresolved facts.
- Set-generated equalities from source maps have an explicit generated proof
  route, including reflexivity/conversion.
- The theorem-opening invariant has been named and partially implemented for
  clausal proof reuse under result contexts.
- Vampire-side certificate output has moved several frequent metadata clusters
  out of anonymous string-field assembly and into named rendered certificate
  records.
- Unit-resulting resolution now exposes a primitive expansion chain summary
  that includes ordered primitive substeps and requires at least one `resolve`
  primitive.

The most important limitation is that the Vampire side still does not have the
full Prover9/Ivy-style internal primitive proof-object builder. Current
Vampire records are a migration layer: they are named and structured better
than raw string vectors, but most fields are still rendered text rather than
typed Vampire terms, literals, substitutions, positions, and source payloads.
Megalodon can audit them and use some focused native proof-term paths, but the
general primitive consumer is not finished.

My current assessment:

- The project direction is now correct.
- The earlier Python/string-reconstruction path is not the qualifying path.
- The broad OCaml replay engine must remain a regression oracle, not the main
  implementation surface.
- The immediate engineering target should be the Prover9/Ivy-style primitive
  builder in Vampire plus a small Megalodon kernel elaborator.
- The next meaningful milestone is not another broad `PASS 100`; it is a small
  number of original-context E1 examples with no trust-boundary exception.

## Evidence Classes Used Here

The current documentation uses these evidence classes:

- E1: original Megalodon theorem reconstructed in its original context, with
  no `admit`, no `aby`, no bridge assumption, and no certificate-derived
  `Known`.
- E2: closed native `Syntax.pf` proof of a live Vampire certificate, still
  bound to exported THF rather than the original Megalodon theorem context.
- E3: synthetic or focused primitive-kernel native proof-term checks.
- E4: structural certificate/source/metadata validation and transitional
  diagnostics.

This classification is important because several older numbers are real
engineering signals but not proof reconstruction. For example, strict live
`PASS 100` runs show that Vampire can regenerate certificates and Megalodon
can parse, source-check, and metadata-audit them. They do not prove the
inferences. Similarly, preprocessing frontiers that require
`MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1` are structural
triage, not proof checking.

## What Has Been Done Since the Previous Report

### 1. Accepted the July 16 audit and reset the trust boundary

The branch now treats the July 16 audit as correct. The audit's central point
was that dynamic insertion of certificate-derived `Known` propositions is a
hidden bridge assumption. That pattern is no longer allowed in counted native
proof-term modes.

The current checker has a guard that traverses proof terms before
`check_propofpf` and rejects generated certificate-derived proof constants
whose names start with `vampire_`, except for the fixed reviewed logical
basis such as the choice and not-forall/existence principles. The old
transitional behavior is still available only under
`MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1`, and the tests and
documents classify it as E4.

This is the most important methodological change. It prevents the project from
raising pass counts by adding more hidden assumptions.

### 2. Extracted the first kernel syntax boundary in Megalodon

Megalodon now has `src/vampire_kernel_syntax.ml` and
`src/vampire_kernel_syntax.mli`. This module defines the shared
`kernel_v1` schema, rule vocabulary, primitive-expansion contracts, structural
migration rules, and supported rule names.

`src/vampire_cert_v1.ml` still remains large and still owns too much. However,
the rule-contract data is no longer entirely embedded in the monolith. The
strict checker uses the extracted module to reject unsupported kernel rules.
The negative fixture `native_cert_v1_invalid_kernel_rule.sexp` exercises that
failure mode.

This is only the first extraction. The real target remains:

- `vampire_kernel_syntax.ml`: certificate syntax and rule contracts;
- `vampire_kernel_check.ml`: small structural/kernel checks;
- `vampire_kernel_elab.ml`: `Syntax.pf` elaboration;
- `vampire_source_context.ml`: original source/context resolution.

### 3. Added the matching kernel syntax boundary in Vampire

Vampire now has `Shell/MegalodonChecker/MegalodonKernelSyntax.{hpp,cpp}`.
The exporter consumes that boundary for schema strings, supported rule names,
and primitive-expansion contracts.

The latest Vampire commit before this report is:

```text
d426e8d70 Expose URR primitive expansion chain
```

The important effect is that unsupported `kernel_v1` rules fail closed on the
Vampire side before a certificate is printed. This mirrors Megalodon's strict
rule-name guard and reduces the risk that a misspelled or experimental rule
silently lands in a certificate that the checker interprets differently.

This is still not a full primitive IR. It is the beginning of the vocabulary
boundary needed for that IR.

### 4. Moved frequent Vampire metadata clusters into named rendered records

The Vampire side has begun moving away from ad hoc field vectors in
`MegalodonChecker.cpp`. During this branch, the following clusters were
represented as named rendered-domain records:

- parent and conclusion payloads;
- literal selections;
- rewrite-position metadata for superposition and demodulation;
- unit-resulting-resolution trace steps and trace objects;
- AVATAR component metadata;
- AVATAR definition metadata;
- split dependencies;
- AVATAR split metadata;
- AVATAR refutation metadata.

The current wrappers also distinguish rendered units, terms, formulas,
literals, clauses, substitutions, and positions instead of storing every field
as an undifferentiated `std::string`.

This should be understood precisely. It is not yet typed Vampire proof data.
The serialized certificate is still a string-oriented S-expression format.
But the exporter now has named objects at the certificate boundary, which makes
the next conversion to typed terms/literals/substitutions/positions more
mechanical and auditable.

### 5. Made unit-resulting resolution more Prover9/Ivy-like

The most concrete recent inference-class improvement is for
unit-resulting resolution, abbreviated URR.

Prover9's Ivy exporter does not leave hyper-resolution or unit-resulting
resolution as a large opaque inference. It expands the proof into primitive
resolution-like steps, checking that the expansion reconstructs the original
clause. The current branch starts moving Vampire in that direction.

For URR, Vampire now emits not only the macro record and trace fields, but also
a primitive expansion chain summary in the `kernel_v1` metadata:

- `primitive_expansion_step_count`;
- `primitive_expansion_step_N_rule`;
- `primitive_expansion_step_N_id`;
- `primitive_expansion_requires_count`;
- `primitive_expansion_requires_N`.

The focused audit requires every emitted URR macro record to contain at least
one ordered primitive `resolve` step and at least one `resolve` requirement.
The refreshed fixtures include examples such as:

- `hammer.11453.77.native.sexp`, where URR step `u459` has a 7-step primitive
  chain including `substitute` and `resolve`;
- `hammer.11703.242.native.sexp`, where URR step `u1680` has a 10-step chain
  including `substitute`, `equality_symmetry`, and several `resolve` steps.

The focused validation passed:

```text
kernel_v1 records: 48
kernel_v1 rewrite-position records: 3
unit_resulting_resolution 3
```

The native primitive audit over the same two-case sample also passed, with
counts including:

```text
resolve 9
substitute 10
equality_symmetry 7
paramodulate 6
```

A strict Megalodon certificate check on the two refreshed fixtures passed:

```text
hammer.11453.77: strict checked 65 steps
hammer.11703.242: strict checked 44 steps
```

This remains E4 structural/metadata evidence for URR. It becomes E2 or E1 only
when Megalodon consumes the primitive chain as proof terms and no longer uses a
broad URR replay rule.

### 6. Improved source-context binding

The source-context work is now more concrete than in the early reports.
`src/vampire_source_context.ml` defines source facts as:

```ocaml
type source_proof =
  | GlobalKnown of string * tm
  | LocalHyp of int * tm
  | Definitional of tm * pf
  | Generated of tm * pf
```

The resolver tracks:

- hash-backed global known facts;
- local hypotheses;
- local definitions;
- generated facts;
- conjecture and negated-conjecture facts;
- unresolved facts.

It also reports the number of source assumptions that remain after
source-context proofs are consumed. Smoke tests cover source-map aliases,
hash-backed known facts, local facts, multi-local contexts, local definitions,
and generated `set_reflexivity` source-map entries.

This matters for the user's concern about linking proof skeletons back to the
original Megalodon development. The system now has an explicit path for
recovering original source labels and for distinguishing facts that came from
the library, local context, definitions, generated set equations, and the
conjecture boundary.

What remains missing is full E1 composition. Local hypotheses and matched
local definitions can be recognized and audited, but the whole Vampire
refutation is not yet generally converted into a proof of the original theorem
in its original proof context.

### 7. Handled generated set equalities by reflexivity/conversion

The user pointed out that some TPTP axioms come from Megalodon's `set`
command and may not correspond to user-written claims. The current source
context treats `set_reflexivity` and `local_set_reflexivity` as generated
source kinds.

The generated proof path attempts reflexivity/conversion:

- quantified generated equalities are handled by recursively adding type
  lambdas;
- implications of the form `P -> P` are proved by `fun h => h`;
- equality-like propositions are handled by the native reflexive equality
  proof path where possible.

This is not the whole original-context story, but it addresses the concrete
case where an exported source axiom is not a named theorem and should be
proved directly.

### 8. Advanced the theorem-opening invariant

One recurring native proof-term problem has been that certificate steps are
stored theorem-like, often with step-variable `TLam` binders, and later
reused under a different result-variable context. Blind proof shifting or
global normalization caused either de Bruijn failures or regressions.

The current branch names the required operation:

```ocaml
native_core_open_step_theorem_body_in_result_context
```

The intended future abstraction is:

```ocaml
open_step_theorem :
  global_context ->
  parent_step_variables ->
  result_step_variables ->
  substitution ->
  stored_proof ->
  opened_proof
```

The helper is now shared by several core rules, including `resolve`,
`substitute`, `equality_resolution`, `equality_factoring`, `paramodulate`, and
`factor`. A regression checks that dropping a parent step variable without an
explicit Vampire substitution fails closed.

This is E3/E2 infrastructure, not final E1 completion. But it is the right
kind of fix: one named operation with a binder invariant, rather than many
local special cases.

### 9. Added focused native proof-term progress for Skolemization and AVATAR

Skolemization is still one of the main source/preprocessing blockers, but the
current branch has a narrow proof-producing seed for direct existential
choice. The accepted case defines the generated Skolem symbol by a Megalodon
delta definition, uses the fixed choice principle, and checks the resulting
`Syntax.pf` without dynamic `Known` insertion.

Dependent Skolemization remains harder. The current representative failure
class involves theorem opening, retained variables, and dependent generated
Skolem terms. This should not be patched by guessing in OCaml. It needs typed
Vampire metadata and the shared theorem-opening operation.

AVATAR also has focused proof-term seeds. The branch can replay a restricted
AVATAR split-definition/component shape and a restricted SAT-resolution trace
without transitional-known opt-in. The supported SAT fragment requires each
SAT input to be exactly a proved split clause and each RUP step to be a binary
resolution step over earlier SAT proof clauses.

This is meaningful E3 progress, but general AVATAR is not solved. Full
SAT/RUP checking and split-dependency proof production remain open.

## Current Problems

### 1. No full E1 theorem reconstruction yet

The system can identify and audit source facts, and it can prove some generated
source entries. It does not yet generally produce:

```ocaml
source_context -> certificate -> Syntax.tm * Syntax.pf
```

where the resulting proof term is the original theorem in the original
Megalodon context. This is still the main project gap.

### 2. Vampire primitive IR is not complete

The Vampire side has named rendered certificate objects, supported-rule guards,
and primitive-expansion metadata. It still lacks the full internal object
requested by the audit:

```text
MegalodonPrimitiveStep {
  id;
  rule;
  parents;
  conclusion;
  selected literal/equality indices;
  rewrite position and direction;
  substitution;
  variable and symbol sorts;
  source/preprocess payload;
}
```

Until this exists, too much proof reconstruction pressure remains on the
Megalodon importer.

### 3. The OCaml importer is still too large

`src/vampire_cert_v1.ml` still contains parsing, structural checking, native
core proof-term code, preprocessing handling, source assumptions, and legacy
textual emission. It has been partially fenced by new modules, but it has not
yet been broken into the checker/elaborator/source modules needed for a small
auditable core.

The next Megalodon-side work should be extraction and shrinkage, not broad
feature growth inside this file.

### 4. Smolka-style transformations remain partial

The current source/preprocessing layer has pieces for:

- source entry;
- definitions and folds;
- rectification;
- FOOL transformations;
- ENNF/formula normalization;
- CNF projection;
- Skolemization;
- AVATAR-related formulas.

But these are uneven. Some are structural-only, some have focused proof-term
seeds, and some still require transitional diagnostics for broad coverage.

The Smolka-style path should be a separate proof-producing layer above the
clausal kernel. It should not be encoded as clausal primitive rules, and it
should not be justified by hidden `Known` propositions.

### 5. Skolemization is still not fully solved

Direct existential Skolemization has a narrow choice-based proof-term path.
Dependent Skolemization and interaction with theorem opening remain open.

The right solution is probably a combination of:

- Vampire exporting introduced symbols, dependencies, sorts, and substitution
  structure explicitly;
- Megalodon defining generated symbols conservatively;
- proof terms based on classical choice and the exported dependencies;
- strict rejection when the dependency structure is outside the supported
  fragment.

### 6. AVATAR remains a separate proof layer

AVATAR should not be hidden behind a bridge theorem. The focused native
proof-term seeds for AVATAR split definitions and binary SAT resolution are
useful, but full AVATAR needs either:

- a checked SAT/RUP-style proof object, or
- a dedicated, explicit Megalodon AVATAR proof layer with clear semantics.

The current branch has metadata for AVATAR components, definitions, splits,
split dependencies, and refutations, but full proof checking is still open.

### 7. Equality must remain Megalodon's equality

The current certificate still contains wrappers such as proposition equality
forms because of the exported THF encoding. The design requirement is that the
final proof path use Megalodon's real equality and logical constants, not a
private equality theory. The source-context code already recognizes the
Megalodon polymorphic equality hash for generated equality proofs. Further
work should normalize wrappers toward the real equality boundary rather than
inventing new equality constants.

## Prover9/Ivy Lessons Applied So Far

The Prover9 analysis remains central. Prover9's Ivy mode is not merely a
printer. It expands Prover9 proof justifications into a small lower-level
proof vocabulary while still inside the prover. It then checks that the
expanded clause equals the original proof clause.

For this project, the corresponding design is:

- Vampire expands macro inferences while it still knows selected literals,
  substitutions, positions, and orientations.
- The emitted certificate uses a small primitive vocabulary.
- Megalodon checks and elaborates that vocabulary into `Syntax.pf`.
- Compound names like superposition, demodulation, URR, and AVATAR do not
  become opaque Megalodon rules unless they have separate checked proof
  layers.

Current Vampire work applies this lesson partially:

- demodulation and superposition now share a rendered rewrite metadata shape;
- URR now exposes a resolve-oriented primitive chain summary;
- unsupported `kernel_v1` rules fail closed;
- rendered-domain wrappers make the next typed conversion more reviewable.

What is still missing is the central Prover9/Ivy move: a first-class typed
primitive step list built before printing, with a single printer and a
post-expansion consistency check against Vampire's original conclusion.

## Recommended Next Work

The next work should be deliberately narrow and evidence-driven.

1. Build a real Vampire primitive-step builder.

   URR should be the first macro lowered through it. The builder should produce
   actual primitive records for `substitute`, `equality_symmetry`, and
   `resolve`, then serialize those records. The existing URR chain summary is
   the migration contract, not the endpoint.

2. Add a Vampire-side expansion consistency check.

   For each macro lowered into primitive records, Vampire should check that the
   final primitive result equals the original Vampire inference conclusion.
   This mirrors Prover9's expansion discipline and keeps the exporter honest.

3. Extract the Megalodon primitive checker/elaborator.

   Move the small kernel proof-term path out of `vampire_cert_v1.ml`. Start
   with the core rules already supported: input/source entry, substitute,
   resolve, factor, equality resolution, equality factoring, equality symmetry,
   and paramodulation.

4. Consume URR primitive chains as proof terms.

   The immediate E2 target should be a small live set where URR is checked by
   consuming the primitive chain, not by accepting URR as a broad macro.

5. Implement a minimal E1 source-context example set.

   The first E1 corpus should be small but representative:

   - one theorem using only global known facts;
   - one theorem with a local hypothesis;
   - one theorem with a local definition;
   - one theorem with a generated `set_reflexivity` fact;
   - one theorem requiring conjecture-negation discharge.

6. Add Smolka-style transformations one family at a time.

   The recommended order is source entry, definitions, rectification, FOOL,
   ENNF, CNF projection, then Skolemization. Each family should have one or
   more proof-producing fixtures before broad pass counts are pursued.

7. Keep the 100-theorem gate for later.

   The 100-theorem gate should be rerun after ten live E2 examples and at
   least five E1 source-context examples exist. Running it too early rewards
   broad structural coverage rather than proof reconstruction.

## Outlook

The project is now in a healthier but stricter state than a few days ago. The
branch no longer has a credible path to success through Python translation,
generated scripts with admits, or broad OCaml guessing. It has to succeed by
making Vampire emit small explicit proof objects and making Megalodon check
them as native proof terms.

The recent URR chain work is a good example of the desired direction: expose
the macro's primitive explanation in the certificate, audit that the
explanation exists, and prepare Megalodon to consume the primitive sequence.
The next step is to turn that explanation from metadata into proof-term input.

The main project risk is still scope. Vampire proofs contain source
transformations, clausal inferences, equality reasoning, Skolemization, and
AVATAR. Trying to solve all of them at once in `vampire_cert_v1.ml` caused the
earlier architectural drift. The better path is to finish one narrow vertical
slice:

```text
original Megalodon theorem
  -> exported THF
  -> Vampire primitive certificate
  -> Megalodon small-kernel Syntax.pf
  -> source-context theorem proof
```

for a small but real set of examples. Once that slice exists, the project will
have a reliable standard for broadening coverage. Until then, all broad pass
counts should remain secondary evidence.
