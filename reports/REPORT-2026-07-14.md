## Executive Summary

The project goal remains to reconstruct Vampire proofs inside Megalodon for
Megalodon-exported THF/TPTP problems, eventually over larger Megalodon
developments, without `admit`, without `aby`, and without
`-allowincompleteqed`. The intended final system should connect the Vampire
refutation back to the original Megalodon theorem, original lemmas and
definitions, generated `set`-command facts, Skolem symbols, and transformation
steps such as FOOL, CNF, normal form, and skolemization.

Since the 2026-07-13 report and audit, the project has made a significant
operational shift in the right direction. The counted reconstruction path is no
longer the Python reconstructor. The active path is now Megalodon's native OCaml
certificate importer/emitter in `src/vampire_cert_v1.ml`, fed by a Vampire
native S-expression certificate. That is aligned with the audit's
recommendation to stop building a Python prover and to reuse Megalodon's own
syntax and checking machinery.

The native path now has a real, repeated benchmark gate. On the current
committed Megalodon head `d59d931`, it emits and checks 213 source-linked
Megalodon proof scripts from cached Vampire native certificates. Those generated
scripts contain no textual `admit`, no `aby`, and no
`-allowincompleteqed`. The validating artifact is:

```text
/project/tmp/source_linked_slice_1_400_emit_fool_helpers_091647
PASS 213
```

This is substantial progress compared with the earlier admitted skeletons. It
means Megalodon can parse the native certificate, emit a large self-contained
proof script, and kernel-check the resulting script for at least 213 cached
Vampire proofs.

However, this is still not the finished project. The generated scripts still
contain 5,817 bridge assumptions. These bridge assumptions are not `admit`; they
are explicit theorem premises. Therefore Megalodon is checking a theorem of the
form:

```text
original source assumptions + reconstruction bridge assumptions -> False
```

That is useful and much better than hidden admissions, but it is not yet a full
proof reconstruction of the original theorem. The remaining work is to eliminate
those bridge assumptions by replaying or certifying the corresponding Vampire
inferences and preprocessing transformations.

Recent committed work has been moving individual bridge classes into explicit
Megalodon proof terms. The most recent examples include structural resolution,
strict substitution, unit and non-unit paramodulation fragments, CNF identity
and conjunction projection fragments, factor modulo clause order, atomic FOOL
formula lifts, guarded equality symmetry, and guarded FOOL implication
conversions via reusable helper claims.

The largest latest improvement is `d59d931`. It converts a previously failed
FOOL-implication experiment into a committed, full-suite-passing change. The
successful version does not inline huge ad hoc proof terms. It factors common
proposition-as-boolean conversions through helper claims and keeps a conservative
guard around generated `db*` binder names. That reduced the total bridge count
from 6,287 to 5,817, and reduced FOOL bridges from 707 to 237, without reducing
the 213-case pass count.

There is one newer uncommitted substitution experiment in
`src/vampire_cert_v1.ml`. It is not counted in this report because targeted
large cases exposed unsoundly broad `vampire_or` normalization. That experiment
should be reverted or replaced by a narrower FOOL-exhaustiveness-specific
substitution replay before any future commit.

The bottom line is:

- The project has a real native Megalodon-side certificate path now.
- The path has checked more than 100 generated scripts without textual proof
  holes.
- The path is still bridge-heavy and therefore not a completed reconstruction
  system.
- The next phase should focus on eliminating the largest bridge classes using
  richer Vampire-side primitive certificates, not by reviving Python heuristics.

## What Changed Since the Previous Reports

### From Python Prototype to Native OCaml Importer

The biggest architectural change is that the accepted path now lives inside
Megalodon. Earlier reports described a large Python reconstructor that parsed
Vampire output, guessed or recovered proof details, and emitted Megalodon
scripts. The audits correctly warned that this was becoming a second prover.

The current native path is different. Vampire emits a native certificate in an
S-expression format. Megalodon reads that certificate in OCaml, validates
step-level structure, tracks propositions and variable sorts, and emits
Megalodon proof terms/scripts. The central implementation is:

```text
/project/Megalodon/src/vampire_cert_v1.ml
/project/Megalodon/src/vampire_cert_v1.mli
```

The relevant command shape is:

```sh
bin/megalodon -vampirecertv1strict \
  -vampirecertv1 /project/tmp/.../cases/CASE/native.sexp \
  -vampirecertv1source /project/tmp/.../CASE.p \
  -vampirecertv1emit /project/tmp/.../out.mg \
  /project/tmp/.../dummy.mg

bin/megalodon /project/tmp/.../out.mg
```

The strict importer is not relying on `-allowincompleteqed`. It is not invoking
the old Python proof search. It emits explicit Megalodon source text and then
checks that source with Megalodon.

## Current Architecture

The pipeline has four main components.

### Megalodon to THF/TPTP

Megalodon exports problems to THF/TPTP. These problems contain:

- original theorem hypotheses and library lemmas;
- definitions and generated facts;
- TPTP names produced by Megalodon's name mangling;
- in some cases, axioms corresponding to `set` commands or definitional
  equalities;
- conjectures or negated goals suitable for Vampire.

The source-linked corpus used in the current run is:

```text
/project/tmp/source_linked_strict_100_corpus_fresh_041947
```

The corresponding native Vampire certificate run is:

```text
/project/tmp/source_linked_slice_1_400_fresh_042040
```

### Vampire Native Certificate Export

The Vampire branch emits native S-expression certificates. These certificates
contain step records such as:

- source inputs;
- formula inputs;
- formula copies;
- FOOL transformations;
- CNF formula-to-clause transformations;
- substitutions;
- resolution;
- factoring;
- equality symmetry;
- equality resolution;
- paramodulation;
- predicate definition folds;
- skolemization metadata;
- normal-form metadata;
- variable sorts and symbol declarations;
- original source names and roles.

The certificate format is intentionally closer to Prover9/Ivy than to the old
ad-hoc text proof. The certificate carries exact step IDs and enough explicit
data for Megalodon to avoid guessing in many cases.

The current certificate is not yet fine-grained enough for all transformations.
That is why bridge assumptions remain for CNF, normal form, skolemization,
large FOOL transformations, and many equality/rewrite inferences.

### Megalodon Native Import and Emission

The OCaml module `vampire_cert_v1.ml` parses the certificate, validates many
local step shapes, tracks each step's emitted proposition, and emits a
self-contained Megalodon script.

The emitted script currently starts with a local prelude:

```text
Definition False : prop := forall p:prop, p.
Definition True : prop := forall p:prop, p -> p.
Definition vampire_false : prop := False.
Definition vampire_true : prop := True.
Definition or : prop -> prop -> prop := ...
Definition vampire_or : prop -> prop -> prop := or.
Definition vampire_and : prop -> prop -> prop := ...
Definition vampire_eq_prop : prop -> prop -> prop := ...
Section Eq.
  Variable A:SType.
  Definition eq : A->A->prop := ...
End Eq.
```

This prelude is a practical standalone certificate harness. It is not the final
source-linked integration style. The user has correctly pointed out that
Megalodon's own equality, `or`, `False`, classical `xm`, and library constants
should be used directly in final reconstructed proofs. The current prelude is
therefore a compatibility layer for generated standalone proof scripts, not the
desired final proof inserted back into a Megalodon development.

## What Is Actually Replayed Today

The native emitter now proves a number of Vampire steps directly in Megalodon
instead of adding bridge assumptions. The following categories have at least
partial committed replay support.

### Input and Formula Steps

Source inputs, formula inputs, and simple formula copies are emitted as
assumptions or direct claims. Source labels are recovered from the TPTP source
map when available. Generated names are still often visible, but the
`src_*__uNNN` names are tied back to source labels rather than being completely
opaque.

This is useful for human inspection, but still short of final integration with
the original theorem. The current proof script is self-contained and theorem
like. It does not yet patch the original Megalodon file with a proof replacing
the theorem body.

### Substitution

Strict substitution replay exists for many clause substitutions. The emitter
instantiates quantified parent variables with the explicit substitution terms
from the certificate and then projects or reorders the resulting clause.

Recent improvements avoid re-quantifying known names and accept
`vampire_or`-encoded parents in some substitution contexts.

Remaining bridges:

```text
767 substitute
```

These are often due to formula-shape differences, variable-sort context issues,
or substitutions involving generated higher-order/lambda terms.

### Resolution

Structural resolution replay exists for many ordinary binary and clause-level
resolution steps. The proof term recursively eliminates disjunctions and
applies complementary pivots.

Recent improvements accept `vampire_or` parents in more cases.

Remaining bridges:

```text
708 resolve
```

The remaining resolution bridges often involve clause encodings that are not
syntactically identical after FOOL/CNF transformations, or parents whose emitted
propositions differ from the structural clause proposition.

### Factoring

Factoring has committed replay support for structural duplicate-literal removal
and, recently, for some cases modulo clause order.

Remaining bridges:

```text
46 factor
```

This class is now small enough that it is not the highest priority.

### Equality Resolution

Reflexive equality-resolution proof terms exist for some simple negative
equality cases. Clause-level removal of reflexive disequalities is supported in
some structural contexts.

Remaining bridges:

```text
69 equality_resolution
```

The remaining cases likely need more robust equality orientation, richer
sort-sensitive equality helpers, and better support for formula/FOOL encodings.

### Equality Symmetry

Equality symmetry can now be replayed for non-`db*` clauses. The latest committed
change, `e03d440`, widened equality-symmetry replay beyond exact textual parent
matches while deliberately guarding out generated de-Bruijn names.

The reason for the `db*` guard is concrete. An earlier unconditional attempt
passed targeted simple cases but failed full-suite checking on examples such as
`hammer.10157.86.th0`, where generated binders caused proof terms to prove an
equality over the wrong variable instance. The committed guard avoids replaying
such binder-sensitive cases until the lambda/de-Bruijn representation is made
more reliable.

Effect on the full passing suite:

```text
before e03d440:
bridge_total 6289
equality_symmetry 137

after e03d440:
bridge_total 6287
equality_symmetry 135
PASS 213
```

This is a small improvement, but it is sound and validated.

### Paramodulation

Unit and non-unit paramodulation fragments are replayed in a number of cases.
The proof term uses equality transport into the selected target literal and then
reconstructs the resulting clause.

Remaining bridges:

```text
841 paramodulate
```

This is currently the second-largest bridge class. The size reflects the fact
that paramodulation is where Vampire knows exact selected literals, positions,
orientations, unifiers, and instantiations. The more of that data Vampire emits
as primitive certificate information, the less Megalodon needs to infer.

This is also one of the places where Prover9/Ivy is most instructive: Prover9
expands demodulation and rewrite steps into primitive paramodulation with exact
positions and instantiated parents. The Vampire/Megalodon path should follow
that model more aggressively.

### CNF and Formula Transformations

Some exact CNF identity steps, application-bracketing steps, definitional exact
steps, and direct conjunction projections are replayed.

Remaining bridges:

```text
1477 cnf
508 normal_form
338 skolem_formula
353 rectify_formula
211 formula_term_copy
```

This is the largest open area. It includes Smolka-style transformations, FOOL
lifting, clausification, skolemization, normal-form conversion, and formula
rectification. These are not ordinary clause inferences. They require a
separate certified transformation layer.

### FOOL Transformations

Atomic FOOL formula lifts, proposition-to-boolean equality conversions, and
some implication-shaped FOOL steps are replayed. For example, steps of the
form:

```text
P
---- fool
vampire_eq_prop P vampire_true
```

are handled in some contexts.

Remaining bridges:

```text
237 fool
```

The guarded FOOL implication replay was the largest latest bridge reduction. It
changed the recursive shape guard in `simple_fool_formula_proof` to allow paired
implication structure, not only prefix universal atomic lifting. It also added
small helper claims for the common conversions between a proposition and
`vampire_eq_prop` against `vampire_true`, for example:

```text
P -> vampire_eq_prop P vampire_true
vampire_eq_prop P vampire_true -> P
```

Targeted examples improved substantially:

```text
hammer.11925.125.th0:
  fool bridges 18 -> 2
  all bridges 49 -> 41

hammer.11888.36.th0:
  fool bridges 8 -> 0
  all bridges 14 -> 10

hammer.1193.26.th0:
  fool bridges 4 -> 0
  all bridges 57 -> 55
```

The first broad version was not sound enough. It produced:

```text
/project/tmp/source_linked_slice_1_400_emit_fool_imp_shape_090035
CHECK_FAIL 24
PASS 189
```

The failures included type errors involving generated `vdb*`/`db*` lambda
binders and proof terms where `vampire_eq_prop_sym` or local proof variables
appeared in term positions.

A guarded version skipped formulas containing generated `db*` names. It reduced
bridges even more, but still timed out or failed on some large scripts:

```text

PASS 213
bridge_total 5817
fool bridges 237
```

The lesson is that FOOL replay can be expanded safely, but only when it is
implemented with proof-term sharing, helper lemmas, and binder-safe guards.

## Linking to Original Megalodon Lemmas and Definitions

This remains only partially solved.

### What Works

The native certificates carry source labels, TPTP roles, symbol declarations,
step propositions, and variable sorts. The emitter uses that information to
name assumptions as source-linked `src_*` assumptions where possible. This is
much better than purely opaque Vampire unit names.

The current emitted proofs therefore give a human a readable connection between
many proof assumptions and the original Megalodon/TPTP source facts.

The current approach also preserves original declared symbol names where the
Megalodon-to-TPTP mangling can be inverted or avoided. For many examples, the
emitted script contains recognizable original names such as:

```text
In
SNo
omega
ordsucc
binunion
Repl
setprod
mul_SNo
add_SNo
```

This is useful for human review and for future integration.

### What Is Still Missing

The generated proof is still emitted as a self-contained theorem with a long
list of assumptions. It is not yet glued back into the original Megalodon file
as the proof of the original theorem.

In particular:

- The final emitted theorem is a refutation-style theorem ending in `False`.
- Original source lemmas are assumptions, not necessarily references to the
  original named Megalodon declarations.
- Some TPTP axioms generated from Megalodon `set` commands are treated as
  premises. They should eventually be re-proved explicitly, often by
  reflexivity or definitional unfolding.
- Local prelude definitions for equality, `or`, `False`, and Vampire Boolean
  encodings are still emitted in standalone scripts. Final integrated scripts
  should use Megalodon's existing library constants and the classical context
  including `xm`.
- Name recovery is good enough for many symbols but not yet formally specified
  as a reversible source-map contract.

The source-linking problem should be separated into two layers:

1. Certificate-level source provenance: every input is either an original
   source fact, a generated definitional fact with a proof recipe, or an error.
2. Development-level proof insertion: the generated refutation is wrapped into
   a proof of the original theorem using the original theorem statement and
   local context.

The first layer is partially present. The second layer is still mostly future
work.

## Skolemization Status

Skolemization is not solved. The current passing artifact still has:

```text
338 skolem_formula bridges
```

The Vampire branch has begun exporting Skolem dependencies from parent
occurrences, and the native certificate carries step propositions and variable
sorts. That is useful, but the Megalodon emitter currently still bridges many
skolemization steps rather than proving them.

The likely final design should treat skolemization as a transformation
certificate, not as a clause inference. Each Skolem step should identify:

- the source formula;
- the quantifier being skolemized;
- the dependency variables;
- the introduced Skolem symbol and its type;
- the resulting formula;
- the local classical/existential principle used to justify the transformation.

Because the setting is classical and `xm` may be assumed, we do not need to
force a constructive account of Skolemization. But we do need a Megalodon proof
term or accepted transformation theorem that justifies each step.

For source integration, Skolem symbols should also be scoped carefully. They
are proof-local artifacts of the refutation, not original library definitions.

## Smolka-Style Transformations

The user specifically asked about Smolka-style transformations and provided the
Smolka et al. paper for context. The practical interpretation for this project
is:

- Preserve the ATP proof graph and the relation to the original source problem.
- Do not ask the target assistant to rediscover large preprocessing steps.
- Translate each preprocessing step into a sequence of small, checkable
  transformations.
- Keep names and dependencies explicit so the final proof can be related back
  to the original development.

The current project has moved toward this but is not finished.

Current evidence:

- Native certificates include explicit `step_proposition` and
  `step_variable_sorts` metadata.
- Vampire exports details for FOOL, CNF, normal-form, Skolem, and rewrite
  transformations.
- Megalodon can replay a few simple transformation fragments, such as exact CNF
  identities, direct conjunction projections, some formula copies, and atomic
  FOOL lifts.
- Most transformation steps remain bridge assumptions.

The main missing piece is a certified transformation calculus. The bridge
profile gives the work list:

```text
1477 cnf
508 normal_form
353 rectify_formula
338 skolem_formula
237 fool
211 formula_term_copy
```

These should not be addressed by broad ad-hoc proof-term generation alone. They
should be addressed by a small set of named transformation rules with explicit
parents, positions, substitutions, introduced symbols, and side conditions.

The Prover9/Ivy lesson applies here too. Complex transformations should be
expanded on the prover/exporter side while Vampire still knows the exact
operation. Megalodon should check and elaborate a small primitive step, not
infer which transformation happened.

## Equality Encoding Status

The emitted standalone scripts currently define their own equality wrapper:

```text
Section Eq.
Variable A:SType.
Definition eq : A->A->prop := ...
End Eq.
Infix = 502 := eq.
```

They also define:

```text
Definition vampire_eq_prop : prop -> prop -> prop := ...
Theorem vampire_eq_prop_sym : ...
Theorem vampire_eq_set_sym : ...
```

This was a pragmatic way to make standalone generated scripts check without
depending on the full original Megalodon library context. It is not ideal.

The user is right that final integrated proof reconstruction should use
Megalodon's equality directly where possible, and use existing library
definitions for `or`, `False`, and classical principles rather than redefining
them in every generated script.

The current state is therefore:

- Standalone checking: local equality/prelude is used.
- Final desired source-linked checking: Megalodon library equality and logical
  constants should be used.
- Open work: remove or parameterize the local prelude when emitting proofs back
  into original developments.

This matters for proof readability and for avoiding divergence between the
certificate harness and Megalodon's real logic.

## Relationship to the Audits

### Audit 2026-07-12

The first audit warned that the project was confusing admitted skeleton
checking with proof reconstruction, and that Python reconstruction was becoming
an unbounded heuristic prover.

The current state responds to that by:

- using Megalodon's native OCaml certificate path for counted runs;
- checking generated `.mg` files without `admit`, `aby`, or incomplete-QED;
- reporting bridge assumptions explicitly;
- using cached parallel validation instead of slow sequential loops;
- treating Python as diagnostic rather than qualifying.

The current state does not fully satisfy the audit because bridge assumptions
remain. But the success accounting is now much cleaner.

### Audit 2026-07-13

The second audit said the project should:

- use a strict, fail-closed path;
- avoid derived assumptions masquerading as inputs;
- start with a small clause-level certificate;
- move the accepted importer into OCaml;
- avoid dependence on the old Python reconstructor;
- use Prover9/Ivy as a model for primitive proof objects.

The current work follows these directions more closely than before:

- The active counted path is OCaml in Megalodon.
- The native certificate format is S-expression based.
- The 213-pass suite is checked by Megalodon, not by Python.
- The old Python monolith is not the source of the current bridge counts or
  emitted proof scripts.
- The current reports distinguish bridges from completed reconstruction.

Remaining issues relative to the audit:

- The native certificate is still not small enough. It contains many macro-like
  steps that become bridges.
- The standalone proof script still has bridge assumptions, so it is not a
  complete reconstruction.
- The final source-development integration is not done.
- CNF, skolemization, normal form, and FOOL transformations are still too coarse.

```sh
  /project/tmp/source_linked_slice_1_400_emit_NAME/cases \

```

7. Compare bridge profiles against the last passing artifact.
8. Commit only if the full cached suite passes and the change is a genuine

This is a much faster and more reliable loop than the earlier one-problem-at-a-

## Recent FOOL Implication Replay Work

The latest landed implementation generalized `simple_fool_formula_proof` in a
guarded way.

### Motivation

Many FOOL bridges have a simple shape:

```text
forall x, P x -> Q x
```

becoming:

```text
forall x, vampire_eq_prop (P x) vampire_true ->
          vampire_eq_prop (Q x) vampire_true
```

The existing recursive proof builder could already construct much of this proof
term, but the shape guard rejected implication nodes.

### First Version, Rejected

The first version allowed implication structure recursively. Targeted examples
passed and bridge counts improved significantly:

```text
hammer.11920.18.th0:
  all bridges 6 -> 5

hammer.11888.36.th0:
  all bridges 14 -> 10

hammer.11925.125.th0:
  all bridges 49 -> 41
```

But the full cached suite failed:

```text
/project/tmp/source_linked_slice_1_400_emit_fool_imp_shape_090035
CHECK_FAIL 24
PASS 189
```

Representative failures included:

```text
Failure at line 167 char 1272: Type Error found prop expected set
Failure at line 349 char 2350: Unknown term vampire_eq_prop_sym
Failure at line 121 char 1110: Unknown term Hfool_arg_0
```

These failures exposed binder and sort bugs around generated `db*`/`vLAM`
terms, and proof-term placement bugs in complex higher-order formulas.

### Guarded Version, Still Too Large

A second version skipped formulas containing generated `db*` names. This fixed
the direct binder/type failures and reduced bridge counts substantially:

```text
/project/tmp/source_linked_slice_1_400_emit_fool_imp_db_guard_090424
CHECK_FAIL 10
PASS 203

bridge_total 5817
fool bridges 237
```

But 10 large cases still failed under the strict harness. Their generated
scripts were around 1.1 to 1.6 MB. Several appeared to hit the 30-second check
timeout rather than produce explicit type errors.

### Landed Version

The committed version introduced helper claims for recurring FOOL conversion
patterns and avoided repeating large proof subterms inline. That made the same
bridge reduction pass the cached 213-case suite:

```text
/project/tmp/source_linked_slice_1_400_emit_fool_helpers_091647
PASS 213
bridge_total 5817
fool bridges 237
```

This is now counted progress. It does not solve all FOOL reconstruction, but it
shows that the correct direction is small reusable Megalodon proof claims plus
conservative guards, not large heuristic proof-term synthesis.

The right next step is:

- introduce small reusable FOOL equivalence helper lemmas;
- avoid duplicating huge proof terms inline;
- handle `vLAM`/`db*` binders through Megalodon's native binder machinery;
- add targeted negative tests for proof terms appearing in term positions;
- apply a strict full-suite gate before committing.

## Recent Unsafe Experiment: Broad `vampire_or` Substitution Normalization

After the FOOL helper work, an uncommitted experiment tried to replay more
`substitute` bridges by treating `vampire_or`, infix `\/`, and some parent
formula differences as broadly interchangeable in the substitution parent
matcher.

Small targeted cases improved:

```text
hammer.11745.21.th0:
  substitute bridges 2 -> 0
  all bridges 12 -> 11

hammer.11870.37.th0:
  substitute bridges 2 -> 0
  all bridges 11 -> 9
```

But larger cases failed type checking. The broad normalization could match a
nested disjunction against a single projected literal, producing a proof term
for the wrong proposition. A representative failure had the shape:

```text
proof term proves vampire_or A B C
but expected to prove A
```

That means this experiment is not a sound general replay rule. The useful
future version is much narrower: recognize the exact FOOL-exhaustiveness
substitution pattern and replay only that shape. The broad `vampire_or`
normalization should be reverted or replaced before the next counted commit.

## Main Remaining Problems

### 1. Bridge Assumptions

Bridge assumptions are the central remaining correctness gap.

They are explicit and therefore honest, but they still mean the final theorem is
proved from extra premises. The project is not complete until these bridges are
either eliminated or replaced by accepted, source-justified transformation
lemmas.

The top bridge classes are:

```text
1477 cnf
841 paramodulate
767 substitute
708 resolve
508 normal_form
353 rectify_formula
338 skolem_formula
237 fool
```

### 2. CNF and Normal-Form Transformations

The largest class is CNF. Direct projection and exact identity help, but most
CNF steps are still whole-formula transformations.

Needed:

- explicit clausification certificates;
- exact clause index and parent formula path;
- transformation lemmas for `vampire_and`, `vampire_or`, implication, negation
  as `-> False`, and quantifier movement;
- Skolem symbol introduction records;
- proof sharing so generated scripts do not explode.

### 3. Paramodulation and Rewriting

Paramodulation bridges remain numerous. The Prover9/Ivy model suggests the
right fix:

- expand complex superposition/demodulation in Vampire;
- emit exact instantiated parents;
- emit exact selected literals;
- emit exact term positions;
- emit direction and substitution;
- let Megalodon replay one primitive equality transport.

Megalodon should not infer these details from printed clauses.

### 4. Higher-Order Lambdas and Generated Binders

`vLAM`, `db*`, and `vdb*` are a recurring source of fragility. They caused the
failed equality-symmetry attempt and the failed broad FOOL replay attempt.

The current strategy is conservative: skip direct replay when generated DB names
make a proof term unsafe. That is acceptable for incremental progress, but not
the final solution.

The final solution should use Megalodon's native binder representation rather
than treating DB-like names as ordinary constants in emitted source.

### 5. Source Integration

The generated proof is not yet spliced back into the original development. It
is a standalone refutation theorem.

Needed:

- identify the original conjecture theorem and local context;
- map source assumptions to original declarations;
- prove generated `set`-command equalities by reflexivity/unfolding;
- remove the standalone prelude or replace it with imports;
- wrap the refutation into the original theorem statement.

### 6. Equality and Logical Prelude

The standalone prelude is useful for testing but not final. Final integration
should use Megalodon's existing equality and logical constants.

This will likely require the emitter to have two modes:

- standalone certificate harness mode;
- source-integrated proof mode.

### 7. Performance and Proof Size

Some generated scripts exceed 1 MB. Broad direct proof-term generation can
reduce bridges while making scripts slower or impossible to check under normal
timeouts.

Needed:

- proof sharing through named intermediate claims;
- helper lemmas for recurring FOOL/equality patterns;
- size-aware replay decisions;
- benchmark gates that report both bridge count and check time.

## Final Assessment

The project has moved materially since the previous reports. It is no longer
accurate to say that all progress is in Python reconstruction. The current

check without textual proof holes.

The project is also still not finished. The 5,817 bridge assumptions in the last
passing artifact are the clearest measure of remaining work. They represent
Vampire inferences and preprocessing transformations that are not yet
reconstructed in Megalodon.

The right direction remains the audit-recommended direction:

- richer and more atomic Vampire-side certificates;
- OCaml/Megalodon-side checking and proof-term generation;
- no Python guessing in counted successes;
- no admitted proofs;
- no unsupported derived assumptions;
- explicit source linking;
- strict, parallel, reproducible testing.

If the next phase continues along that path, the project can converge. If it
falls back into adding broad heuristic replay in Python or unchecked bridge
premises, it will produce impressive-looking scripts without satisfying the
actual goal.
