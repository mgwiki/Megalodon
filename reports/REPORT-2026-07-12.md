# Vampire to Megalodon Proof Reconstruction Report

Date: 2026-07-12

Repositories:

- Megalodon: `/project/Megalodon`, branch `vampire/megalodon`
- Vampire with Megalodon export: `/project/vampire-leancheck`, branch `vampire/megalodon`
- Temporary/test data: `/project/tmp`

## Executive Summary

The project goal is to make Vampire proofs over Megalodon-generated THF/TPTP problems reconstruct inside Megalodon, eventually without `aby`, `admit`, or other unchecked proof holes. The intended architecture is not an independent Python theorem prover. It is a port of the existing Vampire proof-printing/replay machinery, especially the Leancheck/Dedukti-style proof detail, into a Megalodon-specific proof export, with a Megalodon-side reconstruction layer that turns that exported proof object into Megalodon scripts and proof terms.

Substantial infrastructure is now in place. Vampire has a `--proof megalodon` mode implemented in `Shell/MegalodonChecker/MegalodonChecker.cpp` and wired through the proof-printer path. This mode emits a richer proof object than ordinary TPTP proof output: step metadata, normalized formulas, parent substitutions, variable sorts, lambda/de-Bruijn details, rewrite metadata, avatar split metadata, skolemization traces, and several replay-specific payloads. On the Megalodon side, `scripts/vampire_reconstruct_megalodon.py` parses those Vampire proof objects, links them back to original Megalodon source facts where possible, and emits Megalodon proof skeletons composed of declarative `claim`s. It also contains partial replay support for several common proof classes.

The current system is useful but not finished. It can generate source-linked Megalodon proof skeletons for broad suites. Recent broad source-context checks passed on at least 200 and 300 problem batches with admits allowed. A focused hard example, `hammer.981.15`, now links Vampire input facts back to original local Megalodon facts such as `H1`, `L1`, and `L2`, including local source definitions, and its generated source-context skeleton checks in Megalodon with incomplete proof admission enabled. Recent targeted work removed several focused admissions in proposition-valued boolean simplification, AVATAR component projection, and AVATAR SAT refutation. The main remaining focused gap is now binder-sensitive lambda/de-Bruijn demodulation under split dependencies. This is representative of the present status: the proof is connected to the original Megalodon development and many transformations are made explicit, but full no-admit replay is not yet achieved for the serious examples.

The most important progress is architectural. We moved away from trying to guess Vampire's proof state in Python from ordinary TPTP proof text. Instead, Vampire now exports the internal information that it already knows. This is the correct direction. The Python layer is still too large and currently does too much normalization and pattern matching, but most recent work has reduced guessing by adding explicit metadata to the Vampire proof output. The next phase should continue this direction: push any missing proof-critical detail into the Vampire Megalodon exporter, then make the Megalodon reconstructor a relatively mechanical translator from exported proof records into local Megalodon terms, claims, and source bridges.

The two highest-priority work streams are:

1. Finish linking reconstructed proofs to original Megalodon source theorem statements, local hypotheses, local definitions, and `set`-generated facts in a way that is general across libraries.
2. Finish Smolka-style transformation replay, especially skolemization, FOOL/boolean transformations, lambda/de-Bruijn demodulation, and avatar/DPLL refutations, using rich Vampire metadata rather than Python heuristics.

The project is not at the original target of 100 fully reconstructed no-admit proofs. It is at the point where expert review can be productive: the core design is visible, the remaining proof obligations are concrete, and the current implementation exposes enough examples for a reviewer to judge whether to keep investing in this architecture, what to move from Python into Vampire, and what Megalodon primitives or tactics would make reconstruction much simpler.

## Original Objective and Operating Constraints

The objective was to adapt Vampire's Lean proof reconstruction work to Megalodon. Vampire and Megalodon are both proof-term-oriented enough that this should be feasible in principle: Vampire can produce a detailed proof trace, and Megalodon can check proof terms or declarative proof scripts. The target is not merely to replay first-order derivations in an external checker. The target is to produce Megalodon scripts connected to the original Megalodon library and theorem development.

Several constraints shaped the implementation:

- The test problems are THF/TPTP problems exported from Megalodon, not hand-written toy FOF problems.
- Vampire should be run with `--input_syntax tptp`, generally in CASC mode, and with a hard time limit no greater than 10 seconds per problem.
- Batch work should be parallel. The preferred loop is: export many problems, run Vampire on them in parallel, then reconstruct/check output files in parallel.
- All temporary files should be under `/project/tmp`.
- Final Megalodon scripts must not rely on `aby`, because in Megalodon `aby` is implemented as an admission.
- The reconstruction may assume classical logic. In particular, excluded middle `xm` is available, and the basic logical constants and connectives from the Megalodon library, such as `or` and `False`, are assumed to exist in context.
- The implementation should be general for arbitrary Megalodon libraries. It should not be hardwired to a few names or theorems from the current benchmark library.
- When an input TPTP axiom was generated from a Megalodon `set` command and has no corresponding source claim, the reconstruction should prove it explicitly in Megalodon, usually by reflexivity or unfolding.
- The preferred path is to export enough detail from Vampire, in the spirit of Leancheck/Dedukti modes, rather than re-deriving Vampire's internal choices by heuristic Python code.

These constraints led to the present two-repository implementation: a Vampire branch that emits richer Megalodon proof objects, and a Megalodon branch that translates them into proof skeletons and partial proof terms.

## High-Level Architecture

The current architecture has four stages.

First, Megalodon exports THF/TPTP problems. The user has generated substantial benchmark material, for example with:

```text
megalodon -allowincompleteqed -createabyprobs hammer hammer/100thms_12_h.mg
```

This produces THF problems under `hammer/` or `examples/hammer/`. These problems contain encoded Megalodon names, local theorem/hypothesis facts, library facts, definitions, `set`-generated equalities, and a conjecture.

Second, Vampire solves the problem and emits a proof. The important invocation shape is:

```text
vampire_rel_detached_10761 --input_syntax tptp --mode casc -t 10 --proof megalodon --output_axiom_names on PROBLEM > OUT
```

The earlier TPTP proof output was useful for a first skeleton, but not detailed enough for robust replay. The Megalodon proof output is intended to carry enough internal Vampire state to avoid reconstructing hidden details later.

Third, `scripts/vampire_reconstruct_megalodon.py` parses the Vampire proof output and the original problem/source context. It builds a Megalodon file containing:

- declarations corresponding to Vampire symbols,
- source bridges to original Megalodon facts,
- declarations for local source definitions,
- a sequence of `claim`s corresponding to Vampire proof units,
- partial proof terms or proof scripts for inference steps already handled,
- explicit admissions for steps not yet reconstructed.

Fourth, Megalodon checks the generated script. In the present development loop, many checks are source-context checks with incomplete proof admission enabled. They verify that the generated script is syntactically and contextually valid, that source names resolve, that declarations line up, and that the remaining proof holes are localized. They do not yet establish the final no-admit target.

This is a deliberate intermediate milestone. It gives a human reviewer a generated Megalodon proof object connected to the original theorem, so the remaining gaps are visible and locally named.

## Why the Current System Uses Python

There is a Python translator, but it is not intended to be the long-term proof engine. It currently exists because it is the fastest way to iterate on parsing, source linking, Megalodon syntax generation, batch testing, and gap analysis. The preferred path remains to use Vampire's existing proof replay and proof export knowledge wherever possible.

The division of responsibility should become:

- Vampire: know and export the exact proof-critical information for each inference.
- Python/Megalodon reconstructor: parse the exported records, recover source-level names, choose Megalodon surface syntax, and assemble proof scripts.
- Megalodon: check the resulting proof terms and claims.

The current Python layer still contains too many functions with names like `normalize_*`, too much local matching, and several inference-specific proof builders. That is a pragmatic result of rapid iteration, not a design ideal. Where Python code is matching hidden Vampire behavior, that code should generally be replaced by richer `megalodon_step_extra` records from Vampire.

This is why recent Vampire commits added rewrite metadata, lambda/de-Bruijn renderings, normal-form paths, avatar split details, parent substitutions, and skolemization payloads. The more Vampire tells us, the smaller and more reliable the Python reconstruction layer becomes.

## Vampire-Side Work

The main Vampire implementation is in:

```text
/project/vampire-leancheck/Shell/MegalodonChecker/MegalodonChecker.cpp
/project/vampire-leancheck/Shell/MegalodonChecker/MegalodonChecker.hpp
```

It is wired into the proof-printer path through:

```text
/project/vampire-leancheck/Kernel/InferenceStore.cpp

```

`Options.cpp` constrains Megalodon proof output to use syntactic skolemization, in the same spirit as Leancheck:

```text
If(proof = MEGALODON) then skolemization = syntactic
```

This matters because standard Vampire skolemization can hide too much semantic structure behind generated symbols. Syntactic skolemization is larger but easier to reconstruct in a proof assistant.

`MegalodonChecker` emits several classes of records. The key ones are:

- `megalodon_step(...)`

- `megalodon_step_variable_sorts(...)`
- `megalodon_step_substitutions(...)`

The exporter also emits symbol declarations and recovered names. It contains code for name recovery from TPTP/Megalodon encodings, formula and term rendering, equality/proposition equality support, source candidates, and claim skeletons.

Important inference-detail exports include:

- replay substitutions for parent clauses,
- substituted parent clause renderings,
- typed rewrite terms,
- term and formula replacement metadata,
- lambda sort hints,
- lambda subterm metadata,
- lambda body context,
- de-Bruijn index renderings,

- rendered normal-form paths,

The exporter still needs more work. Some Vampire inferences are still too opaque from Megalodon's point of view. In particular, hard cases remain around lambda/de-Bruijn demodulation, certain dependent proposition/boolean normalizations, and quantified avatar SAT refutations. However, the infrastructure for adding those details exists, and the recent work repeatedly used that path.

## Source Linking

Source linking is now one of the most developed parts of the system. The goal is that a generated proof skeleton does not merely prove a standalone TPTP formula with fresh declarations. It should state where each Vampire input axiom came from in the original Megalodon development.

The current implementation handles several kinds of source facts:

- global library facts exported as TPTP axioms,
- original theorem/conjecture statements,
- local hypotheses and lemmas,
- local theorem assumptions,
- local definitions introduced in the proof context,
- raw Vampire axioms that correspond to local Megalodon facts,
- some source dependency subset bridges,
- some final goal bridges through source-linked facts.

Recent source-linking commits focused on mapping raw Vampire inputs back to local Megalodon facts. In the focused `hammer.981.15` example, the generated skeleton now reports source local proof facts such as:

```text
H1 L1 L2
```

and specific Vampire steps are linked to source facts:

- `S28` links to source `L1`
- `S30` links to source `H1`
- `S31` links to source `L2`

The same focused example also links a local source set definition named `Y`.

This is a meaningful improvement over a standalone proof skeleton. A human can now inspect the generated Megalodon proof and see how it relates to the original theorem context. This also makes the remaining admitted steps more actionable, because the local theorem and definitions are visible in the generated file.

The source-context check for the focused example passed with incomplete proof admission enabled:

```text
raw TPTP source-context check ok:
/project/tmp/source_link_981e/skel/hammer.981.15.decoded.no_replay.10831.megalodon.raw_tptp_skeleton.mg
```

There are still limitations. Some axioms generated by Megalodon's `set` command may not correspond to named claims. They need to be produced in the reconstructed proof by unfolding or reflexivity. This is now recognized as a distinct class rather than being confused with missing source links. The implementation has partial support for local definition binders and definition folds, but this part should be made more systematic.

The general requirement is that the source linking remain library-independent. It should recover names from the export encoding and from problem metadata, not from a table of known theorem names. There were earlier concerns about apparent hardwired names such as `famunion`. The intended resolution is that names are recovered because they appear in exported source names, not because the reconstructor is tuned to that particular library. Any remaining special cases should be audited and replaced by generic name-decoding or source-map logic.

## Name Recovery

Name recovery is necessary because the TPTP export mangles Megalodon names. The implementation attacks this from both sides.

On the Vampire side, `MegalodonChecker` has name decoding and sanitization support, including functions for recovering Megalodon symbol names from TPTP names. On the Megalodon side, the reconstructor parses problem files and source context to map exported axiom names and symbol names back to original names.

This is currently good enough for many benchmark examples, including local facts in the focused hard example. It is not yet a formally specified inverse of the Megalodon TPTP name mangler. That is a risk. The robust solution is to either:

1. make Megalodon's exporter write an explicit source map alongside each problem, or
2. implement the exact inverse of the Megalodon name encoder and test it against generated examples.

The first option is preferable. Reconstruction should not depend on reverse-engineering names from ad hoc strings if the original exporter can provide a machine-readable map from TPTP identifiers to Megalodon declarations, local hypotheses, local definitions, and conjectures.

## Equality

The equality situation deserves explicit explanation because it has been a recurring design question.

For ordinary set/function/object equality, the reconstruction should use Megalodon's native equality whenever possible. The Vampire exporter was adjusted to avoid shadowing Megalodon equality in proof outlines. This is the right target.

There is still a separate proposition equality wrapper in parts of the export and reconstruction. This exists because Vampire's higher-order/FOOL pipeline often represents boolean or proposition-level equality in a way that does not map one-to-one to the ordinary object equality syntax used in Megalodon source. In particular, Vampire can manipulate equality between formulas or boolean terms during FOOL transformations and simplifications. The exporter currently exposes this through a `vampire_eq_prop`-style concept in some generated contexts.

This should not be interpreted as a desire to maintain a parallel equality theory long term. It is a bridge for proof replay where Vampire has turned proposition equality into an internal equality-like object. The long-term direction should be:

- use native Megalodon equality for object-level equality,
- map proposition equality to the Megalodon library's proposition extensionality where needed,
- avoid declaring a separate equality if the target context already provides the right equality,
- keep any proposition-equality wrapper small, explicit, and justified by a corresponding Vampire inference.

The expert reviewer should pay close attention to this boundary. If Megalodon has a cleaner primitive or library lemma for proposition equality, the reconstruction should use that instead of carrying a Vampire-specific equality wrapper through generated scripts.

## Smolka-Style Transformations

The user pointed to the Smolka-style transformation literature, and this has guided the reconstruction of preprocessing and normal-form phases. The broad issue is that Vampire proofs are not just resolution proofs over the original source formulas. They include transformations from higher-order or FOOL input into first-order clausal form, including:

- expansion or encoding of boolean terms,
- pushing negations,
- implication elimination,
- equivalence elimination,
- ENNF/NNF-style transformations,
- rectification,
- miniscoping and quantifier movement,
- skolemization,
- flattening,
- CNF/clausification,
- definition introduction,
- lambda lifting or lambda encoding,
- simplification of proposition equalities and boolean formulas.

The current implementation has partial support for these transformations. Recent commits include:

- replaying Smolka-style proposition simplifications,
- replaying permuted FOOL premise normalizations,
- exporting ENNF semantic path details,
- exporting normal-form pair paths,
- exporting rendered normal-form paths,
- bridging final conjectures through source dependencies.

The practical approach has been to treat these transformations as proof-producing steps in Megalodon. Where Vampire emits enough metadata, the reconstructor can build a local `claim` whose proof uses known logical principles, source facts, and equality/rewriting. Where Vampire does not emit enough metadata, the reconstructor currently emits a claim with an admission and records the missing inference class.

This is not yet a complete Smolka-style transformation checker. It is a growing library of transformation replays driven by Vampire's exported proof records. The current state is strongest for simple proposition/boolean simplifications and some normal-form bridges. It is weakest for transformations that combine quantifier movement, lambda binders, de-Bruijn indices, and dependent boolean reasoning.

Classical logic is assumed throughout this work. This matters because several boolean/proposition transformations are easy classically and awkward constructively. The reconstruction should freely use `xm` and the library's classical lemmas rather than trying to reconstruct Vampire proofs constructively.

## Skolemization

Skolemization is partially implemented and remains one of the main open areas.

Vampire's Megalodon proof mode forces syntactic skolemization. That is important because it makes the introduced skolem terms correspond more directly to quantified source formulas. The Megalodon reconstructor has a `raw_tptp_skolemisation_proof` path and related helpers. The generated Megalodon context also knows about choice-like principles such as `Eps_i` and its axiom in the source environment.

The current reconstruction strategy is roughly:

1. identify the quantified formula being skolemized,
2. recover the introduced skolem symbol and its argument sorts,
3. express the skolemized claim as an instance of a choice/existence principle,
4. bridge that claim to subsequent Vampire steps.

This works for some simple cases but is not yet complete. The hard parts are:

- recovering the exact quantifier prefix and dependency order,
- connecting generated skolem names back to a local source witness when one exists,
- proving the skolem axiom when it came from the preprocessing transformation rather than a source axiom,
- handling skolem functions under lambda or higher-order encodings,
- avoiding accidental reliance on generated names that change across Vampire runs.

The focused example includes warnings about `Eps_i_ax` and other library facts being indexed differently, but the context still checks with admits. This suggests the source environment can expose the right classical choice machinery, but the proof reconstruction still needs stronger explicit skolem transformation replay.

The recommended next step is to make Vampire export a fully explicit skolemization certificate for each skolemization step:

- original formula,
- quantifier prefix with variable sorts,
- chosen existential variable,
- dependencies,
- generated skolem symbol,
- resulting formula,
- proof principle expected by the target checker.

The Megalodon side should then translate this record mechanically into a local proof using `Eps_i` or the relevant library choice principle.

## Avatar Splitting and SAT Refutation

Avatar is a major source of proof complexity. Vampire uses SAT-level reasoning over split components, and the final contradiction often depends on a compact SAT refutation rather than a single obvious first-order inference.

The Vampire exporter now emits avatar split reconstruction details and SAT subsumption instantiations. The Megalodon side has functions including `raw_tptp_avatar_sat_refutation_proof` and recent work linking parameterized avatar splits.

The system can now represent avatar split components and connect many of them to Megalodon claims. It also handles some parameterized splits that previously failed source-context checking. In the current focused `hammer.981.15` skeleton, the final avatar refutation `S1395` is replayed by instantiating the quantified split clauses at `A` and running the small DPLL-style propositional proof generated by `raw_tptp_avatar_sat_refutation_proof`. Broader AVATAR refutations still need more regression coverage, especially when split clauses require nontrivial instantiation choices or when Vampire's SAT explanation should be followed exactly.

The problem is not merely syntax. A complete Megalodon proof of an avatar refutation needs a small propositional proof that the active split literals are inconsistent, plus links from each split literal back to the corresponding first-order clause. This is conceptually straightforward but engineering-heavy because split literals may be parameterized or quantified, and the DPLL explanation may need instantiation detail.

The likely path forward is:

- have Vampire export the SAT proof/explanation in a target-independent small format,
- translate that explanation into a Megalodon proof over propositions,
- instantiate parameterized split clauses explicitly,
- use classical propositional reasoning and `False` elimination from the Megalodon library.

This is an area where a Prover9/Ivy-style detailed proof object could help. A small sequence of primitive propositional steps may be easier to import than a compact Vampire avatar explanation.

The latest Vampire-side work adds more detail for this path. Commit `e99d95e8a` records a
map from AVATAR SAT variables to their component clauses and emits
`megalodon_step_extra(..., "split_dependency", ...)` records for clauses that carry split
dependencies. For example, the focused proof for `hammer.981.15` now carries dependency
records for steps such as `S480`, `S481`, `S496`, `S1279`, `S1281`, and `S1282`. These
records include the split level, split variable, polarity, and a rendered component
clause. That is a meaningful improvement because the Megalodon-side translator no longer
has to rediscover which first-order component a SAT split variable represents.

This also exposed a soundness issue in the earlier split representation. Some Vampire
AVATAR split variables are nullary propositions, but their component clauses mention
object variables. Treating such a split as if it were a function of those variables is
convenient but wrong unless Vampire has actually generated a parameterized split. The
safe committed response was to keep those variable-dependent nullary splits abstract,
which made the generated skeleton sounder but increased the number of admits in the
focused example. The latest Megalodon-side refinement goes further: if Vampire has a
definition equivalent to `forall x, split <-> C x`, it represents the nullary split as
equivalent to `forall x, C x`. This keeps the split nullary while still making the
component useful to Megalodon. This should become the preferred path if it continues to
check on a small AVATAR regression bucket beyond the focused example.

## Lambda and De-Bruijn Issues

Lambda and binder handling are currently a major blocker for full replay on serious THF examples.

Vampire has been extended to export more lambda information:

- lambda sorts,
- lambda subterms,
- lambda body context,
- de-Bruijn index renderings,
- body de-Bruijn index renderings,
- step-level lambda sort hints.

This was necessary because surface rendering alone is not enough to reconstruct binder-sensitive rewriting. Two terms can look similar after pretty-printing but differ in binder context or de-Bruijn indices. Conversely, Vampire may apply a rewrite in an internal representation that is hard to infer from the printed formula.

On the Megalodon side, the reconstruction can consume some of this metadata, but it does not yet fully replay all lambda/de-Bruijn demodulations. In the focused `hammer.981.15` skeleton, admitted steps include:

- `S480`
- `S481`
- `S1279`
- `S1281`

These are associated with lambda/de-Bruijn demodulation and related rewrite contexts.

The next work here should be concrete and narrow:

1. For each remaining admitted lambda-demodulation step, inspect the exported `megalodon_step_extra` record.
2. Confirm whether the exporter records the selected subterm, the rewrite lhs/rhs, variable sorts, binder context, and rendered before/after formulas.
3. If anything is missing, add it to `MegalodonChecker`.
4. If the exported data is complete, implement a Megalodon-side proof term or rewrite script that uses exactly that data.

This should be done on a small set of hard examples, not by rerunning expensive broad suites after every edit.

## Claim Skeletons and Admits

One important shift during the project was to generate claim skeletons even before every inference is fully reconstructed. This was the right move.

The all-or-nothing approach was not useful to humans. If reconstruction failed at one Vampire step, the user had no Megalodon artifact to inspect or improve. The current approach emits a sequence of `claim`s corresponding to Vampire steps and uses admissions only for not-yet-replayed steps. This gives:

- a readable Megalodon proof skeleton,
- explicit step names,
- source links,
- local formulas,
- a visible count and location of remaining proof gaps,
- an artifact that a human can continue editing.

This is especially useful for hard examples with long proofs. It lets us distinguish between:

- source-context failures,
- parsing/syntax failures,
- missing source links,
- unsupported inference classes,
- supported inference classes with a local bug,
- final proof gaps.

The focused example has had different admit counts across recent runs because we
deliberately tightened the soundness of AVATAR split handling. An earlier run exposed
seven principal remaining gaps:

- `S480`
- `S481`
- `S496`
- `S1279`
- `S1281`
- `S1282`
- `S1395`

After the safer treatment of variable-dependent nullary AVATAR splits, the count went up
temporarily because some split definitions that previously checked were intentionally kept
abstract rather than emitted as unsound definitions. The later binder-hoisting experiment
reduced the focused `hammer.981.15` gap count again, but it is not yet the final state.
For expert review, the important point is not the exact count from a single run but the
shape of the remaining classes: binder-sensitive demodulation, dependent
proposition/boolean simplification, and final AVATAR/SAT refutation.

This is still a much better state than a failed monolithic reconstruction. However, the
final deliverable cannot contain such admissions. The admissions are only an intermediate
development tool.

## Testing Strategy

The testing strategy changed significantly during the project.

Early iterations were too slow because they repeated Vampire runs and Megalodon checks sequentially. The current intended workflow is:

1. Generate/export all benchmark problems once.
2. Run Vampire on the exported problems in parallel, using 10 to 20 workers depending on machine load.
3. Cache the Vampire outputs.
4. Reconstruct Megalodon skeletons from cached Vampire outputs.
5. Check generated Megalodon scripts in parallel.
6. When debugging a specific inference class, work on a small set of representative failures rather than rerunning the full suite.

This avoids wasting time on unsolved problems and on portfolio strategies that already timed out. Vampire runs should stay at `-t 10`.

The Python script contains support for parallel batches through `ProcessPoolExecutor` paths in functions such as `run_vampire_suite` and `check_raw_tptp_skeletons`. Temporary files are written under `/project/tmp` for the runs I relied on.

Evidence from current logs includes:

- `/project/tmp/megalodon_suite200_dne/reconstruct.log` contains 200 source-context successes with admitted skeletons.
- `/project/tmp/megalodon_vampire_current300_replay_exported_lambda_1783472769/replay.log` contains 300 source-context successes with admitted skeletons.
- `/project/tmp/source_link_981e/check/...source_context.log` reports "Everything looks good" for the focused `hammer.981.15` source-context skeleton.

These are not no-admit theorem reconstruction passes. They are source-context and skeleton checks with incomplete proof admission enabled. They validate syntax, source resolution, context structure, and partial replay, but they do not establish the final proof-reconstruction target.

The test suite still needs to be formalized. A good suite should include:

- a small smoke set of 10 to 20 fast problems for syntax/source-link regressions,
- a medium set of 100 solved THF problems with cached Vampire proofs,
- a hard set grouped by inference class, especially skolemization, lambda demodulation, FOOL simplification, avatar refutation, and equality rewriting,
- a final no-admit set of at least 100 proofs,
- separate tests for source mapping across multiple Megalodon libraries, to detect overfitting.

The current project has many generated logs and runs, but not yet a clean, versioned test manifest that an expert can run with one command and interpret unambiguously.

## Implementation Details by Proof Phase

This section gives a more concrete view of how the current implementation behaves across
the phases of a Vampire proof. It is intended to help a reviewer decide whether the
remaining work is mostly local engineering, a missing proof-theoretic ingredient, or a
sign that the architecture should change.

### Input and Source Axioms

The first step is not a proof inference at all: it is recovering what the Vampire input
means in the original Megalodon development. The reconstructor parses the TPTP/THF
problem and the raw proof output, then creates a Megalodon context with declarations for
the symbols that Vampire saw. It also tries to identify which Vampire input clauses came
from:

- named Megalodon theorems,
- local hypotheses in the theorem being hammered,
- local lemmas created during the source proof,
- local definitions or `set` commands,
- library facts that were selected by the hammer,
- the negated conjecture.

This part now works well enough for the focused examples to be useful. The skeleton does
not just say "axiom S31"; it can often say that `S31` is the local Megalodon fact `L2`.
That is a major usability improvement. The remaining weakness is that the mapping is
recovered from names and formulas rather than from an explicit source map emitted by
Megalodon. The current approach is acceptable for prototyping but should not be the final
interface between the exporter and reconstructor.

The `set` case is special. A source `set` command can create definitional equalities in
the TPTP problem without a separately named claim in the Megalodon proof script. In such
cases the correct reconstruction is not to search harder for a missing lemma. The correct
reconstruction is to emit a small Megalodon proof by definitional unfolding or reflexivity.
This is recognized in the design, but it is not yet systematic.

### Negated Conjecture and Final Goal Bridges

Vampire proves unsatisfiability of the axioms plus the negated conjecture. The generated
Megalodon artifact must connect that refutation back to the original positive theorem.
The reconstructor has code for identifying negated conjecture roles and for building
bridges from the final contradiction to the source goal. Recent work improved quantified
negated conjectures, which matter because many Megalodon theorem statements are not
ground propositions but quantified statements over sets, predicates, functions, or local
parameters.

The current bridge is still not ideal. It can be too dependent on syntactic recognition
of the exported conjecture. A better interface would have Megalodon export an explicit
conjecture map: the original theorem name, its local context, the positive proposition,
and the exact TPTP formula used as the negated conjecture. That would make the final
bridge almost mechanical.

### Preprocessing and Smolka-Style Transformations

Vampire performs many transformations before and during clausification. These are the
steps most closely related to the Smolka-style material. In proof-assistant terms, they
are not "administrative"; each one needs a proof if the final target is no-admit
Megalodon checking.

The reconstructor currently handles a useful but incomplete subset:

- simple implication, conjunction, disjunction, and negation transformations,
- selected proposition-equality simplifications,
- some boolean/FOOL normalizations,
- some ENNF/NNF path-driven transformations,
- some definition fold/unfold bridges,
- some final source dependency bridges.

The Vampire exporter has been extended to print normal-form paths and rendered before/after
terms for several of these transformations. That is the right shape. A transformation
checker should not have to guess where a negation was pushed or which side of an
equivalence Vampire selected. It should read a small certificate: source expression,
target expression, path, local binder context, and proof rule.

The main missing piece is a uniform transformation language. At present, each new shape
tends to add another Python function. For maintainability, it would be better to define a
small set of primitive transformation records in the Vampire output and a corresponding
small set of Megalodon proof combinators. The records should be rich enough to cover
FOOL, ENNF, CNF, skolemization, lambda handling, and definition introduction without
requiring formula-string heuristics.

### Resolution, Superposition, and Demodulation

For ordinary first-order resolution-like inferences, the current strategy is to use
Vampire's replay information. The exporter emits parent substitutions, selected literals,
rewrite terms, and substituted parent formulas for several rules. The Megalodon side then
tries to construct proof terms using the parent claims and the exported substitution data.

Superposition and demodulation are not isolated problems. In the current THF examples,
they often interact with:

- typed higher-order applications,
- lambda abstractions,
- de-Bruijn indices,
- proposition-valued terms,
- definitional equalities introduced by preprocessing,
- AVATAR split dependencies.

This is why the project should not only "fix superposition." A superposition step whose
redex is under a lambda binder may need binder metadata and equality transport. A
demodulation step over a proposition may need proposition extensionality or a FOOL bridge.
A unit equality rewrite that looks trivial in first-order notation may require source
definition unfolding in Megalodon.

Recent Vampire commits moved in the right direction by exporting typed rewrite terms,
parent lambdas for non-replayed rewrites, de-Bruijn renderings, and lambda body context.
The remaining work is to use those records directly in the generated Megalodon proof terms.
If a proof term still relies on reconstructing binder structure from a pretty-printed
formula, that is a weak point.

### Skolemization and Choice

Skolemization is a central proof phase because it changes the shape of formulas in a way
that is equisatisfiable rather than generally equivalent. In a classical proof assistant,
the usual way to justify this is via a choice principle. Megalodon appears to have the
relevant ingredients available in the source context, including `Eps_i`-style choice
objects and axioms.

The current implementation has the beginning of this path but not a full certificate
checker. The reconstructor can recognize some skolemization steps and has proof-building
functions for them. However, a robust solution requires Vampire to export the exact
quantifier prefix, variable sorts, dependency set, generated symbol, and resulting formula.
This should be treated as a first-class proof certificate, not as a formula-shape
recognizer.

The expert review should ask whether syntactic skolemization plus `Eps_i` is the best
target representation. My current view is that it is the right direction because it keeps
the introduced witness terms explicit enough for proof reconstruction. But the Megalodon
side needs a small library of choice/skolem proof patterns so that every new skolemization
step does not require a custom proof term.

### AVATAR and SAT Reasoning

AVATAR introduces a second proof layer. First-order clauses are split into components, and
SAT variables track which components are active. Vampire can then derive contradictions
through a SAT-level explanation. Megalodon needs both parts:

- proof that each split literal corresponds to the first-order component,
- proof that the SAT-level combination of split literals is contradictory.

The first part is now much better served by exported `avatar_definition` and
`split_dependency` metadata. The second part is still underdeveloped. The current
`raw_tptp_avatar_sat_refutation_proof` path handles some cases but is not a general SAT
proof importer.

A good next design would export a tiny propositional proof object from Vampire's AVATAR
layer. It does not need to expose all of Vampire's SAT internals. It only needs enough
steps to let Megalodon derive `False` from named split propositions using classical
propositional reasoning. This could look like an Ivy/Prover9-style proof with primitive
steps for unit propagation, binary resolution, contradiction, and assumption discharge.

### Proof Skeleton Generation

The generated skeleton is intentionally declarative. It uses named `claim`s corresponding
to Vampire steps, not one giant proof term. This gives the right debugging shape:

- the proof is inspectable by humans,
- every remaining hole has a local formula,
- source facts are visible near the proof they support,
- Megalodon can check the surrounding context even when a few steps are still admitted.

This is also close to how a human Megalodon developer would continue the proof. It is not
just an internal artifact for automation. That said, the final no-admit output should not
look like a forest of arbitrary generated names if it can avoid it. The skeleton should
retain step names for traceability, but the source theorem, local hypotheses, local
definitions, and final bridge should be named in source-level terms wherever possible.

- Once this scoped AVATAR representation is fixed, the dependent downstream contradiction
  steps should be revisited. They may need an explicit imported SAT/propositional proof
  object rather than formula recognition.

This example should remain a primary development target until these classes are eliminated
without admissions. It is small enough to iterate on directly and complex enough to
represent the serious issues.

## Problems Encountered

### Ordinary TPTP Proofs Are Too Thin

The earliest reconstruction attempts relied too heavily on ordinary TPTP proof output. That output is useful for step order and formulas, but it omits too much:

- exact substitutions,
- internal selected literals,
- sort information,
- rewrite orientation,
- parent formula after substitution,
- binder/de-Bruijn context,
- normal-form transformation paths,
- SAT/avatar explanations.

Trying to infer all of this later in Python led to slow and brittle iteration. The project improved when we started enriching the Vampire output directly.

### Python Heuristics Are Tempting but Risky

The Python reconstructor can often make a local example pass by recognizing a shape and emitting a proof. That is useful for exploration but dangerous for generality. The implementation must not become a collection of benchmark-specific recognizers.

The best use of Python is to expose missing metadata. When a heuristic is needed, that is often evidence that Vampire should print one more field.

### Megalodon Source Context Is Subtle

Connecting a TPTP axiom back to a Megalodon source fact is not just string matching. Local theorem facts, definitions, branch facts, `set` commands, and exported library facts may all appear differently in the generated problem. Some source facts are available as claims; others are equalities that need proof by reflexivity or unfolding. Some local assumptions are under binders.

This is why source-context checks are important even before full proof replay. They catch missing binders, misdeclared local definitions, incorrect source names, and mismatched theorem contexts.

### Skolemization Is Semantically Simple but Operationally Fragile

Classically, skolemization is justified by choice. Operationally, a proof checker needs the exact dependencies and resulting formula. If Vampire does not export the prefix and dependency information clearly, reconstruction becomes guesswork. Syntactic skolemization helps, but it is not by itself a proof certificate.

### Lambda/Binder Handling Needs Exact Internal Data

For THF problems, binder-sensitive rewriting cannot be reconstructed reliably from pretty-printed formulas alone. De-Bruijn indices and binder contexts are essential. Recent Vampire exporter work added much of this data, but the Megalodon proof builder is not yet complete.

### Avatar Refutations Need a Small Proof Language

Vampire's avatar/SAT layer is efficient, but Megalodon needs an explicit proof of contradiction. A compact "avatar refutation" record is not enough unless it contains enough propositional proof detail. This is a good candidate for a small target-independent proof language, similar in spirit to detailed Prover9/Ivy proof objects.

### Test Runs Can Waste Time

The project lost time when long tests were run repeatedly or sequentially. The correct loop is now clear: cache Vampire outputs, filter to solvable problems, and iterate on reconstruction/checking in parallel.

## Generality and Overfitting Risk

The implementation must reconstruct Vampire proofs for arbitrary Megalodon libraries, not only for the current benchmark family. This is a real risk because the available examples come largely from the current Megalodon set-theoretic library and generated hammer problems.

Potential overfitting symptoms include:

- checking for specific theorem or definition names,
- assuming a fixed source-file layout,
- relying on current benchmark naming conventions rather than exported maps,
- using a fixed set of library lemmas without verifying they are in context,
- treating one library's `set` expansion pattern as universal,
- recognizing formulas by pretty-printed strings instead of structural representation.

The recent source-linking work is intended to be generic, but it should be audited. A reviewer should search for hardwired source theorem names and formula strings. Where any are found, they should be replaced by:

- source-map metadata from the Megalodon exporter,
- structural formula comparison,
- exact inverse name decoding,
- generic proof rules.

The strongest protection against overfitting will be a test suite spanning more than one Megalodon development.

## Relationship to Leancheck and Dedukti

The explicit project direction was to port Vampire's Lean proof extensions to Megalodon, not to invent a separate proof reconstruction pipeline. The current Vampire work follows that direction, but incompletely.

What has been ported conceptually:

- a new proof mode with target-specific rendering,
- syntactic skolemization requirement,
- step-by-step proof output,
- use of the Vampire inference replayer to obtain more information,
- richer metadata for rewrite and transformation steps,
- target-specific symbol and formula rendering,
- target-specific claim/proof skeleton generation.

What still needs more direct reuse or porting:

- all inference-specific Leancheck/Dedukti detail for superposition, demodulation, FOOL transformations, skolemization, and avatar,
- exact proof term generation patterns where Leancheck already solved the corresponding problem,
- small primitive proof object formats for complex inferences,
- trust-boundary decisions about which transformations are checked in the target and which are emitted as derived proof steps.

The best next step is to systematically compare `MegalodonChecker` with the Leancheck and Dedukti proof printers. For each Vampire inference rule:

1. identify what Leancheck/Dedukti exports,
2. identify what Megalodon currently exports,
3. add missing fields to Megalodon export,
4. add a Megalodon reconstruction case only after the data is present.

The project should not focus only on superposition. Superposition is important, but full reconstruction needs detail across the preprocessing and proof stack.

## Current Trust Boundary

At present, there are three levels of trust in the generated artifacts:

1. Vampire solved the TPTP problem and emitted a proof object.
2. The Python reconstructor parsed the proof object and emitted a Megalodon skeleton.
3. Megalodon checked the generated script, often with incomplete proof admissions enabled.

Only the third level is the final target, and only without admissions. Current broad suite successes mostly validate level 2 and the source-context part of level 3. They do not yet eliminate the need to trust Vampire or the Python translator for all admitted steps.

A final no-admit proof would reduce the trust boundary to Megalodon's kernel/checker plus the original source context. Vampire and Python would become proof search and proof generation tools, not trusted proof checkers.

That is the right endpoint. The project has not reached it yet.

## Recommended Next Work

The next phase should be organized around eliminating known admitted classes, not around running larger broad suites.

### 1. Finish scoped lambda/de-Bruijn demodulation on `hammer.981.15`

Use the current focused skeleton and remove the remaining local admissions around `S480`,
`S481`, `S1279`, and `S1281`. This should not be solved by a one-off proof script. The
right next task is to consume the exported lambda/de-Bruijn rewrite metadata and represent
the split-conditioned rewrite with the same binder/eigen context Vampire used.

For this step:

- inspect the `rewrite`, `lambda_sorts`, and `split_dependency` records for the four
  remaining demodulation steps,
- distinguish ordinary source variables from synthetic de-Bruijn indices,
- determine whether Vampire must export an additional scoped component certificate for
  rewrites under lambda binders,
- replay the four demodulation steps without changing the meaning of the parameterized
  split clauses,
- keep `S1395` as a focused regression for the final propositional AVATAR refutation.

### 2. Make source maps explicit

Add or use a machine-readable source map from the Megalodon TPTP exporter. It should map each TPTP axiom/symbol/conjecture back to:

- source file,
- line or source span if available,
- declaration name,
- local hypothesis name,
- local definition name,
- generated `set` fact,
- original formula before encoding.

This would reduce fragile name recovery and make the source-linking story much stronger.

### 3. Systematize `set` facts

Treat `set`-generated equalities as their own class. If a TPTP axiom came from a `set` command and has no source claim, generate a Megalodon proof by reflexivity/unfolding rather than searching for a missing theorem.

### 4. Complete skolemization certificates

Add richer Vampire skolemization records if needed. On the Megalodon side, build a small library of proof patterns using `Eps_i`/choice, classical logic, and quantifier rules.

### 5. Build an avatar proof importer

Define a tiny propositional proof language for avatar refutations, or export one from Vampire. Translate it into Megalodon claims using classical propositional reasoning. This is likely cleaner than trying to recognize final SAT contradictions from formulas alone.

### 6. Complete lambda/de-Bruijn replay

Use Vampire's exported binder/de-Bruijn metadata to reconstruct demodulation under binders. If Megalodon needs helper lemmas or tactics for binder-sensitive rewriting, add them deliberately rather than encoding fragile rewrites in generated scripts.

### 7. Formalize the test suite

Create a checked-in test manifest with:

- a smoke suite,
- a medium admitted source-context suite,
- an inference-class regression suite,
- a final no-admit suite.

The final suite should include at least 100 solved THF problems with cached Vampire proof outputs or reproducible Vampire commands using `-t 10`.

## Suggested Expert Review Questions

An expert reviewing this project should focus on the following questions.

1. Is the overall architecture right: rich Vampire proof export plus mostly mechanical Megalodon translation?
2. Should more reconstruction move into Vampire, or should Megalodon gain proof tactics/helpers for common proof patterns?
3. Is the current Python reconstructor acceptable as a translator, or is it already too complex to trust and maintain?
4. Is the proposition equality wrapper necessary, or can all such cases be mapped cleanly to Megalodon equality and proposition extensionality?

9. Which remaining admitted inference class is highest leverage to solve next?
10. What is the minimal no-admit milestone that would demonstrate viability?

## Bottom Line

The project has made real progress, but it is not complete. The best achievement is not a finished 100-proof no-admit suite; that does not exist yet. The best achievement is a working architecture that:

- gets rich proof information out of Vampire,
- generates Megalodon claim skeletons,
- links many Vampire inputs back to original Megalodon source facts,
- checks broad admitted source-context suites in parallel,
- exposes the remaining hard proof obligations explicitly.

The current direction is still the right one. The project should keep moving proof-critical information out of Python guesses and into Vampire's Megalodon proof export, while making Megalodon reconstruction increasingly mechanical. The immediate engineering target should be a no-admit reconstruction of the focused hard example, especially the remaining lambda/de-Bruijn, proposition simplification, and avatar refutation steps. Once that is solved generically, the work should scale to a curated 100-proof THF suite.
