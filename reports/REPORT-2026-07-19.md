## Executive Summary

The original project goal is not yet complete.

The target remains:

```text
Original Megalodon theorem and source context
  -> THF/TPTP export
  -> Vampire proof search, with a per-problem timeout no greater than 10s
  -> rich Vampire proof certificate
  -> Megalodon parser/checker
  -> native Megalodon Syntax.pf proof term
  -> checked proof of the original theorem at the original Megalodon site
```

The current branches do not yet deliver a 100-theorem original-context suite
with no `aby`, no `admit`, no incomplete QED, no certificate-derived bridge
assumptions, no Python-produced proof terms, and no hidden trusted theorems.

The project has nevertheless moved from a largely textual/Python skeleton
prototype to a more credible native-certificate path:

- Vampire now emits a Megalodon-oriented S-expression certificate with much
  richer rule, source, sort, substitution, parent, Skolem, equality, and
  kernel metadata.
- Megalodon parses those certificates in OCaml.
- Several structural and metadata audits are implemented.
- The trust boundary is better enforced than in the first attempts.
- Native `Syntax.pf` checking exists for a real seed fragment.
- The source-context machinery can now distinguish several original-source
  classes that were previously blurred.
- Small no-incomplete source-command examples now work with real live Vampire
  output.
- A real hammer source prefix now closes through `Empty_Subq_eq` without `aby`,
  without `admit`, and without incomplete QED.

The most important current positive result is small but qualitatively useful:

```text
LIVE_HAMMER_PREFIX_NO_INCOMPLETE_PASS 27
```

This is a Megalodon source-file test, not just a cached certificate audit. It
copies the early prefix of `examples/hammer/100thms_12_h.mg`, rewrites the
first 27 `aby` commands, including explicit lemma arguments, to `vampire`
commands, invokes real Vampire with
`--proof megalodon`, and checks the result in Megalodon's strict native path.
It runs without `-allowincompleteqed`.

The second current positive source-command result is:

```text
LIVE_CERTIFIED_VAMPIRE_NO_INCOMPLETE_PASS 4
```

This uses a compact synthetic Megalodon source file, also with live Vampire
certificates and no incomplete proof mechanisms.

The strongest broad result remains a strict 100-case regenerated THF
certificate gate. It is useful, but it is not final proof reconstruction:

```text
PASS 100
```

This gate verifies that Vampire can solve a known-solvable set and that
Megalodon can parse and audit the rich certificates with source-map and
primitive-metadata checks. It is E4 integration evidence, not E1 original
Megalodon theorem reconstruction.

The latest committed branch also contains closure of the former focused
17-case certificate frontier at the strict certificate/metadata level, plus
standard-Skolemization and subsumption metadata improvements. These were
important for moving explanatory detail into Vampire. They should still be
classified as certificate/metadata and partial native-kernel progress rather
than as completed original-context reconstruction.

The main caution is equally important. The first attempt to extend source-level
constructive proof search for nested Church-conjunction introduction was too
broad and regressed `and3E`. The committed version is guarded to fire only for
top-level introduction-chain goals. This episode is a concrete example of the
risk identified by the audits: Megalodon-side heuristic growth can regress
unrelated reconstruction and should not be the main path.

My current assessment is:

```text
Architecture: directionally correct, still not clean enough.
Vampire-side detail: much improved, but still not a small isolated IR.
Megalodon-side importer: useful, but too monolithic and still has heuristic
  growth pressure.
Source linkage: partial and improving; not complete original-context glue.
Smolka-style transformations: partially supported and audited, not yet a
  standalone proof-producing source/preprocessing layer.
Skolemization: materially improved at the certificate level, not fully solved
  as source-composed proof reconstruction.
AVATAR: still not cleanly certified as a small proof object.
Testing: faster and more disciplined than before, but final E1 test suite is
  not present.
```

The next direction should be stricter, not broader:

```text
Vampire:
  emit a small typed primitive certificate object, with exact parents,
  substitutions, positions, orientations, sorts, branch witnesses, and
  preprocessing payloads.

Megalodon:
  check that object, resolve original source facts, elaborate to Syntax.pf,
  and reject unsupported steps instead of guessing.
```

## Terminology and Evidence Classes

Several earlier reports used the word "pass" too broadly. The audits were
right to object. This report uses the following evidence classes.

E1: original-context native proof reconstruction.

An E1 result starts from a real Megalodon theorem site, uses the original
available source facts, invokes Vampire, reconstructs a native Megalodon proof
term, and checks the theorem without `aby`, `admit`, incomplete QED, bridge
assumptions, or certificate-derived trusted theorems. This is the final class
that matters.

E2: exported-THF-bound closed proof reconstruction.

An E2 result starts from an exported problem and checks a closed proof of the
exported problem. It may not yet compose back into the exact original
Megalodon theorem context, but it proves the exported statement without
bridges.

E3: native proof-term fragment checking.

An E3 result checks selected certificate fragments or synthetic cases with
native `Syntax.pf` proof terms. It is useful for validating kernel rules and
preprocessing steps.

E4: structural, source-map, and metadata integration.

An E4 result shows that the pipeline can export, solve, parse, source-map, and
audit certificates. It does not prove the theorem unless paired with E1/E2
proof-term checking.

Non-qualifying:

- any result using `aby`;
- any result using `admit`;
- any result requiring `-allowincompleteqed`;
- any result that dynamically installs a certificate step as a trusted
  theorem;
- any result with bridge assumptions;
- any result where Python constructs the final proof term;
- any result where the source name is linked but the source proposition is
  not checked.

The current broad `PASS 100` result is E4. The current source-command
prefixes are small E1-style smoke tests, though not yet the requested
100-theorem suite. The native kernel fragments are E3. Some older generated
script successes are non-qualifying because they used bridges or transitional
trusted facts.

## Original Objective and Constraints

The requested engineering endpoint was a port of Vampire's Lean proof
reconstruction/export ideas to Megalodon. The important point was not merely
to translate proof text into another syntax. Megalodon, like Lean, has proof
terms. The intended solution is to make Vampire emit enough proof information
that Megalodon can replay the proof as native proof objects.

Operational constraints that have shaped the work:

- Use THF/TPTP where relevant.
- Use Vampire with no more than a 10-second timeout per problem.
- Avoid repeated expensive Vampire runs over known-unsolved problems.
- Prefer parallel batch workflows, typically 10 to 20 workers.
- Use `/project/tmp` for temporary/generated test artifacts.
- Do not count Lean checking as success; the target checker is Megalodon.
- Do not use `aby` in resulting scripts, because `aby` is implemented as an
  admission mechanism.
- Do not use `admit`.
- Assume the project is classical; excluded middle `xm` and the logical
  library constants are available.
- Do not hardwire library-specific names such as `famunion`; reconstruction
  must be driven by proof objects and source maps.
- Give humans useful skeletons or intermediate artifacts only if they remain
  connected to original theorem names, lemmas, definitions, and source facts.
- Focus on large/frequent classes, not isolated tail failures.

These constraints are still correct. The current implementation only partly
satisfies them.

## Audit-Driven Course Corrections

The July 14 audit identified three serious defects.

First, "strict" certificate checking still allowed bridge premises. A proof
script could kernel-check because the generated theorem had extra assumptions.
That is not proof reconstruction.

Second, the bridge count undercounted extra premises. Some generated
assumptions did not have obvious `bridge_*` names.

Third, "source-linked" meant label-linked, not proposition-linked. A
certificate could refer to a valid source name while carrying a different
proposition.

The July 14 audit also warned that the OCaml rewrite had not by itself solved
the problem. The Megalodon side was still largely textual and heuristic, and
the scope had expanded beyond the MVP.

The July 16 audit accepted the native `Syntax.pf` seed as real progress, but
found another critical trust issue: the preprocessing proof-term path was
dynamically installing propositions as `Known` theorems and then applying
them. This moved the bridge problem into the proof-checker environment.

The July 16 audit also reclassified the strict 100 live run. It is useful
certificate-generation and structural-validation evidence, but it is not
closed proof reconstruction because it does not invoke the closed/native
proof-term checker on the final theorem.

The small-kernel plan was adjusted accordingly:

- counted native paths must not dynamically insert certificate-derived
  `Known` facts;
- original source propositions must be semantically linked, not just
  name-linked;
- proof detail should move into Vampire;
- Megalodon should check a small fixed calculus;
- preprocessing/source transformations should be a separate layer;
- broad pass counts should not be optimized before the trust boundary is
  correct.

This report agrees with those audit conclusions. Where current work deviates,
it is called out explicitly.

### Python Skeleton Phase

The earliest practical path was a Python translator/skeleton generator. That
path parsed Vampire output, attempted to recover proof structure, and produced
Megalodon-looking proof skeletons, often with `claim` blocks and admissions.

That phase was useful for exploration:

- it exposed how Vampire named exported symbols;
- it showed which inference families appeared frequently;
- it gave humans visible proof skeletons instead of all-or-nothing failures;
- it helped identify source-linking and name-recovery problems;
- it made clear that AVATAR, Skolemization, and FOOL/CNF transformations were
  major frontiers.

It was not a sound final approach:

- it guessed too much from printed terms;
- it duplicated logic that Vampire already knows precisely;
- it encouraged library-specific or name-specific patches;
- it could not reliably reconstruct binders, sorts, and substitutions;
- any script requiring `admit`, `aby`, or bridge assumptions was
  non-qualifying.

Python should now be treated only as analysis/reporting infrastructure.
No Python-generated proof term should count toward the final result.

### Native Certificate Phase

The next phase moved toward Vampire-emitted S-expression certificates and an
OCaml parser/checker in Megalodon. This was a meaningful improvement over
reading ordinary TPTP proof text.

Vampire now emits certificate records for many step classes, including:

- source formulas;
- term/formula inputs;
- substitutions;
- resolution;
- factoring;
- equality resolution;
- equality factoring;
- paramodulation and superposition-related steps;
- subsumption-related steps;
- rectification;
- FOOL transformations;
- ENNF;
- CNF;
- Skolemization;
- AVATAR split/definition/component/refutation records;
- kernel metadata records.

This improved the pipeline because Vampire can print information while it
still knows the exact parent units, selected literals, variable sorts,
substitutions, orientations, and rewrite positions.

The problem is that the certificate vocabulary and the Megalodon importer grew
large before the small primitive kernel was isolated. This matches the audit
concern: the project moved in the right direction but kept adding cases to a
large monolith.

### Native Proof-Term Phase

The native `Syntax.pf` phase introduced proof-term checking inside
Megalodon. This is the correct trust boundary: the importer may elaborate,
but Megalodon's own checker must verify the resulting proof term.

Useful native fragments now exist. The broadest stable evidence, however, is
still mixed:

- synthetic and focused E3 fragments are genuine proof-term checks;
- the strict 100 live gate is E4 metadata/source/certificate validation;
- old generated script passes with bridges are non-qualifying;
- small no-incomplete source-command gates are the first meaningful E1-style
  smoke evidence.

### Prover9/Ivy Pivot

The Prover9/Ivy analysis changed the intended design. The main lesson was:
do not ask the proof assistant importer to rediscover a large theorem prover's
internal reasoning. Instead, have the prover lower its complex inferences into
a small certificate object that a simple checker can validate.

For this project, the intended analogue is:

```text
Vampire macro inferences
  -> primitive proof records emitted by Vampire
  -> small Megalodon kernel checker
  -> native Megalodon proof term
```

This is only partially implemented. Some Vampire-side metadata and primitive
expansions exist, and some Megalodon-side checks exist. There is not yet an
isolated, stable `MegalodonKernelStep` IR in Vampire comparable to the desired
Ivy object. This is the largest architectural gap.

## Current Architecture

The current implementation is best understood as five layers.

Layer 1: Megalodon source export.

Megalodon exports the current theorem obligation and available source facts
to THF/TPTP. Source-origin information is carried through comments and
metadata so certificate inputs can be linked back to source objects.

Layer 2: Vampire proof search.

Vampire is invoked on the exported THF problem, normally with:

```text
--input_syntax tptp --mode casc -t 10 --proof megalodon --output_axiom_names on
```

The project standard is not to run Vampire for longer than 10 seconds per
problem.

Layer 3: Vampire certificate emission.

The Vampire fork emits a Megalodon-oriented S-expression certificate. This is
currently implemented in the large Megalodon checker/printer area of the
Vampire source. It emits both macro-level certificate steps and newer
`kernel_v1` metadata.

Layer 4: Megalodon certificate import.

Megalodon parses the S-expression certificate, parses formulas/terms, checks
source metadata, audits primitive metadata, reconstructs or validates step
relationships, and in some modes elaborates native `Syntax.pf` terms.

Layer 5: Megalodon source-command integration.

The `vampire` proof command uses the certificate path to try to close the
current Megalodon proof goal. This is the layer that matters most for the
original objective. It is now working on small examples and the early hammer
prefix, but it is not broad enough.

The architecture is directionally correct. The implementation boundaries are
not yet clean enough:

- the Vampire printer is still too monolithic;
- the Megalodon importer/checker is still too monolithic;
- the source/preprocessing layer is mixed with clausal replay;
- some source-level constructive search was added as a workaround for hard
  certificate fragments;
- a stable primitive certificate IR is not yet the central implementation
  artifact.

## Detailed Implementation Notes

This section gives a more concrete account of what changed in code and why.
It is included because several earlier reports described progress at too high
a level. An expert review should be able to distinguish between sound
proof-producing work, useful metadata work, diagnostic tooling, and code that
is intentionally transitional.

The Vampire fork contains the proof-emission side. Its work is concentrated
around `Shell/MegalodonChecker/MegalodonChecker.cpp` and
`Shell/MegalodonChecker/MegalodonKernelSyntax.cpp`. The important design
choice was to stop treating the ordinary printed TPTP proof as the main
object. Instead, the fork emits Megalodon-specific certificate records. These
records include macro step names, parent IDs, clause/formula payloads, source
origin data, variable sorts, substitutions, rewrite data, and a growing
`kernel_v1` side channel for primitive replay data.

The `MegalodonKernelSyntax` work is a first step toward a better boundary. It
centralizes some printing of kernel metadata rather than scattering every
field directly through the macro proof printer. This is still weaker than the
desired final design, because it mostly serializes metadata supplied by the
larger exporter. The future design should build typed primitive records first
and only then serialize them. The difference matters. Serialization helpers
make the output more uniform, but they do not guarantee that every macro rule
has been lowered through the same small set of checked primitives.

The Megalodon repository contains the import and source-command side. Most
certificate work is currently in `src/vampire_cert_v1.ml`, and source-command
integration is in `src/megalodon.ml`. The importer can parse the S-expression
certificate, maintain a step table, interpret source-origin records, perform
strict metadata audits, and in selected modes build native `Syntax.pf` proof
terms. The source command path invokes Vampire, collects the emitted
certificate, and attempts to close the current Megalodon proof goal directly.

The current native source-command successes are significant because they run
through Megalodon's own proof checking. They are not textually generated
scripts that happen to parse. They are also not Lean results. The proof
command is executed at a Megalodon theorem site, against the current
Megalodon environment, and without `-allowincompleteqed`.

The report nevertheless classifies these as smoke results because the number
of covered theorems is small and the proof search still contains some
specialized source-goal handling. In particular, the early hammer file starts
with a logical prelude whose theorems are simple but structurally awkward for
Vampire certificates because they use Church encodings of connectives and
because some short proofs trigger AVATAR or preprocessing paths. Closing the
prefix is useful, but it does not yet demonstrate that arbitrary later hammer
theorems can be reconstructed from detailed clausal certificates.

### Source-Proof Fallback

One recent change links already-audited source proofs into the native
constructive goal search. This was added to handle examples such as
`Eps_i_ex`, where the theorem can be proved from an explicitly supplied source
axiom argument. The important point is that the implementation is not keyed to
the particular name `Eps_i_ax`. The proof command receives source proof
candidates from the current context and threads them through term and proof
binders using the existing shift operations. The constructive search can then
apply those candidates when their propositions match the current subgoal.

This is a better pattern than hardwiring source names. It still needs careful
scope auditing. Any source proof imported into a binder context must be
shifted correctly, and any application of that proof must be checked by
Megalodon's proof checker. The current tests cover the first useful instance,
but the source-context abstraction should make this discipline explicit
rather than relying on local conventions inside the proof command.

### Circular Source-Definition Defect

Another recent change fixed a circularity in proposition-extensionality
reconstruction. The source proof for `prop_ext_2` was previously able to see a
known theorem named `prop_ext_2` while proving `prop_ext_2` itself. That made
the final `Qed` fail because the theorem depended on its own not-yet-proved
definition. The fix was to avoid using that current theorem as a shortcut and
to construct the `iff` proof from the given implications before applying the
source axiom `prop_ext`.

This is a small defect, but it is representative of the source-linking
problem. Original-context reconstruction must distinguish:

- previously checked global facts;
- source axioms declared before the current theorem;
- local hypotheses;
- the current theorem under construction;
- generated facts with proof terms;
- certificate steps that must not be installed as facts.

Confusing any of these can produce either an explicit failure, as in
`prop_ext_2`, or a more dangerous hidden trust leak.

### Hammer Prefix Harness

The hammer-prefix no-incomplete harness copies a source prefix of
`examples/hammer/100thms_12_h.mg` into `/project/tmp`, rewrites each
admission-shaped proof command in that prefix from `aby...` to `vampire...`,
and then runs Megalodon on the generated source file. This means both bare
commands such as:

```text
aby.
```

and argument-bearing commands such as:

```text
aby prop_ext.
aby set_ext Subq_Empty.
```

become source-level `vampire` commands. The current default prefix ends before
`Empty_eq` and expects 27 reconstructed commands.

The harness checks several things mechanically:

- the number of generated `vampire` commands matches the expected count;
- the generated source contains no `admit`, `aby`, or
  `-allowincompleteqed`;
- Vampire supports `--proof megalodon`;
- Megalodon is run without incomplete QED;
- every proof command produces a proof artifact;
- the log contains no forbidden bridge/admission markers;
- generated THF files carry Vampire-origin metadata.

The harness currently uses a single Megalodon source-file run, not separate
parallel Vampire invocations, because it is checking the interactive
source-command integration path rather than a batch certificate corpus. For
large corpus testing the better method remains batch export, parallel Vampire,
and parallel certificate/import checks. The source-command prefix gate is kept
small precisely so it does not become another slow broad test.

### Current Concrete Frontier

The next hammer-prefix theorem is:

```text
Theorem Empty_eq : forall X:set, (forall x, x /:e X) -> X = Empty.
aby Empty_Subq_eq.
Qed.
```

The focused probe for this theorem currently fails in the strict native
certificate path at Vampire step `u311`:

```text
strict certificate v1 kernel_v1 rewrite metadata has no matching certificate step
```

The failure appears to be a Vampire-side certificate-detail problem rather
than a reason to add another Megalodon heuristic. The emitted step is a
forward-demodulation/rewrite step. A nearby later rewrite step carries enough
explicit equality location and substituted-equality metadata for the strict
checker, while `u311` appears to omit some of that explicit data. The correct
next implementation is therefore likely to make Vampire emit the missing
rewrite/equality-side primitive metadata uniformly for this demodulation case.

This is exactly the type of work the audits recommend: when a macro inference
is too large or too implicit, enrich or lower the Vampire certificate rather
than making Megalodon guess.

### Why the Report Still Mentions Python

Python still appears in the repository and in this report because it was part
of the project history and remains useful for diagnostics. It is not the
preferred final proof reconstruction path. The current preferred path is:

```text
Vampire-owned detail -> small certificate -> OCaml checker -> Syntax.pf
```

Python-generated proof terms, Python-generated trusted scripts, and Python
heuristics do not count for E1/E2 success. If Python is used, it should be for
batch orchestration, statistics, corpus selection, or report generation, not
as the trusted elaborator of the final proof.

## Vampire-Side Work

The Vampire fork has accumulated several important improvements.

### Richer Source and Rule Records

The certificate records now carry more source information than ordinary TPTP
proof output. This includes names, roles, source origins, hashes or source
references where available, rule names, and formula data.

This was necessary because ordinary Vampire proof text is too thin. Vampire
internally knows sorts, selected literals, substitutions, and parent
relationships. Trying to rediscover those from a printed proof in Megalodon or
Python is both slow and brittle.

### Substitution and Instantiation Metadata

Substitution handling was a repeated failure source. Vampire now emits more
explicit data for non-identity substitutions, including parent/result
relationships and kernel metadata. This supports audits that reject missing
substitution information.

The current strict 100 gate includes substitute metadata auditing. This is
E4 evidence, but the metadata itself is useful for later E1/E2 proof-term
work.

### Equality Metadata

Equality-resolution, equality-factoring, and superposition/paramodulation
metadata were expanded across several commits. Current changes include:

- equality-resolution substitute helpers;
- equality metadata aligned with primitive replay;
- typed equality-factoring constraints;
- split-backed parent handling for superposition;
- subsumption metadata aligned with direct resolve chains.

This work moved information from Megalodon guessing into Vampire emission,
which is the right direction.

### Skolem Metadata and Standard-Skolemization Direction

Skolemization was one of the hardest recurring areas. Vampire-side work now
prints more detailed Skolem-related contracts, including:

- top-level Skolem quantifier metadata;
- macro-edge shape metadata;
- free-variable metadata;
- introduced witness contracts;
- child and branch contracts;
- parent instantiation contracts;
- branch binder instantiation;
- branch proposition contracts;
- branch choice witness terms;
- standard-Skolem Megalodon certificate details.

This has materially improved the Skolem frontier. It does not by itself solve
source-level Skolemization proof composition, but it supplies data that
Megalodon should check rather than infer.

### Remaining Vampire-Side Gaps

The most important gap is absence of a clean primitive IR.

The current C++ emits many S-expression records, but the architecture still
needs an internal typed object like:

```text
MegalodonKernelStep {
  id;
  primitive_rule;
  parents;
  conclusion;
  selected_literals;
  substitutions;
  positions;
  orientations;
  sorts;
  macro_origin;
}
```

The point is not the exact name or structure. The point is that Vampire should
lower complex inferences through one shared primitive builder before printing.
That would make the certificate comparable to a Prover9/Ivy proof object and
would keep Megalodon from becoming a second, heuristic Vampire.

The main macro classes that should lower through this object are:

- unit-resulting resolution;
- demodulation and rewrite;
- superposition;
- subsumption resolution;
- equality factoring;
- AVATAR clauses/refutations, eventually;
- selected preprocessing transformations where Vampire has the exact
  transformation data.

## Megalodon-Side Work

### Certificate Parser and Structural Checker

Megalodon now has a large OCaml certificate parser/checker for Vampire's
S-expression format. This path can:

- parse certificate records;
- parse terms and formulas;
- track step IDs and parent references;
- enforce source-map requirements in strict modes;
- reject missing metadata in audited modes;
- classify source origins;
- produce diagnostics and rule-count audits;
- drive live and cached regression harnesses.

This is useful infrastructure. It is not, by itself, proof reconstruction.

### Native `Syntax.pf` Proof-Term Seed

The native proof-term work is the strongest trust-boundary improvement. Where
it is used properly, Megalodon constructs `Syntax.pf` proof terms and checks
them using its own proof checker rather than accepting generated text or
trusted bridge facts.

The July 16 audit correctly identified this as genuine progress. The same
audit also correctly warned that some native preprocessing paths had
reintroduced trust by dynamically installing `Known` propositions. The counted
path must avoid that.

### Source-Command Integration

The Megalodon `vampire` proof command can now run a real Vampire proof search
and attempt native reconstruction at the source theorem site. This is the
most relevant user-facing integration path.

Two current source-command gates pass:

```text
LIVE_CERTIFIED_VAMPIRE_NO_INCOMPLETE_PASS 4
LIVE_HAMMER_PREFIX_NO_INCOMPLETE_PASS 27
```

The hammer-prefix gate is the better evidence because it uses a real library
prefix from `examples/hammer/100thms_12_h.mg`. It currently reconstructs the
first 27 `aby` commands, including explicit lemma arguments, through
`Empty_Subq_eq`.

The source-command layer now also includes a direct constructive source-goal
attempt before expensive generic replay in some cases. This helped close
`or3E` using a shape-based Church-disjunction proof. That improvement is
useful for the early hammer prefix, but it should not become the main strategy
for general reconstruction. General proof replay should come from Vampire
certificates.

### Explicit Trust of Declared Source Axioms

The hammer prefix depends on declared Megalodon axioms such as `prop_ext`.
The branch introduced an explicit `-trustdeclaredaxioms` switch so source
axioms can be trusted when checking these prefixes.

This is an important distinction:

- trusting a Megalodon source `Axiom` declaration is a source-context policy;
- trusting a certificate-derived theorem is a proof reconstruction failure.

The flag is off by default. It should remain explicit.

### Current Experimental Conjunction Work

There is a guarded source-level constructor in `src/megalodon.ml` that tries
to recognize and prove Church-encoded conjunction introduction chains. The
goal was to extend the live hammer-prefix frontier from `or3E` into the
following `and4I`, `and5I`, `and6I`, and related source commands.

The first broad experiment reconstructed some later explicit-argument commands
but also regressed `and3E`. The guarded version reconstructs the explicit
argument commands through `and7I`. The relevant source commands include:

```text
aby and3I.
aby and4I.
aby and5I.
aby and6I.
```

to:

```text
vampire and3I.
vampire and4I.
vampire and5I.
vampire and6I.
```

The stable version is deliberately conservative: it only fires when the outer
proof context is empty, the goal is an implication chain, and the final
conclusion is a Church-encoded conjunction pair. That avoids the earlier
misuse inside elimination subgoals such as `and3E`. The same promoted prefix
now also passes `not_or_and_demorgan`, `not_ex_all_demorgan_i`, `iffEL`,
`iffER`, `iff_refl`, `iff_sym`, `iff_trans`, `eq_i_tra`, `neq_i_sym`, and
`Eps_i_ex`.

## Source Linking to Original Megalodon Developments

Source linking is one of the central requirements. The human needs to see how
the reconstructed Vampire proof connects to the original theorem, lemmas,
definitions, local hypotheses, and generated facts in the Megalodon
development.

### What Works Now

The certificate/source layer can classify several source kinds:

- global source facts;
- local source hypotheses;
- definitions;
- generated facts;
- conjecture facts;
- unresolved facts;
- set-generated facts.

The source-map infrastructure no longer treats every certificate input as an
ordinary axiom merely because it has a name. It can require source-origin
metadata and reject missing or incompatible source references in strict modes.

Name recovery is partly handled. Exported TPTP names are mapped back through
source metadata where possible. This is better than relying on ad hoc
unmangling in a separate translator.

The hammer-prefix source-command gate is important because it exercises
source linkage inside a real Megalodon source file. The proof command is
located at the theorem site, Vampire is called live, and the reconstructed
term is checked against the current source goal.

The `vampire` command shares the argument-handling path used by `aby`, so
explicit dependency arguments such as:

```text
vampire Hp.
vampire and3I.
```

are syntactically supported. The current committed hammer-prefix harness
rewrites both bare and argument-bearing `aby` commands in the selected prefix.
This is why examples such as `vampire Eps_i_ax.`, `vampire prop_ext.`, and
`vampire set_ext Subq_Empty.` are part of the 27-command gate rather than
separate exploratory-only probes.

### What Is Still Missing

The source-linking layer is not yet complete enough for the final result.

Open items:

- A qualifying final proof must resolve every certificate input to one of:
  original global theorem/axiom, original local hypothesis, definition,
  generated reflexivity fact, approved logical principle, or conjecture
  negation.
- Source proposition equality must be semantic, not just name/hash matching.
- Local hypotheses must survive export/import with correct binder scopes.
- Definitions must be connected through Megalodon's definitional conversion
  or explicit definitional proof terms, not treated as arbitrary facts.
- The negated conjecture must be converted back into the original theorem
  proof at the source site.
- Generated facts from `set` commands need explicit proof terms, usually
  reflexivity.
- The resulting proof object should be auditable: each `Known` occurrence
  should have provenance from the original context or approved library basis.

The most concrete next milestone should be a small E1 suite where all of
these checks are on. The existing hammer-prefix gate is a start, but it does
not yet constitute the broad source-composition layer.

## Set-Generated Equalities

The user pointed out that some TPTP axioms come from Megalodon's `set`
command and may not have corresponding claims. These are typically equalities
generated by definition or assignment-like source elaboration.

The intended treatment is:

```text
TPTP input from set command
  -> source kind = generated set equality
  -> Megalodon proof = reflexivity / definitional equality proof
```

This should not be handled as a trusted axiom and should not require a human
lemma. It should be generated by the source/preprocessing layer.

Current status:

- Generated-set source obligations are recognized in audits.
- Some source-obligation checks now account for generated-set facts.
- The final original-context proof path still needs systematic generation and
  checking of the actual reflexivity proof terms at the theorem site.

Expert review should pay attention to whether generated facts are treated as
definitions/proofs or as hidden assumptions. Only the first is acceptable.

## Name Recovery

Name recovery is partially solved and should remain source-map driven.

The wrong path would be to maintain a separate hand-written reverse mangler
that guesses original names from TPTP strings. That can be useful for display,
but it is not a proof boundary.

The better path is:

- Megalodon export attaches source IDs and enough canonical formula data.
- Vampire preserves those source IDs in certificate inputs.
- Megalodon importer resolves the ID back to an original source object.
- Pretty-printing uses the original Megalodon name when displaying a proof
  skeleton or diagnostic.

This is especially important for local hypotheses and definitions, where a
name alone is not enough. A local `H` under binders is not interchangeable
with another source declaration named similarly elsewhere.

The current infrastructure has enough metadata to support this direction, but
the final proof object audit is not complete.

## Equality

The desired endpoint is to use Megalodon's equality, not a separate private
equality invented for the certificate importer.

Earlier work had custom equality encodings in proof skeletons and TPTP
translation layers. That was acceptable for exploration but is not the final
design. The final native proof terms should use Megalodon's equality and its
standard equality principles/conversion behavior.

Current status:

- The certificate layer handles typed equality metadata better than before.
- Equality-resolution and equality-factoring metadata have improved.
- Superposition and paramodulation parent metadata are more explicit.
- Some equality-related native checks pass in focused or strict metadata
  gates.

Open items:

- Ensure all equality proof terms elaborate against Megalodon's actual
  equality constants/principles.
- Remove or quarantine any legacy private equality bridge used only for
  textual scripts.
- Make equality orientation and rewrite-position data explicit in the
  primitive IR.
- Prove `set` equalities by reflexivity/definitional equality, not by
  importing them as assumptions.

## Skolemization

Skolemization has improved significantly, but it is not finished.

### What Has Improved

The project moved from trying to guess Skolem behavior in Megalodon/Python to
having Vampire print more of the data it used. The Vampire branch now has a
sequence of Skolem metadata commits, including branch, parent, witness, and
standard-Skolemization details.

Megalodon-side work then used this richer data to close focused strict
certificate/metadata frontiers. The former 17-case frontier that included
Skolem-related failures now closes at the current strict certificate/metadata
level.

There is also a focused Skolem live frontier reporting:

```text
SKOLEM_PF_PASS 35
```

This is real progress over the earlier state where Skolemization mismatches
were frequent blockers even for structural/certificate checking.

### What Remains Open

The final Skolem problem is not merely printing a Skolem function. It is
proving the transformation in Megalodon and composing it with the source
context.

The final checker needs a source/preprocessing proof rule roughly of the form:

```text
from exists x, P x
derive P (sk deps)
where sk deps is defined using a classical choice operator
and dependencies are exactly the surrounding universally quantified variables
```

Complications include:

- dependent Skolem functions;
- multiple introduced witnesses;
- branch-specific witnesses;
- retained parent variables;
- binder instantiation order;
- alpha-renaming/rectification around the Skolem step;
- conversion between Vampire's formula shape and Megalodon's internal
  `Syntax.tm`;
- ensuring generated Skolem definitions are conservative delta definitions,
  not arbitrary assumptions.

The current branch has enough data to proceed more systematically than before.
The missing piece is a clean Smolka/source-transformation proof object that
Megalodon checks natively.

## Smolka-Style Transformations

The Smolka-style part of the project concerns the transformation from source
higher-order/classical formulas into the clausal form used by the prover. It
includes:

- rectification;
- alpha-conversion;
- lambda/binder normalization where needed;
- Boolean/FOOL transformations;
- negation normal form;
- definitional transformations;
- CNF projection;
- Skolemization;
- conjecture negation;
- source-to-clause connection.

This layer is distinct from the clausal kernel. Resolution, factoring, and
paramodulation can be checked by a small clausal calculus only after the
source formulas have been soundly transformed into clauses.

Current status:

- Certificate records and audits exist for several transformation families.
- Some focused native proof-term seeds exist.
- Generated-set source obligations are recognized.
- Standard Skolemization metadata is much better.
- The hammer-prefix source-command path can bypass some hard AVATAR/source
  replay cases with direct checked source-goal proof terms for simple
  Church-encoded logical theorems.

What is still missing:

- a standalone transformation checker module;
- a stable transformation proof-object vocabulary;
- native proof terms for every counted transformation;
- composition from original source facts to clausal inputs;
- negative tests proving unsupported transformations fail closed;
- a clear boundary between source/preprocessing proof and clausal kernel
  proof.

The expert should be skeptical of any pass count that crosses this layer
without explaining which transformation proof terms were checked.

### Smolka-Style Work Needed in Practice

The paper-oriented view of the source-to-clause problem is attractive because
it separates two proof obligations that are often conflated in prover exports:

```text
source formula proves transformed clause set
transformed clause set refutes by clausal reasoning
```

For this project, that separation should become an executable interface. The
source/preprocessing layer should not simply return a list of clauses. It
should return clauses together with a proof object explaining why those clauses
are sufficient for the original theorem. That proof object must be checked in
Megalodon. If a transformation is unsupported, the pipeline should fail closed
or fall back to a known smaller fragment, not assert a generated implication.

A reasonable first Smolka-style object vocabulary would include the following
families.

Source assumption object:

```text
kind = source_input
source_id = original declaration or local hypothesis
source_prop = Megalodon proposition
exported_prop = THF/Megalodon-parsed proposition
proof = original proof handle or local hypothesis reference
```

This object is the boundary between the original development and the
certificate. It should be checked by resolving the source ID and comparing the
exported proposition against the actual Megalodon proposition under the
current binder context.

Definition object:

```text
kind = definition_unfold or definition_fold
parent = formula before conversion
result = formula after conversion
definition_id = original Megalodon definition
proof = conversion/reflexivity proof
```

This is where `set` command equalities also belong when the exported formula
is just a definitional equality. They should be proved by reflexivity or
conversion. They should not be imported as axioms merely because Vampire used
them as TPTP inputs.

Rectification object:

```text
kind = rectify
parent = formula with original binders
result = formula with renamed binders
renaming = explicit binder map
sorts = explicit binder sorts
proof = alpha-conversion proof or checked syntactic alpha equivalence
```

Rectification should be one of the easiest transformations to certify, but it
must still be scope-correct. A name-only check is not enough.

Boolean/FOOL object:

```text
kind = fool_transform
parent = formula
result = formula
cases = explicit Boolean/proposition cases when needed
logical_basis = approved classical principles
```

Because Megalodon is treated classically and `xm` is available, the proof
basis can use excluded middle. The object should still record which classical
principle is used and where.

Negation-normal-form object:

```text
kind = ennf
parent = formula
result = formula
rewrite_path = explicit path through connectives and quantifiers
logical_basis = De Morgan, implication, quantifier duality, double negation
```

This is not just a printer normalization. The importer needs either a checked
recursive proof recipe or a small verified transformation checker that
constructs the proof term.

CNF projection object:

```text
kind = cnf_project
parent = formula
clauses = clause list
definition_introductions = list of definitional clauses
proof = chain from parent to conjunction of clauses or refutation-sufficient
        implication
```

The final object does not necessarily have to prove equivalence in both
directions if the refutation pipeline only needs satisfiability preservation
in one direction. But the direction must be explicit and checked. This is
especially important when definitional CNF introduces fresh predicates or
functions.

Skolem object:

```text
kind = skolemize
parent = formula with existential position
result = formula with witness term
dependencies = surrounding universal variables
witness = Skolem function/application or choice term
choice_contract = proof obligation using classical choice/epsilon
```

The current Vampire branch emits much more of this data than before, but the
Megalodon side still needs a general proof-producing rule for it. The rule
should be conservative: introduced Skolem symbols must be tied to explicit
choice definitions or proof contracts, not global axioms with no provenance.

Conjecture-negation object:

```text
kind = conjecture_negation
original_goal = theorem proposition
refutation_assumption = negated exported conjecture
closing_proof = derive False from negated conjecture, then use classical
                contradiction to prove original goal
```

This object is what glues an exported refutation back to the theorem being
proved. Without it, the system may check a refutation of a related exported
problem but still not prove the original Megalodon theorem command.

The implementation should not try to complete all of these at once. A better
order is:

1. source input and local-hypothesis linkage;
2. generated set equality by reflexivity;
3. definition unfold/fold by conversion;
4. conjecture negation for a simple implication-free theorem;
5. rectification;
6. first-order ENNF fragments;
7. a single Skolemization pattern using one witness and no branch splitting;
8. CNF projection for a small formula family;
9. only then broader FOOL and AVATAR-heavy cases.

This order keeps the early milestones close to original-context E1 results
instead of broad structural E4 results. It also gives the expert concrete
objects to inspect.

## Clausal Kernel Status

The desired small kernel should be much smaller than the current certificate
vocabulary. A plausible core is:

- input/boundary from preprocessing;
- instantiate;
- alpha-rename, preferably as checked alpha-conversion rather than a logical
  rule;
- flip/orient equality;
- resolve;
- factor;
- equality resolution;
- equality factoring;
- paramodulate/superpose;
- truth conflict, if it really belongs in the clausal layer;
- final contradiction marker for the empty clause.

The current branch has seeds for several of these. It also has audits for
missing metadata and primitive records.

But the project does not yet have the clean object the audits recommend:

```text
complex Vampire inference
  -> list of primitive kernel records
  -> Megalodon small checker validates each primitive
```

Instead, there is still a large mixture of:

- macro certificate records;
- kernel metadata side records;
- direct native proof-term code;
- structural audits;
- textual legacy support;
- special paths for preprocessing and source goals.

The next architectural step should be to extract and enforce the primitive
IR. New reconstruction power should come from this IR, not from more
Megalodon-side ad hoc proof search.

### Desired Primitive Certificate Shape

The primitive certificate should be boring. That is a virtue. It should avoid
large rule names such as "forward demodulation" or "superposition" as trusted
atomic facts unless those rules are themselves decomposed into data that a
small checker can replay.

A primitive clausal step should contain at least:

```text
step_id
primitive_rule
parents
conclusion_clause
parent_clause_views
selected_literal_indices
substitutions
term positions
equality orientation
variable sorts
fresh variable policy
macro_origin
```

For a resolution step, the checker should know:

- which parent literal was positive;
- which parent literal was negative;
- the substitution applied to each parent;
- the complementary atom after substitution;
- the remaining literals in the conclusion;
- whether duplicate literals were removed by factoring.

For factoring, the checker should know:

- the two literals to merge;
- the unifier/substitution;
- the resulting literal;
- the retained literals.

For equality resolution, the checker should know:

- the equality literal being removed;
- the substitution that makes both sides identical;
- the resulting clause after deleting the literal.

For equality factoring, the checker should know:

- the two equality literals;
- which side is unified with which;
- the residual equality literal;
- the exact substitution and retained literals.

For paramodulation/superposition, the checker should know:

- the equality parent and target parent;
- equality literal index;
- equality orientation;
- target literal index;
- position of the rewritten subterm;
- substitution applied to both parents;
- target term before rewrite;
- replacement term after rewrite;
- conclusion clause after replacing the subterm and merging retained
  literals.

The current `u311` failure in `Empty_eq` is a useful example. A human can see
from the emitted certificate that the intended rule is a rewrite, but the
strict checker cannot match it to a complete primitive certificate step. The
right fix is not to make the Megalodon checker infer the missing equality
parent data from nearby strings. The right fix is for Vampire to emit the
primitive rewrite object in the same complete format for every demodulation
case.

For truth or Boolean conflicts, the object should state whether the conflict
belongs to the clausal kernel or to the preprocessing layer. If it is a
clausal rule, it should be expressed as a contradiction between complementary
Boolean literals after substitution. If it arises from FOOL rewriting, it
should be a Smolka/preprocessing proof object instead.

The key expert question is whether this primitive set is small enough. My
current view is that it is. The branch already contains data for many of
these fields, but they are not enforced through one central typed builder.
Until they are, the implementation remains too dependent on per-rule metadata
patches.

### How Macro Inferences Should Lower

Many Vampire inferences are useful at the prover level but too large for the
checker boundary. The lowering should happen in Vampire, not in Megalodon.

Unit-resulting resolution can usually lower to a resolution primitive plus
zero or more instantiate/rename/factor cleanup steps. Subsumption resolution
can lower to a direct resolution chain when the pivot and substitutions are
explicit. Demodulation can lower to oriented paramodulation or rewrite with a
fully specified redex. Superposition can lower to paramodulation plus
factoring or simplification steps when needed. Equality simplifications should
lower to equality-resolution/factoring/paramodulation rather than a separate
large family of trusted simplifier rules.

The Prover9/prooftrans lesson is that the proof object can be more verbose
than the search proof. That is acceptable. The certificate should optimize for
checkability, not for matching Vampire's internal proof-tree names.

This also affects testing. A useful regression is not only "does the original
macro proof parse?" but "does the macro proof lower to a sequence whose every
primitive field is checked?" A missing position, substitution, sort, or parent
literal index should be a failing test.

## AVATAR and SAT Reasoning

AVATAR remains a major open problem.

The `or3E` source-command result is useful but should not be misread. The
Vampire certificate for `or3E` is AVATAR-heavy, but the current committed path
closes it using a direct source-level Church-disjunction proof before the
expensive generic certificate replay. That proves the source theorem, but it
does not solve general AVATAR replay.

The AVATAR certificate records currently include split-related data such as:

- split dependency;
- avatar split;
- avatar definition;
- avatar component;
- avatar refutation;
- SAT/refutation metadata in some paths.

What is still needed:

- a small proof object explaining split introduction and component use;
- a representation of the propositional/SAT proof, preferably lowered to
  simple resolution-like steps or a small checked RUP/DRAT-style kernel;
- composition of AVATAR branch facts back into the clausal proof;
- no dynamic `Known` facts for avatar components or refutations;
- negative tests for malformed split dependencies and unsupported SAT
  justifications.

For the final 100-theorem result, either the test suite must initially avoid
AVATAR-heavy proofs or AVATAR must be given a real small certificate layer.
Given the user's emphasis on serious hammer examples, avoidance can only be a
temporary milestone.

## Testing Discipline

Testing has improved relative to the first days of work.

The current discipline is:

- avoid repeated expensive Vampire runs on broad unsolved sets;
- determine known-solvable subsets once, then iterate on them;
- run Vampire in parallel where broad testing is justified;
- keep Vampire timeout at 10 seconds;
- use `/project/tmp` for generated artifacts;
- distinguish E1/E2/E3/E4 evidence;
- maintain small focused tests for current frontiers;
- avoid promoting slow frontier probes to default gates.

This is better than the earlier slow sequential loop. The main remaining risk
is not raw performance but choosing the wrong target: optimizing broad E4
pass counts can still waste time if the proof-term/source boundary is not
being improved.

The next test suite should be shaped as follows:

T0 build/syntax:

- `TMPDIR=/project/tmp ./makeopt`
- `bash -n` for shell harnesses
- `git diff --check`

T1 small no-incomplete command gates:

  resolution, equality factoring, paramodulation, and truth conflict;

Broad strict 100 E4 gates should remain as regression/integration tests, but

checking for success. However, the Megalodon proof reconstruction is not yet
complete, and the Vampire-side proof object is not yet the desired isolated
primitive IR.

Requirement: avoid slow sequential iteration and use parallelism for broad
tests.

Status: improved. Broad certificate gates use parallel live Vampire runs and
the known-solvable set. The current source-command prefix test is deliberately
small and is not designed as a broad parallel run. Future 100-theorem E1
testing should use batch export, parallel Vampire, and parallel Megalodon
certificate/source checks where possible.

Requirement: use `/project/tmp` for temporary operations.

Status: done for the current harnesses and generated artifacts discussed in
this report. The harnesses set or default `TMPDIR=/project/tmp` and create
work directories there.

Requirement: do not run Vampire for more than 10 seconds.

Status: enforced in the active harnesses described here. The source-command
gate sets `MEGALODON_VAMPIRE_TIMEOUT=10` by default. The broad certificate
gate has also been run with 10-second per-problem limits.

Requirement: no `aby`, no `admit`, no incomplete QED in final scripts.

Status: enforced in small source-command gates, not achieved for a 100-theorem
result. The hammer-prefix harness rejects admission-shaped tokens in the
generated source and logs. The final broad objective remains open.

Requirement: assume classical logic and use library logic constants.

Status: reflected in the implementation direction. The current source-command
work assumes classical logic, and reports/plans treat `xm` as available.
There remains cleanup work to ensure every final equality/false/or proof uses
Megalodon's actual library constants rather than legacy private encodings.

Requirement: avoid hardwiring names and optimize for general reconstruction.

Status: mixed. Recent source-proof fallback avoids hardwiring particular
source theorem names and applies source proofs by proposition. Some
source-level constructors are shape-specific, especially for Church-encoded
logical lemmas. These are guarded and useful for the early prefix, but the
general reconstruction path must come from Vampire primitive certificates.

Status: partial. The source-command gate proves small theorems at original
Megalodon source sites, with explicit lemma arguments supported. Source-origin
metadata and classification exist. The missing part is a complete
source-context API and proof audit that proves every certificate input comes
from an original source object, approved generated fact, or approved logical
basis.

Status: recognized but not fully finished. Generated-set obligations are
classified and should be proved by reflexivity/definitional equality. The
system still needs systematic proof-term generation for all such obligations
in final E1 mode.

Requirement: solve Skolemization.

Status: improved but not solved. Vampire emits much richer Skolem contracts,

Status: directionally yes, execution still incomplete. Work has moved more

not yet central enough, and the OCaml importer remains too large.

Status: not done. There is a 100-case live certificate/source/metadata gate
and a 27-command original-source prefix gate. The requested 100-theorem
original-context native proof reconstruction suite is still absent.

## Risk Register

Risk 1: Hidden trust reappears under a new name.

The project has already seen two versions of this: explicit bridge premises
and dynamic `Known` declarations. Any new proof-term mode should include a
mechanical provenance audit over all trusted constants and known proof names.
The final result should fail if a certificate-derived implication is inserted
into the proof environment.

Risk 2: The Megalodon importer becomes a second theorem prover.

This is the central engineering risk. Some local constructive search is
acceptable for simple source-level goals, but the main proof detail must come
from Vampire. If the importer keeps growing case-specific reconstruction
logic, the project will become brittle and hard to audit.

Risk 3: Pass counts reward the wrong layer.

The broad `PASS 100` gate is useful but E4. It can hide the absence of
original-context proof composition. Reports and CI should keep E1/E2/E3/E4
labels visible and should not headline E4 as reconstruction.

Risk 4: Source names are accepted without propositions.

Name recovery is helpful for humans, but proof reconstruction must compare or
prove propositions. Two same-looking names under different binders are not the
same source fact. Source IDs, binder contexts, and semantic proposition checks
must be part of the final source-context API.

Risk 5: Skolem symbols become axioms.

Skolemization must be explained by choice/epsilon definitions or proof
contracts. Introducing Skolem functions as unconstrained global symbols would
make the exported refutation unsound relative to the original theorem.

Risk 6: AVATAR is postponed too long.

Early tests can avoid AVATAR-heavy cases, but serious Vampire proofs often use
AVATAR. The final architecture should decide whether AVATAR is lowered to
resolution-like certificates, checked through SAT proof objects, or temporarily
disabled for an E1 milestone. Avoidance is only acceptable as an explicitly
bounded milestone.

Risk 7: Reports drift from branch state.

This happened several times during rapid iteration. Future reports should
record exact heads, default harness parameters, and the most recent successful
commands. They should also say what did not run.

## Current Problems

### Problem 1: No 100-Theorem E1 Result

The final requested result is not present. There are small E1-style smoke
tests, but no 100-theorem original-context suite.

### Problem 2: Megalodon-Side Heuristic Growth

The initial broad conjunction experiment demonstrated the danger. A
shape-based source proof constructor can be useful for simple logical library
theorems, but broad heuristic proof search inside Megalodon can regress
unrelated cases and does not scale to arbitrary Vampire proofs.

The right response is not to add more heuristics. The right response is to
make Vampire print smaller, clearer proof steps and make Megalodon check them.

### Problem 3: Vampire Primitive IR Is Not Isolated

The Vampire fork emits more information than before, but the small-kernel IR
is not yet a first-class isolated object. This makes it harder to guarantee
that all macro inferences are lowered through the same trusted route.

### Problem 4: Source/Smolka Layer Is Not Cleanly Separated

Source formula linkage, definitional facts, set facts, conjecture negation,
FOOL, ENNF, CNF, and Skolemization are still intertwined with clausal replay.
The final architecture needs a separate proof-producing transformation layer.

### Problem 5: AVATAR Is Still a Large Gap

Many serious Vampire proofs use AVATAR. The current source-level bypass for
`or3E` is not a general AVATAR solution.

### Problem 6: Trust Audit Must Remain Mechanical

The July 16 dynamic-`Known` problem should remain a standing warning. A
qualifying mode should mechanically traverse the final proof and verify that
every `Known` reference comes from approved source/library/proved-definition
provenance.

### Problem 7: Source-Level Shortcuts Must Stay Guarded

The conjunction-introduction fix is useful, but it is exactly the kind of
Megalodon-side shortcut that can become dangerous if generalized too far. It
must remain narrowly guarded and covered by no-incomplete source-command
tests.

## Recommended Next Work

### Step 1: Preserve the Green Source-Command Baseline

Acceptance criteria:

- `TMPDIR=/project/tmp ./makeopt` passes;
- `LIVE_CERTIFIED_VAMPIRE_NO_INCOMPLETE_PASS 4` passes;
- `LIVE_HAMMER_PREFIX_NO_INCOMPLETE_PASS 27` passes;
- no new admission/bridge markers;
- no promotion of a slow frontier gate.

### Step 2: Move Past the Logical Prelude Carefully

After restoring the gate, the next useful source-command frontier is the
series after `or3E` in `examples/hammer/100thms_12_h.mg`:

```text
and4I  by vampire and3I.
and5I  by vampire and4I.
and6I  by vampire and5I.
and7I  by vampire and6I.
```

This block is now covered through `and7I`, and the default gate also includes
`not_or_and_demorgan`, `not_ex_all_demorgan_i`, `iffEL`, `iffER`,
`iff_refl`, `iff_sym`, `iff_trans`, `eq_i_tra`, `neq_i_sym`, `Eps_i_ex`,
`prop_ext_2`, `Subq_ref`, `Subq_tra`, and `Empty_Subq_eq`. The next observed
frontier is `Empty_eq`, which currently exposes missing Vampire-side rewrite
metadata (`u311`) rather than a source proof composition failure.

### Step 3: Define the Source-Context API

The code needs an explicit source-context abstraction, conceptually:

```ocaml
type source_proof =
  | GlobalKnown of source_id * Syntax.tm * Syntax.pf option
  | LocalHyp of source_id * int * Syntax.tm
  | Definitional of source_id * Syntax.tm * Syntax.pf
  | GeneratedSetEq of source_id * Syntax.tm * Syntax.pf
  | ConjectureNegation of source_id * Syntax.tm
  | LogicalBasis of string * Syntax.tm * Syntax.pf
```

The exact OCaml type may differ, but the proof obligations should be explicit.
This would give experts and tests a concrete way to inspect whether the final
proof is really glued to the original source.

### Step 4: Specify the Smolka Transformation Objects

Before expanding to many theorems, define the proof objects for the
source/preprocessing layer:

- source input;
- generated set equality;
- definitional unfold/fold;
- rectification/alpha-conversion;
- FOOL atom lift and exhaustiveness;
- ENNF;
- CNF projection;
- Skolemization with explicit choice witnesses;
- conjecture negation.

Each object needs:

- parent formula;
- result formula;
- binder context;
- variable/sort map;
- proof term or primitive proof recipe;
- negative tests.

### Step 5: Extract the Vampire Primitive Builder

On the Vampire side, implement a shared primitive builder for:

- instantiate;
- resolve;
- factor;
- equality resolution;
- equality factoring;
- paramodulate/superpose;
- equality flip/orientation;
- truth conflict.

Then lower frequent macros through it, starting with the highest-volume and
least controversial classes:

- unit-resulting resolution;
- demodulation/rewrite;
- subsumption resolution direct chains;
- superposition helper chains.

The output should be a certificate Megalodon can check without guessing.

### Step 6: Grow E1 Results, Not E4 Counts

The near-term result should be:

```text
E1_PASS 1
```

for a nontrivial real theorem after `xm`, with source linkage and no
admissions.

Then:

```text
E1_PASS 10
```

Then:

```text
E1_PASS 100
```

The strict 100 E4 gate should continue running as a regression check, but it
should not be optimized at the expense of E1.

## Outlook

The project is no longer at the "can we get any proof-shaped text at all"
stage. It has live Vampire invocation, rich certificate emission, Megalodon
certificate parsing, source metadata, native proof-term seeds, and small real
source-command successes. These are substantial pieces.

The project is also not yet at the "port is finished" stage. The main
remaining work is architectural:

- isolate Vampire's primitive proof object;
- separate source/Smolka transformations from the clausal kernel;
- finish original-context proof composition;
- keep the trust boundary mechanical;
- expand only after the E1 path is real.

The largest risk is continuing to grow the Megalodon-side importer as a
heuristic prover. The initially broad conjunction regression was a small but
clear example, even though it has now been narrowed and validated. The better
path is the one the audits recommended: make Vampire explain its proof in
smaller steps, then make Megalodon check those steps.

## Bottom Line

The project has made real engineering progress, but the correct status is
"promising partial reconstruction infrastructure," not "completed
Vampire-to-Megalodon proof reconstruction."

The stable committed branch now has:

- rich Vampire certificate emission;
- Megalodon certificate parsing and audits;
- strict 100-case live certificate/source/metadata evidence;
- improved equality, subsumption, superposition, and Skolem metadata;
- focused Skolem frontier progress;
- a 4-case no-incomplete source-command smoke test;
- a 27-case real hammer-prefix no-incomplete source-command gate through
  `Empty_Subq_eq`.

The branch still lacks:

- 100 original Megalodon theorem proofs;
- a clean Vampire-side primitive IR;
- a standalone source/Smolka proof-producing layer;
- full Skolemization composition;
- full AVATAR proof replay;
- a broad proof-term path free of Megalodon-side heuristics.

The next work should first finish the current `Empty_eq` original-context
frontier: compose the loaded `Empty_Subq_eq` theorem, unfolded `Subq`/`In`
definitions, oriented equality transport, and expanded Leibniz equality goal
without introducing a trusted bridge axiom. After that, the priority remains
Smolka/source transformations and moving inference detail into Vampire's
primitive certificate object. Broad Megalodon-side heuristic reconstruction
should be frozen or treated as diagnostic only.
