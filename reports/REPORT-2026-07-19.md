## Executive Summary

The target remains:

```text
Original Megalodon theorem and context
  -> THF/TPTP export
  -> Vampire proof search, <= 10 seconds per problem
  -> detailed Vampire proof certificate
  -> Megalodon native certificate parser/checker
  -> native Megalodon Syntax.pf proof term
  -> proof of the original theorem at the original theorem site
```

That target has not yet been achieved at the requested scale.

The work has moved substantially from the first approach to the current one.
The early phase produced Python-generated Megalodon proof skeletons and
placeholder-heavy scripts. Those scripts were useful because they exposed
Vampire proof structure to humans, but they were not a sound final route:
they duplicated inference reconstruction outside Vampire and outside the
Megalodon checker. The audits and user feedback correctly pushed the project
toward a Prover9/Ivy-style design:

```text
Megalodon source theorem/context
  -> THF/TPTP export with source metadata
  -> Vampire proof search
  -> Vampire-side macro detailing while exact inference data is still present
  -> Lisp-like S-expression certificate
  -> Megalodon OCaml parser plus small proof-term checker/elaborator
  -> original-context proof composition
```

The important positive facts are:

- Vampire emits a Megalodon-oriented S-expression certificate.
- Vampire emits `kernel_v1` metadata for many proof steps.
- Vampire has begun separating certificate vocabulary and primitive metadata
  construction into helper code rather than leaving every contract in the
  main exporter.
- Megalodon parses the native certificate into OCaml data structures.
- Megalodon has native `Syntax.pf` elaboration for a clausal core and several
  source/preprocessing fragments.
- Counted native proof-term paths are not allowed to introduce arbitrary
  certificate-derived `Known "vampire_*"` theorems.
- The source-context work now distinguishes global source facts, local
  hypotheses, definitions, generated facts, conjecture facts, unresolved
  facts, and `set`-generated reflexivity/conversion obligations.
- Megalodon uses its own equality/logical constants on the intended path.
  There should be no private equality layer in the final reconstruction.
- Recent work makes local source hypotheses remain explicit assumptions at
  the original-context composition boundary rather than trying to prove them
  inside the exported certificate fragment.
- Recent work reifies original-source free variables in native external
  hypotheses so that source local facts can be consumed at the right de
  Bruijn depth.
- Recent Vampire work emits richer Skolemization contracts: source/result
  formulas, child formulas, macro-edge records, branch records, introduced
  witnesses, free variables, quantified variables, parent step variables,
  parent instantiations, and branch binder instantiations.
- Recent Megalodon work registers nullary, dependent, and compact Skolem
  witness replacements as epsilon/choice definitions where this can be done
  in a fail-closed way.
- The latest committed Megalodon change makes two targeted corrections in
  the grouped Skolem/AVATAR replay. First, contract-preserved variables are
  not duplicated outside the result formula when Vampire has already printed
  them as result quantifiers. Second, grouped continuation targets are
  normalized with the witness and AVATAR split replacement table before the
  CPS candidate is checked.

The important negative facts are:

- There is no qualifying E1 100-theorem result.
- There is no committed qualifying 10-theorem original-context milestone.
- The current importer/checker remains too large and too monolithic.
- The Vampire exporter still needs a stronger typed primitive proof-object
  builder; the current `kernel_v1` metadata remains a migration format.
- The Smolka-style source/preprocessing layer is partial.
- Skolemization remains the main proof-producing transformation blocker.
- AVATAR is only partially handled and is not yet lowered to a small checked
  proof object.
- Current evidence is concentrated in focused targets and structural gates,
  not in a broad original-context proof suite.

proof-producing certificate layers, while Vampire should keep taking
responsibility for lowering its own complex inferences to a small primitive
object. Megalodon should check and elaborate that object; it should not grow
another heuristic prover.

## Evidence Classes

The reports now use evidence classes because earlier work repeatedly
overstated structural success as proof reconstruction.

E1 is the actual goal:

```text
Original-context proof reconstruction. A proof term checks inside the
original Megalodon development and proves the theorem at the original proof
site. No aby, admit, incomplete QED, bridge assumption, certificate-local
trusted theorem, or Python proof reconstruction is used.
```

E2 is exported-bound proof reconstruction:

```text
A native Megalodon proof term checks the Vampire certificate against the
exported THF/TPTP problem, but it has not yet been composed back into the
original theorem command.
```

E3 is focused proof-term evidence:

```text
A synthetic or focused live certificate exercises native Syntax.pf
elaboration for a small-kernel rule or a source/preprocessing fragment.
```

E4 is structural/integration evidence:

```text
Vampire emits certificates; Megalodon parses them, validates metadata,
validates source maps, validates trust policy, audits expected fields, and
classifies failures. This is useful engineering evidence, but it is not proof
reconstruction.
```

Under this classification:

- broad `STRICT_CERT_V1=1` runs are E4 unless they also construct and check
  native proof terms;
- earlier preprocessing pass counts that relied on dynamic `Known`
  declarations are E4 diagnostics, not E2;
- focused native `Syntax.pf` checks can be E3 or E2 depending on whether they
  are synthetic or exported-bound;
- there is no current broad E1 result.

This evidence discipline is one of the most important corrections introduced
after the audits.

## Requirements and Constraints

The project is constrained by explicit user requirements:

- Use Megalodon THF/TPTP export.
- Use Vampire over THF/TPTP, normally with `--input_syntax tptp`.
- Do not run Vampire for more than 10 seconds per problem.
- Prefer batch export, parallel Vampire runs, and parallel certificate checks.
- Use `/project/tmp` for temporary artifacts.
- Do not use `aby` in resulting scripts or proof terms. In Megalodon, `aby`
  is implemented as admission.
- Do not use `admit`.
- Do not use incomplete QED in a qualifying result.
- Assume the setting is classical; `xm` is available.
- Use Megalodon's own equality, `False`, disjunction, and other logical
  constants from the library/context rather than private replacements.
- Do not optimize for hardwired library names. The reconstruction must work
  for arbitrary Megalodon developments exported to THF.
- Move detailed proof data into Vampire where possible. Do not build a large
  uncertain Python or OCaml guessing layer to recover information Vampire
  already knows.
- Use Prover9/Ivy as the architectural model: expand complex prover
  inferences into small checkable proof objects.

The current branch follows these constraints better than the early work, but
not yet completely. In particular, the native Megalodon side is still too
large and carries too much proof reconstruction logic.

## Chronology of the Approach

### Initial Python/Skeleton Phase

The first implementation route parsed Vampire proof output outside Vampire
and generated Megalodon proof skeletons. This work produced files with
`claim` blocks and admissions. It was valuable because it gave a human an
inspectable approximation of the proof and exposed which source names,
definitions, and inference classes appeared frequently.

However, this route was not suitable as the final architecture:

- it did not use Vampire's internal typed inference data;
- it guessed too much from rendered proof text;
- it encouraged Megalodon-side heuristics;
- it could produce useful-looking files that were not real reconstruction;
- it could not satisfy the no-`aby`/no-`admit` requirement.

The user explicitly objected to this "all or nothing" and slow path. The
intermediate skeletons helped clarify what a human would need, but they are
now diagnostic artifacts, not the qualifying route.

### Batch and Parallel Testing Phase

The next correction was test discipline. Instead of repeatedly trying slow
Vampire runs one at a time, the workflow moved toward:

- export many problems once;
- run Vampire in parallel over the exported THF problems;
- use a 10-second Vampire timeout;
- cache proof outputs and classify which problems are Vampire-solvable;
- iterate on the solvable subset;
- check certificates in parallel;
- store temporary outputs under `/project/tmp`.

This is still the right test shape. The current focused gates use `TARGETS`,
`JOBS`, `MEGALODON_VAMPIRE_TIMEOUT=10`, and `/project/tmp`. Broad runs should
be used carefully because they are expensive and can obscure the immediate
proof-term blocker.

### Trust Reset

The audits identified the central trust problem. Some early native
preprocessing paths would construct a proposition such as "parent implies
result", insert it into Megalodon's known-theorem table under a generated
name, and then apply that generated `Known`. This made `check_propofpf`
succeed, but only because the checker had been given exactly the theorem the
certificate needed.

That is not proof reconstruction. It is a hidden bridge axiom.

The current counted path is supposed to reject certificate-derived dynamic
`Known` declarations. The old behavior is retained only as a structural
diagnostic mode. This correction is crucial and should remain non-negotiable.

### Prover9/Ivy Pivot

The Prover9/Ivy analysis changed the direction. The important lesson is that
the theorem prover should explain its proof while it still has exact
inference data. The checker should not recover missing substitutions,
rewrite positions, selected literals, orientations, or variable sorts by
heuristic parsing of pretty-printed text.

For this project, the intended analogue is:

```text
Vampire internal proof DAG
  -> Vampire-side macro expansion / primitive detailing
  -> small S-expression certificate
  -> Megalodon native checker/elaborator
```

This is only partially implemented. Vampire emits useful metadata and has
helper abstractions for schema/rule vocabulary, but the exporter is not yet a
clean primitive proof-object generator. Megalodon checks more than before, but
the checker is still too entangled with old textual replay and transformation
logic.

### Source and Smolka Focus

The more recent work shifted to the most important missing pieces:

- linking certificate inputs back to original Megalodon lemmas, definitions,
  local hypotheses, and conjectures;
- treating `set`-generated equalities as generated reflexivity/conversion
  obligations rather than missing source claims;
- proving source-to-clause transformations in a Smolka-style layer;
- handling Skolemization by conservative epsilon/choice witness definitions;
- composing the exported refutation back into the original theorem.

This is the right focus. The current hard failures are no longer basic proof
text parsing failures; they are real proof-term alignment problems at the
source/preprocessing boundary.

The key practical change is that Skolemization is no longer represented only
as a rendered formula transition. Vampire now emits enough metadata to say
which witnesses were introduced, where the source/result children are, what
the branch structure is, which variables survive into the parent/result
contexts, and how branch binders should be instantiated.

That is exactly the kind of information Megalodon should receive from
Vampire. Vampire knows these details. Megalodon should not be trying to
reconstruct them by inspecting a printed formula.

The remaining Vampire-side gap is that this metadata is not yet a final
primitive proof object. It is still a migration contract layered onto broad
certificate steps. For clausal inferences, the desired object should look
closer to Ivy: small steps with exact parent references, literal selections,
substitutions, rewrite positions, equality orientation, and variable sorts.
For preprocessing, the desired object should identify the source
transformation and its typed parameters, not just the before/after formulas.

The next Vampire-side direction should be:

- define a small primitive certificate type in C++;
- build that type before printing;
- make unsupported primitive names impossible to emit accidentally;
- lower frequent Vampire macros into that type while exact data is available;
- print that type as the S-expression consumed by Megalodon;
- retain legacy fields only as migration diagnostics.

The source-variable and local-hypothesis changes matter because they move
source gluing toward the right boundary:

- global facts should be resolved from the loaded Megalodon context as
  `Known hash` proofs;
- local hypotheses should remain local proof assumptions and be applied during
  original-context composition;
- generated `set` facts should become generated proof obligations, typically
  reflexivity/conversion;
- conjecture negation should be introduced by the refutation wrapper rather
  than trusted as an external theorem.

This is a material improvement over earlier attempts that tried to prove
local source facts inside the exported Vampire fragment.

The Skolem witness work also matters:

- nullary witnesses can be represented by epsilon/choice definitions;
- dependent witnesses such as `sK3 x` can now be registered as lambda
  replacements when their dependency argument types are known;
- compact named-body witness cases now register their epsilon replacements
  instead of only substituting them locally;
- grouped Skolem/AVATAR continuation targets are now normalized using the
  registered witness replacements and AVATAR split replacements before the
  CPS candidate is checked;
- result-formula quantifier metadata is used to avoid duplicating
  contract-preserved variables that already appear as explicit result
  quantifiers;
- all of this remains fail-closed because the final proof term is checked.

This does not solve the hard target, but it changes the failure from "missing
replacement for all introduced witnesses" to a more precise branch-local
dependent witness and alias-normalization problem inside the grouped
Skolem/AVATAR continuation.

## Source Linking Status

The project is significantly closer to linking certificates back to original
Megalodon source facts than it was earlier, but the work is incomplete.

Implemented or partially implemented:

- source labels are preserved through export and certificate import;
- source origins are parsed and classified;
- source-map aliases cover raw, normalized, and hash-prefixed names in more
  places;
- hash-backed global facts can be checked against the loaded Megalodon
  signature/context;
- source local facts are now treated as local assumptions rather than global
  known facts;
- the native proof path can carry external source proof assumptions;
- some generated facts are recognized separately from user lemmas;
- `set`-generated equalities are understood as generated reflexivity or
  conversion obligations in the intended design;
- focused diagnostics show source local hypotheses being consumed at the
  original-context boundary.

Still missing or partial:

- there is no completed E1 source-context composer for a broad suite;
- not every `formula_input` is supplied by a real original-source proof;
- not every `formula_term_input` is supplied by a generated proof;
- local definitions are not fully handled as unfolding/conversion proof
  objects;
- set-generated facts need a committed proof-producing path rather than just
  classification;
- unresolved source facts must become hard failures for E1 gates;
- the final proof returned from the certificate checker is not yet routinely
  inserted at the exact original theorem command site;
- source demangling is useful for diagnostics but should not be trusted as
  proof resolution unless backed by stable source metadata.

The current state of linking is therefore: source categories and some proof
supply mechanisms exist, and focused proof-term examples use them, but this
is not yet a complete original Megalodon theorem reconstruction layer.

## Set-Generated Facts

The user pointed out an important case: some TPTP axioms come from the
Megalodon `set` command and do not correspond to user-written claims. These
should not be expected to resolve to original source lemmas. They should be
proved explicitly in Megalodon, usually by reflexivity or definitional
conversion.

The correct classification is:

```text
source fact from user theorem/lemma      -> resolve to original proof
source local hypothesis                  -> consume as local assumption
source definition                         -> prove by unfolding/conversion
set-generated equality                    -> prove by reflexivity/conversion
negated conjecture                        -> introduced by refutation wrapper
certificate-generated preprocessing fact  -> prove by Smolka/source layer
```

The current branch has metadata/classification for this distinction, but the
generated proof supply is not complete. For E1, a `set` fact must not be a
trusted axiom merely because it is in the TPTP file. It must produce a
Megalodon proof term of the equality in the loaded context.

## Equality Status

There should not be a private equality in the final proof reconstruction.
Earlier experiments used wrappers and normalized representations that could
look like a separate equality layer. That is not the intended final state.

The intended rule is:

- use Megalodon's equality;
- preserve polymorphic type information;
- treat TPTP equality wrappers as parsed/exported syntax that maps back to
  Megalodon's equality;
- prove equality transformations using Megalodon equality rules and
  conversion;
- do not introduce a new trusted equality predicate.

Some certificate displays still show terms like:

```text
((eq prop) A B)
```

This is the internal term representation of equality at a type, not a desired
new object logic. The reviewer should check that any counted proof path maps
this to Megalodon's real equality and that no private equality theorem is
trusted as a shortcut.

## Skolemization Status

Skolemization is currently the central blocker.

What works or has focused evidence:

- direct nullary existential Skolemization can be reconstructed with a
  conservative epsilon/choice definition in narrow cases;
- source/result formulas and introduced witnesses are parsed from Vampire's
  richer metadata;
- parent step variables and instantiations are now emitted by Vampire;
- branch binder instantiations are now emitted by Vampire;
- Megalodon registers witness replacements for nullary, dependent, and compact
  cases when the scope and types can be checked;
- the checker rejects replacement candidates that do not type-check or prove
  the required proposition.

What remains open:

- dependent Skolem functions in branching transformations;
- multiple simultaneous witnesses;
- witness definitions whose dependency binders must be aligned across
  source, branch, and result contexts;
- substitution of witness definitions through AVATAR split continuations;
- proof-term opening after witness replacement;
- avoiding stale certificate-local choice witnesses in stored formulas;
- making the whole transformation a small explicit Smolka-style proof object
  rather than a large Megalodon-side replay procedure.

The latest hard diagnostic is for:

```text
examples/hammer/100thms_12_h.mg:11925:125
```

After the latest commits, the debug trace no longer reports the earlier
duplicate result-context binders for the main `u271`/`u273` Skolem steps.
It now reports two more specific problems:

```text
u273: native preprocess grouped Skolem CPS failed candidate group witness:
  introduced term symbol sK1 in term #sK1 ...
u273: native preprocess grouped Skolem CPS target still mentions group witness:
  introduced term symbol sK1 in term #sK1 ...
native preprocess final refutation first bad application:
  proof argument mismatch; expected SNo; actual #SNo
```

The registered witness table covers the witnesses that the current direct and
compact proof paths can justify, for example `sK0` and `sK2` in the latest
trace. The remaining raw `sK1` is a branch-local dependent witness under a
branch binder, not a library-specific symbol and not a nullary Skolem
constant. The checker currently knows how to use it as a local CPS fallback
inside the branch, but the replacement is not exported to the grouped
continuation target as a globally checked lambda/epsilon definition.

There is also a related alias-normalization issue: some formulas still
distinguish raw source symbols such as `SNo` from hash-prefixed or
certificate-local aliases such as `#SNo` at the final proof application
boundary. That must be solved by stable source/symbol metadata and checked
normalization, not by hardwired library names.

This is a useful failure. It says the next step should not be another
string-level Skolem replacement. The next step should specify the branch proof
object:

- what assumptions are opened at each branch;
- which variables are term binders and which are proof binders;
- which witness definitions are active;
- how branch-local Skolem witnesses are abstracted;
- how AVATAR split assumptions are carried;
- what exact proposition each continuation consumes.

Once that is explicit, the Megalodon checker can either accept the proof term
or reject a small local rule. At present the proof term is too large and the
debugging happens too late.

## Smolka-Style Transformations

The Smolka-style transformation layer is broader than Skolemization. It is
the layer that justifies the clauses consumed by the clausal kernel from the
original Megalodon formulas.

The transformations include:

- source input;
- definitional input;
- `set`-generated equality/reflexivity input;
- conjecture negation;
- rectification;
- FOOL/boolean normalization;
- ENNF;
- CNF projection;
- variable instantiation and renaming;
- Skolemization;
- predicate definitions and folds;
- selected AVATAR preprocessing facts.

The current branch has partial proof-producing support for some of these:
source entry, several checked formula transformations, some predicate
definition/fold shapes, and narrow Skolem cases. It does not have a complete
standalone Smolka checker.

The key architectural point is that Smolka-style transformations should not
be hidden as clausal kernel rules. The clausal kernel should start from
clauses already justified by the source/preprocessing layer. Conversely, the
source/preprocessing layer should not become a broad heuristic prover. It
should consume explicit transformation records from Vampire and produce
Megalodon proof terms by a small number of reviewed logical principles:

- implication introduction/application;
- universal introduction/application;
- existential elimination through classical choice;
- equality reflexivity/conversion;
- definition unfolding/folding;
- classical negation principles including `xm` where needed;
- boolean/FOOL normalization lemmas from Megalodon's logic.

The current work is aligned with this direction in intent, especially by
moving Skolem data into Vampire, but the implementation is not yet clean
enough. The review should focus on whether each new Megalodon-side patch
shrinks the uncertainty in this transformation layer or merely adds another
special case.

## Clausal Kernel Status

The intended clausal kernel is close to the Ivy model. A reasonable stable
core is:

- input boundary from source/preprocessing layer;
- instantiate;
- alpha/rename;
- literal flip/orientation;
- resolve;
- factor;
- equality resolution;
- equality factoring;
- paramodulation/superposition;
- contradiction/empty clause marker.

Possible exclusions:

- `truth_conflict` may belong in FOOL/preprocessing rather than the clausal
  kernel;
- AVATAR should probably not be part of the first clausal kernel and should
  either lower to clauses plus SAT/RUP evidence or have its own tiny checked
  layer;
- large Vampire macros should lower to the primitive kernel before Megalodon
  sees them as proof-producing steps.

The current clausal proof-term seed is genuine but still limited. Synthetic
and focused fixtures can check native `Syntax.pf` terms for several clausal
rules. Real hammer certificates still frequently stop in
source/preprocessing before a broad clausal-kernel run can become qualifying
proof reconstruction.

The next kernel milestone should not be "add every Vampire inference to the
Megalodon OCaml importer." It should be "make Vampire emit a primitive object
for the frequent real inferences and make Megalodon check that small object."

## AVATAR Status

AVATAR has partial support:

- Vampire emits AVATAR-related metadata in the certificate;
- Megalodon has focused support for split definitions/components in some
  native proof-term paths;
- grouped Skolem/AVATAR replacement candidates are attempted in the current

## Why the Current Work Is Not Hardwired to One Library

The user has repeatedly raised the risk that the implementation might become
optimized for this particular Megalodon library. That risk is real and should
be watched, but the current intended path is not to hardwire library facts.

General pieces:

- source resolution uses exported source metadata and hashes, not theorem
  names alone;
- symbol aliases are used to relate TPTP names, normalized names, and
  hash-prefixed names;
- Skolem witness detection uses Vampire's introduced-witness metadata;
- witness replacements are typed from certificate/source contexts;
- generated `set` equalities are classified by origin, not by theorem name;
- focused failures are used as representatives of proof-shape classes, not as
  name-specific rewrite rules.

Places to keep auditing:

- any code branch that mentions a concrete library symbol such as `famunion`
  would be suspect unless it is only in a fixture or diagnostic;
- source demangling should remain diagnostic/resolution support, not a trusted
  proof rule;
- equality/logical constants should come from Megalodon's context, not a
  private prelude;
- Skolem fixes should depend on introduced-witness contracts, not on `sK1`
  naming patterns except as parsed certificate identifiers.

The current hard target includes symbols such as `SNo`, `eps`, `In`,
`omega`, and ordinal successors, but the implementation changes around
witness replacement are not specific to those names. They operate over the
certificate's introduced witness terms and their typed dependencies.

## Lisp and OCaml Status

The concern is not that OCaml is used. Megalodon is implemented in OCaml and

## Current Risks

### Risk 1: Megalodon-Side Reconstruction Creep

The biggest implementation risk is that every hard Vampire inference becomes
a new large Megalodon-side reconstruction procedure. This would repeat the
earlier mistake in OCaml instead of Python.

Mitigation:

- require Vampire to emit exact typed primitive data;
- reject proof-producing paths that guess missing substitutions or binder
  orders;
- isolate the Megalodon checker modules;
- add a rule that every new proof-producing inference must have a documented
  certificate object.

### Risk 2: Misclassified Evidence

Structural certificate success is valuable but can be mistaken for proof
reconstruction.

Mitigation:

- keep E1/E2/E3/E4 labels in reports and harness outputs;
- require proof-term construction and Megalodon checking for E1/E2;
- audit all `Known` uses in counted proofs.

### Risk 3: Hardwired Library Behavior

Focused work on `examples/hammer/100thms_12_h.mg` may accidentally encode
library-specific names.

Mitigation:

- use representative failures only to identify proof-shape classes;
- make rules depend on certificate metadata, types, and source origins;
- run against multiple source areas once a new rule passes the focused
  target;
- keep a review grep for concrete library names in proof-producing code.

### Risk 4: Skolemization Becomes Too Large

Skolemization can become a complex standalone prover if handled by recursive
formula guessing.

Mitigation:

- specify a Skolem proof object with branch contracts;
- make Vampire emit exact binder, witness, and substitution data;
- use Megalodon epsilon/choice definitions only under checked scope;
- split Skolemization into smaller proof obligations if necessary.

### Risk 5: AVATAR Is Deferred Too Long

Many real Vampire proofs use AVATAR. If AVATAR remains only partially handled,
the system may pass small examples but fail on realistic proofs.

Mitigation:

- decide whether AVATAR lowers to ordinary clauses plus SAT/RUP evidence or
  to a small separate AVATAR kernel;
- avoid mixing AVATAR split assumptions implicitly into Skolem continuations;
- add focused AVATAR fixtures independent of Skolemization.

## What the Expert Should Review

The expert should focus on these questions.

1. Is the source/preprocessing versus clausal-kernel boundary correct?

The current recommendation is yes: source/Smolka transformations should
justify clauses before the clausal kernel starts. The clausal kernel should
not absorb all preprocessing rules.

2. Should Skolemization be handled as a Megalodon-side transformation checker
or lowered further by Vampire?

The current recommendation is both, with a clear boundary: Vampire emits the
exact branch/witness object, Megalodon checks it using choice/epsilon and
proof terms. Megalodon should not infer the object.

3. How should AVATAR be certified?

This remains an open architectural decision. The likely choices are
SAT/RUP-style evidence or a tiny dedicated AVATAR proof layer. It should not
remain an implicit large macro.

4. Is the current OCaml checker too large to audit?

Yes. It is functional enough for focused progress but should be split. The
audit's suggested modules remain appropriate:

- `vampire_certificate_source.ml`
- `vampire_kernel_syntax.ml`
- `vampire_kernel_check.ml`
- `vampire_kernel_elab.ml`
- `vampire_preprocess_smolka.ml`
- `vampire_preprocess_skolem.ml`
- `vampire_original_context.ml`

5. What should count as success in the next review?

The next convincing milestone is not another structural pass count. It is a
small number of original-context proofs that are fully checked without
admissions. Ten is the right next target before 100.

## Detailed Current Diagnosis

The current hard failure gives a concrete illustration of where the system
stands.

At `11925:125`, Vampire produces a proof that includes Skolem and AVATAR
structure. Megalodon can parse the certificate and resolve enough source
context to reach the native refutation candidate. It can register some
witnesses as epsilon/choice definitions. It can verify that the candidate is
not yet valid. That is the right failure mode.

The failure says:

```text
Proof term for an implication applied to a proof term for the wrong proposition
```

This means the checker is no longer stopped by a missing source name or by a
simple untyped Skolem symbol. Instead, an already-built proof term has the
wrong proposition at a branch application point. The proof context contains
both large branch formulas and smaller AVATAR predicate assumptions. The
generated continuation uses the smaller proof where the larger branch
premise is expected.

This points to a design gap:

- the branch proof object does not explicitly say which proof variable proves
  which branch proposition;
- the replacement pass cannot safely rewrite witnesses through that branch
  proof without knowing the proposition contract;
- AVATAR split assumptions and Skolem branch assumptions are being composed
  too implicitly.

The next implementation unit should be a small, explicit representation of
branch proof contexts. It should be derived from Vampire's emitted branch
contracts and checked in Megalodon before proof-term construction proceeds.

## Appendix F: Reviewer Checklist

The expert can use this checklist to assess the direction.

- Does every counted proof avoid `aby`, `admit`, and incomplete QED?
- Does every counted proof avoid certificate-derived dynamic `Known`?
- Does every source input resolve to an original or generated Megalodon proof?
- Are `set` facts proved by reflexivity/conversion rather than trusted?
- Is equality Megalodon's equality?
- Is classical reasoning explicit and based on available principles such as
  `xm`?
- Does Vampire emit exact substitutions, variable sorts, branch binders, and
  witness information?
- Does Megalodon check a small object rather than recover missing data?
- Are AVATAR assumptions explicitly represented?
- Are pass counts labeled E1/E2/E3/E4?
- Is there a committed original-context gate?
- Are temporary artifacts under `/project/tmp`?

## Appendix G: Bottom Line

The project is not done. It is now closer to the right proof architecture than
the early work was, but it still needs a decisive implementation step:
turn the current Skolem/AVATAR continuation diagnostics into a small explicit
proof object emitted by Vampire and checked by Megalodon, then use that to
complete original-context reconstruction for a small theorem set before
attempting the requested 100-theorem result.
