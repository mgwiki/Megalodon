This report summarizes the state of the Vampire-to-Megalodon proof
reconstruction project for expert review. It takes into account the previous
daily reports, the audits and audit responses, the Prover9/Ivy analysis, the
small-kernel design documents, the Smolka-style transformation discussion, and
the current local implementation state on `vampire/megalodon5`.

The report is deliberately conservative. The original goal has not been
finished. The project now has substantially better architecture, much richer
Vampire-side certificates, and meaningful focused proof-term evidence, but it
does not yet have a 100-theorem original-context reconstruction suite.

## Executive Summary

The target remains:

```text
Given a theorem in an original Megalodon development, export the theorem and
its relevant context as a THF/TPTP problem, let Vampire solve it with a
per-problem timeout of at most 10 seconds, emit a detailed proof certificate,
import that certificate into Megalodon, elaborate it to native Megalodon proof
terms, and check a proof of the original theorem in the original context.
```

That target is not yet achieved.

There is no broad suite of 100 original Megalodon theorems reconstructed from
Vampire proofs with all required restrictions:

- no `aby`;
- no `admit`;
- no `-allowincompleteqed`;
- no hidden bridge premise;
- no certificate-derived trusted theorem;
- no Python proof-producing reconstruction step;
- no library-specific name hardwire;
- no unverified mapping from exported THF axioms back to the original
  Megalodon context.

The project has nevertheless moved materially closer to the right shape. The
early work grew a Python-oriented translator and Megalodon script skeletons.
That was useful for exploration, but it was the wrong final trust boundary.
The audits correctly pushed the project toward a Prover9/Ivy-style design:

```text
Megalodon theorem and context
  -> THF/TPTP export with source metadata
  -> Vampire proof search
  -> Vampire-side detailing while Vampire still has exact proof data
  -> small certificate language
  -> Megalodon checker and Syntax.pf elaborator
  -> proof of the original Megalodon theorem
```

The current branch has partially implemented this pivot:

- Vampire emits a native Megalodon-oriented S-expression certificate.
- Vampire emits a growing `kernel_v1` metadata vocabulary.
- Vampire now exposes much more exact Skolemization data: macro edges, branch
  contracts, introduced witnesses, parent instantiations, branch binders,
  free variables, and quantifier metadata.
- Megalodon parses this data into typed OCaml structures.
- Megalodon constructs native `Syntax.pf` proof terms for the clausal core and
  for important preprocessing fragments.
- Counted native proof paths reject the old dynamic certificate-derived
  `Known` theorem escape unless an explicit diagnostic environment variable
  enables transitional behavior.
- The source-context layer now knows about global facts, local hypotheses,
  definitions, generated facts, conjecture facts, unresolved facts, and
  `set`-command equalities handled by reflexivity or conversion.
- Focused original-site proof reconstruction works for at least one live
  target, notably `examples/hammer/100thms_12_h.mg:10654:21`.

The most important remaining gaps are:

- no qualifying 100-theorem original-context suite;
- no committed qualifying 10-theorem original-context milestone;
- no complete standalone primitive IR comparable to Ivy proof objects;
- no isolated Megalodon kernel checker/elaborator module;
- no complete source/preprocessing proof-producing layer;
- no complete Smolka-style transformation pipeline;
- no complete general Skolemization proof reconstruction;
- no complete composition from exported-source refutation back to arbitrary
  original Megalodon theorem commands.

The current hard frontier is no longer basic certificate parsing or basic
proof-output plumbing. The representative difficult target is
`11925:125` in `examples/hammer/100thms_12_h.mg`. That target reaches deep
into final theorem-site reconstruction, but still fails in Skolem CPS replay:
branch-local choice witnesses such as Megalodon's `Eps_i` or `Eps_set_prop`
are not always transported to the corresponding certificate-local Skolem
witnesses such as `sK1`, `sK2`, or `sK3` in the exact branch context where the
proof is checked.

Recent commits have moved that failure forward:

- `0c0877f Use Skolem parent instantiations in formula proof` uses Vampire's
  explicit parent-instantiation contracts rather than dropping parent
  variables that are no longer syntactically visible.
- `dfc0812 Transport unchanged Skolem disjunction branches` repairs one
  branch of Skolem disjunction replay by transporting unchanged no-existential
  branches through the recorded source/result branch formulas.
- `ea04f2c78 Emit branch binder instantiation contracts` makes Vampire emit
  missing branch binder instantiation data, which reduces Megalodon-side
  guessing.

## Evidence Classes

The project previously used the word "pass" too broadly. The audits repeatedly
warned that structural validation, proof script generation, native AST
checking, and original-context theorem reconstruction must be reported
separately. The current reports use the following evidence classes.

### E1: Original-Context Reconstruction

This is the actual goal.

```text
The proof checks at the original Megalodon theorem site, using the original
global lemmas, local hypotheses, definitions, generated facts, and conjecture
binding. It uses no aby, no admit, no incomplete QED, no bridge premise, no
certificate-derived Known proposition, and no Python proof-producing step.
```

Current status:

- There is no broad E1 suite.
- There is at least one focused E1-style success, `10654:21`.
- The representative difficult target `11925:125` still fails.
- The project should not claim completion until many original theorem sites
  pass this exact gate.

### E2: Exported-THF-Bound Closed Reconstruction

This is useful but not final.

```text
A native Megalodon proof term checks a Vampire certificate against the
exported THF problem, but the result has not yet been composed back into the
original theorem command and its live source context.
```

Current status:

- There is meaningful focused evidence in this class.
- It is not enough to satisfy the user's goal.
- E2 results are good regression tests for the certificate checker and
  elaborator, but they do not prove that source-context gluing is solved.

### E3: Focused Proof-Term Evidence

This covers synthetic or focused live cases that exercise a particular native
proof-term path.

Current status:

- The clausal core has real `Syntax.pf` evidence.
- Focused fixtures exercise resolution, factoring, equality symmetry,
  equality resolution, paramodulation, substitution, and selected
  preprocessing transformations.
- The Skolem CPS work is increasingly represented by focused live tests rather
  than only synthetic examples.

### E4: Structural and Integration Evidence

This is certificate generation, parsing, metadata validation, source-map
validation, or broad strict runs that do not construct and check final proof
terms.

Current status:

- E4 evidence is strong.
- Broad certificate generation and validation are useful.
- E4 must not be reported as proof reconstruction.

This evidence separation is now one of the project's most important process
improvements.

## Constraints and Policy Decisions

The following constraints are active project requirements.

- Use THF/TPTP exports from Megalodon.
- Use Vampire with `--input_syntax tptp`.
- Do not run Vampire for more than 10 seconds per problem.
- Prefer batch export and parallel runs for broad testing.
- Use `/project/tmp` for generated or temporary artifacts.
- For focused iteration, avoid broad expensive tests unless a real milestone
  justifies them.
- Use parallel target gates, typically with 10 to 20 workers when many
  independent problems are available.
- Do not use `aby` in final proof scripts or final proof terms. In Megalodon,
  `aby` is implemented as admission.
- Do not use `admit` or incomplete QED in qualifying results.
- Assume classical logic. `xm` is available.
- Use Megalodon's existing equality and logic constants, including equality,
  `False`, disjunction, and classical principles. Do not invent private
  duplicate logical constants in the final proof path.
- Do not hardwire names from the current library such as individual theorem
  names, `famunion`, or benchmark-specific Skolem names.
- Get exact proof data from Vampire whenever possible. Vampire knows the
  selected literals, substitutions, positions, directions, sorts, generated
  symbols, parent clauses, and result clauses. Megalodon should check that
  data, not rediscover it by broad search.
- Treat TPTP axioms generated from Megalodon `set` commands as generated
  definitional/reflexivity obligations when appropriate. They need not
  correspond to existing source claims.

These constraints rule out a final architecture based on Python guessing,
library-specific name recovery, broad OCaml heuristics, or hidden trusted
theorems introduced from certificate step IDs.

## Audit-Driven Corrections

The July 12 report and audit captured an early prototype state. At that point
the system had useful examples and a proof skeleton generator, but it was too
dependent on Python translation and generated Megalodon scripts with admits or
claim skeletons.

The July 13 and July 14 reports added source-linking and richer certificate
parsing. The audits observed that strict certificate parsing is not the same as
proof checking. They also warned that source-name recovery is only meaningful
if the proposition attached to the source name is semantically checked against
the original Megalodon context.

The July 15 and July 16 audits were the decisive course correction. They
accepted the native `Syntax.pf` direction but rejected a hidden trust loophole:
the importer sometimes constructed the implication it needed, added it to a
dynamic known-theorem table, and then built `Known "vampire_*"` applications.
That made proof-term checking pass for the wrong reason. The proof was checked
only because the desired transformation had just been declared known.

The branch now treats that as non-qualifying. The counted native path must not
install arbitrary certificate-derived theorems. Transitional knowns may still
exist behind explicit diagnostic flags or in legacy paths, but they do not
count toward reconstruction milestones.

The July 16 audit also recommended a Prover9/Ivy-style path:

- do proof detailing on the Vampire side;
- define a small fixed certificate calculus;
- check that calculus in Megalodon;
- keep source/preprocessing transformations proof-producing and separate;
- stop the uncontrolled growth of the broad importer.

The current implementation has followed that recommendation partially but not
fully. The important success is that Vampire now emits much richer exact
metadata, especially for Skolemization. The remaining failure is that there is
still no fully isolated primitive proof-object layer, and much logic still
lives in large monolithic files.

## Audit Reconciliation

This section states directly how the current work stands against the previous
expert audits. It is included because the most useful next review is not a
line-by-line audit of pass counts; it is a judgment about whether the project
is now converging on the right architecture.

The July 12 audit said the project had become three projects at once: a
target-specific Vampire exporter, a Python reconstruction engine, and a
Megalodon-side tactic/skeleton generator. That criticism was correct. The
current branch has stopped treating the Python proof producer as a qualifying
path. Python remains useful for batch orchestration and statistics, but no
reported final proof should depend on Python-generated proof obligations,
library-specific searches, or Python-discovered proof steps. The old Python
scripts are still in the tree and remain useful as historical diagnostics.
They are not gone, so the quarantine is process-level rather than physical.
That is acceptable short term, but not ideal.

The July 13 audit identified the most serious early soundness-accounting bug:
derived Vampire clauses could be introduced as theorem assumptions. That has
been fixed in the native certificate accounting. A result cannot be counted as
closed if it contains bridge assumptions or derived premises. This matters
because the Megalodon kernel checking a theorem with an extra premise is not a
kernel unsoundness bug, but it is a reconstruction failure. Current reporting
keeps that distinction.

The July 14 audit said that "strict" certificate validation was not proof
reconstruction and that source names had to be proposition-linked, not merely
label-linked. The source-map path has been strengthened: supported exported
formulas are parsed and structurally compared with the certificate/source
binding, and unsupported syntax fails closed when formula matching is required.
There is also specific handling for generated facts, including `set`-command
equalities that have no existing source claim but should be discharged by
reflexivity or conversion. This still does not complete original-context
proof reconstruction, because resolving a source formula is only the first
part of building a proof in the original theorem site.

The July 15 audit accepted the first meaningful closed proof-reconstruction
evidence, but warned that the broad OCaml importer was growing into another
large theorem prover. That warning remains valid. The current work has added
important native proof-term machinery, but most of it still lives in
`vampire_cert_v1.ml`. The planned extraction into a small checker,
source-context module, preprocessing module, and legacy orchestration shell
has not yet happened. The report therefore treats the recent Skolem work as
useful frontier work, not as evidence that the architecture is finished.

The July 16 audit found that a native preprocessing path was injecting
certificate-derived `Known` theorems and then checking proofs against those
newly installed facts. That is now classified as non-qualifying. The current
counted path must reject arbitrary `vampire_*` known propositions, except for
the fixed reviewed logical basis such as classical principles and typed
choice-style lemmas that are part of Megalodon's intended proof environment.
This correction is essential. Without it, a proof term may typecheck while
the substantive Vampire transformation is still assumed.

The design documents written after those audits point toward a Prover9/Ivy
model. The current branch is only partially there. It has richer Vampire
metadata and a native Megalodon proof-term checker for important fragments,
but it does not yet have a separate Vampire primitive-expansion pass that
lowers all common macro inferences into a small proof-object calculus. The
expert should therefore regard the current state as a better prototype and a
source of regression tests, not as the final architecture.

The most important unresolved audit issue is not one bug. It is the risk that
each hard Vampire inference becomes a new large Megalodon-side reconstruction
procedure. The current Skolemization work is close to that boundary. It is
acceptable only because it is being driven by newly emitted Vampire contracts:
branch binders, parent instantiations, child formulas, free-variable counts,
and introduced witness metadata. The more that future work can move these
macro explanations into Vampire-side primitive certificate records, the safer
the project becomes.

## Current Architecture

The current pipeline is:

```text
Original Megalodon file
  -> hammer/export command emits THF/TPTP and source maps
  -> Vampire proves the THF problem
  -> Vampire emits a Megalodon certificate
  -> Megalodon parses certificate S-expressions
  -> source/context audit resolves exported inputs
  -> native proof-term elaboration reconstructs proof fragments
  -> final theorem-site replay attempts to prove the live goal
```

There are three major implementation surfaces.

### Vampire Certificate Emission

Vampire-side work is mainly in:

```text
/project/vampire-leancheck/Shell/MegalodonChecker/MegalodonChecker.cpp
```

and newer syntax/boundary files around the Megalodon certificate printer.

Vampire now emits:

- proof-unit identifiers;
- parent links;
- source identities;
- TPTP axiom names;
- result formulas;
- macro-edge information;
- Skolem child formulas;
- Skolem branch contracts;
- introduced witness symbols;
- witness dependencies;
- top-level quantifier metadata;
- free-variable metadata;
- parent-instantiation contracts;
- branch binder instantiation contracts.

This is a major improvement over relying on textual TPTP proof output alone.
It means Megalodon can consume exact data that Vampire already knows.

The remaining Vampire-side weakness is architectural. The data is still mostly
metadata attached to a broad exporter. It is not yet a normalized sequence of
small primitive steps analogous to Prover9's Ivy proof objects. The next
Vampire-side step should be a real primitive expansion pass with a single
printer, not more ad hoc metadata around individual macro failures.

### Megalodon Certificate Parser and Checker

Megalodon-side work is mainly in:

```text
/project/Megalodon/src/vampire_cert_v1.ml
/project/Megalodon/src/vampire_kernel_syntax.ml
/project/Megalodon/src/megalodon.ml
```

The importer parses the S-expression certificate and elaborates pieces into
native `Syntax.tm` and `Syntax.pf` values. The clausal core has a genuine
proof-term checking path. Preprocessing fragments are increasingly native but
are not complete.

The current problem is size and boundary control. `vampire_cert_v1.ml` has
grown into a large module containing parsing, source checks, legacy textual
emission, native proof construction, transformation replay, diagnostics, and
trust policy. The project needs extraction into smaller modules before adding
many more inference classes.

The intended module split is:

```text
vampire_kernel_syntax.ml     certificate datatypes
vampire_kernel_check.ml      small primitive checker
vampire_kernel_elab.ml       Syntax.pf elaboration
vampire_source_context.ml    original-context resolution
vampire_preprocess.ml        Smolka/source transformations
vampire_cert_v1.ml           legacy parser/orchestration shell
```

This split is not yet complete.

### Source-Context Glue

The source-context work is where exported THF proof reconstruction becomes
original Megalodon theorem reconstruction.

Current source facts may be:

- `GlobalKnown`: a theorem or lemma already in the Megalodon context;
- `LocalHyp`: a local hypothesis exported with the problem;
- `Definitional`: a source definition usable by conversion;
- `Generated`: a generated fact such as a `set` equality obligation;
- `Conjecture`: the exported negated theorem goal;
- `Unresolved`: a source item that has not yet been connected safely.

The current implementation can:

- recover many exported source names;
- resolve many global facts to live `Known` hashes;
- bind local source hypotheses into native certificate checking;
- link source-map definitions not only to exported names but also to live
  Megalodon symbol hashes;
- treat some generated `set` equalities as reflexivity/conversion facts;
- continue guided quantified search after the exported conjecture target has
  matched the live goal.

This is real progress, but not completion. The source-context layer still does
not prove arbitrary exported refutations back into arbitrary original theorem
commands. The final theorem-site replay can find the right target and still
fail because the proof term has not been transported through all necessary
binders, definitions, and Skolem/choice transformations.

### Branch Binder Instantiation Contracts in Vampire

Vampire commit:

```text
ea04f2c78 Emit branch binder instantiation contracts
```

The failure analysis of `11925:125` showed that some Skolem branch formulas
contained locally peeled binders that were not represented in the emitted
parent step variables. Megalodon was then asked to reconstruct parent
instantiations for variables that existed in Vampire's transformation state
but were not explicit in the certificate.

The Vampire patch records those branch binders and emits corresponding
instantiation contracts. This is exactly the preferred direction: Vampire
exports exact data from the proof state instead of forcing Megalodon to infer
it from formula shape.

The build used `/project/tmp` and parallel compilation:

```text

```

The resulting binary used in focused tests was:

```text

```

### Parent Instantiations in Megalodon Skolem Formula Proofs

Megalodon commit:

```text
0c0877f Use Skolem parent instantiations in formula proof
```

The native Skolem formula proof path previously tried to open parent proofs
using a small local list of candidate binders and substitutions. That worked
for simpler cases but failed when a parent variable was dropped from the
immediate syntactic result while still being needed by the proof obligation.

The fix adds an explicit `parent_instantiations` argument and uses Vampire's
`skolem_parent_instantiations` contract. The parent-proof opening order is now
roughly:

1. try the result variable binder;
2. try explicit Vampire parent instantiations;
3. try the existing substitution witness;
4. fall back to the original variable.

This moved `11925:125` past the earlier error:

```text
cannot instantiate dropped parent variable X1
```

That is an example of the desired pattern: the Megalodon checker became less
heuristic because Vampire supplied more exact contract data.

### Transport of Unchanged Skolem Disjunction Branches

Megalodon commit:

```text
dfc0812 Transport unchanged Skolem disjunction branches
```

The next failure was in a Skolem CPS disjunction replay. One branch of the
disjunction did not introduce an existential, so the old code expected it to
match syntactically after witness replacement selection. In `11925:125`, the
branch was logically unchanged but not syntactically identical under the
current source/result orientation and replacement context.

The fix is narrow. In the no-existential branch of disjunction replay, if the
direct propositional match fails, the checker tries `skolem_formula_transport`
between the branch's recorded source and result formulas. It does not install
a trusted theorem, and it does not mention benchmark names. It uses the
certificate's source/result formulas to build a checked transport.

This moved the hard target past:

```text
unchanged disjunction branch does not match result
```

The target still fails later because the candidate proof can still contain
choice witnesses or introduced Skolem symbols in a branch-local position.

### Result Free-Variable Metadata in Skolem CPS Replay

Megalodon commit:

```text
16c9362 Trust Skolem result free-variable metadata
```

After branch binder transport was fixed, the focused hard target exposed a
different binder mismatch. For one Skolem preprocessing step, Vampire emitted
a result formula whose explicit free-variable metadata said that the result
had zero external free variables. The Megalodon replay nevertheless
reintroduced a preserved parent variable when constructing the
result-to-target proof obligation. That duplicated a binder that was already
present inside the result formula itself.

The concrete failure was in the representative target:

```text
/project/Megalodon/examples/hammer/100thms_12_h.mg:11925:125
```

The problematic step was reported as `u273`. Before the fix, the
result-to-target comparison had an extra leading binder:

```text
forall _:(set -> prop), ...
```

where the branch-local current proposition began at the next binder level:

```text
forall _:prop, ...
```

The new code changes the preservation policy only when the certificate has an
explicit `result_formula_free_variable_count` field. In that case, the replay
uses Vampire's result free-variable contract directly and does not add
preserved parent variables again. If the field is absent, the older
preservation behavior remains available for compatibility.

This is a general correction rather than a benchmark patch. The guiding rule
is that explicit Vampire metadata wins over Megalodon-side reconstruction. It
also illustrates why the exporter work is valuable: the checker cannot safely
decide whether a syntactically preserved variable belongs outside the result
formula or has already been re-bound inside it unless Vampire gives the
contract.

The focused test after the change passed the easy target and kept the hard
target as an expected failure:

```text
TARGETS='10654:21 11925:125'
EXPECT_FAIL_TARGETS='11925:125'
JOBS=2
MEGALODON_VAMPIRE_TIMEOUT=10
```

Result:

```text
10654:21     PASS
11925:125   EXPECTED_FAIL
```

The important qualitative result is that `u273` moved past the old
result-to-target binder mismatch. The remaining failure is now about residual
choice/Skolem artifacts in the candidate continuation, not about the result
free-variable contract.

### Negative Experiment: Dummy Unused-Branch Witnesses

A deliberately small experiment tried to plug unused disjunction branches by
adding dummy witness replacements for unused dependent Skolem symbols.

The result was rejected. It built, and the easy regression target still
passed, but the hard target produced an ill-typed final refutation. The
diagnostic shape was:

```text
Type Error: Found prop but expected set
```

That experiment was reverted and is not part of the committed state. It is an
important negative result: arbitrary dummy witness fallbacks are too ad hoc
and can be unsound or ill-typed. The remaining fix must be certificate-guided,
not a generic "fill the hole with something" strategy.

### No-Shadow Diagnostic

The no-shadow diagnostic tested:

```text

```

with the same focused parallel target gate. The result was:


This suggests that simply disabling shadow replay does not solve the current
Skolem choice-witness leak. The shadow continuation may still be part of the
problem, but the deeper issue is the branch-local witness transport and

contains an introduced symbol and certificate-local choice witnesses:

```text
u273: native preprocess Skolem CPS exists-continuation sK1 still contains
introduced symbol

u273: native preprocess Skolem CPS candidate still contains
certificate-local choice witnesses; keeping original refutation
```

For `u276`, the certificate records:

```text
branch contract #0 unit=u275 parent=1 binders=1
parent_instantiations=3 witnesses=sK3
source_exists=1 target_exists=0 source_symbols=- target_symbols=sK3
```

The remaining failure is:

```text
u276: native preprocess Skolem CPS or-elimination candidate still contains
introduced symbol:
root.left.left.proof.proof.proof.term.left:
introduced term symbol sK3 in term #sK3; enclosing term (#sK3 #X0)
```

The final theorem-site reconstruction then fails:

```text
Vampire native source-context direct goal reconstruction did not find a proof.
Failure at line 11925 char 125:
Vampire native certificate did not reconstruct current proof goal
```

Interpretation:

- Vampire is now exposing the relevant branch contracts.
- Megalodon can parse and use several of them.
- The remaining proof term still leaks a branch-local introduced witness or a
  choice witness through a continuation where it should have been abstracted
  or transported.
- This is a real Skolem CPS proof-reconstruction problem, not a source-name
  lookup problem and not a Vampire timeout problem.

## Source Linking Status

The link from reconstructed Vampire proofs to original Megalodon lemmas and
definitions is substantially better than at the start of the project, but not
finished.

### What Works

The importer can now distinguish several kinds of source facts:

- global Megalodon facts already known in the signature;
- local hypotheses exported from the proof site;
- definitions and aliases;
- generated facts;
- generated `set` equalities;
- conjecture facts;
- unresolved facts.

It can semantically compare many exported formulas against the certificate
source formulas. It no longer treats source-map labels as sufficient proof by
themselves.

The source-map delta now links definitions to live Megalodon symbol hashes, not
only to exported TPTP names. This matters because a theorem-site goal may use
the live internal symbol while the certificate uses an exported name or a
readable recovered name.

Local hypotheses are also part of the source context. This fixed an earlier
class of failures where a proof site exported a local fact that was not a
global theorem and therefore could not be reconstructed as `Known hash`.

Generated `set` equalities are treated specially. Some THF axioms come from
Megalodon's `set` command and do not correspond to source claims. They should
be proved in Megalodon by reflexivity or conversion, not looked up as global
lemmas. The current source layer has support for that policy.

### What Does Not Yet Work Generally

The source-context layer does not yet provide a complete, standalone API of
the form:

```ocaml
source_context -> certificate -> Syntax.tm * Syntax.pf
```

for arbitrary original theorem sites.

The missing pieces include:

- robust handling of all local binder lifetimes across export/import;
- complete conversion between exported definitions and live goal definitions;
- complete transport from a refutation of the exported negated conjecture to
  the original theorem statement;
- full proof-producing handling of generated source obligations;
- complete failure diagnostics organized by source item rather than by the
  current large importer call stack.

The hard target `11925:125` is an example. The source layer reaches the right
conjecture target more reliably than before, but final replay still fails when
the Skolemized refutation proof has not been transported through the needed
branch-local witness substitutions.

## Smolka-Style Transformations

The project has repeatedly discussed Smolka-style transformations: a structured
pipeline from higher-level Megalodon formulas to the clausal or near-clausal
forms that Vampire proves, with each transformation justified by a proof term
or a small checked certificate step.

Current coverage is partial.

### Covered or Partially Covered

The current code has native paths for several transformation families:

- source formula normalization;
- selected definitional folds/unfolds;
- selected rectification patterns;
- selected FOOL and formula-level transformations;
- CNF formula-clause projection under some binders;
- selected Skolemization transformations;
- selected equality transports;
- final negated-conjecture target search.

The strongest recent progress is in Skolemization. Vampire emits much more
structural data than before, and Megalodon uses it to build native CPS-style
proof terms rather than accepting Skolemization as an opaque step.

### Still Missing

The Smolka-style pipeline is not complete. In particular:

- unsupported transformations must fail, not become dynamic trusted theorems;
- every transformation that is counted must produce a checked proof term or a
  checked small-kernel certificate;
- Skolemization needs a complete proof-producing account for dependent
  witnesses and branch-local continuations;
- definitional transformations must be clearly separated from arbitrary
  proposition facts;
- the pipeline should be modular, not embedded entirely in
  `vampire_cert_v1.ml`.

The current implementation is best understood as a growing proof-producing
frontier, not a complete Smolka transformation engine.

## Skolemization Status

Skolemization is the current hardest technical area.

### What Has Improved

Earlier in the project, Skolemization was too opaque. Megalodon had to infer
what Vampire did from formula shape and generated symbol names. That approach
was brittle and encouraged broad OCaml search heuristics.

Vampire now emits:

- top-level Skolem quantifier metadata;
- macro-edge records;
- branch records;
- source and target formulas for edges and branches;
- introduced witness symbols;
- witness dependencies and sorts;
- parent instantiation contracts;
- branch binder instantiation contracts.

Megalodon consumes this data in `native_core_skolem_refutation_cps_proof` and
related helpers. Recent work added:

- replay under forall binders;
- dependent witness replacements;
- branch-preserved instantiations;
- parent-instantiation fallback;
- transport of unchanged disjunction branches;
- proof-order replay of Skolem CPS entries.

The hard target has moved through several concrete old failures:

- dropped parent variable instantiation;
- nullary-only dependent witness replacement;
- unchanged disjunction branch mismatch;
- some nested equality branch orientation failures.

### What Still Fails

The remaining problem is not that Skolem metadata is absent. It is that the
Megalodon proof term sometimes still contains the wrong witness representation
inside a branch-local continuation.

The certificate-local Skolem term and Megalodon's local choice witness are
morally the same witness in the transformation proof, but the proof term must
make that relationship explicit. A candidate that still contains an
unabstracted `Eps_i`, `Eps_set_prop`, or introduced `sK3` in the wrong scope is
not acceptable.

The next fix should be one of:

- a Vampire-emitted primitive branch proof object for the Skolem branch
  transformation;
- a more explicit branch-local abstraction contract using the existing
  witness and parent-instantiation metadata;
- a checked Megalodon primitive for the exact Skolem branch schema, with all
  variables, witness dependencies, and source/result formulas supplied by
  Vampire.

The next fix should not be:

- a dummy witness fallback;
- benchmark-specific name rewriting;
- global search over arbitrary closed subterms;
- installing the branch implication as `Known`.

## Equality and Logic Constants

The final path should use Megalodon's own equality and logic constants. The
project does not need a private equality for reconstructed proofs.

Historically, some intermediate exporters and parsers introduced internal
formula constructors or printed forms that looked like their own equality or
logic vocabulary. That is acceptable only as an internal syntax layer if it is
elaborated back to Megalodon's actual equality, `False`, `or`, implication,
quantifiers, and classical principles.

The current native path increasingly does this. The trusted basis is supposed
to be Megalodon's library and a small reviewed classical logical basis, not a
new parallel logic. `xm` and other classical facts can be assumed available.

This remains a point to audit carefully, especially around formula parsing and
TPTP-to-Megalodon symbol recovery.

## Prover9/Ivy Direction

The Prover9/Ivy lesson is not "write more translators." It is:

```text
Complex prover inferences should be expanded or justified by the prover into
a small proof-object language whose checker is much simpler than the prover.
```

For this project, that means Vampire should lower its own inferences into a
small Megalodon certificate language while it still has exact proof-state
information.

The candidate primitive layer should cover:

- input/source fact;
- checked instantiation;
- alpha-renaming or binder transport;
- literal resolution;
- factoring;
- equality resolution;
- equality factoring;
- paramodulation/superposition with explicit side, position, direction, and
  substitution;
- formula/clause projection where needed;
- explicit contradiction from the empty clause;
- a small set of source/preprocessing primitives, including certified
  Skolemization schemas.

Some of this exists in focused form. It is not yet a complete isolated layer.

The main architectural recommendation remains:

- stop treating `vampire_cert_v1.ml` as the place where every new inference is
  solved;
- move proof detail emission into Vampire;
- move checking into a small Megalodon kernel module;
- keep the legacy importer as an oracle and compatibility harness.

## Python, OCaml, Lisp, and Certificate Syntax

Earlier work used Python heavily. That is no longer the preferred qualifying
path. Python remains useful for batch orchestration, statistics, and corpus
triage, but it should not produce proof terms that count toward the final
result.

Megalodon itself is implemented in OCaml, so the native checker and elaborator
naturally live in OCaml. The audit concern was not "never write OCaml." The
concern was uncontrolled growth of a second theorem prover inside the OCaml
importer. The acceptable OCaml code should be a small checker and elaborator,
not an expansive heuristic reconstruction engine.

The certificate is S-expression-like. That choice is compatible with the
Prover9/Ivy lesson because the important property is not the surface language;
the important property is a small, explicit, checkable proof object. Lisp-like
syntax is useful because it is simple and robust to parse, but it is not by
itself a proof architecture.

## Testing Strategy

The testing strategy has changed in response to user feedback and audit
findings.

Broad sequential iteration was too slow and misleading. The preferred mode is
now:

1. export many problems at once;
2. run Vampire in parallel with per-problem timeout at most 10 seconds;
3. check certificates in parallel;
4. iterate on focused failing classes rather than rerunning unsolved problems
   repeatedly.

For current implementation work, the branch uses small focused gates:

- one known passing original-site target;
- one hard expected-failing target;
- native certificate smoke tests;
- build checks.

This is intentional. Running the broad suite before the hard Skolem CPS class
moves would waste time and produce a large expected-failure log. Once the hard
target passes, the next appropriate run is a small parallel bucket of fragile
targets, followed by a fresh 10-theorem original-context milestone, and only
then a broader 100-theorem run.

All current substantial logs and generated artifacts are under `/project/tmp`.

## Detailed Implementation Map

The project currently has four implementation strata. They should be judged
separately because they have different trust properties.

The first stratum is the Megalodon exporter and source map. Its job is to turn
an original theorem site into a THF/TPTP problem and to record where each
exported axiom, definition, generated fact, local hypothesis, and conjecture
came from. This layer is essential for original-context reconstruction. It is
also where generated `set` facts enter the problem. Some of these facts do not
correspond to named user lemmas; they arise from commands or definitional
expansion. The right proof in Megalodon is usually reflexivity or conversion,
not a recovered `Known` theorem. This is why source linking cannot be a simple
dictionary from TPTP names to Megalodon theorem names.

The second stratum is Vampire's certificate emission. It has improved the most
in the last several branches. The current exporter no longer merely prints
Vampire's human-readable proof. It emits structured S-expression records with
source identities, result formulas, parent steps, primitive or macro rule
names, substitutions, shape metadata, Skolem contracts, introduced symbols,
free-variable counts, and branch-instantiation contracts. For hard examples,
this additional Vampire-side information has repeatedly removed Megalodon-side
guessing. Parent instantiation metadata moved one failure. Branch binder
metadata moved another. Result free-variable metadata moved another. These are
good signs because they show that the project is learning from Vampire's proof
state rather than reconstructing it independently.

The third stratum is Megalodon's certificate parser, checker, and proof-term
elaborator. This is the part most likely to become too large. The current
native code has useful pieces: S-expression parsing, source checks, proof
terms for clausal core steps, proof-term checks against `check_propofpf`,
source-context binding, and partial preprocessing/Skolem replay. However,
`vampire_cert_v1.ml` still contains too many responsibilities. Its role should
shrink over time. In the final architecture, it should not be the component
that performs broad proof search or library-specific reconstruction. It should
orchestrate smaller modules that have clear input and output contracts.

The fourth stratum is testing and corpus management. The project has learned
that broad sequential testing is inefficient and often misleading. The useful
pattern is to pre-export many problems, run Vampire once per problem with a
hard timeout, store certificates and logs under `/project/tmp`, and then run
Megalodon checking in parallel. Focused iteration should use a small target
gate with one known pass and one or more expected failures. Broad results
should only be run after a focused blocker moves. This keeps cycle time low
and prevents expensive reruns of problems that Vampire has already failed to
solve under the agreed timeout.

The most important boundary between these strata is the trust boundary.
Vampire is untrusted. The certificate parser is untrusted. Batch scripts and
Python diagnostics are untrusted. A result counts only when Megalodon's own
kernel checks a proof term whose assumptions are exactly the allowed original
source facts and fixed reviewed logical basis. Anything else is still useful
engineering evidence, but not a solved theorem.

## Detailed Chronology

The project began with the natural idea of modifying Vampire's Lean proof
printing path for Megalodon. That was reasonable because Lean and Megalodon
both have proof terms, and Vampire already had Lean-oriented proof output. The
early work explored that path by generating Megalodon proof skeletons, mapping
TPTP names back to more readable Megalodon names, and using declarative
`claim` structures to make partially reconstructed proofs inspectable by a
human. This was useful for learning the shape of Megalodon proofs, especially
after the user supplied examples such as `examples/form100/SepE`.

That initial path also exposed a danger. Skeletons with `admit` or `aby` are
useful for inspection, but they do not reconstruct proofs. Megalodon's `aby`
is implemented as an admission, so it cannot appear in counted results. A
workflow that only produces all-or-nothing scripts, or scripts where most
interesting obligations are admitted, is hard for a human to continue from
and easy to overcount. The project therefore introduced explicit evidence
classes and stopped treating admitted scripts as proof reconstruction.

The next phase focused on batch testing. Problems were exported from
Megalodon, Vampire was run over them, and solvable THF examples were separated
from problems where Vampire simply did not finish within the timeout. This
was important for iteration speed. The project should not repeatedly rerun
unsolved Vampire searches while working on reconstruction. A one-time
solvability pass gives a stable set of Vampire-proved problems, and then the
reconstruction work can iterate over those certificates.

The Python translator phase was valuable but became the wrong center of
gravity. It parsed Vampire output, tried to recover proof structure, generated
Megalodon scripts, and accumulated many local reconstruction heuristics. It
also learned many source-name and formula-shape facts that are still useful.
But it was becoming an independent proof-search layer. That contradicts the
project's architecture: Vampire should provide proof details, and Megalodon
should check them. The final proof path should not depend on Python guessing
substitutions, pivots, set-theoretic lemmas, or proof scripts.

After the first audits, the project moved to a native certificate format. The
surface format became Lisp/S-expression-like, not JSON, and Megalodon parses
it in OCaml. The important property is not Lisp syntax by itself; it is that
the certificate is explicit, versioned, and mechanically checkable. The audit
recommended Prover9/Ivy-style proof objects. The current certificate format is
closer to that than the old output, but it is still too broad. It contains
macro certificates and preprocessing records that are not yet lowered into a
small primitive core.

The next major improvement was closed-mode accounting. Earlier versions could
typecheck generated Megalodon scripts by adding bridge premises or treating
derived clauses as inputs. The current qualifying path rejects that. It also
distinguishes strict structural validation from closed proof reconstruction.
This was a major correction in how results are reported.

The native proof-term phase added actual `Syntax.pf` construction for a core
clausal fragment. This is the strongest architectural seed in the branch. It
shows that the right direction is feasible: parse a certificate, resolve
sources, build Megalodon proof terms, and check them. But the live broad
problem set exercises preprocessing, Skolemization, AVATAR-like splitting,
FOOL transformations, and higher-order or typed binder details that are not
covered by the small core. That is why the current frontier is dominated by
preprocessing and Skolem CPS problems rather than simple resolution.

The most recent phase has focused on Skolemization. This is a hard but
unavoidable part of original-context reconstruction because Vampire's proof
uses Skolemized formulas while the original Megalodon theorem is stated with
ordinary quantifiers and exists/forall structure. The project has added
Vampire-side contracts for Skolem macro edges, top-level quantifiers, child
formulas, branch shapes, introduced witness symbols, dependencies, parent
instantiations, branch binders, and free-variable counts. Megalodon consumes
some of this data to build CPS-style proofs that try to discharge the
Skolemized refutation back to the original formula.

The current hard failure is exactly in that phase. It is not an issue of
Vampire failing to find a proof. It is not primarily a name-recovery issue.
It is a proof-term problem: the candidate continuation still contains either
an introduced Skolem symbol or a certificate-local choice witness where the
final original-context proof must not contain it.

## Relationship to Smolka-Style Reconstruction

The Smolka-style lesson is that ATP proof reconstruction should preserve the
proof graph and source correspondence, but target-side proof construction
should use controlled local proof-producing procedures for individual edges.
It is not a recommendation to reproduce the entire ATP preprocessing pipeline
with ad hoc pattern matching. For this project, the lesson has three concrete
consequences.

First, formula-processing transformations should have explicit certificates.
Rectification, negation normal form, FOOL elimination, clausification,
definition introduction, and Skolemization should not be rediscovered by
searching formula strings. Each transformation needs a before formula, an
after formula, exact binder information, substitutions or dependencies, and a
small schema that Megalodon can elaborate into a proof term. When the
transformation is complex, Vampire should split it into more atomic steps
before printing.

Second, source correspondence must survive transformation. A reconstructed
refutation of an exported problem is not enough if it cannot be connected to
the live theorem site. The source-context layer must show how the exported
axioms arise from local hypotheses, global lemmas, definitions, generated
facts, or the negated conjecture. The current work has made progress here,
but it still does not have a finished theorem-site composition API.

Third, compression and readability are secondary. The immediate target is a
correct proof term. A later tool can compress a large proof into a more
readable Megalodon script or declarative proof. The current priority should be
small, explicit, checkable certificates and no hidden assumptions.

Skolemization is the clearest example. A Smolka-style reconstruction should
not simply accept Vampire's Skolemized formula as a new premise. It should
prove that a refutation of the Skolemized formula yields a refutation of the
original existential/forall formula, using classical choice or an equivalent
approved Megalodon principle. That proof must bind dependencies correctly,
must respect variable sorts, and must eliminate certificate-local choice
symbols from the final theorem. The branch is now working precisely on this
problem, but the hard case still fails.

## Prover9/Ivy Comparison in More Detail

The Prover9/Ivy analysis remains one of the most important design inputs.
Prover9 does not ask Ivy to reconstruct arbitrary prover internals. It first
expands the proof. Hyper-resolution, unit-resulting resolution, demodulation,
and other compound steps are lowered to a smaller set of operations such as
instantiation, resolution, paramodulation, equality flip, and propositional
simplification. The Ivy proof object carries parent identifiers, positions,
and substitution pairs. The checker is intentionally much less intelligent
than the prover.

For Vampire/Megalodon, the equivalent move is still incomplete. The current
Vampire exporter emits many useful fields, but it is not yet a central
primitive proof builder. The desired Vampire-side component should construct
objects of this form internally before printing:

```text
primitive step id
primitive rule
parent ids
conclusion clause or formula
selected literal indices
rewrite side and position
rewrite direction
substitution
variable and symbol sorts
source/preprocess payload when the step is not clausal
```

The difference between metadata and primitive objects matters. Metadata says:
"Here is extra information that may help the importer understand this macro."
A primitive object says: "Here is the exact small inference the checker must
verify." The audits recommend the second. The current branch has a mixture.

The first high-value Vampire-side macro to lower remains unit-resulting
resolution or another frequent clausal macro that has simple binary
resolution expansion. This would demonstrate the intended architecture on a
large class without entangling Skolemization, source contexts, or higher-order
preprocessing. Demodulation and superposition should eventually follow the
same pattern: emit exact paramodulation/rewrite positions and substitutions,
not vague rewrite-chain hints.

This does not mean abandoning the current Skolem work. Skolemization is a
formula-processing macro and needs a dedicated proof schema. But the long-term
lesson is the same: the certificate should carry a small, complete contract,
and Megalodon should elaborate that contract rather than rediscover the
transformation.

## Current Skolemization Design

The current Skolem replay is best understood as a CPS transformation. Vampire
has a proof of contradiction from a Skolemized formula. Megalodon needs a
proof of contradiction from the original formula. For existential
introductions and removed quantifiers, this requires a continuation that can
turn a proof using introduced witnesses into a proof under ordinary logical
binders.

The key objects are:

- the original source formula before the Skolem step;
- the result formula after the Skolem step;
- introduced Skolem symbols;
- dependencies of each introduced symbol;
- parent and child formula relationships;
- branch contracts for conjunctions/disjunctions;
- branch binder instantiations;
- result free-variable counts;
- proof terms for the refutation continuation.

The Megalodon code currently attempts to build a proof term that transforms a
refutation of the result into a refutation of the source. It must preserve the
right variables, open the right binders, replace or abstract witness terms,
and ensure that no certificate-local choice object leaks into the final
proof.

Several mistakes have already been found and fixed. Parent variables can be
needed even when they are not syntactically present in an immediate result.
Unchanged disjunction branches can still require formula transport. Result
formulas may already bind variables that a naive preserved-variable heuristic
would re-add. Each of those cases is now handled with certificate data rather
than benchmark names.

The current failure indicates that the remaining abstraction step is not yet
complete. A continuation contains `sK1` or `sK3` in a place where the final
proof should instead be abstracted over the corresponding existential or
choice construction. Separately, some proof candidates contain
certificate-local choice witnesses such as `Eps_set_prop` and choice theorems
such as `vampire_exists_set_prop_choice`. These are allowed internally only
if they are fully discharged by the end of the transformation. They cannot
remain in a counted original-context proof.

The next fix should not be a dummy witness fallback. That was tested and
rejected because it produced ill-typed proof terms. The likely correct fix is
to make the CPS proof carry a precise abstraction/replacement environment for
dependent witnesses and to apply it consistently to branch continuations,
or-elimination candidates, and result-to-target transports. If the existing
certificate is still missing information for that abstraction, Vampire should
emit it explicitly.

## Original-Context Gluing

The final output must be a proof of the user's theorem in the original
Megalodon file. That requires more than a checked certificate for the exported
problem.

First, every input fact in the certificate must be classified. A source axiom
may map to a global theorem, a local hypothesis, a definition, a generated
fact, a `set` equality, or the conjecture. Each class needs a different proof
source. Global theorems can be referenced by `Known` names. Local hypotheses
must be represented as bound proof assumptions in the theorem-site context.
Definitions may require unfolding or conversion. Generated `set` equalities
should be proved by reflexivity or definitional equality. The conjecture is
the negated goal and must be connected to the live proof target, not treated
as an arbitrary input axiom.

Second, symbol names must be resolved semantically. TPTP names are mangled.
Readable names can often be recovered, but the proof should not trust the
string alone. The current source-map work links definitions to live symbol
hashes and can recover many locals. This is a substantial improvement over
hardwired name recovery. The missing piece is a stable, narrow API that turns
each exported source fact into a Megalodon proof object or bound assumption
inside the live context.

Third, theorem-site binders must be transported correctly. A Vampire problem
often represents a local theorem goal after exporting hypotheses, definitions,
and a negated conjecture. Reconstructing the refutation yields a proof of
`False` from those exported assumptions. The final Megalodon script or proof
term must discharge exactly the original hypotheses and prove the original
goal. The current code can guide search after a target match and can bind
some local source hypotheses, but the general theorem-site composition remains
unfinished.

Fourth, preprocessing must be composed with sources. If Vampire proves a
clausified or Skolemized form, the proof of the transformed formula must be
transported back through preprocessing before it can discharge the original
conjecture. This is where source gluing and Smolka-style transformation
proofs meet. The current Skolem CPS blocker is therefore directly on the path
to original-context reconstruction.

The practical next milestone should be ten original-context theorem sites,
not a broad 100-case structural run. Ten small but real examples would force
the pipeline to solve source classification, local hypotheses, definitions,
generated facts, conjecture negation, and proof-term composition in a way that
an expert can inspect.

## What Has Been Rejected

The project has tried and rejected several shortcuts. Recording them matters
because they are tempting to repeat.

Admitted Megalodon proof skeletons are not qualifying evidence. They helped
make proof structure visible to humans, especially through `claim`, but they
do not prove the original theorem. `aby` is also disallowed because it is an
admission in Megalodon.

Treating derived Vampire clauses as inputs is not acceptable. It can make the
kernel check a theorem, but only after strengthening the assumptions with a
fact that was supposed to be proved.

Installing certificate-derived `Known` theorems is not acceptable. It hides a
bridge premise inside the proof environment. The kernel then checks a proof
relative to a theorem that the importer invented.

Library-specific name hardwiring is not acceptable. The project must work
over arbitrary Megalodon libraries exported to THF, not only the current set
development. Name recovery is useful, but proof reconstruction should depend
on source maps, symbol hashes, types, and certificate propositions rather than
special theorem names.

Dummy witness replacement for Skolem branches is not acceptable. It was tried
in a narrow form and led to ill-typed proof terms. Witness handling must be
driven by the Skolem certificate contract and Megalodon's type checker.

Sequential broad testing is not acceptable for ordinary iteration. It wastes
time on unsolved Vampire searches and makes the development loop too slow.
The project should keep a cached solved set, use parallel workers, and reserve
broad runs for milestone validation.

## Expert Review Questions

The expert review should focus on five questions.

First, is the current Skolem CPS schema logically the right one for
Megalodon's proof terms, or should the project introduce a smaller explicit
preprocessing certificate calculus before attempting more live Skolem cases?
The branch currently builds source-to-result and result-to-source proof terms
inside a large module. That may be salvageable, but it needs review.

Second, where should the primitive expansion boundary live in Vampire? The
project has added many metadata fields in `MegalodonChecker.cpp`, but the
audits recommend a dedicated primitive IR. The expert should inspect whether
the current exporter can be refactored incrementally into that shape, or
whether a cleaner side module is needed.

Third, what is the minimal trusted logical basis in Megalodon? The user has
specified classical logic with `xm`, and Megalodon's own equality and logic
constants should be used. Choice-like principles appear in the Skolem work.
The project needs a reviewed list of allowed logical theorems and a mechanical
test that no other certificate-derived knowns enter counted proofs.

Fourth, what should the first original-context milestone contain? The best
candidate is ten real theorem sites that include local hypotheses,
definitions, generated `set` facts, ordinary clausal reasoning, and at least
one Skolemized proof. They should be small enough to debug and diverse enough
to prevent overfitting.

Fifth, should the old Python and textual emitters remain in the repository as
diagnostics, or should they be moved out of the main tree? Keeping them helps
compare historical behavior, but it also creates confusion about the
preferred path. At minimum, qualifying tests should not import them.

## Current Risks

### Risk 1: The Importer Keeps Growing

The largest risk is that `vampire_cert_v1.ml` keeps absorbing every new
inference class. That repeats the audit's central criticism. The project needs
to extract a small checker and a separate source/preprocessing layer.

### Risk 2: Vampire Metadata Is Not Yet a Primitive IR

Vampire emits much richer metadata, but metadata is not the same as a small
proof-object stream. The current direction is good, but the project still
needs a real primitive expansion pass.

### Risk 3: Skolemization Becomes a Special-Case Patch Cycle

Skolemization failures are tempting to fix by local formula matching and
fallback replacements. That is dangerous. The dummy witness experiment showed
that such patches can create ill-typed proofs. The branch should only accept
certificate-guided or kernel-schema-guided fixes.

### Risk 4: Source Linking Is Mistaken for Source Proving

Recovering original names is necessary but not sufficient. The checker must
prove that the exported formula is the original fact, a local hypothesis, a
definition, a generated reflexivity/conversion fact, or the conjecture in the
right scope.

### Risk 5: Integration Pass Counts Are Overstated

Broad strict certificate runs are valuable, but they are not proof
reconstruction unless native proof terms are checked and composed back into
the original context.

## Outlook

The project is technically viable, but the implementation needs discipline.

The promising facts are:

- Vampire can generate detailed certificates for Megalodon problems.
- Megalodon can parse them and build native proof terms for nontrivial
  fragments.
- Source linking has moved from name recovery toward semantic context
  resolution.
- Skolemization is no longer opaque; the certificate carries substantial
  proof-state data.
- Focused original-site replay can succeed.

The warning signs are:

- the importer and exporter are still too large;
- the primitive kernel layer is not yet isolated;
- Skolemization is still incomplete;
- there is still no broad original-context suite;
- reports and tests must remain strict about evidence class.

The best next direction is not to chase a broad pass count. It is to finish the
current hard Skolem CPS representative in a certificate-guided way, extract the
small checker boundary, and then build a ten-theorem original-context
milestone. That would give the expert reviewer and future developers something
real to extend: a small number of fully checked examples, a clear trust
boundary, and a path from Vampire's internal proof data to Megalodon's native
proof terms.
