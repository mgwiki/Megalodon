## Executive Summary

The original project goal remains:

```text
Given a theorem in an original Megalodon development, export the theorem and
its context as a THF/TPTP problem, let Vampire solve it with a per-problem
timeout of at most 10 seconds, emit a detailed certificate, import the
certificate into Megalodon, elaborate it into Megalodon proof terms, and check
the proof of the original theorem in the original Megalodon context.
```

That goal is not finished.

There is still no broad suite of 100 original Megalodon theorems reconstructed
from Vampire proofs with all of the following restrictions:

- no `aby`;
- no `admit`;
- no `-allowincompleteqed`;
- no Python proof-producing step;
- no bridge assumptions;
- no certificate-derived `Known` proposition;
- no hidden extra premise;
- no library-specific hardwired reconstruction pattern;
- no unverified mapping from an exported THF axiom back to the original
  Megalodon theorem, lemma, definition, local hypothesis, or generated fact.

The most important progress is architectural and trust-boundary progress:

- The Python proof-producing path has been quarantined from qualifying runs.
- Vampire now emits a native Megalodon-oriented S-expression certificate with
  rich `kernel_v1` metadata.
- Megalodon parses that certificate in OCaml and uses native `Syntax.tm` and
  `Syntax.pf` values for the counted native proof-term paths.
- Counted native paths now reject certificate-derived `Known "vampire_*"`
  propositions rather than treating them as proved implications.
- Source maps are no longer just name links. Supported exported formulas are
  semantically checked against certificate inputs, and source-context checking
  can resolve many global facts to actual Megalodon `Known hash` proofs.
- Generated equalities from Megalodon `set` commands are treated as generated
  reflexivity/conversion obligations, not as arbitrary source claims.
- Local source hypotheses are now part of the native source context, including
  standalone local source facts that appear in the exported problem but are not
  global library theorems.
- Some original-site reconstruction works. A focused live target at
  `examples/hammer/100thms_12_h.mg:10654:21` reconstructs through the native
  Vampire path in the original Megalodon process.

The most important remaining gap is also architectural:

- The project still lacks a small, stable, complete Prover9/Ivy-style
  primitive proof-object layer into which Vampire lowers its internal
  inferences.
- Too much proof-specific logic remains inside Megalodon's large
  `src/vampire_cert_v1.ml` importer and Vampire's large
  `Shell/MegalodonChecker/MegalodonChecker.cpp` exporter.
- Skolemization and Smolka-style source/preprocessing transformations are only
  partially proof-producing.
- Final composition from the exported refutation back into the original
  Megalodon theorem still fails on representative larger examples.

The current system should be viewed as a substantially improved prototype and
test laboratory, not as a finished proof reconstruction system.

## Evidence Classes Used in This Report

The previous audits repeatedly found that reports were too optimistic because
they grouped parsing, script generation, structural validation, and actual
proof reconstruction under the same word "pass." This report uses the stricter
evidence classes now adopted by the branch.

### E1: Original-Context Reconstruction

This is the actual goal.

```text
The proof checks at the original Megalodon theorem site, using the original
global lemmas, local hypotheses, definitions, generated facts, and conjecture
binding. It uses no aby, no admit, no incomplete QED, no bridge premise, no
certificate-derived Known proposition, and no Python proof-producing step.
```

Current status:

- There is no broad E1 suite.
- There is at least one focused original-site success with the native Vampire
  path, but it was run in a targeted hammer mode and is not enough to count as
  a final theorem-suite milestone.
- A representative larger target still fails at final source-goal composition.

### E2: Exported-Problem Native Proof Reconstruction

```text
Megalodon checks native proof terms derived from a Vampire certificate against
the exported THF/TPTP problem and source map. This proves the exported problem
or a post-preprocessing refutation, but it has not necessarily been composed
back into the original theorem command.
```

Current status:

- There is meaningful E2-like evidence for cached and focused certificates.
- Recent source-context checks make this evidence stronger than the earlier
  textual skeleton results.
- It still does not replace original-context proof checking.

### E3: Focused Proof-Term Regression

```text
A synthetic, cached, or narrowly selected certificate exercises one inference
family, one preprocessing transformation, one Skolemization pattern, or one
known blocker.
```

Current status:

- This is where most successful current development lives.
- These regressions are useful and should be kept.
- They should not be reported as 100-theorem proof reconstruction.

### E4: Structural and Integration Evidence

```text
Vampire emits certificates, Megalodon parses them, metadata is present,
source maps are audited, trust policy checks run, or `kernel_v1` records pass
schema and consistency checks.
```

Current status:

- The branch has a lot of E4 evidence.
- E4 is important for finding breakage and measuring coverage.
- E4 does not prove theorems.

## What Has Been Done

The project has gone through several distinct phases.

### Phase 1: Python Skeleton Translation

The initial path took Vampire proof output and translated it into Megalodon
scripts, often as declarative `claim` skeletons. This quickly produced useful
human-readable artifacts and helped identify common inference classes:
resolution, factoring, superposition, demodulation, CNF, FOOL, AVATAR,
Skolemization, and source/preprocessing transformations.

This phase was useful for exploration but not acceptable as the final path.
The Python script accumulated a large amount of logical reconstruction logic,
including bounded proof search, equality transport, quantified proof search,
and library-pattern recognition. That contradicted the requirement that the
reconstruction be general and driven by Vampire's proof data rather than by a
separate heuristic prover.

Current status:

- Python remains useful for diagnostics, corpus analysis, and offline
  summarization.
- Python is not considered part of any qualifying proof reconstruction path.
- New proof-producing Python logic should remain prohibited.

### Phase 2: Native S-Expression Certificate

The next path introduced a native Vampire certificate intended for Megalodon.
This was the first major course correction after the audits.

Vampire now emits structured S-expression data containing formulas, clauses,
step identities, source names, source roles, source-map information, inference
names, parent steps, substitutions, positions, and `kernel_v1` records.

This was a clear improvement over scraping ordinary TPTP proof text. Vampire
has access to substitutions, parents, selected literals, generated symbol
information, Skolem metadata, and inference details at the point where proof
search and preprocessing happen. The audits correctly pushed us to export
that information from Vampire instead of rediscovering it in Megalodon or
Python.

Current status:

- The native certificate format exists and is used by the current branch.
- It is still too broad and too ad hoc to be called a finished Ivy-style
  certificate calculus.
- `kernel_v1` metadata is an audit and migration vocabulary, not yet a clean
  standalone primitive proof object.

### Phase 3: Closed Source-Linked Textual Reconstruction

The branch then added stricter source validation and closed textual modes.
This fixed two early audit failures:

- Unsupported derived Vampire clauses were previously allowed to become
  theorem assumptions.
- Source names were previously too close to label links; a source name could
  be present even when the formula did not semantically match.

The later closed mode rejected bridge and derived assumptions. Source maps
were checked more semantically for the supported THF fragment. That made
closed exported-problem evidence more meaningful.

Current status:

- This work is valuable as a regression oracle and source-linking baseline.
- It is still not the final desired proof-term path because textual emitted
  scripts and generated proof helpers are not the clean trust boundary.

### Phase 4: Native `Syntax.pf` Proof-Term Seed

The project then moved proof reconstruction into Megalodon's native proof-term
machinery. This was the right direction.

The key point is that a qualifying importer should produce Megalodon proof
ASTs and use Megalodon's checker:

```ocaml
source_context -> certificate -> Syntax.tm * Syntax.pf
```

instead of only producing text:

```ocaml
certificate -> string
```

The branch now has native proof-term checking for a core and for selected
preprocessing/refutation paths. It uses `check_propofpf` and native proof
terms in important places.

A major trust-boundary correction happened after the July 16 audit. Earlier
native preprocessing checks sometimes created the desired implication as a new
`Known` theorem and then checked a proof by applying that newly installed
known proposition. That was equivalent to a hidden bridge axiom. The counted
native paths now reject certificate-derived `Known "vampire_*"` propositions.

Current status:

- There is a real native proof-term path.
- It is still incomplete.
- The native proof-term implementation is embedded in large modules rather
  than isolated as a small kernel elaborator.

### Phase 5: Source-Context Integration

The most recent work has focused on connecting the certificate back to the
original Megalodon context rather than merely checking the exported THF
problem.

The source-context layer now distinguishes:

- global facts that can be checked as `Known hash`;
- local hypotheses;
- definitions;
- generated facts;
- generated equalities from `set`;
- conjecture facts;
- unresolved or unsupported facts.

Recent work also synthesizes standalone local source hypotheses from the
source map. This matters because many exported problems contain local facts
that are not global library theorems but are nevertheless legitimate
assumptions at the original theorem site. They must become `Hyp`-based proof
bindings in the native reconstruction, not missing axioms and not global
`Known` assumptions.

Current status:

- Source-context auditing is much stronger.
- Global source facts can be connected to checked `Known hash` proofs in the
  loaded Megalodon development.
- Standalone local source facts are now represented in the source context.
- Generated set equalities are handled as reflexivity/conversion obligations
  in source-obligation auditing.
- Full final composition into original theorem goals still fails on larger
  examples.

### Phase 6: Skolemization Metadata and Partial Proof Replay

Skolemization has been one of the hardest parts of the project. Earlier
versions tried to infer too much from generated names and formula strings.
That was both brittle and too Megalodon-side.

The current Vampire fork emits much richer Skolem metadata:

- top-level Skolem quantifier metadata;
- macro-edge shape metadata;
- macro-edge binders;
- macro-edge free-variable metadata;
- macro-edge child metadata;
- branch contracts;
- introduced witness contracts;
- proof contract metadata;
- parent instantiation contracts.

Megalodon now consumes many of these records and uses them to avoid treating
generated Skolem symbols as ordinary original variables or globally scoped
proof terms. Several earlier binder and de Bruijn escape failures were fixed
by preserving contract variables and branch binders across the CPS-style
Skolem replay.

Current status:

- Skolemization is no longer opaque string rewriting.
- Several focused Skolem proof-term cases now get past earlier blockers.
- General dependent Skolemization and source-connected Skolem transformations
  remain incomplete.
- The next failures tend to be around transporting equalities and source
  premises through dependent generated symbols and final goal composition.

## Audit-Driven Course Corrections

The audits were useful and, in several places, correct. The current branch is
materially different because of them.

### July 12 Audit

The July 12 audit identified that the then-current implementation had become
three overlapping systems:

- a Vampire exporter;
- a large Python reconstructor;
- a Megalodon-side tactic/skeleton generator.

It also warned that reported successes were mostly admission-based or
source-context syntax checks rather than proof reconstruction. That criticism
was valid. It led to the quarantine of Python from qualifying runs and the
shift toward native certificate import.

### July 13 Audit

The July 13 audit accepted the conceptual Prover9/Ivy-style pivot but found
that the new path had already started recreating the old monolith. It also
found that unsupported derived Vampire clauses could become assumptions.

That defect has since been addressed in closed and counted modes. Derived
Vampire clauses cannot count as source assumptions in the qualifying path.

The audit also asked for OCaml inside Megalodon rather than Python for accepted
reconstruction. The current path follows that.

### July 14 Audit

The July 14 audit found the critical source-map loophole: source linking was
too label-based. A certificate could attach a nontrivial formula to a source
name whose exported declaration was `$true`.

This led to stronger formula checking and fail-closed source validation for
the supported THF fragment. The current source-obligation audit goes further
by checking supported source obligations against the loaded Megalodon context.

### July 15 Audit

The July 15 audit accepted that closed mode and semantic source checks had
become meaningful. It still warned that the implementation was growing in the
wrong place and that source-linked exported proof checking was not the same as
original-context reconstruction.

That warning remains true. It is one of the central messages of this report.

### July 16 Audit

The July 16 audit found a subtler trust-boundary failure: the native
preprocessing path could dynamically install certificate-derived `Known`
propositions and then use them as if they were library theorems.

The current branch has addressed this in counted paths. It includes a native
proof `Known` provenance scan and rejects generated certificate-derived proof
constants in counted native core/preprocess checks. Older preprocessing
frontier numbers that relied on dynamic `Known` insertion must remain
classified as structural/transitional evidence, not proof reconstruction.

The July 16 audit also recommended a real small-kernel primitive layer and
better original-context API. Those remain only partially implemented.

## Current Source-Linking Status

Source linking is much better than it was, but it is not complete.

### Global Lemmas and Definitions

For hash-backed source facts, the source-context path loads the Megalodon
development and checks whether the referenced hash is available as a known
fact with the expected proposition. When that succeeds, the source fact can be
used as a real `Known hash` proof, not as an imported certificate assumption.

This is a major difference from the earlier source-map-only path. It means
some exported axioms are now connected to real original Megalodon library
lemmas.

Limitations:

- The mapping is still partial.
- Not all exported facts have a corresponding global claim.
- Definitions and generated facts need separate handling.
- The final theorem proof still needs to be composed back into the exact
  original proof goal, including local binders and local facts.

### Local Hypotheses

Local hypotheses are now represented in the source context and are connected
to native certificate checking. The current branch handles them in two steps.

First, source-map entries tagged as local facts are resolved to
`Vampire_source_context.LocalHyp` entries. This is necessary because local
facts may appear as TPTP axioms but are not global Megalodon theorems.

Second, native core and preprocess checking receives an external-hypothesis
list whose entries are indexed by the live local proof context but whose
propositions are computed in the same native certificate context used by the
preprocess elaborator. This is the important correction from today's work:
the earlier experiment tried either to omit local facts from native checking
or to shift all live local hypotheses blindly under certificate variables.
Both were wrong. The committed code instead asks
`Vampire_cert_v1.native_certificate_source_bindings_native_context` for the
certificate-side source proposition and places it at the local-hypothesis
index supplied by the source resolver.

Focused synthetic smoke fixtures demonstrate the intended pattern:

- a local fact `Hp : p` is exported;
- the certificate refutes `p` and `~p`;
- source-context strict mode consumes the local fact;
- native preprocess proof checking succeeds;
- remaining source assumptions are reduced to the conjecture.

The smoke suite also now checks local equality transport: from a local
hypothesis proving `x = y`, the native source-audit path can prove a current
goal `y = x` by constructing and checking a Megalodon equality-symmetry proof
term. This is not a broad theorem-proving tactic; it is a narrow checked
transport for a proof term whose proposition is already known.

This is a real step toward original-context reconstruction. It does not yet
solve all local-binder, source/preprocessing, or conjecture-composition cases.

### Generated `set` Facts

Some TPTP axioms come from Megalodon's `set` command and do not correspond to
ordinary user-written `claim`s. In the common equality case, they should be
proved by reflexivity or conversion, not assumed.

Current status:

- Source-obligation auditing recognizes equality-shaped generated facts.
- Reflexivity/conversion-style generated facts are counted separately from
  global knowns and local hypotheses.
- The latest broad source-obligation audit found formula obligations checked
  and no missing source obligations in the tested corpus.

This is still a source/preprocessing layer, not a complete final proof of all
set-generated obligations in every original theorem.

### Conjecture Binding

The refutation proves inconsistency of the source assumptions plus a negated
conjecture. To prove the original theorem, Megalodon must convert the
refutation into a proof of the current goal at the original proof site.

Current status:

- There is code for guided negated-conjecture reconstruction and final
  conjecture composition.
- The focused original-site target at `10654:21` succeeds.
- The larger target at `11925:125` fails precisely at this final
  source-goal transport/composition stage.

This is now one of the main blockers.

## Current Smolka-Style Transformation Status

The Smolka-style lesson, as interpreted for this project, is not "duplicate
all of Vampire's preprocessing in Megalodon." The useful principle is:

```text
Keep the ATP proof graph and source correspondence, but justify each local
source/preprocessing edge by a small, explicit target-side proof-producing
procedure.
```

The project has partial support for this but not a finished framework.

### What Works Partially

The current native paths can prove or check selected transformations and
clausal steps without dynamic `Known` insertion:

- selected resolution and clausal-core steps;
- selected instantiation/substitution cases;
- some single predicate folds;
- some rectification and variable-map cases;
- selected direct or metadata-backed Skolem patterns;
- some final-conjecture composition cases;
- generated equality/reflexivity source obligations in auditing.

### What Is Still Open

The general Smolka-style transformation layer is incomplete for:

- full FOOL transformations;
- ENNF;
- CNF projection from source formulas;
- broad definition introduction and predicate-definition folding;
- general formula normalization;
- full dependent Skolemization;
- AVATAR and SAT-layer explanation;
- final source-goal transport through intermediate arithmetic/equality
  consequences;
- proof compression and intelligible declarative script output after native
  reconstruction.

The current problem is not lack of one more formula recognizer. The missing
piece is a disciplined source/preprocessing certificate layer whose rules have
explicit semantics, required Vampire fields, and native Megalodon proof-term
elaboration.

## Current Skolemization Status

Skolemization has improved substantially since the early reports.

Earlier problems:

- generated Skolem names were treated too much like original symbols;
- dependencies were inferred from names or formulas;
- generated witnesses escaped their intended binder scopes;
- delayed sibling formulas in CPS-style replay lost fresh binders;
- de Bruijn-like scope issues produced invalid proof terms;
- final dependent Skolem transport often failed after a local fix.

Current improvements:

- Vampire emits explicit Skolem contract metadata.
- Generated Skolem dependencies and introduced witnesses are represented in
  the certificate.
- Megalodon preserves branch binders and contract variables in several
  formerly failing CPS paths.
- Megalodon avoids installing context-dependent epsilon witnesses as arity-zero
  global definitions.
- Some focused Skolem proof-term frontier tests now get past earlier blockers.

Remaining limitations:

- There is not yet a fully general Skolemization proof rule.
- Dependent Skolem functions remain hard, especially when later
  paramodulation/equality transport unfolds or compares them.
- Source-connected Skolemization, where the transformation is composed all the
  way from original formula to clause refutation and then back to the original
  theorem, remains incomplete.

This is one of the right places to continue work, but only with explicit
Vampire-owned metadata and proof-producing Megalodon rules. It should not be
handled by name guessing or broad Megalodon-side search.

- The source map includes known lemmas such as `nat_p_omega`, `omega_SNo`,
  `SNo_eps_SNoS_omega`, `add_SNo_SNoS_omega`, `add_SNo_1_ordsucc`,

- The certificate/preprocess path gets far enough that Skolem proof replay is

- The final source-goal reconstruction now reaches wrong-proposition

- Equality-symmetry transport is attempted where applicable, but it does not

This failure is useful because it separates two issues:

- native certificate/preprocess replay can succeed;
- final source-goal transport back to the original theorem can still fail.

An attempted broad generic source-premise closure search was rejected because

### Late July 19 Refresh: Native Local-Hypothesis Binding

Commit `3466f58` turns the local-hypothesis experiment into committed
implementation. The motivating failure was `11925:125`, whose exported THF
contains local facts:

```text
% megalodon_source_map (local_type "k_tp" "k" "")
thf(k_tp,type,(k : $i)).
% megalodon_source_map (local_fact "c_Lek" "Lek" "")
thf(c_Lek,axiom,(c_SNo @ (eps_5F @ k))).
% megalodon_source_map (local_fact "c_Hk" "Hk" "")
thf(c_Hk,axiom,((c_In @ k) @ omega)).
```

The investigation found a real context-indexing issue:

- if local source proofs are fed into native preprocess/core without live
  external hypotheses, proof checking fails with a proof-hypothesis index
  out-of-bounds error;
- if the live Megalodon proof context is passed directly as external
  hypotheses, the local hypothesis is in scope but its proposition is indexed
  differently from the exported certificate proposition;
- blindly shifting those external hypotheses by the full certificate variable
  context overshoots the target index and is known wrong.

The committed correction is to build the external-hypothesis list from
`Vampire_source_context.LocalHyp` entries by local proof index, but to use the
certificate-side source proposition computed in the native certificate
context. This gives native preprocess/core checking the proposition it expects
without pretending that the live local context can be blindly inserted under
all certificate variables.

The same commit leaves the final proof obligation checked against the live
Megalodon goal. It does not turn local facts into global facts and it does not
introduce a certificate-derived `Known` theorem.

## Current Test Discipline

The current test discipline is better than the early iterative workflow.

Principles:

- use `/project/tmp` for generated artifacts;
- do not repeatedly rerun slow Vampire searches when cached certificates are
  enough;
- use Vampire timeout at most 10 seconds per problem;
- export batches where possible;
- run Vampire and certificate checks in parallel, usually with 10 workers;
- classify evidence explicitly as E1, E2, E3, or E4;
- run broad structural tests less often than focused proof-term tests;
- do not count `aby`, `admit`, incomplete QED, bridge assumptions, or
  certificate-derived `Known` propositions;
- assume classical logic and use the available `xm`;
- use Megalodon's native logical constants and equality rather than private
  replacements.

Problems remaining in the test setup:

- There is still no committed broad E1 harness.
- Some important live target commands still use `-allowincompleteqed` because
  they run inside larger files with unrelated incomplete proofs.
- The huge number of untracked generated hammer files in the worktree makes
  status noisy.
- The old broad integration numbers are not comparable with the newer counted
  proof-term numbers.

## What Is General and What Is Not

The user has repeatedly asked whether the implementation is becoming
hardwired to the current library. That is a valid concern.

General work:

- source-map parsing and semantic formula checking;
- resolving global facts by hash;
- representing local facts as local hypotheses;
- generated equality/reflexivity handling;
- native proof-term checking with `Syntax.pf`;
- rejecting certificate-derived `Known`;
- Vampire-side emission of substitutions, pivots, positions, parent formulas,
  result clauses, Skolem dependencies, and branch contracts;
- `kernel_v1` metadata audits.

Risky or not-yet-general work:

- any proof search in Megalodon that tries to rediscover source consequences
  without explicit certificate guidance;
- broad source-premise closure over all source lemmas;
- ad hoc reconstruction of arithmetic/set-theoretic intermediate facts;
- specialized textual disjunction reshaping helpers;
- one-off fixes for individual hammer targets;
- relying on theorem names such as `omega_SNo` or `mul_SNo_distrL` in the
  reconstruction logic.

The current committed code does not intentionally hardwire the large failing
target's theorem names. The failed broad closure experiment was deliberately
not committed because it moved in the wrong direction: it was too slow and too
close to a Megalodon-side prover.

The next source-goal fix should be general but narrow:

- use the exact remaining source bindings and expected goal shape;
- instantiate source facts only with terms already present in the goal,
  certificate, or source context;
- avoid unrestricted recursive closure;
- produce checked proof terms for each derived intermediate fact;
- fail quickly when no guided reconstruction exists.

## Prover9/Ivy Path Status

The audits repeatedly recommended a Prover9/Ivy-style direction. The branch is
partially on that path, but not enough.

What has moved toward that path:

- Vampire emits richer proof data instead of expecting Megalodon to guess.
- `kernel_v1` records identify rule kinds, parents, substitutions, selected
  literals, result clauses, rewrite fields, and Skolem transformation data.
- Megalodon has native proof-term checks for a small subset.
- Broad metadata audits enforce required fields for many rule families.

What is still missing:

- A small first-class Vampire-side `MegalodonKernelStep` list that macro
  inferences lower into.
- A stable primitive calculus with a small set of constructors.
- A separate Megalodon module that checks only that primitive calculus and
  elaborates it to `Syntax.pf`.
- A proof-transformation pass in Vampire analogous to Prover9's lowering of
  hyper-resolution, demodulation, and other macros into Ivy-checkable
  resolution/paramodulation steps.
- A clean separation between clausal kernel proof objects and source/
  preprocessing transformations.

The current `kernel_v1` metadata is useful but still too attached to the
large existing exporter. It is not yet the final small certificate language.

## Recommended Architecture From Here

The architecture should be:

```text
Original Megalodon context
  -> THF/TPTP export with lossless source map
  -> Vampire search, timeout <= 10 seconds
  -> Vampire proof normalization into small certificate objects
  -> Megalodon source/preprocessing proof layer
  -> Megalodon clausal kernel proof layer
  -> final composition into the original theorem goal
  -> Megalodon kernel check of the final Syntax.pf
```

The clausal kernel should remain small. A reasonable first set is:

- input from an already proved source/preprocessing clause;
- explicit instantiation/substitution;
- alpha-renaming;
- binary resolution;
- factoring;
- equality resolution;
- equality factoring;
- paramodulation/superposition with exact position and orientation;
- reflexive simplification;
- contradiction/empty-clause close.

Macro rules should be lowered in Vampire:

- unit-resulting resolution -> binary resolution chain;
- hyper-resolution -> binary resolution chain;
- demodulation -> paramodulation/simplification proof;
- subsumption resolution -> primitive resolution/factoring chain;
- AVATAR -> separate propositional certificate layer, not mixed into the
  first clausal MVP;
- Skolemization -> separate source/preprocessing transformation certificate.

The source/preprocessing layer should have separate rules for:

- source input from `Known hash`;
- local hypothesis input from `Hyp`;
- generated equality/reflexivity input;
- definitions/conversions;
- conjecture negation and final contradiction-to-goal transport;
- rectification;
- FOOL;
- ENNF;
- CNF projection;
- Skolemization.

Each rule needs:

- exact certificate syntax;
- semantic meaning;
- required Vampire fields;
- Megalodon proof-term elaboration;
- positive tests;
- negative tests;
- failure mode when unsupported.

## Immediate Technical Priorities

### 1. Make Original-Context Closure the Main Milestone

Do not optimize for another broad structural pass count. The next real
milestone should be:

```text
10 original-context Megalodon theorem sites reconstructed by the native
Vampire certificate path, with no aby, no admit, no incomplete QED in the
counted theorem, no bridge assumptions, no certificate-derived Known, and
Vampire timeout <= 10 seconds.
```

The target should then increase to 100 only after the 10 are committed and
reproducible.

### 2. Finish the Source-Context API

The source context should become an explicit typed object:

```ocaml
type source_proof =
  | GlobalKnown of string * Syntax.tm
  | LocalHyp of int * string * Syntax.tm
  | Definition of string * Syntax.tm * Syntax.pf
  | Generated of string * Syntax.tm * Syntax.pf
  | Conjecture of string * Syntax.tm
```

The current `vampire_source_context.ml` is close to this direction. The
remaining work is to make final theorem composition consume this object
uniformly.

### 3. Solve Final Goal Transport Narrowly

The `11925:125` failure should be used as a representative blocker, but not as
a reason to hardwire its lemmas.

The desired fix is a guided proof-producing source transport:

- collect candidate terms from the current goal, certificate result, and
  source bindings;
- instantiate only source facts whose conclusion can match the needed premise
  or goal;
- recursively solve premises only through already available source proofs or
  very small checked instantiation/application chains;
- cap the search aggressively;
- emit `Syntax.pf` at each step;
- fail quickly when the certificate does not provide enough guidance.

The rejected broad closure experiment showed that unrestricted source-premise
search is too slow and architecturally wrong.

### 4. Continue Skolemization, But Only With Explicit Contracts

Skolemization should remain a major focus. The correct path is:

- Vampire emits dependencies, sorts, introduced symbols, parent/child formulas,
  branch contracts, and witness contracts.
- Megalodon checks a local transformation theorem using classical choice and
  `xm`.
- Generated Skolem symbols remain generated certificate symbols, not original
  variables or arbitrary globals.
- Dependent Skolem definitions unfold only under the correct context.

Avoid name-based Skolem dependency recovery.

### 5. Extract the Small Kernel

The next architectural cleanup should extract the genuine native proof-term
seed into smaller modules:

- `vampire_kernel_syntax.ml`
- `vampire_kernel_check.ml`
- `vampire_kernel_elab.ml`
- `vampire_source_context.ml`
- `vampire_preprocess_elab.ml`

The existing `vampire_cert_v1.ml` can remain as a legacy parser/oracle during
the migration, but new counted proof-term logic should stop accumulating
there.

On the Vampire side, a corresponding `MegalodonKernelStep` builder should be
introduced and used by macro expansions before printing. The current
`MegalodonKernelSyntax.*` files are a start, but the main exporter still owns
too much of the logic.

## Current Blockers

### Blocker 1: No Broad E1 Suite

There is still no 100-theorem original-context suite. There is not yet even a
committed 10-theorem original-context suite under the strict final criteria.

### Blocker 2: Final Source-Goal Composition

The branch can check selected exported/preprocess refutations but still fail
to turn them into a proof of the exact original goal. The `11925:125` failure
is the current representative.

### Blocker 3: Incomplete Smolka-Style Transformations

FOOL, ENNF, CNF, broad definitions, generated facts, and Skolemization need
explicit proof-producing rules. They are not solved by structural metadata
alone.

### Blocker 4: Monolith Growth

The importer and exporter remain too large:

- `src/vampire_cert_v1.ml`: about 32,800 lines.
- `Shell/MegalodonChecker/MegalodonChecker.cpp`: about 25,980 lines.

This makes expert review and trust-boundary reasoning harder. The next phase
should reduce or isolate the proof-critical core, not add thousands more lines
to those files.

### Blocker 5: Primitive Proof Object Not Yet Stable

`kernel_v1` records provide useful data, but they are not yet a finalized
Ivy-like proof object. The project needs a small specification and a
Vampire-side lowering pass.
