## Executive Summary

The original project goal is still not complete.

The requested endpoint is:

```text
Original Megalodon theorem and source context
  -> THF/TPTP export
  -> Vampire proof search with <= 10 seconds per problem
  -> detailed Vampire proof certificate
  -> Megalodon parser and checker
  -> native Megalodon Syntax.pf proof term
  -> checked proof of the original theorem at the original Megalodon site
```

The current branches do not yet provide a 100-theorem original-context suite
with no `aby`, no `admit`, no incomplete QED, no bridge assumptions, no
certificate-derived trusted theorems, and no Python proof production.

There has been real progress, but the progress should be classified
carefully:

- The early Python/script route produced useful proof skeletons and
  diagnostics, but it is not a qualifying proof-reconstruction path.
- The current implementation is much closer to the Prover9/Ivy direction:
  Vampire emits richer certificate data, Megalodon parses S-expression
  certificates, and Megalodon constructs native proof terms for several
  checked fragments.
- The source-context layer is materially better than it was: it distinguishes
  global source facts, local hypotheses, definitions, generated facts,
  conjecture facts, unresolved facts, and `set`-generated reflexivity facts.
- The trust-boundary problem identified by the July 16 audit has been partly
  addressed: counted native paths are intended to reject arbitrary
  certificate-derived `Known "vampire_*"` propositions.
- Recent focused work closes four source-linked/native proof-term targets:
  `172:4`, `183:4`, `233:4`, and `10654:21`.
- The standard-Skolemization direction is now committed in Vampire and
  reflected in Megalodon live-test defaults. A 35-case Skolem-focused live
  frontier now reports `SKOLEM_PF_PASS 35`.
- A tracked known-solvable strict 100-case gate now passes with 20-way
  parallel live Vampire runs, strict certificate validation, source-map
  checking, primitive audits, and `kernel_v1` metadata audits.
- The 100-case gate is still E4 integration evidence, not 100 original
  Megalodon theorem proofs. It says that 100 known-solvable THF problems can
  be regenerated and structurally checked with rich metadata.
- A separate 176-case probe produced `PASS 123 / FAIL 17 / TIMEOUT 36`. The
  original 17 failures were useful frontier cases: Skolem explicit
  substitution mismatches, equality-resolution metadata/parent issues,
  superposition missing-parent metadata, and two subsumption-resolution
  contract problems.
- The now-committed equality-resolution metadata, Skolem normalization,
  split-backed superposition-parent, and subsumption direct-chain work closes
  the former 17-case frontier at the current strict certificate/metadata
  level. The latest focused rerun of the last two frontier cases reports
  `PASS 2`, and the former 17-case frontier reports `PASS 17`.

The best description of the current state is:

```text
Architecture: directionally correct, still too monolithic.
Source linkage: partial and improving, not complete E1 composition.
Smolka/source transformations: partial proof-producing support, not a clean
  standalone layer.
Skolemization: much improved; the focused frontier passes, and the specific
  eight-case explicit-substitution frontier from July 19 now passes under
  strict certificate/source-map checking.
Clausal kernel: real seed exists, but Vampire has not yet fully lowered macro
  inferences to a minimal Ivy-like primitive object.
Testing: much better parallel/cached discipline, including a tracked strict
  100-case E4 gate, but no qualifying 100 E1 suite.
```

The recommended next direction is not another broad Megalodon-side replay
heuristic. The next direction should be a sharper Prover9/Ivy-style proof
object:

```text
Vampire C++:
  define and emit a small typed primitive certificate object, including exact
  parents, substitutions, positions, selected literals, orientations, sorts,
  branch witnesses, and preprocessing payloads.

Megalodon OCaml:
  parse that object, resolve original source facts, check Smolka-style
  transformations and clausal primitive steps, elaborate Syntax.pf, and run
  Megalodon's own checker.
```

## Evidence Classes

The reports now use evidence classes because earlier reports and harnesses
overstated structural success as proof reconstruction.

E1 is the actual goal:

```text
Original-context proof reconstruction. The proof term checks inside the
original Megalodon development and proves the original theorem at the original
site. No aby, admit, incomplete QED, bridge assumption, certificate-local
trusted theorem, or Python proof construction is used.
```

E2 is exported-bound native reconstruction:

```text
A native Megalodon Syntax.pf proof term checks a live Vampire certificate
against the exported THF/TPTP problem, but the result has not yet been
composed back into the original theorem command.
```

E3 is focused proof-term evidence:

```text
A synthetic or focused live certificate exercises native Syntax.pf
elaboration for a small-kernel rule, source-context operation, or
source/preprocessing transformation.
```

E4 is structural and integration evidence:

```text
Vampire proves or times out on exported THF problems; Megalodon parses
certificates, validates metadata, validates source maps, audits expected
fields, and classifies failures. This is important engineering evidence, but
it is not proof reconstruction unless native proof terms are also built and
checked.
```

Current evidence should be classified as follows:

- The focused four-target native-aby gate is E3.
- The tracked known-solvable strict 100-case gate is E4. It validates live
  Vampire solving, source maps, native primitive records, and `kernel_v1`
  metadata for 100 known-solvable THF problems, but does not compose proofs
  back into original Megalodon theorem sites.
- The 35/35 Skolem proof-term frontier is E3, because it is a focused closed
  frontier rather than original theorem composition.
- There is no broad E1 result.

This classification is not cosmetic. It is necessary to avoid repeating the
earlier mistake where a structural or bridge-backed check was described as
proof reconstruction.

## User Requirements and Standing Constraints

The implementation has been guided by these non-negotiable requirements:

- Use THF/TPTP exports from Megalodon.
- Run Vampire on THF/TPTP input.
- Use a per-problem Vampire timeout of at most 10 seconds.
- Avoid rerunning known-unsolved Vampire searches during iteration.
- Export problems in bulk when practical, run Vampire in parallel, and check
  certificates in parallel.
- Use `/project/tmp` for all temporary artifacts and generated test output.
- Use 10 to 20 workers for independent problem runs when the harness permits.
- Do not use `aby` in resulting scripts or proof terms. In Megalodon, `aby`
  is admission.
- Do not use `admit`.
- Do not use incomplete QED in a counted proof.
- Assume the setting is classical; `xm` is available.
- Use Megalodon's own equality, `False`, disjunction, and other logical
  constants from the loaded library/context. Do not introduce a private
  object logic.
- Do not hardwire Megalodon library symbols such as `famunion` into proof
  reconstruction.
- Prefer Vampire-side rich proof/certificate detail over Python or OCaml
  guessing.
- Follow the Prover9/Ivy pattern: expand prover inferences into a small,
  checkable proof object while the prover still knows exact inference data.

The current branch follows these constraints better than the early work, but
not completely. The main remaining violation in spirit is that too much
logic still resides in large Megalodon-side replay procedures instead of in a
small, explicit certificate checker.

## Historical Approach

### Initial Python and Skeleton Phase

The first working route parsed Vampire output outside Vampire and produced
Megalodon proof skeletons. These skeletons used `claim` blocks and could
contain `admit` placeholders. They were useful for human inspection because
they gave a shape to the proof:

- the original conjecture was visible;
- source axioms and lemmas appeared under recoverable names;
- Vampire proof units were listed;
- common inference classes became visible;
- missing reconstruction work could be counted roughly.

The skeleton route was never a sound endpoint. It had these defects:

- it inferred too much from pretty-printed proof text;
- it did not use Vampire's internal typed proof data;
- it encouraged another prover-like reconstruction engine in Python;
- it could produce human-readable progress with no kernel proof;
- it relied on placeholders;
- it did not prove the original Megalodon theorem.

The user pushed correctly against this route. The skeletons should now be
viewed only as diagnostics and possible human-facing output after a native
certificate has already checked.

### Batch and Parallel Test Phase

The second correction was test discipline. Iterating by repeatedly invoking
Vampire on the same hard or unsolved problems was too slow and obscured the
real reconstruction failures.

The better test shape is now:

```text
1. Export all candidate Megalodon obligations once.
2. Run Vampire over the THF files in parallel with -t 10.
3. Cache which problems Vampire solved.
4. Iterate only on the solved subset for reconstruction.
5. Run Megalodon certificate checks in parallel.
6. Keep all generated outputs under /project/tmp.
```

This shape is used by the current `run_native_live_parallel.sh`,
`run_native_live_skolem_pf_frontier.sh`, and native-aby target harnesses.
The harnesses still need clearer evidence labels in their output, but their
basic parallel/cached shape is now aligned with the user request.

### Trust-Boundary Reset

The July 16 audit identified the most important correctness bug in the
native preprocessing route. Some proof-term checks succeeded because the
importer dynamically installed exactly the proposition it needed as a
generated `Known` theorem and then applied it.

That is equivalent to a hidden bridge assumption. It is not proof
reconstruction.

The current counted direction rejects certificate-derived dynamic knowns in
native proof-term paths. Transitional behavior remains useful for structural
debugging only, and should never be counted as E1 or E2.

This reset is one of the most important improvements in the project. It
forced the reports to distinguish:

- structural certificate validation;
- native AST plumbing;
- native proof-term construction;
- original-context theorem reconstruction.

### Prover9/Ivy Pivot

The Prover9 analysis found the right model. Prover9's Ivy output is not just
a printer. The Prover9 pipeline first expands complex justifications into
more atomic proof steps, then lowers them into a small proof-object language
with rules such as input, instantiate, flip, resolve, paramodulate,
propositional, and limited new-symbol introduction.

The lesson for this project is direct:

```text
Do not ask Megalodon or Python to rediscover substitutions, rewrite
positions, literal choices, branch witness scopes, or orientation choices from
pretty text. Make Vampire emit that information while it still has it.
```

The current Vampire fork is moving in that direction. It emits a
Megalodon-oriented S-expression certificate and a growing set of `kernel_v1`
metadata records. It also has a `MegalodonKernelSyntax` boundary. But this is
still a migration layer, not the final primitive IR.

The final design should look more like:

```text
Vampire proof DAG
  -> Vampire-side macro expansion / primitive detailing
  -> canonical S-expression proof object
  -> Megalodon small checker
  -> Megalodon Syntax.pf elaboration
```

Relevant Megalodon files include:

- `src/vampire_cert_v1.ml`
- `src/vampire_kernel_syntax.ml`
- `src/vampire_kernel_syntax.mli`
- `src/vampire_source_context.ml`
- `src/vampire_source_context.mli`

The Megalodon side can:

- parse native S-expression certificates;
- parse source maps and origin metadata;
- validate source names and several source/hash relationships;
- parse and validate `kernel_v1` metadata;
- construct native `Syntax.pf` proof terms for selected clausal and
  preprocessing fragments;
- reject arbitrary certificate-derived `Known "vampire_*"` terms in counted
  native paths;
- resolve some global facts against the Megalodon loaded context;
- carry local source hypotheses as proof assumptions instead of treating them
  as global facts;
- reify source free variables in external hypotheses;
- register some Skolem witnesses as epsilon/choice definitions;
- normalize selected grouped Skolem/AVATAR continuation targets;
- check current-goal proof candidates with Megalodon's own proof checker.

The main limitation is also structural: too much remains in
`src/vampire_cert_v1.ml` and adjacent code in `src/megalodon.ml`. The
audited target is a split into smaller modules:

- certificate syntax and parser;
- source context resolver;
- Smolka/source-preprocessing checker;
- clausal primitive kernel checker;
- proof-term elaborator;
- original-context composer.

### Source Context

The source-context work is one of the most important parts of the project.
The final reconstruction must prove the original Megalodon theorem, not just
an exported THF problem.

Current implemented or partial source-context features:

- source labels are preserved through export and certificate import;
- source origin comments are parsed and classified;
- raw, normalized, and hash-prefixed aliases are used for lookup;
- global source facts can resolve to known Megalodon facts;
- local source hypotheses are represented as local proof assumptions;
- local definitions can be recognized in some contexts;
- generated facts are classified separately from user lemmas;
- source variables are reified in external hypotheses;
- unresolved source facts are visible in diagnostics;
- source-map checks can be required in live harnesses.

Current missing pieces:

- complete original-context composition for a broad suite;
- proof supply for every `formula_input`;
- proof supply for every `formula_term_input`;
- complete local definition unfolding/conversion;
- committed proof-producing handling for every `set` equality;
- hard failure on every unresolved source fact in E1 mode;
- final insertion of the returned proof at the exact original theorem site;
- robust semantic comparison of every certificate source proposition against
  the original Megalodon source proposition.

The current state is therefore partial: the right categories exist, but the
E1 composer is not finished.

### Smolka-Style Transformation Layer

The Smolka-style layer is the proof-producing path from original formulas to
the clauses consumed by the clausal kernel. It is not the clausal kernel
itself.

The transformations include:

- source input;
- definition input;
- set-generated equality/reflexivity input;
- conjecture negation;
- rectification;
- FOOL and Boolean normalization;
- ENNF;
- CNF projection;
- predicate definition and folding;
- Skolemization;
- variable instantiation and renaming;
- selected AVATAR preprocessing facts.

The current branch has partial proof-producing support for source entry,
several formula transformations, predicate definition/fold shapes, and many
Skolem-focused closed cases. It does not have a clean standalone Smolka
checker.

The intended design is:

```text
source/preprocessing certificate record
  -> checked logical transformation proof
  -> clause theorem supplied to clausal primitive kernel
```

The checker should rely on a small set of reviewed principles:

- implication introduction and application;
- universal introduction and application;
- existential elimination or choice introduction in the classical setting;
- equality reflexivity and conversion;
- definition unfolding and folding;
- proposition extensionality where Megalodon provides it;
- classical principles through `xm`;
- Boolean and FOOL library lemmas from the Megalodon context.

This layer is the main current gap between structural success and real E1
proof reconstruction.

After the earlier report refresh `d82ad38`, the work first focused on one of

that was attached to the final Vampire unit even when the native certificate
expanded the unit through helper steps. That work was committed in Vampire

The representative failure was `hammer.10863.46`, step `u290`. The native
certificate contained an actual primitive sequence of the following shape:

```text
equality_resolution "u290_eqres" from parent "u290_subst"
equality_symmetry "u290" from parent "u290_eqres"
```

The emitted `kernel_v1` metadata, however, still annotated `u290` as though
it were itself the equality-resolution step. Megalodon's strict checker was
right to reject that: the metadata rule must describe the certificate step it
annotates, not a later helper or final symmetry step.

The Vampire patch changes the certificate emission so
`certificateEqualityResolutionStepSexpr` returns the actual primitive step id
and result clause when an equality-resolution unit is replayed through helper
steps. `printReplayExtra` can then emit the `kernel_v1` metadata under the
native primitive id, for example `u290_eqres`, rather than blindly under the
final unit id. This is a Prover9/Ivy-style correction: make the proof object
expose the actual low-level step rather than making Megalodon infer the hidden
helper chain.

The same patch adds a fail-closed guard for superposition metadata. If Vampire
cannot emit all required fields for a superposition contract, including
selected parents, literal indices, rewrite position, orientation, substituted
literals, and rewritten target, it now withholds the incomplete `kernel_v1`
record instead of emitting a record that looks authoritative but cannot be
checked. This is deliberately conservative; missing detail should produce an
unsupported-frontier case, not a misleading proof object.

## Source Linking Status

The current source-linking work is materially better than at the time of the
early audits, but it is still not complete.

### What Works or Partially Works

Global source facts:

- exported source ids and aliases are preserved;
- hash-backed global facts can be resolved against the Megalodon loaded
  signature/context;
- source-map aliases handle several naming forms.

Local hypotheses:

- local source facts are no longer forced into global known facts;
- they are carried as external hypotheses at the original-context boundary;
- source free variables are reified so local facts can be consumed at the
  right de Bruijn depth.

Definitions:

- local and external definition names are recognized in the source context;
- some unfolding/conversion support exists;
- definition-generated facts are classified separately from user lemmas.

Generated facts:

- `set`-generated facts are classified separately;
- the intended handling is reflexivity or definitional conversion;
- the source context knows that these are not ordinary user-written claims.

Conjecture:

- the conjecture is distinguished from source axioms;
- the intended final refutation wrapper introduces the negated conjecture
  rather than trusting it as a source lemma.

### What Is Missing

The E1 composer still needs to ensure:

- every certificate source input is supplied by a real proof object;
- every local hypothesis is mapped to a proof-context index with correct
  shifting;
- every local definition is supplied by unfolding/conversion;
- every `set` fact is proved by reflexivity/conversion;
- unresolved facts are hard failures;
- the negated conjecture is discharged only by the final refutation-to-goal
  conversion;
- no source source id is accepted merely because its label matches;
- source proposition equality is checked semantically, not only by comments
  or displayed names.

The current status is therefore:

```text
Source categories: implemented or partially implemented.
Source proof supply: partial.
Original theorem composition: not complete.
Broad E1 gate: not present.
```

## Set-Generated Equalities

The user correctly pointed out that some TPTP axioms come from Megalodon
`set` commands. These often do not correspond to user-written claims.

They should be handled as generated proof obligations:

```text
set-generated equality -> Megalodon reflexivity/conversion proof
```

They must not be treated as arbitrary source axioms. The correct source input
classification is:

```text
user theorem or lemma        -> resolve to original proof
local source hypothesis      -> consume as local assumption
source definition            -> prove by unfolding/conversion
set-generated equality       -> prove by reflexivity/conversion
negated conjecture           -> introduce in final refutation wrapper
preprocessing-generated fact -> prove in Smolka/source layer
```

The code has the classification machinery and a generated reflexivity proof
path for some equality-shaped facts. The remaining work is to make this
complete and required in E1 mode.

## Equality Status

The final reconstruction should use Megalodon's equality directly. It should
not introduce a private equality predicate or a private object logic.

The intended interpretation is:

- TPTP equality wrappers are parser/export syntax;
- Megalodon terms should map them to Megalodon's actual equality;
- equality transformations should be proved using Megalodon equality rules
  and conversion;
- proposition equality can use Megalodon's existing logical/equality
  principles, including proposition extensionality if available;
- no counted path should trust a certificate-local equality theorem.

Some internal displays look like:

```text
((eq prop) A B)
```

That is an internal typed representation of equality at a type, not an
intended new object logic. The reviewer should still audit all counted
equality paths to ensure they ultimately use the real Megalodon equality.

## Skolemization Status

Skolemization has been the most persistent hard problem.

### What Has Improved

Vampire now emits significantly richer Skolem metadata:

- source formulas;
- result formulas;
- child formulas;
- macro-edge records;
- branch records;
- introduced witness records;
- free-variable records;
- quantified-variable records;
- parent step variables;
- parent instantiations;
- branch binder instantiations;
- branch proposition roles;
- branch choice witness terms.

Megalodon now uses this metadata to:

- parse typed Skolem contracts;
- register nullary witnesses as epsilon/choice definitions in narrow cases;
- register dependent witnesses when dependencies and types are known;
- register compact named-body witnesses;
- preserve variables that Vampire says remain in the result;
- avoid duplicating result-context binders already printed as result
  quantifiers;
- normalize grouped Skolem/AVATAR target propositions with witness and split
  replacements;
- fail closed when a replacement does not type-check or does not prove the
  target proposition.

The 35/35 Skolem frontier is evidence that this work is not just cosmetic.

### What Remains Open

The unresolved Skolemization work includes:

- dependent Skolem functions under branch contexts;
- multiple simultaneous witnesses;
- alignment of dependency binders across source, branch, parent, and result
  formulas;
- substitution of witness definitions through AVATAR continuations;
- proof-term opening after witness replacement;
- stale certificate-local choice witnesses inside stored formulas;
- symbol alias normalization at final proof application boundaries;
- a small explicit Skolem proof object rather than a large replay procedure.

The broader 176-case probe still exposes Skolem issues, but the current shape
is more specific than the earlier crash frontier: several cases fail because
the checker cannot match the result against Vampire's explicit Skolem
substitution record. That is exactly the kind of mismatch that should be
solved by richer Vampire-emitted source/preprocessing objects, not by
guessing from formulas on the Megalodon side.

The design lesson is the same as before:

```text
Skolemization should be an explicit source/preprocessing proof object with
typed witness declarations, dependency binders, branch propositions, and
instantiations emitted by Vampire. Megalodon should check that object; it
should not infer it from final formulas.
```

## Smolka-Style Transformations

The Smolka-style transformation pipeline remains incomplete, but the project
now has a clearer understanding of what it must contain.

The transformation layer should prove that the clauses used by Vampire are
valid consequences of the original Megalodon formulas. It should not be
hidden inside the clausal kernel.

A plausible structure is:

```text
SourceContext.resolve(input)
  -> source theorem or local hypothesis proof

Preprocess.rectify(record)
  -> alpha/renaming proof

Preprocess.fool(record)
  -> Boolean lifting or logical normalization proof

Preprocess.ennf(record)
  -> classical negation-normalization proof

Preprocess.cnf(record)
  -> projection from a transformed formula to a clause

Preprocess.definition(record)
  -> definition intro/fold/unfold proof

Preprocess.skolem(record)
  -> classical choice/epsilon proof with explicit witness object

Kernel.check(primitive_clause_steps)
  -> refutation from checked clauses

OriginalContext.compose(refutation)
  -> proof of original theorem
```

The current implementation contains pieces of this, but not the clean
pipeline. The biggest problem is not missing syntax. It is boundary control:
each transformation needs a small record, a checker, and a proof-term
constructor that can be reviewed locally.

The immediate Smolka priority should be:

1. Complete source input proof supply for one focused theorem.
2. Complete `set` reflexivity/conversion proof supply.
3. Specify the Skolem branch proof object.
4. Move Skolem/branch checking out of broad replay code into a small local
   checker.
5. Only then expand coverage.

## Clausal Kernel Status

The intended clausal kernel should remain close to Ivy:

- input boundary from source/preprocessing layer;
- instantiate;
- alpha/rename or incorporated instantiation;
- literal flip/orientation;
- resolve;
- factor;
- equality resolution;
- equality factoring;
- paramodulate/superposition as equality transport at an explicit position;
- final contradiction/empty clause marker.

The kernel should not absorb all of Vampire's macros. For example:

- unit-resulting resolution should lower to binary resolve steps;
- demodulation and definition rewrite chains should lower to explicit rewrite
  or paramodulation steps with exact positions;
- superposition should expose instantiated parents, selected sides, and
  positions;
- factoring/condensation should become small propositional or factor steps;
- AVATAR should be either separate SAT/RUP evidence or a tiny AVATAR layer.

The current kernel support is real but incomplete. Synthetic and focused
fixtures exercise native `Syntax.pf` construction for several rules. Real
hammer proofs still often stop in source/preprocessing before broad clausal
kernel coverage becomes the main bottleneck.

The next Vampire-side kernel task should not be "print another ad hoc field".
It should be:

```text
Create a typed primitive-step builder and make at least one frequent macro
emit a primitive expansion through that builder before printing.
```

Unit-resulting resolution remains a good first macro-lowering target because
it naturally lowers to binary resolution and appears often in real proofs.

## AVATAR Status

AVATAR is partly represented and partly checked, but it is not solved.

Currently:

- Vampire emits AVATAR-related metadata;
- Megalodon recognizes split definitions and components in some paths;
- split dependency metadata can be audited;
- split-backed primitive records are now accepted when they validate;
- grouped Skolem/AVATAR target normalization exists in focused cases.

Still missing:

- complete SAT/RUP or equivalent evidence for AVATAR decisions;
- small checked split-dependency proof object;
- explicit separation between AVATAR split assumptions and Skolem branch
  assumptions;
- original-context composition through AVATAR;
- broad E1 coverage for AVATAR-heavy proofs.

The current recommendation is to avoid making AVATAR a hidden macro in the
Skolem checker. It should have a separate certificate object or lower to
ordinary clauses plus SAT/RUP evidence.

## Python, Lisp, and OCaml

The audits' language recommendation has sometimes caused confusion.

The intended roles are:

- Lisp-like means the certificate surface should be a simple S-expression or
  equivalent data object, not JSON-driven proof scripting.
- OCaml is the right implementation language for Megalodon's checker and
  proof-term construction because Megalodon is implemented in OCaml.
- Python is acceptable for orchestration, log classification, and temporary
  diagnostics, but not for producing qualifying proofs.

The current project uses a Lisp-like S-expression certificate surface and
OCaml-side checking. That is aligned with the audit in form.

The remaining problem is not that OCaml exists. The problem is that the OCaml
checker is still too monolithic and too reconstruction-heavy. It must be
split into smaller auditable modules and should consume exact Vampire
primitive data rather than infer missing proof details.

## Current Problems

### Problem 1: No E1 Milestone

There is still no committed gate proving even ten original Megalodon
theorems end-to-end in their original contexts. This should be the next
major visible milestone before any claim about 100 theorems.

### Problem 2: Monolith Growth

Both sides have large central files:

- Megalodon: `src/vampire_cert_v1.ml` and related code in `src/megalodon.ml`;
- Vampire: `Shell/MegalodonChecker/MegalodonChecker.cpp`.

Some growth was necessary to expose proof data and test the boundaries, but
the audit's warning still applies. The project should now extract, not
continue expanding, broad replay logic.

### Problem 3: Skolem Branch Proof Object Missing

Recent Skolem work emits much more metadata and closes many focused cases,
but it is not yet a clean proof object. The branch proof context should be
first-class:

- which assumptions are opened at each branch;
- which variables are term binders;
- which variables are proof binders;
- which witness definitions are active;
- how branch-local witnesses are abstracted;
- how parent and branch instantiations are applied;
- what exact proposition each continuation consumes.

### Problem 4: Skolem Proof Object Still Not Standalone

The standard-Skolemization direction is now committed, the focused Skolem
frontier passes, and the eight explicit-substitution failures from the
July 19 17-case frontier now pass after equality-leaf normalization. This is
real progress, but it is still not the same as a clean Smolka-style proof
object. Skolemization should remain a certificate contract: Vampire must emit
the exact branch/witness object, and Megalodon must check that object rather
than synthesize a plausible witness alignment by heuristic search.

### Problem 5: Source Proposition Equality

Source labels and hashes are not enough. For E1, the checker must know that
the certificate input proposition is the same proposition as the source
Megalodon theorem, hypothesis, definition, or generated fact. Name matching
is only a lookup mechanism. The proof supply must be semantic.

### Problem 6: AVATAR Is Not Cleanly Certified

AVATAR appears in realistic Vampire proofs and interacts with Skolemization.
It cannot remain an implicit split assumption mechanism. It needs either:

- SAT/RUP-style proof evidence; or
- a small dedicated AVATAR kernel.

## Recommended Next Work

### Step 1: Freeze New Megalodon-Side Heuristics

New proof-producing behavior should require:

- a named certificate object;
- exact Vampire-emitted data;
- a local checker;
- a Megalodon `Syntax.pf` constructor;
- a test that fails closed when metadata is missing.

The former 17-case frontier should remain a small, fast regression gate. It

- patch the Vampire-emitted primitive detail or the Megalodon local checker;
- rebuild Vampire with `-j10`;
- rerun the focused case or class;
- only then rerun the 17-case frontier and the strict 100 gate.

This keeps iteration on concrete certificate/checker contracts and avoids
rerunning unsolved or timeout-heavy Vampire searches.

- source formula;
- result formula;
- child formulas;
- introduced witnesses;
- witness dependency binders;
- parent step variables;
- parent instantiations;
- branch binder instantiations;
- branch proposition variables;
- branch choice bodies;

This object should be emitted by Vampire and checked by Megalodon.

- rule;
- parent ids;
- conclusion;
- selected literal indices;
- term positions;
- equality direction;
- substitution;
- variable sorts;

Start by lowering one frequent macro, preferably unit-resulting resolution,

- every source input resolved;
- every set equality proved;
- every local hypothesis mapped;

### Step 6: Expand to Ten, Then 100

Once one E1 example exists, build a ten-theorem gate. Only after ten
original-context theorems pass should the project scale to a 100-theorem E1
suite.

## What the Expert Should Review

The expert should focus on these questions:

1. Is the proposed split between source/Smolka transformations and clausal
   kernel correct?

The current recommendation is yes. Clausal rules should not absorb
Skolemization, FOOL, ENNF, source input, or AVATAR.

2. Is standard Skolemization the right default for Megalodon proof mode?

The current branch has committed standard Skolemization for Megalodon proof
mode while preserving Leancheck's syntactic-Skolemization behavior. The
expert should review whether this split is theoretically acceptable and
whether the current equality-leaf normalization is an acceptable short-term
contract check while a smaller Vampire-emitted Skolem transformation object is
specified.

3. How should Skolemization be certified?

The current recommendation is a Vampire-emitted branch/witness proof object
checked by Megalodon with classical choice/epsilon. Megalodon should not
infer the object from before/after formulas.

4. How should AVATAR be certified?

This is still open. SAT/RUP evidence is probably the cleanest long-term
choice, but a small dedicated AVATAR layer may be acceptable if it is narrow
and audited.

5. Is the current OCaml checker too large?

Yes. It has enough functionality to justify extraction. The next phase should
move proof-producing code into isolated modules, not add broad new replay
cases to `vampire_cert_v1.ml`.

6. What should count as success?

The next convincing success is a small E1 suite, not another E4 structural
run. One original-context theorem is the next hard milestone. Ten is the next
reviewable milestone. 100 comes after that.

## Outlook

The project is viable, but it is not near the original 100-theorem endpoint
in the strict sense. The main positive sign is that the failures have become
more specific:

- source categories are no longer completely opaque;
- local hypotheses are no longer treated as global facts;
- the 35-case Skolem-focused closed frontier passes;
- branch-choice metadata is now emitted by Vampire;
- the tracked known-solvable strict 100-case gate passes with primitive and
  `kernel_v1` metadata audits;
- the former 17-case strict metadata frontier now passes, so the immediate
  bottleneck has shifted from those concrete certificate-contract failures to
  original-context proof composition.

The main risk is continuing to grow Megalodon-side reconstruction code faster
than Vampire-side primitive proof objects. That would repeat the early Python
mistake in OCaml. The audits were right about this.

The practical next path is:

```text
Specify the Skolem branch proof object.
Keep the former 17-case certificate-contract frontier as a regression gate.
Move one frequent macro to a Vampire primitive IR builder.
Complete one original-context theorem.
Scale to ten original-context theorems.
Only then attempt the 100-theorem goal.
```

This report should therefore be read as a candid status and direction
document, not as a completion report. The project has moved from exploratory
proof skeletons to a plausible certificate/checker architecture, but the
strict proof-reconstruction result still remains to be delivered.
