The latest Megalodon implementation commit is deliberately small but important:
it excludes `LocalHyp` source proofs from the native core's internal
source-proof list so that local hypotheses remain explicit assumptions at the
original-context composition boundary. This is the correct ownership boundary
for theorem-local facts: they should be supplied by the original Megalodon
proof context, not reproved inside the exported Vampire certificate fragment.

This report is written for external expert review. It summarizes what has been
done, how the approach has changed, what is currently known to work, what is
still blocked, and what the next direction should be. It takes into account
the previous project reports, the audits, the audit responses, the
Prover9/Ivy analysis, the Smolka-style transformation discussion, and the
latest branch state.

The report is intentionally conservative. The original project goal is not
complete. There is still no qualifying 100-theorem suite of original
Megalodon theorems reconstructed from Vampire proofs with no `aby`, no
`admit`, no incomplete QED, no bridge assumptions, no certificate-derived
trusted theorems, and no Python proof-producing step.

## Executive Summary

The target remains:

```text
Original Megalodon theorem and context
  -> THF/TPTP export
  -> Vampire proof search, <= 10 seconds per problem
  -> detailed Vampire proof certificate
  -> Megalodon native certificate parser/checker
  -> native Megalodon Syntax.pf proof term
  -> proof of the original theorem at the original theorem site
```

That target has not yet been achieved at the required scale.

The project has nevertheless moved in the right architectural direction. The
early work produced Python-generated Megalodon proof skeletons and
placeholder-heavy scripts. Those artifacts were useful for understanding the
shape of Vampire output and for giving a human something to inspect, but they
were not a sound final path. The audits and user feedback correctly identified
that this was turning into an external reconstruction prover. The current
branch instead treats Vampire as the place where proof detail must be emitted,
while Megalodon should parse, validate, elaborate, and check a small proof
object.

The intended architecture is now:

```text
Megalodon source theorem/context
  -> THF/TPTP export with source metadata
  -> Vampire proof search
  -> Vampire-side macro detailing while exact inference data is still present
  -> Lisp-like S-expression certificate
  -> Megalodon OCaml parser and native proof-term elaborator
  -> original-context proof composition
```

This is the Prover9/Ivy-style path recommended by the audits. The work is not
fully there yet. Vampire now has the beginning of a structured
`MegalodonKernelStep` builder and a shared `MegalodonKernelSyntax` vocabulary,
but much of the certificate still contains rendered fields rather than typed
primitive objects. Megalodon has native proof-term checking for a clausal core
and several preprocessing fragments, but the implementation still lives mostly
inside large modules and still lacks a clean isolated checker boundary.

The strongest accomplishments are:

- Vampire emits a Megalodon-oriented S-expression certificate.
- Vampire emits `kernel_v1` metadata for many proof steps.
- Vampire has begun extracting certificate vocabulary and field construction
  into `MegalodonKernelSyntax` and `MegalodonKernelStep` records.
- Megalodon parses the native certificate into OCaml data structures.
- Megalodon has native `Syntax.pf` elaboration for a clausal core and selected
  preprocessing fragments.
- Counted native proof-term checks reject certificate-derived dynamic
  `Known "vampire_*"` proof constants, except for a fixed reviewed logical
  basis.
- The old transitional dynamic-known path is now treated as structural
  diagnostics, not as proof reconstruction.
- Source metadata now distinguishes global facts, local hypotheses,
  definitions, generated facts, conjecture/negated-conjecture facts,
  unresolved facts, and `set`-generated reflexivity facts.
- Megalodon `set` facts that have no corresponding source claim are recognized
  as generated reflexivity/conversion obligations in the intended path.
- Source-map aliases are threaded through more of the native checker, including
  raw, normalized, and hash-prefixed variants.
- Recent Vampire commits emit richer Skolemization and branch-binder contracts:
  source/result formulas, child formulas, macro-edge records, branch records,
  introduced witnesses, free-variable metadata, quantified-variable metadata,
  parent step variables, parent instantiations, and branch binder
  instantiations.

The strongest negative results are:

- There is no qualifying E1 100-theorem result.
- There is no committed qualifying 10-theorem original-context suite.
- Original-context composition exists only in pieces.
- The Smolka-style preprocessing layer is partial.
- Skolemization remains the hardest proof-producing transformation.
- The small-kernel certificate object is still a migration object, not a
  finished Ivy-like primitive proof object.
- Megalodon's importer/checker is still too large and still contains too much
  reconstruction logic.
- Vampire's Megalodon exporter has improved, but still needs a stronger typed
  primitive builder rather than mostly rendered certificate strings.

The representative hard target remains
`examples/hammer/100thms_12_h.mg:11925:125`. The latest focused gate still
classifies it as expected failure, while a nearby source-linked target passes:


The important current blocker is no longer missing symbol names, hardwired
library constants, or the earlier bad application of a local hypothesis proof
at the wrong de Bruijn depth. Commit `fd1b74f` reifies source-context free
variables in native external hypotheses, and commit `44d95e4` keeps local
facts as assumptions to be consumed during original-context composition. The
previous concrete mismatch:

```text
expected: ((forall _:prop, (_0 -> _0)) -> (#SNo (#eps_ _2)))
actual:   ((forall _:prop, (_0 -> _0)) -> (SNo (eps_ _5)))
```

is no longer the immediate hard failure after the local-hypothesis deferral.
The remaining failure is one step later and is more informative: after source
composition, the checker opens enough of the prefix to apply the source local
hypotheses `u83` and `u84`, recognizes the double-negated target, and then
rejects the candidate proof because it still contains a certificate-only
Skolem witness symbol. In the hard diagnostic, the core proposition first has
the expected source shape:

```text
forall _:prop,
forall _:(set -> set -> prop),
forall _:set,
  SNo (eps k) ->
  In k omega ->
  ...
```

The source-binding application then consumes:

```text
u83: SNo (eps k)
u84: In k omega
```

and reaches the double-negated target:

```text
((original target) -> false) -> false
```

The double-negation-elimination candidate is rejected because the candidate
proof checks only with the certificate delta and contains a certificate-only
term symbol `sK3`, including terms of the form:

```text
sK3 (Eps_i ...)
```

This is a Smolka/Skolemization proof-producing blocker. The source linker has
not finished, but the next hard failure is not a missing alias for `SNo`,
`eps`, `In`, or `omega`; it is the need to eliminate introduced Skolem
witnesses by a sound choice/CPS transformation rather than making them live
constants.

The recommended next milestone is not a broad pass-count run. It is:

```text
Ten committed, reproducible, original-context Megalodon theorem reconstructions,
using regenerated Vampire certificates with <= 10 second timeouts, with no aby,
no admit, no incomplete QED, no bridge premise, no certificate-derived Known
theorem, and no Python proof-producing step.
```

Only after that milestone should the project claim progress toward the final
100-theorem goal.

## Evidence Classes

The project now uses evidence classes because previous reports and tests mixed
several different kinds of success. This distinction is central.

E1 is the actual goal:

```text
An original Megalodon theorem is proved at the original theorem site. The proof
term checks in the original context. It uses no aby, no admit, no incomplete
QED, no bridge assumption, no certificate-derived trusted theorem, and no
Python proof-producing step.
```

E2 is exported-problem proof checking:

```text
The Vampire certificate is elaborated to a native Megalodon proof term and
checked against the exported THF/TPTP problem. The proof may not yet be
composed back into the original theorem command.
```

E3 is focused native proof-term evidence:

```text
A synthetic or focused live certificate exercises native Syntax.pf elaboration
for a clausal primitive or preprocessing fragment.
```

E4 is structural and integration evidence:

```text
Vampire emits certificates; Megalodon parses them, validates metadata and
source maps, checks trust-policy invariants, or runs transitional diagnostics.
This is useful, but it is not proof reconstruction.
```

Under this classification:

- broad strict certificate runs are E4 unless they construct and check native
  proof terms;
- cached runs that relied on transitional known implications are E4;
- synthetic core proof-term fixtures are E3;
- exported THF-bound proof-term checks can be E2;
- only original Megalodon theorem-site proofs are E1.

There is currently no broad E1 result.

## Requirements and Non-Negotiable Constraints

The user requirements and design constraints currently treated as binding are:

- Use THF/TPTP exports from Megalodon.
- Use Vampire with `--input_syntax tptp`.
- Do not run Vampire for more than 10 seconds per problem.
- Prefer batch export, parallel Vampire runs, and parallel checking.
- Use `/project/tmp` for temporary artifacts.
- Do not use `aby`; in Megalodon it is implemented as admission.
- Do not use `admit` or incomplete QED in qualifying results.
- Assume classical logic; `xm` is available.
- Use Megalodon's existing library constants for equality, `False`,
  disjunction, and related logic.
- Do not introduce a private equality or private logical layer as the final
  target.
- Do not hardwire names from the current library, such as individual set or
  family lemmas.
- Recover original names through source metadata and inverse TPTP name mapping,
  not benchmark-specific heuristics.
- Get proof detail from Vampire whenever possible: sorts, selected literals,
  substitutions, positions, directions, generated symbols, dependencies,
  parent/result formulas, and transformation contracts.
- Treat TPTP axioms generated from Megalodon `set` commands as generated
  definitional/reflexivity obligations when no corresponding source claim
  exists.

These constraints rule out the old approach based on Python guessing or large
Megalodon-side heuristic reconstruction. They also rule out treating arbitrary
certificate steps as new trusted Megalodon theorems.

## High-Level History

The project began with a natural but ultimately inadequate idea: translate
Vampire's existing proof output into a Megalodon script. That produced
human-readable skeletons and allowed the project to inspect many proof steps.
It also exposed early issues around TPTP name mangling, local hypotheses,
Megalodon `set` facts, and Skolemization.

The prototype then added a Python translator. The Python layer could create
claims with placeholders and sometimes recover names from the exported TPTP
problem. This was useful for exploration, especially when the immediate goal
was to give a human an inspectable skeleton. However, the approach did not
scale to trusted reconstruction. Every time Vampire omitted a substitution,
sort, selected literal, rewrite position, or transformation dependency, the
Python layer had to guess. That is exactly the failure mode the audits warned
against.

The project then pivoted to a Vampire-owned certificate. Vampire now emits a
Megalodon-oriented S-expression certificate. The choice of S-expressions is
intentional: it is Lisp-like, easy to parse robustly in OCaml, easy to inspect,
and more suitable for proof objects than ad hoc proof text. This is the
current answer to the audit question about Lisp and OCaml: the certificate
format is Lisp-like S-expression data, and the trusted consumer is the
Megalodon OCaml checker. Python is not on the qualifying proof path.

After the July 16 audit, the project also stopped treating pass counts from
transitional known-injection modes as proof reconstruction. The main trust
boundary is now:

```text
Megalodon may accept known theorems already in the source context and a fixed
logical basis. It may not accept new arbitrary Known propositions invented
from certificate step IDs.
```

This correction is important. Earlier "preprocess proof term" counts were
overstated because some succeeded by dynamically installing the proposition
needed for a transformation as a known theorem. Those runs are now understood
as structural diagnostics only.

## Previous Audits and Course Corrections

The July 12 audit pushed against proof-script skeletons and bridge claims. The
response was to classify skeletons as human-aid artifacts rather than proof
reconstruction, and to increase source metadata in certificates.

The July 13 audit emphasized Prover9/Ivy: use a simple, explicit proof object
with small primitive inferences, and avoid reconstructing complex Vampire
inferences in a separate importer. The project responded by studying Prover9
and adding design documents for a small kernel, primitive expansion, and
original-context reconstruction.

The July 14 and July 15 audits emphasized that growth in Megalodon-side OCaml
heuristics was a warning sign. The response was to move more proof detail to
Vampire, add `kernel_v1` metadata, start extracting shared syntax into
dedicated modules, and relabel structural runs.

The July 16 audit identified the most serious trust problem: the native
preprocessing path was dynamically installing certificate-derived `Known`
theorems. The current branch partially addresses this by rejecting generated
`Known "vampire_*"` proof constants in counted native paths, except for a
fixed reviewed logical basis. Transitional knowns are available only through
an explicit diagnostic opt-in and are not counted as proof reconstruction.

The same audit also recommended stopping monolithic growth. This is only
partially achieved. There are now extracted syntax modules on both sides, but
the main Megalodon importer and Vampire exporter are still too large. This
must remain a project risk until the primitive kernel and source-context code
are isolated.

## What Has Been Implemented

### Vampire Certificate Emission

Vampire now emits a Megalodon-oriented certificate rather than relying only on
standard proof text. The certificate is S-expression-based and contains step
metadata, source references, parent information, primitive-expansion metadata,
and transformation contracts.

The current certificate is still transitional. It is richer than proof text,
but not yet the final small primitive IR. Many fields are rendered terms,
clauses, literals, positions, and substitutions rather than typed C++ objects
that are later serialized by a single certificate printer.

The implemented direction is still correct: Vampire knows selected literals,
unifiers, rewrite positions, directions, sorts, and Skolem dependencies at the
time the proof is produced. That information should be emitted by Vampire, not
rediscovered by Megalodon or Python.

### Kernel Vocabulary and Builder Extraction

Vampire contains a `MegalodonKernelSyntax` helper and a first
`MegalodonKernelStep` builder. This moves some fixed certificate vocabulary
and field construction out of the main exporter.

Implemented field clusters include:

- schema and rule names;
- primitive expansion records;
- conclusion and parent metadata;
- selected-literal records;
- rewrite records for superposition/demodulation-style metadata;
- URR trace-step metadata;
- Skolem and branch-binder contract metadata.

This is a migration step toward a Prover9/Ivy object. It is not yet the
finished object. The next extraction must replace rendered strings with typed
parent references, term references, literal references, substitutions,
positions, and introduced-symbol records.

### Megalodon Certificate Parser and Checker

Megalodon parses the native certificate in OCaml and has native proof-term
elaboration for a clausal core and selected preprocessing families.

The native path constructs `Syntax.pf` proof terms and runs Megalodon's proof
checker. This is materially different from textual proof emission.

Important trust-boundary work has been added:

- counted native paths reject generated `Known "vampire_*"` proof constants;
- only a fixed reviewed logical basis is allowed;
- dynamic known-injection behavior is diagnostic only;
- source-derived assumptions are tracked separately from generated
  definitions and generated proof obligations.

This addresses the central July 16 audit finding, but only partially. Some
legacy or diagnostic paths still exist, and the code needs stronger module
boundaries to prevent accidental regressions.

### Source Context and Original Names

The project now carries source metadata from Megalodon export through Vampire
and back into Megalodon. The source resolver distinguishes:

- `GlobalKnown`: a theorem or lemma already present in the original
  Megalodon context;
- `LocalHyp`: a local proof hypothesis from the original theorem context;
- `Definitional`: a local or global definition usable through conversion;
- `Generated`: a generated proof obligation, such as a `set` reflexivity fact;
- conjecture and negated-conjecture source facts;
- unresolved facts, which must not silently become assumptions.

Name recovery is source-map based. Raw TPTP names, normalized names, and
hash-prefixed aliases are all considered. This is the general answer to the
earlier concern about names such as `famunion`: the implementation should not
hardwire library names. It should recover original names from export metadata.

The current hard target shows that name recovery is not enough. We can often
identify the original symbol or local hypothesis, but the proof still fails if
the source-local variable is placed at the wrong de Bruijn depth inside the
certificate proof term.

The latest committed source-variable reification fixes an important part of
that problem. External native hypotheses are now rewritten so free variables
from the source context are represented by source names before they are
localized into the native checker. For the hard target, the relevant local
facts are now visible in the expected source-linked form:

```text
u83: SNo (eps k)
u84: In k omega
```

rather than as anonymous raw de Bruijn propositions detached from the source
variable `k`. The remaining issue is not name recovery for these facts; it is
the order and choice of instantiations needed to expose the implication
prefix where those facts can be applied.

### Equality and Logical Constants

The intended final path uses Megalodon's equality and logical constants. A
private equality layer is not acceptable as a final target.

Some intermediate certificate terms may carry wrappers or rendered encodings
from THF/Vampire, but the Megalodon-side proof term must check against the
library equality, `False`, `or`, implication, quantifiers, and classical
principles already in the Megalodon context. Classical excluded middle `xm` is
assumed available.

For `set` command facts, the current design treats generated equalities as
reflexivity/conversion obligations when there is no matching source claim.
This avoids turning generated TPTP axioms into arbitrary assumptions.

### Smolka-Style Transformation Layer

The project has begun implementing the transformations needed between the
original higher-order source problem and Vampire's clausal proof:

- rectification;
- FOOL atom/formula transformations;
- formula definitions and predicate folds;
- ENNF-like transformations;
- CNF projection;
- Skolemization;
- AVATAR split components and selected SAT-resolution traces;
- equality and rewrite-oriented clausal steps.

The current implementation is partial. It has made useful progress on
predicate-definition folds, source-local aliases, theorem-local variables,
choice-witness cleanup, and Skolem contract validation. It does not yet provide
a complete proof-producing Smolka-style pipeline.

The key design requirement remains: these transformations must either be
expanded in Vampire into small proof objects, or represented by explicit
typed contracts that Megalodon can check with simple proof constructors.
Megalodon should not infer missing transformation structure through broad
heuristics.

### Skolemization

Skolemization is the deepest current blocker.

Vampire now emits much more Skolem data than before:

- top-level Skolem formula records;
- macro-edge metadata;
- child formulas;
- branch contracts;
- introduced witness records;
- free-variable metadata;
- quantified-variable metadata;
- parent step variable lists;
- parent instantiation lists;
- branch binder instantiation contracts.

Megalodon consumes some of this data and checks several invariants. The code
can handle some direct existential and CPS-style Skolemization fragments using
classical choice and explicit generated definitions. Recent work also cleans
some registered choice witnesses from Skolem CPS candidates instead of
allowing Skolem symbols to leak into propositions that should use source-local
existentials.

The problem is not solved generally. The hard examples require aligning:

- source theorem variables;
- branch-local variables;
- parent step variables;
- Skolem witnesses;
- generated predicate definitions;
- negated conjecture binders;
- external local hypotheses;
- current theorem goal binders.

The latest hard failure is exactly in that space. The source-local hypotheses
are now known, carried through the original-context boundary, and applied in
the focused diagnostic. The proof then reaches the double-negated target but
is rejected because the proof of that proposition still contains the
certificate-only Skolem witness `sK3`.

## Linking to Original Megalodon Lemmas and Definitions

This is the area the project should prioritize now.

The current linker is partway implemented. It can resolve many source facts
back to Megalodon objects through source-map names and hashes. It can
distinguish ordinary source facts from generated facts. It can keep some local
source aliases live through certificate checking. It can use local hypotheses
as external source proofs in the native checker.

What works conceptually:

- A TPTP axiom derived from an existing Megalodon lemma should map back to a
  `Known` theorem already in the original context.
- A TPTP axiom derived from a local hypothesis should map back to the
  corresponding proof-context hypothesis.
- A TPTP axiom derived from a local definition should be handled by conversion
  or an explicit definitional proof.
- A TPTP axiom derived from a `set` command with no corresponding claim should
  become a generated equality proof, usually by reflexivity or conversion.
- A conjecture refutation should be composed with the original theorem goal
  using the original local context.

What is still incomplete:

- The source-context API is not yet isolated as its own module.
- Local hypotheses are now reified at the external-hypothesis boundary and
  deferred to the original-context composition boundary, but the source-binding
  pass still needs to be made cleaner and module-local rather than embedded in
  the large command checker.
- Source-local variables can still be captured or shifted incorrectly.
- Definitions and generated equalities are not yet uniformly represented as
  separate conservative proof objects.
- Negated conjecture composition is guided but not complete.
- There is not yet a committed example suite proving original theorems at
  their original sites.

The latest `11925:125` diagnostic remains valuable because it shows both
progress and the remaining hard boundary. The earlier defect was that external
local hypotheses carried propositions whose free de Bruijn variables were
relative to the source context, but the native certificate checker appended
them under the certificate's variable context. That could make a source-local
`k` appear as `_5` where the current goal expected `_2`. The committed
reification and local-hypothesis deferral fixes remove that as the immediate
failure.

The current diagnostic now reaches the expected source facts:

```text
u83: SNo (eps k)
u84: In k omega
```

and applies them before reaching the double-negated target. The remaining
failure is that the proof term for double-negation elimination still mentions
a certificate-only Skolem witness `sK3`. That is not a source-name problem; it
is a missing proof-producing Skolem/choice transformation.

## Testing Strategy

The project should keep tests fast and staged.

The current preferred testing model is:

```text
1. Export all candidate THF problems in batch.
2. Run Vampire over the batch in parallel, 10 seconds per problem.
3. Cache the Vampire proof outputs.
4. Iterate on Megalodon certificate checking using cached outputs.
5. Rerun Vampire only when certificate emission changes.
6. Check focused hard targets before broad suites.
7. Run broad suites only after local blockers are fixed.
```

Parallelism should normally be 10 to 20 jobs, depending on the stage. The user
explicitly allowed 10-problem parallel runs and later 10-20 CPU parallelism.
Vampire compilation should use `make -j10` when rebuilding.

The proposed test stages are:

- T0: OCaml build and native certificate smoke tests.
- T1: synthetic small-kernel fixtures, including negative trust-boundary tests.
- T2: cached live certificate rechecks without rerunning Vampire.
- T3: focused original-context targets such as `10654:21` and `11925:125`.
- T4: 10 original-context theorem milestone.
- T5: 100 original-context theorem suite.

Only T4 and T5 should count toward the final project goal. T0-T3 are necessary
engineering gates, not completion evidence.

The project should maintain two generated corpora:

- a small focused corpus for rapid iteration;
- a held-out broad corpus for honest measurement after fixes.

The broad corpus should be regenerated with Vampire only when Vampire's
certificate emission changes. Megalodon-side checker changes should usually
use cached proof outputs first.

## Why Not Python Reconstruction

Python remains useful for automation, summarization, corpus management, and
non-trusted diagnostics. It should not produce the proof.

The reason is technical, not stylistic. Proof reconstruction needs exact
information that Vampire has internally:

- selected literals;
- substitutions;
- variable sorts;
- rewrite positions;
- rewrite direction;
- parent/result clause shapes;
- Skolem dependencies;
- branch binders;
- transformation provenance.

If Python or Megalodon has to infer these from pretty-printed proof text, it
becomes a second prover. That is fragile and not a credible trust boundary.
The audit-recommended path is to have Vampire emit the detailed primitive
certificate directly, then have Megalodon check it.

## Prover9/Ivy Comparison

The Prover9/Ivy lesson is that complex prover inferences should be translated
into a small set of explicit kernel steps. The checker should not understand
all of the prover's internal heuristics. It should understand a small proof
object with simple rules.

For this project, the intended kernel contains rules in the neighborhood of:

- input or source boundary;
- instantiate;
- alpha-renaming or checked binder opening;
- resolve;
- factor;
- equality resolution;
- equality factoring;
- paramodulation/superposition as explicit rewrite;
- contradiction from empty clause or complementary literals;
- possibly a small controlled truth/Fool conflict layer.

The exact list can still be adjusted, but the principle is fixed: each rule
needs explicit parents, selected literals, substitutions, positions, result
clauses, and types. Vampire should lower complex macro steps to this small
object before serialization.

Current work is on the path but incomplete. The `kernel_v1` records and
`MegalodonKernelStep` builder are good migration scaffolding. They are not yet
the final typed Ivy-like proof object.

## Smolka-Style Transformations

The Smolka-style part of the project covers the translation from typed
higher-order Megalodon formulas to the clausal forms Vampire proves.

The main transformation families are:

- source formula normalization;
- rectification;
- lambda/formula handling;
- FOOL atom lifting;
- ENNF;
- CNF;
- definition introduction and unfolding/folding;
- Skolemization with classical choice;
- conjecture negation and refutation-to-goal conversion.

The current implementation handles some cases but not the whole pipeline.
Predicate-definition folding has improved. Source-map handling has improved.
Skolem contracts have become much richer. Generated `set` equalities are
understood as reflexive/generated obligations. However, the transformation
layer still lacks a clean proof-producing sequence for all real hammer proofs.

The most urgent Smolka-style work is:

- isolate and finish the source-context binding operation for local variables
  and local hypotheses;
- represent external source facts as proof objects, not raw appended
  propositions;
- prove generated `set` equalities by Megalodon reflexivity/conversion;
- complete Skolem CPS replay using Vampire's branch and parent instantiation
  contracts;
- compose the negated-conjecture refutation back into the original theorem
  goal.

The design should prefer explicit Vampire contracts and small Megalodon proof
constructors over local pattern-matching heuristics in `megalodon.ml`.

## Current Blockers

The current blockers are ordered by importance.

### 1. Skolemization and Choice Witness Elimination

Skolemization now has much richer Vampire metadata, but the Megalodon checker
does not yet replay the full CPS/choice proof for all real examples. The
branch-binder and parent-instantiation data recently added to Vampire should
be consumed by a general Megalodon proof constructor, not by benchmark-specific
repairs.

The hard target `11925:125` currently fails here. The latest committed work
fixes source-variable reification for native external hypotheses and defers
local hypotheses to original-context composition. In the debug run, the source
facts are applied and the checker recognizes the double-negated target. The
candidate proof is then rejected because it still contains certificate-only
Skolem witness `sK3`. The next implementation step must eliminate or replace
that witness through a proof-producing choice/CPS transformation, using
Vampire's emitted Skolem contracts.

### 2. Original-Context Binding

The project can often identify which original lemma, definition, or local
hypothesis a TPTP source fact came from. The current hard diagnostic shows
real progress: the source facts `u83` and `u84` are carried to the
composition boundary and consumed there. This still needs to be isolated into
a cleaner source-context module, made less dependent on `megalodon.ml`, and
extended to definitions, generated `set` equalities, and a committed original
theorem-site suite.

### 3. Primitive Kernel Object

The Vampire-side small-kernel object is still rendered-data-heavy. It needs
typed fields for terms, literals, substitutions, positions, and parent
references. This is the main work needed to fully align with the Prover9/Ivy
recommendation.

### 4. Module Boundaries

Megalodon's `vampire_cert_v1.ml` and Vampire's `MegalodonChecker.cpp` remain
too large. The code needs extraction into:

- kernel syntax;
- kernel checking;
- kernel elaboration;
- source context;
- Smolka/preprocessing proof constructors;
- legacy/transitional diagnostics.

This is not merely cosmetic. Strong module boundaries are how the project
prevents another drift into a large heuristic importer.

### 5. Evidence Discipline

The project must continue to distinguish:

- structural certificate validation;
- native proof-term checking of exported problems;
- original theorem-site proof reconstruction.

Pass counts should say which evidence class they measure.

## Recommended Next Plan

The next work should be narrow and proof-producing.

### Milestone A: Eliminate Certificate-Only Skolem Witnesses

Use the emitted Skolem parent-instantiation and branch-binder contracts to
turn introduced witness symbols such as `sK3` into proof-local choice/CPS
witnesses. The live proof returned to `megalodon.ml` must contain no
certificate-only symbols. The checker should continue rejecting candidates
that check only with the certificate delta.

Expected focused gate:

```text
TARGETS='10654:21 11925:125'
JOBS=2
MEGALODON_VAMPIRE_TIMEOUT=10
TMPDIR=/project/tmp
```

The goal is for `11925:125` to stop being an expected failure without adding
any `aby`, `admit`, bridge theorem, dynamic known, live Skolem constant, or
theorem-specific name hack.

The implementation should stay general. In particular, it should not special
case `SNo`, `eps_`, ordinal arithmetic, or any current-library theorem name.
It should use the source map and typed certificate/source terms to select
instantiations, and it should fail closed when no typed candidate is available.

### Milestone B: Isolate Source-Context Composition

Move the current source-binding logic toward a small explicit source-context
API. It should cover global known facts, local hypotheses, definitions,
generated `set` equalities, conjecture/negated-conjecture bindings, and
source-local variables without relying on benchmark-specific aliases.

### Milestone C: Commit a 3-Target Original-Context Suite

Once the hard target passes, define a tiny original-context suite:

- one global-known theorem case;
- one local-hypothesis case;
- one generated `set` reflexivity/equality case.

This suite should run quickly and should not rerun Vampire unless the
certificate emitter changes.

### Milestone D: Consume Branch-Binder Contracts

Use the latest Vampire branch-binder instantiation records to make
Skolemization replay less heuristic. The checker should validate that parent
and branch binders are opened with the emitted instantiations.

### Milestone E: Replace Rendered Kernel Fields

On the Vampire side, extend `MegalodonKernelStep` with typed fields for:

- parent references;
- literal references;
- selected literal indices;
- term substitutions;
- rewrite positions;
- rewrite direction;
- generated symbol declarations;
- introduced witness dependencies.

Then have the existing renderer serialize those typed fields into the current
S-expression format. This permits gradual migration without breaking every
consumer at once.

### Milestone F: Ten E1 Proofs

Produce ten original Megalodon theorem proofs with:

- regenerated THF exports;
- Vampire timeout <= 10 seconds;
- cached Vampire proofs;
- native Megalodon proof-term checking;
- no `aby`, `admit`, incomplete QED, bridge premise, or dynamic known theorem;
- no Python proof-producing step.

This is the next meaningful expert-review milestone.

### Milestone G: 100 E1 Proofs

Only after Milestone F should the project run the 100-theorem original-context
suite. The suite should be parallelized and cached:

```text
export all problems once
run Vampire in parallel, 10 second cap
check reconstruction in parallel
```

The result should report:

- number exported;
- number solved by Vampire;
- number with parseable certificates;
- number with native proof-term checks;
- number composed into original theorem proofs;
- number of failures by inference/transformation family;
- exact command lines and artifact directory in `/project/tmp`.

## Suggested Expert Review Questions

The expert should focus on these questions:

- Is the source-context binding design sufficient for original theorem-site
  reconstruction?
- Should external local hypotheses be represented as source-variable aliases
  before certificate localization, or should the certificate carry explicit
  source variable references?
- Is the proposed small kernel rule set close enough to Ivy, or should it be
  further reduced?
- Which Smolka transformations should be proved inside Megalodon using a fixed
  library theorem basis, and which should Vampire lower to primitive steps?
- Are the current Skolem contracts sufficient, or does Vampire need to emit a
  more explicit choice proof object?
- Should the current large `vampire_cert_v1.ml` be split before adding more
  proof power?
- What minimal 10-theorem E1 suite would provide credible evidence without
  creating a slow test burden?

## Bottom Line

The project has made real progress, but the final goal is still open.

The good news is that the architecture is now much closer to the right one:
Vampire emits richer proof data, Megalodon checks native proof terms, dynamic
trusted certificate theorems are no longer counted, and source metadata is
being used to reconnect proofs to original Megalodon lemmas, definitions, and
local hypotheses.

The bad news is that the central hard problem is still exactly the one the
audits predicted: original-context proof reconstruction needs a precise
source-context binding layer and explicit small proof objects, not growing
Megalodon-side reconstruction heuristics. The current `11925:125` failure is
therefore useful. It is a concrete, general, local-context mismatch that points
to the next implementation step.

The recommended direction is to stop optimizing broad structural pass counts
and finish a small number of original-context proofs end to end. The next
credible milestone is ten E1 proofs, not another 100-certificate structural
run.
