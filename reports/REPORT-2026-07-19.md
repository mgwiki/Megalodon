This report is intended for expert review. It summarizes the current state of
the Vampire-to-Megalodon proof reconstruction project, the work done so far,
the approach used, the current problems, the status of original-context
linking and Smolka-style transformations, and the recommended outlook. It
takes into account the prior project reports, the audit reports, the
Prover9/Ivy analysis, the Smolka-style discussion, and the current local branch
state.

The report is deliberately conservative. The original goal is not complete.
The project has made real architectural and implementation progress, but it
does not yet have a qualifying 100-theorem result, and it does not yet have a
committed suite of original Megalodon theorems reconstructed from Vampire
proofs with no `aby`, no `admit`, no incomplete QED, no bridge assumptions, no
certificate-derived trusted theorems, and no Python proof-producing step.

## Executive Summary

The target remains:

```text
Given a theorem in an original Megalodon development, export the theorem and
its usable context as a THF/TPTP problem, let Vampire prove the problem with a
per-problem timeout of at most 10 seconds, emit a detailed proof certificate,
import that certificate into Megalodon, elaborate the certificate into native
Megalodon proof terms, and check a proof of the original theorem at the
original theorem site.
```

That target has not yet been achieved.

The most important change in the project over the week is a pivot away from a
Python-heavy reconstruction prototype and toward a Vampire-owned, Prover9/Ivy-
style certificate path:

```text
Megalodon theorem/context
  -> THF/TPTP export with source metadata
  -> Vampire proof search
  -> Vampire-side proof detailing while exact proof data is still available
  -> native S-expression certificate
  -> Megalodon OCaml parser/checker/elaborator
  -> native Syntax.pf proof term
  -> original theorem proof composition
```

The audits repeatedly identified the same core problem: if Megalodon has to
guess pivots, substitutions, sorts, source formulas, Skolem dependencies, or
preprocessing transformations after the fact, the importer becomes a second
prover. That is not a convergent design. The current branch now reflects that
lesson better than earlier branches, but the implementation still carries too
much proof logic in the large Megalodon importer and too much metadata rendering
inside one large Vampire printer.

The strongest positive results are:

- Vampire emits a native Megalodon-oriented S-expression certificate.
- Vampire emits `kernel_v1` metadata with a centralized
  `MegalodonKernelSyntax` vocabulary.
- Vampire now reports substantially richer Skolemization contracts, including
  source/result formulas, child formulas, macro-edge records, branch contracts,
  introduced witness records, dependency metadata, free-variable metadata,
  quantified-variable metadata, parent step variables, parent instantiations,
  and branch binder instantiations.
- Megalodon parses the native certificate into OCaml data structures.
- Megalodon has native `Syntax.pf` proof-term elaboration for a clausal core
  and selected preprocessing fragments.
- Counted native proof-term modes reject certificate-derived dynamic `Known`
  implications except for a fixed reviewed logical basis. The old dynamic
  `Known` behavior is now classified as transitional structural diagnostics,
  not proof reconstruction.
- The source-context layer now distinguishes known global facts, local
  hypotheses, local definitions, generated facts, conjecture/negated-conjecture
  facts, unresolved facts, and `set`-generated reflexivity facts.
- `set` command facts that have no corresponding source claim are no longer
  treated as arbitrary assumptions in the intended path. They are recognized as
  generated reflexivity/conversion obligations, with Megalodon-side proof terms
  for reflexive equality where the shape is supported.
- Source-map names are now threaded more generally into the native checker,
  including raw, normalized, and hash-prefixed aliases.
- The latest committed Megalodon change localizes source-local type aliases
  such as theorem-local type parameters before native preprocessing proof
  checks. This removes a concrete leak where an exported alias such as `#k`
  appeared where the Megalodon proof checker expected a local de Bruijn
  variable.

The strongest negative results are:

- There is no qualifying E1 100-theorem suite.
- There is no committed qualifying 10-theorem original-context suite.
- The current small-kernel proof-term path is not yet applied broadly to real
  exported hammer proofs.
- The original-context composition path exists in pieces, but is not complete.
- The Smolka-style preprocessing layer is partial.
- Skolemization remains the hardest technical blocker.
- The representative hard target `examples/hammer/100thms_12_h.mg:11925:125`
  is still an expected failure.
- The latest focused gate is:

```text
10654:21   PASS
11925:125 EXPECTED_FAIL
PASS 1
EXPECTED_FAIL 1
```

The current observed failure for `11925:125` is:

```text
native preprocess refutation discharged Skolem witness symbols #sK0, sK0
```

This is a better failure than earlier ones. The latest fix moved the failure
past a source-local alias problem and into the grouped Skolem/choice witness
cleanup boundary. But it is still not a pass.

The recommended next milestone is not another broad pass-count run. It is:

```text
Ten committed, reproducible, original-context Megalodon theorem reconstructions,
with Vampire timeouts <= 10 seconds, no aby/admit/incomplete QED, no bridge
premises, no certificate-derived Known theorems, and no Python proof-producing
step.
```

Only after that should the project rerun and report a fresh 100-theorem E1
gate.

## Evidence Classes

The project now uses evidence classes to avoid confusing integration success
with proof reconstruction.

E1 is the real goal:

```text
An original Megalodon theorem is reconstructed at its original proof site.
The produced proof term checks in the original context. The result uses no
aby, admit, incomplete QED, bridge assumption, certificate-derived trusted
Known theorem, or Python proof-producing step.
```

E2 is useful but not final:

```text
A closed native Syntax.pf proof of a live Vampire certificate checks against
the exported THF/TPTP problem, but the proof has not yet been composed back
into the original theorem command.
```

E3 is focused proof-term evidence:

```text
Synthetic or focused live certificates exercise native Syntax.pf elaboration
for a small-kernel rule or for one preprocessing fragment.
```

E4 is structural/integration evidence:

```text
Vampire emits certificates; Megalodon parses them, validates their structure,
source maps, metadata, trust policy, and diagnostics, or runs broad non-proof
certificate checks. This is valuable, but it is not proof reconstruction.
```

Under this classification:

- broad strict certificate runs are E4 unless they construct and check native
  proof terms and compose those terms into original theorem sites;
- preprocessing proof-term runs that rely on transitional dynamic `Known`
  implications are E4;
- focused native proof-term examples are E2-like or E3 depending on whether
  they are live exported proofs or synthetic fixtures;
- a current-goal focused target that checks at a real Megalodon theorem hole is
  an E1 candidate, but it does not establish an E1 suite;
- no broad E1 result currently exists.

This classification is one of the most important corrections after the audit
cycle. Earlier reports and harnesses sometimes used words such as "strict",
"closed", or "PASS" too broadly. The current report uses those labels only with
the evidence class attached.

## Requirements and Constraints

The project is constrained by explicit requirements from the user:

- Use THF/TPTP exports from Megalodon.
- Use Vampire proof search over those exports.
- Use `--input_syntax tptp` on the Vampire side.
- Do not run Vampire for more than 10 seconds per problem.
- Prefer exporting all problems first, then running Vampire and reconstruction
  checks in parallel.
- Use `/project/tmp` for temporary and generated artifacts.
- Run tests in parallel, typically with 10 to 20 workers when doing broad
  batches.
- Avoid slow repeated runs over unsolved problems; identify the Vampire-solvable
  subset once and iterate on that subset.
- Do not use `aby` in resulting scripts or proof terms. In Megalodon, `aby` is
  implemented as admission.
- Do not use `admit` or `-allowincompleteqed` in qualifying results.
- Assume the classical setting; `xm` is available.
- Use Megalodon's library equality and logic constants, including equality,
  falsehood, disjunction, and related primitives.
- Do not create a private equality or private logic layer for final proof
  reconstruction.
- Prefer Vampire-emitted proof detail over Megalodon-side guessing.
- Prefer a Prover9/Ivy-style small certificate calculus over broad heuristic
  reconstruction.

Those constraints are now reflected in the design documents and in the way
results are classified. They are not yet fully reflected in the implementation
shape.

## Prior Audit Trajectory

The audits form a coherent story.

The July 12 audit said the first implementation line should stop. It found
that the Python layer had become a heuristic prover, that "source-context
check passed" was being overinterpreted, and that the project was replaying
too much of Vampire outside Vampire. It recommended a normalized small
certificate calculus, modeled after Prover9/Ivy, with Skolemization specified
as a separate macro-certificate carrying complete prefix, sorts, dependencies,
generated symbol, and before/after formulas.

The July 13 audit accepted the decision to move toward a versioned certificate,
OCaml, and S-expressions, but found that the new path was already recreating
the old derived-assumption loophole. It specifically warned against generic
`input` clauses that did not have to correspond to original source facts. It
also recommended that Python be restricted to orchestration and diagnostics,
and that the accepted importer be native OCaml using Megalodon's term, type,
substitution, conversion, and proof-term machinery.

The July 14 audit found that "strict" still allowed bridge premises, that
source-linking was still largely label-linking rather than proposition-linking,
and that the OCaml switch was only partial because structural OCaml checks did
not yet construct `Syntax.pf` proof terms. It recommended an immediate strict
qualifying mode: no bridges, semantic source checks, native proof terms, and
reported `CLOSED_PASS` rather than ordinary pass labels.

The July 15 audit was more positive. It accepted that closed mode and source
formula checks had improved and that evidence had become more reproducible.
It also noted a useful nine-rule core. But it still warned that the broad
implementation was growing into another reconstruction prover, now in OCaml.
It said the next iteration should be constrained to native AST proofs, exact
source linkage, and Vampire-side macro expansion.

The July 16 audit accepted the architecture but rejected the milestone order.
It found that the native preprocessing path had recreated the bridge problem
in a subtler form by dynamically installing the proposition it needed as a
`Known` theorem. It also reclassified the live `PASS 100` as structural
integration evidence, not proof reconstruction. Its central instruction was:

```text
Eliminate all certificate-derived Known declarations from the counted native
path before chasing preprocessing pass counts.
```

The current branch takes that instruction seriously. Counted native proof-term
paths now reject certificate-derived `Known` propositions, with the old
behavior behind the diagnostic environment variable
`MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1`. This is an important
trust-boundary repair. It also means that several older pass counts must be
treated as historical diagnostics, not current proof-reconstruction evidence.

## Approach

The accepted approach has four layers.

First, Megalodon exports a theorem goal and its usable source context to THF.
The export includes source-map comments with source names, TPTP names, source
hashes, source kinds, and, where possible, source formulas.

Second, Vampire proves the THF problem and emits a native certificate. The
current certificate is S-expression based. It carries input formulas, clauses,
proof steps, source references, and `kernel_v1` metadata. The important design
principle is that Vampire should emit the nondeterministic proof data while it
still has it: selected literals, pivots, substitutions, variable sorts, rewrite
positions, inference directions, introduced Skolem symbols, dependencies, and
branch structure.

Third, Megalodon imports the certificate. The importer should parse and check
the certificate structure, resolve source references, build Megalodon terms
and proof terms, and call Megalodon's native proof checker. It should not
search for missing proof data. It should fail closed if an inference lacks the
needed details.

Fourth, the exported refutation must be composed back into the original theorem
context. This is the original-context gluing problem. A refutation of the
exported negated conjecture is not by itself a proof at the Megalodon proof
site. Megalodon must show that every source input used by the certificate is
justified by the current local context, a global known theorem, a local
definition, a generated reflexivity fact, or a checked transformation from the
original conjecture.

The current implementation has pieces of all four layers. The weakest layer is
still the fourth, especially when Skolemization and dependent local context are
involved.

## Work Done in Megalodon

The Megalodon repository contains the bulk of the importer and checking work.
The current implementation is still concentrated in `src/vampire_cert_v1.ml`,
with related source-context support in `src/vampire_source_context.ml`,
certificate vocabulary support in `src/vampire_kernel_syntax.ml`, and command-
line integration in `src/megalodon.ml`.

The principal implemented capabilities are as follows.

The importer parses the native Vampire S-expression certificate into typed
OCaml records. It recognizes formula inputs, clause inputs, native terms,
native formulas, source references, source-map metadata, and a broad set of
Vampire inference names. This importer started as a broad compatibility layer,
and that history still shows in its size. The intended future is to extract
the stable pieces into smaller modules.

Megalodon has strict and closed validation modes for certificate source facts.
The source map records the original declared formula when possible, and
strict/closed validation compares certificate input propositions against
the exported source proposition rather than only comparing labels. This fixed
the earlier problem where a nontrivial certificate premise could be associated
with a trivial source declaration.

The source-context resolver classifies source obligations. It can distinguish
global known facts, local facts, local definitions, generated facts, conjecture
facts, negated conjectures, and unresolved obligations. This is crucial for
the original-context path. A source reference to an exported theorem should
become a `Known` only if it resolves to an existing Megalodon known theorem.
A source reference to a local assumption should become a local proof-context
reference, not a global theorem. A generated set equality should be proved by
reflexivity/conversion, not looked up as a claim.

The implementation now includes set-reflexivity support. Source-map kinds
`set_reflexivity` and `local_set_reflexivity` are recognized. For supported
unit equality forms, the native proof-term path builds a proof using
Megalodon's equality/reflexivity basis. This directly addresses the user's
observation that some TPTP axioms come from Megalodon's `set` command and may
not correspond to user-written claims.

The native proof-term path uses Megalodon's `Syntax.pf` representation and
`check_propofpf`/`extr_propofpf` checking. This is materially different from
emitting scripts with assumptions or from Python-generated proof skeletons.
It is the right trust boundary: success is counted only when Megalodon's
checker accepts the proof term.

Counted native preprocessing no longer accepts arbitrary certificate-derived
`Known` implications. The helper that would install a dynamically constructed
implication now fails in counted mode and tells the user to implement a real
proof term or opt into the old structural diagnostic mode with
`MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1`. This is the main
post-audit trust-boundary repair.

The core clausal path supports a small group of proof-term reconstructions for
input, resolution-like steps, factoring-like steps, equality reasoning, and
selected substitution/paramodulation patterns. This is not yet a complete
small-kernel module. It is an implementation seed inside the legacy importer.

The preprocessing path has partial proof-term support for selected
transformations. It also has significant Skolem CPS machinery. The CPS idea is
to turn a refutation of a Skolemized result back into a refutation of the
source formula by abstracting over the introduced witnesses and using
Megalodon's classical/choice principles. This is the right logical direction,
but the current implementation remains incomplete.

The latest committed Megalodon work fixes source-local variable closure and
source-local alias localization:

- `20c5a75 Close source-local variables in native certificates`
- `599e3c5 Localize source local aliases in native preprocess checks`

The first commit ensures that source-map `local_type` variables, such as
theorem-local type parameters, are included in native proof variable contexts.
The second commit maps aliases generated by the THF export and Vampire
certificate back to the correct de Bruijn variables before native
preprocessing proof checks. This is general source-map handling, not a
theorem-specific hardwire.

The concrete symptom fixed by the latest commit was a mismatch in which the
debug output for the hard target included an exported/local alias such as
`#k` where the native proof checker expected a local variable. After the fix,
the high-signal debug output shows source-local aliases localized as variables,
for example formulas involving `#eps_ _0` instead of leaking `#eps_ #k` into
the proof checker.

## Python Status

Python was useful early in the project for diagnostics, corpus analysis,
translation experiments, and skeleton generation. It should no longer be
treated as a proof-producing component in a qualifying result.

The audits were clear that the Python reconstruction layer had become a second
prover. It inferred missing pivots, attempted formula matching, generated
proof skeletons, and repaired gaps after the fact. Even if a generated proof
eventually checked, that approach was not a convergent engineering direction.
It made every unsupported Vampire step into a new Python search problem.

The current project direction is:

- Python may orchestrate batch runs.
- Python may summarize proof statistics.
- Python may compare logs and classify failures.
- Python may generate diagnostic reports.
- Python must not construct logical arguments for accepted reconstruction.
- Python output must not be counted as E1 or E2 proof reconstruction.

This report therefore does not count older Python-generated outline successes
as final proof reconstruction evidence.

## Source Linking Status

The source-linking problem is the problem of connecting the certificate back to
the original Megalodon development. It is broader than name demangling.

A complete source link must answer, for every certificate input:

```text
What original Megalodon fact, local hypothesis, local definition, generated
fact, or conjecture transformation justifies this certificate input?
```

The current state is partial but substantially better than earlier branches.

Megalodon export now emits source-map comments with source names, TPTP names,
source hashes, source kinds, and in many cases source formulas. The importer
uses this metadata when resolving source obligations. It does not only rely on
labels. In strict modes, it checks that the certificate formula agrees with
the exported source formula where the formula is supported by the importer.

Global facts are represented as known theorem candidates. The intended
qualifying behavior is that a `Known` in the final proof must resolve to an
existing Megalodon theorem or to a fixed reviewed logical basis theorem. A
certificate-generated implication is not allowed to become a `Known`.

Local facts are represented as local proof-context obligations. This matters
for theorem parameters, local assumptions, local definitions, and theorem-local
type variables. The latest source-local alias fix is part of this. When THF
export mangles a local type parameter, the certificate may mention aliases such
as a raw source name, a TPTP name, a hash-prefixed name, or a normalized
identifier. The native proof checker needs all of those to resolve to the
same local de Bruijn variable. The current commit implements that localization
for `local_type` source-map entries in the native preprocessing checks.

Local definitions are not the same as global theorems. They need to be matched
against the current context and unfolded or used definitionally. The source-
context layer has explicit categories for local definitions. This is necessary
because generated terms and local abbreviations can shift local de Bruijn
indices.

Set-generated facts now have a specific treatment. Some TPTP axioms come from
Megalodon `set` commands and do not correspond to a user-written claim. The
current path classifies them as generated reflexivity facts where possible and
proves supported unit equalities by reflexivity/conversion. This is a better
trust boundary than assuming them as claims.

The negated conjecture remains special. Vampire proves by refuting the negated
conjecture. The importer must not treat the negated conjecture as an ordinary
source axiom in the final theorem proof. It must compose the refutation back
to the original goal by using the current theorem goal and classical logic.
This final composition remains incomplete for the hard examples.

The current source-linking state can be summarized as:

- name recovery from source maps: partially implemented and improving;
- source formula checking: implemented for supported formulas;
- global theorem binding: partially implemented;
- local hypothesis binding: partially implemented;
- local type binding: recently improved;
- local definition binding: partially implemented;
- set-reflexivity obligations: partially implemented with actual proof terms
  for supported equality shapes;
- negated-conjecture-to-goal composition: partial and still a main blocker;
- complete original-context suite: not achieved.

## Equality and Logic Basis

The current design is to use Megalodon's equality and logic, not a private
equality layer.

Earlier experiments and intermediate representations sometimes looked as if
there was a separate equality. That is not acceptable for final proof
reconstruction. The accepted path must elaborate equality reasoning into
Megalodon's existing equality constants and proof principles. The current
native proof-term work uses Megalodon's proof checker and logical basis. The
set-reflexivity support is also based on proving Megalodon equalities by
reflexivity/conversion, not by introducing a new equality axiom.

The same principle applies to `False`, disjunction, implication, quantifiers,
choice, and excluded middle. They should come from the Megalodon library or
from a fixed reviewed basis already available in the classical setting. The
certificate may guide how to use them; it may not define private substitutes.

Classical logic is assumed. `xm` and classical choice-like principles may be
used where they are part of the approved Megalodon basis. The hard part is not
whether classical reasoning is permitted. The hard part is making each use
explicit in a kernel-checked proof term rather than hiding the transformation
behind a certificate-derived theorem.

## Smolka-Style Transformation Status

The Smolka-style part of the project is the source/preprocessing proof layer.
It is separate from the clausal kernel.

The clausal kernel should prove things such as resolution, factoring, equality
resolution, equality factoring, and paramodulation once the proof is already
in a clausal form. It should not also be responsible for proving that a source
formula was rectified, transformed through FOOL, put into negation-normal form,
clausified, Skolemized, split by AVATAR, and projected into a particular
clause.

The Smolka-style layer should produce proof terms for transformations such as:

- source formula input;
- formula-term input;
- definition introduction;
- definition fold/unfold;
- rectification;
- FOOL Boolean lifting;
- FOOL exhaustiveness and truth-conflict transformations;
- ENNF;
- CNF projection;
- Skolemization;
- selected AVATAR component transformations when AVATAR is enabled.

The current implementation has partial support for several of these, but not
a complete layer. Earlier branches sometimes treated these transformations as
trusted dynamic implications. That is now non-qualifying.

The current positive state:

- Vampire emits before/after data for many transformations.
- Megalodon parses and structurally validates much of that data.
- Some transformation proof terms are built directly.
- Unsupported transformations now fail in counted mode instead of installing
  arbitrary dynamic `Known` implications.
- Skolemization now has rich contract data and a CPS replay attempt.

The current negative state:

- There is no separate, audited Smolka transformation module.
- Many transformation classes are still inside `vampire_cert_v1.ml`.
- Some older pass counts depended on transitional `Known` implications and
  must not be counted.
- CNF projection and clause-source justification are not complete.
- Rectification and definition handling are partial.
- Skolemization is still incomplete for dependent/grouped cases.
- AVATAR is not yet represented by a small checked SAT/RUP-like layer.

The correct direction is not to hand-code larger after-the-fact pattern
matching in Megalodon. It is to make Vampire emit explicit transformation
objects with all nondeterministic choices and to make Megalodon check those
objects by fixed proof-term templates.

## Skolemization Status

Skolemization is currently the hardest technical blocker.

The logical shape is:

```text
If the Skolemized result refutes, then the source formula refutes.
```

For simple cases, this can be justified by introducing a choice witness for an
existential and replaying the refutation under that witness. For dependent
and grouped cases, the proof has to respect source binders, preserved
variables, introduced Skolem symbols, local type parameters, and mutually
dependent Skolem steps.

The implementation uses a CPS-style approach. It attempts to take a refutation
of the Skolemized formula and construct a continuation that abstracts over
introduced witnesses, replaces Skolem symbols with Megalodon choice witnesses,
and replays the proof against the source formula.

Vampire now emits enough metadata to make this plausible:

- the source unit;
- the source formula;
- the result formula;
- source formula children;
- result formula children;
- introduced symbols;
- dependencies;
- macro edges;
- parent step variables;
- parent instantiations;
- branch binders;
- branch binder instantiations;
- whether classical choice is used.

Megalodon consumes this data and validates many invariants. The debug logs show
that grouped Skolem CPS replay can reach the empty clause for the hard target
under some shadow assumptions. However, the final proof term still does not
survive the full native check in the representative hard target.

The latest hard target is:

```text
examples/hammer/100thms_12_h.mg:11925:125
```

The current focused command classifies it as an expected failure. The latest
debug failure is:

```text
native preprocess refutation discharged Skolem witness symbols #sK0, sK0
```

The meaning is important. The checker has built a candidate that gets farther
than earlier attempts, and debug reports that choice terms match registered
witnesses in the relevant Skolem CPS entries. But the candidate still contains
certificate-local choice witnesses at a point where counted proof terms must
not leak them. The remaining work is to transport or eliminate those witnesses
inside the checked proof term, not to mark them trusted.

The latest committed alias-localization fix narrowed the issue. Before that
fix, one debug path still showed source-local aliases such as `#k` inside a
term where a local de Bruijn variable was required. After the fix, the
high-signal local context lines are sane, for example:

```text
Vampire native source external local hypothesis u83 -> __1 : (#SNo (#eps_ _0))
Vampire native source external hypothesis __1 final : (#SNo (#eps_ _0))
```

That does not solve Skolemization, but it removes a separate source-context
name-recovery error from the same target.

The next Skolemization fix should be general. The likely options are:

- keep the grouped CPS candidate in Skolem-symbol form until the final checked
  witness cleanup;
- implement a safe exact reverse replacement from registered choice witness
  terms back to Skolem symbols before the candidate is rejected for containing
  certificate-local choices;
- compute grouped Skolem discharge over dependency components rather than one
  entry at a time;
- have Vampire emit a smaller primitive branch proof object for Skolemization,
  including the exact continuation schema expected by Megalodon.

The implementation should not:

- use `aby`;
- use `admit`;
- use a dynamic `Known` implication for the Skolem branch;
- trust a certificate-local choice witness;
- hardwire names such as particular library constants beyond source-map alias
  recovery and fixed Megalodon logical basis names;
- expand Megalodon-side search to guess missing branch structure.

## Current Problems

The first problem is that original-context composition is incomplete. The
project can parse source maps, classify many source facts, and build some
native proof terms, but it does not yet reliably produce a proof of the
original theorem at the original proof site. The final step from exported
refutation to current Megalodon goal remains a real technical boundary.

The second problem is Skolemization. The project has moved from opaque
Skolemized formulas to rich Vampire-emitted contracts, but grouped/dependent
Skolem CPS replay still leaks or fails to discharge certificate-local witness
terms in hard examples. This is the current highest-priority technical issue.

The third problem is that the small kernel is not yet isolated. The audits
asked for a small Ivy-like proof object and a small checker. The branch has a
kernel vocabulary and proof-term seeds, but new logic still tends to land in
`src/vampire_cert_v1.ml`. That module is too large and mixes parsing,
structural validation, source context, proof elaboration, preprocessing replay,
debugging, and legacy paths.

The fourth problem is that Vampire-side detailing is still partly a rendering
layer. `MegalodonKernelSyntax` is a good boundary, but the code does not yet
build a complete typed primitive proof object internally before printing.
Macro inference handlers still need to be lowered systematically to primitive
records.

The fifth problem is that AVATAR remains outside a clean proof layer. Some
AVATAR-related data and split handling exists, and it has been useful in
focused debugging. But a final design should probably use a small SAT/RUP-like
or propositional certificate layer, not a broad mix of split metadata and
Megalodon-side reconstruction.

The sixth problem is test classification. The project now has many useful
scripts and artifacts, but the labels must remain strict. A broad structural
pass should never be reported as proof reconstruction. A run using transitional
`Known` should never be reported as a proof-term result. Expected failures are
useful when they pin down the next blocker, but they are not progress metrics
by themselves.

The seventh problem is code growth. Some growth is expected in a research
prototype. But the audits correctly warned that another monolith would be a
bad outcome. The current branch still needs extraction into smaller modules
and a measurable rule that new broad reconstruction features do not continue
to accumulate inside the legacy importer.

## What Was Learned From Prover9/Ivy

The Prover9/Ivy lesson remains central.

Prover9 does not ask Ivy to reconstruct arbitrary prover internals from a
pretty-printed proof. It transforms proofs into a small proof-object calculus
that Ivy can check. Complex inferences are expanded into simpler inferences
before they reach the checker. The checker receives explicit parents,
substitutions, selected literals, positions, and conclusions.

For this project, the analogous design is:

```text
Vampire macro proof
  -> Vampire-side primitive expansion
  -> explicit Megalodon certificate records
  -> deterministic Megalodon proof-term elaboration
```

The important point is not the surface syntax. Lisp/S-expressions are a good
fit because Megalodon already has S-expression-style infrastructure and because
Ivy used a small Lisp-like proof-object discipline. But the important
property is semantic: the certificate must be small, explicit, and complete.

The small clausal kernel should remain close to:

- input boundary from source/preprocessing proof;
- instantiate;
- resolve;
- factor;
- equality resolution;
- equality factoring;
- paramodulate;
- contradiction/empty clause marker.

`rename` should be alpha-conversion or part of instantiation, not a broad
logical rule. `truth_conflict` probably belongs to FOOL/source preprocessing
unless real clausal proofs show it must be primitive. AVATAR should remain
outside the first small clausal kernel milestone.

The next Vampire-side macro lowering target should still be a frequent class
with clear primitive expansion, such as unit-resulting resolution lowered to a
chain of binary `resolve` steps. The project should not spend more time
expanding rare cases before frequent and structurally clear classes are
handled.

## Suggested Module Extraction

The implementation should start reducing the monolith. A practical extraction
plan is:

```text
src/vampire_kernel_syntax.ml
  Shared rule names, primitive contracts, metadata parsing helpers.

src/vampire_kernel_check.ml
  Structural checks for primitive clausal certificate records.

src/vampire_kernel_elab.ml
  Syntax.pf elaboration for primitive clausal steps.

src/vampire_source_context.ml
  Original-context source binding, local/global/generated fact resolution.

src/vampire_preprocess_elab.ml
  Smolka-style preprocessing proof-term templates.

src/vampire_skolem_elab.ml
  Skolem/choice CPS proof reconstruction from explicit contracts.
```

`src/vampire_cert_v1.ml` can remain the compatibility parser and integration
front end while this extraction happens. But new broad proof logic should not
continue to accumulate there. The extraction should not be a rewrite that
changes behavior all at once. It should move already-tested functions out with
focused tests, then add new proof power only in the smaller modules.

On the Vampire side, the analogous extraction is:

```text
MegalodonPrimitiveStep
MegalodonPrimitiveProof
MegalodonPrimitiveBuilder
MegalodonCertificatePrinter
```

The exact names do not matter. The key is that inference handlers should build
typed primitive records first, and one canonical printer should serialize
them. Direct string assembly inside individual inference cases should be
migration-only.

## Test Suite Design

A good test suite should have layers.

T0: unit tests for certificate parsing and malformed input. These should be
fast and deterministic. They should include invalid pivots, invalid
substitutions, wrong sorts, missing source formulas, wrong source hashes, and
unsupported rule names.

T1: synthetic kernel tests. These should exercise each primitive rule with
positive and negative tests. They are E3 evidence.

T2: live exported-THF proof-term tests. These should regenerate Vampire proofs
with <= 10 second timeouts, import the certificate, and check a native proof
term against the exported problem. They are E2 evidence.

T3: original-context theorem tests. These should run at actual Megalodon proof
sites and prove the original theorem. They are E1 evidence.

T4: broad parallel integration tests. These should export many problems, run
Vampire in parallel, and classify all failures. They are necessary for scale,
but they should not blur E1/E2/E3/E4 labels.

For performance, broad runs should use the already-agreed pattern:

```text
export all problems once
run Vampire in parallel with 10-second timeout
check certificates in parallel
summarize by evidence class and failure class
```

During focused development, broad runs should be avoided. The current hard
Skolem blocker is visible in a two-target gate, so it is wasteful to rerun a
large suite until that blocker moves.

## Risk Assessment

The largest technical risk is that Skolemization continues to be debugged as a
sequence of local patches. The mitigation is to define the Skolem proof
contract more explicitly and make the Megalodon checker consume that contract
mechanically.

The largest architectural risk is continued growth of `vampire_cert_v1.ml` and
`MegalodonChecker.cpp`. The mitigation is extraction of a small primitive IR
and small Megalodon checker modules, with a rule that counted reconstruction
does not depend on broad legacy compatibility paths.

The largest evidence risk is overreporting. The mitigation is the E1-E4
classification and explicit denominators.

The largest soundness accounting risk is accidental introduction of hidden
facts: bridge assumptions, dynamic `Known` implications, source facts with
wrong propositions, or local witnesses escaping scope. The mitigation is
proof-term checking, source formula validation, final proof provenance audits,
and fail-closed behavior for unsupported transformations.

The largest performance risk is slow iteration. The mitigation is to use small
focused gates while debugging, and parallel batch runs only after a blocker
moves.

## Bottom Line

The project is progressing, but not finished.

It is no longer primarily a Python translator. It is moving toward the
Prover9/Ivy-style path recommended by the audits: Vampire emits more proof
detail, Megalodon parses native S-expressions, source facts are checked more
semantically, dynamic bridge-like `Known` propositions are disallowed in
counted modes, and native `Syntax.pf` proof checking is the intended measure
of success.

The most important implemented advances since the last audit are richer
Vampire Skolem contracts, stricter Megalodon trust boundaries, source-context
classification, set-reflexivity handling, source-local variable closure, and
source-local alias localization. These are all on the path to original-context
proof reconstruction.

The main failure remains exactly where the design says the hard work is:
connecting Vampire's transformed, Skolemized refutation back to the original
Megalodon theorem context with a checked proof term. The current hard example
`11925:125` still fails because grouped Skolem/choice witness cleanup is not
complete.

The right next move is not a broad, slow test run and not another layer of
Megalodon-side guessing. The right next move is to finish the current
Skolem/source-context blocker in the focused gate, then establish ten real
original-context reconstructions, and only then scale back to 100.
