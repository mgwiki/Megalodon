## Executive Summary

The project goal is to reconstruct Vampire proofs inside Megalodon, starting from
THF/TPTP problems exported from Megalodon developments, and ultimately to produce
Megalodon proof scripts or proof terms that kernel-check without `aby`, `admit`,
or `-allowincompleteqed`. The target is not just to parse Vampire proof text. The
target is a general proof-reconstruction path that connects a Vampire refutation
back to the original Megalodon theorem, local hypotheses, definitions, library
facts, and generated facts such as `set`-command equalities.

The previous report, dated 2026-07-12, documented a rich prototype: a large
Megalodon-oriented Vampire proof exporter and a large Megalodon-side Python
reconstructor. That prototype demonstrated valuable plumbing: source linking,
name recovery, proof skeleton generation, many benchmark runs, partial replay of
several inference classes, and concrete examples of difficult proof obligations.
It also made the remaining failure modes visible.

The audit of that report was correct. The prototype line had drifted into an
unbounded implementation strategy. The Python layer had grown into a heuristic
reconstructor with library-specific proof search, and the Vampire exporter had
grown into a stringly typed dump of many internal proof details rather than a
small semantic certificate. The reported broad successes were mostly admitted
skeleton checks, not no-admit proof reconstruction successes. That distinction
matters: admitted source-context checks validate plumbing and syntax, but they
do not prove the final reconstruction goal.

The main change since the previous report is therefore architectural. The current
branch `vampire/megalodon1` treats the rich exporter/reconstructor as a prototype
and diagnostic asset, not as the intended final path. The new intended path is a
small, versioned, Prover9/Ivy-style certificate calculus:

- Vampire should elaborate its own proof into small primitive steps while it
  still has exact access to parents, selected literals, substitutions, rewrite
  positions, and final clauses.
- The Megalodon importer should parse and validate these primitive steps, then
  elaborate them mechanically into Megalodon proof terms.
- Python should not guess pivots, substitutions, hidden clauses, AVATAR state, or
  library-specific proof patterns.
- The only success criterion that counts as proof reconstruction is final
  Megalodon checking without `admit`, without `aby`, and without
  `-allowincompleteqed`.

This pivot is now partially reflected in the repository. There is a draft
certificate specification, a smaller certificate checker/renderer in
`scripts/vampire_certificate.py`, a suite of positive and negative JSON
certificate tests, and early support for consuming explicit Vampire certificate
records. The small path covers a useful initial fragment: inputs, explicit
substitution, binary resolution, factoring, equality resolution, subsumption
resolution, paramodulation, equality symmetry, definition inputs, several
propositional/first-order refutation patterns, and some limited higher-order
syntax rendering.

The project is still not finished. There is no demonstrated suite of 100 real
Megalodon/Vampire no-admit reconstructions. The committed small-certificate
path is healthier than at the start of the pivot: the previous higher-order
lambda smoke failure has been fixed, the local JSON smoke suite has passed, and
a live Vampire outline smoke has passed on the committed heads. Recent committed
work also made instantiated positioned definition rewrites explicit enough to
be checked and replayed in the certificate path. The active working tree now
contains the next uncommitted experiment: a `bool_simplify` certificate emitted
by Vampire and partially validated by the Megalodon importer. That experiment
is not yet compiled, fully elaborated, or counted as a success.

The outlook is still viable, but only if the project continues the pivot and
resists adding more heuristic reconstruction logic to the old Python monolith.
The immediate direction should be to finish a restricted no-admit fragment,
starting with small first-order certificates, then obtain 10 and then 100 real
Megalodon reconstructions in that restricted fragment before adding
skolemization, AVATAR, or higher-order-heavy proof steps.

## Scope and Success Criteria

The original objective remains:

- use Vampire proofs over Megalodon-exported THF problems;
- adapt the relevant Vampire proof-reconstruction/export machinery, especially
  the Leancheck/Dedukti-style detailed proof paths, to Megalodon;
- generate Megalodon proof terms or scripts connected to the original Megalodon
  development;
- test on at least 100 Megalodon theorems and Vampire proofs;
- finish with no `aby`, no `admit`, and no incomplete checking.

Several important constraints have been repeatedly clarified during the project:

- Vampire runs should use THF/TPTP input and should not spend more than 10
  seconds per problem in the normal benchmark loop.
- Batch testing should export all problems first, run Vampire in parallel, and
  then run reconstruction/checking in parallel.
- `/project/tmp` is the working directory for temporary outputs.
- Classical logic may be assumed; `xm` is available.
- Library logical constants such as `or` and `False` should be taken from the
  Megalodon context and not re-invented in final source-linked developments.
- The implementation must be general over Megalodon libraries and cannot
  hardwire particular names such as set-theoretic facts from the current test
  library.
- TPTP axioms produced from Megalodon `set` commands may not correspond to a
  source claim and should be proved explicitly, typically by reflexivity or
  unfolding.
- Source names should be recovered from Megalodon/TPTP mangling rather than
  replaced by opaque generated names wherever possible.

The current state satisfies only part of this. The system has source-linking
infrastructure, proof skeletons, benchmark corpora, a prototype rich exporter,
and a new small-certificate path. It does not yet satisfy the final 100-proof
no-admit requirement.

## What the Previous Report Established

The 2026-07-12 report described the first large prototype. Its main
accomplishments were:

- a Vampire proof output mode oriented toward Megalodon;
- a Megalodon-side Python script that could parse rich Vampire output and emit
  declarative Megalodon proof skeletons;
- source-context linking to original Megalodon facts in representative cases;
- benchmark loops over dozens to hundreds of exported THF problems;
- partial replay of several inference classes;
- analysis of difficult cases involving skolemization, AVATAR, de-Bruijn
  binders, lambda demodulation, CNF/FOOL transformations, and source definitions.

The previous report was honest about admissions, but it still mixed several
kinds of progress in a way that could be misleading:

- "source-context check passed" meant Megalodon accepted a script with
  incomplete proofs enabled;
- "filled claims" meant some proof obligations were solved, but not necessarily
  the final theorem;
- "0 `aby`" was useful, but not equivalent to "0 proof holes";
- many broad checks were proof-skeleton plumbing checks, not final proof
  reconstruction checks.

The useful lesson from the previous report is that source linking and
proof-object plumbing are possible. The negative lesson is that finishing the
old approach by adding more patterns to Python is not a credible route to the
full objective.

## What the Audit Changed

The audit in `/project/Megalodon/reports/audit-REPORT-2026-07-12.md` made six
central criticisms.

First, the reported successes were not proof-reconstruction successes because
they mostly required `-allowincompleteqed` and contained admissions.

Second, the Python layer had become an independent prover. It contained bounded
rule-chain search, equality-chain search, quantified and implicational
introduction, atom transport, source-proof inlining, definition synthesis,
finite successor-induction recognition, and library-specific patterns. Even if
kernel checking protects soundness, such a layer is not a maintainable or
general reconstruction architecture.

Third, "add more metadata whenever Python has to guess" was not a terminating
design. It made the Vampire exporter increasingly large and stringly typed
without producing a small semantic proof calculus.

Fourth, the project was replaying too much of Vampire. The audit argued that
the right analogy is Prover9/Ivy: expand complex prover operations into a small
primitive calculus rather than asking the importer to understand the whole
search engine and preprocessing pipeline.

Fifth, the Smolka-style lesson was interpreted too literally at a low level.
The better reading is to preserve the ATP proof graph and source correspondence,
but justify small local edges using generic target-side procedures and
fine-grained transformation certificates.

Sixth, development had become uncontrolled local hill-climbing: many commits
recognized one more benchmark shape without a small stable target language.

I accept these criticisms. The audit response, stored in
`/project/Megalodon/reports/audit-response-2026-07-12.md`, records the decision:
the current branches should pivot to a small certificate calculus, and the old
rich reconstruction should be treated as a prototype and diagnostic database.

## Prover9/Ivy Analysis

After the audit, I downloaded and inspected Prover9/LADR under
`/project/prover9-ladr`. The relevant files are:

- `apps.src/prooftrans.c`
- `ladr/xproofs.c`
- `ladr/ivy.c`
- `ladr/ivy.h`
- `ladr/just.c`
- `ladr/paramod.c`
- `ladr/demod.c`

The key finding is that Prover9's Ivy export is not just a printer for the
native proof. It is a prover-side proof elaborator.

The `prooftrans ivy` path first calls the general proof expander:

```c
Plist proof2 = expand_proof(proof, &jmap);
Plist proof3 = expand_proof_ivy(proof2);
```

The first stage expands compound Prover9 proof steps while staying inside
Prover9's own term and clause machinery. Hyper-resolution and UR-like steps are
expanded into binary resolution. Demodulation is turned into
paramodulation-style steps. Equality flips, merges, unit deletion, and
`x=x` simplifications are made explicit.

The second stage lowers the already-expanded proof to a small Ivy vocabulary:

- `input`
- `instantiate`
- `resolve`
- `paramod`
- `flip`
- `propositional`
- `new_symbol`

Each printed Ivy line contains a step ID, a primitive justification, parent IDs,
positions where needed, substitution pairs where needed, and the resulting
clause.

I also generated a concrete Ivy proof object:

```sh
/project/prover9-ladr/bin/prooftrans ivy \
  -f /project/prover9-ladr/apps.src/test-directproof/3.1.out \
  > /project/tmp/prover9-ivy/3.1.ivy
```

The first proof object shows the desired shape:

```lisp
(48 (instantiate 24 ((v0 . (A)) (v1 . (B)) (v2 . (B)))) ...)
(44A (paramod 48 (1) 43 (1 1)) ...)
(49 (instantiate 18 ((v0 . (B)))) ...)
(44B (paramod 49 (1) 44A (1 1 2)) ...)
(51 (instantiate 0 ((v0 . (one_for_ivy)))) ...)
(44 (resolve 44C () 51 ()) false NIL)
```

This is the architectural model the Vampire/Megalodon work should follow.
Vampire should elaborate its own proof into such primitive steps. The importer
should not reconstruct missing details by search.

## Current Implementation Work Since the Pivot

The new implementation path has several concrete pieces.

### Draft Certificate Specification

The file `/project/Megalodon/reports/vampire-megalodon-certificate-spec.md`
defines the intended replacement format. It is a draft MVP, not a finished
standard. The important points are:

- certificates are JSON and versioned;
- Vampire and the importer are untrusted;
- accepted success requires Megalodon kernel checking without admissions;
- the importer may parse, validate, instantiate exact substitutions, and
  elaborate fixed constructors;
- the importer must not guess pivots, substitutions, clauses, or library-specific
  arguments.

The MVP constructors include:

- `input`
- `rename`
- `substitute`
- `resolve`
- `factor`
- `equality_factoring`
- `equality_resolution`
- `subsumption_resolution`
- `paramodulate`
- `paramodulate_all`
- `equality_symmetry`
- `definition_input`
- `truth_conflict_resolution`
- `contradiction`

The MVP intentionally excludes AVATAR, SAT split explanations, direct
demodulation replay, direct hyper-resolution or UR replay, higher-order
lambda/de-Bruijn reconstruction, and library-specific source proof search.

That exclusion is not because those features are unimportant. It is because the
project needs a working no-admit restricted fragment before adding harder
features.

### Small Certificate Checker and Renderer

The file `/project/Megalodon/scripts/vampire_certificate.py` implements the
current small-certificate path. It can:

- parse JSON certificates;
- parse a subset of Vampire's emitted `megalodon_certificate_clause(...)` and
  `megalodon_certificate_step(...)` records;
- validate several primitive inference constructors;
- reject malformed substitutions, invalid pivots, bad paramodulation positions,
  invalid equality-resolution steps, and other negative examples;
- emit simple Megalodon proof scripts for selected no-admit smoke tests.

Recent committed work in this file includes:

- treating `vLAM`, `vPI`, and `vSIGMA` as syntax symbols rather than ordinary
  constants;
- rendering bare `vPI` and `vSIGMA` under expected quantifier-function sorts;
- sanitizing Megalodon identifiers so names such as `L'` do not leak as invalid
  surface syntax;
- rendering lambda applications under expected sorts;
- handling source propositions with sanitized symbol names;
- parsing optional full intermediate clauses for definition rewrite chain
  steps;
- splitting positioned definition rewrite chains into smaller intermediate
  Megalodon claims where possible;
- using equality-symmetry helper claims when a clause matches only modulo
  equality orientation;
- instantiating sorted hidden binders before generated proof fragments are
  applied;
- checking instantiated definition rewrite certificates, including concrete
  `from` and `to` terms at the reported position.

The current uncommitted work adds validation for a `bool_simplify` constructor.
The validator recognizes the local Boolean simplifications that Vampire's
`BoolSimp.cpp` performs over `and`, `or`, `not`, Boolean constants, complements,
and reflexive proposition equality. The importer currently checks the reported
parent, target literal, term position, `from`/`to` simplification, rewritten
target literal, and conclusion clause. It does not yet fully elaborate these
steps into no-admit Megalodon proof terms.

This is useful progress, but it also illustrates a risk: the small certificate
script must not become the new monolith. Whenever it starts inferring what
Vampire should have told it, the missing information should be pushed into the
certificate format.

### Vampire-Side Primitive Detail

The latest committed Vampire changes add more explicit information for
definition rewrite chains. In `Shell/MegalodonChecker/MegalodonChecker.cpp`,
the exporter now attempts to compute positioned definition rewrites over the
full current clause. For each rewrite it can emit:

- the definition parent;
- the literal index;
- the term position;
- the `from` term;
- the `to` term;
- the full intermediate clause after the rewrite.

It also self-checks the final locally rewritten clause against Vampire's actual
child clause and falls back to the older unpositioned rewrite payload if the
local computation does not match.

The current uncommitted Vampire change applies the same idea to Boolean
simplification. For a `BOOL_SIMP` clause step, it compares the parent and child
clauses, identifies the single changed literal and changed Boolean subterm, and
emits a `bool_simplify` certificate record containing the parent ID, `from`,
`to`, literal index, term position, rewritten target literal, and full child
clause. This is exactly the right kind of proof-critical data to export from
Vampire, but it still needs compilation, edge-case checking, and Megalodon
proof-term elaboration before it becomes part of the verified path.

This is aligned with the Prover9/Ivy direction. A rewrite should not be
represented merely as "some definition was unfolded." It should be represented
as a primitive replacement at a specified position, producing a specified
intermediate full clause, with a local check that the primitive chain reaches
the actual Vampire child.

The same pattern should be generalized:

- superposition and demodulation should become explicit paramodulation-like
  primitive sequences;
- UR and hyper-resolution should become binary resolution sequences;
- equality flips should be whole-clause transformations preserving all side
  literals and split dependencies;
- cleanup should be explicit structural/propositional steps;
- alpha-renaming should be explicit when needed.

## How the Work Was Done

The development process evolved through several phases.

The first phase was exploration. Vampire was run on Megalodon-exported THF
problems, initially using ordinary TPTP proof output and later using richer
Megalodon-specific proof output. This showed quickly that ordinary proof text
does not carry enough information for reliable proof-assistant reconstruction.
Important details such as exact substitutions, selected equality sides, rewrite
positions, local variable sorts, split dependencies, and transformed formula
origins are often implicit in Vampire's internal state.

The second phase was skeleton generation. The Megalodon-side scripts learned to
parse Vampire output, recover as many original names as possible, and write
Megalodon files containing declarative `claim`s. These files were often checked
with incomplete proofs enabled. That phase was useful because it forced the
source-linking and syntax problems into the open. It exposed missing binders,
bad identifier rendering, shadowed equality names, unresolved generated facts,
lambda/de-Bruijn escaping issues, and failures to connect final contradiction
steps back to the theorem context.

The third phase was rich metadata. Whenever the Megalodon side could not
reconstruct a proof step reliably, additional data was exported from Vampire.
This included substitutions, normal-form paths, lambda hints, AVATAR split
metadata, SAT refutation summaries, skolemization traces, and rewritten parent
clauses. This phase produced many concrete fixes, but it also produced the
architecture criticized by the audit: the exporter became large and the importer
started consuming an open-ended collection of one-off fields.

The fourth and current phase is the pivot to a normalized certificate. The key
change is conceptual: missing information should not be added as arbitrary
metadata for a Python heuristic. It should be added as part of a small proof
constructor with a specified meaning and a local checker. For example, if a
definition rewrite happened, the certificate should say which equality was used,
which target subterm was replaced, and what full clause resulted. If a
resolution happened, the certificate should say which instantiated pivot was
resolved. If a substitution was needed, it should be an explicit preceding
certificate step.

This current phase is still incomplete. Some current code and tests still carry
the older habit of reconstructing or bridging shapes on the Megalodon side.
However, the direction is much sharper than before: each feature should migrate
toward a constructor in the certificate calculus, and each constructor should
have both positive and negative tests.

## Rule and Feature Status

This section summarizes the status of major proof-rule families as of this
report.

### Inputs and Source References

Inputs are supported in both the old skeleton path and the new certificate path,
but final source-map integration is incomplete.

The old path can often recover source names and produce readable Megalodon
claims. That work is valuable. The new certificate path has a `source` field on
input steps, but the end-to-end contract from the Megalodon THF exporter through
Vampire and back into Megalodon proof terms is not complete.

The open work is to make source references lossless and authoritative:

- local theorem hypotheses should have stable IDs;
- local definitions should have stable IDs;
- imported library facts should have stable IDs;
- generated `set` equalities should be marked as generated facts with a local
  proof method such as reflexivity;
- conjecture and negated conjecture clauses should be linked to the theorem
  being proved.

### Explicit Substitution

Explicit substitution is one of the better-supported MVP features.

The small certificate path can validate that a claimed substituted clause is
the result of applying an exact substitution to a parent clause. It has positive
tests such as `valid_substituted_resolution.json` and negative tests such as
`malformed_substitution.json` and `invalid_substitution_result.json`.

This is a strong example of the desired style. The importer should not infer a
substitution from parent and child clauses. Vampire should print it, and the
importer should check it.

### Binary Resolution

Binary resolution is supported in the small certificate checker and in several
generated Megalodon smoke proofs. The certificate names the pivot and the two
parents; the checker verifies that the pivot and complement are present and that
the conclusion is the remaining literals modulo normalization.

The next step is to ensure Vampire emits resolution in this normalized form for
real proof outputs, including cases where a parent first needs explicit
substitution or equality symmetry.

### Factoring and Equality Factoring

Duplicate literal factoring is part of the small calculus. Equality factoring is
represented separately because Vampire's equality factoring has a specific
equality-oriented shape.

The smoke tests include `valid_prop_equality_factoring.json`; however, the
current `run_smoke.sh` invokes Megalodon with `-allowincompleteqed` for the
generated equality-factoring file. That means this part is not yet a clean
no-admit success and should not be counted as final reconstruction.

The right next step is to either finish the Megalodon proof-term elaboration for
equality factoring or keep it out of the MVP no-admit count until it is finished.

### Equality Resolution

Equality resolution is represented in the small certificate path. The checker
requires a negative equality that becomes reflexive after the supplied
substitution, and the conclusion must remove that literal from the substituted
parent clause.

This is also a good example of why explicit substitutions matter. A negative
equality may not be syntactically reflexive before unification, but the
certificate should tell the importer exactly how it becomes reflexive.

### Paramodulation and Demodulation

Paramodulation is a central rule and is partially supported. The small checker
validates paramodulation positions, orientation, selected equality side, target
parent, and resulting clause. There are tests for positive, negative, side
literal, proposition-equality, and simultaneous-style variants.

Demodulation should not be a separate final primitive in the first-order core.
Following Prover9/Ivy, it should be expanded to paramodulation steps. The
current Vampire-side positioned definition rewrite work is a move in that
direction for definition unfolding/folding chains.

The hard part is making Vampire emit this form for all common demodulation and
superposition cases, including nested positions and substitutions. The importer
should not search for redexes. It should check the positions Vampire gives it.

### Definition Inputs and Definition Rewrites

Definition inputs are supported for simple smoke cases. The certificate path can
represent generated definitions, including some function-sort definitions.

Definition rewrite chains are one of the strongest pieces of recent progress.
The committed Vampire branch emits positioned, instantiated rewrite steps with
full intermediate clauses. The committed Megalodon branch parses those records,
checks that the reported `from` term occurs at the reported position, checks
that replacement produces the reported intermediate clause, and uses the
resulting chain in the proof outline. This is one of the best current examples
of the audit's recommendation being applied.

The remaining risk is that the implementation is still embedded inside a large
exporter function rather than a clean reusable primitive-step builder. Once the
idea is validated, it should be factored into shared certificate expansion
helpers.

### Boolean Simplification

Boolean simplification is the current active in-progress rule.

Vampire frequently emits `boolean simplification` steps after FOOL/Boolean
normalization, including transformations such as `not true = false`,
`A /\ true = A`, `A \/ false = A`, idempotence, complement simplification, and
reflexive proposition equality becoming true. These are not all definitional
equalities in Megalodon, so simply treating them as normal-form conversion is
unsound and was rejected by the kernel in an earlier probe.

The current uncommitted direction is better:

- Vampire emits the exact Boolean redex, replacement, literal, position, and
  child clause.
- The Megalodon importer checks that the redex/replacement pair is one of the
  supported `BoolSimp.cpp` simplifications.
- Megalodon proof elaboration should justify the corresponding proposition
  equality using the available classical context, including `xm`, and a
  proposition-extensionality bridge where needed.

This rule is not complete yet. It is reported here because it is the next
visible instance of the Prover9/Ivy principle: export the local primitive
transition from Vampire, then elaborate that small transition in Megalodon.

### CNF and Formula Processing

CNF and formula processing remain partly handled and partly out of scope.

The smoke script constructs several small CNF projection/conjunction examples.
Those check successfully in the current run:

- CNF conjunction projection;
- CNF disjunction/projection;
- quantified CNF projection;
- lambda-containing CNF projection.

These examples are useful, but they should not obscure the larger problem:
general formula processing is a separate proof layer. The Smolka-style and
Matryoshka-style lesson is to use fine-grained transformation certificates, not
one recognizer per formula shape.

For the MVP, it may be better to restrict Vampire schedules or problem classes
so that the first-order clause calculus can be validated before general formula
processing is added.

### Skolemization

Skolemization is understood as an important requirement but is not implemented
as a final certificate constructor.

The project should not infer skolemization from generated names. It needs a
macro-certificate that records the original formula, the transformed formula,
the quantifier dependency information, the generated symbol, and the principle
used to justify the step in classical Megalodon.

Until that exists, benchmarks requiring skolemization should either be excluded
from the first MVP count or counted separately as unsupported.

### AVATAR and SAT Refutation

AVATAR is not ready for the main success path. The prototype identified the
nullary split versus quantified component issue, but it did not solve it in a
stable general way.

The small certificate path currently preserves some AVATAR refutation outlines
as auditable derived assumptions rather than pretending they are reconstructed.
That is the right conservative behavior for now.

The final AVATAR design should have a separate propositional certificate layer.
It should explain the SAT conflict independently and bridge SAT split literals
to first-order component clauses explicitly.

### Higher-Order Lambda and De-Bruijn Terms

Higher-order syntax rendering has improved, but this remains an experimental
area. The earlier smoke failure in
`valid_higher_order_lambda_paramodulation.json` was fixed by preserving and
instantiating sorted hidden binders before applying generated proof fragments.
That fix is committed as `c179890`.

The lesson from that failure remains important: generated proofs cannot treat a
universally quantified claim as if it were already a proof of its body. Object
binders must be instantiated in the right order before the proof argument is
applied. This suggests the importer needs a principled representation of clause
quantifiers and proof-term application structure, even for generated smoke
proofs.

For project planning, higher-order lambda/de-Bruijn work should be delayed
until the first-order fragment is stable.

## Suggested Expert Review Questions

An expert reviewer should focus on several questions.

First, is the proposed small certificate calculus the right target language for
Megalodon? The current constructors mirror the Prover9/Ivy lesson, but
Megalodon may benefit from a slightly different primitive set if certain proof
terms are much easier or harder to build.

Second, where should the boundary sit between Vampire expansion and Megalodon
elaboration? The current recommendation is that Vampire should expand complex
inferences into primitive clauses, while Megalodon elaborates each primitive
using fixed proof templates. An expert should check whether any planned
constructor is still too high-level.

Third, what is the right representation of clauses in Megalodon proof terms?
Many current proof-generation bugs come from turning clauses into nested
`or`/`forall` terms and then applying proofs in the wrong order. A small
clause-elaboration library in Megalodon itself may be better than ad-hoc string
generation in Python.

Fourth, how should source maps be represented? This may require changes to the
Megalodon THF exporter. The proof-reconstruction problem is not just about
Vampire's derivation; it is also about recovering the original theorem context.

Fifth, what is the minimal Vampire schedule for the first 100 no-admit proofs?
Disabling AVATAR and higher-order-heavy transformations may be necessary. The
goal should be a restricted but honest theorem set rather than a broad admitted
skeleton set.

Sixth, should equality use Megalodon's native equality directly in the final
output? If encoded equalities remain necessary for some THF sorts, their
relationship to native equality should be specified and proved.

Seventh, how should skolemization be certified? This is probably the first major
feature to add after the core first-order calculus works.

## Source Linking Status

Source linking is one of the genuinely valuable outcomes of the prototype. The
old skeleton path can often connect Vampire input clauses back to Megalodon
source hypotheses, local definitions, and named facts. The project also
identified several necessary source-linking requirements:

- TPTP symbol names must be mapped back to Megalodon names.
- Local theorem hypotheses and local definitions need explicit source anchors.
- Generated `set` facts may need local reflexivity/unfolding proofs rather than
  source claims.
- The conjecture and its negation must be represented in a way that connects the
  final refutation to the original Megalodon theorem.
- Source maps must be explicit and lossless. Inferring origin from mangled names
  is not robust enough.

The current small-certificate path does not yet fully replace the old source
linking. It has input/source fields in the certificate format and can represent
some source references, but a complete source-map mechanism from the Megalodon
THF exporter through Vampire and back into Megalodon proof terms remains a major
unfinished piece.

The correct direction is:

1. Megalodon's THF exporter should emit an explicit source map for every TPTP
   declaration, axiom, local hypothesis, definition, generated `set` equality,
   and conjecture.
2. Vampire should preserve source identifiers in the certificate.
3. The importer should use the source map mechanically, not by searching the
   Megalodon library or guessing from names.

This source map is as important as the proof calculus. Without it, even a
correct clause-level refutation remains hard to connect to the original
Megalodon theorem.

## Skolemization Status

Skolemization is not solved in the current final sense.

Earlier work explored syntactic skolemization and exported skolemization traces
from Vampire. This was valuable because ordinary Vampire skolemization can hide
too much information behind generated symbols. For proof-assistant
reconstruction, we need:

- the original quantified formula;
- the transformed formula;
- the quantifier prefix;
- the dependency vector;
- the generated Skolem symbol;
- the sort/type of the Skolem symbol;
- the principle used to justify the transformation, typically choice in the
  classical setting.

The audit recommends treating skolemization as a separately specified
macro-certificate, not as a collection of string-pattern recognizers in Python.
That recommendation should be followed.

The MVP certificate spec currently excludes skolemization from the first
restricted fragment. That is appropriate. The next stage after first-order
resolution/paramodulation works should add one explicit skolemization
constructor with positive and negative tests.

## AVATAR Status

AVATAR remains a hard case and should not be part of the first qualifying MVP.

The prototype discovered a specific representation issue: Vampire's SAT split
variables are nullary propositions, while the first-order component clauses may
carry bound object variables. In a focused example, the branch reached a state
where most scoped split/lambda demodulation claims were no longer admitted, but
a remaining obligation had the shape:

```text
forall db0:set,
  or (vampire_eq_prop (In db0 (Power A)) False -> False) split_23
```

The underlying split definition was closer to a nullary SAT proposition
equivalent to a universally quantified component formula:

```text
split_23 <-> forall db0:set, C db0
```

That does not directly imply the pointwise clause:

```text
forall db0:set, or (C db0 -> False) split_23
```

without additional structure. The project therefore needs to distinguish:

- the SAT-level nullary split proposition;
- the first-order component predicate or quantified component formula;
- the propositional proof of the SAT conflict;
- the first-order bridge from component clauses into SAT literals.

The recommended near-term policy is to disable AVATAR in the qualifying
restricted Vampire schedule. Later, AVATAR should be added as its own
propositional certificate layer, probably LRAT-like or resolution-like, rather
than mixing SAT state into lambda/de-Bruijn and first-order reconstruction.

## Higher-Order and Lambda/De-Bruijn Status

Higher-order syntax is partially handled but not robust enough for the main
success path.

Recent work improved rendering of:

- `vLAM` as Megalodon `fun`;
- `vPI` as `forall`;
- `vSIGMA` as an existential encoding;
- lambda applications under expected result sorts;
- de-Bruijn-like variables in local binder contexts;
- sanitized symbol names so raw TPTP/Megalodon encodings do not leak invalid
  identifiers.

This already helps with several generated smoke cases, including lambda hints
and CNF lambda projection. However, the failing
`valid_higher_order_lambda_paramodulation.mg` test shows that quantified proof
application remains fragile.

The audit's recommendation remains sound: higher-order lambda/de-Bruijn
reconstruction should come after the first-order small certificate path is
working. The current HO work should be preserved as diagnostics and as a guide
to necessary certificate fields, but not used as the first milestone for project
success.

## Equality Status

The project originally used custom encodings such as `vampire_eq_prop` and
function-sort equality encodings. The user asked why this is not directly using
Megalodon equality.

The short answer is that Vampire's THF encoding and the current certificate
path often represent equality at several object/function/proposition sorts, and
the translator introduced explicit Leibniz-style equalities to make the
generated proof terms uniform. This is serviceable for prototype smoke tests,
but it is not obviously the best final integration.

The final system should prefer Megalodon's native equality wherever the source
logic and exported problem use it directly. If an encoded equality is needed
for a specific THF representation or sort-polymorphic workaround, that encoding
should be specified in the certificate/source-map layer and bridged explicitly
to Megalodon equality. It should not silently shadow or replace native equality
in source-linked final proofs.

For the first-order MVP, equality should be handled through a small set of
certificate constructors:

- equality symmetry/flip;
- equality resolution;
- equality factoring;
- paramodulation;
- definitional/reflexive simplification.

Each should be checked locally and then elaborated to Megalodon equality proof
terms.

## Problems and Risks

The main current problems are clear.

### The Old Python Reconstructor Is Too Large

`scripts/vampire_reconstruct_megalodon.py` is over 81,000 lines. It should not
receive more logical reconstruction features. It remains useful for:

- extracting benchmark statistics;
- preserving source-linking experiments;
- mining examples;
- comparing old skeleton behavior against the new certificate path;
- generating diagnostics for unsolved inference classes.

It should not be the path to final proof reconstruction.

### The New Certificate Path Is Not Yet Complete

The new path has a spec, tests, and an implementation, but it is not yet the
full system. It lacks:

- a complete Vampire-side normalized certificate pass;
- a complete source map from original Megalodon developments;
- no-admit checking on 10 real restricted examples, let alone 100;
- skolemization;
- AVATAR;
- robust higher-order/lambda reconstruction;
- completed and verified Boolean-simplification proof elaboration.

### The Vampire Exporter Still Mixes Old and New Ideas

The committed definition-rewrite work and the uncommitted Boolean-simplification
work are aligned with the primitive certificate direction. However, the large
`MegalodonChecker.cpp` file still contains many old rich-export mechanisms. The
exporter should gradually be reorganized around a stable primitive certificate
vocabulary rather than one-off `megalodon_step_extra` payloads.

### Test Result Categories Need Discipline

The project must keep separate dashboards for:

- Vampire solved problem count;
- certificate emitted count;
- certificate parsed/validated count;
- Megalodon script generated count;
- Megalodon no-admit checked count;
- admitted skeleton/source-context check count.

Only the no-admit checked count should be used as proof-reconstruction success.

### Avoiding Library-Specific Reconstruction

Several earlier prototype features recognized set-theoretic library patterns.
Those may be useful examples, but they cannot be part of the general
reconstructor. General reconstruction should use source facts explicitly
provided by the problem and proof certificate, not name-specific proof search.

## Recommended Plan

The recovery plan should be staged and enforced with gates.

### Gate 1: Stabilize the Small Certificate Core

The first target is to keep `tests/vampire_certificate/run_smoke.sh` green while
adding one constructor at a time. The next constructor is `bool_simplify`; it
should not be merged into the success-counting path until both the Vampire
export and Megalodon proof-term elaboration are verified without admissions.

### Gate 2: Vampire Emits the Small Calculus Directly

Vampire should produce explicit primitive steps for a restricted schedule:

- no AVATAR;
- no higher-order-heavy preprocessing where avoidable;
- demodulation expanded to paramodulation;
- UR/hyper expanded to binary resolution;
- exact substitutions and pivots exported;
- full resulting clauses included;
- exporter-side self-check that primitive sequences reach the actual Vampire
  child clause.

The current positioned definition rewrite work is a good local example of this
pattern.

### Gate 3: Ten Real No-Admit Proofs

Before scaling, select 10 real Megalodon-exported THF problems in the restricted
fragment. For each problem record:

- problem file;
- Vampire command and timeout;
- whether Vampire solved it;
- whether the small certificate was emitted;
- whether the importer validated it;
- whether Megalodon checked the generated proof without `admit`, `aby`, or
  `-allowincompleteqed`.

This gate should not include admitted skeletons.

### Gate 4: One Hundred Real No-Admit Proofs

Only after the 10-proof gate should the project scale to 100 no-admit proofs.
The run should be parallelized:

1. export all problems;
2. run Vampire in parallel with a 10-second timeout;
3. reconstruct/check all emitted certificates in parallel;
4. produce a denominator-aware report.

The report should separate:

- total exported problems;
- Vampire solved;
- certificate emitted;
- certificate valid;
- Megalodon checked no-admit;
- failures by rule class.

### Gate 5: Add Skolemization

After the first-order core works, add skolemization as a macro-certificate.
This requires a written rule specification and negative tests.

### Gate 6: Add AVATAR Separately

AVATAR should be added as a separate propositional proof layer, not as
ad-hoc side data on first-order clauses. The nullary split versus quantified
component issue must be represented explicitly.

### Gate 7: Add Higher-Order Lambda/De-Bruijn Support

Higher-order support should be staged after the first-order proof pipeline is
real. It needs explicit binder contexts, expected sorts, lambda bodies, and
application typing in the certificate. The current experiments provide useful
test cases but should not define the core architecture.

The large old scripts should be mined for test cases and source-linking

## Current Outlook

The project remains feasible, but the success path is narrower than the
prototype suggested.

The encouraging facts are:

- Vampire has enough internal information to emit useful primitive proof
  details.
- Prover9/Ivy gives a concrete precedent for prover-side elaboration into a
  small proof-object language.
- Megalodon can check generated proof terms for several primitive certificate
  examples without admissions.
- The project now has negative tests, which is essential for avoiding an
  importer that accepts malformed proof objects.
- Source linking is understood much better than at the beginning.

The discouraging facts are:

- the final 100-proof no-admit objective is not close yet;
- the old Python path grew too large and should be quarantined;
- the current uncommitted Boolean-simplification work is not yet verified;
- skolemization, AVATAR, and higher-order reconstruction remain open;
- source maps are still not a complete end-to-end contract.

The most important next action is not to fix one more large benchmark by adding
another recognizer. The next action is to make the small first-order certificate
path boring, green, and real on a small set of Megalodon examples. Once that is
done, the project can add one feature at a time with a specification, negative
tests, and denominator-aware benchmark reporting.

## Bottom Line for Expert Review

The expert should evaluate the project as a pivoting prototype, not as a nearly
finished implementation.

The previous rich-export/Python-reconstruction work answered useful research
questions: what information is missing, how source names flow, what
Megalodon syntax is needed, where skolemization and AVATAR break naive replay,
and how proof skeletons can be connected to source contexts.

The audit correctly identified that this prototype is not a convergent final
implementation. The current branch has begun the right correction: a
Prover9/Ivy-style small certificate calculus with a stricter importer and
positive/negative tests.

The recommendation is to continue only on that corrected path. The project
should count success only when Megalodon checks generated proofs without
admissions. It should avoid new library-specific Python reconstruction logic.
It should make Vampire explain proof steps as normalized primitive certificates,
then let Megalodon check the result.

At the time of this report, the project is not complete, but its next credible
milestones are well-defined:

1. green MVP smoke tests;
2. Vampire-side emission of the small calculus for a restricted schedule;
3. 10 real no-admit Megalodon proof reconstructions;
4. 100 real no-admit Megalodon proof reconstructions;
5. staged addition of skolemization, AVATAR, and higher-order support.
