# Vampire to Megalodon Proof Reconstruction: Project Report

Date: 2026-07-18

Primary repositories:

- Megalodon: `/project/Megalodon`, branch `vampire/megalodon5`
- Vampire fork: `/project/vampire-leancheck`, branch `vampire/megalodon5`
- Temporary/generated artifacts: `/project/tmp`
- This report: `/project/reports/REPORT-2026-07-18.md`

This is a consolidated expert handoff report. It takes into account the earlier
daily reports, the audits through `audit-REPORT-2026-07-16.md`, the audit
responses, the Prover9/Ivy analysis, the Smolka-style transformation
discussion, and the latest local implementation work.

The short version is deliberately conservative:

- The original goal is not finished.
- The codebase now has useful infrastructure for a real solution.
- The project has mostly accepted the audit direction, but the implementation
  still contains too much broad Megalodon-side reconstruction.
- The right path is now clear: Vampire should emit small primitive proof
  certificates, Megalodon should check them as native proof terms, and a
  separate source/preprocessing layer should connect those proof terms back to
  the original Megalodon theorem and context.
- The most important current technical frontier is no longer "can Vampire find
  proofs" or "can we print skeletons"; it is final composition of a checked
  native refutation with the original Megalodon goal, especially across source
  context, proposition extensionality, local definitions, Skolem witnesses, and
  Smolka-style preprocessing transformations.
- The latest focused change is a real improvement on the representative
  Skolem/AVATAR line-172 exported certificate: the checker now replays
  descendants under a shadow Skolem-result hypothesis and uses a choice-free
  quantified AVATAR split replay, so the final Skolem CPS candidate is accepted
  without the certificate-local `Eps_prop` /
  `vampire_exists_prop_choice` leak that blocked the previous draft of this
  report.

The requested target remains:

```text
100 representative original Megalodon theorems reconstructed from THF exports
and Vampire proofs, checked by Megalodon, with no admit, no aby, no incomplete
QED, no hidden bridge assumptions, no certificate-local trusted propositions,
no private replacement for Megalodon's equality or logic, and no Python proof
reconstruction on the qualifying path.
```

That target has not yet been reached.

The two most important committed Megalodon implementation commits since the


Those commits changed the immediate Skolem/AVATAR status materially. Earlier
July 18 diagnostics had localized the remaining problem to Skolem formula step
`u30` and to descendant proof pieces that still exposed the certificate-local
choice witness/theorem pair:

```text
Eps_prop
vampire_exists_prop_choice
```

That diagnostic was useful but not a solution. The new implementation changes
the proof shape:

1. It does not try to accept the direct epsilon-heavy Skolem formula proof as a
   reusable original-context proof.
2. It installs the checked Skolem-result proposition only as a local shadow
   proof hypothesis.
3. It replays the descendant chain of formula copies, CNF/literal projection,
   split dependencies, resolution/factoring/equality steps, AVATAR
   split/refutation steps, and contradiction under that shadow hypothesis.
4. It abstracts the resulting empty-clause derivation as the continuation of
   the Skolem CPS proof.
5. It handles the quantified AVATAR split shape seen in the line-172 fixture by
   eliminating `vampire_exists_prop` directly with a continuation, instead of
   deriving a choice term through `vampire_exists_prop_choice`.

## 2. Evidence Vocabulary

The audits correctly objected that earlier reports mixed together very
different kinds of evidence. This report uses the later evidence classes.

E1: original-context proof reconstruction.

The system proves the original Megalodon theorem in the original local and
global context. The proof has no `admit`, no `aby`, no incomplete QED, no bridge
assumptions, no certificate-local trusted `Known` propositions, and no private
logical constants. This is the actual goal.

E2: exported-THF-bound closed native proof checking.

Megalodon checks a native proof term for a Vampire certificate of an exported
THF/TPTP problem. Source obligations are checked against exported formulas, but
the proof has not yet been composed into the original Megalodon theorem
context.

E3: focused or synthetic primitive-kernel native proof checking.

Megalodon checks native `Syntax.pf` proof terms for a small kernel fragment,
often on synthetic or focused cases. This is important, but it is not the final
workflow.

E4: structural, metadata, and integration evidence.

Vampire finds proofs, emits certificates, Megalodon parses them, source maps
audit, metadata contracts validate, transitional structural preprocessing
diagnostics pass, or generated proof skeletons are useful to inspect. These
results guide development but do not count as proof reconstruction.

The current project has substantial E4 evidence, some useful E3 evidence, and
some exported-certificate E2-style evidence. It does not have the requested 100
E1 proofs.

## 3. Original Goal and Constraints

The project started with a concrete request:

1. Download Vampire from `https://github.com/vprover/vampire`.
2. Locate the code for reconstructing Vampire proofs in Lean.
3. Modify that proof reconstruction route to reconstruct in Megalodon.
4. Download Megalodon from `https://github.com/mgwiki/Megalodon`.
5. Use THF, not just FOF/CNF.
6. Test properly on at least 100 Megalodon theorems and their Vampire proofs.
7. Use the paper `https://arxiv.org/abs/2509.08264` and later the local
   `smolka_etal.pdf` paper as design input.
8. Work iteratively until the result is finished and tests pass.

The later conversation added several non-negotiable constraints:

- Use branch `vampire/megalodonN` in both projects, currently
  `vampire/megalodon5`.
- Use `/project/tmp` for generated and temporary files.
- Do not waste time on repeated unsuccessful Vampire runs. Determine which
  THF problems Vampire can solve once, then iterate on those.
- Use parallel testing for large runs, typically 10 to 20 jobs.
- Limit Vampire proof search to 10 seconds per problem.
- Compile Vampire with parallel make, for example `make -j10`.
- The final scripts/proofs must not use `aby`, because `aby` is implemented as
  admission-like behavior in Megalodon.
- The final scripts/proofs must not use `admit` or `-allowincompleteqed`.
- Classical reasoning is assumed to be available. In particular, `xm`
  (excluded middle) is available in the Megalodon context.
- Megalodon's own equality, false, disjunction, conjunction, implication,
  `iff`, and logical constants should be used. There should be no private
  replacement equality or private replacement logic in counted proofs.
- Generated equalities from Megalodon's `set` command may not correspond to
  named source claims. They must be proved explicitly, normally by reflexivity
  or definitional conversion.
- The implementation must be general across libraries. It must not hardwire
  theorem names or optimize for one current Megalodon library.

These constraints are now reflected in the reports and design documents, but
not all are fully achieved in code.

## 4. Timeline of Architectural Direction

### 4.1 Initial Lean-Port Idea

The first natural idea was to use Vampire's Lean proof output as a guide. This
was reasonable because Lean and Megalodon both check proof terms. Vampire's
LeanChecker and LeanPrinter also already know how to expose more information
than ordinary TPTP proof text.

The relevant lesson from the Lean path was not "print Lean syntax and translate
textually to Megalodon". The better lesson was:

- Vampire has internal proof state at the point where each inference is
  printed.
- That state includes substitutions, pivots, clause shapes, selected literals,
  equality directions, rewrite positions, sorts, Skolem symbols, and
  macro-inference structure.
- The target checker should consume this information explicitly.

This became the basis for the native certificate path.

### 4.2 Python Skeleton and Translator Phase

The earliest productive path used Python scripts to parse Vampire output and
generate Megalodon proof skeletons. That phase was useful in several ways:

- It produced readable `claim`-based skeletons.
- It showed humans how Vampire proof steps relate to Megalodon theorem
  statements.
- It helped recover source names from mangled TPTP names.
- It exposed common inference classes.
- It showed where Vampire's default TPTP proof output lacked the detail needed
  for proof-term reconstruction.
- It provided batch scripts, corpora, and failure classification.

But the Python layer quickly became the wrong architecture. It was no longer a
translator. It had begun to perform bounded proof search, equality-chain search,
source-proof inlining, definition synthesis, finite-pattern recognition, and
library-specific reasoning. The July 12 audit correctly characterized that as
an independent heuristic prover outside Vampire and outside Megalodon's kernel.

That old Python work should remain diagnostic infrastructure only. It should
not be on the qualifying path.

### 4.3 Small Certificate Pivot

The project then shifted to a versioned certificate format. The accepted
interchange format is Lisp/S-expression-like, not JSON. JSON was an earlier
diagnostic format and is no longer the preferred final path.

The intended MVP certificate calculus is small:

- input/source reference;
- explicit instantiation/substitution;
- alpha-renaming or checked variable conversion;
- binary resolution;
- factoring;
- equality resolution;
- equality factoring;
- paramodulation/equality transport;
- contradiction/empty clause.

The key design principle is ownership:

- Vampire should lower complicated search inferences into primitive certificate
  records while it still has the exact internal data.
- Megalodon should parse, validate, and elaborate those explicit records.
- Megalodon should not search for missing pivots, substitutions, positions, or
  sorts.

This is the Prover9/Ivy lesson.

### 4.4 Broad Native Certificate Phase

In practice, the implementation grew faster than the small design. Megalodon
gained a large native OCaml certificate importer in `src/vampire_cert_v1.ml`.
This was useful because it moved away from Python and into Megalodon's own
syntax/proof infrastructure, but it remained broad.

The importer took on many responsibilities:

- certificate parsing;
- source-map parsing;
- source formula comparison;
- THF fragments;
- native term normalization;
- bridge/derived-assumption policy;
- proof-term generation;
- textual proof generation;
- preprocessing transformations;
- AVATAR/SAT handling;
- Skolemization experiments;
- proof debugging.

This phase produced useful evidence, but the July 15 and July 16 audits
correctly warned that simply moving the monolith from Python to OCaml would not
solve the project.

### 4.5 Trust-Boundary Reset

The July 16 audit found a critical issue in the native preprocessing proof-term
frontier. The path constructed native `Syntax.pf` terms, but many transformation
steps were justified by dynamically inserting the desired proposition into the
checker as a new `Known` theorem and then applying it.

That is not proof reconstruction. It is a hidden bridge assumption.

The branch now treats this as follows:

- Dynamic certificate-derived `Known` insertion is rejected by default in
  counted native paths.
- The old behavior is only available when explicitly enabled with
  `MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1`.
- Harnesses that use the old behavior label it structural diagnostic evidence,
  not proof reconstruction.
- `-vampirecertv1corepfcheck` is the genuine native proof-term seed.
- Strict live `vampireaby` must have a native certificate and must fail if that
  certificate cannot reconstruct the current goal.

This trust reset is one of the most important achievements of the project. It
reduced apparent progress numbers, but it made the remaining results honest.

The main Megalodon work is:

1. Native certificate parsing and checking.

   `src/vampire_cert_v1.ml` parses Vampire's native S-expression certificate
   format and performs structural checks, source checks, and proof construction
   for supported fragments.

2. Strict and closed modes.

   The checker distinguishes ordinary strict structural validation from closed
   proof reconstruction. Closed modes reject bridge assumptions and derived
   non-source premises. Unsupported derived clauses cannot be silently turned
   into theorem assumptions.

3. Source-map formula checks.

   For supported THF fragments, source formulas are parsed and compared against
   certificate inputs. This fixed the earlier `$true` source-map loophole where
   a nontrivial certificate premise could be associated with a trivial exported
   declaration.

4. Native proof terms.

   The core path constructs actual `Syntax.pf` terms and calls Megalodon's
   proof checker. This is the accepted direction.

5. Source-context resolver.

   `src/vampire_source_context.ml` and `.mli` define a resolver that can audit
   source obligations against the loaded Megalodon context. It distinguishes:

   - global known facts;
   - local hypotheses;
   - definitions;
   - local definitions introduced by `set`;
   - generated facts;
   - conjecture bindings;
   - unresolved facts.

6. Generated set equalities.

   Generated equalities from Megalodon's `set` command are not counted as
   named source lemmas. Supported generated equality obligations can produce
   native reflexivity proofs rather than becoming assumptions.

7. Local-context boundary.

   The live proof path now distinguishes source-map presence from actual
   dependency in the empty-clause proof. This matters when Vampire sees a local
   definition in the exported problem but the refutation does not actually use
   it.

8. Trust-boundary hardening.

   Certificate-local intermediate proofs are not accepted as proof
   reconstruction. A candidate that checks only under the certificate-local
   delta and not in the live context is rejected.

9. Guarded Skolem CPS path.

   The branch added a guarded Skolem continuation-style proof path, including
   AVATAR split replacement propagation. It first made the cached exported
   line-172 certificate pass the ordinary native preprocess proof-term check
   while exposing that the Skolem CPS candidate itself still contained
   certificate-local choice material. The latest revision goes further: it
   replays the descendant chain under a shadow Skolem-result hypothesis and
   discharges the final focused CPS candidate without the
   `Eps_prop`/`vampire_exists_prop_choice` leak.

10. Live proof-leak diagnostics.

   The live original-context path now has path-aware diagnostics for
   certificate-only symbols inside proof terms and term subexpressions. The
   diagnostics report the offending symbol, its proof path, the containing
   term, and, for bad applications, the expected and actual propositions. This
   converted a vague final-composition failure into concrete reports involving
   `Eps_prop` and then `sK0`.

11. Skolem CPS discharge guard.

   A Skolem CPS candidate is now accepted as discharging certificate-local
   witnesses only if the candidate proof checks and does not contain
   certificate-local choice witnesses such as `Eps_i`, `Eps_prop`,
   `Eps_set_prop`, `Eps_set_set`, or `Eps_set_set_prop`. If the candidate still
   contains such witnesses, the checker keeps the original refutation and
   reports the leak instead of falsely counting the candidate as a successful
   witness discharge.

12. Skolem CPS leak localization.

   The focused work identified where certificate-local choice material first
   entered and survived. The first stored formula proof containing a local

   intentionally not the final original-context artifact. The current solution

The main Megalodon-side problem is that too much still lives in

- `vampire_kernel_syntax.ml`;
- `vampire_kernel_check.ml`;
- `vampire_kernel_elab.ml`;
- `vampire_source_context.ml`;

## 7. Source Linking Status

Source linking is one of the most important parts of the project because the
final proof must be attached to the original Megalodon theorem, not merely to
the exported THF problem.

Current source linking can do the following:

- preserve origin metadata from generated THF problems;
- parse source-map entries from THF comments;
- record source kind, source name, source hash, formula, and generated source
  category where available;
- reject unsupported or mismatched source formulas in strict formula-matching
  modes;
- resolve hash-backed global known facts against the loaded Megalodon known
  table;
- resolve some local hypotheses against the live proof context;
- recognize local definitions introduced by `set`;
- produce reflexivity proofs for some generated equality facts;
- distinguish matched source facts from source facts that actually occur in
  the dependency closure of the empty-clause refutation;
- report source-context audit counts during live certificate checking.

The source-context audit currently reports counts such as:

```text
source_context known=<n> local=<n> local_definition=<n> conjecture=<n> unresolved=<n>
```

This is useful, but not yet enough for the final E1 objective.

The missing pieces are:

1. A proof-producing `source_context` API.

   The planned shape is:

   ```ocaml
   type source_proof =
     | GlobalKnown of string * Syntax.tm
     | LocalHyp of int * Syntax.tm
     | Definitional of Syntax.tm * Syntax.pf
     | Generated of Syntax.tm * Syntax.pf
     | Unresolved of string * Syntax.tm

   type source_context = source_id -> source_proof
   ```

   The implementation has parts of this audit/resolver shape, but not a clean
   final proof-producing API consumed by a separated kernel elaborator.

2. Full local-hypothesis binding.

   Local hypotheses after `set` definitions require careful index projection.
   Some of this was implemented, but the final original-context composition is
   still fragile.

3. Definition proof production.

   Definitions should not merely be matched by source-map metadata. If a
   definition-generated equality is used by the refutation, the system must
   produce a proof by definitional conversion or reflexivity.

4. Conjecture discharge.

   The negated conjecture is a source input for the refutation, but the final
   theorem proof must discharge it at the refutation-to-goal boundary. This
   composition layer remains one of the open problems.

5. Name unmangling and stability.

   The export path preserves names and hashes, and much of the recovery works.
   However, the final design should not rely on guessing how a TPTP name maps
   back to a Megalodon object. The exporter should emit lossless metadata, and
   the importer should use it directly.

In short: source linking is no longer a blank spot. It is a real partial
system. But it is not yet a completed original-context proof reconstruction
layer.

## 8. Smolka-Style Transformation Status

The Smolka-style lesson is that ATP proof graphs can be reconstructed by
preserving the proof DAG and proving local transformation steps in the target
system. The target checker should not duplicate the entire ATP preprocessing
implementation as an unchecked external program. It should either receive
small transformation certificates from the prover or produce proof terms for
well-specified local transformations.

For this project, source-to-clause transformation proof production is distinct
from the clausal kernel. It should include:

- source formula introduction;
- formula-term input;
- rectification and alpha-renaming;
- FOOL Boolean lifting;
- FOOL exhaustiveness and truth-conflict handling;
- boolean/propositional normalization;
- ENNF;
- CNF projection;
- definition introduction, fold, and unfold;
- Skolemization;
- AVATAR, if enabled, through a separate SAT/RUP-like layer or checked
  propositional proof layer.

Current status by transformation:

Source/formula input:

- Source-map validation exists for supported THF fragments.
- Source-obligation audits distinguish formula-checked, formula-missing, and
  formula-unsupported obligations.
- Original-context proof production from these source facts is partial.

Rectification:

- Vampire emits rectification variable maps.
- Megalodon validates and uses some of this metadata.
- Compact binder cases exposed a problem: Megalodon-side guessing of binder
  identity is unsafe. The durable fix is richer Vampire-side primitive
  rectification data.

FOOL and boolean normalization:

- Some structural handling exists.
- It should be kept in the preprocessing layer, not promoted into the clausal
  kernel unless a truly clausal proof requires it.
- Counted proof production is incomplete.

ENNF:

- There has been structural and native-preprocessing work.
- Earlier pass counts involving ENNF are not qualifying if they relied on
  certificate-derived `Known` implications.
- This needs explicit local proof terms.

CNF:

- Vampire emits CNF-related metadata, and Megalodon has partial validation.
- CNF projection is still one of the areas where broad reconstruction could
  grow without discipline. It should be lowered to a specified preprocessing
  proof layer.

Definition introduction/fold/unfold:

- Function-definition metadata and predicate-definition metadata are emitted.
- Some guarded definition-input equalities can be handled by Megalodon
  definitions and reflexivity.
- Predicate definition proofs have some native support, including branch data
  that assumes classical `xm` when required.
- The implementation must avoid hardwiring library theorem names. Definitions
  should be checked from formulas and source metadata, not from names like
  `famunion`.

Skolemization:

- This is the most important transformation frontier.
- The current branch has a guarded Skolem proof path based on choice and
  generated delta definitions.
- Vampire emits useful Skolem metadata: introduced symbols, sorts,
  dependencies, witness data, and parent formula information.
- A cached line-172 case now checks as an exported native preprocess proof, and
  the guarded Skolem CPS attempt reports precise residual choice leaks instead
  of claiming success.
- Opened application-spine uses of the Skolem-result proof are now abstracted,
  but descendant CNF/preprocessing subproofs can still contain inlined
  `vampire_exists_prop_choice` material from the original epsilon-heavy proof.
- The live original-context case still fails later at final composition.

AVATAR:

- AVATAR metadata is richer than before: definitions, components, split
  dependencies, split refutations, and SAT subsumption information are emitted
  or audited.
- Some restricted AVATAR proof-term experiments exist.
- For the final architecture, AVATAR should either be disabled in early
  qualifying runs or checked through a separate propositional certificate layer.
  It should not be hidden inside a broad bridge theorem.

Overall, the Smolka-style transformation layer is understood and partially
implemented, but it is not yet cleanly separated or complete.

## 9. Skolemization in More Detail

Skolemization has been one of the central blockers because it sits exactly
between source formulas and clausal refutation. It is not just a clausal
inference. It changes the shape of formulas by introducing witnesses.

The current approach is:

- Use Megalodon's classical choice principle.
- Introduce generated Skolem symbols as delta definitions where possible.
- Track dependency vectors so a Skolem symbol depends only on the appropriate
  universally quantified variables.
- Normalize generated definitions carefully enough that equality/comparison
  checks do not drift.
- Avoid treating Skolem output as a new source axiom.
- Avoid certificate-derived `Known` implications in counted modes.

Several false starts were rejected:

- globally expanding generated Skolem definitions inside certificate formulas;
- treating every generated Skolem symbol as an ordinary function definition;
- broad proof shifting that ignored local binder structure;
- repairing binder mismatches by global Megalodon-side name rebinding.

Those rejected fixes are important because they confirm the audit's point: the
system should not guess. It should receive explicit primitive transformation
data and use a small proof-producing checker.

The recent committed Skolem/AVATAR improvements are:

```text
269904a Refresh July 18 expert report after Skolem diagnostics
```

With the change, the cached exported certificate passes the native preprocess

## 10. Equality and Logical Constants

The project originally had traces of private or placeholder equality handling.
That is not acceptable for the final result.

The current intended policy is:

- Use Megalodon's own polymorphic equality.
- Use Megalodon's own propositions and logical constants.
- Use the library's `False`, disjunction, conjunction, implication, `iff`, and
  related connectives.
- Use `xm` from the Megalodon context as an approved classical principle.
- Do not introduce private equality or private propositional constants into
  counted reconstruction proofs.

This policy is partly implemented:

- Native equality-resolution and paramodulation proof paths now target
  Megalodon's typed equality where possible.
- Source-context deltas include approved logical knowns with proposition
  checks.
- The live certificate path rejects arbitrary axioms masquerading as approved
  logical principles.

The remaining trouble is proposition extensionality across contexts.

In the loaded Megalodon library, `prop_ext` has a proposition equivalent to:

```text
forall p q:prop, iff p q -> p = q
```

The native certificate core prefers a directional form:

```text
forall p q:prop, (p -> q) -> (q -> p) -> p = q
```

The library also has:

```text
iffI : forall A B:prop, (A -> B) -> (B -> A) -> A <-> B
```

The live line-172 work exposed a mismatch between these two representations. A
proof fragment shaped like:

```text
prop_ext p q (iffI p q fwd bwd)
```

is checked in a context expecting:

```text
prop_ext p q fwd bwd
```

This was not a theorem-specific issue. It was a context-transport issue between
loaded Megalodon proof terms and the certificate's approved native logical
basis. The committed `src/megalodon.ml` diagnostics now try both presentations
and print better proof-application and certificate-only-symbol diagnostics.
This improved the boundary diagnostics, but it did not close the live proof.

A later focused diagnostic tightened the picture. The first reported live
failure was indeed the proposition-extensionality shape mismatch above. After
adding a more permissive directional normalizer for
`prop_ext p q (iffI p q fwd bwd)`, the cached exported proof still checks, but
the live original-context proof still fails. The new failure reports a
certificate-only symbol in the live proof:

```text
Vampire native proof-of-prop live rejection certificate-only proof symbol:
Eps_prop
```

That matters because `Eps_prop` belongs to the certificate's internal choice
basis for prop-sorted Skolem witnesses. It is acceptable inside the closed
exported certificate proof if the Skolem transformation discharges it before
crossing the source boundary. It is not acceptable as an unaccounted symbol in
the live original Megalodon theorem proof.

The newest guard changes the interpretation of this failure. If the Skolem CPS
candidate still contains `Eps_prop`, it is no longer accepted as a successful
candidate. Later diagnostics also show the first surviving choice theorem:

```text
vampire_exists_prop_choice
```

The checker can then fall back to the original refutation and report a raw
generated witness symbol that remains:

```text
certificate-only term symbol sK0 in term #sK0
```

The next fix should therefore eliminate the direct Skolem witness through a
real proof-level transformation, not add `Eps_prop`, `vampire_exists_prop_choice`,
or `sK0` to the live context as hidden axioms.

## 11. Prover9/Ivy Path: How Far Are We?

The audit recommended the Prover9/Ivy path:

```text
complex prover proof
  -> expanded small primitive proof object
  -> small checker in target
```

The project is partially on that path.

What exists:

- A shared `kernel_v1` vocabulary.
- Primitive metadata for many rules.
- A small native proof-term seed in Megalodon.
- The beginning of a Vampire-side kernel syntax/builder extraction.
- Structural audits that check metadata requirements.
- Negative tests for unsupported kernel rule names.

What is missing:

- A complete internal Vampire primitive IR.
- A canonical printer that serializes only primitive records for the kernel
  layer.
- A separated Megalodon kernel checker and elaborator that consumes those
  primitive records.
- A disciplined macro-lowering pass for Vampire inferences such as URR,
  superposition/demodulation chains, subsumption variants, AVATAR, and CNF.
- A clear rule that broad Vampire inferences must be expanded into primitive
  records before Megalodon sees them as proof obligations.

The honest answer is:

```text
We are on the Prover9/Ivy path conceptually, and there are concrete first
modules and metadata contracts, but the implementation is not fully there yet.
The broad OCaml checker and broad Vampire printer are still too prominent.
```

The next work should make this path real by selecting one frequent macro,
lowering it into primitive records in Vampire, and checking only those records
in a small Megalodon module. Unit-resulting resolution is still a good first
macro target because it lowers naturally to a chain of binary resolutions and
appears frequently in live proofs.

## 15. Problems and Risks

### 15.1 The Original Goal Is Still Open

The project does not yet have 100 original-context Megalodon theorem proofs
reconstructed from Vampire certificates. This must remain explicit. Earlier
large pass counts were useful, but they were not E1.

### 15.2 The Monolith Risk Remains

The central Megalodon importer is still too large. The audits warned that a
large Python prover could turn into a large OCaml prover. That risk is still
real.

The current size snapshot is:

```text
28618  /project/Megalodon/src/vampire_cert_v1.ml
11016  /project/Megalodon/src/megalodon.ml
25313  /project/vampire-leancheck/Shell/MegalodonChecker/MegalodonChecker.cpp
 1314  /project/vampire-leancheck/Shell/MegalodonChecker/MegalodonKernelSyntax.cpp
  637  /project/vampire-leancheck/Shell/MegalodonChecker/MegalodonKernelSyntax.hpp
   54  /project/Megalodon/src/vampire_kernel_syntax.ml
   15  /project/Megalodon/src/vampire_kernel_syntax.mli
```

This shows both things at once:

- extraction has begun;
- most complexity is still in the old large files.

### 15.3 Broad Metadata Is Not Yet a Small Certificate

Adding metadata to Vampire is directionally right when it removes guessing from
Megalodon. But metadata alone is not a Prover9/Ivy proof object. A stable small
certificate needs actual primitive steps with semantics, parents, side
conditions, and proof elaboration.

The next design review should ask of every new field:

```text
Is this a field of a stable primitive constructor,
or another ad hoc clue consumed by a broad reconstructor?
```

Only the first is aligned with the audit.

### 15.4 Source Formula Checking Is Not Full Source Proof

Checking that an exported THF formula matches a certificate source input is
valuable. But E1 needs proof terms from the original Megalodon context:

- global known proof;
- local hypothesis proof;
- definitional proof;
- generated set-reflexivity proof;
- conjecture-negation proof;
- transformation proof.

The resolver is moving in this direction, but final composition remains open.

### 15.5 Proposition Extensionality Has a Boundary Contract Problem

The current live line-172 failure exposes a sharper issue than ordinary proof
search incompleteness. The loaded Megalodon context exposes proposition
extensionality in an `iff`-packaged form, while the native certificate core
wants the directional form with the two implications supplied separately. These
are mathematically equivalent, but they are not interchangeable proof terms.

The current bridge normalizers can rewrite some occurrences, but the live
target still fails. The risk is that hash-level identity is hiding two
different presentation contracts:

```text
prop_ext p q (iffI p q fwd bwd)
prop_ext p q fwd bwd
```

This must be resolved by an explicit approved logical-basis boundary. Either
the native core should use the loaded library shape everywhere, or the
source-context bridge should inspect/know which shape is present in the live
delta and normalize to that shape before final checking.

### 15.6 Skolemization Can Become Unsound If Rushed

Skolemization is tempting to handle by just adding the generated witness as an
axiom. That would be unsound for this project. It must be justified by choice,
conservative definitions, and exact dependency tracking.

The current guarded approach is better, but not complete.

### 15.7 AVATAR Should Not Be Mixed Into Everything

AVATAR creates propositional split definitions and SAT-level dependencies. It
can be valuable for Vampire search, but it complicates reconstruction. The
early qualifying path should either disable AVATAR or handle it through a
separate checked propositional certificate layer.

The current code has some restricted AVATAR proof-term support and richer
metadata, but the design should resist treating AVATAR as just another bridge
macro.

### 15.8 Test Runs Must Stay Fast and Focused

The user repeatedly objected to slow sequential iteration. That criticism was
correct. The right workflow is:

1. Export all problems once.
2. Run Vampire once in parallel with a 10-second timeout.
3. Cache solved certificates.
4. Iterate on reconstruction using cached outputs.
5. Use focused live tests only for final integration checks.
6. Run broad parallel suites only at milestone boundaries.

The current project has adopted much of this discipline, but it must be kept.

## 16. What Has Genuinely Improved Since the Audits

The project is not finished, but several improvements are real.

Trust accounting improved.

- Hidden certificate-derived `Known` propositions are no longer counted.
- Strict live mode fails closed without a native certificate.
- Candidate proofs that only work under a certificate-local delta are rejected.
- Source assumptions and proof-producing source bindings are distinguished.

Vampire metadata improved.

- Many frequent inference classes now export explicit details.
- The kernel metadata contract is partially extracted into a separate C++
  module.
- Unsupported kernel rule names are rejected.

Megalodon source context improved.

- The checker can audit global knowns, local hypotheses, local definitions,
  generated facts, conjecture facts, and unresolved facts.
- Generated set equalities can be handled by reflexivity in supported cases.
- Proof dependency closure is used so unused source-map entries do not become
  spurious obligations.

Native proof-term checking improved.

- The small core path constructs real `Syntax.pf` values.
- Several focused clausal and preprocessing fragments now check natively.
- The cached line-172 AVATAR replacement mismatch was fixed.
- The Skolem CPS path now uses shadow replay plus a choice-free quantified
  AVATAR split branch to check the focused line-172 final candidate without the
  old `Eps_prop`/`vampire_exists_prop_choice` leak.

Documentation improved.

- The reports and design documents now distinguish evidence classes.
- The Prover9/Ivy direction is explicit.
- The Smolka-style transformation layer is recognized as a separate layer.
- The branch records audit responses rather than silently changing the
  scoreboard.

## 17. What Has Not Improved Enough

The biggest missing result is still E1:

```text
original Megalodon theorem/context -> checked proof term
```

The implementation has not yet demonstrated this at scale. The live line-172
frontier shows why. Even after the exported certificate proof term checks, the
proof must still be transported into the loaded context and made to prove the
current goal. That final step is nontrivial, and the latest run identifies
`prop_ext` presentation transport as the next concrete blocker.

The second missing result is a clean primitive IR:

```text
Vampire macro inference -> list of small primitive certificate steps
```

The implementation emits much more data, and some primitive-expansion records
exist, but the broad exporter still dominates.

The third missing result is module separation:

```text
large importer -> small parser/checker/elaborator/source modules
```

Extraction has begun, but the majority of logic remains in
`vampire_cert_v1.ml`.

## 18. Recommended Plan From Here

The next phase should be strict and narrow.

### 18.1 Stop Broad Growth

No new qualifying proof logic should be added to the broad replay portions of
`src/vampire_cert_v1.ml` unless it is a correctness fix required to unblock
extraction. The file can remain as:

- a parser for legacy certificates;
- a regression oracle;
- a diagnostic harness;
- a temporary migration layer.

It should not keep gaining new theorem-search behavior.

### 18.2 Finish the Kernel Module Split

Create or complete:

```text
src/vampire_kernel_syntax.ml
src/vampire_kernel_check.ml
src/vampire_kernel_elab.ml
src/vampire_source_context.ml
src/vampire_preprocess_elab.ml
```

The small kernel should own only clausal proof steps. The preprocessing
elaborator should own source-to-clause transformations. The source context
module should own original Megalodon context resolution.

### 18.3 Implement a Real Vampire Primitive Builder

On the Vampire side, continue the extraction started by
`MegalodonKernelSyntax.{hpp,cpp}`. The target should be:

```text
struct primitive_step {
  id;
  rule;
  parents;
  result;
  selected literals;
  substitutions;
  rewrite positions;
  equality direction/from/to;
  variable sorts;
  origin inference id;
}
```

Macro inference handlers should build these records. A single printer should
serialize them. Megalodon should consume these primitive records, not guess
from a mixture of broad rule names and auxiliary strings.

### 18.4 Pick One Frequent Macro and Lower It Fully

The best next target is still unit-resulting resolution or another frequent
macro with a simple primitive expansion. The milestone should be:

```text
Vampire emits only primitive resolve/factor/instantiate records for the macro.
Megalodon checks those primitive records in an isolated kernel module.
The broad replay path is not used.
```

This is more valuable than gaining a few more broad preprocessing passes.

### 18.5 Verify and Then Generalize the Live Skolem-CPS Boundary

The line-172 boundary should remain the next live gate because it blocks
original-context composition. One already identified part of the boundary is
proposition extensionality transport:

- treat loaded `prop_ext` plus `iffI` and native directional `prop_ext` as two
  presentations of the same approved logical principle;
- normalize this at the proof-boundary layer;
- avoid theorem-specific names or line-number checks;
- keep final kernel checking responsible for rejecting ill-typed results.

The more important recent part was Skolem CPS discharge. The focused exported
proof must not contain certificate-only `Eps_prop`, certificate-only choice
theorems such as `vampire_exists_prop_choice`, or generated Skolem symbols such
as `sK0`. The latest implementation now uses guarded shadow replay:

- when a Skolem formula is eligible for CPS, create a shadow proof of its
  result as a temporary hypothesis under an extended proof context;
- replay descendant CNF, AVATAR, substitution, equality, and refutation steps
  under that temporary hypothesis;
- shift ordinary non-shadow parent proofs into the extended context rather than
  rebuilding them heuristically;
- use the shadow final refutation as the continuation consumed by the Skolem
  CPS proof;
- accept the result only if Megalodon's proof checker accepts it and the
  resulting proof term contains no certificate-local choice witnesses, choice
  theorems, or generated Skolem symbols.

This is exactly the boundary where the project must be strict. Adding
`Eps_prop`, `vampire_exists_prop_choice`, or `sK0` to the live symbol table
would make the immediate failure disappear, but it would violate the audit's
trust-boundary reset.

The strict native live line-172 target has now been run after the shadow replay
and choice-free AVATAR split commits. The next implementation step is not to
redesign the Skolem proof again. It is to fix the now-observed
prop-extensionality/source-context boundary:

- report the live proposition bound to the `prop_ext` hash before trying final
  goal composition;
- report which expanded candidate variant proves which proposition under the
  live delta;
- choose the loaded or directional presentation based on the live binding, not
  based on a hardwired theorem name or on retry order alone;
- add a focused regression that fails if the final live proof depends on a
  certificate-local `prop_ext`, `iffI`, `Eps_prop`, or generated Skolem symbol.

### 18.6 Make a Tiny E1 Suite Before Scaling

Before chasing 100, build a deliberately small E1 suite:

- one theorem using only a global known fact;
- one theorem using a local hypothesis;
- one theorem after a `set` command where the generated equality is unused;
- one theorem where a generated set equality is used and proved by
  reflexivity;
- one theorem requiring conjecture-negation discharge;
- one theorem requiring a simple source transformation;
- one theorem requiring Skolem choice in the supported fragment;
- one theorem requiring equality transport;
- one theorem requiring a lowered URR or resolution macro;
- one theorem requiring a small definition fold/unfold.

Every case must check in the original Megalodon file/context without `aby`,
`admit`, or incomplete QED. This is more important than another large E4 run.

### 18.7 Scale Only After the Tiny E1 Suite

After the small E1 suite is real:

1. Export a fixed batch of problems once.
2. Run Vampire once in parallel with 10-second timeouts.
3. Freeze the solved set.
4. Run reconstruction against cached certificates in parallel.
5. Record:
   - denominator exported;
   - solved by Vampire;
   - certificate emitted;
   - source-context resolved;
   - primitive kernel checked;
   - source/preprocessing checked;
   - original-context theorem checked.

This scoreboard prevents E4 progress from being mistaken for E1 completion.

## 19. Outlook

The project is viable, but only if it stays disciplined.

The hard parts are not mysterious anymore:

- proof objects must be primitive enough for Megalodon to check locally;
- source facts must be proof-producing, not just labels;
- preprocessing transformations must have checked proof terms;
- Skolemization must be justified by choice and dependency-correct generated
  definitions;
- local definitions and set-command equalities must be handled explicitly;
- proposition extensionality and library logical constants must be transported
  into the live context correctly.

The main risk is not lack of information. Vampire can expose the required
information. The main risk is architectural drift: adding more Megalodon-side
guessing every time a focused proof fails.

The right near-term expert question is therefore:

```text
Is the next implementation step really reducing a Vampire inference to a small
checked primitive object, or is it adding another broad reconstruction heuristic
to Megalodon?
```

If the answer is the first, the project is moving in the right direction. If
the answer is the second, it is repeating the mistake identified by the first
audit.

## 20. Concrete Open Questions for Expert Review

1. Is the proposed clausal kernel still the right primitive set?

   Current proposed core:

   ```text
   input, instantiate, resolve, factor, equality_resolution,
   equality_factoring, paramodulate, contradiction
   ```

   Should `rename` be a separate primitive, or just alpha-conversion inside
   `instantiate` and source/preprocessing?

2. Should `truth_conflict` belong to the clausal kernel or to the FOOL
   preprocessing layer?

3. Should AVATAR be disabled for the first E1 suite, or should a small SAT/RUP
   layer be specified immediately?

4. What is the best Megalodon proof-term interface for source-to-clause
   transformations?

   Options include:

   - one transformation-specific proof constructor per Smolka transformation;
   - a small formula-processing proof calculus;
   - Vampire-emitted fine-grained formula-processing certificates.

5. How should Skolemization be represented?

   The current choice/delta-definition approach is plausible, but it needs a
   crisp specification:

   - prefix;
   - dependencies;
   - introduced symbols;
   - sorts;
   - witness terms;
   - before/after propositions;
   - exact proof term using choice.

6. Is the proposed shadow replay for Skolem CPS the right way to avoid
   descendant CNF/preprocessing proofs destructing and inlining the
   epsilon-heavy direct Skolem proof?

   The alternative is further post-hoc term rewriting, which has already shown
   signs of being brittle.

7. Should loaded library `prop_ext` be normalized to the directional native
   form at the source-context boundary, or should the certificate core use the
   loaded library shape everywhere?

8. What invariants should a separated `open_step_theorem` operation satisfy?

   This operation is needed whenever stored step proofs under variable binders
   are reused in a result context with retained, dropped, or substituted
   variables.

9. How aggressively should `src/vampire_cert_v1.ml` be frozen?

   The strongest position is:

   ```text
   no new proof-producing behavior there except migration to separated modules
   ```

   That is likely correct, but it may slow near-term debugging.

## 22. Final Assessment

The project has made real progress, but the report should not claim completion.

The most valuable achievements are:

- recognizing that admitted skeletons and broad structural passes are not
  reconstruction;
- moving away from Python as proof producer;
- making trust boundaries explicit;
- forcing strict live certificate mode to fail closed;
- enriching Vampire output with real proof data;
- starting both Megalodon-side and Vampire-side kernel-vocabulary extraction;
- building source-context auditing;
- making generated set equalities and Skolem witnesses explicit obligations;
- reducing the representative exported Skolem/AVATAR blocker to a concrete
  Skolem-CPS/choice-leak problem, identifying `u30`, four abstracted result
  subproofs, `Eps_prop`, and `vampire_exists_prop_choice`, and then fixing the
  focused final CPS candidate by shadow replay plus choice-free quantified
  AVATAR split elimination.

The most serious remaining gaps are:

- no 100-proof E1 suite;
- no fully isolated small-kernel checker/elaborator;
- no complete Vampire primitive proof IR;
- no complete Smolka-style source/preprocessing proof layer;
- unresolved live original-context composition for the representative line-172
  theorem after the exported-certificate fix, currently localized to
  proposition-extensionality/source-context transport;
- continued risk of broad OCaml/Vampire monolith growth.

The recommended direction is therefore:

```text
Freeze broad reconstruction growth.
Finish the small primitive certificate path.
Make source and preprocessing proof-producing.
Solve the live context-composition boundary.
Build a tiny E1 suite.
Only then scale to 100.
```

That is the shortest credible route to the original goal.
