## Executive Summary

The project began with the request to adapt Vampire's Lean proof printing and
reconstruction machinery to Megalodon. The motivating observation is sound:
Vampire, Lean, Dedukti, and Megalodon all operate close enough to typed proof
terms that a detailed Vampire proof should in principle be replayable inside
Megalodon. The first implementation path was a rich Vampire proof dump plus a
large Python translator that generated Megalodon `claim` skeletons. That path
proved useful for diagnostics, name recovery, source mapping, and benchmark
generation, but the audits correctly identified it as non-convergent. It was
becoming a second heuristic prover outside both Vampire and Megalodon's kernel.

The current path is different. Python is no longer treated as a qualifying
proof reconstruction route. The intended architecture is now a Prover9/Ivy-style
certificate architecture:

```text
Megalodon source theorem and local context
  -> THF/TPTP export with source/origin metadata
  -> Vampire proof search, timeout <= 10 seconds
  -> Vampire-side expansion into primitive certificate records
  -> Megalodon native parser/checker and Syntax.pf elaboration
  -> proof of the original Megalodon theorem
```

The implementation is partially on that path:

- Vampire has a Megalodon proof-output mode and now emits increasingly explicit
  certificate metadata, including primitive payloads for several important
  inference families.
- Megalodon has a native OCaml certificate importer in `src/vampire_cert_v1.ml`
  that parses the S-expression certificate, validates source metadata, checks
  several clausal proof-term fragments, and builds Megalodon `Syntax.pf`
  terms for growing pieces of the proof.
- The old broad preprocessing proof-term frontier that relied on dynamically
  installed certificate-local `Known` propositions has been reclassified as
  structural evidence only. Counted proof-term paths now reject such hidden
  bridge assumptions.
- The live `vampireaby` path has been wired to require Vampire's native
  Megalodon certificate output in strict mode. It no longer accepts a proof just
  because an internal certificate-local candidate was built.
- Recent commits fixed concrete trust-boundary defects: proof-source
  assumptions are separated from wider source bindings, local proof leakage is
  rejected at the final theorem boundary, misleading certification logging was
  corrected, and proof-of-prop candidates that only check under the certificate
  delta are rejected before they can be installed as live theorem proofs.

The strongest current evidence is exported-certificate proof-term checking, not
original-context theorem reconstruction. A broad cached native proof-term
preprocessing fragment has passed for well over 100 parseable certificates
after the dynamic-`Known` reset, and focused core proof-term checks pass for
real closed cases such as `hammer.10455.26`. This is meaningful, but it is
still E2 evidence: the certificate refutation is checked at an exported problem
boundary. It is not yet E1 evidence: a proof term for the original Megalodon
theorem in its original context.

The current live original-context frontier is small and concrete. The first
native smoke theorem is reconstructed. The next theorem, the standard
conjunction-left eliminator at line 172 of the current smoke slice, reaches a
checked exported certificate refutation but fails to close the live Megalodon
theorem. Earlier code incorrectly built a certificate-local candidate and later
failed at `Qed`; current code now rejects that candidate earlier and honestly.
The immediate technical reason is Skolem/epsilon leakage: a proof that is valid
inside the exported certificate environment mentions certificate-local
Skolem/choice symbols such as `#sK0` and `#Eps_prop`, while the live theorem
requires a proof over the original proposition `A /\ B -> A`.

The next engineering priority is therefore not another broad pass-count chase.
It is to finish the original-context glue and the Smolka-style transformation
layer, especially Skolemization, in a way that removes certificate-local
symbols and transports the Vampire refutation back to the original Megalodon
statement.

## Evidence Classes Used in This Report

Several earlier reports overcounted integration evidence as reconstruction
evidence. The later audits corrected that. This report uses the following
classes.

E1: original-context proof reconstruction.

The system proves the current Megalodon theorem in the original local context,
without `admit`, `aby`, incomplete QED, bridge assumptions, synthetic
certificate-local `Known` propositions, or private logical constants. This is
the final goal.

E2: exported-certificate proof-term checking.

Megalodon checks a native `Syntax.pf` proof of the exported THF/certificate
problem, with source obligations semantically checked, but the proof has not
yet been composed into the original Megalodon theorem context.

E3: small-kernel or synthetic proof-term checking.

A restricted certificate fragment is checked by native proof terms, usually on
synthetic or curated cases. This is valuable for kernel design but not evidence
that real Megalodon theorems reconstruct end to end.

E4: integration and structural evidence.

Vampire finds proofs under the timeout, emits certificates, Megalodon parses
them, metadata and source maps validate, scripts with holes typecheck, or
structural/preprocessing diagnostics pass. This is useful engineering evidence
but not proof reconstruction.

The project currently has useful E2, E3, and E4 evidence. It has only very
limited E1 evidence from the earliest smoke theorem. It does not have the
requested 100 E1 proofs.

## What Has Been Built

### Vampire Megalodon Proof Output

The Vampire fork contains a Megalodon proof-output path. The implementation is
centered in the `Shell/MegalodonChecker` code. The original motivation was to
reuse and adapt ideas from Vampire's Leancheck/Dedukti proof output rather than
infer all details from ordinary TPTP proof text after the fact.

The exporter now emits native S-expression certificate data for Megalodon. Over
the iterations, this output has gained metadata for:

- source inputs and formula-term inputs;
- proof parent relationships;
- selected substitutions and variable maps;
- variable sorts and de-Bruijn renderings;
- definition inputs and predicate-definition chains;
- FOOL and boolean transformation payloads;
- Skolemization substitutions, Skolem definition metadata, and compressed
  Skolem parents;
- AVATAR split/component/refutation metadata;
- unit-resulting resolution and subsumption primitive payloads;
- rewrite and definition-rewrite chain metadata;
- SAT-side component data for some AVATAR cases.

This is directionally correct because Vampire knows the real internal proof
state. Any detail that Megalodon tries to rediscover later from two printed
formulas is a source of fragility. The current exporter is still too large and
not yet organized around a clean primitive IR, but the information flow is now
closer to what a reliable reconstruction system needs.

### Megalodon Native Certificate Importer

The main Megalodon-side implementation is `src/vampire_cert_v1.ml`. It parses
the S-expression certificate, performs source and origin checks, represents
certificate formulas in Megalodon's native syntax, and elaborates fragments to
`Syntax.pf` proof terms.

The importer currently includes:

- certificate parsing and structural validation;
- source-map parsing and semantic checks for the supported THF fragment;
- source obligation auditing;
- theorem and local-hypothesis source metadata handling;
- source proof/source binding separation;
- native formula-to-proposition translation for the certificate vocabulary;
- a native proof-term elaborator for a core clausal fragment;
- a broader preprocessing proof-term elaborator for exported-certificate
  diagnostics;
- strict, closed, core-only, and native proof-checking modes;
- several fail-closed checks for hidden trust, unsupported syntax, missing
  metadata, and certificate-local leakage.

This importer is also too large. It mixes parser, checker, source handling,
proof elaboration, pretty-printing, testing hooks, and trust policy in one
module. The audits repeatedly objected to this. The right next design step is
to split the new qualifying path into smaller modules such as:

- `vampire_kernel_syntax.ml`
- `vampire_kernel_check.ml`
- `vampire_kernel_elab.ml`
- `vampire_source_context.ml`

`vampire_cert_v1.ml` should become a compatibility/parser/oracle layer rather
than the place where all future proof power is added.

### Source Linking Infrastructure

The project has built several layers of source linking.

At the exported problem level, THF/TPTP problems carry source/origin metadata
that can be linked back to Megalodon facts. The source validator can parse
supported exported formulas, compare them with certificate formulas, and reject
unsupported source syntax in strict modes rather than silently accepting it.

At the native proof level, recent work distinguishes:

- source facts actually used as proof assumptions; and
- broader source bindings needed for context lookup, definitions, or reporting.

This distinction matters for original-context proof reconstruction. A source
fact being available in the exported problem is not the same as it being a
premise in the final live theorem proof. Commit `907da98` separated proof-used
source assumptions from source bindings to avoid composing unused facts into the
final theorem.

The current source link is still not complete E1 original-context linkage. It
does not yet expose a clean API that maps each exported source obligation to a
native proof object in the current Megalodon context. The design documents now
sketch such an API:

```ocaml
type source_proof =
  | GlobalKnown of string * Syntax.tm
  | LocalHyp of int * Syntax.tm
  | Definitional of Syntax.tm * Syntax.pf
  | Generated of Syntax.tm * Syntax.pf
  | SetReflexivity of Syntax.tm * Syntax.pf
```

That kind of API needs to become real. It should answer, for each exported
axiom or conjecture component:

- Is it a global theorem or definition from the original environment?
- Is it a local hypothesis?
- Is it a generated equality from a `set` command?
- Is it a definitional unfolding/refolding fact?
- Is it the negated conjecture boundary?
- What exact `Syntax.tm` proposition and `Syntax.pf` proof object are available
  in the current Megalodon context?

Generated `set` equalities deserve special mention. Some TPTP axioms originate
from Megalodon's `set` command and have no corresponding user-written claim.
These must not be treated as arbitrary bridge assumptions. The agreed solution
is to prove them explicitly in Megalodon, usually by reflexivity or by the
appropriate definitional conversion. The source context layer should classify
them as generated definitional/reflexive facts and construct their proof terms.

### Native Live `aby` Integration

The live `vampireaby` integration is important because it is where the system
must eventually prove the current Megalodon theorem. In strict native mode, it
now treats a configured `-vampireaby` prover as a certificate obligation. If
Vampire emits no native Megalodon certificate, or if the certificate cannot be
composed into the current goal, the command fails.

Recent commits tightened this boundary:

- `3524c06 Report Vampire proof payloads before native closure`

  This separated proof payload logging from final theorem certification. A

## Current Live Frontier

The focused line-172 case is the best description of the current E1 frontier.
It comes from a slice containing standard propositional facts. The relevant
live theorem is the conjunction-left eliminator:

```text
forall A B:prop, A /\ B -> A
```

The exported source theorem exposed to Vampire has the Church-style shape:

```text
forall A B:prop, (forall P:prop, (A -> B -> P) -> P) -> A
```

That is a correct definitional expansion of conjunction, but the final proof
must still be transported back to the live Megalodon theorem statement.

After the source-target transport fixes, a focused debug run showed:

```text
Vampire native core proposition after source composition:
  forall P:prop, ((Psrc -> forall _:prop,P) -> forall _:prop,P)
source u8 = Psrc
source u9 = Psrc -> forall _:prop,_0
found native refutation for target ...
Vampire native certificate built local aby proof candidate...
Vampire produced aby proof payload...
Native reconstructed proof term does not close final theorem...
expected proposition includes #sK0 and #Eps_prop, actual has #sK0 -> #sK0
Failure at line 172 char 4:
  Native reconstruction produced a local proof term that does not close final theorem
```

After commit `878515d`, the same focused case fails earlier and more honestly:

```text
proof-of-prop candidate checked only with certificate delta ... rejecting live proof
Vampire native source-context direct goal reconstruction did not find a proof.
Vampire native certificate checked 41 steps and 2 sources...
Vampire produced aby proof payload...
Failure at line 172 char 4:
  Vampire native certificate did not reconstruct current proof goal at line 172 char 4
```

This is an improvement in trust accounting, not a solved theorem. The checker
now refuses to install a proof that depends on certificate-local Skolem/choice
symbols.

The certificate details show the main Skolem issue:

- source steps construct a nested existential over proposition witnesses;
- a Skolemization step introduces nullary proposition witnesses such as `sK0`
  and `sK1`;
- downstream refutation uses these witnesses;
- the forward Skolem proof is valid inside the certificate environment by using
  choice/epsilon symbols;
- the final live theorem cannot mention those private witnesses.

The current uncommitted experiment is a CPS/backward Skolem refutation
transformation for nullary witnesses. The idea is to avoid leaking Skolem
symbols by turning a refutation of the Skolemized result into an eliminator for
the original existential source:

```text
exists x. P x
  -> (forall x. P x -> target)
  -> target
```

In Megalodon's Church encoding of existence, that is the natural proof-term
shape. The helper currently:

- supports only nullary introduced witnesses;
- counts source existential binders against the substitution length;
- attempts to abstract the Skolemized result proof out of the final refutation;
- recursively eliminates nested `vampire_exists_prop` binders;
- replaces witness symbols with de-Bruijn variables under the eliminators.

This helper is not yet wired, built, or tested. It is included here so the
expert understands the immediate in-progress line of attack. It should be
reviewed carefully before being counted: proof-term shifting around `TLam`,
`PLam`, and term binders is easy to get subtly wrong.

## Smolka-Style Transformations

The user explicitly pointed to the Smolka-style transformations, and later
provided `smolka_etal.pdf` for reading. The lesson taken from that material is
that proof reconstruction should treat preprocessing as a sequence of typed,
compositional transformations, not as an unstructured list of formulas whose
relationships are guessed afterward.

The transformations that matter here include:

- definitional expansion and contraction;
- FOOL boolean encodings;
- proposition-valued boolean simplification;
- rectification;
- lambda and de-Bruijn normalization;
- conversion between higher-order formulas and clausal representations;
- skolemization;
- CNF projection and clause extraction;
- equality and paramodulation-oriented rewriting;
- AVATAR split introduction and SAT refutation.

Some of these are already partly replayed. The project has implemented native
handling for definition rewrite chains, predicate-definition chains, several
FOOL implication conversions, compact and dependent Skolem metadata, quantified
AVATAR definitions, mixed AVATAR split clauses, and negative AVATAR component
replacement.

The important caveat is that "partly replayed" is not the same as "available as
a clean Smolka-style transformation checker." Much of this work still lives in
the broad `vampire_cert_v1.ml` monolith. Some of it began as replay-specific
logic around concrete certificates rather than as a small typed transformation
language. The audits are right that this must be corrected.

The preferred Smolka-style layer should have these properties:

- each transformation has a typed input and output proposition;
- each transformation produces a `Syntax.pf`, not a new trusted `Known`;
- source and generated facts are resolved through the source-context API;
- choice/classical principles are used from the approved Megalodon logical
  basis, not declared privately;
- unsupported transformations fail closed;
- Vampire emits enough metadata that Megalodon does not infer substitutions,
  sorts, rewrite positions, or Skolem dependencies by search.

Skolemization is the current most urgent Smolka-style transformation because it
is exactly what blocks line 172 from becoming an E1 proof. The right direction
is not to use an internal `Eps_prop` proof in the final theorem. The right
direction is to transform refutations under Skolem witnesses back through
existential elimination or a logically equivalent classical transformation
whose proof term lives in the original context.

## Equality and Logical Constants

The project should use Megalodon's equality and logical constants directly.
Earlier prototypes introduced or shadowed Vampire-local encodings such as
`vampire_eq_prop`, `vampire_false`, or private equality helpers. Those encodings
can be useful internally while parsing Vampire output, but they must be
eliminated before a final proof is installed in the live Megalodon context.

The current direction is:

- parse Vampire's internal equality/logical vocabulary;
- map it to Megalodon's existing equality, `False`, implication, universal
  quantification, conjunction encodings, and library principles;
- use classical principles such as excluded middle from the available context;
- reject final proofs that mention certificate-only symbols.

Commit `0ed0d38` added checks for certificate-only symbols in final theorem
proofs. Commit `878515d` extended similar hygiene to proof-of-prop candidates.
This is why the line-172 proof no longer incorrectly passes as a local
candidate.

There is still cleanup to do. The native certificate language contains
Vampire-specific names because Vampire output needs a stable vocabulary. The
trust invariant should be that those names are either:

- parsed away into Megalodon syntax;
- resolved to reviewed Megalodon library constants by hash/name/context;
- retained only in certificate-internal propositions that never escape to the
  final theorem; or
- rejected.

They should not become private axioms in the final proof.

## Prover9/Ivy Influence

The Prover9/Ivy analysis remains one of the clearest architectural guides for
this project.

Prover9 does not ask an external checker to reconstruct large macro
inferences from printed before/after formulas. Its proof pipeline expands the
normal Prover9 proof into more explicit steps and then lowers those steps into
a small Ivy object language. The important Ivy-style primitives are things
like:

- input;
- instantiate;
- flip;
- resolve;
- paramodulate;
- propositional;
- limited new-symbol introduction.

Each step carries the data needed by the checker: parent IDs, positions,
substitutions, and the resulting clause.

The intended Vampire/Megalodon analogue is:

```text
Vampire macro proof
  -> Vampire primitive expansion records
  -> canonical Megalodon certificate S-expression
  -> Megalodon small checker
  -> Syntax.pf elaboration
```

The current implementation is only halfway there. We do have `kernel_v1`
metadata and several primitive payloads, but there is not yet an isolated
Vampire-side primitive proof builder analogous to Prover9's `expand_proof_ivy`.
Much of the C++ code still prints or assembles Megalodon metadata directly in
the exporter. Much of the OCaml code still reconstructs broad proof families in
one monolithic module.

The July 16 and July 17 design documents therefore recommend a stricter split:

- Vampire should build internal primitive records first.
- One canonical printer should serialize them.
- Megalodon should consume the records mechanically.
- Macro inferences should either lower to primitive records or declare an
  explicit unsupported/fail-closed status.
- The initial clausal kernel should stay small: input, instantiate, resolve,
  factor, equality resolution, equality factoring, paramodulation, and final
  contradiction.

Unit-resulting resolution is a good first macro-lowering target because it is
frequent in real proofs and decomposes naturally into binary resolution steps.
AVATAR should not be hidden in a bridge theorem; it needs either explicit
SAT/RUP-style checking or a separate audited AVATAR layer.

## Problems Encountered

### 1. Overclassification of Evidence

Earlier reports counted admitted skeletons, structural strict runs, and
preprocessing proof-term checks as stronger evidence than they were. The audits
were right to correct this. The project now distinguishes E1-E4 evidence and
does not count hidden `Known`-based preprocessing passes as proof
reconstruction.

### 2. Python Reconstruction Drift

The Python translator was useful but not the preferred final path. It grew into
heuristic reconstruction, including name recovery, formula parsing, proof
pattern detection, and library-specific proof search. The project has stopped
treating that as qualifying. Python remains useful for diagnostics and batch
analysis only.

### 3. Monolith Growth

Both sides have grown too much:

- Megalodon's `src/vampire_cert_v1.ml` combines too many responsibilities.
- Vampire's `MegalodonChecker.cpp` remains a large exporter rather than a clean
  primitive proof builder plus canonical printer.

This is an architectural risk. It makes correctness review harder and
encourages adding another special case whenever a benchmark fails.

### 4. Source Linkage Is Still Not Native Enough

The current system can link exported THF facts to source metadata, but it does
not yet provide the final source-context API that returns native proof objects
for original Megalodon facts, local hypotheses, generated set equalities, and
definition unfoldings. That API is mandatory for E1 proof reconstruction.

### 5. Skolemization Leaks Certificate-Local Symbols

Skolemization currently blocks the line-172 live theorem. The certificate can
be checked internally, but the proof candidate mentions private Skolem/choice
symbols. The final proof must eliminate those symbols by transforming the
refutation back through the original existential/choice principle in the source
context.

### 6. AVATAR Needs a Real Checked Layer

Some AVATAR component and split cases have been handled, including a negative
split case. But AVATAR is not yet a principled small-kernel layer. It should
eventually be checked through explicit SAT/RUP-style data or a separately
audited AVATAR proof object.

### 7. Equality Must Be Megalodon's Equality

Internal Vampire equality encodings are acceptable as parse-time vocabulary,
but final proofs must use Megalodon's equality and known equality principles.
The code now rejects final proof leakage of certificate-only symbols, but the
mapping and cleanup need to be completed.

## What Is Working

The following are real accomplishments:

- Vampire can prove many exported Megalodon THF problems under the agreed
  timeout and emit Megalodon-specific certificate data.
- Megalodon can parse and structurally validate those certificates.
- Source and origin metadata are validated much more strictly than in the
  early prototypes.
- Python is no longer a qualifying proof reconstruction path.
- The native proof-term checker has a real clausal core seed.
- Several real certificate fragments now elaborate to `Syntax.pf`.
- The old dynamic-`Known` loophole has been identified and reclassified.
- Live strict `vampireaby` no longer silently falls back to unchecked behavior.
- Final theorem installation now rejects certificate-local symbols.
- Proof payload logging is no longer conflated with proof certification.
- The line-172 failure is now a crisp original-context/Skolemization problem
  rather than a vague "Vampire reconstruction failed" issue.

These are meaningful improvements over the state at the start of the week.

## What Is Not Working Yet

The following are still not solved:

- There is no 100-theorem E1 benchmark.
- The main source-context API is not complete.
- The negated conjecture/refutation-to-theorem boundary is still incomplete for
  nontrivial live theorems.
- Skolemization is not yet discharged without leaking private symbols.
- Smolka-style preprocessing is not yet a small typed transformation checker.
- Vampire does not yet have a clean isolated Prover9/Ivy-style primitive
  expansion builder.
- AVATAR is not yet represented as a small checked proof object.
- The qualifying implementation is still too concentrated in large modules.
- The current uncommitted Skolem CPS helper is experimental and unverified.

## Recommended Next Milestone

The next milestone should be narrow and auditable:

> Produce 10 original-context Megalodon theorem proofs through the native
> Vampire certificate path, with no `admit`, no `aby`, no incomplete QED, no
> bridge assumptions, no certificate-local `Known`, no certificate-only symbols
> in the final proof, and no Python reconstruction.

The line-172 conjunction eliminator should be the first target. It is small
enough to analyze, but it exercises exactly the missing pieces: source theorem
transport, conjunction definitional expansion, nested proposition
existentials, Skolemization, and final live theorem closure.

The concrete work plan is:

1. Finish and verify the nullary-Skolem CPS discharge for the line-172 case.

   This must be built, proof-checked, and reviewed for binder shifting. If it
   succeeds, generalize carefully. If it fails, use the failure to define the
   needed transformation explicitly rather than adding another heuristic.

2. Implement the source-context API for live theorem composition.

   It should resolve local hypotheses, global known facts, definitions,
   generated set/reflexivity facts, and conjecture negation into `Syntax.pf`
   objects.

3. Isolate the small kernel modules.

   New qualifying code should move out of `vampire_cert_v1.ml`. The monolith
   can remain as parser/oracle during transition, but not as the long-term
   proof checker.

4. Move one frequent Vampire macro inference into true primitive expansion.

   Unit-resulting resolution or subsumption-resolution chains are good first
   candidates. Vampire should emit the primitive sequence; Megalodon should
   check it mechanically.

5. Keep broad tests cached and parallel.

   Do not spend time repeatedly rerunning unsuccessful Vampire searches. Use
   the known solvable THF set, cache certificates under `/project/tmp`, and run
   Megalodon checks in parallel.

6. Only after 10 E1 proofs, scale to 100.

   Broad pass counts before the source-context and Skolem boundary are solved
   will mostly measure integration, not reconstruction.

## Questions for Expert Review

The expert review should focus on these questions:

1. Is the proposed CPS/backward treatment of Skolemized refutations the right
   way to eliminate certificate-local Skolem witnesses in Megalodon's proof
   term language?

2. Should Skolemization be handled as a source/preprocessing transformation
   using existential elimination, as a classical choice theorem from the
   Megalodon library, or by a different Smolka-style normal-form theorem?

3. What should be the smallest stable primitive kernel for the clausal part?
   Should `truth_conflict`, `rename`, and AVATAR live in the kernel or outside
   it?

4. How much of the existing `vampire_cert_v1.ml` should be retained as an
   oracle, and how aggressively should the new small modules be split out?

5. What source-context representation is best for local hypotheses and
   generated `set` facts across the THF export/Vampire/import round trip?

6. Is the current Vampire-side certificate vocabulary close enough to support a
   true Prover9/Ivy-style primitive expansion, or should the exporter be
   redesigned around an internal primitive record type before adding any more
   metadata?

7. Which benchmark should define the first accepted milestone: the line-172
   smoke theorem plus nine nearby theorem-library facts, or a held-out set from
   the hammer corpus?

## Chronology of the Project

This section reconstructs the main technical arc, because the repository now
contains many commits and several reports whose claims were later corrected by
audits.

### Initial Prototype: Rich Export and Python Skeletons

The earliest implementation was designed around a practical question: can we
get anything useful out of Vampire proofs over Megalodon-generated THF problems
quickly? The answer was yes. Vampire could solve many exported problems, and a
Python script could parse ordinary and enriched proof output well enough to
generate Megalodon files with declarative `claim` skeletons.

This phase produced several useful assets:

- a corpus of exported THF/FOF problems;
- cached Vampire outputs;
- name-recovery logic for mangled TPTP names;
- source-origin comments and source-map validation ideas;
- Megalodon skeletons shaped like the original developments;
- early statistics about frequent Vampire inference classes;
- concrete examples where source linking, Skolemization, AVATAR, FOOL, and
  equality rewriting fail.

It also revealed the main risk. The Python layer started to do too much. It
parsed formulas, reconstructed missing sorts, guessed substitutions, tried to
recognize proof patterns, and emitted increasingly specialized Megalodon
lemmas. That path could generate human-readable skeletons, but it did not scale
as a trusted proof reconstruction architecture.

The user repeatedly pushed against this failure mode. The important questions
were:

- why are we not modifying Vampire's Lean/Dedukti-style proof output directly?
- why are we guessing details in Python that Vampire already knows?
- why are we not focusing on frequent large proof classes?
- why are pass counts based on admits or `aby` being treated as progress?
- why are there hardwired library names?

Those criticisms were correct. The Python phase should be viewed as diagnostic
infrastructure, not as a foundation for the final system.

### First Pivot: Native Certificates and Closed Textual Scripts

The next phase moved proof output into a native Vampire S-expression
certificate and built an OCaml importer inside Megalodon. This was a major
improvement because it removed Python from the counted path and reused
Megalodon's own syntax and checking infrastructure.

The initial native importer could emit Megalodon proof scripts from
certificates. It supported source maps and a growing set of inference replays.
Early broad runs reported hundreds of passing generated scripts. Those results
were useful, but the July 14 audit identified a serious issue: the scripts
could contain bridge assumptions. A script with a premise named
`bridge_resolution_123` and a final proof without textual `admit` is still not
a proof of the original theorem. It is a proof of a stronger theorem whose
extra premise states the missing inference.

The response was to add closed modes. Closed modes rejected bridge and derived
assumptions and required source obligations to be validated. This gave the
project its first meaningful closed textual frontier. The July 15 audit
accepted that as genuine progress while warning that the architecture was still
growing in the wrong direction.

The lesson from this phase is that closedness must be a machine-enforced trust
policy, not a convention in the shell harness. The checker must know which
premises are original source facts, which are approved logical/library facts,
which are generated definitional facts, and which are forbidden derived
premises.

### Second Pivot: Native `Syntax.pf` Proof Terms

The next phase addressed a deeper concern: textual generated scripts are a poor
intermediate representation for proof reconstruction. They are difficult to
inspect mechanically, encourage arity-specific helper lemmas, and make it hard
to distinguish proof construction from pretty-printing.

The project therefore started constructing Megalodon `Syntax.pf` values
directly. The clausal `corepfcheck` path is the cleanest seed of this idea. It
checks a small proof fragment using Megalodon's native proof checker:

- source/input;
- substitution or instantiation;
- resolution;
- factoring;
- equality resolution;
- equality factoring;
- paramodulation;
- contradiction.

The July 16 audit accepted this as genuine progress but found another trust
defect in the broader preprocessing proof-term checker. Many preprocessing
steps created exactly the theorem they needed as a certificate-local `Known`
and then applied it. This was a hidden bridge assumption. It did not appear as
a textual `bridge_*` premise, but it had the same trust shape.

The response was a trust-boundary reset:

- transitional certificate-derived `Known` installation is no longer a
  qualifying proof-term path;
- modes that opt into it are structural diagnostics only;
- counted native proof-term checking rejects certificate-local `Known` names;
- final live proofs reject certificate-only symbols.

This correction is one of the most important pieces of the current state. The
project lost some headline pass-count momentum, but the remaining evidence is
more honest.

### Third Pivot: Live Original-Context Composition

The latest phase is about moving from E2 exported-certificate checking to E1
live theorem reconstruction. This is where the hardest boundary appears.

In an exported THF problem, Vampire proves unsatisfiability of a set of source
formulas and a negated conjecture. Inside Megalodon, the desired result is a
proof of the current theorem in the current local context. Bridging these two
worlds requires:

- resolving each exported source formula to a live proof object or local
  hypothesis;
- representing generated facts such as `set` equalities by actual proof terms;
- transporting definitional expansions back to the user's notation and
  definitions;
- converting a refutation of the negated conjecture into a proof of the
  original goal;
- eliminating any Skolem or preprocessing symbols introduced only in the
  certificate.

The live native `vampireaby` path now exercises this boundary. It can invoke
Vampire, request `--proof megalodon`, parse the certificate, check it, and try
to install a native proof of the current goal. The first smoke theorem is
handled. The second theorem, line 172, exposes the current blocker:
Skolemization/choice leakage and source theorem transport.

This is the right kind of failure. It is not a batch infrastructure problem.
It is a small, inspectable failure at the trust boundary that the final system
must solve.

## Audit Incorporation

The reports and audits changed the project substantially. The following audit
points are now accepted as standing constraints.

### From the July 12 and July 13 Audits

The early audits objected that Python reconstruction and enriched proof text
were growing without a small trusted core. The project response was to begin
the native certificate path and to study Prover9/Ivy as the model.

The current standing rule is:

> Python may help inspect, batch, or diagnose, but it is not a qualifying proof
> reconstruction path.

The project has not deleted the old Python infrastructure, because it is still
useful for corpus analysis and comparisons. But no final claim should rely on
it.

### From the July 14 Audit

The July 14 audit's central point was that strict structural checking was not
the same as closed proof reconstruction. Bridge premises were still allowed in
the generated theorem. The response was the closed-mode work: derived and
bridge assumptions became explicit and forbidden in closed modes.

The standing rule is:

> A generated theorem is not closed unless every premise is classified as a
> verified original source fact, an approved logical/library theorem, or an
> explicitly generated definitional/reflexive fact. Any other premise fails the
> run.

This also changed reporting discipline. Runs that merely validate certificate
structure or source maps are useful, but they are E4 integration evidence.

### From the July 15 Audit

The July 15 audit accepted the closed textual progress but warned that the
architecture was still poor. It emphasized that the system was accumulating
large amounts of Megalodon-side replay code rather than moving proof detail
into Vampire primitive records.

The standing rule is:

> The broad textual replay engine should be preserved as an oracle/regression
> asset, not extended indefinitely as the final checker.

This report repeats that warning because the codebase still shows the risk.
Recent correctness fixes in `vampire_cert_v1.ml` were necessary, but adding
large new inference families there is not the right long-term plan.

### From the July 16 Audit

The July 16 audit found that the native preprocessing proof-term checker had
recreated the bridge-assumption problem by dynamically installing
certificate-local `Known` propositions. This was the most important recent
correction.

The response was:

- reclassify old preprocessing proof-term pass counts as structural diagnostics
  unless they run without transitional `Known`;
- reject certificate-derived `Known` in counted proof-term paths;
- add final theorem closure checks for live proofs;
- reject certificate-only symbols in final proofs;
- reject proof-of-prop candidates that only check under the certificate delta.

The standing rule is:

> A proof term only counts if its `Known` references resolve to the approved
> Megalodon logical/library basis or original source context. The certificate
> itself may not declare new trusted theorems that justify its own steps.

This rule is now reflected in the line-172 behavior. The system can still build
a local proof candidate under the certificate delta, but it refuses to install
it as a live theorem proof.

## Detailed Component Status

### Vampire Exporter

The Vampire exporter is productive but needs refactoring. It emits enough data
to make many previously opaque proof classes inspectable. The recent commits
on the Vampire branch include primitive metadata for SAT subsumption, rectify
variable maps, subsumption fast paths, predicate-definition primitives,
unit-resulting resolution expansion chains, and AVATAR-related payloads.

The main issue is not lack of metadata. The issue is that metadata is still
added case by case rather than produced by a central primitive proof object.
The target design should introduce an internal representation like:

```text
MegalodonPrimitiveStep {
  id;
  rule;
  parents;
  conclusion;
  selected literal indices;
  rewrite position;
  rewrite direction;
  substitution;
  variable sorts;
  symbol sorts;
  source/preprocess payload;
}
```

The exact C++ API can differ, but the architectural requirement is that macro
handlers produce primitive records first. Printing should be a separate
canonical serialization step.

The exporter should also fail closed when a macro inference claims to have a
primitive expansion but cannot supply the required fields. This is preferable
to printing a partial record and asking Megalodon to infer missing data.

### Megalodon Certificate Parser and Checker

The Megalodon parser/checker can handle the current certificate syntax and has
become much stricter. It validates source maps, parses supported THF formulas,
checks native proof terms for core fragments, and enforces several trust
policies.

The main issue is maintainability and trust clarity. The module
`src/vampire_cert_v1.ml` now acts as:

- certificate syntax definition;
- S-expression parser;
- THF parser;
- source map checker;
- source obligation auditor;
- proof-term elaborator;
- textual emitter;
- normalization engine;
- inference replay engine;
- debug harness;
- trust policy gate.

That concentration is risky. Expert review should pay special attention to
whether future work should first split the module, even if it slows the next
few benchmark improvements. My assessment is that a split is necessary before
the project can be trusted as a long-term proof reconstruction path.

### Source Context

Source context is the most important missing abstraction. The project has
source metadata and source validation, but not a complete native source-context
object.

The eventual source-context layer should be constructed by Megalodon at the
moment it exports the Vampire problem or invokes `vampireaby`. It should retain
enough information to answer proof requests after Vampire returns:

- source ID;
- original name;
- original local hypothesis index, if any;
- original theorem/global identifier, if any;
- proposition as `Syntax.tm`;
- available proof as `Syntax.pf`, if already proved;
- definitional proof or conversion path;
- generated set/reflexivity proof;
- role in the conjecture/refutation boundary.

The current approach can recover many names from mangled TPTP identifiers, but
name recovery is not enough. The final proof should not depend on best-effort
string demangling. It should use stable source IDs and native proof handles
recorded by Megalodon when exporting the problem.

### Preprocessing and Smolka Transformations

The preprocessing layer has many pieces but lacks a clean proof language. The
project can replay specific FOOL, definition, rectification, Skolem, and AVATAR
cases, yet the code often proceeds by recognizing concrete certificate shapes.

The desired layer should be closer to:

```text
Transformation step:
  input proposition P;
  output proposition Q;
  rule name R;
  explicit parameters;
  proof term pf : P -> Q, or pf : Q -> P, or equivalence proof;
  trust basis used by pf.
```

This representation would make it clear whether a transformation is proved,
assumed, source-derived, or unsupported. It would also make composition into
the final theorem explicit.

Skolemization should be prioritized within this layer because it is currently
the E1 blocker. The project should avoid the tempting shortcut of making
`Eps_prop` available in the final context as a private choice symbol. If a
choice principle is needed, it must be an approved Megalodon principle, and the
final proof must eliminate or encapsulate the witness so no certificate-local
symbol remains in the theorem.

### Clausal Kernel

The small clausal kernel is the healthiest part of the design. It should remain
small. The likely stable core is:

- input boundary;
- instantiate;
- resolve;
- factor;
- equality resolution;
- equality factoring;
- paramodulation;
- contradiction/final empty clause marker.

It is worth debating whether `rename` is a kernel rule or just alpha-conversion
inside instantiation. It is also worth debating whether `truth_conflict` belongs
in the clausal kernel or in preprocessing/FOOL. AVATAR should stay outside the
first kernel milestone.

The core should be checked by native proof terms only. It should not call into
the textual replay engine for missing cases.

## Current Technical Debt

The following debt should be considered real, not cosmetic.

### Large Untracked Artifact Sets

Both repositories contain many untracked generated files: hammer exports,
Vampire outputs, build artifacts, and local binaries. This has not directly
affected proof correctness, but it makes status inspection noisy and increases
the risk of accidentally depending on stale artifacts. The project should keep
generated corpora under `/project/tmp` or clearly committed test fixtures, not
as large untracked trees under source directories.

### Report Duplication

There are top-level reports under `/project/reports` and branch-local reports
under `/project/Megalodon/reports`. They are not always identical. For expert
review, the branch-local documents are useful because they travel with the
code, but the user requested reports in `/project/reports`. The project should
either mirror intentionally or choose one authoritative location.

### Naming and Evidence Drift

Earlier terms such as "strict", "closed", "preprocesspfcheck", and "PASS" were
used inconsistently. The current report's E1-E4 classification should be used
in future status updates. A run named `PASS 100` is not self-explanatory; it
must say what it passed: structural certificate validation, exported proof-term
checking, or original-context theorem closure.

### Transitional Modes

Any mode controlled by an environment variable like
`MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1` should be clearly marked
as diagnostic. Its output should never be mixed into qualifying pass counts.
Ideally such modes should print a prominent warning.

### Binder Shifting Risk

The native proof-term work manipulates de-Bruijn variables and proof binders.
This is inherently error-prone. The current uncommitted Skolem CPS helper is a
good example: the distinction between proof-hypothesis shifting, term-binder
shifting, and proof-term term-variable shifting must be verified carefully.
Focused tests should include negative cases where an off-by-one shift would
produce a proposition that only checks under an accidentally extended context.

## Suggested Test Suite Shape

The project still needs a good test suite that supports rapid iteration and
honest evidence classification.

### T0: Unit Tests for Native Proof Terms

These should be tiny Megalodon-side tests that construct or parse one
certificate step and check the exact expected proposition. They should include
negative tests for:

- wrong substitution sort;
- wrong literal index;
- wrong rewrite direction;
- missing source proof;
- certificate-only symbol leakage;
- certificate-derived `Known`;
- de-Bruijn shift mistakes.

### T1: Small-Kernel Fixtures

These should cover each clausal primitive in isolation and in short
combinations. They can include synthetic examples, but each should build a
real `Syntax.pf` proof term.

### T2: Exported THF Certificate Checks

These are cached real Vampire certificates over Megalodon-exported THF
problems. They prove that the exported problem boundary is handled. They should
run in parallel from cached certificates and avoid repeated Vampire search.

### T3: Focused Original-Context Smokes

These are live Megalodon files with `vampireaby` calls at known source
locations. They should use `-vampireabytarget line char` for fast iteration.
Line 168 and line 172 of the current smoke slice are examples. The next target
set should contain about 10 nearby theorems that exercise source hypotheses,
definitions, set equalities, Skolemization, and simple clausal proof.

### T4: Broad Original-Context Benchmark

Only after T3 passes should the project run a 100-theorem broad benchmark. It
should:

- export all problems at once;
- run Vampire in parallel with 10-second timeout;
- cache the successful certificate outputs;
- replay/check certificates in parallel;
- report E1/E2/E3/E4 counts separately;
- keep artifacts under `/project/tmp`;
- identify the first failing frequent class rather than rerunning the whole
  suite during every edit.

This test staging avoids the slow iteration pattern the user objected to.

## Outlook

The project remains viable, but only if it keeps the trust reset. The work has
shown that Vampire can supply the necessary information and that Megalodon can
check nontrivial native proof terms. The failures are now better localized:
source-context composition and preprocessing transformations, especially
Skolemization, are the main blockers.

There are two plausible futures.

The good future is a small, auditable certificate checker:

- Vampire lowers macro proof steps into explicit primitive records;
- Megalodon checks a small kernel mechanically;
- preprocessing transformations are typed and proof-producing;
- original source facts resolve through a native source-context API;
- broad tests scale after focused E1 proofs exist.

The bad future is another monolithic reconstructor:

- each benchmark failure adds a new special case to `vampire_cert_v1.ml`;
- Vampire emits more ad hoc metadata without a primitive IR;
- pass counts improve but trust explanations remain difficult;
- source-context closure remains just out of reach.

The recent fail-closed commits moved away from the bad future by rejecting
misleading candidates. The next few commits will determine whether the project
continues that direction or falls back into pass-count chasing.

## Bottom Line

The project has moved from a Python skeleton generator and broad admitted
checks toward a native proof-term certificate architecture. The trust boundary
is much clearer than it was a week ago. Several serious loopholes have been
closed, especially hidden bridge assumptions and certificate-local proof
leakage.

But the project is not complete. The current implementation still lacks the
main E1 bridge from a checked exported Vampire refutation to the original
Megalodon theorem. Skolemization is the immediate blocker, and source-context
proof resolution is the broader missing API. The right next phase is not a new
round of broad heuristic replay. It is a narrow, auditable push to turn the
line-172 certificate into a real original-context proof, then factor that work
into the small-kernel and Smolka-style architecture the audits have been
recommending.
