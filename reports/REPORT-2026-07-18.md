## Executive Summary

The project began by trying to adapt Vampire's Lean proof output to
Megalodon. That was a reasonable starting point: Lean, Dedukti, and Megalodon
all have proof-term-based kernels, and Vampire already contains proof-printing
paths that expose more detail than ordinary TPTP proof text.

The first working route was a Python translator that consumed Vampire output
and generated Megalodon `claim` skeletons. It was useful for learning the
problem, recovering names, building test corpora, and identifying common
Vampire inference classes. It was not a viable final architecture. The audits
correctly identified that it was becoming a second prover outside both
Vampire and Megalodon's kernel.

The intended architecture is now Prover9/Ivy-style:

```text
Megalodon source theorem and context
  -> THF/TPTP export with source/origin metadata
  -> Vampire proof search, timeout <= 10 seconds
  -> Vampire-side expansion into primitive certificate records
  -> Megalodon native parser/checker and Syntax.pf elaboration
  -> proof of the original Megalodon theorem
```

The current implementation is partially on that path:

- Vampire emits a native S-expression certificate for Megalodon.
- Vampire's certificate metadata has been enriched repeatedly with primitive
  payloads for inference families such as URR, AVATAR, CNF, predicate
  definitions, rectification, subsumption, and SAT subsumption.
- Megalodon has a native OCaml certificate importer in
  `src/vampire_cert_v1.ml`.
- Megalodon now constructs and checks `Syntax.pf` proof terms for a growing
  native fragment rather than relying only on generated text.
- Source formulas are compared with exported THF formulas for supported
  fragments, instead of merely trusting matching labels.
- Global knowns, local hypotheses, local definitions, generated
  set-reflexivity facts, and conjecture-backed assumptions are now
  distinguished by source-context auditing.
- The hidden-trust problem found in the July 16 audit has been addressed:
  certificate-derived dynamic `Known` propositions are no longer counted as
  proof reconstruction.
- The live `vampireaby` path now requires a Vampire native certificate in
  strict mode and fails closed if the certificate cannot be composed into the
  current Megalodon goal.

The strongest current evidence is still not the original target. There is
meaningful E2/E3/E4 evidence, as defined below, but only very limited E1
evidence. The current concrete frontier is the first nontrivial live smoke
theorem after the identity case, the conjunction-left eliminator around line
172 of the current test slice. Its exported Vampire certificate refutation
checks, but composing it back into the live theorem is blocked by Skolem/choice
symbols and witness-dependent AVATAR split definitions.

Recent code has made this failure more honest and more local. Earlier versions
could build a certificate-local proof candidate and fail later at `Qed`.
Current code rejects certificate-local leakage earlier and keeps a guarded,
fail-closed Skolem CPS attempt. The latest committed Megalodon code head is:

```text
4e7ee54 Start guarded Skolem CPS discharge
```

That commit does not solve line 172. It adds a checked, fail-closed mechanism
for attempting to remove nullary Skolem symbols through continuation-passing
existential elimination. The candidate currently fails on a remaining
witness-dependent AVATAR split mismatch, and the checked exported refutation
fallback is preserved.

## Evidence Classes

Earlier reports used broad pass counts too loosely. The later audits corrected
that. This report uses four evidence classes.

E1: original-context proof reconstruction.

The system proves the original Megalodon theorem in the original local and
global context. The proof has no `admit`, no `aby`, no incomplete QED, no
bridge assumptions, no certificate-local trusted `Known` propositions, and no
private logical constants. This is the actual target.

E2: exported-certificate proof-term checking.

Megalodon checks a native `Syntax.pf` proof for the exported THF/certificate
problem. Source obligations are semantically checked, but the proof has not
yet been composed into the original theorem context.

E3: small-kernel or focused proof-term checking.

Megalodon checks a restricted kernel fragment, often on synthetic or focused
cases. This is important architectural evidence, but it does not by itself
show that real Megalodon theorem exports reconstruct end to end.

E4: structural and integration evidence.

Vampire finds proofs under timeout, emits certificates, Megalodon parses them,
metadata validates, source maps audit, generated scripts check with explicit
bridges, or structural preprocessing diagnostics pass. This is useful
engineering evidence, but it is not proof reconstruction.

The current project has useful E2, E3, and E4 evidence. It does not have the
requested 100 E1 proofs.

## Audit History and Corrections

### July 12 and July 13

The early work produced Python-generated Megalodon scripts and admitted or
claim-based skeletons. These were useful for humans to inspect, and they
confirmed that names could often be recovered from TPTP exports, but they did
not meet the goal. The audits pushed the project toward three principles:

- stop treating admitted skeletons as proof reconstruction;
- avoid reimplementing Vampire proof search heuristically in Python;
- use a Prover9/Ivy-style proof object with explicit primitive inferences.

The Prover9/Ivy analysis was especially important. Prover9 does not merely
print its high-level proof. It expands proof steps into smaller operations and
then lowers them into a small Ivy object language. The lesson for this project
is that Vampire should emit exact primitive data while it still has access to
substitutions, selected literals, rewrite positions, equality directions,
sorts, AVATAR state, and parent clauses. Megalodon should consume and check
that data, not rediscover it.

### July 14

The July 14 audit accepted that the native OCaml/S-expression direction was an
improvement but identified several severe issues:

- "strict" certificate checking still allowed bridge premises;
- bridge counts undercounted non-source assumptions;
- source linkage was label-based, not proposition-based;
- the OCaml path was still mostly a text generator;
- the implementation had grown beyond the intended MVP;
- Python reconstruction logic was not fully quarantined.

The response fixed important parts of this. Closed mode began rejecting
non-source premises. Source formulas began to be parsed and compared against
certificate inputs for supported THF fragments. The `$true` source-map loophole
was closed for those fragments.

### July 15

The July 15 audit was the first to call some results meaningful closed
reconstruction at the exported THF boundary. It confirmed:

- closed mode rejected bridge and derived premises;
- supported source formulas were checked structurally against exported THF;
- a committed closed corpus existed;
- Python was no longer on the qualifying path.

It also warned that the project was still architecturally unhealthy. The
central OCaml importer was growing into a large textual reconstruction engine,
and too much work remained on the Megalodon side instead of in Vampire's
primitive proof expansion.

### July 16

The July 16 audit found a subtler but critical trust defect. The
`preprocesspfcheck` path constructed native `Syntax.pf` terms, but many
transformation steps were justified by dynamically inserting the desired
proposition into the proof-checking environment as a `Known` theorem. That is
equivalent to a hidden bridge assumption.

This forced a trust-boundary reset. The accepted corrections are:

- old preprocessing proof-term frontier counts are reclassified as E4
  structural diagnostics;
- certificate-derived dynamic `Known` propositions are forbidden in counted
  proof-term modes;
- the genuine proof-term seed is the small core/native proof-term checker;
- future qualifying work should move toward isolated kernel modules and away
  from broad monolith growth;
- original-context reconstruction needs a concrete source-context API.

The current branch includes this reset. Later commits strengthened it further
by rejecting certificate-local intermediate proofs, distinguishing proof-source
assumptions from broader source bindings, and refusing to install candidates
that only check under the certificate-local delta.

## What Has Been Implemented

### Vampire Certificate Output

Vampire has a Megalodon proof-output path under `Shell/MegalodonChecker`.
It emits a native S-expression certificate. The exact implementation is still
too large and too entangled, but it now exports substantially richer data than
ordinary TPTP proof text.

The certificate includes or has recently gained metadata for:

- source inputs and formula-term inputs;
- source names, roles, hashes, and origin comments;
- parent proof relationships;
- step propositions;
- variable and symbol information;
- CNF and preprocessing records;
- Skolem introduced symbols and dependency information;
- AVATAR definitions, components, split dependency metadata, and refutations;
- URR primitive expansion chains;
- substitution and rectification maps;
- subsumption and SAT-subsumption primitive payloads;
- predicate definition and definition-folding payloads.

This is directionally aligned with the Prover9/Ivy model, but only partially.
The audit recommendation was not simply "emit more metadata"; it was to make
Vampire lower macro inferences into a small primitive proof object before
printing. Current Vampire work has moved toward a `MegalodonKernelSyntax`
boundary and explicit primitive-expansion metadata, but the full typed
internal primitive IR is not complete.

### Megalodon Native Certificate Importer

Megalodon's main implementation remains `src/vampire_cert_v1.ml`. It has
grown large and should not be treated as the ideal long-term module boundary.
It currently performs several jobs:

- S-expression certificate parsing;
- TPTP/THF source parsing for supported fragments;
- source-map and source-context validation;
- certificate structural checking;
- legacy textual Megalodon script emission;
- native `Syntax.tm` construction;
- native `Syntax.pf` proof construction for selected fragments;
- native proof checking through Megalodon's proof checker;
- live `vampireaby` composition attempts.

The positive side is that Megalodon is no longer merely printing `.mg` text
and hoping it checks. Several paths now construct native proof terms and call
the kernel-facing proof checker. The negative side is that this work still
lives in a large monolith. The design documents already call for extracting:

- `vampire_kernel_syntax.ml`;
- `vampire_kernel_check.ml`;
- `vampire_kernel_elab.ml`;
- `vampire_source_context.ml`.

That extraction remains a design goal, not completed implementation.

### Trust Boundary Fixes

The most important recent Megalodon changes are trust-boundary fixes:

- Closed mode rejects bridge and derived premises.
- Source formula matching rejects the `$true` label loophole for supported
  fragments.
- Certificate-derived dynamic `Known` propositions are not allowed in counted
  proof-term modes.
- Proof-source assumptions are separated from broader source bindings.
- Live strict `vampireaby` cannot silently fall back to ordinary native `aby`
  if no usable certificate proof is available.
- Final theorem candidates that depend on certificate-local proof facts are
  rejected before being installed.
- Debug output distinguishes candidate proof checks from actual certified
  proof closure.

These changes reduced misleading pass counts. They also made the current
failure smaller and more honest.

### Source Linking

Source linking is significantly better than it was at the start, but it is not
finished.

Implemented or partially implemented:

- TPTP source names can be connected to source-map records.
- Hash-backed global knowns and axioms can be checked against the loaded
  Megalodon context.
- Source formulas are parsed and compared against certificate inputs for a
  substantial supported THF fragment.
- Local hypotheses can be matched against the live proof context.
- Local definitions introduced by `set` commands are detected and reported.
- Generated `set_reflexivity` and `local_set_reflexivity` obligations can be
  discharged by native reflexivity proofs.
- Source-map presence is separated from actual dependency in the empty-clause
  proof closure.
- Conjecture-backed sources are treated specially at the final
  refutation-to-goal boundary, rather than as ordinary global assumptions.

Still incomplete:

- Full E1 composition into the original theorem context.
- General proof-producing handling of local definitions used by the refutation.
- Robust end-to-end mapping from all exported names and binders back to the
  original Megalodon declarations.
- Complete handling of generated facts that are not simple reflexive
  equalities.
- A clean `source_context -> certificate -> Syntax.tm * Syntax.pf` API.

The current source resolver is useful, but it is still partly an audit layer.
It is not yet the final original-context proof engine.

### Smolka-Style Transformations

The project now treats source-to-clause transformations as a separate layer
from clausal proof replay. This is the right conceptual separation. The
Smolka-style lesson is that transformations such as rectification,
definition expansion, FOOL processing, ENNF, CNF, and Skolemization need their
own proof-producing certificates. They should not be hidden as arbitrary
clausal kernel rules.

Current status by transformation family:

- Source input and formula input: supported structurally and formula-checked
  for a growing THF fragment.
- Definition input and generated set facts: simple equality/reflexivity cases
  are handled; general local-definition proof use remains incomplete.
- Definition folding/rewrite chains: some native replay exists, helped by
  Vampire metadata, but this still needs exact position/direction primitive
  lowering in the Prover9 demodulation style.
- Rectification: Vampire now emits variable maps; Megalodon can validate some
  structural cases, but a complete proof-producing transformation layer is not
  done.
- FOOL transformations: several representative helpers exist, but FOOL should
  remain in the preprocessing layer, not the small clausal kernel.
- ENNF and CNF: partial native support exists for common shapes; full
  source-to-clause proof production is not complete.
- Predicate definitions: metadata and some native support exist; proof
  production is still part of the broader preprocessing frontier.
- Skolemization: this is the main live blocker. There is now a guarded
  nullary-Skolem CPS discharge attempt, but dependency tracking, choice
  symbols, and AVATAR split interaction remain unsolved in the live case.
- AVATAR: metadata and some proof-term support exist, including components,
  definitions, split depth, and SAT/subsumption payloads. AVATAR is not yet
  reduced to a small auditable primitive layer, and witness-dependent split
  definitions are currently blocking live Skolem discharge.

## The Current Live Blocker in Detail

The line-172 cached certificate is useful because it is small enough to inspect
and nontrivial enough to expose the real integration problem.

Relevant facts:

- The target theorem is the conjunction-left eliminator, morally
  `A /\ B -> A`.
- Vampire proves the exported negated conjecture using Skolem/choice symbols.
- Step `u30` is a Skolem step introducing `sK0` and `sK1`.
- Step `u38` is a CNF clause from `u30`, with a step variable and a literal
  involving `sK0`.
- Step `u41` is another CNF clause from `u30`, producing a negated literal
  involving `sK0`.
- Step `u46` defines an AVATAR split atom `split_1` for a component literal
  involving `sK0`.
- Step `u47` is an AVATAR component involving `split_1`.
- Step `u50` defines another split atom `split_2` for a component involving a
  step variable.
- Step `u52` is an AVATAR split combining `u38`, `u50`, and `u46`.
- Step `u58` derives `not split_1`.
- Later steps combine split clauses and end in an AVATAR refutation.

The guarded Skolem CPS attempt tries to prove the live theorem by abstracting
over the existential witness instead of leaving `sK0` in the proof. This is the
right broad shape:

```text
source existential
  -> eliminate existential with a fresh witness variable
  -> replay the refutation under that witness variable
  -> derive False
  -> close the original implication
```

The failure is not a generic type error anymore. The parent-step forall
opening was fixed, the source existential binder count is tracked, and several
result subproof occurrences are abstracted. The remaining problem is that
AVATAR split atoms are not ordinary transparent formulas. They are new
propositional atoms whose certificate definitions are tied to component
literals. If a split definition was introduced for `sK0`, replacing `sK0` by a
bound existential variable in one part of the proof must also transport the
split definition and every downstream split proof. Otherwise the checker sees
one branch proving a proposition about the bound witness and another branch
still proving a proposition about `#sK0`.

This is the immediate technical focus. It should be solved generally, not by
hardwiring `split_1`, `sK0`, or the conjunction theorem.

## Skolemization Status

Skolemization remains the highest-risk transformation. The project now has
better metadata and better local proof attempts than it did earlier, but not a
complete solution.

What is working:

- Vampire exports introduced symbols and some dependency information.
- Megalodon can normalize and inspect Skolem definitions in several contexts.
- Some focused Skolem preprocessing cases check at the exported-certificate
  boundary.
- The latest guarded CPS helper supports nullary introduced witnesses and is
  fail-closed.
- The helper counts source existential binders against substitution length.
- It opens Skolem parent step-variable foralls before Church-existential
  elimination.
- It replaces witness symbols with de Bruijn variables in candidate proof
  terms.
- It abstracts occurrences of checked Skolem result subproofs from the final
  refutation.
- It only installs a candidate if `final_refutation_proof_checks` confirms
  that it proves `False`.

What is not working:

- The live line-172 theorem still does not close.
- Skolem witnesses can appear inside AVATAR split definitions and downstream
  split proofs.
- Non-nullary or dependency-bearing Skolem functions are not solved by the
  current nullary helper.
- Choice/epsilon symbols need a principled relation to Megalodon's classical
  basis.
- The transformation still lives inside the large importer rather than a
  clean source/preprocessing proof layer.

The recommended direction is to keep the fail-closed CPS logic only as a
scaffold and implement a real Skolem transformation certificate:

- identify the exact source formula;
- identify the quantified subformula;
- record introduced Skolem symbols and dependency variables;
- record the proof direction needed for refutation;
- prove the transformation using Megalodon's classical principles, including
  excluded middle and choice/existence principles already available from the
  library;
- scope introduced symbols so they cannot escape into the final original
  theorem.

## Equality and Logical Constants

The final reconstruction should use Megalodon's equality and logical constants.
Earlier standalone certificate harnesses introduced private encodings such as
`vampire_eq_prop`, `vampire_or`, `vampire_false`, and related helpers. Those
were practical for a self-contained exported-certificate harness, but they are
not the final original-context target.

The correct end state is:

- source-linked theorem reconstruction uses Megalodon's real equality;
- `False`, disjunction, implication, quantifiers, and excluded middle come
  from the Megalodon library/context;
- any Vampire-side normalized logical encoding is proved equivalent to the
  original Megalodon proposition by a checked transformation proof;
- no private equality can become part of the final statement.

The existing private-style names are best understood as transitional
certificate syntax, not as the final proof language.

## Prover9/Ivy Path Status

The project has absorbed the main Prover9/Ivy lesson but has not fully
implemented it.

Completed or partially completed:

- Prover9/LADR was inspected and analyzed.
- The analysis identified the two-stage pattern: expand prover proof steps,
  then lower to an Ivy kernel.
- A Megalodon kernel IR plan was written.
- Vampire now emits explicit primitive-expansion metadata for several macros.
- URR has the clearest migration path: lower unit-resulting resolution to a
  chain of binary `resolve` steps and record that chain explicitly.
- Vampire now rejects or reports unsupported kernel rule names more explicitly
  than before.

Not completed:

- There is not yet a fully isolated Vampire internal primitive IR that all
  macro inference handlers lower into before printing.
- There is not yet a small standalone Megalodon kernel elaborator module that
  consumes only this IR.
- AVATAR has not been lowered to a compact SAT/RUP-style certificate or a
  similarly small checked layer.
- Preprocessing transformations are still partly replayed in the broad
  importer.
- The existing large C++ and OCaml files are still growing, even though the
  design calls for freezing broad replay growth.

The recommended expert position should be: the project is directionally on the
Prover9/Ivy path in its design and some recent metadata work, but not yet in
its module boundaries or implementation discipline.

## Python Status

Python is not a qualifying proof reconstruction path. It remains useful for:

- corpus generation;
- certificate inspection;
- statistics;
- old-output comparison;
- human-readable skeleton diagnostics.

It should not receive new proof-producing logic. A Python-generated proof term
or script should not count toward E1 or E2 results. This is now explicit in
the design and should remain enforced.

## Test Strategy

The user correctly pushed against slow sequential testing. The intended test
strategy is:

1. Export many problems once.
2. Run Vampire on them in parallel, using 10 to 20 jobs and a per-problem
   timeout not exceeding 10 seconds.
3. Cache the native certificates under `/project/tmp`.
4. Iterate quickly on the Megalodon checker against cached certificates.
5. Run broad live Vampire regeneration only at milestone boundaries.
6. Use focused failing certificates for daily implementation loops.

The current active loop follows this in spirit. The line-172 certificate is
cached and reused; Vampire is not rerun repeatedly for the same failure.

A good future test suite should have separate gates:

- T0: parser and negative trust-boundary fixtures;
- T1: synthetic small-kernel fixtures;
- T2: real live exported certificates restricted to the small kernel;
- T3: exported-certificate source/preprocessing transformations;
- T4: original-context theorem reconstruction.

The scoreboard should report evidence classes E1-E4 separately. A single
"PASS 100" label without class is too easy to misread.

## Main Problems

### 1. The 100-Theorem Goal Is Not Met

The project does not yet reconstruct 100 original Megalodon theorems in their
source context. Any report or summary should state this plainly.

### 2. Original-Context Composition Is Still the Central Gap

Exported-certificate checking can prove that a THF/certificate problem is
refutable. The final target is stronger: it must turn that refutation into a
proof of the live Megalodon theorem using the original context.

The source-context resolver is a real step, but the final composition layer is
not complete.

### 3. Skolemization and AVATAR Interact Badly

Skolemization alone can be understood through classical existential
elimination or choice. AVATAR alone can be checked through split definitions
and SAT/refutation reasoning. Together, they create witness-dependent split
atoms. The current line-172 failure is exactly this interaction.

### 4. The Implementation Is Still Too Monolithic

The Megalodon importer and Vampire exporter are both large. The audits were
right that "move code to OCaml" is not enough. The qualifying path should be
small, typed, and auditable, with legacy textual replay kept as an oracle.

### 5. The Vampire Primitive IR Is Not Fully Real Yet

The C++ side now emits richer metadata and some primitive expansion summaries,
but many inference handlers still effectively print macro-specific payloads.
The goal is an internal primitive list and one canonical printer.

### 6. Broad Pass Counts Can Be Misleading

Past pass counts mixed structural validation, bridge-based generated scripts,
native proof terms with hidden `Known` injection, and real closed checks. The
current evidence classes are meant to prevent this from recurring.

## Chronological Work Log

This section summarizes the project arc in practical terms. It is not a full
commit-by-commit changelog, but it records the major technical changes and why
they were made.

### Phase 1: Skeleton Generation and Name Recovery

The earliest implementation tried to make progress quickly by translating
Vampire's proof output into Megalodon scripts with `claim` steps. The goal was
not initially to produce perfect proofs. The goal was to give a human a
readable skeleton that connected the original theorem, the exported TPTP
problem, and the Vampire proof graph.

This phase established several useful facts:

- Megalodon can export enough THF/TPTP structure for Vampire to solve many
  small library obligations.
- The mangled TPTP names often retain enough information to recover original
  Megalodon source names.
- `claim`-style declarative Megalodon proof scripts are a plausible human
  interface for inspecting reconstruction.
- Generated set-command facts appear in the exported problem and need special
  treatment because they are often not original named claims.
- Vampire's ordinary TPTP proof text is not detailed enough for robust replay
  of nontrivial inferences.

This phase also showed the main failure mode of a script-skeleton approach.
It is easy to generate a readable sequence of statements with holes. It is much
harder to eliminate those holes generally. Without richer Vampire-side proof
data, the translator starts guessing selected literals, substitutions,
orientations, positions, and missing transformation proofs. That is exactly
what the user warned against and what the audits later rejected.

### Phase 2: Batch Testing and Solvable Problem Selection

The next step was to build a faster testing loop. The user pointed out that
rerunning Vampire sequentially was wasting time. The intended workflow became:

```text
export all problems once
run Vampire in parallel with 10-second timeout
cache successful certificates
iterate on cached proof reconstruction
rerun broad Vampire only at milestone boundaries
```

This was an important operational correction. It separated three questions:

- Can Megalodon export problems that Vampire can solve?
- Can Vampire emit useful proof/certificate data for those solved problems?
- Can Megalodon reconstruct the proof from the cached certificate?

The user also requested focusing on the problems known to be solvable by
Vampire under the agreed timeout. That remains the correct approach. Failing
portfolio searches should not be part of the fast reconstruction loop.

The generated `hammer/` and `out1/` corpora from commands such as:

```text
megalodon -allowincompleteqed -createabyprobs hammer hammer/100thms_12_h.mg
vampire --input_syntax tptp --mode casc -t 10 --proof tptp --output_axiom_names on ...
```

provided more serious examples than the earliest toy cases. They also exposed
that real proofs quickly involve preprocessing, Skolemization, AVATAR, equality
rewrites, and higher-order/lambda artifacts. This made the "small first-order
only" path harder to reach from the available corpus, but it did not invalidate
the small-kernel design. It means Vampire-side lowering and source/preprocess
certificates are necessary.

### Phase 3: Native S-Expression Certificates

The project then moved toward native Vampire certificates. The motivation was
to avoid reconstructing proof information from lossy proof text. Vampire knows
the exact inference, parents, selected literals, substitutions, sorts, and
generated symbols. The certificate should expose that data directly.

This produced the first significant architecture pivot:

- Vampire began emitting a Megalodon-specific native S-expression certificate.
- Megalodon parsed that certificate in OCaml.
- Source names, roles, origin comments, and hashes were recorded.
- Derived clauses were no longer silently presented as ordinary source inputs.
- Negative fixtures were added for malformed or mismatched certificates.

This direction matched the audit recommendation in broad form. However, the
first native importer still generated textual Megalodon scripts and inserted
bridge assumptions when it could not reconstruct an inference. That meant
"strict" still mostly meant "certificate structure is valid," not "the proof
has been reconstructed."

### Phase 4: Closed Mode and Source Formula Checking

The July 14 audit forced a clarification of trust. A certificate whose proof
script contains bridge assumptions is not reconstructed. A source name match is
also not enough if the certificate can attach an arbitrary proposition to that
name.

The following fixes were made in response:

- Closed mode rejects bridge and derived assumptions.
- Source formulas are parsed from THF/TPTP for supported fragments.
- Certificate source inputs are compared with the exported source formulas.
- Hash-backed `$true` loopholes are rejected.
- Unsupported source syntax fails closed when formula checking is required.
- The test harness rejects `admit`, `aby`, incomplete QED, bridges, derived
  assumptions, and unindexed axioms for closed-corpus checks.

This was real progress. It produced meaningful exported-THF-bound evidence,
but it still did not solve original-context theorem reconstruction. The
generated proof was still a separate exported certificate proof, not yet a
proof term inhabiting the user's current Megalodon theorem.

### Phase 5: Native Proof Terms

The next improvement was to construct actual `Syntax.pf` values. This is the
right target because Megalodon's kernel checks proof terms. A proof term can
also be audited more directly than a generated text script with a large helper
prelude.

The genuine seed was the core proof-term checker, which supports a restricted
clausal fragment. It checks each proof step and then checks a final proof of
`False` from the source assumptions. This is materially different from the old
textual emitter.

The limitation is coverage. Many real Vampire proofs are not in the tiny core
fragment. They contain preprocessing, Skolemization, AVATAR, and macro
inferences. The project then tried a broader native preprocessing proof-term
frontier. That exposed the July 16 hidden-`Known` issue: many transformations
were "proved" by installing the desired proposition as known.

The current branch rejects that pattern in counted modes. This reset made pass
counts worse but made the trust story much better.

### Phase 6: Source Context and Live `aby`

The user repeatedly emphasized that the reconstructed proof must connect to
the original theorem, lemmas, definitions, and generated set facts. The
implementation began adding source-context resolution:

- `-vampirecertv1sourcecontext` loads the `.mg` file and audits source
  bindings against the live context.
- Hash-backed global knowns are checked against the Megalodon environment.
- Local hypotheses are matched against proof context entries.
- Proof-local `set` definitions are accounted for when projecting indices.
- Generated set-reflexivity facts can be proved by reflexivity.
- The final refutation-to-goal boundary treats the negated conjecture
  specially.

This is the beginning of E1 support. It is not complete. The current line-172
failure shows exactly where more source/preprocessing proof is needed: the
exported refutation contains local Skolem and split artifacts that must be
removed before the proof can inhabit the original theorem.

### Phase 7: Trust Reset and Guarded Skolem CPS

After the July 16 audit, the project stopped counting broad preprocessing
passes that relied on dynamic `Known` insertion. Recent commits tightened the
boundary further:

- `0ed0d38 Fail closed on Vampire local proof leakage`
- `907da98 Separate proof source assumptions from source bindings`
- `59d46ca Distinguish native aby candidates from certified proofs`
- `878515d Reject certificate-local intermediate proofs`
- `4e7ee54 Start guarded Skolem CPS discharge`

The current Skolem CPS work is deliberately guarded. It tries to transform a
certificate-bound refutation that mentions nullary Skolem witnesses into a
proof that eliminates the corresponding source existential. It checks the
candidate before accepting it. If the candidate does not prove `False`, the
old exported-certificate proof is retained and the live theorem is not falsely
claimed.

That is the right failure behavior. The next work is to fix the remaining
AVATAR split transport issue in the candidate proof.

## Implementation Inventory

### Megalodon-Side Components

The main file is still `src/vampire_cert_v1.ml`. Important functional areas
inside it include:

- certificate S-expression parser;
- rule and metadata datatype definitions;
- THF/TPTP source parser for supported syntax;
- source map validation;
- source-context audit;
- native term construction;
- native proof construction;
- closed/core/preprocess proof-checking modes;
- legacy text emission;
- live `vampireaby` integration.

Key behaviors implemented or tightened:

- `-vampirecertv1strict` validates certificate structure and source metadata.
- `-vampirecertv1closed` rejects non-source premises in generated-script mode.
- `-vampirecertv1corepfcheck` checks a restricted native proof-term core.
- `-vampirecertv1preprocesspfcheck` now has a fail-closed trust boundary for
  certificate-derived knowns.
- `-vampirecertv1sourceaudit` reports source-obligation counts.
- `-vampirecertv1sourcecontext` and `-vampirecertv1sourcecontextstrict` audit
  certificate sources against a loaded Megalodon context.
- Live strict `vampireaby` no longer treats "Vampire ran" as enough; it must
  obtain a native certificate and a usable proof candidate.

The most important checker-side invariant is:

```text
An accepted proof candidate must check as a proof of the required proposition
without relying on certificate-local derived facts as trusted Known theorems.
```

The current code enforces this much better than earlier versions, but a full
module separation is still needed so the invariant can be audited locally.

### Vampire-Side Components

The Vampire branch contains the Megalodon proof-output implementation under
`Shell/MegalodonChecker`. The latest commits show a clear shift toward richer
primitive metadata:

- explicit URR expansion chain metadata;
- URR parent and rule payload metadata;
- AVATAR definition/component/split/refutation metadata;
- primitive parent substitutions;
- rewrite metadata;
- predicate definition metadata;
- rectification variable maps;
- subsumption and SAT-subsumption payloads.

The current issue is not that Vampire lacks all information. The issue is that
the information is still exposed partly as macro metadata and partly as
primitive-like records. The project needs a stricter internal boundary:

```text
Vampire inference object
  -> macro expansion/lowering
  -> list of primitive Megalodon certificate steps
  -> canonical S-expression printer
```

As long as individual inference handlers directly assemble certificate text or
ad hoc metadata, Megalodon will continue receiving semi-expanded proof data
and will be tempted to reconstruct missing details.

### Test Harnesses and Corpora

Several harnesses exist, with different evidence meaning:

- native smoke tests: good for parser/checker regressions;
- closed corpus tests: useful for exported-THF-bound checks;
- live parallel tests: useful for Vampire regeneration and integration;
- source audit tests: useful for source-map/source-context invariants;
- preprocess frontier tests: useful diagnostics, but only counted when free of
  certificate-derived knowns;
- cached focused line-172 tests: current daily development target.

The important operational rule is to keep broad live tests rare. Cached
certificates should drive most iterations. This has been followed more closely
in recent work than in the early phase.

## Detailed Source-Linking Status

The source-linking problem has several distinct classes. Conflating them was
one reason earlier reports overcounted progress.

### Global Lemmas and Axioms

For hash-backed global entries, the current resolver can check that the
declared known theorem exists in the loaded Megalodon environment and has the
expected proposition. This is a meaningful improvement over label matching.

Open issues:

- unsupported formula shapes still need either parser support or direct
  original-`Syntax.tm` access;
- the final proof term must use these known proofs directly, not reintroduce
  them as source assumptions;
- hashes and source-map records need a stable contract across export/import.

### Local Hypotheses

Local hypotheses are harder because they live in a binder/proof context, not
as global theorem names. The current implementation can match them in several
cases and can project indices through local definitions introduced by `set`.

Open issues:

- binder shifts need more stress testing;
- higher-order local hypotheses may still expose unsupported THF syntax;
- the source-context API should represent local hypotheses explicitly rather
  than through ad hoc tables.

### Local Definitions and `set` Commands

The user pointed out that TPTP axioms can come from Megalodon `set` commands
and may not correspond to original claims. The current implementation now
distinguishes some of these facts.

Working cases:

- `set_reflexivity` and `local_set_reflexivity` equalities can produce native
  reflexivity proofs.
- Matched local definitions are counted separately from ordinary source
  assumptions.
- Unused local definitions do not block a refutation simply because they are
  present in the exported problem.

Open cases:

- if a local definition is actually used in the proof dependency closure, it
  must be discharged by conversion, unfolding, or a generated proof term;
- source-map matching alone is not enough;
- definitional equality should eventually use Megalodon's existing conversion
  machinery rather than a certificate-local theorem.

### Conjecture and Negated Goal

The conjecture is not a source lemma. It is the negation of the goal used for
refutation. The final step must convert:

```text
source assumptions + not goal -> False
```

into a proof of:

```text
goal
```

in the live context, using classical reasoning where needed. The current live
composition code handles this boundary in simple cases, but line 172 shows
that certificate-local witnesses and split atoms can still prevent closure.

## Detailed Smolka-Transformation Status

The Smolka-style transformation layer should be viewed as a proof-producing
compiler from source formulas to clausal inputs. It is not the same as the
small clausal kernel.

### Rectification

Rectification changes bound variable names and scopes. Vampire now emits
variable maps. Megalodon can inspect these maps, but the final form should be
alpha-conversion checking over native syntax. The checker should not search
for a matching renaming. Vampire should state the renaming, and Megalodon
should verify it.

### FOOL and Boolean Processing

FOOL transformations introduce Boolean/proposition reasoning such as
exhaustiveness and truth-value distinctions. Some helper proofs exist, and
classical logic is assumed available. However, these transformations should
remain outside the clausal kernel. The small kernel should not grow a large
collection of FOOL-specific rules.

### ENNF and CNF

ENNF and CNF are common in exported Vampire proofs. Partial support exists for
standard shapes, but a complete proof-producing chain needs explicit records:

- original formula;
- normalized formula;
- clause projection;
- polarity and quantifier movement information;
- proof direction used by the refutation.

The current implementation can handle some common cases, but it is not yet a
principled Smolka transformation checker.

### Definition Introduction and Folding

Definition folding was one of the places where the Prover9 demodulation model
was most useful. Prover9 records enough information to replay a particular
rewrite at a particular occurrence. Vampire should do the same:

- definition parent;
- exact occurrence position;
- direction;
- instantiated terms;
- result after the rewrite.

Megalodon should then check one local rewrite step, not search across a large
term for a plausible fold.

### Skolemization

Skolemization is currently the hardest transformation. The proof-theoretic
shape depends on the direction in which the transformation is used. For
refutation, it is often enough to show that the Skolemized problem is
equisatisfiable with the source problem under classical reasoning, but
Megalodon needs an actual proof term connecting the refutation back to the
source theorem.

The current nullary CPS helper is a step toward this, but not a complete
Skolem certificate. A complete design should handle:

- nullary Skolem constants;
- dependency-bearing Skolem functions;
- proposition-valued witnesses;
- choice/epsilon terms;
- nested existentials;
- interaction with CNF projections;
- interaction with AVATAR split atoms.

### AVATAR

AVATAR introduces split atoms and uses SAT-style reasoning over them. It is a
major source of non-local proof structure. The current metadata support is
much better than before, but AVATAR should not be hidden inside broad
Megalodon-side replay.

There are two plausible long-term approaches:

- Ask Vampire to avoid AVATAR for the first E1 milestone, then add AVATAR
  later.
- Give AVATAR its own small certificate layer, likely SAT/RUP-like for the
  propositional part plus checked definitions for each split atom.

The current line-172 proof uses AVATAR, so avoiding AVATAR entirely may not be
practical for the existing smoke path. That makes witness-dependent split
transport the immediate technical problem.

## Risk Register

### Risk: The Project Becomes Another Prover

If Megalodon keeps gaining inference-specific replay functions that infer
missing Vampire details, the implementation will become a large unsoundness
risk and will be hard to audit. Mitigation: make Vampire emit exact primitive
records and make Megalodon check them mechanically.

### Risk: Trust Boundary Regressions

The hidden dynamic-`Known` issue shows how easy it is to accidentally convert
"we checked a proof term" into "we checked a proof term under an environment
that already contains the desired theorem." Mitigation: audit every `Known`
in final proof terms and reject names sourced from certificate step IDs.

### Risk: Source Linkage Remains Export-Bound

An exported THF proof can be correct without proving the original theorem if
the export/import mapping is incomplete. Mitigation: implement a concrete
source-context API and make E1 tests run inside or against the loaded original
Megalodon context.

### Risk: Skolemization Is Treated Too Locally

Replacing `sK0` in a final proof term is insufficient if downstream AVATAR,
CNF, or definition steps encode propositions involving `sK0`. Mitigation:
prove a transformation over the whole dependency subgraph, not only over the
final refutation term.

### Risk: Broad Testing Slows Iteration

Running Vampire repeatedly over unsolved or irrelevant problems wastes time.
Mitigation: cache certificates, classify solvable THF problems once, and run
focused checks during implementation.

### Risk: Metrics Drift Again

Different harnesses report `PASS` for different things. Mitigation: every
reported number must state E1/E2/E3/E4 and the exact command/harness.

## What an Expert Should Not Infer

The following conclusions would be too strong:

- "The project has 100 reconstructed proofs." It does not.
- "The line-172 theorem is solved." It is not.
- "The preprocessing proof-term frontier is fully trustworthy." Only if it is
  free of certificate-derived `Known`; older frontier results were not.
- "Python is part of the final checker." It is not.
- "The private Vampire logical encoding is the final Megalodon proof
  language." It is transitional.
- "Vampire-side primitive IR is complete." It is only partially present.

The following conclusions are justified:

- The trust boundary is much clearer than it was.
- The current implementation can parse and validate rich native Vampire
  certificates.
- Source formula checking and source-context auditing are real improvements.
- Native `Syntax.pf` checking is implemented for meaningful fragments.
- The current failure is concrete, reproducible, and technically informative.
- The best next work is narrow and proof-theoretic, not broad pass-count
  chasing.

## Recommended Next Work

The next iteration should be narrower than earlier iterations.

1. Keep counted modes fail-closed.

Do not reintroduce certificate-derived `Known` propositions, hidden bridges,
`aby`, `admit`, or incomplete QED in any counted path.

2. Finish line-172 original-context closure.

Use the cached certificate. Do not rerun Vampire repeatedly. The next technical
target is witness-dependent AVATAR split transport under the Skolem CPS
abstraction. The implementation must be general over introduced witness
symbols and split definitions.

3. Define the source-context API concretely in code.

The design already suggests:

```ocaml
type source_proof =
  | GlobalKnown of string * Syntax.tm
  | LocalHyp of int * Syntax.tm
  | Definitional of Syntax.tm * Syntax.pf
  | Generated of Syntax.tm * Syntax.pf
  | Unresolved of string * Syntax.tm
```

This should become an actual module boundary rather than logic embedded in the
large importer.

4. Move one inference family fully to Prover9/Ivy style.

URR is the best first candidate. Vampire should lower it to explicit binary
resolution primitive steps. Megalodon should consume that primitive chain
without a broad URR replay rule.

5. Extract the small kernel modules.

Start with module extraction that adds no new reconstruction power. The goal
is to make trust boundaries auditable:

- syntax and rule names;
- structural checker;
- proof-term elaborator;
- source-context resolver.

6. Treat Smolka-style transformations as their own certificates.

Do not push rectification, FOOL, ENNF, CNF, and Skolemization into the clausal
kernel. Each needs a proof-producing transformation record or must fail in
counted mode.

7. Build a ten-proof E1 gate before chasing 100.

The next milestone should be ten real source-linked original-context proofs.
Only after that should the project run a fresh 100-theorem held-out gate.

## Bottom Line

The project has made real progress, but the correct assessment is not "nearly
done." It is now at a more honest and technically useful frontier.

The main achievements are:

- native Vampire certificates exist;
- source formulas and origin metadata are checked much more seriously;
- hidden bridge assumptions have been identified and excluded from counted
  modes;
- native `Syntax.pf` checking is in place for important fragments;
- Vampire emits richer primitive metadata;
- source-context resolution has begun;
- set-reflexivity-style generated facts can be discharged by reflexivity;
- the current live blocker is concrete and reproducible.

The main missing pieces are:

- 100 original-context reconstructed proofs;
- a completed source-context composition layer;
- complete Skolemization;
- witness-dependent AVATAR split transport;
- a fully implemented Vampire primitive IR;
- extracted Megalodon small-kernel modules;
- a clean proof-producing Smolka-style transformation layer.

The recommended path is to stop broad pass-count chasing, finish the small
line-172 E1 case honestly, extract the kernel/source modules, lower one Vampire
macro family fully into primitive records, and then build a ten-proof E1 gate
before returning to the 100-theorem objective.
