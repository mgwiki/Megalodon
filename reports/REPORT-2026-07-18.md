## Evidence Labels

The reports and audits converged on the following evidence classes. I use them
throughout this report because earlier reports sometimes overclassified
structural certificate validation as proof reconstruction.

```text
E1  Original-context proof reconstruction.
    The proof is checked inside the original Megalodon development context and
    proves the original current goal.

E2  Exported-THF-bound closed proof reconstruction.
    A Vampire certificate for an exported THF problem is checked as a closed
    native Megalodon proof term, but not yet composed with the original source
    theorem position.

E3  Primitive-kernel proof-term checking.
    Synthetic or focused real certificates exercise native proof-term
    elaboration for the small clausal/preprocessing kernel.

E4  Structural certificate validation and diagnostic integration.
    Vampire emits certificates; Megalodon parses them, checks source metadata,
    audits primitive tags, and rejects malformed certificates, but does not yet
    prove every inference as a Megalodon proof term.
```

The qualifying result is E1 only. E2 and E3 are useful engineering milestones.
E4 is important integration evidence but is not proof reconstruction.

## What Has Been Built

The project started with an old path that parsed Vampire TPTP proof output and
used Python to generate Megalodon proof skeletons. That was useful for
exploration, but the user and audits repeatedly pointed out that it was not a
credible final route: Python was inferring too much, guessing too much, and
could become a second prover outside Megalodon's kernel.

The current path is different.

Vampire now emits a Megalodon-oriented native certificate. The main form is an
S-expression proof object embedded in the Vampire output. The certificate
contains:

- source entries and source-origin metadata;
- formulas and clauses in a Megalodon-oriented term representation;
- step IDs and parent IDs;
- kernel rule tags such as resolution, factoring, equality resolution,
  equality factoring, paramodulation, substitution, superposition-related
  records, URR-related records, AVATAR records, Skolem records, predicate
  definitions, FOOL/boolean normalization, and subsumption metadata;
- primitive expansion metadata under the `kernel_v1` schema;
- selected literals, rewrite positions, substitutions, rectification maps,
  split dependencies, AVATAR components/refutations, and Skolem introductions.

On the Megalodon side, `src/vampire_cert_v1.ml` parses and validates this
certificate format. It can run several layers of checks:

- structural certificate validation;
- source-map validation;
- primitive metadata audit;
- native core proof-term checking for a restricted kernel fragment;
- native preprocessing proof-term checking for selected transformation
  fragments;
- source-context reconstruction attempts for live `vampireaby` calls.

The important architectural improvement is that the counted native path now
constructs Megalodon proof terms (`Syntax.pf`) and checks them using the
Megalodon checker, rather than relying on generated scripts with bridge
assumptions.

There is also a live path integrated with `aby`: Megalodon can export the
current goal to THF, run Vampire with the Megalodon proof mode, parse the
certificate, check it, and try to reconstruct the current goal proof. This is
the path that matters for E1.

## Response to the Audits

The audits made several hard criticisms. They were broadly correct.

The July 12 audit argued that the earlier broad successes did not prove the
original theorems because they contained many bridge assumptions and depended
on heuristic reconstruction. The response was to pivot toward a small
certificate calculus and to treat Python as diagnostic only.

The July 13 and July 14 discussions reinforced the Prover9/Ivy lesson:
complex prover inferences should be elaborated by the prover into a simple
certificate language. The importer should not rediscover pivots, substitutions,
or rewrite positions by search.

The Prover9 analysis under `/project/prover9-ladr` showed a concrete pattern:
Prover9 first expands compact proof justifications using its own clause
machinery, then lowers the expanded proof to a small Ivy vocabulary. The key
lesson is not that Vampire should literally use Ivy syntax. The key lesson is
that proof-detail expansion belongs on the prover side, close to the data
structures that already know the selected literals, unifiers, substitutions,
and rewrite positions.

The July 16 audit found a trust-boundary problem in the native preprocessing
path: some proof-term checks succeeded because the checker dynamically
installed certificate-derived propositions as `Known` theorems. That is just a
bridge assumption under another name. The response on branch
`vampire/megalodon5` was to:

- fail closed by default when counted native modes would require
  certificate-derived `Known` insertion;
- leave transitional behavior available only behind an explicit environment
  variable for structural diagnostics;
- classify those runs as E4, not proof reconstruction;
- add proof-term traversal checks that reject generated certificate-derived
  `Known "vampire_*"` constants except for the explicitly reviewed fixed
  logical basis;
- introduce small extracted kernel vocabulary modules on the Megalodon and
  Vampire sides.

This is the right correction, but it is not complete. The implementation still
contains too much logic in the large OCaml and C++ monoliths. The next work
should continue the extraction, not add another broad layer of reconstruction
inside `vampire_cert_v1.ml`.

## Current Architecture

The intended architecture is:

```text
Original Megalodon theorem/context
  -> Megalodon THF export
  -> Vampire proof search
  -> Vampire-side primitive proof expansion
  -> S-expression certificate
  -> Megalodon certificate parser
  -> native kernel/preprocessing proof elaborator
  -> checked Syntax.pf proof of refutation
  -> source-context composition
  -> checked proof of the original Megalodon goal
```

The pieces that exist today:

- THF export exists and has been used for the live hammer examples.
- Vampire can emit S-expression certificates with substantial metadata.
- Megalodon can parse the S-expression format.
- Megalodon can structurally validate many real certificates.
- A native `Syntax.pf` kernel seed exists for core clausal proof steps.
- Selected preprocessing transformations now have native proof-term support.
- Live `vampireaby` can call Vampire and attempt strict native reconstruction.
- Some original live goals now pass.

The pieces that remain incomplete:

- The Vampire-side primitive IR is not yet a clean typed proof-object layer.
- The Megalodon-side kernel is not yet cleanly extracted into small modules.
- Source-context composition is still underdeveloped for local section
  variables, local hypotheses, local definitions, set-command facts, and
  conjecture negation.
- Smolka-style preprocessing is not yet fully certified.
- Skolemization is only partially handled.
- The final 100-theorem E1 gate is not passing.

## Vampire-Side Work

The Vampire fork has moved from "print enough text for a Python translator" to
"emit native certificate records with explicit metadata." That is meaningful.

Recent Vampire-side commits on `vampire/megalodon5` include work to emit:

- URR primitive expansion chain metadata;
- AVATAR component, definition, split dependency, split, and refutation
  metadata;
- unsupported-kernel-rule rejection metadata;
- predicate definition primitive metadata;
- subsumption primitive step and fast-path metadata;
- rectification variable maps;
- SAT subsumption primitive metadata.

The C++ side now has a separate
`Shell/MegalodonChecker/MegalodonKernelSyntax.{hpp,cpp}` component. It is not
yet the full primitive builder requested by the audit, but it is a concrete
place where the certificate contract is being pulled out of
`MegalodonChecker.cpp`.

This matters because every inference detail that Vampire already knows should
be emitted by Vampire. The Megalodon side should check, not guess. Examples:

- For resolution, Vampire should print the selected pivot literals and the
  substitution.
- For paramodulation and superposition, Vampire should print the equality
  parent, side, rewrite position, orientation, unifier, and resulting clause.
- For demodulation, Vampire should lower the rewrite chain into primitive
  equality/paramodulation-style steps.
- For AVATAR, Vampire should print a small propositional proof of the split
  contradiction, or lower the explanation into a simple SAT-resolution/RUP-like
  sequence.
- For Skolemization, Vampire should print the source existential, dependency
  variables, introduced symbols, witness terms, substitution, and a proof
  macro with enough structure for Megalodon to build the choice/CPS proof.

The exporter is still too large. It is acceptable that Vampire-side code grows
while the proof detail is being moved out of Megalodon-side guessing, but the
growth should be organized around a typed primitive certificate IR. Otherwise
the project simply moves a monolith from Python to C++/OCaml.

## Megalodon-Side Work

The Megalodon side now has several important components.

`src/vampire_cert_v1.ml` is the large parser/checker/elaborator. It parses the
native S-expression format, performs structural checks, validates metadata,
constructs native proof terms for supported fragments, and generates diagnostic
output.

`src/vampire_kernel_syntax.ml` and `.mli` are the beginning of the extracted
kernel vocabulary. They are still tiny. The audit's requested endpoint would
have more modules, for example:

```text
vampire_kernel_syntax.ml
vampire_kernel_check.ml
vampire_kernel_elab.ml
vampire_source_context.ml
vampire_preprocess_elab.ml
```

That extraction has not happened yet.

`src/megalodon.ml` contains the live `vampireaby` integration and source-goal
composition logic. This is where the most recent E1 work happened.

The latest committed source-level Megalodon change relevant to E1 reconstruction
is:

```text
17e9e05 Transport native basis in live Vampire proofs
```

That commit addressed a real live-basis problem. The native certificate core
has its own internal basis for principles such as double-negation elimination,
not-forall/existence, `False` elimination, and proposition extensionality. In
the live Megalodon file, those concepts exist through the library definitions
and the facts loaded so far. The final proof cannot simply refer to
certificate-private theorem names. It must be transported into the live
context.

The commit added live-basis expansion and changed final live rechecking to use
the live delta and symbol table. In concrete terms:

- native double-negation elimination is expanded through the loaded `xm`;
- `not` is transported through the loaded library `not` head;
- `False` elimination is built using the loaded false eliminator;
- not-forall/existence principles are expanded rather than trusted as private
  certificate constants;
- `prop_ext` variants are chosen based on the currently available live delta.

This is not just a fix for one theorem. It is the correct general direction:
the certificate may have a normalized internal logical basis, but final E1
composition must produce proof terms in the actual Megalodon context.

After that commit, the branch received report commits and one uncommitted
source-context experiment. The experiment is worth describing because it is the
current active frontier for line 183.

The line-183 proof certificate gives Megalodon a checked proposition whose
essential shape is a closed, universally quantified, double-negated
conjecture:

```text
forall P1 P2 P3. ((target(P1,P2,P3) -> False) -> False)
```

Under the live section context for `and3I`, `target(P1,P2,P3)` should
instantiate to:

```text
P1 -> P2 -> P3 -> P1 /\ P2 /\ P3
```

The debug output shows that a convertible target exists after instantiating
the exported proposition variables with the live local variables. In the
internal de Bruijn display, the successful target candidate used the live
variables in the order `_2`, `_1`, `_0` and was definitionally convertible to
the current goal. This is strong evidence that the missing piece is not a
logical axiom and not theorem-name hardwiring. It is a source-context
instantiation algorithm.

The uncommitted helper currently tries two useful eliminations:

```text
native refutation:  ((target -> False) -> False) -> target
CPS proposition:    forall r. ((target -> r) -> r) -> target
```

Both are reasonable in the classical live context, because `xm` is assumed
available and is already the intended route for double-negation elimination.
However, the helper still enumerates candidate proposition terms in a broad
way. Because that enumeration is sorted by OCaml structural comparison, it can
try many wrong instantiations before the live local variables, and it may never
reach the right instantiation within the bounded search. That is why the
early focused line-183 runs ended with:

```text
Vampire native certificate checked 52 steps and 2 sources at line 183 char 4;
source_context known=0 local=0 local_definition=0 conjecture=2 unresolved=0.
Failure at line 183 char 4:
  Vampire native certificate did not reconstruct current proof goal
```

The next fix should not be another broader search. It should instantiate the
leading universal binders in the certificate proposition while simultaneously
updating the corresponding source binding, and stop as soon as the
negated-conjecture target is convertible to the live current goal. That is the
generic operation needed for source-linked conjecture reconstruction.

After this report draft was first written, a deterministic suffix experiment
was added. Once the source binding has been instantiated far enough that its
negated-conjecture target is convertible to the live goal, the experiment
applies the remaining preferred local proposition variables directly before
falling back to the generic supplied-refutation path. This is closer to the
desired guided operation and avoids one class of unordered search. It still
does not make line 183 pass:

```text
/project/tmp/line183_guided_suffix_082640
RC=1
Failure at line 183 char 4:
  Vampire native certificate did not reconstruct current proof goal
```

So the current conclusion is sharper but unchanged: the necessary next step is
not more theorem-specific matching and not a broader enumeration. It is a
single source-context operation that instantiates the exported conjecture and
the checked certificate proposition in lockstep, proves that the resulting
target is convertible to the live goal, and then invokes the appropriate
native refutation/CPS/double-negation eliminator.

## Equality and Logical Basis

The user asked why there is a private equality rather than Megalodon's equality.
That concern is valid.

The current system still has an internal certificate representation for
equality-like and proposition-equivalence facts. That is useful for parsing and
normalization, but the final proof should not depend on a private equality
theory. It must use Megalodon's equality and Megalodon's loaded logical
constants.

The same issue appears for:

- `not`;
- `False`;
- `or`;
- `and`;
- `iff`;
- `exists`;
- `forall`;
- `prop_ext`;
- double-negation elimination through `xm`;
- excluded middle itself.

The agreed assumption is that the development is classical and that `xm` is
available. The final proof should use the library's `xm`, not introduce a new
unchecked excluded-middle principle. Likewise, `or`, `False`, and related
constructs should be taken from the library/context.

The live-basis work is a step toward this. It does not finish the equality
story. The final architecture should have a small, explicit "logical basis
transport" layer:

```text
certificate-normal form
  -> live Megalodon logical constants
  -> checked proof term in live delta
```

That layer should be generic and should reject if a required logical fact is
not present in the current development.

## Source Linking

Source linking is the largest remaining E1 boundary.

Earlier reports used "source-linked" too loosely. The audits correctly
distinguished:

- label-linked: the certificate refers to a source name that exists;
- hash-linked: the certificate and source map carry matching formula hashes;
- proposition-linked: the certificate source formula is semantically the same
  as the original Megalodon proposition;
- proof-linked: the source proposition has an actual Megalodon proof in the
  current context.

The final system needs proof-linked source entries.

The source resolver now distinguishes several classes:

- known global facts;
- local hypotheses;
- local definitions;
- generated facts;
- conjecture entries;
- unresolved source obligations.

It also has some support for source-map aliases and hash-backed known
definitions. Set-command equalities need special handling: they may be exported
as TPTP axioms but have no corresponding named claim in the Megalodon source.
Those should not become assumptions. They should be proved in Megalodon,
normally by unfolding or reflexivity.

The current live target diagnostics show the remaining gap clearly.

For the passing line-172 target, the source-context and live-basis transport
are now sufficient.

For line 183, the certificate checks but final goal reconstruction fails:

```text
Vampire native certificate checked 52 steps and 2 sources at line 183 char 4;
source_context known=0 local=0 local_definition=0 conjecture=2 unresolved=0.
Vampire native source-context direct goal reconstruction did not find a proof.
Failure at line 183 char 4:
  Vampire native certificate did not reconstruct current proof goal
```

The source theorem is:

```text
Section PropN.
Variable P1 P2 P3:prop.

Theorem and3I : P1 -> P2 -> P3 -> P1 /\ P2 /\ P3.
aby.
Qed.
```

The expected live goal has local section variables in the current Megalodon
context. The Vampire conjecture is exported in a closed/universally quantified
form. The current source-context resolver sees two conjecture sources, but no
known/local/local-definition sources. Reconstruction then tries simple
refutation-to-goal candidates and gets propositions such as an identity
`P1 -> P1`, not the intended full theorem.

This is not a theorem-name hardwiring problem. It is a general local-context
composition problem:

```text
closed exported conjecture over P1 P2 P3
  -> instantiated live theorem body under current section variables
  -> current Megalodon goal
```

The next source-linking implementation should instantiate universally
quantified conjecture/refutation propositions with the actual live local
variables and then use the native refutation eliminator on that instantiated
goal. The de Bruijn accounting must be done carefully; for line 183 the live
debug output shows variables in the expected order `_2`, `_1`, `_0`.

The right design is a guided source operation rather than a general proof
search:

```ocaml
instantiate_conjecture_to_goal :
  live_context ->
  current_goal ->
  certificate_proof ->
  certificate_proposition ->
  negated_conjecture_binding ->
  instantiated_proof * instantiated_proposition * instantiated_target
```

Its checking condition should be simple:

```text
instantiated_target is convertible to current_goal in the live source delta
```

Only after this condition holds should Megalodon apply the classical
refutation/CPS eliminator. This keeps the source-linking step general, avoids
hardwiring theorem names such as `and3I`, and avoids reintroducing broad
Megalodon-side proof search.

This should be implemented as a generic source-context operation, not as a
special case for `and3I`.

## Smolka-Style Transformations

The Smolka-style lesson is that Vampire proofs over THF/FOOL input include a
large preprocessing layer before the clausal proof:

- source entry and definition expansion;
- rectification and alpha-renaming;
- lambda and de Bruijn normalization;
- FOOL/boolean formula transformations;
- ENNF and quantifier movement;
- CNF projection;
- Skolemization;
- theory distinctness/exhaustiveness;
- predicate definitions and folds;
- AVATAR split generation.

The project initially tried to repair many of these by Megalodon-side
normalization. That was too heuristic. The current plan is better:

```text
Vampire emits explicit transformation certificates.
Megalodon checks each transformation as a proof term or a small verified macro.
Unsupported transformations fail closed in counted modes.
```

Current status:

- Simple propositional/boolean transformations have partial support.
- Predicate definition folding has improved scoped-parameter matching.
- Rectification metadata is emitted, including variable maps, but the proof
  layer is not fully separated.
- CNF projection and literal projection have proof-term support for selected
  shapes.
- AVATAR components and some restricted SAT-resolution traces are replayed in
  focused tests.
- Skolemization has focused direct and CPS support but remains incomplete.
- The broad preprocessing frontier is still E4 unless every transformation in
  the path produces an actual checked proof term without certificate-derived
  `Known`.

The final design should separate source/preprocessing proof from clausal
kernel proof. It should not mix all of that logic inside one importer.

## Skolemization

Skolemization is the most important unfinished Smolka-style transformation.

The project has made real progress:

- Vampire emits introduced Skolem symbols and replaced variables.
- It emits dependency variables and witness terms.
- It emits source formulas and result formulas.
- Megalodon has proof-term support for some direct existential-choice cases.
- The focused line-172 Skolem/AVATAR case now passes after replaying
  descendants under a shadow Skolem-result hypothesis and eliminating
  quantified AVATAR splits without leaking certificate-local choice witnesses.

The line-172 work is important because earlier attempts exposed private
certificate constants such as:

```text
Eps_prop
vampire_exists_prop_choice
```

Those must not leak into final E1 proofs as unapproved assumptions. The
current line-172 path avoids the earlier choice-theorem leak by using live
basis expansion and shadow replay.

However, Skolemization is not solved generally. The line-233 failure from the
early parallel live run shows:

```text
failed native certificate check:
  u35: skolem_formula result does not match explicit skolem substitution
```

That is a lower-level certificate/preprocessing mismatch, not just final goal
composition. It indicates that the checker and Vampire's emitted substitution
record disagree on the result of applying an explicit Skolem substitution in a
more complex formula.

The Skolemization plan should be:

1. Define a typed Skolem macro certificate:

   ```text
   source existential formula
   dependency context
   introduced symbol declarations
   explicit substitution
   result formula
   proof strategy: direct choice or CPS
   ```

2. Make Vampire emit that macro from its internal Skolemization data.
3. Make Megalodon check the macro by constructing proof terms using classical
   choice/epsilon from the live library basis.
4. Add negative tests where the result formula does not match the substitution.
5. Keep broad Skolem runs disabled until the focused macro checks are solid.

## AVATAR and SAT

AVATAR remains a major proof-family issue. The current work has:

- explicit AVATAR component metadata;
- split definitions;
- split dependencies;
- split refutations;
- restricted SAT-resolution trace replay in focused tests.

The audit direction remains correct: AVATAR should not be reconstructed by
large Megalodon-side guesses. Vampire should emit a small propositional proof
object for the SAT-level inconsistency, analogous to a tiny RUP/LRAT-like
certificate or to Prover9/Ivy primitive steps. Megalodon should check that
object and connect each split literal to its first-order clause.

The line-172 proof used AVATAR-related replay under a Skolem shadow
hypothesis. That was good focused progress. It should not be generalized by
adding one ad hoc branch for every AVATAR shape. The goal should be a small
propositional certificate layer.

## Clausal Kernel

The small clausal kernel is the best part of the project technically.

The intended kernel vocabulary includes roughly:

- input/source boundary;
- instantiate/substitute;
- rename/alpha conversion;
- flip/symmetry;
- resolve;
- factor;
- equality resolution;
- equality factoring;
- paramodulation;
- contradiction/empty clause marker.

Some reports and metadata also include truth conflict, subsumption, URR,
superposition, and demodulation. Those should usually be elaborated into the
small primitives rather than accepted as large primitives. That is exactly the
Prover9/Ivy lesson: macro rules should be expanded by the prover and checked
as primitive sequences.

Megalodon has proof-term support for a core subset. The earlier
`corepfcheck` fixtures exercised resolution, factor, paramodulation, equality
symmetry, subsumption resolution, equality resolution, and substitution in
synthetic or focused settings. Later work added theorem-opening fixes for
derived parent proofs.

The next clausal-kernel task is extraction. There should be one kernel
theorem-opening operation, with a specification like:

```ocaml
open_step_theorem :
  global_context ->
  parent_step_variables ->
  result_step_variables ->
  substitution ->
  stored_proof ->
  opened_proof
```

The operation must specify:

- retained variables;
- substituted variables;
- dropped variables;
- global variables;
- shadowing rules;
- proof shifting;
- failure conditions.

That operation should be shared by resolution, substitution, factor,
equality-resolution, equality-factoring, and paramodulation. It should move
out of `vampire_cert_v1.ml`.

## Detailed Chronology

This section records the main project phases because the expert will otherwise
see several different implementation paths in the repository and may reasonably
ask why they exist.

### Phase 1: TPTP proof text and Python skeletons

The first working prototype consumed ordinary Vampire proof output and emitted
Megalodon proof skeletons, frequently as `claim ... admit` blocks. This was
useful because it showed that a human-readable skeleton could be connected to
the original theorem names and that many Vampire steps had recognizable
counterparts in Megalodon's proof language.

That path was never adequate as a final proof checker. It had three structural
problems.

First, the proof text did not contain all the data needed to replay each
inference. For example, a superposition or paramodulation step requires exact
rewrite position, orientation, selected literal, side, parent instantiation,
and result clause. If those are not printed, the importer has to infer them by
search.

Second, the Python layer grew proof knowledge. It did not merely parse. It
normalized formulas, guessed instantiations, recognized benchmark shapes, and
constructed proof snippets. This made local progress fast but made the final
trust story weak. The final trusted checker must be Megalodon, not Python.

Third, generated scripts with bridge assumptions could kernel-check while
proving a stronger theorem than the original goal. This is the mistake the
audits emphasized repeatedly. A proof script with assumptions such as
`bridge_123 : parent -> child` is not a proof of the original theorem; it is a
proof of the theorem under an extra unproved premise.

The lasting value of Phase 1 is diagnostic:

- it identified common Vampire inference families in the target corpus;
- it showed which original Megalodon names must be recovered;
- it exposed set-command equalities as source facts without ordinary claims;
- it established that proof skeletons can be useful for human inspection;
- it motivated moving proof-critical detail into Vampire's exporter.

### Phase 2: Rich Vampire metadata

The next phase enriched Vampire output. Instead of asking Python to infer
hidden details, Vampire began printing them. This was the right direction and
was explicitly requested by the user.

The exported metadata grew to include:

- parent/result formulas and clauses;
- selected literals;
- substitutions and variable maps;
- rewrite positions and orientations;
- normal-form and lambda/de-Bruijn hints;
- split dependency data;
- AVATAR component and refutation data;
- Skolem introduced symbols and dependencies;
- predicate definition fold/fold-chain data;
- theory and FOOL transformation data.

This reduced guessing but did not by itself define a proof calculus. A large
record that says what Vampire did is not automatically a small certificate that
Megalodon can check. The audit's core complaint applied here: the project was
still at risk of adding one more metadata field and one more importer heuristic
for every failing proof.

The lesson from this phase is that "more metadata" is not enough. The metadata
must be organized as primitive proof objects with local checking rules.

### Phase 3: Prover9/Ivy pivot

The Prover9/LADR source was downloaded and analyzed. The key finding was that
Prover9's Ivy output is not merely pretty proof text. It is a two-stage
elaboration:

1. Prover9 expands compact justifications using its own clause operations.
2. It lowers the expanded proof to a small Ivy vocabulary.

The relevant idea is that Prover9 does not ask an external script to discover
the proof detail. It uses the prover's own internal objects and checks that
the expanded clause matches the original derived clause before printing a
small proof object.

That maps directly to the Vampire/Megalodon project:

```text
Vampire macro inference
  -> Vampire-side primitive expansion
  -> explicit small certificate
  -> Megalodon-side checker
```

This pivot also explains why the project should not add large new Python
rules. The final reconstruction logic should be a small Megalodon-side checker
for a small certificate language, not a growing external prover.

### Phase 4: Native S-expression certificate and OCaml checker

The project then introduced a native certificate format and a Megalodon-side
OCaml checker. Earlier drafts used JSON for some experiments, but the current
preferred certificate surface is S-expression based.

This phase produced the current `vampire_cert_v1.ml` module. The benefits are
substantial:

- the checker works with Megalodon's native term/proof syntax;
- source metadata and formula hashes can be validated in the same runtime that
  knows Megalodon's syntax;
- generated proof terms can be checked by `check_propofpf`;
- positive and negative certificate fixtures can be run in Megalodon's test
  suite.

The drawback is equally clear: the OCaml file became large. Some of that size
is unavoidable during migration, but it is not acceptable as the final
architecture. The expert should view `vampire_cert_v1.ml` as a staging area
that must be split, not as the desired endpoint.

### Phase 5: Trust-boundary reset

The July 16 audit found that native preprocessing proof-term checks could pass
by adding certificate-derived propositions to the known-theorem table and then
using `Known` to apply them. This is a hidden bridge assumption.

The branch now contains guardrails against that in counted modes. Transitional
known insertion is disabled by default for counted proof-term reconstruction.
Proof terms are traversed to reject forbidden generated `Known "vampire_*"`
constants. Harnesses distinguish structural preprocessing diagnostics from
proof reconstruction.

This was a necessary correction. It also reset the interpretation of many
previous pass counts: they are useful as structural/integration evidence, but
they are not proof reconstruction.

### Phase 6: Live original-context reconstruction

The current phase is E1 composition. This is the hardest part because a closed
Vampire refutation over exported THF must be turned back into a proof of the
original current Megalodon goal.

The latest line-172 success is significant because it exercises the live
context:

- Vampire proves the exported THF target.
- Megalodon parses and checks the native certificate.
- The checker transports native logical basis pieces into the live library
  basis.
- The final proof is checked against the current theorem goal.

The line-183 failure is also significant because it shows the next missing
general mechanism: local section variables and universally quantified exported
conjectures must be connected generically.

## Source Names and Mangling

The user asked earlier whether original names can be recovered from mangled
TPTP names. The answer is mostly yes, but the final proof should not rely
solely on name decoding.

Name recovery is needed for human readability and for looking up source facts.
The exporter and source map should preserve:

- original Megalodon theorem/lemma names;
- generated hash names;
- aliases between exported symbols and original symbols;
- section/local variable names where available;
- source locations.

However, a name is not a proof. The source resolver must also compare the
proposition, hash, or original `Syntax.tm`, and then supply a proof:

- global theorem name maps to a `Known` proof already in the live context;
- local hypothesis maps to a de Bruijn proof variable;
- local definition maps to a definitional proof/unfolding;
- set-command equality maps to a reflexivity or definitional equality proof;
- conjecture maps to the current goal or its negation.

Hardwiring names like `famunion` would be wrong. The correct general rule is
to use source maps and exported aliases to recover names and then validate the
propositions.

## Set-Command Equalities

Megalodon's `set` command can produce exported TPTP axioms that do not
correspond to named source claims. These are not external assumptions. They are
definitional equalities introduced by the development.

The final reconstruction should treat them as generated source proofs:

```text
exported set equality
  -> identify corresponding live definition/unfolding
  -> prove by reflexivity or definitional conversion
  -> use as source proof
```

This is likely easy for simple equalities but must still be represented
explicitly in the source-context API. If such facts are left as assumptions,
the result is non-qualifying.

## Classical Logic Assumption

The user clarified that the project should assume classical logic and that
`xm` is available. This is now part of the project contract.

The important distinction is between:

- using the live Megalodon library's `xm`, which is allowed;
- installing a certificate-private `xm` theorem, which is not allowed.

The same applies to choice principles used for Skolemization. If Megalodon has
a reviewed classical choice/epsilon principle, the reconstruction may use it.
If the certificate creates a fresh choice theorem and treats it as known, the
proof is not qualifying.

Line 172 was a useful case because the earlier failure involved exactly this
kind of boundary: a certificate-local existence/choice proof leaked into a
candidate proof. The latest implementation moved closer to the correct live
basis.

## Why Line 183 Matters

Line 183 is the next useful blocker because it is simple at the theorem level:

```text
P1 -> P2 -> P3 -> P1 /\ P2 /\ P3
```

If such a theorem fails after the certificate checks, the issue is not a deep
Vampire inference. It is the source-context bridge from the closed exported
problem back to the local Megalodon section context.

That makes line 183 a good test of the design. A robust source-context
implementation should handle this by:

1. recognizing the exported conjecture source;
2. instantiating its universal quantifiers with live section variables;
3. matching the instantiated proposition to the current goal;
4. using the checked refutation and classical reasoning to prove the goal.

If the solution instead checks for the theorem name `and3I` or for a particular
formula string, it is the wrong solution.

## Why Line 233 Matters

Line 233 exposes a different class of problem: a Skolem transformation failure
inside certificate checking.

This is useful because it prevents the project from focusing only on final
goal composition. Even if source-context instantiation were perfect, the line
233 certificate would still fail until the Skolem macro/substitution checker is
correct.

The expert should view line 233 as a representative Smolka-style
transformation target. It should drive a small Skolem certificate design,
rather than a broad set of formula-normalization guesses.

Do not run large sequential suites after every edit. The user explicitly asked

Do not add theorem-name special cases. The code must reconstruct Vampire proofs

Do not treat structural `PASS 100` runs as proof reconstruction. They are

Do not continue growing the monoliths indefinitely. New counted kernel work

## Open Design Questions

Several design choices should be settled explicitly rather than through
incremental patches.

### Certificate granularity

How small should the primitive kernel be? A very small kernel is easier to
trust but requires more Vampire-side expansion. A larger kernel may be easier
to emit but harder to check. The Prover9/Ivy evidence favors a small kernel and
prover-side expansion.

### AVATAR proof format

Should AVATAR refutations be represented as:

- a RUP/LRAT-like propositional proof;
- a simple binary-resolution trace;
- a compact SAT explanation plus checker;
- a sequence of split-literal contradictions?

The current restricted SAT-resolution replay is a seed, not a settled design.

### Skolem proof principle

For Skolemization, should Megalodon use:

- epsilon/choice definitions for generated symbols;
- CPS transformations avoiding global Skolem definitions;
- local conservative definitions introduced in the source/preprocessing layer;
- a combination depending on existential shape?

The line-172 CPS/shadow replay and direct choice cases suggest a combination
may be needed, but it should be specified.

### Source-context serialization

Should final reconstruction occur inside the original Megalodon process, where
the live context is available, or should the source context be serialized as a
sidecar next to the THF problem?

The current live `vampireaby` path has access to the live context, which is
valuable. A sidecar may still be useful for batch/cached runs, but it must not
become a second source of truth.

### Logical basis discovery

Should the checker search the live delta for facts like `xm`, `FalseE`, and
`prop_ext`, or should the THF export include explicit basis bindings?

Searching is convenient but can be brittle. Explicit basis bindings are more
auditable. The current implementation uses live-delta checks and variants; the
long-term design may benefit from a small explicit basis map.

## Current Outlook

The project is still worth continuing. The latest line-172 pass shows that
live original-context reconstruction is not just theoretical. The failures are
now more precise than earlier broad "reconstruction failed" messages:

- line 183 identifies local-conjecture/source-context composition;
- line 233 identifies Skolem substitution checking;
- the audits identify monolith extraction and trust-boundary enforcement.

That is a good place for expert review. The expert can now evaluate concrete
interfaces and proof obligations rather than a vague promise to "handle more
Vampire inferences."

The highest-risk path is to chase more broad pass counts by adding special
cases. The highest-value path is to make the next two focused failures pass
generically, extract the kernel/source modules, and then rerun a small
parallel slice.

## Final Assessment

This project is not finished, but it is no longer in the early blind
translation phase. The current system has enough machinery for a real solution:
Vampire emits rich certificates, Megalodon parses and checks native proof
terms for a meaningful core, the trust-boundary mistakes found by the audits
have been acknowledged, and live original-context reconstruction has started
to pass focused cases.

The main risk is loss of architectural discipline. The project can still fail
by continuing to grow `vampire_cert_v1.ml` and `MegalodonChecker.cpp` faster
than the small certificate language stabilizes. The expert review should push
hard on that point.

The immediate technical frontier is clear:

```text
line 183: compose checked refutation with local source theorem context
line 233: repair explicit Skolem substitution/macro checking
kernel: extract theorem opening and primitive elaboration
source: prove original facts, set equalities, definitions, and conjecture links
```

Once those are solved generally, the project can return to the 100-theorem
gate. Until then, broad pass counts should remain secondary diagnostics, not
claims of completion.
