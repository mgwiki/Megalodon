# Vampire to Megalodon Proof Reconstruction: Project Report

Date: 2026-07-18

This report is a fresh status report for the Vampire-to-Megalodon proof
reconstruction project. It is written for an external expert who will review
the direction of the project and give a second opinion. It incorporates the
previous reports, the audits and audit responses, the Prover9/Ivy analysis,
the Smolka-style transformation discussion, and the current local
`vampire/megalodon5` branches.

The report is deliberately conservative. The project has made real progress,
but it has not achieved the original deliverable: reconstruction of at least
100 representative Megalodon theorems from THF/TPTP Vampire proofs back into
the original Megalodon development, with no `admit`, no `aby`, no incomplete
QED, no hidden bridge assumptions, no certificate-derived `Known` theorems,
no private equality or private logical basis, and no Python reconstruction in
the qualifying path.

The best current evidence is at the exported certificate boundary. Megalodon
can now check a broad native proof-term preprocessing fragment for more than
100 live Vampire certificates without the old transitional `Known` escape
hatch. That is meaningful E2-style progress, but it is still not E1 original
theorem reconstruction.

## Executive Summary

The project is not finished.

The initial direction was to modify Vampire's Lean proof printing and then
translate the output into Megalodon-style proof terms. The project quickly
learned that a pure post-processing translator was too fragile: it tried to
rediscover sorts, substitutions, Skolem dependencies, rewrite positions,
selected literals, and proof-source links from printed clauses. The audits
correctly pushed the project toward a Prover9/Ivy-style architecture:

```text
Megalodon source theorem and local context
  -> THF/TPTP export with source/origin metadata
  -> Vampire proof search, timeout <= 10 seconds
  -> Vampire-side expansion into primitive certificate records
  -> Megalodon native small checker and Syntax.pf elaboration
  -> proof of the original Megalodon theorem
```

The current implementation is partially on that path:

- Python is no longer a qualifying reconstruction path.
- `aby` and `admit` are not accepted in any final result.
- Counted native proof-term modes reject certificate-derived `Known`
  assumptions.
- Vampire emits richer `kernel_v1` metadata for several macro inferences.
- Megalodon constructs and checks native `Syntax.pf` proof terms for a growing
  fragment of source/preprocessing and clausal certificate steps.
- Batch tests are run in parallel with artifacts under `/project/tmp`.

The remaining gap is still significant:

- There is no completed original-context source API that turns a checked
  refutation into a proof of the current Megalodon theorem.
- The source/preprocessing layer is not a clean, typed Smolka-style
  transformation checker yet.
- The small-kernel IR exists only partially; much logic remains in
  `src/vampire_cert_v1.ml` and in Vampire's `MegalodonChecker`.
- The current frontier includes `definition_rewrite_chain` proof-term replay
  and the next layers of source-context glue.

primitive records, rather than by adding another heuristic search in
Megalodon.

## Objective and Success Criterion

The objective is to port Vampire proof reconstruction to Megalodon. The
original motivation was that Vampire already has proof printing/reconstruction
support for Lean-like proof systems, and Megalodon is also proof-term based.
The right solution should therefore make Vampire emit enough typed proof data
for Megalodon to replay a refutation as a checked proof term.

The final deliverable is:

```text
Given a Megalodon theorem or proof obligation, export the relevant THF/TPTP
problem, run Vampire, import the Vampire certificate, and produce a Megalodon
proof term for the original theorem in the original source context.
```

For a result to count, it must satisfy all of the following:

- no `admit`;
- no `aby`, since `aby` is implemented as admission in Megalodon;
- no `-allowincompleteqed`;
- no hidden bridge premise;
- no certificate-derived `Known` theorem;
- no private equality;
- no private logical constants when the Megalodon library supplies them;
- no hardwired theorem or library names;
- no Python proof reconstruction in the accepted path;
- no broad Megalodon-side search that rediscovers data Vampire had internally.

The setting is classical. The reconstruction may assume Megalodon's standard
library context, including `xm`, equality, `False`, disjunction, and related
classical/propositional facts. The implementation should use Megalodon's
equality and logical constants directly, not define private replacements.

The input side is THF/TPTP. Testing should use batch/parallel workflows,
Vampire timeouts of at most 10 seconds, and temporary artifacts under
`/project/tmp`.

## Evidence Classes

The project uses evidence classes to prevent overclaiming.

E1 is the goal. An original Megalodon theorem is reconstructed in the live
source context with no admissions, no bridge assumptions, no hidden generated
theorems, and no private logical basis.

E2 is a closed native `Syntax.pf` proof of a live Vampire certificate at the
exported THF/certificate boundary. This is real proof-term evidence, but it is
not yet composed into the original theorem command.

E3 is a focused or synthetic native proof-term check for a small-kernel rule
or limited transformation family.

E4 is structural evidence: certificate parsing, metadata validation,
source-map validation, live Vampire success, integration testing, or a
transitional diagnostic.

The current status is:

- E1: zero completed original-context reconstructions.
- E2: at least 112 cached live certificates from a 120-case frontier pass the
  no-transitional native preprocessing proof-term checker.
- E3: many focused proof-term tests for clausal and transformation fragments.
- E4: broader live structural and certificate-generation runs, including the
  200-case frontier with 159 generated/passing certificates and one current
  checked frontier.

Older reports sometimes used "PASS" for E4 integration results. That was
misleading. This report treats those as useful tests but not as reconstruction
success.

## Audit-Driven History

The July 12 work produced source-linked Megalodon proof skeletons and a Python
translator. That was useful for learning, but it was not a final path. The
translator started to become an external prover: it guessed names, matched
formulas, reconstructed equality reasoning, searched for proof fragments, and
special-cased the benchmark library.

The July 13 audit pushed toward an Ivy-style certificate. It pointed out that
the proposed "small" certificate was already growing into a monolith and that
generic `input` clauses were unsafe unless tied semantically to real source
facts.

The July 14 audit found that strict mode still allowed bridge premises and
that "source linked" mostly meant label linked. A certificate could attach a
nontrivial clause to a plausible source name unless the source proposition was
checked semantically.

The July 15 branch introduced more meaningful closed checks and formula-shape
comparison against exported THF. This fixed part of the label-only problem,
but the implementation was still broad.

The July 16 audit found the largest hidden-trust issue in the native
proof-term direction: the preprocessing checker could generate a theorem name,
insert the desired implication into the `Known` environment, and then use it.
That is a hidden assumption, even though the final proof term looks native.

The July 17 work reset the counted trust boundary. Counted proof-term modes
reject certificate-derived `Known`. Transitional `Known` remains only as a
diagnostic option and must not be counted.

The July 18 work continued from there. The project made concrete progress on
Skolemization, AVATAR splits, proof-parent metadata, and substituted
equality-resolution metadata. The risk is that the Megalodon OCaml checker is
still growing. The expert should judge whether each new piece is moving toward
a small typed kernel and Smolka-style transformation layer, or merely adding
another special-purpose replay heuristic.

## What Has Been Implemented

### Source and THF Boundary

Megalodon exports THF/TPTP obligations with source/origin metadata. The
certificate path distinguishes original source facts, generated facts,
definitions, conjecture boundaries, and derived Vampire clauses.

The current source validation is much better than the early label-only
version. For supported source formulas, the checker parses the exported THF
formula and compares it against the certificate input shape. Unsupported
source syntax fails in counted modes rather than becoming a free input.

The remaining source-linking gap is original-context composition. The checker
can often say that a certificate input corresponds to a source fact, but it
does not yet provide a clean API of this form:

```ocaml
source_context -> source_id -> Syntax.tm * Syntax.pf
```

That API must resolve:

- global theorem and lemma references;
- local hypotheses;
- local definitions;
- facts generated by proof commands;
- `set`-generated equalities;
- the negated conjecture boundary;
- final refutation-to-theorem conversion.

For `set`-generated equalities, the user correctly noted that there may be no
corresponding explicit claim. The intended handling is not to import them as
axioms. They should be proved in Megalodon by reflexivity or conversion in the
source context.

### Native Certificate v1

Megalodon has a native certificate-v1 importer and checker in OCaml. It parses
Vampire's S-expression certificate, validates structural metadata, validates
source bindings where required, and constructs native `Syntax.pf` proof terms
for supported fragments.

Important modes include:

- strict schema and metadata validation;
- closed checking;
- `corepfcheck` for the small clausal proof-term seed;
- `preprocesspfcheck` for source/preprocessing proof-term checking;
- transitional preprocessing diagnostics, which are not counted.

The native proof-term path calls Megalodon's proof checker. This is the right
foundation. The implementation concern is size and scope: too much replay
logic still lives in `src/vampire_cert_v1.ml`. The code should be split into a
small kernel elaborator, a source-context resolver, and a transformation
checker.

### Fail-Closed Known Handling

The project fixed the hidden generated-`Known` trust bug. In counted
proof-term modes, certificate-derived generated theorems are rejected.

The old bug had this shape:

```text
build proposition P -> Q
invent name vampire_step_uNNN
add Known vampire_step_uNNN : P -> Q
apply Known vampire_step_uNNN
```

That is a bridge assumption. The current counted mode refuses it. Only a fixed
reviewed logical basis from the Megalodon environment may be used.

This is why the no-transitional 112-case recheck matters. It exercises the
native preprocessing proof-term path without relying on the old escape hatch.

### Vampire Kernel Metadata

Vampire now emits richer `kernel_v1` metadata for several important proof
families. The most relevant families include:

- primitive URR expansion records;
- subsumption and subsumption-resolution primitive metadata;
- SAT-subsumption primitive chains;
- predicate definition primitive metadata;
- rectification variable maps;
- equality-resolution metadata;
- substitution metadata;
- AVATAR component, split, dependency, and refutation metadata;
- Skolemization proof-parent and introduced-symbol metadata.

This is directly aligned with the Prover9/Ivy recommendation: Vampire should
emit selected literals, substitutions, positions, orientations, parent units,
result formulas, sorts, and dependencies while it still knows them.

The current metadata is not yet a clean typed primitive IR. Many parts are
still migration-stage strings and fields in a broad certificate. The target
should be:

```text
PrimitiveStep {
  id;
  rule;
  parents;
  conclusion;
  selected literal and term positions;
  substitutions;
  equality orientation;
  sorts of variables and symbols;
  Skolem dependencies;
  source/preprocess payload;
}
```

Vampire-side inference handlers should build this object first. A single
printer should serialize it. Direct per-inference string assembly should be
treated as temporary.

### Skolemization

Skolemization has improved substantially. It is no longer just a structural
metadata check or a hidden `Known` theorem.

Recent Megalodon work handles:

- generated Skolem definitions in result contexts;
- closed/normalized Skolem definitions;
- parent formula metadata auditing;
- compressed Skolem proof-parent metadata;
- local-depth accounting under nested quantifiers and existential binders.

The most important recent fix was in formula orientation under stripped
binders. The previous proof code recursed under `All` and existential lambda
binders, but normalized generated Skolem formulas with only the outer
`result_variable_count`. That shifted generated Skolem terms too little under
local binders. The fix added local binder depth to normalization. This moved
`hammer.1009.43` past its earlier `u98` failure.

Another recent fix relaxed an overly strict Skolem metadata contract. Some
Vampire certificates compress proof parents: two introduced Skolem symbols may
share one proof parent plus the original source parent. The checker previously
required exactly `introduced_count + 1` proof parents. It now requires enough
proof-parent evidence and still validates all emitted parent formulas and
introduced witness metadata. This fixed `hammer.10609.51/u224`.

Remaining Skolem work is mostly architectural:

- represent Skolem transformation proofs as a typed source/preprocess layer;
- preserve dependencies and binder scopes explicitly;
- avoid reconstructing dependencies by search;
- make the proof compose with original theorem context rather than just the
  exported certificate boundary.

### AVATAR

AVATAR replay has also improved.

The checker now handles more quantified AVATAR components, split definitions,
and split-only result clauses. A concrete fix involved split variable binding:
in `hammer.1009.43/u2097`, two AVATAR components reused the textual variable
name `X0`, but the metadata identified the intended component witness through
`parent_var_binding_*` and `split_var`. The old proof code selected the wrong
witness by following parent order. The fix builds the witness substitution
from Vampire's split-variable metadata and only falls back to parent order
after that.

This made `hammer.1009.43` pass the strict native preprocessing proof-term
path:

```text
source map checked                    4
closed checked                      191
native preprocess proof term checked 186
source bindings checked               4
```

Focused checks after the same work passed:

```text

hammer.10785.27   closed 198, preprocess proof-term 193
hammer.11145.52   closed 195, preprocess proof-term 187
```

These are strong E2-style focused results. They remain certificate-bound, not
original-context E1 reconstructions.

### Equality

The current implementation should use Megalodon's equality directly. Earlier
private equality encodings were useful only as scaffolding and should not
survive in the final proof path.

The latest open equality issue is not a private-equality issue; it is metadata
validation around equality resolution after substitution. In
`hammer.11635.105/u463`, Vampire records:

```text
selected_parent_unit = u338
certificate parent   = u463_subst
parent_0_substitution = X0 := true
```

The certificate step is legitimate if `u463_subst` is exactly the substitution
helper for `u338`. The current uncommitted Megalodon edit validates that:

- if selected parent equals certificate parent, use it directly;
- otherwise the certificate parent must be a `Substitute` step whose parent is
  the selected unit;
- the emitted `parent_0_substitution` must match the helper substitution;
- `selected` is checked against the original parent literal;
- `selected_substituted` is checked against the substituted literal.

After this edit, `hammer.11635.105` proceeds to the next frontier:
`definition_rewrite_chain`.

### Definition Rewrite Chains

`definition_rewrite_chain` is the current important proof-term frontier.

The failing example `hammer.11635.105/u495` contains a chain of 23 exact
definition folds. The certificate and metadata include definition parents,
source and target formulas, rewrite positions, and left/right sides for each
fold. Structural validation already checks much of this.

The missing piece is native proof-term replay. The right implementation is to
lower the chain into a sequence of primitive equality-transport or
paramodulation steps. This mirrors Prover9/Ivy: Prover9 expands each
demodulation/rewrite into a small paramodulation-like proof object with exact
parent, direction, and position.

The short-term Megalodon implementation can reuse existing native
paramodulation transport helpers, but the long-term direction should still be
Vampire-side primitive expansion:

```text
definition_rewrite_chain
  -> rewrite step 1 at exact literal/term position
  -> rewrite step 2 at exact literal/term position
  -> ...
  -> rewrite step n at exact literal/term position
```

Each primitive step should carry:

- equality/definition parent;
- target parent;
- literal index;
- term position;
- direction;
- substitution, if quantified;
- source and result clause/formula.

Megalodon should check those records and elaborate them into `Syntax.pf`; it
should not search a large term for possible rewrites.

### Smolka-Style Transformations

The project uses "Smolka-style transformations" to mean proof-producing
source/preprocessing transformations that preserve source correspondence
through clausification and related preprocessing. This layer is separate from
the clausal kernel.

The transformation layer must justify:

- source input and formula-term input;
- definition unfolding/folding;
- rectification;
- FOOL transformations;
- equality and boolean simplification;
- ENNF;
- CNF and clause splitting;
- Skolemization;
- predicate definitions;
- AVATAR introduction where used before the clausal proof.

Some of these are implemented as native proof-term fragments. The layer is not
complete or cleanly factored. The current code mixes transformation replay,
clausal replay, metadata validation, and source lookup in one large module.

The expert should evaluate whether the next work is converging toward this
division:

```text
source_context_resolver.ml
  resolves exported source ids into Megalodon facts

vampire_transform_checker.ml
  checks Smolka-style source/preprocessing transformations

vampire_kernel_checker.ml
  checks primitive clausal proof steps

vampire_cert_v1.ml
  parses certificate, dispatches, and orchestrates
```

That split is not yet present.

## Current Problems

### E1 Is Still Missing

The central missing deliverable is still original-context proof reconstruction.
The checker can validate many exported certificate fragments and build native
proof terms at that boundary. It does not yet reliably produce a proof of the
current theorem in the current Megalodon proof context.

This requires source glue:

- resolve original theorem statement and negated conjecture;
- resolve local hypotheses and local definitions;
- prove `set` command equalities by reflexivity/conversion;
- use original lemmas and definitions, not imported stand-ins;
- convert an empty-clause refutation into the positive theorem proof.

### The OCaml Checker Is Too Large

`src/vampire_cert_v1.ml` remains the practical center of the project. It
contains too much:

- certificate parsing;
- structural validation;
- source validation;
- formula normalization;
- kernel proof replay;
- preprocessing transformation replay;
- proof-term construction;
- error reporting;
- testing hooks.

This makes local iteration easy but long-term audit hard. The next phase
should split the module along the trust boundary instead of adding more
families directly to it.

### Vampire-Side IR Is Partial

The Vampire branch emits much more metadata than before, but it is not yet a
clean Prover9/Ivy-style primitive IR. Some inference handlers still render
special fields directly. The goal should be an internal primitive proof object
with typed parents, positions, substitutions, symbols, and result clauses,
then one canonical printer.

### Definition Rewriting Is the Current Frontier

The current 200-case frontier is exactly the kind of case the audits warned
about. It should not be solved by another Megalodon-side search over large
terms. Vampire must emit exact rewrite occurrences, or expand the chain before
printing. Megalodon should replay each primitive equality transport.

### Source Transformations Are Not Fully Smolka-Style Yet

Several preprocessing transformations now have native proof-term support, but
the layer is not a principled typed transformation system. The implementation
still contains specialized normalization and formula-orientation code. The
right next step is to make the transformation records explicit and check them
with a small collection of proof-producing constructors.

### Test Labels Are Still Confusing

The live harness label `PREPROCESS_STRUCTURAL_PASS` is now too coarse. Some
runs using that label are only structural diagnostics, while the
no-transitional cached recheck is proof-term evidence. The harness should
distinguish at least:

- `LIVE_CERT_GENERATED`;
- `STRICT_SOURCE_VALIDATED`;
- `PREPROCESS_PF_PASS`;
- `PREPROCESS_STRUCTURAL_DIAGNOSTIC_PASS`;
- `TRANSITIONAL_PASS`;
- `E1_ORIGINAL_CONTEXT_PASS`.

This would reduce future reporting ambiguity.

## Relation to Prover9/Ivy

The Prover9/Ivy lesson remains the best architectural guide.

Prover9 does not ask a postprocessor to rediscover proof details from final
clauses. It has a proof expansion pass that lowers complex inferences into
small proof objects. Ivy then checks a small calculus: input, instantiate,
flip, resolve, paramodulate, propositional simplification, and controlled new
symbols.

For this project, the analogous design is:

- Vampire expands macro inferences into primitive Megalodon certificate steps.
- Each primitive step has exact parents, positions, directions, substitutions,
  and result formulas.
- Megalodon checks those primitives and elaborates them to proof terms.
- Source/preprocessing transformations are checked in a separate layer.

The current work follows that direction in places, especially URR,
subsumption, SAT-subsumption, AVATAR metadata, and Skolem metadata. The
project is not yet there globally. `definition_rewrite_chain` is the next
place where the Prover9 lesson should be applied literally.

## Relation to Smolka-Style Transformations

The Smolka-style lesson is that clausification and preprocessing are proof
transformations, not arbitrary rewrites before the real proof starts.

For Megalodon, this means that the transformation layer must produce proof
terms that connect:

```text
original source formula
  -> transformed formula
  -> clauses used by Vampire
```

This is separate from proving the clausal refutation. It must preserve source
identity, binder scopes, local context, definitions, Skolem dependencies, and
classical principles.

The current implementation has fragments of this layer:

- source/formula input checking;
- rectification variable maps;
- Skolem transformation proof fragments;
- formula orientation proof fragments;
- AVATAR component and split replay;
- predicate definition metadata;
- set-like definitional equalities recognized structurally.

The missing work is a clean typed representation and a proof-producing API
that composes with the original theorem.

## Recommended Next Work

The next milestone should be deliberately narrow:

```text
Ten committed, reproducible, original-context Megalodon reconstructions,
with zero bridge assumptions, zero certificate-derived Known, no admit,
no aby, and no incomplete QED.
```

To get there, the concrete plan should be:

1. Commit or discard the substituted equality-resolution metadata fix after a
   smoke test and focused regression check.
2. Implement `definition_rewrite_chain` as primitive equality-transport
   replay, using Vampire-emitted positions and directions.
3. Prefer adding Vampire-side primitive expansion for rewrite chains over
   adding Megalodon-side search.
4. Split `vampire_cert_v1.ml` into source resolver, transformation checker,
   and kernel checker modules.
5. Define the source-context API that maps source ids to Megalodon proof
   objects in the live proof state.
6. Handle `set` command equalities by reflexivity/conversion in that source
   API.
7. Build a small committed fixture set of ten representative live Megalodon
   theorem obligations, their THF exports, Vampire certificates, and expected
   reconstruction checks.
8. Keep broad batch runs parallel and use them only after focused changes are
   validated.
9. Rename test statuses so proof-term evidence is separated from structural
   diagnostics.
10. Stop expanding Python proof logic permanently; keep Python only for
    corpus analysis and report generation if needed.

After that ten-proof milestone, the project can scale the small-kernel IR to
the larger/frequent classes:

- definition rewriting;
- superposition/paramodulation;
- subsumption and subsumption resolution;
- AVATAR;
- Skolemization and CNF;
- predicate definitions;
- FOOL transformations.

The order should be driven by live failure frequency, not by isolated small
examples.

## Current Honest Status

The project has not delivered the final Vampire-to-Megalodon proof
reconstruction system.

It has delivered useful infrastructure:

- THF/TPTP source metadata and stricter source validation;
- native Vampire S-expression certificate parsing;
- native Megalodon `Syntax.pf` proof-term checking for a growing fragment;
- fail-closed rejection of generated `Known` assumptions in counted modes;
- richer Vampire `kernel_v1` metadata for frequent proof families;
- improved Skolemization and AVATAR replay;
- parallel `/project/tmp` batch testing;
- a current 112-certificate no-transitional proof-term frontier.

The next technical blocker is precise and useful: replay of
`definition_rewrite_chain` as primitive equality transport. The larger
architectural blocker is original-context source glue. Until that glue is
implemented, broad certificate-bound proof-term passes should be reported as
E2 evidence, not as proof reconstruction of Megalodon theorems.

The project is now closer to the audit-recommended direction than it was at
the beginning of the week. The risk is continued growth of ad hoc replay code.
The most important discipline for the next phase is to move detail into
Vampire-emitted primitive records and into a small Megalodon checker, while
making the source-context connection explicit enough to produce real E1
theorem reconstructions.
