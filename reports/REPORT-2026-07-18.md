The report is deliberately not a success narrative. The project has made real
technical progress, but the original goal is not yet achieved. The strongest
recent progress is that the work has mostly stopped treating generated proof
scripts and Python translation as the intended final path; Vampire now emits
substantially richer Megalodon-oriented metadata, and Megalodon has a native
`Syntax.pf` checking path for several fragments. The main remaining concern is
that too much proof reconstruction is still being developed inside the large
Megalodon OCaml importer instead of through a small Prover9/Ivy-style
certificate calculus emitted by Vampire and checked by a small Megalodon
kernel-side elaborator.

## Executive Summary

The target remains:

```text
100 representative original Megalodon theorems, exported as THF, proved by
Vampire with a per-problem timeout no greater than 10 seconds, reconstructed
into Megalodon proof terms, and checked by Megalodon in the original source
context, with no aby, no admit, no incomplete QED, no hidden bridge premise, no
certificate-local trusted theorem, and no Python proof reconstruction on the
qualifying path.
```

That target has not been met.

The current branches contain several important building blocks:

- a Vampire-side `kernel_v1` metadata vocabulary;
- a Vampire-side `MegalodonKernelSyntax` boundary;
- explicit metadata for many major Vampire families, including source formula
  transforms, rectification, CNF clauses, definition folds, AVATAR components
  and split dependencies, URR traces, subsumption-resolution pivots, predicate
  definitions, and Skolemization;
- primitive-expansion metadata for some macro inferences;
- native Megalodon `Syntax.pf` construction for a core clausal fragment and
  selected preprocessing/AVATAR/Skolem fragments;
- stricter trust-boundary checks that reject certificate-derived `Known`
  declarations on counted proof-term paths unless explicitly running a
  structural diagnostic mode;
- source-context plumbing that can identify global facts, local hypotheses,
  definition facts, generated facts, unresolved facts, and set-reflexivity
  obligations;
- focused strict native successes on representative targets, including line
  172 and line 183 in `examples/hammer/100thms_12_h.mg`.

The current branches also contain major unfinished work:

- no passing E1 suite of 100 original-context Megalodon theorems;
- no completed small-kernel primitive IR fully separating Vampire macro
  expansion from Megalodon checking;
- no clean standalone Megalodon kernel checker module consuming that IR;
- no fully solved Skolemization story;
- no fully solved Smolka-style transformation pipeline;
- no complete source-context composition for arbitrary original Megalodon
  lemmas, definitions, local hypotheses, generated `set` equalities, and
  conjectures;
- significant remaining implementation mass in `src/vampire_cert_v1.ml`;
- a current focused blocker around Skolem CPS replay on line 233, where
  source witness ordering has been corrected but branch-local proposition
  binding and certificate-local choice elimination are still not fully
  correct.

The best short summary is:

```text
The project has moved toward the right architecture, but the architecture is
not yet fully realized. Current evidence is a mixture of E3 focused proof-term
checking, E4 structural certificate evidence, and a few E1-like focused live
successes. It is not yet a general proof reconstruction system.
```

## Evidence Classes

The previous reports and audits exposed repeated confusion between structural
certificate validation and proof reconstruction. This report keeps the same
evidence classes used in the recent design documents:

```text
E1  Original-context proof reconstruction.
    A proof term is checked inside the original Megalodon development and
    proves the current theorem goal. No aby, no admit, no incomplete QED, no
    hidden bridge theorem, and no certificate-derived trusted theorem.

E2  Exported-THF-bound closed proof reconstruction.
    A native Megalodon proof term checks a Vampire certificate against the
    exported THF/source problem, but the proof has not yet been composed back
    into the original source theorem position.

E3  Primitive-kernel proof-term checking.
    Synthetic or focused live certificates exercise native proof-term
    elaboration for the small clausal or preprocessing kernel.

E4  Structural and diagnostic integration evidence.
    Vampire emits certificates; Megalodon parses them, validates structure,
    source maps, metadata, and trust policy, or runs transitional diagnostics.
    This is useful but is not proof reconstruction.
```

Only E1 satisfies the user's original goal.

The earlier broad `PASS 100` live runs should be classified as E4 unless the
run explicitly checks native proof terms and composes them into the original
Megalodon context. Likewise, preprocessing frontiers that rely on transitional
known implications or diagnostic environment variables are E4, not proof
reconstruction. Focused native proof-term checks are valuable, but they are E3
or E2 unless they discharge the original theorem in place.

## Background and Original Approach

The original assignment was to use the Vampire repository's Lean proof
reconstruction code as a starting point and port the idea to Megalodon.
Megalodon and Lean are morally similar in the relevant sense: both can check
explicit proof terms. Therefore the intended final direction was never merely
to print a human-readable script or to rely on an external Python translator.
The intended direction was:

```text
Vampire proof object
  -> rich certificate / proof term data
  -> Megalodon proof term
  -> Megalodon checker validates it
```

Early work did not follow that path strictly enough. It leaned on Python
translation, generated Megalodon scripts, `claim` skeletons, `admit`, `aby`,
and library-specific name recovery. Those artifacts were useful for exploring
the shape of the problem and for giving a human something readable, but they
were not a credible final solution. The user repeatedly clarified this point:

- final scripts cannot use `aby`, because `aby` is implemented as an admit;
- the proof must be connected to original Megalodon lemmas, definitions,
  local hypotheses, and conjectures;
- classical logic and `xm` are available and should be assumed;
- Megalodon library logic, including `or`, `False`, and equality, should be
  used rather than private replacements;
- broad tests must run in parallel and Vampire must not be rerun repeatedly on
  unsolved problems;
- Vampire should emit richer proof data rather than forcing Megalodon or
  Python to guess missing sorts, substitutions, literal positions, binders,
  or witness dependencies.

The audits strongly reinforced that correction. The current branch reflects a
substantial pivot, but not a completed one.

## Audit History

The audit reports were unusually important in this project because they caught
several ways the implementation could look successful while still being
logically non-qualifying.

The July 12 audit rejected the first Python/script-oriented direction as a
final architecture. It was useful as a skeleton generator, but it relied on
`admit`, `aby`, bridge assumptions, and heuristic source recovery. It did not
give an auditable kernel of reconstructed proof terms.

The July 13 audit pushed the project toward reading Prover9/Ivy and thinking
in terms of small proof objects. The key lesson was that complex prover
inferences should be lowered into a small set of simple, explicit proof
objects. The checker should verify the small objects, not reconstruct a large
prover's internal search retrospectively.

The July 14 and July 15 audits criticized continued broad growth in the
Megalodon-side importer and emphasized that source linking and Smolka-style
transformations were underdeveloped. They also pointed out that structural
metadata validation was being overcounted as proof reconstruction.

The July 16 audit was the most consequential. It accepted the native
`Syntax.pf` seed as real progress, but found that the preprocessing proof-term
frontier had recreated the old bridge assumption problem in a hidden form:
certificate-derived propositions were installed dynamically as `Known`
theorems and then applied. That is not reconstruction. It is only harder to
see than an explicit bridge axiom.

The accepted audit correction is:

```text
No counted proof-term path may install certificate-derived Known propositions.
Unsupported transformations must fail closed, or run only in explicitly marked
structural diagnostic mode.
```

The current branch has moved in that direction. There is now a
`MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1` escape hatch for
diagnostics, and counted modes reject certificate-derived `vampire_*` knowns
except for the reviewed fixed logical basis. This is a material trust-boundary
improvement, though it does not by itself solve reconstruction.

## Prover9/Ivy Direction

The Prover9/Ivy analysis changed the desired architecture. The useful idea is
not to reproduce Prover9 literally, but to copy the design discipline:

```text
complex prover proof
  -> expanded sequence of simple inferences
  -> small proof object
  -> small independent checker
```

For this project, that means Vampire should expand or explain its macro
inferences before printing the certificate. Megalodon should receive explicit
primitive data:

- parent step ids;
- selected literals;
- selected equality sides;
- rewrite position;
- rewrite direction;
- explicit substitutions;
- variable and symbol sorts;
- source formula and result formula;
- introduced Skolem symbols and dependencies;
- AVATAR split and SAT proof details where applicable.

The Megalodon side should then check these objects with small, typed rules. It
should not search for missing pivots, infer binder mappings from raw strings,
guess Skolem witness order from formula shape, or hardwire library theorem
names.

The current Vampire branch is closer to this direction than before.
`Shell/MegalodonChecker/MegalodonKernelSyntax.*` defines a schema named
`prover9-small-kernel-v1`, supported rule contracts, primitive expansion
metadata, and rendered structures for source transforms, rectification,
AVATAR, SAT proof steps, subsumption, Skolem introduced symbols, and other
families. This is a real architectural improvement.

However, this is still not a fully separated primitive proof IR. Much of the
data is still emitted as compatibility metadata around existing Vampire proof
printing. Some macro families expose primitive-expansion summaries, but the
Megalodon checker does not yet consume a complete first-class primitive proof
stream end to end. The expert should view this as a strong start toward the
Prover9/Ivy path, not as evidence that the path is complete.

## Small Kernel Target

The stable clausal kernel should remain small. The current consensus is that
the core should include approximately:

- `input`, as a boundary from source/preprocessing, not as a logical inference;
- `instantiate` or `substitute`, with explicit substitution and sorts;
- `resolve`, binary resolution with explicit pivot data;
- `factor`, duplicate literal contraction;
- `equality_resolution`, contradiction from negative reflexive equality;
- `equality_factoring`, equality-specific factoring;
- `paramodulate`, equality rewriting at an explicit position and direction;
- `contradiction`, final empty-clause marker.

Some names require care:

- `rename` should be checked as alpha-conversion or represented as a special
  case of instantiation, not become an unrestricted logical rule;
- `truth_conflict` probably belongs in the FOOL/preprocessing layer unless real
  clausal certificates show it must be primitive;
- AVATAR should not be hidden inside arbitrary bridge implications. It should
  be checked through an explicit SAT/RUP-style layer or lowered to explicit
  primitive proof objects with a reviewed trust contract.

The current branch has native proof-term logic for pieces of this, but the
implementation is not yet isolated enough. Much of it is inside
`src/vampire_cert_v1.ml`, which also contains parsing, metadata validation,
legacy textual replay, source-map handling, preprocessing reconstruction, and
debug diagnostics. The audits' recommendation to stop monolithic growth has
not been fully realized.

## What Has Been Implemented

The implementation work falls into several streams.

### 1. Vampire Certificate Enrichment

The Vampire fork now emits much richer Megalodon-specific certificate
metadata. Important additions include:

- a `MegalodonKernelSyntax` C++ layer for schema names, supported rules, and
  rendering of structured metadata;
- supported-rule rejection for unsupported `kernel_v1` rule names;
- primitive-expansion chain metadata for URR and related macro inferences;
- explicit AVATAR component, split, refutation, definition, and split
  dependency metadata;
- SAT proof step metadata for parts of the AVATAR path;
- source formula transformation records;
- rectify variable maps and renaming metadata;
- CNF clause metadata;
- definition fold metadata;
- predicate definition metadata;
- subsumption-resolution pivot and fast-path primitive metadata;
- Skolem introduced-symbol metadata, witness sort metadata, dependency
  metadata, and macro-edge metadata.

The Skolem macro-edge addition is especially relevant. Previously Megalodon
was trying to infer helper edges by inspecting generic parent formulas. Vampire
now emits explicit fields such as:

```text
skolem_macro_edge_count
skolem_macro_edge_i_source
skolem_macro_edge_i_target
```

This is exactly the kind of "Vampire knows the information, so Vampire should
print it" correction requested during the project.

### 2. Megalodon Native Proof-Term Checking

Megalodon now has a native certificate path that constructs `Syntax.pf` terms
and checks them with Megalodon's own proof checker. This path is separate from
the original generated-script translator and from Python-generated skeletons.

Implemented or partially implemented fragments include:

- clausal core proof-term checking for resolution-like fragments;
- selected equality reasoning including equality resolution, equality
  factoring, symmetry, and paramodulation fragments;
- source/context basis transport for live Vampire proofs;
- source obligation tracking;
- local definition and local hypothesis recognition in live source context;
- native set-reflexivity handling for equalities generated by Megalodon's
  `set` command;
- AVATAR component and restricted SAT binary-resolution replay;
- negative AVATAR split cleanup in focused cases;
- Skolem proof-term construction using classical choice and epsilon witnesses;
- Skolem helper formula replay;
- Skolem CPS continuation construction for existential elimination through
  conjunction and disjunction;
- debug and audit passes that reject leaked introduced Skolem symbols, split
  symbols, and certificate-only constants in counted modes.

This is not all complete, but it is real proof-term work rather than textual
script generation.

### 3. Trust-Boundary Hardening

The branch now distinguishes counted proof-term modes from transitional
diagnostic modes. The main trust hardening includes:

- strict native live mode no longer treats absence of a usable certificate as
  success;
- certificate-derived dynamic `Known` facts are rejected on counted
  proof-term paths by default;
- the old transitional preprocessing known behavior requires
  `MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1`;
- final-refutation cleanup candidates are checked before being kept;
- proof-term traversal rejects unauthorized certificate-local constants whose
  names start with `vampire_`, except for fixed reviewed logical basis names;
- source facts are categorized so that unresolved source obligations are not
  silently counted as discharged proofs.

This was necessary after the July 16 audit. It is still not sufficient for E1,
but it prevents a major class of false positives.

### 4. Source Linking Work

Some source linking now exists. Megalodon can distinguish:

- global known facts;
- local hypotheses;
- local definitions;
- generated facts;
- unresolved facts;
- set-command reflexivity obligations.

The implementation can sometimes compose a certificate-derived proof back into
the live context and has focused successes on line 172 and line 183. It also
avoids one earlier unsoundness where certificate-helper delta entries could
overwrite live Megalodon definitions.

However, source linking is still incomplete. A general E1 proof needs a
well-defined source-context contract:

```ocaml
type source_proof =
  | GlobalKnown of string * Syntax.tm
  | LocalHyp of int * Syntax.tm
  | Definitional of Syntax.tm * Syntax.pf
  | Generated of Syntax.tm * Syntax.pf
  | SetReflexivity of Syntax.tm
  | Unresolved of string * Syntax.tm

type source_context = source_id -> source_proof
```

The actual type names do not matter. What matters is that every TPTP source
axiom has an auditable route back to the original Megalodon development:

- a theorem or lemma already in the environment;
- a local proof hypothesis at the correct de Bruijn depth;
- a local definition unfolded by conversion;
- a `set`-generated equality proved by reflexivity/conversion;
- a generated Smolka-style transformation proof;
- the negated conjecture handled only at the final refutation-to-goal
  composition boundary.

This remains a major unfinished part of the project.

### 5. Smolka-Style Transformation Work

The Smolka-style transformation layer is the right way to think about the path
from original higher-order formulas to the clausal forms consumed by the
kernel. It should be separate from the small clausal kernel. It includes:

- source formula copying;
- formula-term copying;
- definition input/fold/unfold;
- rectification;
- FOOL Boolean lifting;
- FOOL exhaustiveness;
- equality-to-truth and truth-to-proposition conversions;
- ENNF;
- CNF formula and literal projection;
- Skolemization;
- predicate definitions;
- possibly AVATAR boundary facts.

The branch contains partial metadata and partial proof-term handling for many
of these transformations. It does not yet contain a clean, complete,
Smolka-style transformation checker. Some transformations are replayed with
proof terms; others are structurally validated; others still depend on local
heuristics or focused-case logic.

The expert should pay particular attention to whether each transformation is
being proved or merely accepted because its shape matches expected metadata.
Shape validation is useful, but it is E4. For E1/E2, each transformation must
produce a checked proof term or be lowered into smaller checked
transformations.

## Current Focus: Skolemization

Skolemization is currently the most active technical area and the most visible
blocker.

The desired proof principle is classical. Since the Megalodon development is
classical and `xm` is available, the reconstruction can use choice/epsilon
principles. The final code should use Megalodon's library equality and logical
connectives rather than private substitutes.

The core problem is that Vampire's Skolemization step can replace nested
existentials across formulas with conjunctions, disjunctions, implications,
universals, and local branch structure. Megalodon must reconstruct a proof
that transports the source formula to the Skolemized result without leaking
introduced Skolem symbols or certificate-only epsilon helpers into the final
live proof.

Recent implemented pieces include:

- proof-level witness replacement;
- generated-CPS-proposition closure under the correct term depth;
- source witness sort fallback;
- binder-erasure witness validation;
- parent-helper implication replay;
- Skolem macro-edge metadata read from Vampire;
- threading accumulated Skolem-symbol-to-epsilon-witness replacements through
  helper matching and implication construction;
- sibling fallback refinement for branch cases;
- final cleanup attempts for AVATAR split symbols and nullary `sK*` symbols;
- result-continuation binding for result step variables;
- source-formula binder-name scanning for nested `vampire_exists_prop`;
- source-binder-ordering of Skolem substitutions before native replay.

Focused line 172 and line 183 pass under strict native live replay. This is a
good sign: the implementation can reconstruct some real original-context
Skolem-heavy examples without `aby` or `admit`.

Line 233 remains the current focused blocker. Its recent history is:

- earlier failures exposed a Skolem substitution mismatch at step `u35`;
- after witness registration and negative AVATAR split replay, line 233
  reached a native refutation;
- after checked AVATAR/sK cleanup, visible `split_*` and nullary `sK*` symbols
  were no longer the first live validation failure;
- the fallback path still leaves a certificate-only `Eps_prop` helper;
- the stronger CPS candidate is rejected by Megalodon's proof checker;
- recent diagnostics show a branch-local proof/proposition mismatch, with
  expected and actual proof variables differing in a deep application path;
- witness ordering was one real cause: Vampire's raw substitution order for
  the representative step was observed as `X0,X1,X2,X3,X4,X6`, while the
  source existential order was `X0,X1,X6,X2,X4,X3`;
- that ordering issue is now addressed by the committed source-binder-order
  patch, but the deeper branch-local CPS proposition alignment issue remains.

The committed source-binder-order fix reads the raw `source_formula` metadata
to recover binder names before Megalodon's parser erases them to de Bruijn
indices, then reorders the Skolem substitution by source binder order. This is
directionally better than guessing from formula shape, because it uses
information Vampire already prints. It is still not a complete Skolemization
solution, because line 233 continues to expose context alignment and
certificate-local-choice issues after the ordering mismatch is removed.

The larger lesson is not "add one more Skolem heuristic." The lesson is that
Vampire should emit a first-class Skolem transformation proof object with
ordered binders, introduced symbols, witness terms, dependencies, sorts, and
macro edges. Megalodon should check that object directly.

## Equality

The equality situation has improved conceptually but remains worth expert
review. The final proof reconstruction should use Megalodon's equality, not a
private equality invented for the certificate path.

Some internal code still uses helper recognizers and wrappers around
Megalodon equality forms because the TPTP/Vampire certificate formulas arrive
through a normalized representation. That is acceptable as parsing and
orientation infrastructure, but it is not acceptable if it becomes a second
trusted equality theory.

The intended invariant is:

```text
All equality reasoning in counted proof terms eventually elaborates to the
Megalodon equality and Megalodon's equality eliminators/conversion principles.
```

The expert should check whether any remaining helper equality symbol is only a
parser/intermediate notation or whether it survives as a trusted logical
constant. Surviving private equality would be a serious design defect.

## Original Lemmas, Definitions, and TPTP Names

Source linking has two distinct problems:

1. recover the original Megalodon names, source positions, local contexts, and
   definitions from exported TPTP names;
2. prove or resolve every exported source axiom in Megalodon.

The name recovery problem is partly solved by studying the Megalodon exporter
and by using metadata. Mangled TPTP names can often be mapped back to original
Megalodon names. However, name recovery alone is not proof reconstruction. It
only identifies where the proof obligation should come from.

The second problem is the real trust boundary. Each TPTP axiom must be one of:

- an original lemma/theorem already known in Megalodon;
- a local claim/hypothesis in the active proof context;
- an unfolding or definitional equality;
- a generated equality from `set`, proved by reflexivity/conversion;
- a generated transformation fact with an explicit proof term;
- a conjecture-negation assumption introduced only for refutation and then
  discharged at the final goal boundary.

The user specifically noted that some TPTP axioms come from Megalodon's `set`
command and may not correspond to claims. These should not be looked up as
lemmas. They should be proved directly by reflexivity or conversion. The
branch has code in that direction, but it should be tested on deliberately
chosen examples with local `set`s and definition-heavy contexts.

At present, the focused line 172 and line 183 successes show that source
composition can work in some cases. They do not prove that arbitrary original
Megalodon developments are handled.

## Python Translator Status

The Python translator and generated script path should be considered legacy
exploration and debugging infrastructure. It can still be useful for:

- quickly inspecting proof skeletons;
- producing claim/admit outlines for human reading;
- comparing source names and TPTP names;
- triaging broad certificate corpora.

It should not be part of the qualifying path. A proof that depends on Python
to guess inference details, reconstruct terms, or generate trusted proof
steps is not the desired Vampire-to-Megalodon reconstruction.

This was a major criticism in the audits, and it remains an important guardrail
because Python is a tempting place to patch over missing certificate data.
Missing data should be emitted by Vampire, not guessed in Python.

## Main Problems

### Problem 1: The Project Is Not Yet E1

The original goal is original-context reconstruction. A proof checked only
against exported THF, or a structurally valid certificate, is not enough.

The branch has focused live successes, but not a representative 100-theorem
E1 suite. Any expert assessment should keep this distinction central.

### Problem 2: Skolemization Is Still Too Ad Hoc

The Skolem/CPS work is sophisticated, but much of it is still in the form of
local replay logic in `vampire_cert_v1.ml`. It handles real cases and exposes
real proof obligations, but it is hard to audit and brittle around branch-local
witnesses.

The better endpoint is a Vampire-emitted Skolem transformation proof object:

- ordered source binders;
- introduced symbols;
- replaced variables;
- witness terms;
- dependency terms;
- sorts;
- macro-edge source and target formulas;
- branch structure;
- choice principle used.

Megalodon should check that object, not rediscover it.

### Problem 3: Smolka-Style Transformations Are Not Yet Modular

FOOL, ENNF, rectification, CNF projection, predicate definitions,
definition-folding, and Skolemization are separate transformation families.
They should not be mixed into the clausal kernel, and they should not be
accepted by broad bridge propositions.

The current code has useful metadata and partial proof-term replay, but the
transformation checker is not yet a clean component.

### Problem 4: The Megalodon Importer Is Still a Monolith

The audits recommended stopping growth in the OCaml importer and moving toward
smaller modules such as:

- `vampire_kernel_syntax.ml`;
- `vampire_kernel_check.ml`;
- `vampire_kernel_elab.ml`;
- `vampire_source_context.ml`;
- `vampire_transform_check.ml`.

Some files and boundaries exist conceptually, but the main work still happens
inside `src/vampire_cert_v1.ml`. This is a maintainability and auditability
risk.

### Problem 5: Vampire IR Is Still Transitional

Vampire now has an explicit syntax/rendering boundary, which is good. But the
expert should check how much of it is a real internal primitive proof IR and
how much is structured printing around existing proof steps.

The desired Vampire-side invariant is:

```text
macro inference handler -> primitive step records -> canonical printer
```

Direct string assembly and compatibility-only metadata should shrink over
time. Unsupported rules should fail closed before certificate emission.

### Problem 6: Source Context Is Still Underspecified

The final theorem proof depends on more than the external certificate. It
depends on the original Megalodon context. The system still needs a clearer
contract for:

- global theorem hashes and names;
- local hypothesis indices;
- local `set` definitions;
- local definitions and conversion;
- theorem binder scopes;
- conjecture negation and final refutation discharge;
- generated transformation facts.

Line 172 and 183 show that this can work, but they are not enough to establish
generality.

## Suggested Architecture From Here

The recommended architecture is:

```text
Megalodon source theorem/context
  -> THF export with source ids and enough context metadata
  -> Vampire search
  -> Vampire primitive certificate IR
  -> canonical certificate S-expression
  -> Megalodon certificate parser
  -> small structural checker
  -> native Syntax.pf elaborator
  -> source-context composition
  -> checked proof of original Megalodon theorem
```

The implementation should enforce the following boundaries.

### Boundary A: Source Context

This module knows how exported sources map back to the original Megalodon
development. It should prove `set` equalities by reflexivity/conversion and
resolve local/global facts without inventing new assumptions.

### Boundary B: Transformation Checker

This module checks Smolka-style formula transformations. It is allowed to use
classical principles and library logic. It should produce checked proof terms,
not dynamic known propositions.

### Boundary C: Clausal Kernel

This module checks the small clausal kernel: instantiate, resolve, factor,
equality resolution, equality factoring, paramodulation, and contradiction.
It should consume explicit pivots, positions, directions, substitutions, and
sorts from Vampire.

### Boundary D: AVATAR/SAT Layer

This module handles AVATAR explicitly, either through a small SAT/RUP checker
or through a documented lowering to primitive proof objects. It should not be
a bridge theorem.

### Boundary E: Final Composition

This module converts a refutation of the negated conjecture into a proof of
the original theorem goal in the current Megalodon proof context.

The code should be organized so that each boundary can be reviewed
independently.

## Recommended Milestones

The milestone order matters. The project should not chase broad pass counts
until the trust boundaries are clean.

### Milestone 1: Freeze Counted Trusted-Known Paths

Keep the current policy that counted proof-term paths reject certificate-local
knowns. Add regression tests that intentionally try to install a
certificate-derived known proposition and verify rejection.

Exit criterion:

```text
No counted E1/E2/E3 path can use certificate-derived Known propositions.
```

### Milestone 2: Finish the Vampire Primitive IR Boundary

Move from metadata-as-rendered-fields toward first-class primitive records for
the frequent macro families:

- resolution;
- unit-resulting resolution;
- subsumption resolution;
- superposition/paramodulation;
- substitution/instantiation;
- factoring;
- Skolemization.

Exit criterion:

```text
Vampire emits primitive records with explicit parents, substitutions, sorts,
literals, positions, directions, and conclusions. Unsupported records fail
closed.
```

### Milestone 3: Extract the Megalodon Kernel Checker

Move the small kernel elaboration out of the monolithic importer without
adding new broad replay behavior during extraction.

Exit criterion:

```text
The small kernel can parse and check primitive certificates in isolated modules
and produce native Syntax.pf proof terms.
```

### Milestone 4: Make Skolemization a First-Class Transformation

Stop relying on branch-local witness-order heuristics. Use Vampire-emitted
Skolem transformation data.

Exit criterion:

```text
Line 172, line 183, and line 233 all pass strict native live replay without
certificate-only Eps_prop/sK/split leaks, and without transitional knowns.
```

### Milestone 5: Implement Source-Context Composition on a Designed Set

Build a small hand-picked E1 suite containing:

- one global theorem;
- one local hypothesis;
- one local definition;
- one `set` equality;
- one definition unfold/fold;
- one Skolemized theorem;
- one AVATAR proof;
- one equality-heavy proof;
- one superposition/paramodulation proof;
- one conjecture-negation final discharge.

Exit criterion:

```text
At least 10 examples pass as true E1.
```

### Milestone 6: Run the 100-Theorem Gate

Only after the above milestones, run the broad suite:

- export once;
- run Vampire in parallel with timeout <=10 seconds;
- reconstruct from cached/generated certificates;
- check in Megalodon in parallel;
- report E1/E2/E3/E4 separately;
- do not count diagnostic modes.

Exit criterion:

```text
100 representative original-context E1 proofs pass.
```

## What the Expert Should Review

The expert review should focus on these questions.

1. Is the `MegalodonKernelSyntax` layer in Vampire a good basis for a real
   primitive IR, or is it still too close to formatted metadata?

2. Does any counted Megalodon proof-term path still install
   certificate-derived known propositions under another name?

3. Are the current native proof constructors using Megalodon's real equality,
   `False`, `or`, implication, universal quantification, and classical

8. How should AVATAR be represented: SAT/RUP proof, primitive lowering, or a

## Honest Current Status

The project is substantially better than it was at the first audit. It now has
real native proof-term checking, stricter trust policy, richer Vampire
metadata, focused original-context successes, and a much clearer understanding
of why Python/script reconstruction is not the final path.

It is still not finished. The current implementation remains too ad hoc around
Skolemization and too concentrated in the large Megalodon importer. The
Prover9/Ivy direction is accepted and partially implemented, but not yet the
dominant end-to-end path. The 100-theorem E1 target remains open.

The most useful immediate work is not another broad pass-count run. It is:

1. specify the Skolem CPS context discipline, or replace it with a smaller
   first-class Vampire-emitted Skolem proof object;
2. make Skolemization consume explicit Vampire-emitted proof data;
3. isolate the small kernel and source-context checker;
4. define a small E1 suite that exercises original lemmas, local hypotheses,
   definitions, `set` equalities, Skolemization, equality, and AVATAR;
5. only then return to a broad 100-theorem gate.
