This report summarizes the current state of the Vampire-to-Megalodon proof
reconstruction project for expert review. It incorporates the previous reports,
the audits, the audit responses, the Prover9/Ivy analysis, the small-kernel
plans, the Smolka-style transformation discussion, and the current local branch
state.

The report is deliberately conservative. The original goal is not complete.
There has been substantial implementation progress, but there is not yet a
100-theorem suite of original Megalodon theorems reconstructed from Vampire
proofs with no `aby`, no `admit`, no incomplete QED, no hidden bridge premise,
no certificate-local trusted theorem, and no Python proof-producing step.

## Executive Summary

The target remains:

```text
Given a theorem in an original Megalodon development, export the theorem and
its context as a THF/TPTP problem, let Vampire prove the problem under a
per-problem timeout of at most 10 seconds, emit a detailed Vampire certificate,
import that certificate into Megalodon, elaborate it to native Megalodon proof
terms, and check a proof of the original theorem in the original context.
```

That target has not yet been achieved.

The main positive result is architectural progress. The project started with a
large Python-oriented proof skeleton generator and a Megalodon script emitter.
That path produced useful examples and diagnostics, but it was not the right
final architecture. The audits and user feedback correctly identified that it
was becoming a second reconstruction engine outside both Vampire and the
Megalodon kernel. The current branch has moved toward a Prover9/Ivy-style
design:

```text
Megalodon source theorem/context
  -> THF/TPTP export with origin metadata
  -> Vampire proof search
  -> Vampire-side proof detailing while Vampire still has exact data
  -> native S-expression certificate
  -> Megalodon parser, small checker, and Syntax.pf elaborator
  -> original-context Megalodon proof
```

The strongest current accomplishments are:

- Vampire emits a native Megalodon-oriented S-expression certificate.
- Vampire emits a growing `kernel_v1` metadata vocabulary, not just opaque
  proof text.
- Vampire now has a `MegalodonKernelSyntax` boundary for newer certificate
  metadata.
- Megalodon parses the native certificate into typed OCaml structures.
- Megalodon has a real native `Syntax.pf` proof-term path for a clausal core
  and selected preprocessing fragments.
- Counted native paths now reject certificate-derived dynamic `Known`
  propositions unless an explicit diagnostic environment variable enables the
  old transitional behavior.
- The source-context layer distinguishes global facts, local hypotheses,
  definitions, generated facts, conjecture facts, unresolved facts, and
  `set`-command reflexivity obligations.
- Some Megalodon `set` facts that do not correspond to source claims are now
  handled as generated reflexivity/conversion obligations rather than as
  trusted axioms.
- Focused native replay examples, especially targets `172:4`, `183:4`, and
  `233:4` in `examples/hammer/100thms_12_h.mg`, currently pass.
- Skolemization is no longer opaque string rewriting. Vampire emits top-level
  Skolem proof contracts, child formulas, macro-edge records, branch contracts,
  introduced-witness records, quantifier metadata, and free-variable metadata.
  Megalodon consumes these as typed data and validates several important
  invariants.

The major unfinished items are:

- no qualifying E1 100-theorem result;
- no committed qualifying 10-theorem original-context milestone;
- no complete standalone small primitive IR analogous to Ivy proof objects;
- no isolated Megalodon primitive certificate checker/elaborator module;
- no complete source/preprocessing proof-producing layer;
- no complete Smolka-style transformation pipeline;
- no general complete Skolemization proof reconstruction;
- no complete composition from exported-source refutation back to the original
  Megalodon theorem command;
- too much proof logic still resides in the large
  `src/vampire_cert_v1.ml` importer;
- too much export/detailing logic still resides in the large Vampire
  `MegalodonChecker.cpp` implementation;
- too much current progress is still measured by focused proof-term checks and
  structural certificate runs rather than original-context reconstruction.

The most important recent Skolemization blocker was target `233:4` in
`examples/hammer/100thms_12_h.mg`, step `u35`. That focused blocker is now
fixed on the current branch by shifting delayed sibling formulas under the
fresh term binders introduced while replaying the left branch of the
Skolemization CPS proof. The new committed focused regression runs
`172:4`, `183:4`, and `233:4` in parallel and all three pass.

The next observed frontier is now narrower than the one described in the
first July 18 refresh. A representative current failure is `hammer.1009.43`,
step `u98`. Regenerated Vampire output already includes the relevant
rectification and Skolem contract metadata. Megalodon now avoids installing
context-dependent epsilon witnesses as arity-zero global definitions, so the
earlier de Bruijn escape has been removed. The remaining failure is that the
Skolem CPS replay does not yet have a general typed contract for opening
non-propositional parent step variables and aligning source/result binder
orientation. This is still part of the Smolka-style preprocessing frontier,
but it should be solved by richer Vampire-owned proof-object data rather than
by Megalodon-side guessing.

The recommended next milestone is:

```text
Ten committed, reproducible, original-context Megalodon theorem proofs,
bridge-free and certificate-Known-free, using Vampire certificates emitted
with <= 10 second per-problem timeouts.
```

Once ten genuinely closed original-context examples exist, the milestone should
expand to 100. Broad structural `PASS 100` runs should remain useful
integration evidence, but they should not be reported as proof reconstruction.

## Evidence Classes

The project now uses evidence classes to avoid confusing integration success
with proof reconstruction.

E1 is the actual goal:

```text
Original-context proof reconstruction. A proof term checks inside the original
Megalodon development and proves the theorem at the original proof site. No
aby, admit, incomplete QED, bridge assumption, certificate-local trusted
theorem, or Python proof reconstruction is used.
```

E2 is useful but still not final:

```text
Exported-THF-bound closed proof reconstruction. A native Megalodon proof term
checks the Vampire certificate against the exported source problem, but the
result has not yet been composed back into the original theorem command.
```

E3 is focused proof-term evidence:

```text
Synthetic or focused live certificates exercise native Syntax.pf elaboration
for a small-kernel rule or a particular preprocessing fragment.
```

E4 is structural/integration evidence:

```text
Vampire emits certificates; Megalodon parses them, validates metadata, source
maps, trust policy, and certificate structure, or runs diagnostic modes. This
is valuable, but it is not proof reconstruction.
```

Under this classification:

- broad strict certificate runs are E4 unless they also construct and check
  native proof terms and compose them into the original theorem;
- cached or live preprocessing runs that relied on transitional known
  implications are E4, not E2;
- focused native proof-term checks for live hammer certificates are E2-like or
  E3 evidence depending on whether they are exported-bound or synthetic;
- the current `172:4` and `183:4` successes are meaningful focused native
  evidence, not a completed original-context theorem suite;
- there is no current broad E1 result.

This discipline is one of the most important corrections made after the audit
reports. It should remain enforced in both code and reports.

## Requirements and Constraints

The project is constrained by several explicit user requirements:

- Use THF/TPTP exports from Megalodon.
- Use Vampire proof search with `--input_syntax tptp`.
- Do not run Vampire for more than 10 seconds per problem.
- Prefer batch export, parallel Vampire runs, and parallel certificate checks.
- Use `/project/tmp` for temporary artifacts.
- Do not use `aby` in the resulting scripts or proof terms. In Megalodon,
  `aby` is implemented as admission.
- Do not use `admit` or `-allowincompleteqed` in a qualifying final result.
- Assume classical logic; `xm` is available.
- Use Megalodon's library constants for equality, `False`, disjunction, and
  related logic rather than private final replacements.
- Do not hardwire particular current-library names such as individual set
  facts, `famunion`, or benchmark-specific Skolem names.
- Get exact proof details from Vampire whenever possible, including sorts,
  selected literals, substitutions, positions, directions, generated symbols,
  dependencies, and parent/result formulas.
- Treat TPTP axioms generated from Megalodon `set` commands as generated
  definitional/reflexivity obligations where possible, not as source claims
  that must already exist in the development.

These constraints rule out a final architecture based on Python guessing,
library-specific name recovery, broad OCaml heuristics, or certificate-derived
trusted theorems.

## Audit-Driven Course Corrections

The July 12 state was a prototype. It produced a useful proof skeleton
generator and helped expose the shape of Vampire output, but it did not have
the right trust boundary. It leaned too much on Python translation and on
Megalodon proof scripts that contained placeholder claims.

The July 13 and July 14 work improved source linkage and certificate parsing,
but the audits identified two serious concerns:

- strict validation was not the same thing as closed proof checking;
- source names were sometimes checked without fully guaranteeing that the
  semantic propositions attached to those names matched the original source.

The July 15 and July 16 audits sharpened the architecture. They accepted the
native `Syntax.pf` direction but rejected dynamic certificate-derived
`Known` propositions as a hidden bridge. A proof term that checks because the
importer just inserted the desired implication into the known theorem table is
not proof reconstruction.

The July 16 audit recommended a Prover9/Ivy-style reset:

- Vampire should expand or annotate its own complex inferences while it still
  has exact substitutions, selected literals, positions, equality directions,
  sorts, Skolem dependencies, and result clauses.
- Megalodon should check a small fixed certificate calculus.
- Source/preprocessing transformations should be proof-producing and separate
  from the clausal kernel.
- New pass counts should be gated by closed native proof terms, not structural
  validation alone.

The current branch has partly followed this advice:

- Python is no longer considered a qualifying proof path.
- The native counted paths reject certificate-derived `Known` unless a
  diagnostic environment variable is explicitly set.
- A source-context module exists.
- A shared kernel syntax module exists.
- Vampire emits richer proof metadata, especially around Skolemization.
- Megalodon parses and validates much of that metadata.

The current branch has not fully followed the advice:

- `vampire_cert_v1.ml` remains a large importer/checker/elaborator/debugger
  monolith.
- `MegalodonChecker.cpp` remains a large exporter/metadata/macro-expansion
  monolith.
- There is still no clean small primitive IR that fully separates Vampire
  macro expansion from Megalodon checking.
- Much current work is still inside the broad Megalodon importer because that
  is where the existing proof-term machinery lives.

The audit's main criticism is therefore still partly valid. The work is no
longer primarily Python, but it has not yet fully become the intended small
Ivy-like certificate pipeline.

## Prover9/Ivy Lessons

The Prover9/Ivy analysis remains the clearest external model for this project.

Prover9 does not ask Ivy to rediscover large inference steps by search. It
performs proof-detailing before checking:

- `expand_proof` turns ordinary Prover9 justifications into more explicit
  intermediate clause steps.
- `expand_proof_ivy` lowers those expanded steps into a small Ivy kernel.
- Ivy receives simple proof objects with exact parentage, substitutions,
  positions, equality directions, and new-symbol information.

The central lesson is:

```text
The prover should explain its own proof while it still knows the proof data.
The checker should verify a small fixed proof language.
```

The current Vampire/Megalodon work follows this in some areas:

- Vampire emits `kernel_v1` records for important inferences.
- Substitution and selected-literal information are increasingly explicit.
- Unit-resulting resolution and subsumption resolution have more explicit
  primitive traces than before.
- Rewrite and superposition metadata has been moved toward exact primitive
  fields.
- Skolemization now carries explicit proof contracts, branches, and witnesses.

The design is still incomplete:

- there is no isolated Vampire proof-detailing pass analogous to Prover9's
  expansion pipeline;
- there is no complete typed `MegalodonKernelStep` stream that replaces the
  legacy macro certificate;
- Megalodon still interprets rich macro metadata in one large module;
- many preprocessing transformations remain macro-level objects rather than
  primitive proof objects.

The right next step is not to add more Megalodon-side guessing. It is to keep
moving proof detail and macro expansion to Vampire and keep shrinking the
Megalodon side toward deterministic checking and proof-term elaboration.

## Source Linking to Original Megalodon Developments

Source linking is much better than in the initial prototype, but it is not yet
complete enough to satisfy E1.

The current source-context work represents source facts more concretely than
the old name-only approach. It distinguishes:

- global known facts;
- local hypotheses;
- definitional facts;
- generated facts;
- conjecture and negated-conjecture facts;
- unresolved facts;
- generated `set` reflexivity facts.

This is important because Vampire proof inputs do not merely correspond to
named library theorems. They can also correspond to:

- local hypotheses in the theorem's context;
- local definitions;
- definitional unfoldings;
- facts generated by Megalodon commands;
- the negated conjecture introduced by refutation;
- preprocessing products derived from source formulas.

The current implementation also performs semantic source checks for supported
fragments, rather than merely checking that a source label exists. That was a
direct response to the audit concern that name linkage without proposition
linkage is insufficient.

Set-command facts deserve special treatment. Some exported TPTP axioms come
from Megalodon's `set` command and have no corresponding source claim. The
current source-context approach treats supported such facts as generated
reflexivity/conversion obligations. This is the right direction. They should
not become fake source claims or hidden bridge assumptions.

What remains missing:

- a complete proof-producing original-context entry point at the theorem site;
- a general proof combinator that turns a refutation of the exported negated
  conjecture into a proof of the original theorem in Megalodon's live context;
- complete treatment of local hypothesis scopes and binder lifetimes across
  export/import;
- complete treatment of all local definitions and generated facts in the 100
  problem corpus;
- a committed qualifying 10-case original-context test gate;
- a committed qualifying 100-case original-context test gate.

In short: the system has the beginnings of source-context linking, and it is
now designed around the right categories. It still does not close the loop all
the way back to the original theorem for the desired suite.

## Equality and Logical Basis

The final path should use Megalodon's own equality and logical constants. The
user explicitly questioned why private equality appeared in some code paths.
The answer is historical: older generated scripts and compatibility layers
introduced private `vampire_*` encodings to get early reconstruction skeletons
running. Those are not the desired final path.

The current source-context and native proof-term direction is better:

- classical reasoning is assumed;
- `xm` may be used;
- Megalodon's library `False`, disjunction, implication, and equality should
  be used from the available context;
- polymorphic Megalodon equality is recognized in source-context handling;
- supported generated equality facts from `set` can be proved by reflexivity
  or conversion.

There is still cleanup to do. The large importer contains legacy compatibility
code and textual-emitter support. For expert review, the important point is
that private equality is not intended as the final trusted basis. It is a
legacy transitional artifact where it still appears.

## Vampire Certificate Export

Vampire now emits a Megalodon-oriented certificate in S-expression form. The
certificate contains both legacy macro steps and newer `kernel_v1` metadata.

The certificate includes metadata for:

- input source formulas;
- source origin and source-map information;
- formula inputs and term inputs;
- rectification;
- FOOL and boolean formula transformations;
- ENNF and formula normalization;
- CNF projection;
- substitution and instantiation;
- resolution-like inferences;
- factoring;
- equality resolution;
- equality factoring;
- paramodulation and superposition;
- unit-resulting resolution;
- subsumption resolution;
- predicate definitions and folds;
- definition rewrite chains;
- AVATAR definitions, split clauses, component clauses, SAT/RUP-like data, and
  refutations;
- Skolemization contracts.

The most recent Vampire work is concentrated on Skolemization. It emits:

- top-level source/result formula children;
- top-level source/result quantifier metadata;
- source and result free-variable metadata;
- macro-edge records;
- macro-edge source and target formulas;
- macro-edge formula-shape metadata;
- macro-edge binder metadata;
- introduced Skolem symbols;
- replaced-variable names;
- witness terms and sorts where available;
- witness dependencies;
- branch contracts;
- branch source and target formulas;
- branch introduced-witness ownership;
- macro-edge counts.

This richer certificate is exactly the kind of data Vampire should provide.
The checker should not infer Skolem dependencies, branch ownership, or formula
children by broad search when Vampire already knows them.

## Megalodon Importer and Native Proof Terms

Megalodon consumes the certificate mainly in `src/vampire_cert_v1.ml`, with
supporting typed metadata in:

- `src/vampire_kernel_syntax.ml`
- `src/vampire_kernel_syntax.mli`
- `src/vampire_source_context.ml`
- `src/vampire_source_context.mli`

The native path constructs Megalodon's internal `Syntax.pf` proof terms and
checks them with Megalodon's proof checker. This is materially stronger than
generating textual scripts that may contain placeholder claims.

Important implemented capabilities include:

- parsing native certificate records;
- validating source maps;
- validating source origins;
- representing typed Skolem proof objects;
- validating Skolem top-level witness sets;
- validating branch contract identity;
- validating branch witness ownership;
- using typed child formulas rather than untyped string formulas where
  possible;
- constructing proof terms for selected clausal and preprocessing steps;
- refusing dynamic certificate-derived `Known` declarations on counted paths.

Important architectural debt remains:

- the importer is too large;
- the source/preprocessing layer and clausal kernel are not cleanly separated;
- the small kernel is not yet an isolated module;
- focused debug logic and proof construction logic live near each other;
- macro certificate handling and primitive proof-term handling are intertwined.

The current implementation is a useful bridge toward the intended architecture,
but it should not be allowed to keep growing indefinitely in this shape.

## Small Kernel Status

The intended small kernel is close in spirit to Ivy. It should contain simple
steps such as:

- input boundary;
- instantiate;
- alpha-rename;
- equality flip;
- resolution;
- factoring;
- equality resolution;
- equality factoring;
- paramodulation or superposition with explicit side, position, and direction;
- final empty-clause contradiction.

Some of these are already represented by native proof-term constructors or by
metadata that can support them. The branch has real proof-term evidence for a
core fragment and for selected focused examples.

The small kernel is not complete:

- many Vampire macro inferences still reach Megalodon as macro objects;
- AVATAR is only partially lowered;
- Skolemization is still a major preprocessing frontier;
- some substitution/opening/context operations still rely on broad importer
  logic;
- no final small-kernel certificate stream has replaced the legacy macro
  certificate.

The immediate technical direction should be:

- define the primitive IR as the qualification boundary;
- make Vampire emit that primitive IR explicitly;
- keep Megalodon checking deterministic and small;
- classify every non-primitive macro replay as transitional E4 or focused E3
  until it is lowered.

## Smolka-Style Transformations

The Smolka-style transformation problem is broader than clausal inference. It
includes formula transformations that happen before the clausal refutation
proper:

- rectification;
- lambda/FOOL processing where applicable;
- boolean normalization;
- negation pushing and ENNF;
- CNF projection;
- definitional CNF;
- choice and Skolemization;
- proof-producing treatment of generated definitions;
- projection from transformed formulas back to original source formulas.

The current work treats these as a separate proof-producing layer in design.
That is the right architecture: these transformations should not be disguised
as clausal kernel rules.

Implementation is partial:

- source and formula metadata exist for several transformations;
- Megalodon can parse and structurally validate many transformation records;
- selected transformations have native proof-term support;
- Skolemization has the most active detailed proof-object work;
- the layer is not complete or cleanly factored;
- broad E1 composition through all transformations is not implemented.

The key remaining challenge is compositionality. Each transformation should
produce a checked implication, equivalence, or contradiction-preserving proof
object, and those objects should compose from original source facts down to
the clauses consumed by the clausal kernel and then back to the original
theorem.

## Skolemization Status

Skolemization is the current frontier and the most important recent work.

Earlier states had several problems:

- the importer had to infer too much from before/after formulas;
- witness order could be wrong;
- dependent Skolem functions were hard to bind correctly;
- branch-local conjunction/disjunction/existential structure was opaque;
- generated Skolem definitions risked becoming assumptions;
- proof reconstruction had too many fallbacks.

The current Vampire-side output is much richer. It emits top-level and
branch-level Skolem proof contracts. Megalodon parses these into typed OCaml
records:

```ocaml
type skolem_formula_child = {
  skolem_child_role : string;
  skolem_child_formula : Syntax.tm;
}

type skolem_introduced_witness = {
  skolem_witness_symbol : string;
  skolem_witness_replaced_var : string;
  skolem_witness_term : Syntax.tm option;
}

type skolem_contract = {
  skolem_source_children : skolem_formula_child list;
  skolem_result_children : skolem_formula_child list;
  skolem_introduced_witnesses : skolem_introduced_witness list;
  skolem_macro_edge_count : int option;
}

type skolem_branch_contract = {
  skolem_branch_index : int;
  skolem_branch_parent_index : int option;
  skolem_branch_unit : string option;
  skolem_branch_binder_count : int option;
  skolem_branch_source_formula : Syntax.tm option;
  skolem_branch_target_formula : Syntax.tm option;
  skolem_branch_introduced_witnesses : skolem_introduced_witness list;
}

type skolem_proof_object = {
  skolem_proof_contract : skolem_contract option;
  skolem_proof_branches : skolem_branch_contract list;
}
```

Recent Megalodon commits consume this data by:

- threading optional typed Skolem proof objects into the Skolem CPS replay;
- checking top-level witness-set consistency;
- indexing branches;
- validating branch identity against unit/parent/index data;
- validating branch witness ownership;
- summarizing branch contracts in focused debug output;
- matching branch contracts against formula structure during CPS descent.

Focused target `233:4` produced the branch-contract diagnostics that led to
the current fix. The formerly failing step `u35` reported:

The successful fix was not a broad one-line proposition substitution. It was
to preserve the delayed sibling formula contract but shift the delayed

That fix guards the Skolem witness replacement path so that a witness whose
body still depends on local certificate context is not registered as a nullary
global delta/proof definition. The witness remains available as an explicit
Skolem replacement where it is in scope, but it no longer masquerades as a
closed global term.

## Name Recovery and Original Symbols

The user correctly noted that a human must be able to connect the reconstructed
proof skeleton to the theorem, lemmas, and symbols in the original Megalodon
development. The project handles this partly through source-origin metadata
and source-context records.

The intended model is:

- export original names and stable source identifiers from Megalodon to TPTP;
- have Vampire preserve and report those identifiers;
- import the certificate and resolve each source back to a concrete source
  fact in the original context;
- prove generated facts, such as supported `set` equalities, directly;
- avoid name-specific hacks and broad demangling guesses where structured
  origin metadata exists.

Current status:

- source-origin data exists and is checked for supported paths;
- source facts are classified into useful categories;
- some generated set facts are handled by reflexivity/conversion;
- demangling is not the primary trusted mechanism;
- final human-readable original-context scripts/proofs are not complete.

For expert review, the key question is not whether names can be printed nicely.
The key question is whether source identifiers resolve to the exact original
propositions in the original proof context. That is partially implemented, but
not yet complete.

## Trust Boundary

The trust boundary should be:

```text
Trusted:
  Megalodon kernel/checker
  fixed Megalodon library facts used as logical basis
  small certificate checker rules after review

Untrusted:
  Vampire search
  Vampire certificate contents
  Python scripts
  generated proof skeletons
  cached artifacts
  benchmark names
```

The certificate is evidence to be checked, not a source of new axioms.

Important enforced or intended invariants:

- no `aby`;
- no `admit`;
- no incomplete QED in qualifying runs;
- no bridge assumption;
- no certificate-derived `Known` in counted native paths;
- every source input must resolve to an original or generated source proof;
- every generated source fact must come with a proof, usually reflexivity or
  conversion for supported `set` equalities;
- every Vampire macro should either be lowered to primitive checked steps or
  remain non-qualifying;
- every native proof term should be checked by Megalodon.

The dynamic-`Known` issue identified by the audit is the most important trust
bug that has been corrected in direction. The system now has a diagnostic
environment variable for transitional known insertion, but counted native paths
must not use it.

## Risks

The main risks are:

- continued growth of `vampire_cert_v1.ml` into a large special-purpose
  theorem prover;
- continued growth of `MegalodonChecker.cpp` without an isolated primitive
  builder;
- confusing structural `PASS` results with proof reconstruction;
- spending too much time on broad tests while focused proof-term blockers
  remain;
- overfitting to the current benchmark library;
- relying on private encodings of equality or logic where Megalodon's library
  should be used;
- treating generated set facts or Skolem definitions as assumptions instead
  of producing proofs for them;
- trying to reconstruct Vampire's internal choices in Megalodon after the
  exact data has already been lost.

The controls should be:

- keep pass-count labels tied to E1/E2/E3/E4;
- keep broad runs parallel and checkpoint-only;
- keep Vampire timeout at 10 seconds;
- fail closed when metadata is absent;
- move proof-detailing into Vampire;
- isolate the primitive certificate format;
- require native proof-term checks for qualifying results;
- add a committed small E1 test gate before claiming progress toward 100.

## Chronology of the Work

This section reconstructs the project progression because the direction changed
substantially during the week. The history matters: some code and artifacts
exist because they were useful in earlier phases, but they should not be
mistaken for the target architecture.

### Initial Download and Branch Setup

The project began by downloading the Vampire repository and the Megalodon
repository locally under `/project`. The user requested a branch named
`vampire/megalodon` and later successive branches
`vampire/megalodon1` through `vampire/megalodon5`. Each new branch was created
from the then-current branch in both repositories. This kept the audit-driven
iterations separate enough for comparison while preserving the previous work.

The initial discovery task was to find Vampire's Lean proof reconstruction
code and understand whether it could be adapted directly. Vampire contained
Lean-oriented output and proof metadata code, but it was not a plug-in
translation layer that could simply be pointed at Megalodon. The code had to
be connected to Megalodon's syntax, binder representation, source context, and
proof checker. Still, the Lean path was useful because it showed where Vampire
already had proof-detailing hooks and what kinds of proof objects it could
print.

Megalodon was then inspected to understand:

- how theorem declarations are represented;
- how `aby` is implemented;
- how proof terms are represented as `Syntax.pf`;
- how the checker obtains the proposition of a proof term;
- how TPTP/THF export mangles names;
- how local source context is available during export;
- how `set` commands create generated equalities;
- how examples in `examples/form100` and `examples/hammer` are structured.

The user added `/project/Megalodon/examples/form100/SepE` as a representative
Megalodon proof style example. That example was important because it showed
the declarative `claim` style and made clear that a human-readable skeleton
with claims can be useful as an intermediate artifact. It did not change the
final trust requirements: admitted claims are not acceptable for the finished
reconstruction.

### Python Skeleton Phase

The early implementation leaned on Python. The Python code parsed or consumed
Vampire output, generated Megalodon claim skeletons, and helped map TPTP names
back toward Megalodon names. This was productive for exploration because it
quickly produced files a human could inspect and continue from.

The Python phase clarified several things:

- Vampire proofs contain enough high-level structure to identify many source
  formulas and inference steps.
- The raw TPTP names are not ideal for humans, but they can often be linked to
  source names if export metadata is preserved.
- A skeleton containing one claim per Vampire step is useful for diagnosis.
- Treating each Vampire step as a Megalodon `claim` with an `admit` placeholder
  is a good early visibility tool.
- It is not a final reconstruction method.

The user repeatedly pushed against all-or-nothing reconstruction. That was
correct. A fully admitted skeleton is not a proof, but it gives a human
something to inspect and gives implementers a visible measure of remaining
work. The project therefore learned from that phase while moving the trusted
path away from Python.

The limitation of the Python phase became clear quickly. For hard cases, the
Python code would have to infer Vampire's exact proof choices after the fact:
literal selection, equality direction, substitution, binder shifts, Skolem
dependencies, AVATAR split structure, and sort instantiations. That is the
wrong place to recover such information. Vampire knows these details during
proof construction. Megalodon should receive them as certificate data and
check them.

### Native Certificate Phase

The next phase added a native Megalodon-oriented certificate emitted by
Vampire. This was a major shift. Instead of trying to parse human-oriented
proof text or regenerate Megalodon scripts from Python, Vampire now emits a
structured S-expression certificate.

The early certificate included macro-level steps, source labels, and formula
payloads. Megalodon parsed this in OCaml, validated basic structure, and
started checking source maps. This enabled broad structural tests over many
problems and showed that Vampire could solve a selected 100-problem set under
the required timeout.

The important audit correction was that structural certificate acceptance is
not proof reconstruction. A certificate can be syntactically valid, source
labels can resolve, and the final proof can still be untrusted if inferences
are not justified by native proof terms. This led to the E1/E2/E3/E4
classification used in this report.

### Native Proof-Term Phase

The next major phase built native `Syntax.pf` proof-term construction in
Megalodon. This was the first genuinely kernel-adjacent reconstruction path.
Megalodon would parse certificate steps, build proof terms, and ask the
Megalodon checker for their propositions.

This phase produced a real core proof-term seed. Simple clausal inferences
could be replayed as proof terms rather than hidden assumptions. Focused tests
demonstrated proof-term checking for selected resolution, factoring,
paramodulation, equality symmetry, equality resolution, and substitution
shapes.

The audit then discovered a critical trust issue in the broader preprocessing
path: the importer could dynamically add a proposition of the form "parent
implies result" to the known theorem table and then use `Known` to apply it.
That made `check_propofpf` succeed, but only because the desired theorem had
been inserted as a trusted fact. This is the same trust problem as a bridge
axiom, just hidden inside the proof environment.

The project response was to make counted native paths reject
certificate-derived `Known` propositions unless the explicit diagnostic
environment variable
`MEGALODON_CERT_ALLOW_TRANSITIONAL_PREPROCESS_KNOWN=1` is set. That was an
important correction. Any result that needs the variable is now non-qualifying.

### Prover9/Ivy Pivot

The Prover9 source and prooftrans/Ivy route were then downloaded and analyzed.
That analysis changed the planning. Prover9's approach is not to ask the
checker to understand every large prover inference. It expands proof objects
into simpler steps before the checker sees them.

The lesson applied to this project is that Vampire should contain the
detailing pass. It should emit a smaller proof language with exact data, and
Megalodon should check that language. The current work is now pointed at that
architecture, although the implementation is not yet fully there.

This pivot also clarified that "port the Vampire Lean proof extensions" does
not mean copying Lean output syntax. It means using Vampire's proof-export
infrastructure and internal proof knowledge to emit proof terms or proof
objects that Megalodon can check. Lean and Megalodon are similar enough that
proof-term reconstruction is a sensible target, but Megalodon's source
context, syntax, and trusted basis are different.

### Skolem Contract Phase

The most recent phase focuses on Skolemization. This is unavoidable because
many real THF problems require Skolemization before the clausal proof. The
hard part is not merely replacing existential variables by Skolem functions.
The hard part is producing a proof term that justifies the transformation in
Megalodon's logic, with the right dependencies, binders, and branch-local
context.

Recent Vampire work emits much richer Skolem proof objects. Recent Megalodon
work consumes those objects, validates branch and witness invariants, and
uses them in a CPS-style proof reconstruction. The former target `233:4`
failure showed that this metadata had reached the right level of detail:
the failure was no longer a vague mismatch, but a specific binder-depth problem
inside a branch-local continuation. That focused problem is now fixed by
shifting delayed sibling formulas under the fresh binders introduced before
the delayed branch is replayed.

This is progress, but it should not be overclaimed. It closes one important
representative focused Skolem replay case, not the whole Skolemization
fragment across arbitrary libraries and proof shapes.

## Implementation Details by Component

### Vampire: Megalodon-Oriented Certificate Printer

The Vampire fork contains the proof-emission side. The relevant implementation
has grown around Megalodon-specific output code, including newer shared syntax
printing helpers. The current direction is to make this code less like a
one-off printer and more like a proof-detailing pass.

Current responsibilities on the Vampire side include:

- read the THF/TPTP problem;
- run the normal Vampire proof search;
- retain source formula names and origins;
- print parent/result formulas for certificate steps;
- print selected proof metadata for inferences;
- print `kernel_v1` records;
- print Skolem proof contracts and branch contracts;
- print sorts and variable metadata where available.

The best parts of the current Vampire work are the places where it emits exact
data that would be hard or impossible for Megalodon to recover reliably:

- equality rewrite positions;
- equality directions;
- selected literals;
- substitutions;
- generated Skolem symbol ownership;
- variable dependencies;
- source/result child formulas for macro transformations;
- branch indices and parentage.

The weakest part is module structure. Much of the work still lives in a large
implementation file rather than a clean proof-detailing pipeline. A better
structure would be:

```text
Vampire internal proof
  -> Megalodon proof-detailing IR
  -> primitive certificate IR
  -> S-expression rendering
```

The rendering layer should not be where inference semantics are invented.

### Megalodon: Certificate Syntax

`vampire_kernel_syntax.ml` and its interface now define typed records for
parts of the certificate. This is a significant improvement over ad hoc
association lists and stringly typed metadata.

The most useful recent records are the Skolem records. They make it possible
to validate:

- which witnesses were introduced;
- which variables they replaced;
- which branch introduced which witness;
- which macro edge owns which branch;
- whether top-level and branch witness sets agree;
- whether source and result child formulas are present and shaped correctly.

This typed boundary should be expanded. Expert review should probably insist
that all new qualifying metadata go through typed syntax modules instead of
being decoded inside the large importer.

### Megalodon: Source Context

`vampire_source_context.ml` is the beginning of the original-context bridge.
This is a necessary module because TPTP source formulas do not all correspond
to global theorem names. Some are local hypotheses, local definitions,
generated facts, or the negated conjecture.

The useful design shape is:

```ocaml
type source_proof =
  | GlobalKnown of string * tm
  | LocalHyp of int * tm
  | Definitional of tm * pf
  | Generated of tm * pf
```

The core requirement is that a certificate source id should resolve to a proof
of the exact source proposition in the exact Megalodon context. It is not
enough to recover a plausible human-readable name.

The source-context work has improved, but it must become the main E1 entry
point. In particular, source facts should be supplied as proof terms to the
certificate checker, and the final refutation should discharge the negated
conjecture to prove the original theorem.

### Megalodon: Large Certificate Importer

`src/vampire_cert_v1.ml` remains the central implementation file. It contains:

- certificate parsing;
- source-map checking;
- native formula conversion;
- proof-term construction;
- clausal inference replay;
- preprocessing transformation replay;
- Skolem CPS replay;
- AVATAR replay;
- debug output;
- trust policy checks;
- transitional legacy paths.

This file has carried the project forward, but it is too large to remain the
long-term architecture. The expert should treat its current state as a
migration stage. The most important implementation rule for the next phase is
to prevent new proof reconstruction logic from being added there unless it is
part of extracting a smaller module.

Suggested eventual split:

- `vampire_certificate_parse.ml`
- `vampire_certificate_source.ml`
- `vampire_kernel_syntax.ml`
- `vampire_kernel_check.ml`
- `vampire_kernel_elab.ml`
- `vampire_preprocess_smolka.ml`
- `vampire_preprocess_skolem.ml`
- `vampire_avatar_check.ml`
- `vampire_original_context.ml`

The exact names are less important than the separation:

- parsing is not checking;
- source resolution is not clausal inference;
- preprocessing is not the clausal kernel;
- proof-term elaboration is not certificate trust policy;
- diagnostics are not proof construction.

## Status by Inference and Transformation Family

### Formula Input and Term Input

These are the boundary between original Megalodon facts and the exported THF
problem. They are more important than they look. If these are not proved from
the original context, the rest of the certificate can at best prove a theorem
about the exported problem, not the original source theorem.

Current status:

- source labels and origin metadata are parsed;
- semantic checks exist for supported source formulas;
- source categories are represented;
- generated set-reflexivity facts are partly handled;
- full original-context proof supply is incomplete.

Required next work:

- every `formula_input` should receive a source proof;
- every `formula_term_input` should receive a source proof or generated proof;
- unresolved source facts should fail E1 runs;
- source proofs should be passed into the native checker rather than recreated
  as local trusted names.

### Resolution

Resolution is part of the small clausal kernel and has focused proof-term
support. The current proof-term approach can handle selected simple cases and
some preprocessing reuse.

Remaining issues:

- all resolution uses should come with exact selected literal data;
- substitutions should be explicit primitive instantiation steps when needed;
- resolution should not be hidden behind macro implications;
- AVATAR component resolution must be separated from SAT reasoning.

### Factoring

Factoring has focused support and appears in core proof-term examples. It
should remain a primitive clausal rule with explicit literal identity and
substitution data.

Remaining issues:

- ensure equality and non-equality factoring are both covered;
- keep proof-term construction independent of literal-order accidents;
- require exact Vampire metadata when variable instantiation is involved.

### Equality Resolution and Equality Symmetry

Equality resolution and symmetry are partially supported. These are good
small-kernel candidates because they are simple and reviewable.

The design should use Megalodon's equality directly. Any private equality
encoding should be treated as legacy compatibility or a parsed representation
that elaborates to real Megalodon equality.

Remaining issues:

- proposition-valued equality needs careful treatment;
- equality orientation in formula transformations remains a source of
  failures;
- conversion and definitional unfolding should be explicit.

### Paramodulation and Superposition

Paramodulation/superposition are central for real Vampire proofs. The user
asked specifically why only superposition was being considered and whether
Lean/Dedukti modes already provide richer detail. The answer is that all
complex inferences should be detailed, not only superposition. Superposition
is prominent because it is common and difficult, but it should be part of a
general primitive-detailing pass.

Required data:

- equality parent id;
- main parent id;
- selected equality side;
- selected literal;
- rewrite position;
- rewrite direction;
- substitution;
- result clause;
- sorts of variables and terms;
- retained variables and opening/closing information.

Current status:

- metadata exists for some rewrite/superposition shapes;
- focused failures showed retained-variable opening issues;
- broad Megalodon-side guessing is not the right solution;
- the primitive IR should make the rewrite operation explicit.

### Substitution and Instantiation

Substitution is a cross-cutting issue. Earlier code sometimes treated
substitution as a macro surface constructor. The Prover9/Ivy model suggests
that instantiation should be a primitive step with an exact substitution list
and sorts.

Current status:

- Vampire emits substitution metadata in many places;
- Megalodon consumes some of it;
- some failures were caused by context opening and retained variables rather
  than the substitution mapping itself.

Required next work:

- define one canonical primitive instantiation format;
- ensure all substitutions carry sorted variables and terms;
- make parent theorem opening a specified operation;
- test closed parents, retained-variable parents, and shadowed names.

### Predicate Definitions and Folds

Predicate definitions and folds are preprocessing/definition-management steps,
not core clausal inferences. They should produce proof terms by definitional
unfolding or fixed definitional principles.

Current status:

- metadata and structural handling exist;
- older paths could rely on transitional known implications;
- qualifying proof-term support is incomplete.

Required next work:

- prove definition introduction conservatively;
- prove fold/unfold by conversion where possible;
- avoid treating definition links as trusted certificate claims.

### Rectification, ENNF, and CNF

These are Smolka-style transformation steps. The right treatment is not to
make them large clausal kernel rules, but to build a proof-producing
preprocessing layer.

Current status:

- metadata is present for many transformation steps;
- selected transformations can be structurally checked;
- native proof support is partial;
- older pass counts involving transitional knowns must be reclassified.

Required next work:

- define transformation lemmas using Megalodon's logical basis;
- implement proof-term constructors for the actual transformation shapes in
  the corpus;
- emit enough Vampire metadata to avoid guessing;
- compose transformation proofs into clause provenance.

### Skolemization

Skolemization is discussed separately above because it has been the most
important recent preprocessing frontier. It belongs in the preprocessing
layer, not the clausal kernel. It requires classical choice or equivalent
library support and exact dependency tracking.

Current status:

- rich metadata exists;
- typed records exist;
- branch invariants are checked;
- the focused `233:4` CPS/binder-depth mismatch is fixed;
- general Skolemization coverage remains incomplete.

Required next work:

- specify the proof-term shape independently of the current implementation;
- keep branch-local continuation depth covered by regression tests;
- test dependent and independent witnesses;
- test multi-branch conjunction/disjunction cases;
- test set-generated source facts interacting with Skolemization.

### AVATAR

AVATAR combines clause splitting with propositional SAT reasoning. It should
not be hidden as trusted implications. Either Vampire should lower the
propositional part into a small proof object, or Megalodon should check a
separate SAT proof language.

Current status:

- split definitions and component metadata exist;
- some focused split-definition/component cases pass;
- SAT-subsumption metadata exists;
- no complete AVATAR proof object is checked for the full corpus.

Required next work:

- decide whether SAT reasoning is lowered by Vampire or checked separately;
- ensure split atoms are conservative definitions;
- prove component clauses from split definitions and clausal parents;
- reject opaque AVATAR macro steps in qualifying runs.

## Current Assessment of Direction

The direction is now mostly right, but execution needs stricter boundaries.

Right direction:

- move exact proof detail into Vampire output;
- parse typed certificates in Megalodon;
- build native `Syntax.pf` proof terms;
- use Megalodon's own equality and classical library;
- treat generated source facts as proof obligations;
- classify evidence honestly.

Still risky:

- implementing too much in the large OCaml importer;
- adding rich macro reconstruction instead of primitive lowering;
- allowing focused debugging to become benchmark-specific;
- delaying original-context composition until too late;
- relying on broad structural pass counts for confidence.

The next implementation work should therefore be narrow but structural:

- fix the current Skolem CPS non-propositional parent-instantiation blocker;
- extract or specify the relevant primitive/source-preprocess interface while
  doing so;
- immediately convert the success into an original-context test, not just an
  exported-bound focused pass.

## Bottom Line

The project has made real progress, especially in moving away from Python
proof reconstruction and toward Vampire-emitted proof detail plus Megalodon
native proof-term checking. The latest work on Skolem contracts is aligned
with the audit recommendation to obtain exact data from Vampire rather than
guessing it later.

The project is still not finished. There is no qualifying 100-theorem E1
result, and there is not yet even a committed 10-case E1 milestone. The main
current frontier is Skolem CPS parent-step instantiation in the Smolka-style
preprocessing layer, with regenerated `hammer.1009.43/u98` as the most
concrete current example.

The best next work is not another broad pass-count push. It is to close the
focused preprocessing proof-term frontier, then establish a small
original-context gate, while continuing the architectural migration toward a
Prover9/Ivy-style primitive certificate emitted by Vampire and checked by
Megalodon.

## Late July 18 Final Addendum

After the committed `c3be796` state described earlier, one additional
Megalodon-side narrowing fix was committed as `63513c3 Keep local Skolem
witnesses scoped`. It should not be overclassified as final project evidence,
but it is useful for the expert review because it removes a concrete
well-scopedness bug and narrows the next failure.

The fix addresses regenerated `hammer.1009.43/u98`, a larger
Skolemization/preprocessing example whose current certificate already includes
Vampire-emitted rectification metadata. The initial regenerated failure was a
native proof-term well-scopedness error:

```text
u98: native preprocess proof-term checker built an ill-formed proof term
Term de Bruijn index 11 is out of bounds for context length 11
```

The committed patch has two parts:

- the direct Skolem formula proof builder now carries an explicit local binder
  depth when building epsilon predicates, so proposition views under newly
  opened binders use `checked_formula_prop` at the correct depth;
- Skolem witness definitions are now added to the arity-zero `proof_delta` and
  `definition_delta` tables only when the closed witness is actually scoped
  under the global context. Context-dependent epsilon witnesses are retained
  as Skolem witness replacements, but they are not installed as nullary global
  definitions.

The second point is important. The previous behavior could register a witness
whose apparent name was nullary while its body still depended on local
certificate context. That is exactly the kind of hidden context leak the
audits warned against: it makes later proof terms look closed even when their
de Bruijn indices are only meaningful under a local binder stack.

The current focused recheck artifact is:

```text
/project/tmp/recheck_1009_scoped_only_225537
```

The result moved past the original fatal out-of-bounds proof-term error. The
debug stream now includes:

```text
u98: native preprocess skolem kept context-dependent witness sK0 out of
     arity-zero delta tables
u98: native preprocess Skolem shadow replay reached empty clause
u98: native preprocess Skolem CPS using shadow replay continuation
u98: native preprocess Skolem CPS skipped:
     Vampire_cert_v1.Error("u98: native preprocess Skolem CPS cannot open
     non-prop parent step variable")
```

This means the scoped-witness guard is a real narrowing step, not a complete
solution. The immediate next blocker is that the Skolem CPS replay currently
opens parent step variables using a proposition-only dummy. Larger proofs such
as `u98` have parent step variables of non-propositional type, including
`set`. The current code therefore refuses to instantiate them and falls back
to the older final-refutation assembly, which then fails with an implication
argument mismatch involving original global symbols such as `#A`/`#f` versus
bound de Bruijn variables such as `_14`/`_12`.

The right follow-up is not to add name-specific rewrites for this benchmark.
The follow-up should extend the explicit proof object/boundary contract so
that parent step variables are instantiated from typed Vampire-owned data:
their sorts, their parent/result roles, and their relationship to the
source/result formula variables. A conservative implementation may use typed
default witnesses only as a diagnostic, but a qualifying reconstruction path
should prefer the explicit source/result variable contract or a lower-level
Smolka-style transformation object.

This late addendum slightly changes the final frontier statement:

```text
The former 233:4 Skolem sibling/binder-depth blocker is fixed in committed
code. The current live blocker is regenerated hammer.1009.43/u98: scoped
epsilon witnesses no longer escape into arity-zero globals, but Skolem CPS
still needs a general typed treatment of non-prop parent step variables and
their source/result binder orientation.
```
