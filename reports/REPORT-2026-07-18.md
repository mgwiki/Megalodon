# Vampire to Megalodon Proof Reconstruction: Project Report

Date: 2026-07-18

This report summarizes the current state of the Vampire-to-Megalodon proof
reconstruction project for expert review. It is intended as a continuation of
the reports from 2026-07-12 through 2026-07-17 and should be read together
with their audits, the audit responses, the Prover9/Ivy analysis, the
Smolka-style transformation notes, and the current `vampire/megalodon5`
branches in both repositories.

The report is deliberately conservative. The project has made substantial
technical progress, but it has not reached the original deliverable: at least
100 representative Megalodon theorems exported as THF/TPTP, proved by Vampire
within the agreed timeout, and reconstructed back as Megalodon proofs of the
original theorems with no `admit`, no `aby`, no incomplete QED, no hidden
bridge assumptions, no certificate-derived `Known` theorems, and no private
replacement for Megalodon's equality or logical constants.

The strongest current progress is in the proof-object pipeline: Vampire now
emits richer kernel metadata for important proof families, Megalodon has
fail-closed native proof-term checking for a growing transformation/core
fragment, and the current focused blockers are specific proof-term construction
bugs rather than broad absence of certificate data. The main unfinished work is
still architectural: the project needs a real typed Vampire primitive IR, an
extracted small Megalodon kernel checker/elaborator, a source-context API that
glues a checked refutation back to the original Megalodon theorem, and a clean
proof-producing layer for Smolka-style transformations.

## Executive Summary

The project is not finished. It is now on a better path than at the beginning
of the week, but the final E1 goal has not been achieved.

The central architectural correction remains the one forced by the audits:
proof reconstruction must not be a Python or OCaml heuristic prover that
rediscovers Vampire's inferences from printed clauses. The qualifying path must
look like the Prover9/Ivy path:

```text
Megalodon source theorem and local proof context
  -> THF/TPTP export with source/origin metadata
  -> Vampire proof search with timeout <= 10s
  -> Vampire-side expansion into primitive certificate records
  -> Megalodon small checker and Syntax.pf elaboration
  -> proof of the original Megalodon theorem
```

The project has partially moved to this shape:

- The Python reconstructor is no longer a qualifying path.
- Transitional preprocessing proof terms that install certificate-derived
  `Known` implications are not counted as reconstruction evidence.
- Megalodon now has native `Syntax.pf` proof-term checking for a real fragment
  of the certificate language.
- Vampire now has a `MegalodonKernelSyntax` boundary and migration-stage
  primitive step records for several macro inferences.
- Recent Vampire commits emit richer primitive metadata for unit-resulting
  resolution, subsumption, SAT-subsumption, predicate definitions, and
  rectification variable maps.
- Recent Megalodon commits use this metadata to replay more of Skolemization,
  CNF projection, AVATAR component/split reasoning, and source/preprocessing
  transformations without dynamic `Known`.

## Objective and Success Criterion

The objective is to port Vampire's proof reconstruction work to Megalodon. The
original motivation was Vampire's Lean-oriented reconstruction code: Lean and
Megalodon are both proof-term systems, so the information Vampire already has
when it derives a proof should be sufficient to emit a proof object that
Megalodon can check.

The final deliverable is stronger than "Vampire found a proof" and stronger
than "Megalodon parsed a certificate." The final deliverable is:

```text
Given a Megalodon theorem or proof obligation, export the relevant THF/TPTP
problem, run Vampire, import the Vampire certificate, and produce a Megalodon
proof term for the original theorem in the original source context.
```

For a result to count, it must satisfy all of the following:

- no `admit`;
- no `aby`, since `aby` is implemented as admission;
- no `-allowincompleteqed`;
- no hidden bridge premise;
- no certificate-derived `Known` theorem introduced dynamically;
- no private equality;
- no private logical constants when Megalodon's library provides the relevant
  constants and principles;
- no hardwired names from the current benchmark library;
- no Python reconstruction in the qualifying proof path;
- no broad Megalodon-side search to rediscover data Vampire could have emitted.

Classical logic may be assumed. The project assumes that `xm` and the standard
Megalodon library constants for `False`, disjunction, equality, propositional
reasoning, and related classical facts are available in the source context.

The input side is THF/TPTP. The project should not optimize for synthetic FOF
examples at the expense of real Megalodon THF exports. Testing should use
parallel batch workflows, a Vampire timeout of at most 10 seconds, and
temporary artifacts under `/project/tmp`.

## Evidence Classes

The reports now use evidence classes to avoid ambiguous pass counts.

E1 is the goal: an original Megalodon theorem is reconstructed in its live
source context with no admissions, no bridge assumptions, no certificate-derived
`Known`, and no private logical basis.

E2 is a closed native `Syntax.pf` proof of a live Vampire certificate at the
exported THF/certificate boundary. This is real proof-term evidence, but it is
not yet composed into the original theorem command.

E3 is a focused or synthetic native proof-term check for a small-kernel rule or
a limited transformation family.

E4 is structural evidence: certificate parsing, metadata validation, source-map
validation, live Vampire success, integration testing, and transitional
diagnostics that do not prove every inference by native proof terms.

Under this classification:

- `PASS 100` from `STRICT_CERT_V1=1` live runs is E4.
- Preprocessing runs that enable transitional `Known` facts are E4.
- The current broad 88-case fail-closed `PREPROCESS_PF_PASS` frontier is useful
  proof-term evidence at the exported certificate boundary, but it is not E1.
- Focused live hammer proof-term passes such as `hammer.10640.42` are E2-like
  evidence for the exported certificate boundary.
- No current broad result establishes E1.

This discipline is essential. Much of the project's earlier confusion came
from treating admitted skeletons, structural certificate checks, script checks,
and proof-term checks as comparable "passes."

## Audit-Driven History

The July 12 report described the first working path: Vampire emitted a rich
Megalodon-oriented proof object and a Python reconstructor generated
source-linked Megalodon proof skeletons. That work was useful because it
created benchmark artifacts, source maps, skeletons, and concrete failure
examples. It was not a final reconstruction system. The audit correctly found
that the Python code was becoming an external prover with name recovery,
library-specific recognizers, equality-chain search, quantifier heuristics,
and bounded proof search.

The July 13 report accepted the need for a smaller certificate, but the branch
still let derived Vampire clauses become assumptions through an input-like
mechanism. A generated proof could be free of textual `admit` while still being
a theorem from extra derived premises. The audit identified this as a trust
boundary failure.

The July 14 report moved toward a native S-expression certificate and an OCaml
importer. This improved operational reliability and reduced the role of
Python. The audit found that strict mode still allowed bridge premises and that
source linking was too label-based: a certificate could attach a complex
derived clause to a plausible source name without semantically proving that it
was the exported source formula.

The July 15 report introduced more meaningful closed checks. Closed mode
rejected bridge and derived premises, and supported source formulas were
structurally compared against the exported THF formulas. The audit accepted
some closed results as meaningful, but warned that the main implementation was
still turning into a broad replay engine rather than a small proof-term
checker.

The July 16 report introduced the native `Syntax.pf` direction:
`corepfcheck` and `preprocesspfcheck`. The audit accepted the small clausal
core seed but found the major hidden-trust bug: the broader preprocessing path
could construct a proposition, dynamically insert it into the proof checker's
`Known` table under a generated name, and then apply it. That was equivalent to
a hidden axiom.

The July 17 branch implemented the trust-boundary reset. Counted proof-term
modes fail closed when a step would require certificate-derived `Known`. The
old behavior is retained only as a diagnostic mode and must be reported as
structural evidence. The same branch began extracting a kernel vocabulary:
`src/vampire_kernel_syntax.ml` on the Megalodon side and
`Shell/MegalodonChecker/MegalodonKernelSyntax.{hpp,cpp}` on the Vampire side.

The July 18 state continues that direction, but it also shows the limits of
the current extraction. The frontiers now require a real transformation layer,
not more ad hoc replay embedded in `vampire_cert_v1.ml`.

## What Has Been Implemented

### THF/TPTP Source Metadata

Megalodon exports THF/TPTP problems with more origin information than at the
start of the project. Certificate inputs can now be connected to Megalodon
source locations, local commands, and proof obligations. The certificate
checker distinguishes certified `vampire` commands from legacy `aby`
commands, which matters because `aby` is not acceptable in final scripts.

The strict checker no longer trusts labels alone. For supported source
formulas it parses and compares the exported formula shape. Unsupported source
syntax fails closed in counted modes rather than becoming a generic input
assumption.

The source-context classification now distinguishes:

- global known facts;
- local hypotheses;
- local definitions;
- generated facts;
- `set`-generated equalities;
- conjecture facts and the negated conjecture boundary;
- unresolved facts.

This is still not final E1 reconstruction. The missing step is to turn this
classification into an actual proof-source API that resolves each certificate
source id to a Megalodon proof object in the current proof state. For example:

```text
GlobalKnown     existing theorem, lemma, or definition in Megalodon
LocalHyp        local proof-context hypothesis
Definitional    local/global definitional equality plus proof
Generated       generated fact plus proof, such as set reflexivity
Conjecture      negated conjecture boundary
Unresolved      counted-mode failure
```

This API must preserve local hypothesis indices, binder scopes, local
definition shifts, theorem identities, and the final conversion from a
refutation of the negated conjecture to the original positive theorem.

### Native Certificate v1

Megalodon has a native certificate-v1 importer and checker in OCaml. It reads
Vampire S-expression certificates, validates schema and metadata, validates
source mapping where required, and elaborates supported fragments into native
`Syntax.pf` proof terms.

The important modes are:

- strict structural validation;
- closed textual/script validation;
- `corepfcheck`, the small native clausal proof-term seed;
- `preprocesspfcheck`, the broader source/preprocessing proof-term path;
- transitional preprocessing diagnostics, which are not counted.

The proof-term paths construct actual `Syntax.pf` terms and call Megalodon's
proof checker. This is the right technical foundation. The main weakness is
that the implementation is still concentrated in `vampire_cert_v1.ml`. The
expert should treat every new large replay branch in that file as suspect
unless it is being moved toward a small typed checker interface.

### Fail-Closed Handling of Known Theorems

The largest trust-boundary fix is that counted proof-term modes reject
certificate-derived `Known` facts. The previous bug looked like this:

```text
construct proposition P -> Q
invent name vampire_some_step_uNNN
add Known vampire_some_step_uNNN : P -> Q
apply Known vampire_some_step_uNNN to the proof of P
```

This checked as a native proof term only because the desired implication had
just been inserted into the proof environment. It was a hidden bridge
assumption.

The current counted path permits only a fixed reviewed logical basis from the
Megalodon environment, such as classical/propositional principles and
choice-like facts required for Skolemization. Certificate-derived theorems with
the generated `vampire_` prefix are rejected in counted proof-term modes.

This is why the 88-case fail-closed frontier is meaningful despite not being
E1. It is not just the old 94-case transitional frontier with a new name.

### Vampire Kernel Syntax Boundary

On the Vampire side, `MegalodonKernelSyntax` now owns more of the certificate
vocabulary and `kernel_v1` metadata rendering. It defines migration-stage
objects such as:

- primitive expansion records;
- primitive step records;
- kernel step records;
- rendered parent records;
- rendered conclusion records;
- rule-to-required-primitive contracts.

On the Megalodon side, `vampire_kernel_syntax.ml` defines the corresponding
rule names and contracts. Unsupported `kernel_v1` rule names fail closed, and
there are negative fixtures for invalid rule names.

This is directionally correct, but it is not yet the typed primitive IR the
audits recommended. Many records still carry rendered strings instead of typed
Vampire objects. The target remains a proper internal structure:

```text
PrimitiveStep {
  id;
  rule;
  parents;
  conclusion clause/formula;
  selected literal indices;
  pivot data;
  substitutions;
  rewrite position and direction;
  equality side terms;
  variable and symbol sorts;
  Skolem introduced symbol and dependencies;
  source/preprocess payload for non-clausal transformations;
}
```

The important implementation rule should now be strict: Vampire inference
handlers should build primitive records first, and a single printer should
serialize them. Direct string assembly in individual inference handlers should
be migration-only.

### Primitive Expansion Metadata

Vampire now emits richer primitive metadata for several macro families. This
is the clearest implementation response to the Prover9/Ivy recommendation.

Implemented or partially implemented metadata includes:

- unit-resulting resolution primitive chain summaries;
- primitive final result clauses for URR;
- primitive parent and result metadata;
- subsumption fast-path primitive result metadata;
- subsumption-resolution primitive step metadata;
- SAT-subsumption primitive chains;
- equality symmetry metadata;
- substitution metadata;
- resolution pivot metadata;
- predicate definition metadata;
- rectification variable maps;
- AVATAR component, definition, split, dependency, and refutation metadata.

The recent `hammer.10640.42/u251` failure showed why this matters. The older
Vampire certificate had a rendered SAT-subsumption expansion but lacked enough
structured primitive records for Megalodon to validate the final result. Commit
`0ebdf2a67` fixes this by making the SAT-subsumption path emit a six-step
primitive chain:

```text
substitute
equality_symmetry
equality_symmetry
resolve
factor
substitute
```

The fresh focused certificate then moved past `u251` and exposed later
Megalodon-side proof-term issues, which were partly fixed by the latest
Megalodon commits.

### Skolemization

Skolemization has moved from being a vague global blocker to a set of concrete
frontiers. The current code can prove some Skolem transformations with
conservative definitions and choice-like principles from the Megalodon logical
basis. It no longer simply installs a Skolem implication as a generated known
theorem in counted mode.

Implemented representative pieces include:

- direct existential-choice Skolem proof terms for focused cases;
- compact Skolem definition replay when the parent formula supplies the source;
- Skolemization under conjunctive formula contexts by projecting the changed
  conjunct, applying the recursive Skolem proof, preserving the unchanged
  conjunct, and rebuilding the conjunction;
- parent-formula matching for multiple introduced symbols using Vampire's
  `introduced_i_witness_term` and `parent_i_formula` metadata;
- dependency-context candidate selection that chooses a witness whose body
  actually covers the relevant context variables;
- backtracking of CNF universal projection witnesses when a quantified clause
  can be matched by more than one same-sort variable.

The last two bullets correspond to the most recent Megalodon commits:

```text
102b45a Select Skolem witnesses by dependency context
3309b12 Backtrack CNF universal projection witnesses
```

These are proof-term-side fixes. They are deliberately local: they use Vampire
metadata and proof-term checking rather than hardwiring concrete theorem names.

The remaining Skolem/frontier issues include:

- formula-orientation steps around nested existentials and Boolean/equality
  structure (`hammer.1009.43/u98`);
- formula-orientation or dependency context around `hammer.11145.52/u240`;
- the need to separate actual Vampire Skolem dependencies from extra variables
  that appear only because the Megalodon checker has opened a formula under a
  larger proof context.

The fix should continue to rely on explicit Vampire data: quantified prefix,
dependency vector, introduced symbol, symbol sort, body formula, before/after
formula, and the choice/definition proof.

### AVATAR

AVATAR remains outside the small clausal kernel. It needs either a separate
checked AVATAR layer or a SAT/RUP-like proof object. However, the project now
has representative native proof-term support for several common AVATAR shapes.

Implemented representative pieces include:

- split dependency metadata;
- AVATAR component metadata;
- AVATAR definition metadata;
- AVATAR split metadata;
- AVATAR refutation metadata;
- replay of quantified two-component split families;
- recovery of metadata-only split definitions from split dependencies;
- replay of component clauses with one or more literals instead of only a
  single component literal;
- replay of mixed split-only result clauses that combine old split literals,
  positive component splits, and complemented negative ground components.

The focused `hammer.10640.42` proof is the main success story here. The branch
now moves this certificate past multiple AVATAR blockers:

- `u260`, a multi-literal quantified AVATAR component;
- `u279`, a mixed split-only result clause;
- later CNF projection issues after the split reasoning.

The current `hammer.10785.27/u287` blocker shows that AVATAR is still not
complete. The certificate states an `avatar_definition` where the proposition
has the shape:

```text
(split_3 -> forall X0:set, component(X0))
and
(forall X0:set, component(X0) -> split_3)
```

The source component clause is quantified and includes a negative split
literal. The current proof-term builder constructs a proof whose first
implication has the wrong target:

```text
expected: split_3 -> component_formula
actual:   split_3 -> split_3
```

This should be fixed as a general AVATAR definition proof for quantified
component clauses, not by recognizing `split_3` or the concrete benchmark. The
proof must open the component variables, use the component clause, discharge
the negative split branch by contradiction with the assumed split, and then
close the universal component proposition.

### CNF Projection and Formula Orientation

CNF projection and formula orientation are active transformation-layer
frontiers. The recent `3309b12` change fixed one class of universal projection
witness selection by backtracking over same-sort result variables. This was
needed because a deterministic first-same-sort choice could produce a
well-typed but wrong proof term.

The remaining orientation failures should not be solved by adding
benchmark-specific formula rewrites. Vampire should emit enough detail to
explain the transformation: source formula, target formula, relevant equality
or logical equivalence, direction, and any binder/renaming data. Megalodon
should check that proof object locally.

The currently known focused orientation frontiers are:

- `hammer.1009.43/u98`;
- `hammer.11145.52/u240`.

Both appear in the source/preprocessing layer, not in the final clausal kernel.

### Equality

The project should use Megalodon's equality directly. Earlier private equality
experiments are not the final direction and should not reappear in counted
proofs.

Vampire certificates may contain equality-like wrappers because of TPTP/FOOL
printing and proposition-valued equality. Those wrappers should be interpreted
as exported syntax that maps back to Megalodon's equality and proposition
equality principles. They are not a new equality theory.

For `set`-generated equalities, the source context should classify the fact as
generated/definitional and prove it by reflexivity or conversion. It should
not create a fresh source claim.

### The Megalodon `vampire` Command

Megalodon has a separate `vampire` proof command path. The purpose is to avoid
silently falling back to `aby`, incomplete QED, target skipping, or script
admission. The command should eventually be the user-facing route for E1
proofs.

At present, this command infrastructure is useful but not sufficient. It still
needs complete original-context composition. The native certificate proof term
must be connected to the exact theorem and proof state from which the THF
problem was exported.

## Problems Encountered

### 1. Misleading Pass Counts

The most damaging recurring problem was ambiguous success accounting. Early
reports mixed admitted skeletons, structural passes, bridge-premise scripts,
and real proof-term checks. The audits forced a stricter taxonomy. Future
reports should continue using E1-E4 and should state exactly which command was
run.

### 2. Python and Megalodon-Side Heuristics

The initial Python translator was useful for exploration, but it was not a
final path. It recovered names, guessed transformations, searched for equality
chains, and recognized benchmark-specific proof patterns. That is exactly the
wrong long-term architecture.

Some of the same risk exists in the OCaml importer. When a new failure appears,
the tempting short-term fix is to add another recognizer to
`vampire_cert_v1.ml`. Sometimes a local proof-term constructor is necessary,
but the controlling principle must remain: if Vampire knew the data, Vampire
should emit it; Megalodon should check it.

### 3. Monolith Growth

The project has begun extracting kernel syntax, but the main implementation
still lives in large files:

```text
Megalodon: vampire_cert_v1.ml
Vampire:   MegalodonChecker.cpp
```

This remains an architectural risk. The expert should be skeptical of any plan
that raises frontier counts by adding thousands of lines to these files.

The desired extraction is:

```text
vampire_kernel_syntax.ml
vampire_kernel_check.ml
vampire_kernel_elab.ml
vampire_source_context.ml
vampire_transform_check.ml
```

on the Megalodon side, and a typed primitive certificate builder on the Vampire
side.

### 4. Missing Vampire Detail

Many difficult bugs arose because Megalodon tried to rediscover information
that Vampire already had:

- substitutions;
- selected literals;
- pivot positions;
- equality directions;
- rewrite positions;
- result clauses;
- binder renamings;
- variable sorts;
- Skolem dependencies;
- source/preprocess parent formulas;
- AVATAR split/component dependencies.

The rectification variable-map fix is the preferred model: Vampire emitted the
exact mapping, and Megalodon stopped guessing. The SAT-subsumption primitive
metadata fix follows the same pattern.

### 5. Source/Preprocessing Complexity

Real Megalodon exports are not simple clausal first-order problems. They pass
through definitions, FOOL encodings, formula transformations, Skolemization,
CNF projection, and often AVATAR. These transformations cannot all be hidden
inside a clausal kernel. They need a separate proof-producing layer.

This is the main Smolka-style lesson for the project. The transformation layer
should not be another string-based replay script. It should be a typed sequence
of local transformations, each checked by Megalodon as a proof term.

### 6. Hidden Trust

Bridge assumptions first appeared as explicit derived inputs, then as dynamic
`Known` facts in native proof terms. The current counted path rejects the
second form, but this must remain mechanically enforced. It is the easiest
class of defect to reintroduce.

### 7. Testing Cost

Long sequential Vampire runs wasted time. The process has improved:

- export many problems at once;
- run Vampire in parallel;
- use at most 10 seconds per Vampire problem;
- cache outputs under `/project/tmp`;
- do checker-only iteration on cached certificates when possible;
- focus on live frontiers rather than repeatedly rerunning known-unsolved
  Vampire cases.

The next broad proof-term run should be parallel and should use the current
Vampire binary, but it should be run only when it will answer a meaningful
question.

## Relation to Prover9/Ivy

The Prover9/Ivy analysis remains the best architectural guide. Prover9 does
not ask Ivy to rediscover unifiers or paramodulation sites from a printed
proof. Prover9 expands its own proof internally, while it still has access to
its clause, unification, and rewriting machinery. It then prints a smaller
proof object for Ivy to check.

The corresponding Vampire/Megalodon design is:

- Vampire macro inferences should be expanded inside Vampire.
- Explicit instantiation steps should precede primitive resolution and
  paramodulation.
- Resolution should include exact parent ids and pivot literal positions.
- Paramodulation/superposition should include exact equality side, target
  position, direction, and substitutions.
- Factoring should be explicit and local.
- Equality symmetry and equality resolution should be separate small rules.
- The final primitive clause should be checked inside Vampire against the
  actual derived child clause before printing.
- Megalodon should receive a proof object it can check without replaying
  Vampire's search.

The project is partially on this path. URR and subsumption families now have
primitive metadata. SAT-subsumption now emits a detailed chain. The kernel
syntax extraction gives the primitive IR a place to grow.

The project is not fully on this path yet. Too much of the data remains in
rendered string fields, and too much replay logic still lives in
Megalodon-side OCaml. The next expert review should ask, for every new fix:

```text
Did this add precise Vampire-emitted proof data and a small checker,
or did it add another Megalodon-side recognizer?
```

The former is progress. The latter is drift.

## Relation to Smolka-Style Transformations

The Smolka-style transformations matter because the original theorem is not a
clause set. Between the Megalodon theorem and the Vampire clausal proof there
is a chain of transformations. A trustworthy reconstruction must prove this
chain, not merely assume the clauses.

For this project, the transformation layer should cover:

- source formula input;
- definition input, fold, and unfold;
- rectification and alpha-renaming;
- formula-term copy and formula copy;
- FOOL Boolean lifting and Boolean equality conversions;
- ENNF and propositional normalization;
- CNF literal and formula projection;
- Skolemization using conservative definitions and choice;
- AVATAR split/component/refutation reasoning;
- final refutation-to-original-goal composition.

The current implementation has representative native proof-term support for
some of these classes. Predicate-definition fold chains, rectification
variable maps, compact Skolem definitions, conjunction-context Skolemization,
some CNF projections, and several AVATAR split/component cases are now
proof-producing in focused examples.

The transformation layer is not complete. It is also not yet cleanly isolated.
The next step should be to turn the current working proof-term pieces into a
small transformation checker/elaborator with explicit inputs and outputs, then
fail closed for everything else.

## Source Linking and Original Megalodon Context

This remains the largest gap between the current state and the final
deliverable.

The project can now carry source ids and compare supported source formulas. It
can classify local facts, local definitions, global facts, generated facts, set
equalities, and conjecture facts. It can run source-map smoke tests and reject
several malformed source mappings.

What it does not yet do reliably is compose a checked Vampire refutation back
into the original Megalodon theorem command. That requires:

- resolving global lemma/definition names to actual Megalodon known facts;
- resolving local hypotheses by index and binder context;
- preserving local definitions introduced by proof commands;
- proving `set` equalities by reflexivity or conversion;
- representing generated facts with proof terms;
- handling the negated conjecture as a boundary, not as an arbitrary source
  axiom;
- converting refutation of the negated conjecture into the original goal;
- checking the final proof in the same context in which the theorem was
  stated.

This is not a small final printer task. It is an architectural milestone. The
source-context API should be implemented before the project tries to claim a
new 100-theorem result.

## Current Outlook

The project is viable if it stays disciplined. The worst next move would be to
chase a new 100/100 number by adding more benchmark-specific OCaml replay
heuristics. The best next move is to make the proof object smaller, more
explicit, and more checkable.

Recommended next work order:

1. Fix the current `hammer.10785.27/u287` AVATAR definition proof-term shape
   generally for quantified component clauses.
2. Fix `hammer.1009.43/u98` and `hammer.11145.52/u240` as proof-producing
   formula-orientation/Skolem transformation cases, using explicit Vampire
   metadata rather than library-specific recognizers.
3. Regenerate the broad fail-closed proof-term frontier with current Vampire
   and Megalodon heads.
4. Extract the clausal primitive checker/elaborator out of
   `vampire_cert_v1.ml`.
5. Extract the source/preprocessing transformation checker/elaborator out of
   the same monolith.
6. Extend Vampire's `MegalodonKernelSyntax` from rendered migration records to
   a typed primitive IR.
7. Add Vampire-side self-checks that each primitive expansion ends in the same
   clause or formula Vampire actually derived.
8. Implement the original source-context API and prove `set` equalities by
   reflexivity/conversion.
9. Demonstrate 10 live E2 exported-certificate proof-term reconstructions
   through the small primitive path.
10. Demonstrate 10 live E1 original-context theorem reconstructions.
11. Only then run a fresh held-out 100-theorem E1 gate.

The order matters. A broad run before the primitive IR and source-context
composition are stable mainly produces another diagnostic number. It does not
settle whether the project has achieved proof reconstruction.

## Recommended Questions for Expert Review

The expert should focus on these questions:

1. Is every counted proof-term mode mechanically free of certificate-derived
   `Known` facts?
2. Is `MegalodonKernelSyntax` becoming a typed primitive proof IR, or is it
   merely a helper for rendering string fields?
3. Can the native clausal checker be extracted from `vampire_cert_v1.ml`
   without pulling the old textual replay machinery along with it?
4. Is there a concrete source-context API that can reconstruct a proof of the
   original theorem, including local hypotheses, definitions, `set`
   equalities, and the negated conjecture boundary?
5. Are the current Smolka-style transformations proof-producing, or do any
   still rely on dynamic assumptions?
6. Does Vampire emit every datum needed for Skolemization: quantified prefix,
   dependencies, introduced symbols, sorts, source formula, target formula,
   and choice/definition justification?
7. Does Vampire emit every datum needed for paramodulation/superposition:
   equality side, target position, direction, substitutions, and result clause?
8. Is AVATAR being developed as a separate explicit proof layer, or is it
   drifting into broad Megalodon-side case analysis?
9. Are current fixes general over arbitrary Megalodon libraries, rather than
   optimized for the present hammer corpus?
10. Is the next 100-theorem gate held out enough to prevent overfitting?

## Final Assessment

The project has moved from an admitted, Python-assisted, source-linked skeleton
generator toward a real Vampire-certificate-to-Megalodon-proof-term pipeline.
That is the right direction. The current branch has better source metadata,
native proof-term checking, a stricter trust boundary, a separate kernel
vocabulary, and concrete focused successes on real hammer certificates.

The project is still not at the requested finish line. The biggest missing
pieces are:

- a typed Vampire primitive IR;
- a small extracted Megalodon primitive checker/elaborator;
- a clean proof-producing Smolka-style transformation layer;
- robust Skolem dependency and formula-orientation proof objects;
- an explicit AVATAR proof layer;
- final original-context theorem composition.

The current focused frontiers are encouraging because they are specific and
checkable. They should be used to guide implementation. They should not become
an excuse to grow another broad Megalodon-side reconstruction engine.

The success criterion remains E1: original Megalodon theorems reconstructed
from Vampire certificates with no hidden proof assumptions.
