## Executive Summary

The project has moved materially since the July 14 report and its audit, but it
is still not finished and should not be presented as a completed
Vampire-to-Megalodon proof reconstruction system.

The most important improvement is that we now have a real closed mode in the
Megalodon native certificate importer. A generated script is no longer counted
as a qualifying proof merely because Megalodon can check it with extra bridge
assumptions. Closed mode rejects bridge assumptions and other non-source
derived premises. This directly addresses the main audit criticism that earlier
`PASS` numbers were integration evidence, not actual reconstruction evidence.

The second important improvement is that source linking is now stricter and
more explicit. Exported THF problems carry origin metadata pointing back to the
original Megalodon obligation site. Generated reconstruction scripts carry
machine-readable `vampire_source_assumption` comments. Strict and closed modes
now reject several forms of source-map mismatch that were previously only
label-linked. The implementation can parse and compare a substantial fragment
of exported THF source formulas against native Vampire certificate formulas.

The third important improvement is the closed-pass frontier. The current best
validated source-linked closed cached replay has:

```text
CLOSED_PASS   95
EMIT_FAIL     30
CHECK_FAIL     4
CHECK_TIMEOUT  2
```

This run used cached native certificates and source-linked problems under
`/project/tmp`, with parallel emit/check replay. The relevant artifact is:

```text
/project/tmp/megalodon3_source_linked_closed_emit_250_logical_key.NOX8eg
```

Separately, the standard closed-corpus gate after the latest committed
Megalodon changes reported:

```text
CLOSED_PASS 157
```

from:

```text
/project/tmp/native_cert_v1_closed_after_logical_key.DWROVU
```

These are genuine improvements over the state described in the July 14 audit.
However, the numbers need careful interpretation. The 95-case source-linked
frontier is over a cached subset for which we already have Vampire certificates
and source-linked THF problems. It is not yet the original requested "100
arbitrary Megalodon theorems regenerated from source, proved by Vampire under
the agreed timeout, reconstructed into original-context Megalodon proofs, and
checked without any holes." It is closer to that goal than previous reports,
but it is still a frontier over a curated cached corpus.

The architectural risk identified by the audit remains. The project is now
mostly in OCaml and C++ rather than Python, but the Megalodon side is still
primarily a textual `.mg` proof-script generator. It is not yet a native
Megalodon proof-term elaborator returning `Syntax.tm * Syntax.pf`. The code is
therefore better than the earlier Python-heavy architecture, but it has not
fully reached the intended trusted structure.

The Prover9/Ivy lesson is also only partially implemented. Vampire now exports
a native S-expression certificate with rich metadata, and Megalodon imports it
directly in OCaml. But many difficult steps are still handled by large
Megalodon-side replay functions rather than by a small, explicit,
Prover9/Ivy-style sequence of primitive proof steps emitted from Vampire. The
next architectural step should be to stop broadening the Megalodon-side
heuristic/replay surface and instead define a smaller proof-object kernel for
the remaining hard classes: paramodulation/superposition, demodulation,
substitution, rectification, CNF/ENNF transformations, AVATAR, and
skolemization.

My bottom-line assessment is:

- The branch is now useful and materially more honest.
- Closed mode and stricter source checking are real progress.
- The current 95 source-linked closed frontier is a meaningful milestone.
- The work is still too textual and too Megalodon-side heavy.
- The remaining work should pivot harder toward a small Vampire-emitted proof
  object with exact substitutions, positions, pivots, and source-transform
  certificates.
- Full original-context reconstruction, especially for source theorem glue,
  set-generated facts, and skolemization, is still incomplete.

## Original Objective

The user's original objective was to take code from the Vampire repository for
proof reconstruction into Lean-like proof terms and port that idea to
Megalodon. The intended final system should:

1. Export Megalodon-generated THF problems.
2. Run Vampire on those THF problems with proof output.
3. Reconstruct Vampire's proof inside Megalodon.
4. Connect reconstructed proof steps back to the original Megalodon lemmas,
   definitions, local hypotheses, set-generated equalities, and conjecture.
5. Avoid `aby`, `admit`, or any other unchecked proof holes.
6. Assume classical reasoning is available, including excluded middle.
7. Use Megalodon's existing logical constants and equality where possible.
8. Handle source transformations such as FOOL, ENNF/CNF, skolemization, and
   definitions in a Smolka-style proof-producing way.
9. Test on at least 100 representative Megalodon theorems and their Vampire
   proofs.

Several additional operating constraints were established during the project:

- Use `/project/tmp` for temporary artifacts.
- Do not repeatedly rerun expensive Vampire searches; cache the solved THF
  problems and native certificates.
- Cap Vampire at 10 seconds.
- Parallelize Vampire/proof/checking work, typically 10 to 20 jobs.
- Do not use `aby` in resulting scripts; it is implemented as an admission.
- Treat `xm`, `or`, `false`, and equality as available from the Megalodon
  library/context.
- Avoid theorem-specific hardwiring.
- Prefer exporting more detail from Vampire over re-deriving proof choices in
  Python or another external script.
- Follow the Prover9/Ivy lesson: expand complex prover inferences into smaller,
  explicit proof objects where possible.

## Evolution of the Approach

### First Phase: Python Skeleton Reconstruction

The first working prototype used a Python script to parse a rich Vampire proof
output and emit Megalodon proof skeletons. This phase was useful because it
demonstrated:

- THF problems could be generated from Megalodon examples.
- Vampire could solve a nontrivial subset of them.
- Proof steps could be associated with Megalodon source names in many cases.
- Megalodon scripts could be generated as declarative `claim` blocks.
- Some FOOL, AVATAR, CNF, lambda, and source-linking problems could be explored
  quickly.

But the prototype had the wrong long-term trust shape. Python increasingly
contained proof-producing logic: matching formulas, guessing substitutions,
normalizing clauses, replaying propositional transformations, and choosing
source facts. This made it hard to tell whether a successful script reflected
Vampire proof detail, Megalodon proof checking, or a Python-side theorem prover.

The July 12 report already identified this risk. The later audits made it a
central objection.

### Second Phase: Native Certificates and OCaml Import

The project then moved toward a native certificate format. Vampire emits a
Lisp/S-expression-style certificate with explicit step constructors and
metadata. Megalodon parses that certificate directly in OCaml in
`src/vampire_cert_v1.ml`.

This was the right direction. It removed Python from the nominal qualifying
path, gave Megalodon access to structured proof records, and made it possible
to enforce a closed proof policy.

The native certificate records, among other things:

- input and formula-input source steps;
- clauses and formulas;
- variable sorts;
- step propositions;
- parent links;
- source names and source roles;
- function and predicate definition metadata;
- lambda/de-Bruijn metadata;
- Skolem dependencies and substitutions;
- AVATAR split/component/refutation metadata;
- replay extras for several Vampire transformations.

The Megalodon OCaml side now validates and emits Megalodon scripts from these
native certificates. This is substantially better than trying to reconstruct
all proof information from ordinary TPTP proof text.

### Third Phase: Closed Mode and Source-Linked Reproducibility

The July 14 audit correctly pointed out that "strict" did not mean "closed."
The previous strict mode checked certificate structure and some source-map
properties, but scripts could still pass Megalodon by adding bridge assumptions.

The branch now has `-vampirecertv1closed`.

Closed mode:

- implies strict certificate checking;
- fails emission if any bridge premise would be added;
- fails emission if any non-source derived premise would be added;
- reports successes as `CLOSED_PASS`;
- distinguishes ordinary integration `PASS` from qualifying closed passes;
- has positive and negative smoke tests;
- is used by cached parallel harnesses via `CLOSED_CERT_V1=1`.

This is one of the most important corrections in the whole project.

### Fourth Phase: Focused Replay of Frequent Closed Blockers

After closed mode, most candidate proofs failed because they still required
non-source derived premises. Work then focused on discharging frequent classes
inside the native OCaml replay path:

- FOOL boolean lifting and equality-to-true conversions;
- use of Megalodon's indexed classical axioms such as `dneg`;
- `vampire_xm` derivation;
- ENNF transformations such as `A -> B` to `~A \/ B`;
- negated implication transformations;
- existential ENNF;
- CNF projection and clause selection;
- nested universal binders under disjunction branches;
- predicate and function definitions;
- prop-valued and set-valued definition inputs;
- definition rewrite chains over generated definitions;
- guarded rectification;
- orientation-changing rectification under disjunction and existentials;
- substitution fast paths;
- lambda/de-Bruijn rendering discipline;
- Skolem replay via the existing `Eps_i` and `Eps_i_ax` machinery;
- nested and functional Skolem definitions for guarded set-valued cases;
- inequality name introduction and splitting.

This produced a real closed-pass frontier, not just a lower bridge count.

## Source Linking Status

Source linking has improved, but it remains one of the most important
unfinished areas.

### What Works Now

The exported THF problems now contain origin metadata of the form:

```text
% megalodon_origin ((file "...") (line "...") (char "...") (kind "..."))
```

This gives every generated problem a machine-readable anchor back to the
original Megalodon file and obligation location. For the current Hammer corpus,
many of these point into:

```text
/project/Megalodon/examples/hammer/100thms_12_h.mg
```

The source map also records symbol, definition, known theorem, conjecture, and
source-hash information. Generated Megalodon scripts now include comments such
as:

```text
// vampire_source_assumption (...)
```

These comments record:

- generated theorem parameter name;
- certificate step id;
- certificate source kind;
- TPTP source name;
- original Megalodon source name;
- source-map kind;
- source hash;
- source formula status;
- rendered proposition.

This is useful for human inspection and for future original-context glue.

Strict and closed modes now reject several source-map problems:

- a non-true certificate input mapped to a `$true` THF declaration;
- simple formula mismatches between hashed source formulas and certificate
  inputs;
- unsupported source formulas in closed mode.

The THF source parser handles a significant fragment:

- typed universal and existential binders;
- implication;
- conjunction;
- disjunction;
- negation;
- equality;
- application;
- THF lambdas;
- mapping THF lambdas to the same `vLAM` representation used in the native
  certificate.

### What Does Not Work Yet

The final target is not just to attach a Vampire source step to a THF name. It
is to fill the generated theorem assumptions from the original Megalodon
development:

- original lemmas;
- local hypotheses;
- local definitions;
- branch facts;
- source theorem/conjecture statements;
- generated `set` equalities;
- definitions unfolded from source commands.

That full original-context replay is not complete.

The current scripts are source-linked in the sense that they know which source
facts they are using and often carry the original origin metadata. But they do
not yet universally produce a Megalodon proof in the original local source
context with all source parameters filled by original claims.

The uncommitted `hammer.11231.17` experiment illustrates the problem. Vampire's
metadata proposition for a source/negated-conjecture step contained an extra
leading binder that was not part of the original THF conjecture. Stripping the
vacuous binder fixed one surface problem, but the generated proof still failed
at a rectification step because the source assumption and rectified certificate
shape differed. This shows that source linking needs a principled
alpha/rectification proof layer, not just text rendering.

### Set-Generated Equalities

The user pointed out that some TPTP axioms come from Megalodon `set` commands
and may not correspond to ordinary source claims. These should be proved
explicitly in Megalodon, often by reflexivity or unfolding.

The branch now handles several related classes:

- `definition_input` steps with function-definition metadata;
- set-sorted introduced symbols;
- arrow-valued set definitions;
- prop-valued predicate/function definitions;
- definition rewrite chains over generated definitions;
- some predicate definitions rendered directly from certificate ASTs.

These improvements close real cases. However, the treatment is still not a
complete general source-command reconstruction layer. The code recognizes and
replays guarded shapes. A future source-context pass should classify each
source-map entry into:

- original lemma/hypothesis;
- original definition;
- generated set equality;
- generated choice/skolem fact;
- generated logical/theory fact;
- unsupported source transformation.

Then each class should have an explicit Megalodon proof recipe.

## Skolemization Status

Skolemization has improved substantially but remains incomplete.

### What Works

The current Megalodon replay can handle several common Skolem forms by using
the existing Megalodon choice machinery:

- `Eps_i`;
- `Eps_i_ax`;
- a derived helper corresponding to existential choice.

The emitter can define Skolem constants and some Skolem functions as
Megalodon definitions using `Eps_i`. It can replay:

- one-variable existential skolemization;
- nested set-valued existentials;
- functional Skolem symbols whose arguments come from surrounding Vampire
  variables;
- some Skolem formulas under ENNF-transformed negated universals.

This is an important correction. Earlier experiments risked introducing new
local choice axioms. The current path uses the existing library choice
primitive, which is the right trust boundary.

### What Is Still Missing

The implementation is still guarded and shape-specific. It is not yet a full
Smolka-style skolemization certificate checker. Remaining issues include:

- prop-valued or higher-order Skolem forms outside the current guarded set
  fragment;
- multiple interacting Skolem dependencies;
- Skolem symbols introduced under richer FOOL/lambda transformations;
- proof objects explaining exactly which existential was chosen and under which
  context;
- connecting Skolem replay directly to original source theorem binders rather
  than only to the exported THF formula.

The desired endpoint is a certificate layer that records:

- source formula before skolemization;
- target formula after skolemization;
- introduced Skolem symbol and type;
- dependency variables;
- witness predicate;
- choice operator/axiom used;
- proof term or small proof-object steps that Megalodon can replay.

This should be emitted by Vampire or by the Megalodon exporter at the point
where the transformation is known, not guessed later from pretty-printed text.

## Smolka-Style Transformations

The term "Smolka-style transformations" in this project refers to
proof-producing transformations between the original higher-order/FOOL source
formulas and the first-order/clausal formulas used by Vampire's resolution
engine. Relevant transformations include:

- FOOL boolean lifting;
- equality-to-truth conversions;
- ENNF;
- CNF;
- existential/universal duality under negation;
- predicate definitions;
- definition unfolding/folding;
- Skolemization;
- lambda/de-Bruijn lowering;
- rectification;
- clausification and clause projection.

The branch now contains replay support for many common instances:

- FOOL truth equality helpers;
- `vampire_eq_prop` as proposition equality;
- `A -> A = True`;
- extraction of `A` from `A = True`;
- `A -> B` to `~A \/ B`;
- `~(A -> B)` to `A /\ ~B`;
- `~forall x, A x -> B x` to an existential/conjunction form;
- single and nested CNF projection;
- CNF clause permutation/selection for several shapes;
- predicate/function definition replay;
- definition rewrite chains;
- guarded rectification and equality orientation changes;
- guarded Skolem replay via `Eps_i`.

This is real progress. It is also where the implementation is most at risk of
becoming too large and too ad hoc. The current OCaml code often emits large
Megalodon proof terms as strings. For a few classes this is acceptable; for
the full transformation pipeline it will become brittle.

The Prover9/Ivy recommendation should now be applied more strictly:

- define a smaller kernel of transformation proof steps;
- have Vampire emit exact small steps, not summarized macro transformations;
- include substitutions, occurrence positions, directions, and pivots in the
  certificate;
- let Megalodon import those primitive steps mechanically.

## Equality

The current implementation uses Megalodon's ordinary equality for set-level
equalities. It also has a proposition equality wrapper/convention,
`vampire_eq_prop`, because Vampire's FOOL pipeline often treats formulas as
Boolean terms and rewrites equalities between propositions.

The right long-term story is:

- use Megalodon's equality directly wherever the term sort is `set` or another
  ordinary Megalodon object sort;
- use a proposition-extensional equality principle only where Vampire is
  explicitly reasoning about equality between propositions;
- avoid inventing an independent equality theory;
- make every use of proposition equality traceable to the existing classical
  or extensionality assumptions already present in the Megalodon environment.

Recent work improved this by using indexed/checkable Megalodon prelude
principles rather than arbitrary local assumptions. Still, proposition equality
is a sensitive area and should be reviewed carefully.

## Prover9/Ivy Analysis and Its Implications

The Prover9/LADR analysis under:

```text
/project/reports/PROVER9-IVY-ANALYSIS-2026-07-13.md
```

is central to the current direction.

The key lesson is that Prover9's Ivy output is not merely a pretty-printer for
the original proof. Prover9 first expands complex proof justifications into
more explicit clause-to-clause steps, then lowers those expanded steps into a
small Ivy kernel. For demodulation, for example, Prover9 stores enough data to
identify the exact parent demodulator, occurrence position, and direction. It
does not ask an external script to rediscover which rewrite happened.

For Vampire/Megalodon, the analogous plan should be:

1. Expand complex Vampire inferences inside Vampire, where the internal proof
   state is available.
2. Emit a small S-expression certificate over primitive proof operations.
3. Include exact substitutions, literal selections, pivots, equality
   orientations, and term positions.
4. Keep source transformations in a separate explicit layer.
5. Let Megalodon replay the primitive steps directly.

The current branch follows this in form, but not yet fully in substance.
Vampire emits a native S-expression certificate, and Megalodon imports it in
OCaml. But the Megalodon importer still contains a large amount of replay logic
for broad classes. That means we have not yet achieved the small-Ivy-kernel
architecture.

The expert reviewer should decide whether the current certificate constructors
are already a reasonable kernel or whether they should be collapsed/replaced by
a smaller set of primitive operations.

## Python Status

Python is no longer the nominal qualifying path for closed proofs. That is a
major improvement.

However, earlier Python tooling still exists and should be treated carefully.
It can be useful for:

- corpus inspection;
- summary generation;
- debugging;
- comparing generated scripts;
- staging experiments before moving detail into Vampire/Megalodon.

It should not be used to produce qualifying proof terms. No new proof-producing
Python logic should be added unless it is explicitly marked as diagnostic and
then migrated into the native certificate path.

The audits were right on this point. Moving from Python to OCaml is not by
itself enough if the OCaml code simply becomes a new large heuristic
reconstructor. The real target is structured certificate replay.

## Megalodon-Side Implementation Status

The central file is:

```text
/project/Megalodon/src/vampire_cert_v1.ml
```

It currently performs several roles:

- parses native Vampire S-expression certificates;
- validates certificate structure;
- parses source maps;
- compares source formulas for supported THF fragments;
- manages symbol/type environments;
- renders Megalodon definitions;
- renders Megalodon theorem statements;
- emits proof prelude helpers;
- emits proof claims;
- replays many Vampire transformations;
- rejects non-source assumptions in closed mode.

This is powerful but too much responsibility for one module. The code should be
split conceptually, and ideally physically, into:

- certificate syntax/parser;
- certificate validator;
- source-map/source-context binder;
- primitive proof-step elaborator;
- transformation-certificate elaborator;
- Megalodon proof AST builder;
- optional textual `.mg` pretty-printer.

The audit specifically noted that the desired endpoint should look more like:

```ocaml
val elaborate : source_context -> certificate -> Syntax.tm * Syntax.pf
```

That is still the right endpoint. The current implementation generates strings
and then invokes Megalodon checking on those strings. This is acceptable as an
intermediate debugging route, but it is not the clean final architecture.

## Vampire-Side Implementation Status

The relevant Vampire code is in the Megalodon checker/export path, especially
the native certificate emitter. Recent Vampire-side work added:

- source roles and source metadata;
- Megalodon origin metadata;
- mirrored replay extras;
- Skolem dependency data;
- AVATAR parent links and SAT origins;
- actual predicate definition symbols;
- definition role preservation;
- guards around legacy JSON diagnostics.

This is the correct kind of Vampire-side work. The remaining issue is that the
certificate may still be too high-level for hard inferences. For several
classes, Megalodon has to do substantial reconstruction from a summarized
certificate step.

The next Vampire-side extensions should not simply add more pretty-printed
metadata. They should produce more atomic proof objects:

- superposition/paramodulation with exact side, substitution, equality parent,
  target parent, rewritten position, and direction;
- demodulation/definition rewriting with exact occurrence positions;
- resolution/factoring with pivot literal, substitution, and result literal map;
- AVATAR SAT proofs as small propositional proof traces;
- rectification as explicit alpha-conversion maps;
- skolemization as explicit choice-witness transformations;
- CNF/ENNF as structured transformation derivations rather than final source
  and target strings.

## Current Open Technical Problems

### 1. Original-Context Glue

The generated proof knows which source assumptions it depends on, but it does
not yet universally plug into the original Megalodon theorem context.

The remaining work is to generate, for each original theorem obligation, a
Megalodon proof script or proof term that:

- imports or opens the original context;
- names local hypotheses and local definitions correctly;
- proves generated set equalities by reflexivity/unfolding;
- supplies the conjecture and negated-conjecture source assumptions in the
  correct polarity;
- discharges source assumptions from actual Megalodon facts rather than leaving
  them as theorem parameters.

This is the core "glue to original lemmas and defs" task.

### 2. Source Formula Canonicalization

The current source formula comparison handles a large THF fragment but is not a
complete canonical binding to original Megalodon syntax. The best final design
would resolve source identifiers directly to Megalodon `Syntax.tm`, or else
compare independently computed canonical formula hashes generated from the same
syntax on both sides.

Textual `step_proposition` metadata is useful for diagnostics but should not be
trusted as the source proposition without structural validation.

### 3. Rectification and Alpha Conversion

Rectification appears repeatedly. Some cases are closed, but not all. The hard
cases combine:

- repeated Vampire variable names under different binders;
- lambda/de-Bruijn aliases;
- equality orientation changes;
- extra metadata-only binders;
- source theorem assumptions whose binder shape differs from the rectified
  Vampire formula.

This should become a small explicit proof object, not an accumulation of
rendering rules.

### 4. Paramodulation and Superposition

Paramodulation/superposition remains a major blocker and a source of
timeouts. Some generated proof terms are too large or too difficult for
Megalodon to check efficiently.

The Prover9 path suggests the right fix:

- export exact paramodulation positions and substitutions from Vampire;
- split large proof terms into small checked intermediate claims;
- avoid rebuilding huge disjunction eliminators as one large textual term;
- eventually construct Megalodon proof ASTs directly.

### 5. AVATAR

AVATAR remains underdeveloped for closed proof reconstruction. The certificate
contains more AVATAR metadata than before, including parent links and SAT
origins, but closed mode still rejects many cases with derived AVATAR
components or splits.

The right approach is likely a small propositional proof trace:

- split introduction;
- component clauses;
- SAT assumptions;
- conflict clauses;
- RUP-like or resolution-like SAT proof steps;
- final contradiction mapping back to first-order clauses.

OCaml-side SAT checking is not enough if the result is still introduced as a
theorem premise. The SAT proof must be replayed into Megalodon proof terms or
small claims.

### 6. Performance

The user repeatedly objected to slow sequential iteration, correctly. The
project now mostly uses cached parallel harnesses, but generated proof checking
can still be slow for large textual proofs.

Current policy should remain:

- solve once with Vampire under the 10-second cap;
- cache solved THF and native certificates;
- run emit/check in parallel, 10 to 20 jobs;
- avoid full aggregate sweeps after every small edit;
- focus on representative large/frequent classes;
- use small focused checks while developing a rule;
- run aggregate gates only after a rule is plausible.

The deeper performance fix is to avoid giant generated proof terms and move
toward small claims or native proof AST construction.

### 7. Generality and Overfitting

There is still a real overfitting risk. The work has used the Hammer corpus
heavily, especially examples from `examples/hammer/100thms_12_h.mg`.

Some names such as `famunion` are not supposed to be hardwired theorem hacks;
they appear because they are exported symbols from the Megalodon library and
source map. But the reviewer should still audit for accidental hardcoding.

The right standard is:

- no theorem-specific line numbers in replay logic;
- no hardcoded source theorem names;
- no hardcoded formulas from individual examples;
- library symbols may appear only through source maps, symbol declarations, or
  ordinary context lookup;
- every reconstruction rule should be expressed over certificate constructors
  and term structure.

## The Interrupted Source Formula Experiment

Immediately before this report, I was working on `hammer.11231.17`, one of the
remaining `CHECK_FAIL` cases.

The old failure was in the generated theorem/source assumption:

```text
Type Error found prop expected set
```

The diagnosis was that structural rendering of a source formula reused a
Vampire variable name under the wrong binder sort. The native certificate's
`step_proposition` text for the source input looked more readable and avoided
that immediate type error.

I tried an uncommitted patch that made `FormulaTermInput` prefer
`metadata_step_proposition` and strip leading metadata-only binders. This:

- rebuilt successfully;
- emitted `hammer.11231.17`;
- removed the theorem-statement type error;
- still failed at claim `u222`, where a rectified target formula no longer
  matched the source assumption by `exact`.

This is useful negative evidence. It shows that source propositions should not
be recovered by simply swapping between AST rendering and metadata text. The
proper fix is:

1. render source assumptions structurally from the certificate/source AST;
2. choose binder names with correct scoped sort discipline;
3. separately prove rectification/alpha-conversion steps;
4. compare source formulas against original THF/Megalodon syntax.

The uncommitted patch should either be reverted or replaced by that structural
fix. It should not be committed as-is.

## Relationship to the July 14 Audit

The July 14 audit said the project was improving but not yet controlled. Its
main criticisms were:

1. strict mode still allowed bridge premises;
2. bridge counts undercounted non-source premises;
3. source-linked meant label-linked, not proposition-linked;
4. the OCaml switch was partial because the emitter still generated text;
5. scope had expanded beyond the MVP;
6. Python was not fully quarantined;
7. evidence was not reproducible enough;
8. the next milestone should be ten committed, reproducible,
   source-semantically-linked first-order proofs with zero non-source premises.

Current status against those criticisms:

- Bridge premises: addressed by `-vampirecertv1closed`.
- Non-bridge derived premises: addressed in closed mode; derived inputs such as
  AVATAR components and definition inputs are rejected unless explicitly
  replayed.
- Source proposition checking: partially addressed; several mismatches are now
  rejected, and unsupported formulas are rejected in closed mode, but full
  original `Syntax.tm` binding is not done.
- OCaml/text issue: not fully addressed; the importer is in OCaml but still
  emits textual proof scripts.
- Scope: still broad; the code covers many classes, and the MVP needs to be
  reasserted around a smaller kernel.
- Python: improved; Python is not in the counted closed path, but old tooling
  exists and should stay diagnostic.
- Evidence: improved; closed corpus and cached artifacts exist, but a fully
  committed reproducible 100-case source-linked proof suite is not yet present.
- Ten-case milestone: surpassed numerically in closed-pass tests, but the
  stricter "source-semantically-linked original-context" interpretation is not
  fully satisfied.

So the project has responded to the audit, but the audit's architectural
concerns remain relevant.

## Recommended Next Work

### 1. Stabilize the Current Branch

Before more feature work:

- decide what to do with the uncommitted `FormulaTermInput` experiment;
- either revert it or replace it with a structural binder fix;
- rerun `./makeopt`;
- rerun native smoke and closed-corpus gates;
- commit only validated changes.

### 2. Define the Small Certificate Kernel

Write a short certificate-kernel specification for the next phase. It should
list primitive steps and required fields, for example:

- input/source;
- alpha/rectification;
- equality symmetry;
- equality congruence;
- paramodulation at position;
- resolution;
- factoring;
- substitution/instantiation;
- definition unfold/fold at position;
- CNF projection;
- ENNF transformation;
- skolem choice;
- AVATAR propositional step.

For each rule, specify:

- parents;
- target;
- side conditions;
- exact metadata fields;
- Megalodon proof recipe;
- whether Vampire or Megalodon is responsible for computing it.

### 3. Move Hard Inference Detail Back Into Vampire

The next Vampire work should target the largest remaining bridge classes:

- paramodulation/superposition;
- resolution/factoring;
- substitution;
- AVATAR;
- skolemization;
- rectification.

The goal is not more pretty strings. It is exact operational data:

- substitutions;
- literal indices;
- term positions;
- equality direction;
- selected pivots;
- instantiated parent clauses;
- before/after terms.

### 4. Build Native Megalodon Proof ASTs

The long-term Megalodon importer should elaborate to internal proof structures
rather than generate huge strings. The textual `.mg` file should remain a debug
view, not the primary representation.

This would help:

- performance;
- hygiene;
- binder correctness;
- avoiding precedence/parsing bugs;
- source-context integration.

### 5. Finish Original-Context Source Glue

For a selected small closed corpus, generate proofs that actually plug back
into the original Megalodon file/theorem context. The first target should be a
small number of source-semantically linked examples, not another broad bridge
reduction.

Each generated proof should show:

- original source theorem/obligation;
- original local facts;
- original definitions;
- generated set equalities proved by reflexivity/unfolding;
- conjecture/negated-conjecture bridge handled correctly;
- no `aby`;
- no `admit`;
- no bridge premise.

### 6. Improve the Test Suite

The test suite should be layered:

1. Parser and certificate validation unit tests.
2. Source-map negative tests.
3. Closed-mode negative tests for every forbidden derived premise class.
4. Small committed closed corpus.
5. Source-original-context corpus.
6. Cached broad frontier replay.
7. Optional fresh Vampire regeneration under 10 seconds and parallelism.

The expensive fresh Vampire stage should not be run during every edit.

   first: paramodulation, resolution/factoring, AVATAR, skolemization, or CNF?

## Outlook

The project is now in a substantially better state than it was at the time of
the first report. The strongest improvements are:

- native Vampire certificates;
- OCaml import in Megalodon;
- real closed mode;
- stricter source checking;
- parallel cached test harnesses;
- a nontrivial source-linked closed frontier;
- guarded replay for many FOOL, ENNF, CNF, definition, rectification, and
  Skolem classes.

The project is still not at the final target. The biggest remaining risks are:

- textual proof generation;
- incomplete original-context source glue;
- incomplete source semantic binding;
- paramodulation/superposition proof size and detail;
- AVATAR proof reconstruction;
- too much Megalodon-side reconstruction logic instead of Vampire-side
  expansion into primitive proof objects.

The recommended direction is not to chase a few more closed passes by adding
more local rendering heuristics. The better next step is a controlled
architectural milestone:

```text
Produce a small committed suite of original-context,
source-semantically-bound, closed Megalodon reconstructions using a documented
primitive certificate kernel.
```

After that, broadening to 100 proofs becomes a scaling problem. Without that
milestone, more closed-pass counts may still hide source-glue or architecture
debt.

## Bottom Line

The project is progressing, and the current branch contains real proof
reconstruction improvements. The July 14 audit forced a necessary correction:
we now distinguish integration success from closed reconstruction success.

At the same time, the expert should not approve the project as complete. The
right review question is now narrower and more technical:

```text
Is the current native certificate plus OCaml replay path close enough to a
small, trustworthy proof-object architecture, or should the next iteration
stop broad rule work and redesign the certificate kernel around
Prover9/Ivy-style primitive steps?
```

My recommendation is the latter: keep the current closed-mode infrastructure,
but use it as the test harness for a smaller and more explicit proof kernel.
