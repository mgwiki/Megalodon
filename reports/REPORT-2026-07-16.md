## Executive Summary

The project is not finished. It should not yet be described as a complete
Vampire-to-Megalodon proof reconstruction system for larger Megalodon
developments.

The July 15 audit was correct: the project had reached meaningful closed
reconstruction evidence, but it was still architecturally too Megalodon-side
heavy. The broad OCaml textual replay engine had grown into a second
reconstruction prover. The audit recommended freezing broad replay growth,
preserving the existing work as a regression oracle, and moving toward a
Prover9/Ivy-style path:

1. Vampire expands complicated internal inferences while it still has the exact
   proof data.
2. Vampire emits small primitive certificate steps with parents, positions,
   substitutions, selected literals, source bindings, and result clauses.
3. Megalodon checks those primitive steps mechanically and elaborates them into
   native proof terms, ultimately `Syntax.tm * Syntax.pf`.

The work since that audit is mixed, but more aligned than before.

The good news is that the branch now contains a real native proof-term seed:
`-vampirecertv1corepfcheck`. This mode constructs and checks `Syntax.pf`
objects for a growing clausal core fragment. It no longer only emits textual
`.mg` scripts. It requires source files and origin metadata, checks source
bindings, records source propositions, and rejects unsupported core proof
steps instead of falling back to the broad textual emitter. This directly
addresses the audit's central request to start moving from
`certificate -> string` toward native proof terms.

The second improvement is that more detailed primitive data is now being pushed
from Vampire. The Vampire branch has commits emitting typed equality in
primitive certificates, explicit vLAM binders, equality-factoring side terms,
sorts for subsumption primitive expansions, indexed primitive detail,
superposition substep variable sorts, and metadata for native and side
substitution helpers. This is the right direction: the checker should receive
the local proof facts from Vampire, not rediscover them with heuristic OCaml or
Python code.

The third improvement is that the latest live strict 100-case regenerated run
is stronger than the previous source-linked frontier. The artifact:

```text
/project/tmp/live_strict_100_after_fool_demod_fix
```

has:

```text
PASS 100
```

and its rule-count profile includes:

```text

substitute               397
equality_resolution      317
factor                    57
fool_atom_lift          1300
skolem_formula            77
avatar_split              57
step_extra              6626

```

The important qualification is that the full command exited nonzero after the
100 certificates passed because the final metadata audit was too strict about
empty `substitute` aliases. It required instantiation metadata even for
identity `(subst)` alias steps that do not perform a real instantiation. The
current uncommitted audit-script change corrects that policy to require
metadata only for non-identity substitute steps. That audit-policy adjustment
still needs a clean rerun and commit.

The fourth improvement is a current uncommitted Vampire-side fix for a
representative demodulation/rewrite case, `hammer.11453.77.th0`. The failure
was not best solved by guessing in Megalodon. The fix tracks the target literal
index through the emitted primitive rewrite chain and emits explicit
`equality_symmetry` and `paramodulate` substeps before the final alias step.
That is exactly the Prover9/Ivy pattern: expand a compound rewrite into
smaller primitive equality steps while Vampire still knows what happened.

The bad news is that the main qualifying path is still not fully transformed.
The broad textual emitter in `src/vampire_cert_v1.ml` remains large and still
does too much. Full original-context reconstruction is not complete. The live
100-case evidence is still primarily exported-THF-bound closed proof evidence,
not proof terms inhabiting original Megalodon theorems in their original local
contexts. Smolka-style preprocessing, especially skolemization and the exact
source-to-clause chain, is only partially handled. Set-command equalities still
need clean original-context glue as reflexivity facts. AVATAR and many
preprocessing transformations remain outside the small native proof-term core.

My current assessment is:

- The project has made real progress after the July 15 audit.
- The branch now has a native `Syntax.pf` proof-term seed, not only a textual
  proof-script emitter.
- The Vampire side is now contributing richer primitive metadata, which is the
  right architectural direction.
- The live 100-case regenerated certificate check is an important regression
  milestone, but it is not final completion.
- The next phase must be stricter: grow the small-kernel proof-term path and
  Vampire primitive expansion, not the broad OCaml textual replay engine.
- The project still needs Tier 1 original-context proofs before it can be
  called finished.

## The Original Objective, Restated

The user asked for a full port of Vampire proof reconstruction to Megalodon,
inspired by Vampire's Lean proof output and by the Megalodon proof-term style.
The expected finished system should:

1. Export Megalodon goals to THF/TPTP.
2. Run Vampire on those THF problems, with a short timeout and parallel
   execution.
3. Ask Vampire to emit sufficiently rich proof objects.
4. Reconstruct/check those proofs in Megalodon.
5. Connect proof inputs to original Megalodon theorem statements, lemmas,
   definitions, local hypotheses, set-generated equalities, and conjecture
   negations.
6. Avoid `admit`, `aby`, and `-allowincompleteqed`.
7. Assume classical reasoning, including `xm`, is available from the context.
8. Use Megalodon's real equality and logical constants, not duplicated private
   encodings.
9. Handle FOOL, CNF, ENNF, rectification, definitions, skolemization, and other
   source transformations in a proof-producing way.
10. Test on at least 100 representative Megalodon theorems and their Vampire
    proofs, using THF.

Additional working constraints were established during the project:

- use `/project/tmp` for temporary files;
- run Vampire for at most 10 seconds per problem;
- parallelize search/checking, typically 10 to 20 jobs;
- avoid repeatedly rerunning unsolved Vampire searches;
- do not optimize for a fixed library theorem list;
- recover original names from the export/source map rather than hardwiring
  specific examples;
- do not add new proof-producing Python logic;
- do not let broad pass-count chasing substitute for architectural progress.

The current branch satisfies some of these requirements only partially. It has
parallel THF/Vampire/Megalodon harnesses, proof-hole rejection, strict source
checking for supported exported formulas, a 100-case regenerated strict live
artifact, and a native proof-term seed. It does not yet provide complete
original-context proof reconstruction over larger developments.

## What Changed Since the July 15 Audit

### 1. The audit response was accepted as controlling

The July 15 audit's core criticism was not ignored. The current branch begins
with `audit-response-2026-07-15.md`, which agrees that:

- closed textual evidence is useful but not final;
- the broad importer should not keep growing as the main path;
- `coreclosed` and native proof terms should become the center;
- Vampire should emit exact primitive data;
- original-context source glue is required before Tier 1 success can be
  claimed.

This matters because it changes the intended scoreboard. A larger number of
textual closed passes is no longer the main target. The target is now:

1. original-context, source-bound, closed proof terms;
2. exported-THF-bound closed proofs;
3. synthetic/core closed proof terms;
4. integration proof scripts with bridges.

The current branch has meaningful Tier 2 and Tier 3 evidence. It still has
little or no Tier 1 evidence.

### 2. Native `Syntax.pf` core checking now exists

The command-line option:

```text
-vampirecertv1corepfcheck
```

now exists in `src/megalodon.ml` and uses `check_propofpf` to check the native
proof term produced by `src/vampire_cert_v1.ml`.

The public type in `src/vampire_cert_v1.mli` includes a native proof object:

```ocaml

```

The smoke suite contains positive and negative tests for this path. The
covered seed cases include:

- unit resolution;
- binary/unit resolution;
- binary/binary-style resolution fragments;
- duplicate factoring;
- identity substitution;
- explicit instantiation substitution when enough metadata is present;
- rejection of non-identity substitution without explicit proof data;
- equality resolution over typed Megalodon equality;
- equality symmetry;
- unit equality paramodulation;
- negative-target paramodulation;
- subsumption resolution;
- binary-target paramodulation;
- longer-clause paramodulation;
- equality factoring;
- source-origin requirement checks.

This is the first real answer to the repeated audit demand for
`Syntax.tm * Syntax.pf`. It is still a seed, not the whole system, but it is an
actual native proof-term path.

Important limitations:

- It is not yet the main path for the 100-case live corpus.
- It does not cover all broad certificate constructors.
- It does not yet elaborate full preprocessing and source transformation
  certificates.
- It is still connected to exported source metadata, not fully to original
  Megalodon local contexts.

### 3. Primitive metadata audits were tightened

The post-audit branch added more audit pressure around native primitive data.
In particular, live runs default to substitute-metadata auditing:

```text
AUDIT_SUBSTITUTE_METADATA=1
```

The intention is correct. Non-identity substitute steps should not be accepted
as opaque clause changes. Vampire must emit:

- parent unit;
- parent clause;
- explicit substitution;
- substituted parent literals;
- result clause;
- primitive-expansion contract.

The current uncommitted fix clarifies the boundary:

- non-empty/non-identity `substitute` steps need instantiation metadata;
- empty `(subst)` alias steps do not.

That correction avoids a false failure in the latest 100-case strict live run.
It does not weaken the important requirement that real instantiations be
explained by Vampire.

### 4. FOOL typed/untyped boolean lift mismatch was fixed locally

The latest strict 100-case run originally had five FOOL failures in cases such
as:

```text
hammer.1110.18
hammer.1114.18
hammer.1118.18
hammer.1122.18
hammer.11574.100
```

The failure was a mismatch between an untyped `$true = X` or `$false = X` FOOL
shape and the typed Megalodon `PROP` equality-to-true lift used by the checker.

The current uncommitted Megalodon change extends `typed_fool_bool_lifts` so the
left-constant equality shape is normalized in the same typed way as the
right-constant shape. This is a small checker normalization fix, not a
theorem-specific patch.

### 5. Demodulation/rewrite expansion moved further into Vampire

The remaining focused failure was:

```text
hammer.11453.77
```

The failing internal step was `u484`, a `kernel_v1` rewrite/demodulation case.
The earlier emitter tried to find the current target literal by string in the
intermediate clause after each rewrite. That failed because the rendered target
literal changes during the primitive chain.

The current Vampire-side fix tracks the target literal index through the
generated primitive chain. For `u484`, the emitted proof now contains explicit
primitive steps shaped like:

```text
equality_symmetry "u484_symmetry"
paramodulate "u484_paramodulate0"
paramodulate "u484_paramodulate1"
substitute "u484" ... (subst) ...
```

This is exactly the kind of change the Prover9/Ivy analysis recommends.
Vampire knows the rewrite sequence and can emit the local primitive proof
object. Megalodon should not try to infer a multi-step demodulation path from
before/after clauses.

### 6. Rewrite metadata validation was adjusted to match primitive expansion

The Megalodon strict checker previously expected a `kernel_v1` rewrite record
to correspond directly to the final step ID as a single `paramodulate`.

That is too rigid for a Prover9-style expansion where a macro step may emit:

- helper symmetry;
- one or more primitive paramodulations;
- final chain-closing alias.

The current uncommitted Megalodon change still checks that the explicit
rewrite described by the metadata appears as a primitive `paramodulate` step,
but it allows that primitive step to be a prefixed substep of the macro rather
than the final macro ID itself.

This is an architectural improvement, provided it remains coupled to strong
metadata checks. It lets Vampire decompose a macro into a chain without making
Megalodon rediscover the macro.

## Current Architecture

The current architecture has four layers:

1. Megalodon exports THF/TPTP problems.
2. Vampire solves them and emits a native S-expression certificate.
3. Megalodon imports the certificate in OCaml.
4. Megalodon either:
   - emits/checks a generated `.mg` proof script through the broad textual path;
   - or, for the core seed, constructs and checks a native `Syntax.pf`.

The broad textual path remains useful because it provides:

- a large regression oracle;
- examples of formulas, names, and transformations seen in real Vampire
  proofs;
- a way to inspect generated scripts;
- a bridge from exported THF certificates to Megalodon checking.

But it should no longer be the main design target. Its risks are now well
understood:

- it centralizes too many responsibilities in one OCaml file;
- it uses formatted proof source rather than native proof objects for most
  cases;
- it contains many normalization and replay functions;
- it tempts the project into pass-count-driven special cases.

The native `corepfcheck` path is the better target:

- parse certificate;
- validate source binding;
- validate primitive metadata;
- build `Syntax.tm` propositions and `Syntax.pf` proofs;
- call `check_propofpf`;
- fail explicitly on unsupported rules.

The intended final architecture should make that native path the primary
qualifying path. The textual emitter can remain as a diagnostic and regression
tool, but should not define success.

## Relationship to Prover9/Ivy

The Prover9/LADR inspection remains the best architectural guide.

Prover9's Ivy export is not just a pretty-printer. It first expands the
ordinary Prover9 proof into more atomic proof steps and then lowers those
steps into a small Ivy kernel. For example:

- demodulation is expanded into explicit paramodulation-like steps;
- resolution is decomposed through explicit instantiations and pivots;
- paramodulation is emitted with exact parent and position data;
- substitutions are printed explicitly;
- final substeps preserve useful original proof IDs.

The Vampire/Megalodon project should copy this division of labor:

- Vampire does the proof detailing while internal data is still present;
- Megalodon checks a small certificate;
- no external script re-runs proof search or guesses missing substitutions.

The current branch now has several examples of this:

- typed equality emitted by Vampire;
- explicit equality factoring side terms;
- primitive substitution-helper metadata;
- superposition substep variable sorts;
- demodulation expanded into primitive equality/paramodulation substeps.

However, the implementation is not yet a clean `expandProofForMegalodon`
module. Much of the logic is still embedded inside the large
`MegalodonChecker.cpp` exporter. The next Vampire-side improvement should be
to factor primitive proof expansion into a more explicit internal layer, closer
to Prover9's `expand_proof` plus `expand_proof_ivy` split.

## Original-Context Linking

This remains one of the largest incomplete areas.

The project currently has meaningful exported-source linkage:

- THF source files contain origin/source-map comments;
- certificate source steps carry source roles and names;
- strict mode checks that source declarations exist;
- supported exported THF formulas are parsed and compared structurally to
  certificate inputs;
- source-origin metadata can be required;
- `corepfcheck` requires source files and origin metadata.

This is not the same as original-context reconstruction.

What the current evidence proves in the best Tier 2 cases is roughly:

> The Vampire certificate refutes assumptions matching the exported THF problem
> under the supported source-map checks.

What the final goal requires is:

> The reconstructed proof inhabits the original Megalodon theorem in the
> original Megalodon context, using the original lemmas, local hypotheses,
> definitions, generated set equalities, and conjecture negation.

Remaining source-glue tasks include:

- mapping exported TPTP names back to original Megalodon declarations without
  relying on hand-coded names;
- using original `Syntax.tm` propositions where possible instead of re-parsing
  exported THF as the final authority;
- handling local theorem contexts and local hypotheses;
- connecting generated conjecture negation to the original theorem statement;
- resolving definitions from the original environment;
- proving set-command-generated equality axioms by reflexivity rather than
  expecting original named claims;
- identifying which logical/library axioms are allowed by hash/name and
  resolving them from the Megalodon basis.

The branch has started the necessary machinery, but it does not yet close this
loop.

## Set-Command Equalities

The user pointed out a specific issue: some TPTP axioms come from Megalodon's
`set` command and may not correspond to ordinary named claims. In the common
case these are equalities and should be provable in Megalodon by reflexivity.

Current status:

- exported source-map/source-role machinery can classify some definitions and
  equality-shaped sources;
- strict formula comparison prevents arbitrary source-name attachment;
- the final original-context proof path for set-generated facts is not done.

The required final behavior should be:

1. The exporter records that a TPTP axiom came from a `set` command or an
   equivalent definitional environment action.
2. The importer recognizes it as a generated definitional/reflexive equality,
   not as an unsupported extra theorem premise.
3. The native proof-term path constructs the equality proof directly, normally
   by reflexivity or definitional conversion.
4. The result is used as a real source proof in the reconstructed theorem.

This is a high-value next target because it is narrower than full
skolemization and would improve Tier 1 source glue.

## Skolemization

Skolemization is still not solved at the level required for final completion.

What exists:

- Vampire certificates include `skolem_formula` steps and Skolem-related
  metadata in the broad certificate vocabulary;
- Megalodon has existing choice/epsilon-style facilities such as `Eps_i` and
  `Eps_i_ax`;
- earlier work explored nested and functional Skolem definitions;
- the broad textual path can pass cases containing `skolem_formula` records,
  as shown by the 100-case artifact's `skolem_formula 77` count.

What is missing:

- a small, specified skolemization certificate rule;
- source formula before skolemization;
- target formula after skolemization;
- dependencies of the Skolem symbol on surrounding universal variables;
- witness/choice proof generated as a native `Syntax.pf`;
- proof that the generated Skolem symbol is connected to Megalodon's
  permissible choice principle;
- original-context handling for Skolem symbols introduced during THF export or
  Vampire preprocessing.

The right design is a separate Smolka-style transformation layer rather than
folding skolemization into the clausal inference kernel. The clausal kernel
should check resolution, factoring, paramodulation, equality, and explicit
instantiation. The preprocessing layer should certify transformations from
source formulas to clauses, including skolemization, ENNF, CNF, FOOL, and
definitions.

Current status: skolemization is handled well enough for some exported-THF
closed textual certificates, but not as a general native original-context proof
transformation.

## Smolka-Style Transformations

The phrase "Smolka-style transformations" in this project refers to
proof-producing transformations from higher-level formulas to the clausal forms
Vampire uses. The relevant transformations include:

- FOOL boolean lifting;
- implication and negated-implication normalization;
- ENNF;
- CNF projection and clause extraction;
- rectification;
- definition introduction and unfolding/folding;
- lambda/vLAM representation;
- skolemization;
- conjecture negation;
- set-generated definitional equalities.

Current progress:

- FOOL boolean/literal lifting has many working cases and the latest
  left-constant equality normalization fix addresses a real live failure;
- ENNF explicit existential binder handling has improved;
- explicit vLAM binders and lambda certificate terms are now emitted and
  parsed;
- CNF and formula-clause records are carried in the broad certificate;
- source formula checking prevents unsupported source syntax from silently
  passing strict mode;
- native preprocess primitive bridging exists, but is still not the final
  `Syntax.pf` transformation layer.

Current gaps:

- transformations are still too often validated or replayed as part of the
  broad textual path;
- many transformation steps are not yet native proof terms;
- the system does not yet provide a clean composition from original theorem to
  clauses and from refuted clauses back to the theorem;
- skolemization and definition unfolding/folding need more exact Vampire-side
  metadata.

The correct next step is not to add more broad transformation heuristics. It is
to define a small set of transformation certificate records and elaborate them
to `Syntax.pf` in Megalodon, with Vampire/exporter metadata sufficient to make
the check local and deterministic.

## Equality

The project previously had concern about using an ad hoc equality rather than
Megalodon's real equality. The direction has improved.

Current positive facts:

- typed Megalodon equality is used in native proof-term equality-resolution,
  equality-symmetry, equality-factoring, and paramodulation cases;
- Vampire emits typed equality in several primitive certificate contexts;
- the native core proof-term checker rejects some old untyped equality forms
  instead of silently proving with the wrong equality;
- current uncommitted Vampire code extends typed equality handling in
  equality-swapping helpers.

Remaining concerns:

- old untyped `TMH "="` compatibility paths still exist in the broad textual
  system;
- all new primitive certificates should prefer typed Megalodon equality;
- equality hashes should be centralized rather than copied in local lambdas;
- final original-context proofs should resolve equality from Megalodon's
  context/library, not from a private certificate convention.

The audit direction remains: use Megalodon's real equality directly and make
Vampire emit it with enough type information.

## Python and JSON

Python remains present in the repository as legacy and diagnostic tooling. It
is not the qualifying path described by the current reports.

The current accepted path is:

```text
Vampire native S-expression certificate
-> Megalodon OCaml parser/checker
-> textual closed script or native Syntax.pf core proof
-> Megalodon checker
```

No new proof-producing Python work should be added. Python can remain useful
for:

- summarizing corpora;
- counting rule classes;
- comparing artifacts;
- assisting migration;
- debugging output.

It should not reconstruct missing proof steps or generate accepted proof terms.

JSON is also not the preferred future certificate shape. The current native
S-expression direction is better matched to Megalodon's syntax infrastructure
and to the Prover9/Ivy precedent.

## Test Harness and Performance

The testing approach has improved since the early slow loops.

Current expected testing style:

- export or reuse a fixed problem list;
- run Vampire with `VAMPIRE_SECONDS=10`;
- run with `JOBS=10` to `JOBS=20` where appropriate;
- keep all generated artifacts under `/project/tmp`;
- avoid repeated unsolved Vampire searches;
- separate focused failing-case runs from broad coverage audits;
- use live regenerated runs for current-branch evidence;
- use cached corpus runs for regression evidence.

The latest 100-case artifact followed this style:

```text
LIMIT=100
JOBS=20
VAMPIRE_SECONDS=10
WALL_SECONDS=15
WORK_DIR=/project/tmp/live_strict_100_after_fool_demod_fix
```

The remaining harness issue is that broad audit thresholds are sometimes not
appropriate for small focused slices. For example, a six-case targeted run can
pass all six certificates but fail a primitive coverage audit because the slice
does not contain a factor example. Focused runs should either set matching
minimums or skip broad coverage audits, while full gates should keep them
enabled.

## Current Problems and Risks

### 1. Original-context reconstruction is still incomplete

This is the most important correctness gap. Exported THF source linkage is not
the same as original Megalodon proof reconstruction.

### 2. The broad OCaml importer is still too large

The branch now has a native proof-term seed, but the large textual importer is
still present and still tempting. It should be stabilized and used as an
oracle, not expanded as the main path.

### 3. The native `Syntax.pf` path is not yet broad enough

The core proof-term checker covers useful seed rules, but the live 100-case
run is still not primarily a native proof-term run. This must change before
the project can be considered architecturally converged.

### 4. Preprocessing transformations are not yet a small certified layer

FOOL, CNF, ENNF, rectification, definitions, and skolemization are still too
intertwined with the broad importer. They need explicit certificate rules and
native proof-term elaboration.

### 5. Vampire exporter organization is still monolithic

`MegalodonChecker.cpp` contains a lot of exporter and expansion logic. The
work is moving data into Vampire, which is correct, but it would be cleaner to
factor a dedicated primitive proof-expansion layer.

### 6. Some current fixes are uncommitted

The latest FOOL/demodulation/audit-policy fixes have not yet been committed at
the time of this report. They have focused and 100-case evidence, but need a
clean rerun after the audit-policy adjustment and local commits in both
repositories.

### 7. Test evidence is strong but still narrower than final scope

The 100-case live run is valuable. It does not prove the system works
completely on larger Megalodon developments or produces original-context proof
terms for arbitrary supported Vampire proofs.

## Outlook

The project is still viable. It has solved several early trust-boundary
problems:

- Python is no longer the qualifying proof path.
- Closed mode rejects bridge and derived assumptions.
- Source formulas are checked for the supported exported THF fragment.
- A native `Syntax.pf` core proof-term path exists.
- Vampire is emitting more exact primitive proof data.
- A 100-case regenerated strict certificate run now checks.

But the final target remains ahead:

- proof terms must attach to original Megalodon contexts;
- set-generated facts need reflexivity proof glue;
- skolemization needs a real certificate and choice proof;
- preprocessing needs a small Smolka-style proof-producing layer;
- the native proof-term path must become the qualifying path for real
  corpora;
- Vampire primitive expansion should be factored and made systematic.

The right next move is not another week of broad OCaml textual replay growth.
The right next move is a controlled native-kernel milestone:

1. cleanly commit the current primitive metadata and 100-case audit fixes;
2. produce ten original-context native proof-term reconstructions;
3. expand Vampire proof steps into small-kernel certificates where needed;
4. only then rerun larger held-out live corpora.

If the project follows that path, the existing branch becomes a valuable
regression oracle and source of hard examples, while the trusted architecture
converges toward the intended Vampire-emitted Prover9/Ivy-style certificate
and Megalodon-native proof-term checker.

## Bottom Line

The current project state is better than the July 15 audited branch in one
important way: there is now a real native proof-term seed and more Vampire-side
primitive detail. The current state is also better operationally: the latest
strict live 100-case artifact has all 100 certificates passing Megalodon
checking after the focused FOOL and demodulation fixes.

It is still not finished. The system has not yet demonstrated complete
original-context proof reconstruction over larger Megalodon developments.
The next work should be judged by whether it reduces that gap, not by whether
it adds another textual replay case to the broad importer.
